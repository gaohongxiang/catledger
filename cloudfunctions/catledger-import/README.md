# catledger-import

账单导入事件云函数。MINI-1905/1906 在这里实现多文件上传意图、逐文件私有云存储读取和解析、FinanceUpdate 来源冻结、跨来源 EconomicEvent/Evidence/Relation 整理、ReviewIssue、服务端 postability 与整批原子入账。

当前支持支付宝 App/Web CSV、微信支付 CSV/XLSX，一次最多选择 5 个文件。每个文件独立上传、解析、失败、重试或移除；所有成功批次再组成一个 FinanceUpdate。稳定共享标识且核心字段一致的跨来源证据才允许自动归组；同额、近时或文本相似只生成候选。退款、转账、还款保留专门经济性质和关系，不再降级成逐行 `post/skip`。

退款关系统一由 `RefundRelationPolicy` 冻结候选：先校验来源/账户上下文、币种、发生顺序、时间窗口、金额和累计可退余额，再按稳定来源标识、明确退款金额凭据、规范化商品标题、同来源同商户四层取最高非空层。只有前两层唯一候选可自动确认；商品标题和同商户候选始终人工核对。商品标题会做 Unicode 规范化并去掉“退款”“全款交易”等业务前缀，因此平台聚合商户与实际退款商户不同但商品、金额、账户和时间一致时仍可找到原消费。问题详情、客户端和保存动作不得扩大候选，服务端只接受当前 ReviewIssue candidate 成员中的 proposed 关系。

排除原因是事件领域数据，不是 UI 文案推断结果。账户归属步骤排除事件时同时记录 `manual_exclusion` 与 `account_mapping_excluded`；关闭、失败、重复入账等沿用各自原因码。客户端据此生成默认收起的审计分组，原始 Evidence 始终保留。

退款在整理页逐笔直接展示，每笔独立打开，不再经过汇总入口或处理后自动跳到下一笔。零候选时，用户可明确选择“暂记待关联退款”：FinanceUpdate 以结构化 `refundRelation=pending` 保存决定，posting 写成原消费为空的标准退款交易，只增加到账账户余额，不计收入、不冲减支出、分类或趋势。以后可在交易明细用 `transactions.linkRefund` 选择真实原消费；服务端重新校验用户、版本、类型、时间、金额和累计退款上限，只补关系与分类并写审计链接，不再次改变余额。手工新建退款仍必须当场关联原消费。

幂等分两层：接口回执按用户和客户端 `requestId` 重放；领域 `FinanceAction` 按用户、`updateId`、动作类型和动作请求去重。同一内容重新开始时可以复用不可变 ImportBatch，但新 FinanceUpdate 必须拥有独立动作域，不能与已放弃更新的审计动作冲突。

支付账户使用明确的三层领域模型：`AccountIdentity` 表达现实账户，`PaymentReference(sourceType + paymentMethodKey)` 表达来源账单中的精确引用，`AccountDecisionGroup` 表达用户只需回答一次的账户问题。带银行主体和稳定尾号的同一卡可跨来源共享 `AccountIdentity`；支付宝余额、余额宝、花呗、微信零钱等平台账户按来源隔离；空值和无尾号银行卡/信用卡泛称证据不足，不跨来源合并。一个账户决定会展开写入组内全部精确 `PaymentReference`，因此界面不重复提问，同时证据和正式映射仍能逐来源追溯。

原始支付方式只作证据；支付宝、微信组合字段含 `&` 时，规范层只取第一段作为主资金账户，后续成分不参与账户命名或映射；平台自有账户统一补归属前缀（支付宝账户余额、支付宝余额宝、支付宝花呗、微信零钱、微信零钱通等），已经包含银行主体的名称保持原样。内部转账的一条原始记录可以同时产生独立的 `from`、`to` 引用，例如“余额宝转出到余额”是 `支付宝余额宝 → 支付宝账户余额`，“微信零钱提现”是 `微信零钱 → 到账银行卡`；每个 ReviewIssue 携带 `fundsSide(from/to)` 决定写回哪一端，禁止用原始支付方式列猜测转出端或把一个选择写到两端。

账户裁决只有一处策略实现，固定优先级为“唯一规范全名推断 < 历史映射 < 本批选择 < 本事件手工选择”；同级不同结果回退为一个开放问题，绝不按 SQL 或数组返回顺序取最后一条。仓储只返回全部事实，planner、账户确认后的增量重算、整理处理和 posting 共用这套语义。解析器不会创建账户；用户可以选择已有账户、明确创建、仅本次不计入，或对有稳定映射键的具体支付工具选择“以后默认不计入”。默认忽略不会静默过滤后续账单，下一次仍显示可编辑的账户归属项并允许改选账户。账户映射和后续默认忽略先以 `mapping_action = account / ignore` 写入 FinanceUpdate 草稿，再只在最终确认事务中提升到 `catledger_import_account_mappings`；放弃或失败不会留下规则。

支付宝付款行里的`花呗`和具体机构`信用购`是独立的真实负债账户；还款行里的`花呗｜信用购`是平台合并账单引用，不是第三个账户，也不生成账户映射。整理器把它投影为还款分配问题，并把当前 FinanceUpdate 内同渠道、同聚合族的原子账户冻结为该事件唯一候选；客户端只能展示这组候选，不能追加全账本的其他信用账户。用户可以把全额归到一个候选账户或按金额拆给多个候选账户；服务端验证候选成员关系、账户唯一、有效、类型相容、不同于付款账户且整数分合计严格守恒。最终一个 EconomicEvent 可生成多笔 `repayment_allocation` transfer，并在同一个 posting 事务中一起成功或一起回滚。

部署和运行本候选必须先应用连续、可重入迁移 `0004`～`0008`。`0006_unified_finance_updates.sql` 会为旧已提交单文件建立只引用原交易的历史 FinanceUpdate 投影，不会重复创建正式交易；`0007` 建立正式账本写屏障，`0008` 允许 FinanceUpdate 草稿安全表达账户映射或永久忽略。开发云已登记这些迁移；其他环境仍必须以各自迁移登记表为准，不能仅凭本地文件判断。

运行时使用与 `catledger-api` 相同的私密 MySQL 变量：`CATLEDGER_DB_HOST`、`CATLEDGER_DB_PORT`、`CATLEDGER_DB_USER`、`CATLEDGER_DB_PASSWORD`、`CATLEDGER_DB_NAME`。不得把这些值写入仓库、客户端或日志。

部署入口为 `index.main`，只作为 CloudBase 事件函数由登录后的小程序调用，不配置 HTTP 触发器。函数通过 VPC 访问 MySQL，并需要开启公网出站以读取私有云存储对象；成功入账、重复内容裁决或放弃后会尽力删除原始对象，清理失败时保留可重试状态。
