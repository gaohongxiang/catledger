## 1. 最终产品决定

**一笔贷款/分期、一份完整方案、一张逐期表；每项费用只记一次，每笔付款只记一次。用户不必每期导入，更不必找齐旧账单。**

系统分别保存合同/计划、费用记账依据、真实付款及其关联，但用户在同一个详情页处理。计划不直接变成已发生流水；明确授权后的方案记账是可核对的正式记录，不冒充银行凭证。

| 问题 | 确定的规则 |
| --- | --- |
| 创建时是否一次记完未来利息 | 不默认这样做。完整总成本一次展示；未来未到计费日的费用仍在计划中 |
| 固定费用没有月度账单怎么办 | 用户一次明确授权后，按已确认方案及计费日记息/费；已到期漏月可自动补齐，注明“按确认方案记账，未与账单核对” |
| 用户没有授权 | 只生成缺项预览，允许一次批量确认，不逐期询问、不强迫上传文件 |
| 用户不想补历史 | 选择明确起算日和当前基准；此前缺失不补造，既有记录保留，之后按授权继续 |
| 导入后面一期能否判定前面已还 | 不能。后一期本身不是前期计费或还款凭证；补费依据来自有效授权，已还依据来自付款/明确人工确认 |
| 后来有银行账单 | 同一费用复用并升级核对依据；差额先展示影响、确认更正，不能再新增一份总额 |
| 没有关联贷款能否入账 | 明确资金/费用事实可先记一次并待关联；事实本身不清楚才待核对 |
| 谁决定余额和统计 | 仍由正式 Transaction 聚合；贷款明细、计划和期次不能再叠加一份余额 |

这是一套个人记账产品口径，不宣称是企业财务报表的利息摊销准则。方案记账会影响正式支出和对应负债，所以金额、覆盖范围、起算日、费用账户、分类及授权必须可解释；不能默认替用户开启。

## 3. 从创建到结清的主流程

### 3.1 建立本金：先区分四种起源

| 起源 | 正式账务 | 贷款管理 |
| --- | --- | --- |
| 新现金借款/信用卡现金分期 | 有实际到账才复用或新增一次“负债 → 资产”转账，不计收入 | 建立本金、合同和计划 |
| 已记信用卡消费转分期 | 原消费和欠款保留，不再产生消费、放款或本金转账 | 将既有债务纳入分期计划，不新建虚构账户 |
| 以负债支付的新消费且尚未记账 | 按真实消费凭据记一次，不能免掉原消费或逐期重记本金 | 保存其后偿还方案 |
| 已还一部分的历史接入 | 优先关联已有记录；确认本金/账户基准，不补造放款 | 保留原方案、历史进度及未补资料范围 |

支持同账户多贷款和一个账单分期覆盖多笔消费；不强迫每笔分期对应唯一一笔消费，不按模糊标题猜归属。银行列出的本期本金可能只是原本金转为到期应还，不能据此再增加整笔债务或伪造银行卡扣款。

### 3.2 一次建立完整计划

保存原本金、总期数、计费方式、费用起算/计费日期、还款日、逐期本金/利息/费用、一次性费用及适用的优惠；采用既有整数分计算与舍入规则。总成本和还款合计可立即展示，不等于已记费用。

计费日与还款日分开；仅知道扣款日而不知道费用发生日时，不随意补历史计费日期。可以由用户明确确认采用的记账日期约定，并标注方案依据。未知分项不是零；有明确逐期表时优先采用确认值，利率等只作推算依据。浮动利率或不确定费用不进入无条件自动补费。

新方案、调整后的方案有生效范围和版本。已经记账的期次不因重算计划被覆盖；修改计划只改变尚未记账的有效区间，历史金额更正另走影响预览与确认。

### 3.3 记费用与付钱分开

有明确实际计费/付息凭据时，只确认尚未记录的同一费用。已有完整方案且用户授权自动记费时，到计费日也可以形成方案来源的费用记录，之后等待核对。

**自动记费只增加费用及对应信用/贷款负债，不自动从银行卡扣款，不自动偿还本金。** 此规则适用于同意按费用应计方式记账的固定方案；只按实际扣款确认且未授权应计的产品保留计划/待确认，不猜扣款。资产类账户不能作为无付款凭据的自动扣款端点。

实际一次性收取的全期费用，只建立一个覆盖明确范围的费用事实；逐期表可以显示其分摊，但分摊行不再次记费用。仅有“预计总利息”不能被标为已一次收取。实际预扣费用、提前结清费、罚息等按明确事实处理，不并入未经确认的固定周期费用。

### 3.4 实际还款与分配

优先复用已导入或手工记录的真实付款；没有记录且用户确认发生了付款，才创建一次。付款总额、账户、时间和本金/利息/费组成必须守恒。

未记过的利息随付款确认支出；已由实际账单或授权方案记入负债的同一费用，付款只清偿，不再计支出。一笔付款可以部分/跨期偿还，已分配本金与各费用不得超过本次付款或相应未清偿余额。

信用卡整单还款先作为账户间转账成立；只有银行明确分配、可靠协议或用户明确确认时，才能归属到具体分期/期次。金额相同不能把整笔还款复制挂给多笔分期。分配不清楚不改变已确定的银行卡转账事实，但期次保持待核对。

### 3.5 出账、付款和证据分别显示

期次至少区分“未到期/已出账”“未确认还款/部分还款/已还/已取消”与“账单已核对/按方案记账/人工确认/资料不足”。不用一个 paid 字段同时表达这些事实；可按现有表的最小字段扩展，界面不必显示多套复杂状态机。

出账、收到本期本金行、计了本期利息，都不能自动标已还。已还应由有效付款分配、明确银行结清证据或用户明确确认产生；第 N 期已付不推断前 N-1 期全部已付。

保留“确认已还至 N 期”的批量入口，列出范围和保留的未还/部分未还异常。只改管理进度时明确不生成资金流水；需要补付款时另外确认账户/金额/日期和是否已在账本中。未知日期不能默认为计划日期并标成银行事实。

贷款剩余本金优先由明确基准及实际本金变动/分配计算；仅有人工进度可给出带标识的计划估算，不能伪装成已核对本金，也不能改账户余额。缺凭据不等于逾期；过应还日且有明确未还依据才显示确定逾期，否则提示还款待确认。

## 4. 用户漏月、不补文件与不补历史

### 4.1 自动记费的授权边界

授权至少绑定：可信用户、贷款/既有方案身份、方案版本、生效起止、费用分类与负债账户、明确计费日期规则、固定分项、历史处理选择及确认时间。允许暂停/撤销后续授权；撤销不删除此前已入账记录。账户停用、合同归档/结清、方案变更、来源冲突时停止受影响范围，不自动改用其他账户。

用户可选择：

- **从确认起算日继续记费，不补更早历史。** 起算日包含当天；此前缺失仅保留完整性提示，不反复催交文件。
- **按方案补齐一段已发生月份。** 一次预览月份、每月费用、合计、已有记录和对余额/统计的影响，用户确认后执行；已有有效授权范围内的正常漏月不重复询问。

同一贷款接入本金基准和费用起算范围是两个字段，不能相互推导。账户期初余额若已经包含历史利息/欠款，相关费用应标明被基准覆盖，不能再以历史补记增加一份负债；覆盖不明确时只询问这一处，不强制用户提交原账单。必要的历史账本重建需单独预览，不能用余额调整掩盖重复。

### 4.2 漏月示例（合成）

已记原消费 6,000 元，12 期、每期本金 500 和利息 20。用户确认固定方案并授权从 1 月计费，假设 1～4 月计费日已过、无减免或结清：

| 资料 | 处理结果 |
| --- | --- |
| 1 月账单已入账 | 20 元保留，不重复 |
| 2、3 月没有文件 | 各补 20 元到原计费月份，标记方案来源、未核对 |
| 4 月账单到达 | 已按方案记过就关联核对，没记过就记录一次 |
| 以后月份尚未到计费日 | 仍是计划，不提前记费用 |

四个月合计 80 元，而不是导入 4 月后再加 80 或 240 元。缺少 2、3 月文件不阻止继续；4 月账单也不证明前面已经还款。用户选“从 4 月继续、不补历史”时，只有起算范围内的费用可补记，更早已存在的 1 月记录仍保留。

同一授权下补齐到某日，只处理计费日不晚于服务端允许截止日的缺项。后面一期来源可触发查缺，但不能代替有效授权或覆盖历史边界。

### 4.3 不使用小程序时如何执行

第一版采用**使用时补齐到当前日期**，不承诺后台定时器：进入贷款或账本、刷新相关页面、导入完成后，由客户端在有效授权和登录会话下调用专用同步命令，再读新摘要。每次只同步到服务端确定的当前业务日；长期未打开时，下次补齐，记账发生日回到各原计费日期，创建时间保留实际同步时刻。

不能把写入藏进 `loans.get/list`、统计 GET、缓存命中、导出分页或 `buildView`。首页/统计先协调一次同步再刷新；失败保留旧结果并提示“费用同步未完成”，不能展示“截至今天已完整”。普通读仍保持纯读，已生成导出因实际数据修订按原规则失效重做。

补齐可用有界批次执行，所有入口共用单飞与持久原请求机制。每个批次原子写入，失败不产生半个费用；跨多个批次已完成部分必须如实显示，不宣称整个历史同步全局原子。继续/重试仍靠费用级唯一性和原回执保护，不无限等待全部贷款。原账单导入的整批原子事务不因此拆开。

### 4.4 例外不强求文件

实际与方案不一致、提前结清、浮动利率、退费减免或罚息时，暂停受影响分项，用户可直接确认实际金额/新计划，无须上传原文件。固定正常部分继续，歧义部分单独列出。

用户不补历史付款时，可以从明确当前本金与账户基准继续。历史完整性显示“未补齐”；不得把全期预计利息或人工进度说成全部历史费用/流水已经核实。

## 5. 防重复、后导入核对与删除

### 5.1 三种身份不能混用

**费用身份、文件来源身份、付款身份分别保留。** 多份来源可以证明同一费用；一笔费用可以被多次部分偿还；一次付款也可以跨多项费用/本金分配。

方案费用防重需要用户范围内的稳定费用键，绑定原方案的明确收费项及覆盖范围。不要把金额、请求号或当前 planVersion 当唯一键：金额更正/方案修订/换 requestId 不能让同一费用再生成一次。一次性费用与它的期次分摊共用覆盖关系，不能分别收费。

最低目标是每个确定收费项至多一个活动确认记录，来源和后续调整可多条。来源编号仍按用户、账户、来源类型隔离；同一期合法追加费或两条不同银行收费不能只因金额相等被去掉。

### 5.2 两个先后顺序都成立

| 顺序 | 必须得到同一账务结果 |
| --- | --- |
| 先方案记费，后导入相同实际费用 | 在明确合同/期次/分项/覆盖范围一致时复用，补来源并标已核对 |
| 先导入费用，后建立贷款或启用方案 | 先核对已有覆盖，吸收记录，只补缺项 |
| 多设备同时补费，或补费与导入并发 | 用户锁和数据库唯一约束保证一次；一方重读/重放，不能各记一次 |
| 20 元方案记录，实际为 18 元 | 预览原月份支出、负债、已分配付款及依赖；确认后更正/调整净额 -2，不能另记 18 |
| 一次性 240 元已覆盖全期，后来展示每期 20 元 | 关联/展示分摊，不能再记 12 次费用；确属另一新增收费则独立核对 |

没有明确归属时保留候选，不模糊合并。导入流程中的“待核对费用差异”不是普通历史重复的自动排除；没有实现新关联路径前，不能临时绕过 `LOAN_SOURCE_MISMATCH` 或整组维护保护来获得绿色测试。

### 5.3 已记费用与实际付款不能重复消耗资金

方案记费对应“费用 + 负债”，付款对应“资产减少 + 负债清偿”。普通贷款某次本金 500、已记利息 20：转账清偿 520，实际本金仅减少 500；若利息从未记过且本次实际支付，才拆为本金转账 500 和资产端费用 20。同一利息不得在负债端及资产端各记一次。

按方案记录不会产生真实银行扣款证据。付款关联必须限制同一费用/本金的累计清偿，保持整组金额、账户与版本一致。计划费用核对成功并不自动确认其付款。

### 5.4 归档、删除与费用回收

归档管理记录终止后续自动记费并解除允许解除的管理关联，但已记消费、费用、付款、来源与历史授权保留。不删除收费覆盖凭据；重新建贷款时不能因 loanId 变化把同一合同已记费用再次自动生成。无稳定编号时需要用户明确认领原资料与覆盖范围，不能猜同一合同。

手工删除一条方案费用后，保留该收费项的抑制/撤销标记；自动同步不能把它悄悄复活。重新补记必须显式确认并可追溯。删除一份导入证据不自动删除独立授权产生的费用，删除/更正有付款或退款依赖的费用仍走受保护的完整操作。

提前结清取消未发生的未来费用，不伪造退款；已实际退还的费用才冲回。商品退款、合同取消、管理归档和贷款结清是不同动作，不自动互相替代。

## 6. 展示与数据的最小调整

详情顶部保留账户、原本金、原/当前方案总成本；中间显示确认的剩余本金、已记费用、其中待核对方案费用、下一期应还；下方仍为一张逐期表。正常用户不额外打开三套记录页。

按方案费用与银行核实费用可以共同计入用户授权的记账统计，但显示来源构成，不能统一称“银行已核实实际支出”。现金流只来自有付款依据的资产端流水；预计后续还款不要与账户负债重复累加。

优先复用现有 loans、periods、installment_items、payments、transactions 和回执。必须有持久化的授权范围、费用覆盖/核对状态、收费键及停用标记、付款分配、历史接入依据与必要审计；不能只存在页面内存或 local storage。

Astra 在第一阶段依据真实 schema 冻结最小字段/约束方案，可扩展现有表或增加确有必要的收费登记表，不为每个概念单建表。收费唯一键和付款/来源关系必须由 MySQL 约束兜底；两云函数共用规则仍按现有独立打包一致性检查，不能跨部署包 require。

自动费用计入正式交易后，还要覆盖普通明细分类/删除、导入维护、现金与负债约束、读取修订、导出 manifest、最小角色权限和旧回执重放。新 origin/核对字段如必要，应显式升级公共契约，不能借用 import/manual 字段让新记录伪装旧来源。

## 7. 旧数据迁移

先在隔离副本清点四类：人工确认进度、真实付款分配、仅由来源最大期号推算的进度、已记费用及关联覆盖。保留旧 progress、来源、金额及原始规则/版本依据。

来源推算不再作为已还证据；界面保留“旧规则推算，待核对”的历史依据。明确人工确认和实际付款不清零，明确未还/部分未还异常不被覆盖。旧代码若无法区分单期确认扩散成 through 与用户真正批量确认，保留旧值供一次核对，不臆造确认范围。

**旧贷款默认不开启自动记费，不批量补历史，不按新规则重写历史真实交易。** 用户接入新规则时确认起算日、已有余额/费用覆盖和需要补的区间。新写入可能按授权归属过去月份，这是新目标的显式操作，不是迁移时偷偷回写。

迁移向前、可重入；回退先暂停新费用同步，保留已记交易和审计。不得回滚到不识别新费用关系的旧写接口去解除保护；保留只读或明确阻断直至兼容恢复，不用删数据完成代码回退。

### A0 冻结的实现契约（2026-09-26）

沿用现有用户锁、Transaction、付款/期次与原请求回执。新增连续迁移 0026：`loan_charge_contracts` 保存与管理 loanId 分离的收费合同身份、方案版本、明确起源、授权/计费日期及起算范围；`loan_charges` 以 `(uid,contract_id,charge_key)` 唯一标识收费项，键不含金额、请求号或方案版本；`loan_charge_sources` 连接原分期来源；`loan_charge_allocations` 连接既有真实付款；`loan_charge_audit` 只追加授权、覆盖、修订和停用依据。所有表使用 `catledger_` 前缀和用户范围外键。合同编号按账户隔离；无编号的归档重建必须显式认领旧合同，不能生成新身份绕过已有覆盖。

收费项包括逐期 interest/fee 和明确的一次性收费；一次性覆盖通过 `covered_by_charge_id` 指向同一实际收费，不再生成分摊交易。历史基准覆盖保留为 `baseline` 状态；删除保留 `suppressed`，调整/取消保留审计。方案交易显式使用 `origin=loan_plan`，普通只读接口不产生交易。授权绑定已确认固定金额、日期规则、负债账户及分类，旧贷款默认无授权；服务端业务日固定 Asia/Shanghai。有界同步每批最多 40 项，批内原子，原 requestId 可查回执，后续批次重读缺项。

导入仅在合同/收费项及范围明确一致时认领；实单差额走独立影响预览和确认，不改变原始银行金额，不放宽 `LOAN_SOURCE_MISMATCH`。付款端的 accrued 必须逐项绑定未清偿收费，既有本金与期次分配继续校验。普通修改、删除、分类、退款、导入维护、更正/撤销付款均检查收费关系；导出 manifest 与本机最小角色随迁移更新。

旧 `progress_json` 和接入历史保留；来源期号只表示出账。新进度写入区分单期和明确批量，旧无法确定的 through 标为待核对，实际付款分配继续有效。收费起算范围不从本金基准或已还期数推导。主负责人为当前会话，串行维护迁移/共享契约、两函数、客户端、验收和现行文档；两个旧 worktree 不参与本轮实现。
