# 微信小程序架构设计

> 状态：设计稿，待所有者确认  
> 前置：本设计基于《个人财务用户需求.md》第 12 章，并将定位从「个人使用优先」升级为「面向公众运营获客」，确认后需同步修订需求文档第 12 章与业务规则文档第 1 章「当前不开发微信小程序」的表述  
> 日期：2026-08-19（2026-08-20 修订：主体定为个人主体，变现定为流量主广告，新增 4.1 广告位设计与 M3 变现里程碑）

## 0. 决策摘要

| 决策项 | 结论 | 理由 |
| --- | --- | --- |
| 产品定位 | 面向公众运营获客，小程序为未来主客户端 | 所有者确认；Web 保留为打磨期与重度操作客户端 |
| 部署路线 | **微信云托管 + 云 MySQL**（第 12.4 节路线 B） | 免域名备案（省 1–3 周关键路径）；项目已有 Dockerfile；`callContainer` 内网直连低延迟；标准 MySQL 可随时迁出，无锁定 |
| 技术栈 | **uni-app 3（Vue 3 + TS + Vite CLI 模式）+ Pinia + TDesign uni-app** | 与现有 Vue 3/Pinia/TS 代码同构，service/model/presentation 层可直接复用；微信单端编译最成熟；CLI 工程化不依赖 HBuilderX |
| 后端 | 现有 Go 单体不动主体，仅新增微信登录端点与配置 | 遵守仓库硬约束：模块化单体、不引入第二套账本、不用云开发重写 |
| MVP 范围 | 总览 + 记一笔 + 下一笔待还 + **账单上传与整理待办**（所有者确认导入是主要场景） | 对应需求文档「手机现在必须能」三场景加核心差异化能力 |
| 账号体系 | 微信登录（openid）为主，复用 `UserExternalAuth` 表与现有 JWT 体系 | 新用户零门槛进入；存量 Web 账号可后续绑定打通 |
| 主体与变现 | **个人主体 + 流量主广告变现**（累计独立访客 UV ≥ 500 即可开通） | 所有者确认为个人开发者、以广告变现为目标；个人主体可开通流量主，按月结算到本人银行卡 |

## 1. 总体架构

```
┌─ 微信客户端 ─────────────────────────────────────────────┐
│  小程序（uni-app 编译产物）          Web PWA（现有前端） │
│  主包：登录/总览/记一笔/待办        打磨期与重度操作    │
│  分包：账单整理/账户/贷款/设置                          │
└────────────┬───────────────────────────┬────────────────┘
             │ callContainer（免域名备案）│ HTTPS（云托管公网默认域名）
┌────────────▼───────────────────────────▼────────────────┐
│  微信云托管：ezbookkeeping 单容器（现有 Go 二进制+静态） │
│  ├─ REST API（现有，含 personalfinance 扩展）           │
│  ├─ 新增：微信小程序登录端点                            │
│  └─ 云 MySQL（复用现有三库兼容代码）                    │
└────────────┬────────────────────────────────────────────┘
             │ code2session / 订阅消息（服务端调用微信 API）
┌────────────▼────────────────────────────────────────────┐
│  微信开放平台（AppID + Secret）                          │
└─────────────────────────────────────────────────────────┘
```

关键原则：

- **后端只是又多了一个客户端**。所有业务端点、数据模型、`personalfinance` 命名空间、uid 隔离、三库兼容约束全部原样有效。
- 小程序不引入 BFF 层、不引入云函数；`callContainer` 直达同一个 Gin 进程，避免任何第二套逻辑。
- SQLite → MySQL 只是部署配置切换与一次数据迁移，代码零改动（`user_data export/import` 命令，开工时验证）。

## 2. 后端改造（最小集合）

### 2.1 微信登录端点

新增一个未登录端点，复用现有 JWT / TokenRecord 体系：

```
POST /api/wechat_miniapp/authorize.json
Body: { "code": "<wx.login 下发的 code>" }
Resp:  { "token": "<NORMAL JWT>", "user": {...}, "isNewUser": bool }
```

流程：

1. 服务端用 code + AppId + Secret 调 `code2session` 得 `openid` / `session_key`；
2. 查 `UserExternalAuth`（provider 扩展一枚举值 `wechat_miniapp`，openid 存外部标识），命中即签发 NORMAL token；
3. 未命中：创建新用户（username 自动生成如 `wx_{openid前8位}`，昵称占位），写入 `UserExternalAuth`，签发 token；
4. `session_key` 不下发给客户端（仅服务端留存，供后续解密手机号等，落库需加密）。

改动面预估：`pkg/api/authorizations.go` 附近新增 handler、`pkg/services/tokens.go` 复用签发、`conf` 新增 `miniapp_app_id` / `miniapp_app_secret`、`UserExternalAuth` provider 枚举加一值。**不触碰核心账本与 PF 契约。**

存量 Web 账号打通（二期）：`UserExternalAuth` 已支持一个用户绑定多个外部认证，做一个小程序内「绑定已有账号」入口即可，数据结构无需再动。

### 2.2 部署与数据

| 项 | 方案 |
| --- | --- |
| 容器 | 复用现有 Dockerfile；云托管要求监听 `$PORT` 或 8080，ezbookkeeping 默认 8080，仅需确认配置注入方式 |
| 数据库 | 云托管 MySQL 8；新建空库 + 跑现有迁移；存量个人数据用 `user_data export/import` 迁入（保留本地 SQLite 实例作为灾备） |
| 公网 Web | 云托管默认公网域名直接可访问，Web 端配置里切换 API 地址即可；自定义域名需备案，非首期必需 |
| 密钥 | AppSecret 走云托管环境变量注入，不进仓库 |
| 备份 | 云 MySQL 自动备份 + 定期 `user_data export` 到对象存储，沿用《个人财务运维与备份.md》思路 |

### 2.3 需要为小程序侧微调的现有端点（开工时逐项确认）

- 文件上传：`/personal_finance/import_files/upload.json` 已是 multipart，`wx.chooseMessageFile` → `uni.uploadFile` 可直接对接，预期零改动；
- 图片与地图代理的 JWT query-string 认证方式小程序同样可用；
- 长时任务轮询（导入 process）对移动端足够，无需 WebSocket。

## 3. 小程序端架构

### 3.1 工程位置与代码复用

仓库内新增 `miniprogram/` 子项目（uni-app CLI），与现有前端并列：

```
miniprogram/
├── src/
│   ├── pages/            # 主包页面（见 3.2）
│   ├── subpackages/      # 分包
│   ├── api/              # request 封装（uni.request）+ 按 service 复制的调用层
│   ├── stores/           # Pinia（登录态、总览缓存、账单整理状态）
│   ├── shared/           # vite alias → ../../src/features/personal-finance/**
│   │                     #   直接引用 models.ts / presentation.ts（纯 TS，无 DOM 依赖）
│   ├── components/
│   └── static/
├── manifest.json         # AppID、权限、隐私接口声明
└── package.json
```

复用策略（这是选 uni-app 的核心收益）：

- **直接引用（零拷贝）**：`src/features/personal-finance/**/models.ts`（DTO 类型）、`presentation.ts`（金额/日期格式化、可信度文案等纯函数）；
- **改造后复用**：`service.ts` 里的接口路径、参数组装逻辑保留，axios 调用替换为统一 request 层；
- **不复用**：Vue 组件（Framework7/Vuetify 与小程序组件不兼容，重写 UI）。

### 3.2 页面与分包（主包严控 < 1.5MB）

**主包（TabBar 四页）**：

| 页面 | 内容 | 对应 API |
| --- | --- | --- |
| 总览 | 净资产、本月生活消费、下一笔待还、可信度一句话、金额一键隐藏 | `GET /personal_finance/dashboard/overview.json` |
| 记一笔 | 类型/金额/账户/分类/标签，支持模板快捷 | `POST /transactions/add.json`、模板列表 |
| 待办 | 待处理账单整理任务摘要：新账户、未分类、冲突、分期确认（选择题） | billflow todos、reconciliation cases |
| 我的 | 账号、设置（默认币种/语言/金额隐藏）、会话管理、关于 | users/profile、app cloud settings |

**分包（进入首页后预下载 bill 分包）**：

| 分包 | 页面 |
| --- | --- |
| `subpackages/bill` | 上传账单（`wx.chooseMessageFile` 从聊天记录选文件，核心差异化入口）、整理摘要三行、账户核对、交易整理（合并/分类/不入账勾选） |
| `subpackages/account` | 账户列表/编辑、分类管理、标签管理 |
| `subpackages/loan` | 贷款合同列表、还款计划、分期确认（首期只读摘要+简单操作，复杂录入引导去 Web） |
| `subpackages/settings` | 汇率、数据管理、隐私协议、注销 |

体验主线严格对齐需求文档：「上传本期账单 → 三行摘要 → 只处理待办 → 完成」，小程序上的账单整理收敛为选择题交互，不做大屏对比界面。

### 3.3 网络层与状态

- `api/request.ts`：统一 `uni.request` 封装，JWT 存 `uni.setStorageSync`，401 静默重登（openid 免密），失败重试与超时收敛在一处；
- `callContainer` 封装为请求方法之一（路径前缀转发），保留可切换普通 HTTPS 域名的能力，方便本地开发与未来迁移；
- Pinia store 与现有前端同构（login/dashboard/billflow），方便对照移植。

## 4. 微信生态能力集成

| 能力 | 用途 | 期次 |
| --- | --- | --- |
| `wx.login` + code2session | 免密登录 | 一期（必须） |
| `wx.chooseMessageFile` | 从聊天记录直接选支付宝/微信账单文件上传 —— 小程序相对 Web 的核心优势 | 一期（必须） |
| 隐私协议（`__usePrivacyCheck__`） | 首次使用弹窗，声明收集账单文件与交易数据 | 一期（必须） |
| 订阅消息 | 「下一笔待还提醒」「账单整理完成，还有 N 个待办」 | 二期 |
| 分享（onShareAppMessage） | 金额隐藏默认开启的分享卡片（防财务数据泄露），分享总览页带邀请参数 | 二期 |
| 流量主广告（Banner / 插屏 / 激励视频） | 变现主通道；广告仅置于低频页与流程终点，核心记账路径零广告 | 上线后（UV ≥ 500 开通流量主，见 4.1） |
| 手机号快捷填充 | 账号找回（需企业/个体户主体；openid 免密重登已覆盖找回需求） | 远期（仅升级主体后） |

### 4.1 广告位设计（流量主变现）

开通条件（微信官方现行口径）：小程序**累计独立访客（UV）≥ 500**、无刷量与严重违规记录，个人主体即可在公众平台「推广 → 流量主」自助开通；签署协议后补充本人银行卡财务资料（审核约 7 个工作日），收益按月自动结算。

广告位原则——**记账核心路径零广告**，财务工具的信任是获客和留存的地基：

| 广告位 | 位置 | 形式 | 时机 |
| --- | --- | --- | --- |
| 底部 Banner | 「我的」页、设置分包等低频页 | Banner | 流量主开通后即接入 |
| 流程终点插屏 | 账单整理「完成」页 | 插屏 | 低频（用户每月整理数次的终点，不打断操作） |
| 可选增强激励视频 | 月度报告深度分析、报表导出等锦上添花功能 | 激励视频（eCPM 最高） | 用户主动触发，永不用于解锁记账核心功能 |

明确禁止：总览首屏、记一笔、账单整理进行中、待办选择题中出现任何广告；不用广告解锁查看自己的账目数据。

冷启动冲 500 UV：上线即配置分享卡片（金额隐藏的记账打卡卡片）+ 小程序名称与简介含「记账」关键词吃微信搜一搜自然流量；朋友与社群自然传播。**严禁刷量**（封号且与流量主协议冲突）。

## 5. 合规与上架清单

1. **主体**：**个人主体**即可支撑本方案。「工具 > 效率（记账）」类目对个人开放；**流量主广告对个人主体开放**（UV ≥ 500 即可开通，见 4.1），无需注册公司或个体工商户。个人主体的限制及应对：无微信支付商户能力（本产品无内购，无影响）；不能获取手机号（账号找回依赖 openid 免密重登——openid 即稳定身份，天然覆盖）；不能开通付费会员等超出广告的变现（如未来需要，再升级个体工商户/企业主体，代码与数据无需改动）。
2. **类目**：工具 > 效率（记账），无需金融资质；文案全程避免「理财」「投资」「收益分析」等金融表述，定位「记账工具」。
3. **隐私（PIPL + 微信平台）**：用户隐私保护指引必须列出「账单文件、交易记录、财务数据」的收集目的与保存策略；首启弹隐私授权；提供账号注销入口（`data/clear/all.json` 已有基础）。
4. **域名**：云托管 `callContainer` 免域名白名单免备案；若二期 Web 自定义域名或切换自托管，届时补 ICP 备案并配置 request 合法域名。
5. **审核风险预案**：首次提审常见卡点——未登录可见性（提供游客可看的示例总览页）、隐私协议入口、账号注销路径；预提审一次摸清类目口径。
6. **运营责任**（面向公众后新增）：多用户注册开关、登录限流（已有）、用户数据备份、敏感日志脱敏（PF 仓库隐私 session 约束已覆盖）。
7. **广告合规**：接入广告位后需再过一次审核；小程序必须是功能完整的真实服务（纯广告壳会被拒，本产品无此问题）；广告素材由微信广告平台分发，流量主协议与财务资料（本人银行卡）在开通后及时补齐，否则影响结算。

## 6. 里程碑（目标：提审前约 5–6 周）

| 里程碑 | 内容 | 预估 |
| --- | --- | --- |

| M1 核心 MVP | 总览、记一笔、待还、我的（四个 tab）；上传账单 + 整理待办选择题 | 2–3 周 |

## 7. 风险与开放问题

| 风险 | 应对 |
| --- | --- |
| 整理待办在真机上未收敛为少量选择题（需求文档启动条件未完全满足） | M1 期间用真实账单验证；若待办仍复杂，小程序一期先做「上传 + 摘要 + 跳转 Web 处理」的降级形态 |
| 冷启动 UV 不达 500，流量主开不了 | 上线即配分享卡片 + 搜一搜关键词（名称/简介含「记账」）；社群自然传播；严禁刷量（封号） |
| 广告伤害财务工具信任度与留存 | 广告仅置于低频页与流程终点；激励视频只解锁可选增强；核心路径零广告（见 4.1） |
| 云托管 MySQL 成本随用户增长 | 起步按量费用极低；设定告警阈值；架构保留迁移退路 |
| AppSecret 泄露 | 仅环境变量注入 + 云托管调用统计监控 |
| 微信审核类目口径变化 | 预提审 + 文案中性化 |
