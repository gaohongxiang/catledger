# 账单来源解析规则

> 本页是来源解析能力的长期资产清单，记录当前解析器、来源语义、原项目可复用能力、测试基线和演进规则。文件上传、批次与证据存储见[账单上传与解析](./账单上传与解析.md)，整理与入账见[账单整理与入账](./账单整理与入账.md)。

## 总体结论

原项目和个人财务新流程不能简单二选一：

- 原项目的优势是支付宝、微信等个人高频来源的字段读取、账户方向和特殊动作积累；
- 新流程的优势是不可变原始证据、解析与标准化版本、物理定位、来源身份、跨文件去重、账户映射、人工裁决和整批原子入账；
- 正确演进方向是复用原项目成熟的“格式读取 + 来源具体语义”，统一输出新流程的 `EvidenceDocument`，不得让旧导入器直接绕过证据链写正式交易。

同一来源只能有一套可复用的具体语义分类器。单文件导入与账单整理可以保留各自所需的输出结构，但不能各自复制关键词和优先级；这两个入口属于同一产品，不是新旧兼容关系。

## 当前个人财务解析器

| 来源 | 格式与选择 | 当前版本 | 现行能力 | 明确边界 |
| --- | --- | --- | --- | --- |
| 支付宝 App | CSV，自动 Probe | `alipay-evidence-parser-v1` / `alipay-normalization-v1` | 保留原始列与物理行；读取交易号、订单号、付款方式；具体产品动作优先于宽泛分类 | 当前预发布规则直接作为 v1，不维护历史语义分支 |
| 支付宝 Web | CSV，自动 Probe | 同上 | 与 App 共用标准化语义，按 Web 表头读取交易号和商户订单号 | Web 账单通常没有付款方式，账户可能依赖来源账户或后续确认 |
| 微信支付 | CSV，自动 Probe | `wechat-csv-parser-v1` / `wechat-normalization-v1` | 多编码、别名表头、状态、退款、交易号和付款方式；保留 CSV 物理行；各入口共用动作和状态语义 | 当前预发布规则直接作为 v1，不维护历史语义分支 |
| 微信支付 | XLSX，自动 Probe | `wechat-xlsx-parser-v1` / `wechat-normalization-v1` | 保留 sheet 与行号，拒绝公式单元格冒充原始值，多 sheet 独立读取；与 CSV 共用标准化语义 | 同上 |
| 光大信用卡 | PDF，显式选择 | `ceb-credit-pdf-parser-v3` / `ceb-credit-pdf-normalization-v1` | 识别月结单固定文本结构、账期、账单日、还款日、额度、卡尾号与收支 | 只支持带文本层的既定光大模板，不是通用 PDF/OCR；无稳定流水号 |
| 通用银行 | CSV，显式选择并映射列 | `generic-bank-csv-parser-v1` / `generic-bank-normalization-v1` | 支持 UTF-8/GB18030/GBK、逗号/制表符、单金额列/收入支出双列、列映射 | 不猜银行语义、状态或账户；用户映射错误会形成错误证据，因此必须显式确认 |

## 来源语义

### 支付宝

优先级为：具体商品动作 → 来源交易大类 → 收支方向。当前共享动作如下：

| 商品说明动作 | 标准化结果 | 账户含义 |
| --- | --- | --- |
| `-收益发放` | 收入、正常经济效果 | 收入进入付款方式所映射的资金账户；基金公司不是本人转出账户 |
| `-买入`、`-买入退款`、包含 `-卖出` | 账户资金移动 | 需要结合状态和实际本人账户判断投资账户关系 |
| `充值-` | 充值 | 外部资金账户转入平台余额 |
| `提现-` | 提现 | 平台余额转出到外部资金账户 |
| `转入`、`转出`、`转账`、`还款` | 转账类 | 只有本人账户之间的移动才要求两个不同正式账户 |

“投资理财”只是宽泛来源分类，不能覆盖“收益发放”。“不计收支”也不能单独决定它是转账；状态为关闭或失败时仍优先进入交易异常，不因产品动作变成可入账。

### 微信支付

单文件导入和账单整理证据解析从 `wechat-normalization-v1` 起共用动作与状态分类器。动作优先级为手续费 → 零钱/余额充值 → 零钱/余额提现 → 信用卡还款 → 转账/红包/群收款 → 普通消费、付款、收款、支付、退款 → 零钱通/理财通。单文件导入把 `/` 的零钱充值、零钱提现和信用卡还款输出为对应账户关系，收入支付方式为空时回退到微信零钱；账单整理保留原始付款方式，账户归属交给用户映射。

状态优先于动作结果：失败、未支付、未收款进入失败；关闭、撤销、取消进入关闭；成功退款进入退款；其余明确成功状态才是正常。账单整理保留所有原始证据并把失败和关闭显示为交易异常；单文件直接导入无法保存异常证据，因此跳过这两类记录，不再把“退款失败”误导成退款交易。

### 光大信用卡与通用银行

这两类是新流程新增能力，原项目没有同等的证据解析器可直接替换。光大专用模板比“万能 PDF”可靠：格式特征不足就拒绝解析，`(存入)` 表示流入，其余表示信用卡支出。通用银行 CSV 则只负责用户明确给出的列映射和金额方向，不做关键词猜测。二者都需要整理阶段的账户映射与经济语义校验，解析器本身不创建账户或正式交易。

## 原项目解析资产怎么用

| 原项目能力 | 价值判断 | 接入新流程的方式 |
| --- | --- | --- |
| 支付宝 App/Web、微信 CSV/XLSX | 来源特例和账户方向经验最有价值 | 抽共享来源语义；各导入入口共同调用，禁止再复制规则 |
| OFX/QFX、CAMT.052/.053、MT940 | 主要服务海外或企业银行数据交换，不属于当前国内个人账单范围 | 保留原项目代码但不注册为个人财务解析入口、不安排当前适配任务 |
| QIF、IIF | 更接近财务软件之间的数据迁移，不是国内个人银行的常见下载格式 | 与完整账本迁移统一评估，不混入当前日常账单更新 |
| GnuCash、Beancount、Firefly III | 适合迁移其他完整账本，账户、分类、标签和转账关系较完整 | 作为“账本迁移”来源单独设计，不与日常银行账单自动合并；保留外部身份和关系 |
| 随手记、京东金融 | 有来源专用字段、余额调整、退款和转账拆分经验 | 先建立脱敏金标，再移植来源读取与语义，不直接复用旧写账逻辑 |
| 自定义 CSV/XLSX | 覆盖长尾银行和平台 | 继续显式列映射；保存映射模板时按用户隔离并可修改，不提升为全局猜测规则 |
| AI 文本/图片识别 | 可辅助人工录入 | 不用于自动读取真实账单；未经逐字段确认不得进入证据或正式账本 |

原项目解析器返回的是待创建的账户、分类和正式交易候选，适合一次性导入，但缺少个人财务流程需要的不可变证据、来源身份和跨文件裁决。因此只能复用读取器、字段映射、来源动作和测试样例，不能整体替换新流程。

## 修改与验收规则

1. 先写来源事实：原始列、样例值、状态、具体动作、资金方向和账户角色；不得先写宽泛关键词猜测。
2. 同一来源的各导入入口必须调用同一具体动作分类器；差异只允许存在于必要的输出结构，不得维护历史语义兼容分支。
3. 优先级固定为人工事实 > 稳定来源标识/明确状态 > 具体产品动作 > 宽泛交易大类 > 收支标记 > 未知。未知时进入核对，不用商户名硬编码兜底。
4. 文件结构、表头或物理行读取变化提升 parser 版本；统一字段或经济语义变化提升 normalization 版本。预发布阶段直接重建未入账批次，不增加旧语义兼容代码。
5. 每个解析器至少保留：脱敏金标文件、正常行、关闭/失败、退款、未知语义、金额/时间错误、重复物理行、来源单号、取消上下文和安全错误测试。真实账单不得进入仓库。
6. 来源语义新增或修复时，单文件导入测试与证据解析测试必须同时运行；若两者预期不同，先在本页说明原因，不能静默分叉。
7. 新解析器先证明 Probe 不会抢占其他来源；无法唯一识别的格式必须 `ExplicitSelectionOnly`。

## 当前待办优先级

1. 支付宝共享动作已落地，待从头导入真实“收益发放、买入、卖出、充值、提现和还款”样例验证现行规则。
2. 微信共享动作与状态分类器已落地，待从头导入真实零钱充值、零钱提现、信用卡还款、退款失败和交易关闭样例验证现行规则。
3. 国内个人来源按真实用户账单推进：支付宝、微信优先，其次是用户实际提供的银行 CSV、Excel、带文本层 PDF；不为未知模板预写猜测解析器。
4. OFX/QFX、CAMT、MT940 不纳入当前个人产品路线；随手记、GnuCash、Beancount、Firefly III 等归入独立“账本迁移”设计，不混入当前多账单日常更新。
