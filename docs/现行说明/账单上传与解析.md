# 账单上传与解析

> 本页描述系统当前行为；与代码冲突时以代码为准并修订本页。冻结契约（表结构、字段、checksum）见实施规划，此处不复制。

## 它做什么

用户上传账单文件后，系统保存原文件并按内容哈希防重、创建解析批次、把每一行留存为不可变的原始证据行，并计算来源身份供精确去重。上传与解析本身不写正式账本，也不会立即要求选择付款账户；解析成功的账单自动加入尚未开始的本轮，用户可继续添加或将误选账单移出本轮。整理和入账见 `账单整理与入账.md`。

各来源的具体语义、原项目可复用解析资产、版本和金标要求集中维护在[账单来源解析规则](./账单来源解析规则.md)，新增或修改来源解析器时必须同步更新。

## 数据怎么流

上传 → `pf_import_file`（`uid + SHA-256` 唯一，重复文件直接返回已有记录）→ 原文件进对象存储 → 解析批次 `pf_import_batch` → 逐行 `pf_raw_import_row`（含无效行）→ 来源身份 `pf_source_identity`。

- 上传入口：`POST /api/v1/personal_finance/import_files/upload.json`，multipart 字段 `file`，大小上限为配置项 `MaxImportFileSize`。
- 解析与重解析入口：`POST /api/v1/personal_finance/import_batches/reparse.json`；请求需要币种（ISO 4217 三字母）、时区偏移和原因码，可选 `parserName` 与通用银行列映射 `genericCsvMapping`。
- 同一文件普通重传不重复解析；显式重解析（带原因码）产生新批次，旧批次和旧证据保留。
- 原始底身份自动沿用：账单里有稳定账号或展示名（如微信昵称）时，同一份直接复用，没有则自动新建。看不出平台账号时按原文件作用域自动建档。解析阶段不再弹出「选择账单所属账户」。通用银行 CSV 仍要显式选解析器和列映射，但不先选账本账户；付款账户放到整理页核对。光大信用卡月结单解析不选账本账户，只自动准备身份作用域并落库。

## 当前支持的格式与解析器

解析器在个人财务 flow 应用中注册：

| 解析器 | 格式 | 选择方式 |
| --- | --- | --- |
| 支付宝 App 账单 | CSV | Probe 自动识别 |
| 支付宝 Web 账单 | CSV | Probe 自动识别 |
| 微信支付账单 | CSV | Probe 自动识别 |
| 微信支付账单 | XLSX | Probe 自动识别 |
| 通用银行账单 | CSV | 仅显式选择：`parserName` + 列映射 |
| 光大信用卡月结单 | PDF | 仅显式选择：`parserName=ceb_credit_pdf`，不要列映射 |

未指定 `parserName` 时逐个 Probe，并跳过 `ExplicitSelectionOnly` 的解析器；指定时只使用该解析器。前端上传框接受 `.csv`、`.xlsx` 和 `.pdf`。桌面「账单整理」上传支付宝/微信文件后会立刻 Probe 解析；光大 PDF 仍走专用对话框。未接入新流程的来源仍可使用旧导入功能。

光大月结单是专用模板，不是通用银行 PDF。金额只有一列，说明里带「(存入)」记为收入，其余记为支出；「交易说明」写入交易对方，不写入商品说明。卡号末四位与「光大银行信用卡」组成付款方式后再核对账户。解析时不选账本账户；一份文件里的多张卡在整理页按末四位分成不同付款方式。光大账单没有稳定订单号或流水号；正式站当前发布的 identity-v1 会把时间、金额、说明和末四位等内容指纹当作来源身份，因此不同物理行内容相同时可能被误标为精确重复。本分支 identity-v2 已改为文件内容 SHA-256 与物理定位身份，并保留稳定交易号和完整订单组合的 v1 身份兼容。在合并、发布和重建旧轮之前，正式站旧结果不得用于真实入账。页眉若有账单日、到期还款日和信用卡额度，会随批次保存，并在核对账户时跟对应卡一起展示；没有现成账户时新建信用卡会带上账单日。账单没给的字段保持未知。额度不进核心账户表。已用旧解析器把说明写进商品字段的行，整理页仍把这段显示为交易对方。已用更早解析器处理过的同一文件，须显式重解析才会出现页眉或对方字段。真实账单样本不进仓库。

## 证据行长什么样

每一逻辑行保存三层内容：原始有序字段快照、固定字段投影（原始时间、金额、方向、状态、对手方、商品、支付方式等，缺失用空字符串）、标准化结果（Unix 秒、非负最小货币单位金额、币种、方向、经济效果）以及来源标识材料和逐行 issue。CSV 用起止行定位，XLSX 用 sheet 与行号，PDF 用页码与页内行号。语义有问题的行也完整保留并标注问题码，只有文件级不可读才让整次解析失败。

## 各来源列名怎么对到统一字段

对照由各解析器代码持有并被测试锁定；界面和后续整理只认统一字段，不认来源列名。来源没有的字段留空，不挪用其他列。

| 统一字段 | 支付宝 App CSV | 支付宝 Web CSV | 微信 CSV/XLSX | 光大信用卡 PDF | 通用银行 CSV |
| --- | --- | --- | --- | --- | --- |
| 交易时间 | 交易时间 | 交易创建时间 | 交易时间 | 交易日 | 用户列映射 |
| 金额 | 金额 | 金额（元） | 金额(元) | 金额 | 列映射（单列或收入/支出两列） |
| 方向 | 收/支 | 收/支 | 收/支 | 说明含「(存入)」为收入 | 列映射 |
| 状态 | 交易状态 | 交易状态 | 当前状态 | 无 | 列映射 |
| 交易类型 | 交易分类 | 类型 | 交易类型 | 无 | 列映射 |
| 交易对方 | 交易对方 | 交易对方 | 交易对方 | 交易说明 | 列映射 |
| 商品说明 | 商品说明 | 商品名称 | 商品 | 无（说明已作对方） | 列映射 |
| 支付方式 | 收/付款方式 | 无 | 支付方式 | 卡号末四位 + 光大银行信用卡 | 列映射 |
| 备注 | 备注 | 备注 | 备注 | 记账日 | 列映射 |
| 单号 | 交易订单号、商家订单号 | 交易号、商户订单号 | 交易单号、商户单号 | 无 | 列映射 |

支付宝和微信按表头识别列并容错常见别名（如「交易日期」「交易对象」「商品说明」「付款方式」）；来源改列名先补别名，改语义才升解析器版本。旧批次不动，显式重解析后才按新对照产生新批次。

## 加一种新格式改哪里

1. 在对应来源目录新建解析器，实现 `Descriptor` / `Probe` / `Parse`；解析器是纯转换组件，不碰数据库、账户映射和对象存储；
2. 在 flow 应用注册；能可靠探测的走 Probe 自动识别，无法可靠探测的设 `ExplicitSelectionOnly`；
3. 新载体要扩展 `EvidenceFormat`、物理定位 kind，以及前端 `accept`；
4. 补脱敏合成夹具和解析器测试；真实账单样本不进仓库、不进文档。

不要做「中国信用卡 PDF 通用引擎」；一家银行一个模板。不要用大模型读原始账单。

## 改解析规则怎么升版本、旧批次怎么办

- 解析器只拥有 parser 和 normalization 两类版本；来源账户 key、身份 key、core digest、指纹、原始快照的版本由中心 identity 包持有。解析或标准化行为变化必须升对应版本号，不得原地改语义；
- 旧批次不受影响：原始行写入后不可覆盖，规则变化后通过显式重解析产生新版本批次，旧批次保留可追溯；
- 同一身份出现金额、币种、方向等核心语义不兼容时进入冲突态，人工处理，不用新值覆盖旧证据。

## 与目标需求的差异

本分支 identity-v2 已在稳定交易号和完整订单组合缺失时改用文件内容 SHA-256 与物理 locator，同一文件不同物理行不再因内容相同共享来源身份；同一 locator 显式重解析仍会收敛。正式站尚未发布该实现，旧批次的精确重复数及其派生事件计数仍不可信；发布和重建前保持未入账，原始文件和物理行完整保留。

当前光大 PDF 仍需显式选择专用模板，通用银行只支持 CSV 映射；尚未实现目标架构中的“未知文件失败隔离后直接形成账户覆盖缺口”完整体验。未来优先扩展结构化银行格式和模板注册，不承诺万能 PDF，也不改变现有解析器纯转换边界。
