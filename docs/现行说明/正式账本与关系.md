# 正式账本与关系

> 本页描述当前行为；目标变化见产品需求和架构设计，代码冲突时以代码为准并修订本页。

## 权威边界

现有 `Transaction`、`Account`、分类和标签是余额、现金流与常规报表的唯一权威。原文件、原始行、来源身份、对账 case、贷款计划和整理待办本身都不直接改变余额。

## 证据如何进入账本

解析成功的原始行先获得稳定来源身份。确认入账时，posting 按当前用户和批次在事务内创建或复用正式交易，并写入原始行到交易的证据链接。相同幂等请求重放不重复创建交易；数据库唯一约束是并发最终裁决。

一笔正式交易可以有多条证据，例如支付宝消费和信用卡月结单扣款。证据迟到时可以补充链接，不再创建第二笔消费。

schema v009 会把旧流程当前有效的已入账证据链接回填到 organizer 事件投影。该投影只用于解释、核对和后续纠错；核心 `Transaction` 仍是余额与报表的唯一权威，不会因迁移重复记账。

## 当前关系

- `same_event`：多条来源证据证明同一正式事件；
- `internal_transfer`：两个账户之间的资金移动；
- `refund_reversal`：原消费和退款分别保留为正式事件；唯一强证据存在时建立角色关系，未关联退款仍保留退款经济性质；
- 贷款与分期 binding：正式交易分配到合同和期次的本金、利息或费用组件。

自动关系有规则版本和 case；人工决定不会被规则刷新静默覆盖。已应用关系的撤销先检查交易是否被修改、删除、其他批次共享或贷款关系引用。

核心账本用一笔流入交易承载退款对账户余额的影响，PF 经济事件保留其退款性质。个人财务总览按经济性质把退款从消费中冲回，不计入收入；未关联退款不继承原消费分类，只有建立 `refund_reversal` 后才可归回原消费的分类、商户和累计可退额度。

## 当前限制

organizer 已通过 `updates`、`events`、`actions` 资源接口接入结果页，独立展示事件状态、批次守恒计数和正式交易链接。来源只能确定资金方向而无法确定经济性质时，事件停在 `needs_action`，不会进入正式账本；当前结果页支持确认经济性质或排除，其他字段级高级纠错继续由同一事件接口扩展。

## 扩展边界

新增关系类型不得改变核心账本依赖方向。需要新持久字段或状态时，先冻结迁移和三库兼容契约；不得把内部账户 ID 或关系拓扑偷塞进普通原因文案。
