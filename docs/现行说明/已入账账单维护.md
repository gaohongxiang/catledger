# 已入账账单维护

本说明对应 MINI-1906A1 开发版候选，规则 `import-maintenance-v1`。正式余额、明细及统计仍只读取 Transaction，不新增 JournalEntry / Posting。2026-09-05 开发云已应用 0009、0010 并更新两个云函数；正式发布状态以实施规划为准。

## 模块职责

- `account-draft`：最终 ready 事件的账户端点、聚合分配及这些事件的有效映射草稿引用形成可达集合；只有可达草稿在 posting 事务物化。修改、排除会标记失效草稿；放弃会在同一事务回收草稿和派生整理明细，保留来源与操作审计。
- `maintenance-policy` / `maintenance-state`：旧影响、新影响、账户净差额、交易集合版本与预览摘要。现金约束是不能产生或加深负余额。
- `maintenance-side-effects`：按 posting 保存的前后版本检查并恢复映射，停用本批独占账户；已被后续整理使用、版本变化或无法证明独占的对象保留，并在影响预览列出。
- `finance-update-maintenance`：读取一致快照用于预览，写入时锁定 FinanceUpdate、事件、完整交易集合及账户，重算摘要和门禁，原子提交。

## 更正与撤销

`economicEvents.correctionImpact` 接收 eventId 和待修改 fields，返回完整交易集合、账户差额、冲突、规则版本、updateVersion/eventVersion 与 previewToken。`economicEvents.correct` 必须带相同 fields 与 token；交易被外部修改、账户余额/版本变化或批次变化时拒绝旧预览。单笔保留交易 ID；聚合还款按冻结候选和金额守恒软删除旧集合、标记 superseded 链接、创建全部新分配，任何失败全部回滚。其他多交易事件明确要求整批撤销。

`financeUpdates.undoImpact` 同时预览交易、账户、映射、分类别名和退款依赖。撤销只软删除本批 created 且仍匹配入账版本的交易，保留 reused；外部退款、外部交易版本变化或现金不足阻断执行。仅本批独占且版本未变化的账户会停用；映射恢复有效前值或停用，后续使用/变更的映射保留。历史批次没有 side_effects_json 时返回 LEGACY_SIDE_EFFECTS_UNVERIFIED，不猜测归属。

手工交易、账户余额维护、导入 posting 与导入维护使用事务级 READ COMMITTED，并按账户 ID 锁定账户后读取余额；避免等待锁之前建立的旧快照允许并发现金透支。预览仍使用只读一致快照。后端从可信微信身份解析 uid，所有读写继续参数绑定和用户隔离；previewToken 是一致性校验而非身份凭证。

0010 只为既有表添加四个可空字段：账户草稿/事件交易链接的 superseded_at、FinanceUpdate 的 side_effects_json、分类映射的 disabled_at。迁移可重复执行，旧数据保持 NULL，回退不删除审计列。

## 小程序单笔编辑（TRANSACTION-EDIT-043）

明细和首页近期交易点击哪笔就打开哪笔，标题统一为“编辑账单”。通过服务端 origin（兼容旧 importContext）选择展示方式：导入账单直接显示金额、类型、时间、账户、备注，收入和支出可修改分类或设为未分类；退款继承原支出分类，转账等不单独分类。手工交易沿用金额、账户、日期、备注和分类编辑。缺少被点击交易时提示返回，不选其他记录代替。

导入工作台移除整批维护入口，import-maintenance 不再注册页面路由。上述后端更正与撤销能力保留，当前单笔界面没有入口。

transactions.setCategory 在同一幂等事务内按可信 uid 锁定交易，验证版本和分类所属用户、可用状态与收入/支出类型，只更新 category_id 与 version；支出的关联退款同步分类。金额、账户和余额不变，不更新原始账单、整理快照或分类映射。版本变化使旧维护预览保守失效。同一保存失败重试保持 requestId，选择不同分类才生成新请求；成功返回明细并使交易相关缓存失效。

明细分类筛选顺序为“全部分类”“未分类”、已有分类。未分类传 uncategorized:true，与 categoryId 互斥；服务端在分页前限定当前用户未删除、category_id IS NULL 的收入/支出，继续组合月份、日期、账户和搜索，并纳入游标摘要。退款、转账不混入待补分类列表。客户端和云函数须配套部署；旧云函数不支持该筛选。
