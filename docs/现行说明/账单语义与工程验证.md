# 账单语义、来源证据与规则版本

> 本文展开[主流程中的解析到核对](../招财猫记账本入账逻辑说明.md#import-parse)。它描述当前规则边界，不记录逐次发布和真实账单盘点。旧案例与完整修复记录见[归档](../归档/README.md)。

## 1. 各层只解释自己负责的信息

| 层 | 输入 → 输出 | 边界 |
| --- | --- | --- |
| Adapter / Parser | 文件容器 → 工作表、表头、行与字段位置 | 不直接写账 |
| Source Profile | 平台字段和文本 → 标准字段角色、规则证据与控制项 | 来源特例在此解释，不散落到通用模型 |
| Row Semantic Resolver | 标准行和 profile → 动作、资金效果、账户组件、关系线索与冲突 | 同值候选合并证据，不同值保留冲突 |
| Evidence Matching | 来源身份与核心字段 → 证据组、强关系或冲突 | 不凭相似文本自动消灭独立记录 |
| Event / Relation / Review | 标准语义 → 事件、关系、核对问题及可入账状态 | 不再次解释支付宝/微信原始 token |
| Posting | 已持久化且版本有效的整理结果 → 正式账本 | 不绕过证据检查，不重新解析文件猜新结果 |

代码：[parsers](../../cloudfunctions/catledger-import/src/parsers)、[profiles](../../cloudfunctions/catledger-import/src/profiles)、[resolver](../../cloudfunctions/catledger-import/src/row-semantic-resolver.js)、[planner](../../cloudfunctions/catledger-import/src/organizer-planner.js)。

## 2. 文件层与行层不能互相冒充

文件层观察模板、数据区、列、支持的笔数/收支控制和解析版本；行层保留时间、金额、方向、状态、类型、对方、商品、支付工具、标识以及原位置。未支持的文件控制形式报告未知，不从数据行数推导“账单完整”。

记录结构优先于关键词。商品或备注含“合计”“支付宝账号”不应让一笔结构完整的交易消失。坏日期、额外单元格、未知列和表头前后出现的数据结构必须留下可追溯观察。缺列、空值、零与 `/` 含义不同。

不同来源模板分别版本化；多模板或多账单工作表歧义拒绝猜选。银行三类金额布局分别解释：带符号、金额配方向、收支分列。借贷含义、符号或两列同时有值冲突时，需要明确处理，不能用绝对值抹掉资金方向。

## 3. 语义决策的关键边界

| 情况 | 现行处理原则 |
| --- | --- |
| 明确普通收支 | 根据动作、状态、方向共同确认，再处理账户与分类 |
| 成功退款 | 退款关系单独处理；不因为源方向是收入就记普通收入 |
| 免押授权、解冻等非资金过程 | 明确无资金变化时保留证据，不进入资金统计 |
| 来源字段新增或未知 | 按 profile 的字段角色判断能否解释；不将所有未知词统一套成消费 |
| 金融专用域或状态/动作不兼容 | 保留冲突，不能被普通分类规则覆盖 |
| 多账户有明确分项 | 使用受支持的分配模型检查各账户和金额守恒 |
| 多账户没有分项或不明资金性质 | 持久化阻断；随意补一个账户/分类不能解除 |
| 用户明确排除 | 改变本次选中范围，仍保留来源及其识别状态 |

分类是用途归类，经济性质决定如何写账。已知普通支出可以待补分类；未知资金效果不能因分类已有值而变成 ready。当前规则判断由代码、已确认映射和人工决定完成，没有外部决策模型步骤。

## 4. 账户引用和人工优先级

统一映射规则：inferred < history_alias < history < batch < event。同一最高级候选冲突时明确处理，不依赖遍历顺序。精确全名唯一命中只是推断；历史显式映射和人工决定可以覆盖。旧历史账户类型与当前来源期望不一致时不能复用。

现实账户身份用于合组询问，来源引用仍逐一保留；未知同名工具不能据此认定同一账户。多个信用产品合并显示的还款名称，不构成一个可新建的真实合并账户。

无尾号银行候选等展示建议只帮助用户选择，不等于服务端确认。选择账户后仍要检查有效状态、类型、资金端点和分配金额。来源原文不会被展示建议覆盖。

代码：[account-mapping-policy](../../cloudfunctions/catledger-import/src/account-mapping-policy.js)、[source-funds](../../cloudfunctions/catledger-import/src/source-funds.js)、[funds-allocation](../../cloudfunctions/catledger-import/src/funds-allocation.js)。

## 5. 身份、关系与退款

同来源唯一性把用户及必要的来源/账户范围纳入身份。稳定 ID 相同但金额、币种等核心事实冲突时留下冲突，不能覆盖旧证据；不同来源的强关联也不删除各自身份。

只有核验通过的稳定关联号或明确规则支持自动关系。时间、金额、商户、标题接近只产生候选；同额独立消费必须可保留。用户明确同笔/不同笔的决定有可追溯范围，后续重算不能静默推翻。

退款只在强且唯一的证据下自动关联；弱候选供人工核对，没有合法候选可以保留待关联退款。入账时继续检查原支出版本、时间、累计金额及外部关系，不能以预览中的候选替代锁内验证。

同一明确贷款付款的成员不能被外部按单笔历史记录复用而破坏整组；信用卡分期费用的同笔复用也受来源、账户、期次与金额约束。

代码：[evidence-matching](../../cloudfunctions/catledger-import/src/evidence-matching.js)、[refund-relation-policy](../../cloudfunctions/catledger-import/src/refund-relation-policy.js)、[historical-duplicates](../../cloudfunctions/catledger-import/src/historical-duplicates.js)。

## 6. 覆盖统计的两个出口

每行都要有归宿，包含资金、非资金、重复、待确认、用户排除、无效或未分配。Coverage Report 核查实际行、唯一行、Evidence 归属和事件来源；不能只用“识别条数等于文件行数”证明正确。

`statementFullyRecognized` 要求相应版本的文件观测和受支持控制项成立；`selectedEventsReadyToPost` 要求本次选择的事件满足账务条件。前者不成立时可能仍存在用户明确选定且可入账的范围；后者不成立时不能强制提交。排除不抬高前者。

旧行重算了语义，不代表旧文件自动具有新版完整观测。正式 posting 锁内重验版本和证据守恒，拒绝时不留下新账户或交易。

代码：[coverage-report](../../cloudfunctions/catledger-import/src/coverage-report.js)、[evidence-integrity](../../cloudfunctions/catledger-import/src/evidence-integrity.js)。

## 7. 规则升级与测试

改变平台语义要更新相应 policy/profile 版本；改变容器/记录解释需要更新 adapter/parser/normalization；影响整理结果时同步计划版本。实际版本值只看 [domain-versions](../../cloudfunctions/catledger-import/src/domain-versions.js)及 profiles，不在本说明复制旧数字。

未入账计划升级保护人工字段、排除、关系和原始证据；已入账事实不自动重算。只有同原件摘要、同物理行、原始身份摘要及核心事实等严格条件成立，才可按既有路径识别解释升级，不能把跨文件冲突伪装成升级。

新增规则必须覆盖一个正例、容易混淆的反例及失败/未知路径。比较保留业务关系图和错误码，不仅比金额总和。真实账单需要用户授权和脱敏处理；不把已看过的少数模板宣称为全部银行格式支持。

测试集中在[导入函数测试目录](../../cloudfunctions/catledger-import/test)、[历史核对数据库回归](../../test/import-history-review-db.test.js)、[银行导入回归](../../test/bank-import-db.test.js)。执行命令统一见[开发与验证](../开发与验证.md)。
