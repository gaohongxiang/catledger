# 账单语义与工程验证

本说明对应 MINI-1906V2 开发版候选，当前规则计划为 `organizer-plan-v27`。发布与验收状态以实施规划为准。

## 数据流与职责

```text
CSV / XLSX
  → Adapter + Source Profile：唯一模板、字段位置、记录分类、文件控制
  → Row Semantic Resolver：动作、资金效果、账户引用、规则证据及冲突
  → Evidence Matching：稳定身份去重与证据分组
  → Economic Event Builder：标准经济性质、账户映射、持久化语义阻断
  → Relation Resolver：退款等关系、强证据与人工候选
  → ReviewIssue + Postability：用户决定、账户/分类/关系完整性
  → Posting：锁内校验版本与逐行证据，整批事务写正式账本
```

`organizer-planner.js` 负责协调上述步骤和问题分组。通用事件、关系层只消费标准语义和结构化关系线索；平台类型、状态文本在 Profile 中解释。新增模板优先增加 Profile 和对应夹具，不修改通用事件核心。

## 当前行为

- 账户信息不足的未确认记录在账户步骤显示“请选择账户归属”，不默认新建；待选择时禁止确认。已确认的人工归属继续保留，已有选择失效后回到待选择。相同未知标题不能证明同一账户，仍需分别核对；已识别的稳定引用才复用归属。
- 待选控件用橙色及“待确认”文字区分白底已确认项。账户列表默认收起所有交易信息，保留原有标题与选择框间距，标题右侧仅保留“查看 N 笔”文字入口；已确认项保留灰色账户推荐依据，仅移除绿色“已确认、可修改”提示；点击后在同一面板直接展示每笔摘要及全部原始字段，不再二次点击；多笔列出时间范围和全部成员，每次显示 20 笔。仅为当前显示记录读取原始证据，并发限制为 4；逐笔呈现，失败可原位重试，关闭或离开后忽略晚到响应且停止后续读取。完整字段在限高区域内滚动，只保留一个返回入口。待整理列表卡片使用单行问题标题与简短说明，处理为文字入口，交易名称/金额为主体；保留原有标题底色。待整理详情同样直接展示原始字段；确认表单优先，交易和原字段在同一滚动区，保存为主要操作，稍后处理/不计入为文字操作。分类待确认纳入表单容器显示条件，确保分类选择器实际可见。退款候选原消费也包含来源字段，且不加入待裁决事件集合。账户与待整理共用证据加载实现及字段模板。只读证据层独立于裁决表单，更正页也可携带本批 eventId 进入；整批撤销前可展开本批记录。
- 重复上传未入账文件按 `parse-run-v2` 指纹判断是否复用，版本变化则追加解析批次，保留旧批次及作废更新。只有同一原文件摘要、同一物理行、匹配最初身份摘要且金额/币种/方向一致的证据，才能把资金效果变化认定为解释升级；跨文件或核心字段变化继续形成身份冲突。覆盖统计用当前统一语义解释旧行，文件级完整观测仍须重新解析，不能虚报通过。
- 微信 CSV/XLSX、支付宝 App/Web CSV 各有独立 Profile；同时命中多个完整模板或多个账单工作表时拒绝猜选。
- 数据结构优先于控制词，商品/备注含“合计”“支付宝账号”等文本不会导致整行消失；表头前后的交易结构均保留，坏日期保留为无效行。原字段位置、额外单元格和未知列保留在来源证据中；缺列、空值、`/` 分开观测。
- 动作规则产生独立候选，同值合并证据、不同值输出冲突。支付宝 App 声明 category 字段角色，明确收支可以解释新增普通分类；Web／微信 action 字段继续按已登记动作解释；金融专用域和小荷包中性方向特殊规则仍严格验证。信用免押使用费按成功扣收记支出，零元授权／解冻按非资金生命周期处理；专属到账状态检查动作兼容性。已用用户选择的微信 XLSX 与支付宝 App CSV 进行组合盘点；另外两类只有合成金标，不代表覆盖所有平台导出格式。
- 多个资金账户缺少逐项金额时形成持久化语义阻断，填写一个账本账户或分类不能解除；未知动作、状态、冲突也不会因补字段变成可入账。明确排除仍可用于选择本批范围。
- `deriveRowDisposition` 是覆盖归宿的唯一计算入口，分别统计资金、非资金、重复、待确认、用户排除、无效、未分配。Coverage Report 校验实际行数、唯一行、Evidence 归属和活动事件的来源；用户排除不提高来源识别率。
- `statementFullyRecognized` 还要求当前版本文件观测、无未知列、已支持的笔数/收支控制项通过。未支持的控制形式保守报告未知；不从总行数反推已识别行。
- `selectedEventsReadyToPost` 单独表达所选范围可入账，缺少证据、语义阻断或旧计划均返回 false。正式 posting 在 FinanceUpdate 锁内重验版本、证据守恒与既有账务门禁，拒绝请求不会物化草稿账户或写交易。

## 数据和版本

迁移 `0009_bill_semantic_analysis.sql` 为既有来源表增加三个可空 JSON 列：batch 的 `analysis_json`，row 的 `semantic_json`、`observations_json`。不增加领域表；历史数据可以保持 NULL。

文件分析只包含版本、位置、控制结果和诊断码，字段观测只保存状态。行语义属于用户隔离的内部来源证据，包含解释所需的账户组件和关系线索，不作为公共诊断返回或普通日志输出。原始账单仍遵循既有私有存储及证据保留策略。

本轮支付宝策略为 `alipay-semantic-policy-v4`。v26 review 升级为 v27 时，semantic-plan-upgrade 原位刷新变化的系统语义，保留事件与证据、人工字段、排除和关系决定；受影响共享问题须对全部成员重新评估。事务失败全部回滚，重复组织不重建。组合支付账户组与前端性质统一消费服务端语义。

解析保存版本化行语义；整理优先复用匹配当前 Profile/Policy 的结果，旧结果按来源证据重新解释一次，后续模块共享该结果。历史批次缺少当前文件观测时，即使已重新整理，也不能声称整账已完整识别。posting 消费持久化事件，不重新解析文件。

改变语义规则需升级 Profile 的 `policyVersion`；改变容器/记录解释需升级 `adapterVersion`、parser/normalization 版本；影响整理结果时同步升级 `PLAN_VERSION`。预览后不匹配版本的提交返回 `CONFLICT`，需要刷新并重新整理。`analysis-snapshot.js` 已生成稳定内容摘要与版本封套；`scripts/compare-bills.js` 固定旧提交只读双跑，显式报告解析未完成，差分不含原始字段值。

2026-09-05 开发云已应用 `0009/0010`，核验新增列、迁移校验和及应用账号权限，并更新两个云函数。旧版本未入账文件已通过真实微信身份重新解析、追加批次并整理；原件及旧证据保留。回退代码保留新增可空列，不回删迁移历史；不得跳过版本门禁强行提交旧计划。

## 本地验证

先分别在两个函数目录执行 `npm ci`。根目录入口：

- `npm run check`：JavaScript/JSON 语法、微信项目路径、函数入口、跨部署包依赖、CommonJS 循环依赖、平台语义边界及 diff 空白检查。
- `npm test`：根目录和两函数非数据库测试；主动移除测试数据库环境配置，数据库用例明确跳过。
- `npm run test:db`：需要完整 `CATLEDGER_TEST_DB_HOST/USER/PASSWORD/NAME`（可选 `PORT`）；API 先应用迁移，再串行运行导入套件。必须连接可清空的隔离测试库，API 套件会清空 `catledger_*` 测试数据。缺配置立即失败。
- 两函数 `npm run audit:prod`：生产依赖漏洞审计。

`.github/workflows/verify.yml` 使用 Node 18 和独立 MySQL 8.4 服务执行上述检查。CI 的 root 仅用于临时测试数据库；正式函数继续使用受限应用账号。工作流本次只新增配置，未推送触发远端运行。

本地回归不能替代真实微信身份、真实账单组合盘点、小屏/真机走查、开发云权限复核或正式发布验收。MINI-1906A1 实现见《已入账账单维护》；已完成真实微信身份的解析、整理及只读证据联调，真实账本更正/撤销和真机完整流程仍待验收。

### 无尾号银行候选与批量确认

- 导入页 bank-suggestion.js 提供纯展示建议：缺少一个资金端点、银行及卡类型明确且没有尾号时，筛选同银行同类型的已有账户，排除已知端点及归档账户。唯一候选也不预选；多候选均列出；无候选保留手动选择或新建入口。点击推荐只改本地表单，保存后才形成整理决定。
- 可展开当前批次同银行、同类型、同缺失端点的其他开放问题，原始证据同层展示；默认不勾选。每个选项列出该问题覆盖的全部交易及笔数，可取消整个选项。换卡或收起会清空勾选，不形成跨批历史映射。
- 批量复用 reviewIssues.get/resolve：先校验全部问题的版本、状态、账户候选及批次，再顺序保存并传递更新版本；某项失败则停止、刷新并报告已返回成功的项数。每项沿用服务端原子性，整个批量不是一个数据库事务。
- 交易摘要跳过“/”等占位符、回退交易对方或中文经济性质；原始商品字段仍保留。日期/时间字段中的 Excel 1900 日期序号用无时区偏移的算术转换为可读钟面时间，不改原始存储，也不转换金额或订单号。

### 人工组合支付

用户允许核对详情后手工补齐。唯一 payment-resolution 策略验证全成分、非负整数分守恒（新 v2 允许显式零，旧 v1 仍须正数）、明确支出/还款性质和核对说明；来源与人工决定分区保存。只有有效决定才在 postability 解除指定两项歧义，其他硬阻断保持。旧 v26 事件按冻结 Evidence 兼容补齐成分，不重建批次。posting 按分项产生 expense/transfer 并在原整批事务中提交，草稿引用、现金检查及整批撤销涵盖全部账户。分项退款分配及人工分项事件的局部更正不支持（包括只有一个正数分项），明确阻断避免误改第一分项。详细逐条口径见入账逻辑说明 COMBO-01～07。
