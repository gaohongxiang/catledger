# 贷款、实际借还与信用卡分期

> 主线理解见[项目逻辑说明：贷款与分期](../招财猫记账本入账逻辑说明.md#loans)。本文展开当前兼容边界，不再把 A～F 各阶段的“当前”口径并排保留。历史实施、迁移、金额试算和修复过程完整保存在[归档](../归档/README.md)。

## 1. 先确定用户在做哪件事

| 意图 | 当前机制 | 是否生成正式交易 |
| --- | --- | --- |
| 记录已存在的分期方案 | 贷款资料和逐期计划，保存原本金、成本与历史进度 | 否 |
| 登记一笔真实借款/还款 | 明确实际账户、时间、本金/利息/费用，按规则记账 | 是，或者明确关联已有交易 |
| 关联已有账目 | 核对原交易完整组与构成，建立贷款关系 | 不再生成第二次付款 |
| 更正已有借还构成 | 受保护地替换完整交易组，保留旧关系快照 | 按净影响替换，不重复扣款 |
| 把实际付款分到旧贷款期次 | 实际付款与计划的分项分配 | 不改变已有资金流水 |
| 确认当前分期完成进度 | 连续进度和明确异常 | 否 |
| 补记某期缺少的实际费用 | 明确费用并检查是否已记 | 仅缺失且合法的费用 |

普通信用卡整单还款是资产到信用账户的转账，不自动变成分期或贷款待办。其他负债普通转账也不靠方向扫描生成待关联还款；只有明确确认本息费而选择暂不关联的实际还款进入对应待办。

## 2. 资料与计划

账户余额和贷款本金基准不是两个要相加的负债。贷款基准表示基准日日初已确认本金；未知不同于零。实际活动本金变化用于推导剩余本金，不能让历史任何时点出现不合法的负值。

当前新增分期保存完整方案和全期成本，历史已还期数由用户明确填写；不按日期自动补造已还。方案支持已有的等本等息、等额本息、等额本金、先息后本等方法，以及契约允许的利率/还款额和费用依据；具体字段、精度、可组合条件和期数上限见 shared，不在表单说明里另造一套公式。

只读试算不是实际入账。旧普通贷款的 `previewPlan/generatePlan` 沿用既有门禁，已有期次时不能重复生成；新分期资料与计划按当前入口一次建立。历史本金、一次性费用、后续应还不重复累计。提前还款不能由系统猜银行最终结清金额，未付计划按明确事实修订。

实现：[loan-service](../../cloudfunctions/catledger-api/src/loan-service.js)、[loan-schedule](../../cloudfunctions/catledger-api/src/loan-schedule)、[API 契约](../../shared/catledger-api.json)。

## 3. 明确实际借还

实际还款必须知道总额、资产账户、本金、利息、费用及其入账情况；没有的分项填明确零，未知不能提交。所有分项之和等于真实付款。已计入负债的费用通过转账清偿；未计入的利息/费才增加本次支出。

例如总额 1,000 元，其中本金 800、未计利息 180、未计手续费 20：资产减少 1,000、本金减少 800、本次费用支出 200。若费用已作为负债计入，不能再增加相同支出。此例仅说明守恒，不替代具体合同或银行凭据。

`loans.bookRepayment` 或导入 post 将实际资金、确认明细和可选贷款分配放在同一事务。可以明确暂不关联贷款，但不能用“暂不关联”跳过本息费核对。后续 `assignRepayment` 只建立已确认构成的分配；解除待办确认不删除原真实流水。

普通新放款只按适用贷款类型处理；信用卡原消费已经形成欠款时，创建分期资料不能再次生成到账或负债。活动借还存在后，直接修改本金基准、日期、类型和账户受到保护。

实现：[repayment-booking](../../cloudfunctions/catledger-api/src/repayment-booking.js)、[explicit-repayment-service](../../cloudfunctions/catledger-api/src/explicit-repayment-service.js)、[导入明确还款](../../cloudfunctions/catledger-import/src/explicit-repayment.js)。

## 4. 已有来源、整组更正和旧计划分配

选择已有来源时固定真实账户、时间、总额和全部交易版本；导入来源要展开为经济事件的完整活动组。原构成完全匹配时只关联；全额转账中尚未拆出的费用不能直接硬关联，要走整组更正。

更正在同一事务内处理原组软替换、新组、贷款关系、现金和本金校验及回执。撤销纯关联只解除关系；撤销更正按保留的原组与依赖恢复。外部退款、其他复用或版本变化不能被静默覆盖。明细普通编辑/删除不能绕过活动贷款组保护。

旧普通贷款仍支持部分或跨期分配。每个本金/利息/费用分项分别受实际付款份额及对应期次剩余约束，本金不能拿去补超额利息；未分配金额明确保留。更正或撤销实际付款会处理其计划分配，保留旧修订历史，不能伪装成从未发生。

先手工记录、后导入同笔还款时，需要核对完整组，不能凭金额相同去掉一笔。已属贷款组的历史成员禁止被外部单笔关系破坏。

测试：[loan-payments](../../test/loan-payments.test.js)、[loan-sources](../../test/loan-sources.test.js)、[loan-periods](../../test/loan-periods.test.js)、[explicit-repayment](../../test/explicit-repayment.test.js)。

## 5. 信用卡分期来源的接入

只有明确的信用卡账单、服务端信用账户、期号和分项证据满足条件，才使用“分期本金不重记消费”的分支。普通银行贷款不套用这个假设。

| 来源状态 | 处理 |
| --- | --- |
| 同用户、同账户下已有明确编号绑定 | 归入既有分期的对应期次 |
| 尚无唯一归属 | 正式入账后成为待建立/关联来源；明确费用仍按规则处理 |
| 从来源新建 | 带入已知账户、期数、进度；未知原本金/首期日期等由用户补充 |
| 先手动补费后导入同一期同类同额费用 | 在身份、来源和关系约束满足时复用，不再计一次 |
| 同一期不同银行身份、金额冲突或外部依赖 | 明确拒绝不安全关联，整次事务回滚 |

编号在用户和账户范围内使用，不是全局裸键；无编号不靠金额日期猜分期。来源必须已正式入账且关联有效才参与完成进度，预览不推进进度。

实现：[installment-link](../../cloudfunctions/catledger-api/src/installment-link.js)、[installment-items](../../cloudfunctions/catledger-api/src/installment-items.js)、[bank-installment profile](../../cloudfunctions/catledger-import/src/profiles/bank-installment.js)。

## 6. 连续进度、异常和补费

连续进度综合手动确认（未设置时继承适用历史进度）、有效已关联来源和既有结清期次，上限为总期数。先保留明确取消、未还、部分未还等异常，再判断其他期次是否处于完成范围。连续完成不等于逐期都有独立付款凭证。

| 场景 | 显示与影响 |
| --- | --- |
| 当前第 12 期，仅有效确认至第 10 期 | 前 10 期按进度完成；第 11 期缺凭证提示补账单 |
| 第 11 期无来源但没有明确未还 | 不直接称逾期 |
| 第 11 期明确未还且过应还日 | 显示逾期；部分未还单独保留 |
| 后来第 12 期有来源 | 推进适用连续进度，但不覆盖第 11 期明确异常 |
| 来源撤销或费用修改导致失效 | 重算有效来源，保留独立手动确认与异常 |
| 手动改完成至第 N 期 | 只改进度，不自动补本金或费用 |

明确补记时只补缺少的利息/手续费。撤销手动补费仍要检查导入、退款等依赖；历史计划修订必须明确表达历史修订，不覆盖银行原字段。未知金额或读取失败不能当作零。

## 7. 删除与重新建立

`archiveInstallment` 在同一用户锁事务内归档管理记录、解除来源 loan_id、释放编号绑定、维护版本并保存回执。正式交易、原文和来源身份保持。有效来源重新进入待建立范围；已失效来源不因解绑变成有效候选。

重新建立或关联仍检查账户、期数、金额、已有归属和同笔费用关系。同一费用的手动/导入证据应按原约束一起归属，不留下可重复建立的假独立费用。旧删除请求重放只返回原结果，不解除后来新关系。

旧归档残留由既有 `0025` 显式迁移处理；本次文档整理不执行迁移。保留接口中的恢复显示能力不等于页面存在“自动收回旧来源”的恢复操作。

## 8. 页面和验证边界

当前分期通过一张逐期表查看来源、确认进度、补缺费用和调整计划；普通旧贷款保留相应借还/对账能力。分期类型由资料判断，不能因为期次接口失败就切成旧入口。

期次使用有界追加读取，保留已展开内容；失败可重试，版本或身份变化后旧响应不回填。来自账户的列表/待办保持账户过滤，目录失败不能放宽到其他账户；停用账户仅供历史查询。

规则测试：[installment-flow](../../test/installment-flow.test.js)、[installment-flow-db](../../test/installment-flow-db.test.js)、[installment-flow-ui](../../test/installment-flow-ui.test.js)、[loan-detail](../../test/loan-detail.test.js)。部署、原生和手机状态只看[实施规划](../招财猫记账本实施规划.md)，不把旧记录中的阶段“已通过”当作当前所有流程均已验收。
