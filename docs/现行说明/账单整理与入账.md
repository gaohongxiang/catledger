# 账单整理与入账

> 本页描述系统当前行为；与代码冲突时以代码为准并修订本页。冻结契约（表结构、字段、checksum）见实施规划，此处不复制。

## 它做什么

用户在桌面「账单整理」把已解析的账单收成一个任务：核对付款方式对应哪个正式账户，处理分类等事项，再写入正式账本。不是自己账的可以整组或单笔标成「不入账」：原始证据保留，不创建正式账户，也不进总览。

上传与解析见 `账单上传与解析.md`。正式余额仍只认现有交易、账户、分类和标签。

## 数据怎么流

选文件组成整理任务 → 跨批次汇总付款方式组 → 用户新建、沿用已有账户或不入账 → 自动入账与待办只处理仍为待处理的行 → 确认入账写正式交易。

账户核对照分成三类：待核对、已沿用、不入账。付款方式里的券、红包后缀不拆成新账户，归到对应银行卡或余额账户。支付宝、微信和光大月结单都按付款方式分组核对；通用银行 CSV 仍用来源账户到正式账户的显式映射。

- 已确认过的付款方式默认沿用映射，不必每次再点确认。
- 整组不入账：该组当前待处理行改为忽略，并按来源类型、币种和付款方式规范键记住决定。下次同一组默认继续不入账，可改回。改回只删这条记忆，已有账户映射仍在。整组记忆覆盖支付宝、微信和银行付款方式（含光大末四位）。
- 只去掉组内部分行：只改这些行的处理状态，不写整组记忆。
- 用户点「不入账」的行保持可入账资格，以便和解析器判定不可入账的行区分，也允许改回。
- 自动入账、待办和总览只看待处理行；忽略行仍算作见到的证据，但不进正式账本。
- 排除优先于映射。账户明细只返回安全名称、金额、时间、方向，不返回原始付款方式或原始 JSON。

整理账户 API 在 `/api/v1/personal_finance/billflow/tasks/accounts/` 下：沿用/新建、整组排除/改回、组内明细、单笔跳过/改回。确认入账仍走整理任务的入账接口，写的是现有正式交易。

## 页面怎么用

桌面整理页按步骤推进：选账单 → 核对账户 → 交易分类 → 其他事项 → 确认入账。已经在确认入账的任务不能再塞进新文件。整理页解析光大月结单后，会用这份文件开始下一次整理并进入核对账户。需要新建的组提供「不入账 / 看明细 / 选中的不入账」；已不入账的组提供「改回」。分类页处理未分类待办；退款、冲突等留在分类，不进其他事项。移动端整理只读摘要，完整操作在桌面。

## 扩展时改哪里

- 改变入账门槛、不入账是否记住、改回是否恢复映射，先改需求与业务规则，再改实施规划冻结契约。
- 给银行来源也做整组不入账记忆，要扩展排除允许的来源类型，并补三库唯一约束与隐私查询。
- 不要用金额相同或时间接近自动当成同一付款方式；不要让排除或改映射改写来源身份。

## 版本与旧数据

付款方式映射和排除记忆是独立实体，不改来源身份。旧二进制可以忽略新表；数据库级回滚必须用切换前备份。用户改回后，同一付款方式若已有映射则继续沿用。
