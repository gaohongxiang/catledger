# 账单整理与入账

> 本页描述系统当前行为；与代码冲突时以代码为准并修订本页。冻结契约（表结构、字段、checksum）见实施规划，此处不复制。

## 用户流程

桌面「账单整理」采用同一路由内的紧凑工作台，只包含「交易核对」和「账单记录」两个内部视图，切换不写查询参数、不跳转页面，也不挂载旧重复/转账工作台。「账单记录」保留原始文件、解析行、来源账户和支付方式映射，并提供上传、重解析和隐私删除；它不再提供绕过统一整理流程的逐行直接入账。

「交易核对」内部仍是一条连续三步流程。第一步和账单份数只展开当前工作台的「本轮账单」区域：账单清单始终以低强调的「添加账单」作为唯一上传入口，上传成功即加入本轮，不再要求二次勾选；没有本轮账单时不显示底部操作，有账单后流程推进区只在右下角显示主操作「开始整理 N 份账单」。本轮清单右侧的移除操作只把误选账单移出本轮，不删除账单记录或原始文件。上传只保存并解析原始资料，不打断用户核对资金账户；点击「开始整理」后先执行本轮账户预检，已有可靠映射直接复用，只有尚未解决的资金账户才以紧凑弹窗集中确认。来自不同账单但币种和可辨识账户名称一致的资金账户合并成一张核对卡，用户的一次选择会应用到各来源。每张卡可选择「仅本轮忽略」或「以后自动忽略」：前者只跳过当前选择的账单，下次仍会询问；后者保存当前用户的长期规则。长期忽略项继续集中显示在弹窗底部，用户可取消忽略、重新选择正式账户并加入本轮，不会成为不可恢复的隐藏状态。确认后创建更新并进入「必须处理」。创建更新后来源快照锁定，返回第一步会以紧凑清单显示已选文件、来源类型和有效记录数，概览不再重复列出文件名。来源锁定后不提供原地增删或重新分析，原上传位置改为「放弃本轮，重选账单」，概览不重复显示该操作；旧轮进入 `abandoned` 终态并保留审计事实，随后回到新一轮来源选择。已完成入账后回到新一轮时仍由「添加账单」上传，新文件上传完成即进入下一轮来源选择。顶部三步保留本轮账单数、待处理问题数和可入账结果数，供用户一眼判断进度；第二步处理必要问题，第三步统一入账，整批入账完成后第三步切换为已入账结果。「开始整理」与「继续处理」是同一主操作在不同状态下的文案，均位于当前工作卡右下角；问题列表已经展开时不重复显示。页面不展示内部轮次编号；自动同步状态随顶层「账单整理」标题常驻显示，不再独占结果控制行。

结果页不再并列显示「重新整理」和「刷新」。页面打开、操作完成、窗口重新获得焦点时会自动同步服务器状态；从第一步返回必要问题时显示「继续处理 N 个问题」，第二步已经展开问题列表时不重复显示该按钮；来源清单不再显示返回交易核对按钮。第三步「可入账」标题右侧常驻整批入账按钮：仍有必要问题时按钮禁用并明确提示先处理的问题数，问题清零后才可执行整批入账。

必要问题卡片只保留两层：卡头集中显示问题类型、裁决提示、记录数和处理动作，交易标题、日期、账户、分类、金额及证据入口只在明细行展示一次；不再用重复标题和独立底部操作栏占用纵向空间。

「核对整理数字」分两段展示完整守恒关系：有效证据先扣除附加证据得到最终事件，最终事件再扣除已排除事件得到保留事件；保留事件必须等于可入账、待处理与已入账之和，避免把证据合并和事件状态混为一套数字。

结果页只把本轮账单份数、待处理问题组数和可入账交易数作为主数字。整理后总数、已排除、已入账以及证据守恒均降为次级摘要；完整核对数字默认收起，按需展开后核对两条守恒关系：

- 有效证据 = 最终事件 + 已确认附加证据；
- 最终事件 = 已入账 + 待入账 + 必须处理 + 已排除。

顶部第三步「可入账 N」本身就是可入账结果入口，点击后直接展示交易明细和整批入账按钮，不在下方重复页签。下方只保留四个平级视图：「必须处理」「交易异常」「已排除」「去重核对」，每项常驻显示数量；不再增设「全部」「关系确认」「待入账」或「已入账」工作页签。「交易异常」集中展示账单明确标记为关闭、失败，或核心字段、方向发生冲突的记录；关闭和失败记录不要求用户补账户，也不得进入整批入账。各视图只保留一行精确说明，不显示「结果明细」等无业务含义的层级文案。用户执行整批原子入账后，顶部第三步直接显示本轮已入账数量，页面只给出完成提示并指向正式「记账与明细」查看结果。「必须处理」只承载资金账户、经济性质、分类和关系等需要用户决定的问题；「去重核对」是独立审计视图，不混入问题卡，也不改变任何事件状态，并默认完整展开全部核对组，不再要求用户二次点击「查看全部」。事件列表直接展示日期、经济性质、交易摘要、记账账户、生活分类、金额、状态和必要原因，来源数量直接作为「原始记录」入口，不再把同一份来源摘要同时写进卡片和弹窗。去重核对按同一来源再次观察、跨来源同一事件、转账两侧和还款两侧逐组解释多条来源记录为何只形成一个最终事件，并直接进入完整原始记录；金额或日期相同只作为候选条件，界面明确提示不能单独证明同一事件。「必须处理」优先读取服务端稳定问题投影，一张卡片对应一个待决定事项，并带精确成员与版本；同组多笔独立事件可以原子应用相同字段答案，但不会因此合并身份。疑似同一事件可明确选择同一笔、各自独立或排除无效证据，退款问题展示原交易候选。旧更新尚未重整、问题投影为空时，页面安全回退到事件列表，不把临时视觉分组冒充稳定决定。经济性质、来源类型和原因码统一转换为当前语言的用户文案，未知内部码只显示通用核对提示，不直接暴露英文枚举。原始记录下钻按来源文件和账单行定位，按来源原始顺序完整展示持久化字段，允许重复列名且不以规范化摘要替代账单原文。移动端读取同一问题与状态口径。

## 数据流与语义

创建更新时锁定所选批次的不可变来源快照，同一活动批次不能被另一更新重复领取。统一整理引擎从原始证据和正式账户快照生成经济事件、证据归属、关系与守恒计数；规划阶段不创建正式 `Transaction`。

相同来源身份先归入同一判断单元。本分支 identity-v2 只信任稳定交易号、完整订单组合，或无稳定标识时的文件 SHA-256 + 物理 locator；整理器也会把旧 identity-v1 中没有稳定标识的共享强指纹按物理行拆开。正式站旧轮仍由 identity-v1 生成，发布并新建轮次前不得使用其数量入账。跨来源自动合并还必须有稳定业务引用和金额、币种、账户、方向、时间等语义共同支持。仅金额相同或时间接近不会自动合并。日期级银行入账与平台明细只有在同一已映射账户、同方向、同币种、同额、同日且候选可一一对应时才作为同一事件证据；银行只表达普通入账、平台明确表达退款时，以平台退款语义为准，因此原消费和部分退款会各自合并证据，仍保留两笔事件及 `refund_of` 关系。普通转入不会只凭资金方向认作收入；退款保持独立事件并受原消费累计退款上限约束；信用卡还款和内部转账只有关系明确时自动配对。

经济性质、资金方向、记账账户、对方账户、生活分类、事件关系和判断状态彼此独立。未分类支出可以入账；经济性质未知、关键字段缺失或关系歧义进入 `needs_action`。问题动作只提交人工事实和精确成员版本，统一服务端可入账校验重新派生 `ready`，客户端不能直接把事件改为可入账。字段决定通过掩码持久化，后续自动整理不能覆盖；关系决定写入事件关系或正式交易链接，用户也可以明确排除事件或无效证据。

支付宝的单文件导入与账单整理证据解析共用同一套具体产品动作识别。商品说明中的收益发放、买入、买入退款、卖出、充值、提现、转入、转出、转账和还款先于“投资理财”等宽泛交易分类判断；其中“收益发放”标准化为投资收益流入付款方式所映射的资金账户，不再要求把基金公司当作本人账户，也不再产生转账双方或经济性质待确认。当前预发布规则直接定为 `alipay-normalization-v1`，不维护历史语义分支。

微信 CSV/XLSX 的单文件导入与账单整理证据解析共用同一套动作和状态分类器。手续费优先于提现，零钱充值、零钱提现、信用卡还款、转账、红包、群收款、普通支付和零钱通/理财通分别输出稳定来源类型；退款保留资金流入方向并以退款效果表达，失败和关闭记录进入交易异常。单文件直接导入无法保存异常证据，因此跳过失败和关闭记录；账单整理则完整保留原始证据。当前预发布规则直接定为 `wechat-normalization-v1`，不维护历史语义分支。

支付宝和微信的动作分类同时输出统一的双边资金投影，传统单文件导入与统一整理器共同消费该投影，不各自维护充值、提现和还款的账户方向。账单归属侧复用批次冻结的来源账户映射，付款侧复用现有付款方式映射；两种平台的还款目标共用“精确别名优先、唯一发卡行信用卡兜底”的解析器。同一发卡行只有一个已映射信用卡时直接复用，存在多个不同正式账户或“花呗｜信用购”这类未建立精确映射的复合目标时保持人工确认。两侧账户都已解析、币种一致且不相同时，整理器直接生成 `ready` 的内部转账或还款事件。例如微信零钱已映射到零钱账户、提现付款方式已映射到尾号 5564 的银行卡时，结果直接是「微信零钱 → 5564」；“兴业银行信用卡还款”唯一对应已映射的兴业信用卡时，结果直接是「微信零钱 → 兴业信用卡」，均不再产生转账双方待确认。缺少任一映射、账户相同、候选不唯一或证据冲突时仍进入必要问题。投影只在解析和规划内存中传递，最终仍写现有经济事件的两个账户字段，不新增账本或数据表。

平台还款和银行账单同时存在时，整理器不会再把完整双边投影与单边银行流水当成互斥模型。银行资产侧的还款支出或信用卡侧的还款流入，在金额、币种、对应正式账户、方向、七十二小时时间窗和明确还款语义全部兼容且候选唯一时，作为附加证据并入平台还款事件；平台投影继续提供还款性质和双方账户。每个账户侧出现多个候选时不自动选择，相关记录进入同一事件裁决。普通同额流水、无还款语义的入账和账户不一致记录不会因此归并。

账户待确认问题中的记账账户选择同时写入本轮事件和当前用户的账户映射，不再只修正本轮结果。付款方式具备可复用的稳定别名时保存付款方式映射；没有付款方式且来源账户能安全代表该行时保存来源账户映射。后续上传或重解析命中同一来源账户，或命中同一来源类型、付款方式别名和币种时自动复用；整理器也会在每次新建轮次时读取最新映射，因此规则更新前已解析但尚未入账的银行证据无需重传文件。通用的“银行卡”“未知”等无辨识度文本不会形成跨记录映射。账户映射只改变归属，不改变来源身份，也不会把两条来源记录合并。

支付宝账单中的“余额”和“账户余额”统一识别为“支付宝账户余额”，余额宝仍保持独立。旧版“账户余额”映射继续兼容；旧、新别名若指向不同正式账户则停止自动沿用并要求重新确认，确认后只保留当前别名映射。

## 入账、纠错与撤销

默认「全部入账」只在本轮没有 `needs_action` 时执行，把所有 `ready` 事件作为一个原子动作写入正式账本。显式部分入账由独立资源接口提供，但不是默认按钮。正式余额、现金流和报表仍只认现有 `Transaction`、`Account`、分类和标签。

入账在同一用户隐私事务中写正式交易、事件交易链接、事件状态、守恒计数和动作结果。更新版本、事件版本、幂等键和请求摘要共同裁决重放与并发；任一账本写入或 CAS 失败都会整体回滚，不留下半成品。

尚未入账的事件可按字段纠错或排除。已入账事件不能直接改写；必须先检查该事件的正式交易是否存在、是否被修改或共享、是否有贷款/分期引用以及转账双方是否完整。安全时，同一事务历史化旧链接、软删旧交易并重建；不安全时持久化 `action_required`。

整轮撤销同样先做只读影响检查。只有所有正式交易仍完整且未被其他事实引用时才允许执行；成功后账本软删除、事件回到待入账，历史证据链接继续保留。

## API 与扩展边界

前端调用四组资源接口：

- `updates`：创建、列表、详情、初次整理和放弃未入账轮次；
- `events`：状态分页、证据下钻、字段纠错和排除；
- `review_issues`：问题分页、详情和带版本/幂等保护的原子解决；
- `actions`：默认整批入账、显式部分入账、撤销影响检查和撤销。

旧 billflow 路由、HTTP handler、前端 service、repository、状态机、模型和页面均已删除，不提供别名、双读、双写或兼容字段。历史 `pf_billflow_*` 表和 `pf_category_alias_mapping` 只由 `personalfinance/legacydata` 描述，用于旧迁移结构校验以及用户数据计数和删除；该包没有查询、整理、入账或撤销服务，不是第二套运行架构。

扩展新来源时在来源转换器注册动作与双边资金投影，不得把来源关键词下沉到整理器，也不得绕过来源身份、守恒计数和隐私仓储。新增关系、入账门槛或状态语义时，先更新需求与业务规则，再冻结迁移及 SQLite/MySQL/PostgreSQL 契约。

## 当前限制

- v010 迁移只创建问题投影结构，不自动改写已有更新；升级前创建且尚无稳定问题投影的旧轮次应放弃后以相同或调整后的来源创建新一轮，不再通过页面重复重算旧轮；
- 服务端已支持关联已有正式交易，桌面首轮交互仍需补齐对应搜索与选择入口的真实数据验收；
- 当前总览主要从核心交易类型推导现金流，退款、借款、偿还本金和余额调整的最终语义投影仍需在第一次真实入账前校准；
- 正式数据的一致性检查存在一项升级前已出现的批次派生计数不一致，修复前禁止第一次真实入账；
- PFV2-1802 已在分支修复光大不同物理行被强内容指纹误判的问题，并补齐旧 v1 拆分与跨来源基数回归；正式站旧轮尚未发布和重建，其重复证据、最终事件、待处理和可入账计数仍不得作为入账依据；原始证据完整，可在发布后按新规则重建。

冻结设计见[个人财务待处理问题与关系裁决设计.md](../个人财务待处理问题与关系裁决设计.md)。当前正式批次保持未入账，问题工作台和报表语义通过真实数据验收后再开放入账。

## 版本与回滚

schema v010 在 v009 更新、来源、经济事件、证据、关系、正式交易链接和动作审计之上新增稳定问题及成员投影。正式切换前必须备份；数据库级回滚使用切换前一致备份，不依赖旧页面或旧 API。未入账任务、todo 和自动候选允许在备份后按新规则重建，正式交易、不可变证据、来源身份和人工事实必须保留。
