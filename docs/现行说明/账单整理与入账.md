# 账单整理与入账

> 本页描述系统当前行为；与代码冲突时以代码为准并修订本页。冻结契约（表结构、字段、checksum）见实施规划，此处不复制。

## 它做什么

用户在桌面「账单整理」把已解析的账单收成一个任务：核对付款方式对应哪个正式账户，处理不入账、合并和分类，再写入正式账本。不是自己账的可以整组忽略或单笔不入账：原始证据保留，不创建正式账户，也不进总览。

上传与解析见 `账单上传与解析.md`。正式余额仍只认现有交易、账户、分类和标签。

## 新工作流底座

schema v009 已建立 `personalfinance/organizer` 的更新、来源、经济事件、证据、关系、正式交易链接和动作审计投影，并提供强制 `uid` 隔离的隐私仓储、版本 CAS、守恒计数和幂等动作裁决。迁移会把旧流程中仍然有效的已入账证据链接一次性回填为已完成事件，保留原始证据到正式交易的追溯关系。

统一整理引擎从冻结的来源快照读取原始证据和正式账户快照，一次生成经济事件、证据归属、事件关系与守恒计数。相同来源身份会归入同一判断单元；跨来源自动合并还必须有稳定业务引用及金额、币种、账户、方向、时间等语义共同支持，仅金额相同或时间接近不会合并。普通转入不会只凭方向认作收入；退款保持独立事件并受原消费累计退款上限约束；信用卡还款和账户转账只有在一对一关系明确时自动配对，歧义只阻塞相关事件。未分类支出可以继续，经济性质或关系不清才进入待处理。

整理动作通过版本和幂等键领取，事件计划、证据、关系、守恒计数和动作结果在同一隐私事务中落库；失败不留下半成品，并发重放收敛到同一结果。规划阶段只写 organizer 投影，不创建正式 `Transaction`。

新入账引擎按来源批次有序加进程内锁，并在同一用户隐私事务中写正式 `Transaction`、事件交易链接、事件状态、守恒计数和动作结果。默认整批确认遇到 `needs_action` 会整体拒绝；只有显式“先入账已确认项”才写当前全部 `ready` 事件并进入部分入账，后续重放不会重复创建交易。任一账本写入或状态 CAS 失败会连同本次动作整体回滚。分类为空不阻塞收支、退款、转账或还款，正式余额仍只认核心账本。

撤销分成只读影响检查和显式执行。检查会核对正式交易是否存在且未被修改、是否被其他更新或旧批次证据共享、是否存在活动贷款/分期引用，以及转账双方是否完整；任何一项不安全都会返回原因并在执行请求中持久化 `action_required`，不会伪装成功。全部安全时，账本软删除、事件回到待入账、守恒计数、更新状态和动作审计在同一事务完成；原事件交易链接继续保留为历史证据。

这是直接替换旧工作流的实现，不是兼容层：新代码不通过适配器读写旧 billflow/reconciliation 状态。当前 API 和页面尚未切到 organizer，字段级纠错也尚未完成，因此下面仍描述用户现在能操作的旧页面；切换完成前新引擎不会被正式页面调用。

## 数据怎么流

选文件组成整理任务 → 跨批次汇总付款方式组 → 用户新建、沿用已有账户或忽略账户 → 自动入账与待办只处理仍为待处理的行 → 确认入账写正式交易。

账户核对照分成三类：待核对、已沿用、忽略账户。付款方式里的券、红包后缀不拆成新账户，归到对应银行卡或余额账户。支付宝、微信和光大月结单都按付款方式分组核对；通用银行 CSV 仍用来源账户到正式账户的显式映射。

- 已确认过的付款方式默认沿用映射，不必每次再点确认。银行专用月结单按「银行名 + 卡种 + 末四位」组成付款方式再对已有账户；当前已落地的是光大月结单显示为「光大银行信用卡(末四位)」。名称能唯一对上就直接沿用。不得只按末四位去对其他银行的卡。支付宝、微信和银行账单里同一张卡合并成一块，笔数加总。已经沿用的正式账户若被删除或隐藏，该组回到待核对，尚未确认入账的整理任务退回核对账户，合并和确认入账都不能继续；映射记录仍保留，重新新建或沿用时覆盖。已经确认入账的任务不因删账户而回退。
- 整组忽略：该组当前待处理行改为忽略，并按来源类型、币种和付款方式规范键记住决定。下次同一组默认继续忽略，可改回。改回只删这条记忆，已有账户映射仍在。整组记忆覆盖支付宝、微信和银行付款方式（含光大末四位）。核对账户点「忽略账户」走这条路径。
- 只去掉组内部分行：只改这些行的处理状态，不写整组记忆。
- 用户点「不入账」的行保持可入账资格，以便和解析器判定不可入账的行区分，也允许改回。
- 自动入账、待办和总览只看待处理行；忽略行仍算作见到的证据，但不进正式账本。
- 排除优先于映射。账户明细只返回安全名称、金额、时间、方向，不返回原始付款方式或原始 JSON。

整理账户 API 在 `/api/v1/personal_finance/billflow/tasks/accounts/` 下：沿用/新建、整组排除/改回、组内明细、单笔跳过/改回。确认入账仍走整理任务的入账接口，写的是现有正式交易。

## 页面怎么用

桌面整理页上传后立刻解析：支付宝、微信 CSV/XLSX 自动识别；光大 PDF 仍要选专用模板。解析成功的文件出现在选账单里。点「开始整理」后按步骤推进：核对账户（信用卡月结单页眉的账单日/还款日/额度跟在对应付款方式下面；新建信用卡会把账单日写入账户，还款日和额度只在这里展示；刚新建的账户可在已沿用卡片上记下现在多少钱，也可跳过）→ 整理交易（后台先合并为唯一交易，再只对唯一交易确定分类；每笔可勾选不入账）→ 其他事项 → 确认入账。确认入账前可增删本轮文件，确认后锁定。

整理交易顶部使用后端唯一交易计划展示“有效证据 − 合并重复 = 最终交易”，并分别列出待确认关系与待补分类。五张摘要卡都直接切换下面的对应内容：安全证据摘要、最终交易、重复证据对照、仍阻塞入账的关系、待补分类；不再另放 pane 或桶级 Tab，也不把关系卡跳去无关内容。信用卡月结单属于同一账户、同日、同额同向且两边数量相等时按等量事件匹配；没有稳定交易号的日期行用物理行作为 case 成员，保证两笔真实同额消费不会被来源 fingerprint 压成一个身份。退款先做同日匹配，再允许 48 小时内唯一对照。重复证据只用于审计或处理异常，分类只作用于最终交易；支付宝生活分类优先，微信“商户消费”和银行“其他”不会覆盖清晰分类。未分类不阻止余额入账，关系说不清才阻止确认。首次确认前只保存预览，不写正式账本；确认后 `same_event + applied` 才显示已应用合并。

同来源明确退款按原消费状态中的退款金额、退款收入金额、同一商户、相反方向和先消费后退款时间窗做唯一匹配。命中后自动持久化 `refund_reversal` 关系并关闭旧的逐行退款待办，部分退款同样适用；原消费和退款仍各占一笔最终交易。无法唯一解释的退款、还款、转账、分期和账户关系才保留为待确认关系。

来源明确为收入或支出的普通转账按该方向进入最终交易，分类缺失只进入待补分类；充值、提现、不计收支和还款继续按账户关系处理。信用卡“款项转入”直接显示为已识别还款，只有付款账户未知时才阻塞，不再显示“可能是还款”。

迟到的银行或信用卡账单可以匹配已经 `linked` 的历史支付宝、微信证据；若历史正式交易完整，只补新证据关系，不创建第二笔正式交易。候选规则当前为 v5，旧版本未决定候选不进入当前开放列表。打开页面本身不重新分析；用户点「重新分析本次账单」才刷新任务候选和待办。移动端整理仍为只读摘要。

## 扩展时改哪里

- 改变入账门槛、不入账是否记住、改回是否恢复映射，先改需求与业务规则，再改实施规划冻结契约。
- 给银行来源也做整组不入账记忆，要扩展排除允许的来源类型，并补三库唯一约束与隐私查询。
- 不要用金额相同或时间接近自动当成同一付款方式；不要让排除或改映射改写来源身份。

## 版本与旧数据

付款方式映射和排除记忆是独立实体，不改来源身份。旧二进制可以忽略新表；数据库级回滚必须用切换前备份。用户改回后，同一付款方式若已有映射则继续沿用。

## 与目标需求的差异

当前页面仍以五步整理任务和任务级确认作为主要闸门；v009、organizer 仓储、统一经济事件整理、原子入账和安全撤销已经落地，但字段级纠错、资源化 API 和新结果流尚未依次切换。切换时直接删除旧 billflow 路由和页面，不维护双读、双写或兼容字段。
