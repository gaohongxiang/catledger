# 账单整理与入账

> 本页描述系统当前行为；与代码冲突时以代码为准并修订本页。冻结契约（表结构、字段、checksum）见实施规划，此处不复制。

## 它做什么

用户在桌面「账单整理」把已解析的账单收成一个任务：核对付款方式对应哪个正式账户，处理不入账、合并和分类，再写入正式账本。不是自己账的可以整组忽略或单笔不入账：原始证据保留，不创建正式账户，也不进总览。

上传与解析见 `账单上传与解析.md`。正式余额仍只认现有交易、账户、分类和标签。

## 数据怎么流

选文件组成整理任务 → 跨批次汇总付款方式组 → 用户新建、沿用已有账户或忽略账户 → 自动入账与待办只处理仍为待处理的行 → 确认入账写正式交易。

账户核对照分成三类：待核对、已沿用、忽略账户。付款方式里的券、红包后缀不拆成新账户，归到对应银行卡或余额账户。支付宝、微信和光大月结单都按付款方式分组核对；通用银行 CSV 仍用来源账户到正式账户的显式映射。

- 已确认过的付款方式默认沿用映射，不必每次再点确认。银行专用月结单按「银行名 + 卡种 + 末四位」组成付款方式再对已有账户；当前已落地的是光大月结单显示为「光大银行信用卡(末四位)」。名称能唯一对上就直接沿用。不得只按末四位去对其他银行的卡。支付宝、微信和银行账单里同一张卡合并成一块，笔数加总。已经沿用的正式账户若被删除或隐藏，该组回到待核对，尚未确认入账的整理任务退回核对账户，合并和确认入账都不能继续；映射记录仍保留，重新新建或沿用时覆盖。已经确认入账的任务不因删账户而回退。
- 整组忽略：该组当前待处理行改为忽略，并按来源类型、币种和付款方式规范键记住决定。下次同一组默认继续忽略，可改回。改回只删这条记忆，已有账户映射仍在。整组记忆覆盖支付宝、微信和银行付款方式（含光大末四位）。核对账户点「忽略账户」走这条路径。
- 只去掉组内部分行：只改这些行的处理状态，不写整组记忆。
- 用户点「不入账」的行保持可入账资格，以便和解析器判定不可入账的行区分，也允许改回。
- 自动入账、待办和总览只看待处理行；忽略行仍算作见到的证据，但不进正式账本。
- 排除优先于映射。账户明细只返回安全名称、金额、时间、方向，不返回原始付款方式或原始 JSON。

整理账户 API 在 `/api/v1/personal_finance/billflow/tasks/accounts/` 下：沿用/新建、整组排除/改回、组内明细、单笔跳过/改回。确认入账仍走整理任务的入账接口，写的是现有正式交易。

## 页面怎么用

桌面整理页上传后立刻解析：支付宝、微信 CSV/XLSX 自动识别；光大 PDF 仍要选专用模板。解析成功的文件出现在选账单里。点「开始整理」后按步骤推进：核对账户（信用卡月结单页眉的账单日/还款日/额度跟在对应付款方式下面；新建信用卡会把账单日写入账户，还款日和额度只在这里展示；刚新建的账户可在已沿用卡片上记下现在多少钱，也可跳过）→ 整理交易（先切合并或分类；每笔可勾选不入账）→ 其他事项 → 确认入账。确认入账前可增删本轮文件，确认后锁定。

合并使用任务级只读投影，不再由前端从全局待办猜测。候选关系图的一个连通分量只显示一组；只有金额币种、同一账户、方向、日期与对方证据都兼容，且不存在第二种合法配对时才自动形成预览合并。首次确认前只显示预览，不写正式账本；确认后 `same_event + applied` 才显示已合并。相互独立、内部转账、退款、暂缓和需操作分别标明。点某组会携带准确 case ID 打开对应对账详情，不进入无筛选的全局列表。

迟到的银行或信用卡账单可以匹配已经 `linked` 的历史支付宝、微信证据；若历史正式交易完整，只补新证据关系，不创建第二笔正式交易。候选规则当前为 v2，旧 v1 未决定候选不进入当前开放列表。打开页面本身不重新分析；用户点「重新分析本次账单」才刷新任务候选和待办。移动端整理仍为只读摘要。

## 扩展时改哪里

- 改变入账门槛、不入账是否记住、改回是否恢复映射，先改需求与业务规则，再改实施规划冻结契约。
- 给银行来源也做整组不入账记忆，要扩展排除允许的来源类型，并补三库唯一约束与隐私查询。
- 不要用金额相同或时间接近自动当成同一付款方式；不要让排除或改映射改写来源身份。

## 版本与旧数据

付款方式映射和排除记忆是独立实体，不改来源身份。旧二进制可以忽略新表；数据库级回滚必须用切换前备份。用户改回后，同一付款方式若已有映射则继续沿用。
