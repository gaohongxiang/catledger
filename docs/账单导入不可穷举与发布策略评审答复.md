# 招财猫记账本：账单导入不可穷举与发布策略评审答复

> 历史归档：本文保留2026-09-04的验收或评审背景，不代表当前实现、门禁或授权。当前状态以《招财猫记账本实施规划》0.3、0.5和第19章为准。

> 文档性质：独立架构评审意见，用于和其他评审结果对照；不是已确认规格，不授权实施。
>
> 日期：2026-09-04

## 一、一句话结论

可以发布，但必须放弃“覆盖完支付宝、微信以及各家银行账单以后才能发布”的目标，改成：

> 只对经过认证的模板和业务能力负责；只有满足机器可检查证明义务的账务结论才能进入正式账本，其余输入必须明确进入确认、隔离或拒绝状态。

我们无法证明下一份账单一定认识，但可以把系统设计成：下一份没有被充分证明认识的账单，无权混进正式账本。

这不是降低目标，而是把一个不可完成的开放世界穷举问题，改造成一个可以审计、可以测试、可以发布的安全边界问题。

优化顺序必须是字典序，不能做加权平均：

1. 关键未知或冲突穿透入账门禁为零；
2. 重复入账、部分提交、跨用户污染为零；
3. 已入账后的系统归因财务纠错尽量趋零；
4. 在前三项约束下扩大认证模板覆盖率；
5. 再提高自动整理率、降低用户确认负担。

一千条普通消费识别正确，不能抵消一条还款、退款或转账被静默记错。

## 二、当前架构是否需要推倒重来

不需要。

现有几个核心边界是有价值的，应继续保留：

- Evidence 保存不可变来源事实；
- EconomicEvent 表达现实经济活动；
- FinanceUpdate 隔离未确认工作结果；
- ReviewIssue 承载用户必须处理的不确定性；
- Transaction 继续作为余额与统计唯一权威；
- Account 只保存正式账户；
- 整批 posting 使用事务、幂等和用户隔离；
- 来源适配器不能直接写 Account 或 Transaction。

真正缺少的是 Evidence 与 EconomicEvent 之间的一层“语义防火墙”。当前来源解析、规范化、账户推导和业务语义有时仍直接流入 planner，导致 planner 逐渐认识“支付宝”“微信”“已存入零钱”“信用借还”等来源字符串。继续这样发展，后续每家银行都会给核心 planner 增加一批分支。

应改成：来源层只输出有证据、有版本、有未知状态的语义声明；核心层只理解统一的语义声明和账本影响，不理解来源文案。

## 三、推荐目标架构：失效安全的账单编译器

```text
不可信原始文件
  ↓
ContainerDecoder
  安全读取 CSV / XLSX / 数字 PDF；不解释财务语义
  ↓
RawEvidence
  原文、单元格位置、文件/行稳定身份、不可变
  ↓
TemplateAttestor + CapabilityProfile
  认证来源、导出渠道、模板族、产品类型和能力范围
  ↓
SourceObservation
  只陈述来源实际写了什么；空白、/、解析失败分别表达
  ↓
SemanticClaim
  带证据、规则版本、推导方式、备选和冲突的类型化结论
  ↓
CandidateEconomicEvent / EventGraph
  组装事件候选、去重候选、退款/转账/还款关系候选
  ↓
LedgerImpactCompiler
  用纯领域模型生成 Transaction 影响草稿
  ↓
SafetyGate + Reconciler
  检查证明义务、行覆盖、资金不变量和来源控制总数
  ↓
ReviewPlanner
  只把尚可由用户安全补足的证明义务聚类后交给用户
  ↓
FinanceUpdate Snapshot
  冻结证据集、规则集、用户决定、影响摘要和 expected token
  ↓ 用户确认整批
原子 Posting
  ↓
Transaction / Account
```

这套架构是“编译器式确定性核心 + 受限版本化规则包 + 来源/产品语义代码适配器”。AI/OCR 可以在候选或开发辅助层出现，但不能获得入账权。

## 四、最关键的数据类型不是 confidence，而是 proof

当前很多系统会给推导结果一个 `0.93` 的置信度，然后设置阈值自动通过。对账务系统不够安全：模型或启发式规则的自报分数不是财务证明。

关键字段应使用代数类型，而不是把空字符串、`null`、`/` 和未知混在一起：

```ts
type Conclusion<T> =
  | { state: 'known'; value: T; provenance: Provenance }
  | { state: 'source_blank'; marker: string; evidenceRefs: string[] }
  | { state: 'not_applicable'; evidenceRefs: string[] }
  | { state: 'parse_failure'; reasonCode: string }
  | { state: 'unsupported'; tokenFingerprint: string }
  | { state: 'ambiguous'; alternatives: Candidate<T>[] }
  | { state: 'contradiction'; claims: Claim<T>[] }
  | { state: 'needs_user'; choices: Candidate<T>[] }
```

每个 `known` 还要标明它为何有资格被认为已知：

- `SOURCE_ASSERTED`：来源在已认证模板中明确给出；
- `CERTIFIED_RULE_DERIVED`：由版本固定、唯一命中的确定性规则推出；
- `USER_CONFIRMED`：用户针对明确影响作出结构化决定；
- `MODEL_SUGGESTED`：模型候选，只能排序和解释，不能满足关键证明义务；
- `CONFLICT`：多个证据或规则互相矛盾，必须阻断。

### 证明义务

一笔候选交易进入 posting 之前，服务端必须能机械地证明：

1. 输入命中一个已启用的精确 CapabilityProfile；
2. 文件中的所有记录、工作表和相关页面均有覆盖处置；
3. 金额、币种、时间和资金方向有效；
4. 影响余额的账户端完整且属于同一用户；
5. 业务性质满足对应产品的最小字段集合；
6. 唯一身份、重复关系和事件集合没有未解决冲突；
7. 退款、转账、还款、贷款拆分满足各自硬不变量；
8. 有控制总数时已经精确核对；没有时明确标记无法核对；
9. Evidence、规则包、用户决定和事件集合摘要没有发生版本变化；
10. 统一 LedgerImpactCompiler 给出的影响通过余额、幂等和事务门禁。

只要缺少一项，就不是降低置信分，而是没有 posting 资格。

## 五、怎样定义“支持一份账单”

不能再笼统写“支持支付宝”“支持微信”“支持工商银行”。支持范围至少应由以下维度共同确定：

```text
来源机构
× 导出渠道（App/Web/邮箱/网银）
× 文件容器（CSV/XLSX/数字PDF）
× 模板族与结构指纹
× 产品类型（钱包/储蓄卡/信用卡/贷款）
× 货币
× 已认证业务能力
× 解析器/规则版本
```

例如，同样叫“微信账单”，CSV 和 XLSX 可能不同，旧版和新版状态枚举可能不同；同一家银行的储蓄卡、信用卡和贷款也不是同一种产品语义。

建议建立四级能力状态：

| 等级 | 含义 | 能否生成账本候选 | 能否 posting |
| --- | --- | --- | --- |
| `UNSUPPORTED` | 无法精确认定模板或关键语义 | 否，只生成安全诊断 | 否 |
| `PREVIEW_ONLY` | 可以读取和展示，但尚未认证财务解释 | 可以生成不可信候选 | 否 |
| `ASSISTED` | 关键语义可确定，但需要用户完成明确问题 | 可以 | 证明义务补齐后可以 |
| `CERTIFIED` | 指定模板和能力经过完整门禁 | 可以自动整理 | 仍需用户整批确认 |

未知模板不得因为“看起来很像”而自动继承最近的 profile。模糊匹配只能推荐候选 profile，不能授予 posting 权限。

用户界面不需要展示这些技术词，可以翻译为：

- 完整支持；
- 需要确认；
- 只能预览；
- 暂不支持安全导入。

## 六、每条 Evidence 必须有去向

当前最容易漏掉的风险不是某个字段为空，而是某些行、隐藏工作表或 PDF 页面根本没有进入后续统计。

每条 Evidence 必须恰好获得一种明确处置：

- `POSTED`：已经支持正式交易；
- `DUPLICATE`：有强证据证明已由哪个事件承载；
- `NON_FINANCIAL`：严格规则证明不是资金活动；
- `USER_EXCLUDED`：用户明确排除，保存作用域和原因；
- `DEFERRED`：本次未处理，仍保留稳定身份；
- `REJECTED`：当前能力不支持或证据冲突。

不允许存在“解析器没有输出，所以这行自然消失”。最基础的行覆盖不变量是：

```text
输入数据记录
= 已入账证据
+ 重复证据
+ 已证明非资金证据
+ 用户排除证据
+ 延期证据
+ 拒绝证据
```

XLSX 还必须声明选取了哪些 sheet、是否存在隐藏行列、公式、宏和合并单元格；PDF 必须声明消费了哪些页面。没有消费的区域属于诊断，不是“解析成功”。

## 七、来源适配器怎样拆

不要一家机构一个巨型解析器，也不要让所有来源共用一个充满字符串判断的 planner。

建议拆成三层：

```text
容器解析器
  CSV / XLSX / 数字PDF

模板画像
  来源机构 + 导出渠道 + 表头/锚点 + 模板版本

产品语义适配器
  钱包 / 储蓄账户 / 信用卡 / 贷款
```

最小接口可以是：

```ts
interface StatementAdapter {
  detect(shape: DocumentShape): CapabilityMatch;
  observe(document: ImmutableDocument, profile: PinnedProfile): SourceObservation[];
  interpret(observations: SourceObservation[], rules: PinnedRuleBundle): ClaimSet;
  reconcile(claims: ClaimSet, controls: SourceControls): ReconciliationReport;
}
```

适配器必须是无正式账本写权的纯领域组件：

- 不访问或创建正式 Account；
- 不写 Transaction；
- 不自行绕过 ReviewIssue；
- 不决定事务边界；
- 只输出 Evidence、Claim、Unknown、候选事件和核对结果。

最近三个真实问题应分别归位：

- 微信 `/ + 已存入零钱`：微信来源语义适配器的联合决策规则；
- 支付宝零元免押/解冻：支付宝来源适配器的严格 `NON_FINANCIAL` claim；
- 小荷包旧键失联：账户身份与用户决定解析器的版本兼容问题。

长期红线是：organizer/planner 核心不应继续出现来源专属字符串。

## 八、规则包与代码怎样分工

### 适合放入受限规则包

- 模板锚点和表头别名；
- 列选择和基本类型转换；
- 日期、金额、币种解析配置；
- 有限枚举映射；
- `all / any / equal / contains / safe-regex` 等有限谓词；
- 已声明字段之间的决策表；
- 控制总数字段定位；
- 非资金状态的严格合取规则。

### 必须保留在有类型代码中

- 跨行和跨来源事件组合；
- 去重与冲突裁决；
- 账户身份解析；
- 退款累计上限；
- 转账双端守恒；
- 聚合还款与贷款拆分；
- LedgerImpact；
- 现金门禁、修正、撤销；
- 幂等、锁、用户隔离和事务。

规则包必须是受限 DSL，而不是任意 JavaScript。禁止网络、数据库、动态代码、无限循环和直接创建 Account/Transaction。规则复杂度超过预算时，必须升级为有测试的语义适配器，不能继续往 JSON 里塞条件。

首发没有必要支持远程动态下发规则。先让规则随代码部署更安全。未来如果确有需要，规则包必须：

- 内容寻址并签名；
- schema 校验和静态 lint；
- 声明最低核心版本；
- 在冻结语料上做新旧差分；
- 先影子、再灰度；
- 有 profile/rule 级 kill switch；
- 每个 FinanceUpdate 固定规则摘要；
- 永久保留历史规则工件用于重放。

规则升级只能重建未入账批次。已入账交易绝不能在后台被新规则重新解释；发现错误后只能生成显式撤销或修正候选。

## 九、用户纠错不能直接变成全局真理

用户决定至少要区分四种作用域：

- `INSTANCE_ONLY`：只改这一条事件；
- `BATCH`：只改当前 FinanceUpdate；
- `SOURCE_REFERENCE`：这个来源的精确账户引用以后都这样；
- `ACCOUNT_IDENTITY`：多个明确引用属于同一现实账户。

模板级或平台级全局规则不应由单个用户的一次选择直接提升。全局提升必须经过：

```text
用户私有纠错
  → 脱敏最小复现
  → 规则提案
  → 正例/逐条件反例/冲突测试
  → 冻结语料差分
  → 人工评审
  → 影子运行
  → 灰度
```

默认使用最窄作用域。用户扩大作用域时，界面应显示预计影响多少项、适用哪个账户引用，并允许撤销。

优先级应明确且可审计：

```text
当前事件明确决定
> 当前批次决定
> 当前规范键的用户决定
> 现实账户身份决定
> 历史兼容 alias
> 平台默认建议
```

同级冲突进入 ReviewIssue，不允许“最后写入者”或概率分数静默决定。

## 十、财务硬不变量

任何解析器、规则包、AI 和 UI 都不能绕过以下规则：

1. 金额使用整数最小货币单位，币种和精度明确；
2. 每条 Evidence 恰有一种处置，不允许消失或被两个不相容事件重复使用；
3. 同一稳定来源身份最多形成一次正式事实；
4. 仅金额、时间、商户相似不足以自动去重；
5. 内部转账遵循 `source -amount`、`destination +amount`，同币种守恒；
6. 退款必须满足原交易关系和累计上限，不能记成普通收入；
7. 信用卡消费增加负债，还款减少负债，退款减少负债，利息和费用另列；
8. 贷款还款无法拆清本金、利息和费用时不得伪装成普通转账；
9. `correction = reverse(old) + apply(new)`，维护操作锁完整事件交易集合；
10. 现金门禁在创建、修正和撤销中复用同一纯领域函数；
11. 规则、事件集合或 expected token 变化必须返回冲突；
12. posting 继续在一个事务内原子完成，跨用户对象永远不能相互命中。

对来源提供控制总数时，还应按产品核对：

```text
储蓄账户：
期末 = 期初 + 收入 - 支出 ± 明确调整

信用卡负债：
期末负债 = 期初负债
         + 消费 + 取现 + 利息 + 费用
         - 还款 - 退款
         ± 明确调整

贷款：
期末本金 = 期初本金 + 新放款 + 明确资本化项
         - 已还本金
         ± 明确调整
```

核对结果必须是：

- `PASS`；
- `FAIL`；
- `NOT_PROVIDED`；
- `NOT_APPLICABLE`。

没有控制总数不能显示“核对通过”。同时，对账通过也不能替代语义证明，因为两笔相反错误可能数值上互相抵消。

## 十一、是否允许部分入账

首个公开版本不建议允许一份账单中“已认识的行先入、其他行以后再说”。这样容易造成：

- 后续补录重复；
- 退款或转账只入一半；
- 控制总数看似通过；
- 期间统计永久不完整；
- 用户忘记还有延期记录。

更准确的长期模型不是按行部分入账，而是定义 `ClosureUnit`：

```text
同一 EconomicEvent
+ 该事件生成的完整 Transaction 集合
+ 退款依赖
+ 转账双端
+ 聚合还款分配
+ 重复候选
+ 所属控制总数范围
```

只有完整闭合的 ClosureUnit 才能原子入账。一个未决证据若参与账户期间控制总数，该对账范围不能标成已验证。

首发应选择更简单的口径：关键未知存在时阻断对应文件或整个 FinanceUpdate；用户可以移除不支持的文件后重新形成批次，但不能让未知行静默留在已入账文件里。

## 十二、测试的目标是证明会安全失败

测试体系不应再以“收集了多少真实账单”或“代码覆盖率多少”为主指标，而应覆盖风险空间。

### 1. 金标契约测试

每个 Certified Profile 至少包含：

- 正常脱敏金标；
- 每个关键字段缺失；
- 重复列、冲突列；
- 未知枚举；
- 与该 profile 高度相似但不属于它的反例；
- 每项已声明业务能力的正例和负例。

断言必须覆盖 Evidence、Claim、Unknown、事件、账户端、LedgerImpact、ReviewIssue、CoverageManifest 和 posting 门禁，而不只是“解析出 N 行”。

### 2. 联合决策与逐谓词反例

对以下组合做风险驱动测试：

```text
交易类型 × 收支方向 × 状态 × 支付方式 × 金额正/负/零
```

像“微信收入转账 + `/` + 已存入零钱”这种规则，除了正例，还必须每次只改变一个必要条件形成 near-miss 反例。这样能发现少了一个 `AND` 的危险放宽。

### 3. 属性测试

- 同 Evidence + 同规则版本 + 同用户决定，结果摘要完全相同；
- 行顺序变化不改变稳定身份和事件集合；
- 重复导入不重复记账；
- 金额精度不丢失；
- 每条 Evidence 恰有处置；
- 未知关键字段不能穿透门禁；
- 整批失败不留下账户、映射或交易；
- 用户 A 的规则和账户不能命中用户 B。

### 4. 变形测试

- 改空格、全半角、无关备注、列顺序时，财务影响不应变化；
- 改关键状态、金额符号、币种或到账描述时，必须改变结论或进入未知；
- 增加无关列不能改变结果，删除必要列必须降级。

### 5. 模糊与恶意输入

- BOM、GBK/UTF-8；
- 空行、重复表头、超长文本；
- 科学计数、千分位、括号负数；
- 合并单元格、隐藏行列、公式缓存值；
- 恶意 XLSX/XML、压缩炸弹、CSV 公式注入；
- PDF 跨页表头、错位文本和资源耗尽。

断言不仅是“不崩溃”，还包括不越权、不泄露、不 fail-open、不生成未经证明的账务结论。

### 6. 变异测试

主动删除状态条件、交换 source/destination、放宽零金额、改变映射优先级、破坏去重键。测试必须杀死这些 mutant。关键金额、方向、账户、幂等和排除规则存在任何存活 mutant，都应阻断发布。

### 7. 新旧规则差分与影子运行

每次规则升级双跑旧版和新版，输出发生变化的事件集合，按以下维度分类：

- 金额；
- 币种；
- 方向；
- 账户端；
- 事件性质；
- 排除状态；
- 稳定身份和去重关系。

任何未解释的关键差异都是 No-Go。生产影子运行只能生成差异，不能改变用户看到的结果或正式账本。

### 8. 独立 Oracle

合成账单生成器不能调用生产解析器的同一套 helper 来生成预期结果，否则只是让实现证明自己。输入生成器、财务影响 oracle 和生产规则应尽量独立，再辅以人工金标和变异测试。

## 十三、怎样量化而不自欺

不要再报告单一“识别准确率”。至少拆成：

| 指标 | 含义 | 安全口径 |
| --- | --- | --- |
| `UnsafeAcceptanceRate` | 系统误判且已经通过门禁的事件比例 | 已确认 S0/S1 必须为 0 |
| `UnknownEscapeRate` | 本应隔离的挑战样本被当作已支持 | 发布测试必须为 0 |
| `CriticalOverrideRate` | 用户入账前改动金额、方向、账户端或性质 | 错误代理，不混入分类偏好 |
| `PostCorrectionRate` | 入账后明确归因于导入错误的修正/撤销 | 静默错误下界 |
| `ReconciliationCoverage` | 有独立控制总数并实际核对的批次比例 | 与通过率分开 |
| `DecisionDrift` | 新规则改变关键结论的事件比例和绝对数 | 未解释关键变化为 0 |
| `SafeRejectionRate` | 被安全拒绝或要求人工处理的比例 | 体验债，不是安全事故 |

零失败也不等于真实错误率为零。在近似独立样本下，N 次零失败的 95% 单侧上界约为 `3/N`：

- 0/300，只能粗略说明错误率上界约 1%；
- 0/3000，才接近 0.1%。

同一份账单里的几百行高度相关，不能冒充几百个独立样本。统计至少按用户、批次、模板指纹和关键语义场景分层。样本不足时就诚实标为 Assisted/Beta，而不是用漂亮百分比宣称成熟。

## 十四、隐私条件下怎样观测线上风险

默认可以记录：

- CapabilityProfile、parser、rule、policy 版本；
- 容器类型、列数和粗粒度类型位图；
- 规则命中码、类型化未知码和门禁结果；
- Evidence/Event/ReviewIssue 数量；
- 是否提供控制总数、核对状态；
- 执行阶段、耗时、资源量和不透明 batch trace。

默认不应记录：

- 原始行、表头原文和未知枚举原文；
- 姓名、商户、备注和文件名；
- 完整账号或尾号；
- 精确金额和精确时间；
- OpenID、可跨系统关联的用户身份；
- 可长期关联用户消费轨迹的稳定文件 hash。

普通哈希不等于匿名。尾号、状态文本和列名属于低熵空间，容易被字典反推。确需聚类时使用服务端 keyed HMAC、轮换密钥、短保留期和小样本隐藏，并优先记录原因类别、字符类型、长度区间而不是原值。

可以提供用户主动生成的“解析诊断包”：

1. 用户先在本地预览将要提交的内容；
2. 默认只包含结构、诊断码和最小失败片段；
3. 姓名、账号、商户、备注、金额和时间分级遮盖；
4. 单工单加密存储；
5. 7～30 天自动删除；
6. 有访问审计、撤回和立即删除入口。

不能用一句“用于改进产品”取得永久保存真实账单的授权。

## 十五、AI 和 OCR 应放在哪里

首版运行时不需要 LLM。

AI 可以用于：

- 开发阶段分析未知模板并提出规则草稿；
- 推荐来源/profile 候选；
- 推荐列映射；
- 聚类未知枚举；
- 数字 PDF/OCR 表格结构候选；
- 解释 ReviewIssue；
- 生成测试变体；
- 影子比较规则升级。

AI 不得用于最终决定：

- 金额、币种、正负号和资金方向；
- 账户自动合并；
- 去重；
- 非资金排除；
- 退款、本人转账、还款和贷款拆分关系；
- 余额、统计和 LedgerImpact；
- 幂等、锁、租户隔离和事务；
- posting eligibility；
- 后台重新解释已入账事实。

模型输出只能是 `MODEL_SUGGESTED`，随后必须由确定性规则或用户决定升级。即使记录模型、提示词和参数，托管模型也未必能字节级重放，因此不能成为账务事实来源。

扫描 PDF/OCR 比 LLM 更早面临一个问题：字都认对不代表表格行列还原正确。首发建议：

- CSV/XLSX：正式支持；
- 已认证的文字层数字 PDF：以后实验支持；
- 扫描 PDF/OCR：只做候选和人工预览；
- 低质量图片、跨页错位、公式或宏：明确拒绝。

## 十六、银行账单怎样扩展

不要一开始就追求“所有银行”。按产品风险逐级认证：

1. 储蓄卡 CSV/XLSX；
2. 信用卡 CSV/XLSX；
3. 文字层 PDF；
4. 贷款账单；
5. 扫描 PDF/OCR；
6. 多币种、投资和复杂估值。

新增一家银行理想上只新增：

- 模板画像；
- 脱敏金标和近似反例；
- 机构枚举映射；
- 必要时一个很小的机构差异策略。

核心 Transaction 写屏障、LedgerImpact、原子事务、幂等、用户隔离、Evidence、账户身份和财务不变量不应改变。

可以考虑通用表格导入向导，但首版只允许用户明确映射：日期、金额、方向和一个账户，并生成普通收入/支出。转账、退款、信用卡、贷款和分期如果缺少明确产品语义，应拒绝而不是靠用户随便选一个分类糊过去。向导结果标记为 `MANUAL_IMPORT`，不得自动提升成平台规则。

## 十七、发布、灰度和止损

“发布小程序”和“支持所有账单”必须彻底拆开。

首发可以只公开声明：

- 支持经过认证的支付宝官方导出模板族；
- 支持经过认证的微信官方导出模板族；
- 只支持人民币和已列明业务类型；
- 未认证模板会安全提示，绝不冒充支持；
- 银行账单逐家、逐产品、逐模板加入。

发布阶梯：

```text
离线安全门禁
  → 真实批次影子运行
  → 内部/指定用户，强制 Review
  → 真实身份 opt-in 小流量
  → Assisted Beta
  → Certified Profile
```

必须有以下服务端开关：

- 按来源停用；
- 按 CapabilityProfile 停用；
- 按 parser/ruleVersion 停用；
- 按 ruleId 停用某项推导；
- 降级为 Preview Only；
- 强制全部人工确认；
- 禁止 posting；
- 全局紧急停写。

出现以下任何一种情况应立即止损：

- 一例已确认金额、币种、方向、账户端、重复入账等 S0 错误：停对应 profile/version posting；
- 跨用户泄露、事务半成功或写屏障绕过：全局停写；
- 已认证 profile 单批出现未知关键组合：隔离该批；
- 同指纹短期重复出现关键未知或核对失败：自动降级 profile；
- 新旧规则出现任何未解释的关键差异：阻止规则发布。

回滚只影响未来和未入账批次。已入账交易不得随代码或规则回滚静默改变。每个 posting receipt 应保存 profile、parser、rule、policy、decision-set、evidence-set 和 transaction-set 摘要，以便规则事故发生时一小时内定位受影响批次，再生成显式修正方案。

## 十九、最可能失败的地方

### 1. 未知模板保留旧表头，但改变了字段含义

仅靠表头 hash 不够。Profile 必须同时认证结构锚点、枚举域、组合规则和产品控制总数；线上监控未知组合漂移，一旦出现立即降级。

### 2. DSL 最终变成另一门失控编程语言

限制表达能力和复杂度预算；复杂跨行语义回到有类型代码。所有规则输出 Claim，不直接输出 Transaction。

### 3. 用户把一次错误决定扩大成“以后都这样”

默认最窄作用域，扩大时展示影响数量、样例和账务影响；广域决定可撤销，异常命中应报警。

### 4. 对账刚好抵消两个错误

对账不是唯一证明。金额、方向、账户端、事件类型仍必须分别有合格 provenance。

### 5. 部分入账导致未来重复和关系断裂

首发关闭部分入账；未来只有 ClosureUnit、EvidenceDisposition 和覆盖快照全部具备后才能开放。

### 6. 非资金规则过宽，静默丢掉真实交易

排除本身也是财务决定。必须是精确 profile 下的严格合取规则，并为每个必要条件准备逐项失效测试和变异测试。AI 不得自动排除。

### 7. 为了体验好看，AI 逐渐获得事实决定权

从类型系统上禁止 `MODEL_SUGGESTED` 满足 posting 证明义务，而不是只靠开发规范提醒。

### 8. 线上没有投诉，被误认为没有错误

投诉和撤销只是静默错误下界。必须结合入账前关键改选、入账后修正、余额差、未知漂移、规则影子差分和授权样本审计。

## 二十、Go / No-Go

当前若对外宣称“广泛支持支付宝、微信及银行账单”，结论是 No-Go。

补齐下面门禁后，可以按明确模板范围发布 Certified Beta：

- 支持范围是精确 allowlist，不是平台名称；
- 未知 profile、关键枚举和证据冲突已经验证 fail closed；
- 所有余额关键结论都有可检查 provenance；
- 每条 Evidence 100% 有处置；
- 来源适配器无正式写账权限；
- LedgerImpact 使用统一纯领域模型；
- 有控制总数时差异必须为零，无控制总数时明确写无法核对；
- 关键规则具备正例、逐谓词反例、冲突、版本和变异测试；
- 新旧规则关键差异全部解释；
- 幂等、事务回滚、跨用户隔离和维护操作通过；
- profile/rule/posting 熔断和回退实际演练过；
- 能按版本摘要定位受影响批次；
- UI 清楚显示拟入账、排除、未知和核对范围；
- 真实身份、真实设备完整闭环通过；
- 数据导出、注销、隐私、保留和诊断包边界清楚；
- 没有未关闭的 S0/S1 问题。

不满足某个 profile 的门禁，不代表整个产品永远不能发布。把该 profile 降成 Preview Only 或 Unsupported，其他 Certified Profile 仍可继续。

## 最后的裁决

最优路线不是“再找更多账单，把所有例外写完”，也不是“上一个更聪明的 AI”。

最优路线是：

> 用认证范围解决覆盖问题，用类型化未知和证明义务解决安全问题，用 Evidence/版本摘要解决审计与重放，用财务不变量和对账解决账本影响，用影子/熔断/显式修正解决线上不可避免的规则事故。

这样以后接一家新银行，不是在重新证明整个系统安全，只是在证明新的 profile 和产品适配器没有绕过共同的安全内核。

你不需要拥有全中国所有人的账单才能发布。你需要的是：手里没有见过的那份账单，即使明天出现，也只能安全地停在正式账本之外。
