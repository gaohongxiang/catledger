# 个人财务业务规则与验收

> 用户目标、实际使用方式、页面展示内容、当前优先级与延期事项统一维护在 [个人财务用户需求.md](./个人财务用户需求.md)。本文只负责把已经确认的用户意图细化为业务规则、会计语义和可验证的验收口径，不是另一份用户总规划。
>
> 状态：长期产品与业务口径基线（可继续修订）
> 主项目：ezBookkeeping fork

## 1. 背景

现有 ezBookkeeping 已经具备账户、收入、支出、转账、分类、统计和多种账单导入能力，适合作为个人账本的基础。但当前还有两个核心缺口：

1. 导入流程主要解决“把一个文件转换成交易”，只能防止短时间内重复提交同一个请求，不能持久识别重复文件、重叠账期，也不能把支付宝、微信、银行卡和信用卡里的同一笔经济事件归并起来。
2. 债务账户能表示余额，却没有贷款合同、信用卡分期、逐期计划、费用、优惠、真实年化、已还进度和未来待还明细。

因此，本项目不是重写一个记账软件，而是在 ezBookkeeping 上增加：

- 可追溯的账单预处理、去重和跨来源对账；
- 贷款与分期合同管理；
- 能说明“数据是否完整”的个人财务总览。

已有 IRR 年化计算器项目仅作为算法和交互参考，路径为：

    /Users/gaohongxiang/projects/loan-cost-calculator

它不是本项目的运行时依赖。

## 2. 产品定位与当前决策

- 第一使用者是项目所有者本人。
- 第一形态是自托管 Web/PWA。手机必须能看总览、记一笔和下一笔待还；账单整理、复杂对账和新建贷款以桌面为主，手机给摘要即可。
- 体验原则：第一次慢而清楚，第二次快而可改。已确认判断默认沿用，只把新的、冲突的、说不清的交给用户。
- 当前不开发微信小程序，也不处理小程序上架审核、云同步和商业化；小程序作为未来主客户端的启动条件与部署路线见用户需求第 12 章。
- 所有账单和财务数据默认只进入用户自己的 ezBookkeeping 服务，不调用外部 AI 或第三方分析服务。
- 保留 ezBookkeeping 的多用户隔离规则；即使目前只有一个人使用，新增表和接口也必须按 uid 隔离。
- 优先做可验证、可回滚的导入基础，不追求第一版就自动识别所有银行格式。

## 3. 用户真正要解决的问题

### 3.1 当前财务状况

用户打开总览应先看到：净资产、本月生活消费、下一笔待还、一句可信度。账户明细、覆盖缺口和待办数量放在下一层，必须能点进去处理。

其余问题仍要能回答：

- 我现在有多少资产、多少负债、净资产是多少？
- 其中有多少是可随时使用的资金？
- 各信用卡、银行贷款、网贷和分期还剩多少本金？
- 未来 7 天、30 天和本月需要还多少钱？
- 最近几个月的收入、消费、债务还款和结余如何？
- 这些结论覆盖了哪些账户和时间段，还有哪些数据未导入或未确认？

### 3.2 消费与现金流完整性

用户的消费分散在支付宝余额、微信零钱、银行卡、信用卡和分期平台中。如果直接把每份账单都写入正式账本，会同时产生漏记和重复计算。

系统需要允许用户导入所有账单，但先进入预处理区：

- 同一来源重复导入时识别相同记录；
- 不同来源出现同一笔消费时合并证据，不重复计算支出；
- 银行卡还信用卡时识别为账户间转账，不计算为消费；
- 退款、撤销、手续费、借款到账和还款本金使用正确的会计含义；
- 未达置信标准的数据不能悄悄进入统计。账户已明确且规则允许的自动入账计入正式账本，必须可撤销。

### 3.3 借贷明细

债务不只是一个负数余额。用户还需要记录：

- 信用卡分期、银行贷款、消费金融或网贷、一般借款；
- 合同本金、实际到账、期数、还款方式、利率或已知应还额；
- 一次性费用、每期费用、优惠和减免；
- 总成本、有效年化、逐期本金/利息/费用；
- 应还计划、实际还款、剩余本金和下一还款日。

## 4. 三类数据必须分开

### 4.1 原始账单记录

原始账单记录是“证据”，来自支付宝、微信、银行或信用卡文件。它必须保留来源、原始字段和导入批次，不能因为匹配成功就删除。

### 4.2 正式账本交易

正式账本交易是用于余额、消费、现金流和统计的唯一口径，继续使用 ezBookkeeping 现有交易模型。

一笔正式交易可以对应多条原始记录。例如一笔支付宝消费由信用卡支付，支付宝订单和信用卡流水都是同一笔正式支出的证据。

#### TX-001 正式交易必填与分类

进入正式账本、影响余额和净资产的交易必须同时具备：

1. 时间；
2. 金额与币种；
3. 性质：收入、支出或转账（含还信用卡、充零钱；不是生活消费）；
4. 资金账户；转账必须有对方账户。

账本分类（餐饮、服饰等）用于生活消费构成，不是入账门槛。能从清晰渠道映射则入账时带上：分类优先支付宝「交易分类」，微信「商户消费」「扫二维码付款」不得作为账本分类。无法映射则入账为未分类，计入余额与净资产，不计入分类构成；待办提示补分类，不猜测。已有人工分类不被含糊渠道覆盖。额外标签、备注、地点、图片可选。多渠道同一事件只形成一笔正式交易，每个字段采用能清晰定义的渠道。

### 4.3 贷款合同与计划

贷款合同描述约定，逐期计划描述预期现金流；正式账本交易描述实际发生。

计划到期不等于已经还款。只有用户确认或实际交易匹配成功，某一期才应标记为已还或部分已还。

## 5. 账户与支付渠道的边界

“数据来源”“支付渠道”和“资金账户”不是同一个概念。

| 场景 | 正式账本中的账户 | 来源信息 |
| --- | --- | --- |
| 支付宝余额付款 | 支付宝余额账户 | 支付宝账单 |
| 微信零钱付款 | 微信零钱账户 | 微信支付账单 |
| 支付宝调用银行卡付款 | 对应银行卡账户 | 支付宝账单 + 银行流水 |
| 支付宝调用信用卡付款 | 对应信用卡负债账户 | 支付宝账单 + 信用卡流水 |
| 银行卡归还信用卡 | 银行卡到账户转信用卡账户 | 银行流水 + 信用卡流水 |
| 贷款发放到银行卡 | 贷款负债增加，同时银行卡资产增加 | 贷款/银行流水 |

支付宝或微信只有在使用余额、零钱等自有余额时才是资金账户；仅作为收银台调用银行卡时，它们是来源和渠道，不能再虚构一次资金流出。

## 6. 起账方式与“完整”的定义

资产、负债和净资产默认统计全部正式账户截至当前日期的状态，不以报表起始日裁剪账户余额。账单覆盖日期用于解释历史收支是否完整，不能决定账户是否进入当前财务快照。

### 6.1 当前状况模式

用户开始使用时不必先建立账户。默认路径是直接导入账单，由系统发现付款账户：需要新建的由用户点「新建」，已持久确认的映射默认沿用，不是自己账的可点「不要」。用户也可以选择：

1. 手工补充现金等账单里没有的账户；
2. 填写带明确截至日的当前对账余额；
3. 建立未结清贷款和分期；
4. 从能够取得的最早账期开始持续导入账单。

当前财务快照在至少有一个已确认正式账户后即可使用。若账户尚未录入对账余额，快照必须标记余额未核对。历史收支只对已覆盖的账期作完整性承诺。

### 6.2 完整消费模式

如果要分析某日起的完整消费，必须从该日期开始覆盖所有实际资金账户和支付渠道，并处理重叠和跨来源重复。

系统不得只显示一个“完整/不完整”布尔值，应展示：

- 每个账户已覆盖的日期区间；
- 区间之间的缺口和重叠；
- 未处理、疑似重复和解析失败的记录数；
- 当前报表是否包含未确认数据。

## 7. 主流程

~~~mermaid
flowchart LR
    A["上传账单"] --> B["发现付款账户"]
    B --> C["新建或沿用账户"]
    C --> D["可选核对当前余额"]
    D --> E["同来源去重与跨来源整理"]
    E --> F["高置信自动入账"]
    F --> G["例外待办"]
    G --> H["财务总览"]
~~~

处理留痕必须保留。高置信自动入账视为系统按已确认规则完成的入账，必须可撤销；不得把未达置信标准的跨来源合并或金额/时间接近单独作为入账依据。

## 8. 功能需求

### 8.1 初始化和覆盖范围

#### ONB-001 建立账户当前状态

- 用户可为资产与负债账户录入带明确截至日的对账余额。
- 当前财务快照默认纳入全部有效正式账户，不要求先设置报表起止日期。
- 余额截至日与账单覆盖区间分别展示；前者解释当前状态，后者解释历史收支完整性。
- 从账单首次新建账户后，应提供可跳过的当前余额核对。跳过时账户与总览标记 `balance_unverified`，净资产不得呈现为已对账结论。

#### ONB-002 建立账户清单

- 支持现有现金、银行卡、储蓄、虚拟账户、信用卡、债务等类型。
- 账户可配置外部来源标识，例如卡尾号或平台账户别名。
- 敏感标识展示时默认脱敏。

#### ONB-002A 从账单发现付款账户

- 首次使用不必先去账户页建账户。解析完成后汇总本次付款账户，分成“需要新建”、“已经存在”和“不要”。
- 系统按来源类型、币种和版本化规范键汇总同一付款方式。空格、全角/半角括号、掩码符号和“尾号”等展示差异不应制造重复候选，但泛称、尾号冲突或多个可行账户不得自动裁决。
- 已持久确认的别名映射进入“已经存在”并默认沿用到该组尚未入账行；界面用摘要说明沿用数量，允许改映射，但不要求每次点「确认使用」。
- 用户可将整组或组内所选行标记为「不要」：保留证据、忽略入账、不创建正式账户。整组「不要」按同一规范键持久化并默认沿用，可改回；只去掉部分行时不把整组记成永久不要。界面核对账户用「忽略账户」表示整组不要；整理交易在每笔上勾选不入账表示单笔不要。语义仍是「不要」。
- 银行/信用卡账单若已判定银行，付款方式的展示与匹配应组成「银行名 + 卡种 + 末四位」。不得只显示末四位，也不得仅因末四位相同就对上其他银行的卡。支付宝/微信已给出完整付款方式名称时，用该名称，不再另造。
- 没有映射时，以组成后的规范名称判断是否已有账户。仅末四位相同而银行名对不上，或名称冲突、多候选时，不得自动裁决。仅推荐不足以创建账户。
- “需要新建”展示可编辑的建议名称、币种、账户类型及影响行数。用户改到满意后必须点击「新建」，才通过现有正式账户入口创建账户并持久化映射。新建前可改选已有账户，改选后按已经存在并沿用或确认。
- 账户已删除、币种不一致、多候选或规则冲突时失败关闭，必须由用户选择或新建，不得沿用。
- 同一整理任务同一付款方式只处理一次。支付宝、微信和银行账单中名称相同的卡合并展示并加总笔数；沿用或「不要」一次应用到这些来源。修改映射只影响尚未入账行的默认账本账户，不改变账单身份、历史原始证据或已确认正式交易。来自哪份账单只在明细中区分。
- 常用界面文案使用付款账户与账单种类（支付宝账单、微信账单、信用卡账单）。文件能唯一判定账单所属平台账号时不得再弹出账号选择；多账号或无法判定时才询问。

#### ONB-003 覆盖区间

- 每个成功解析的导入批次记录来源账户、账期开始日和结束日。
- 系统按账户合并区间并显示缺口、重叠和最近更新日期。
- 用户可手工修正文件无法可靠提供的账期。

#### ONB-004 信用卡账单周期

- 每个信用卡账户可记录可空的常规账单日、还款规则及其生效时间；账单解析得到的实际周期开始日、结束日、出账日和到期日按每份证据分别保存。
- 常规账单日只用于提醒和预测，实际账单周期才参与覆盖率裁决。银行调整账单日、节假日顺延或账期长短变化时，不得用当前规则改写历史周期。
- 从账单发现或修改周期规则时必须展示账户和生效范围，由用户确认；同一账户出现互相冲突的周期证据时进入人工处理。
- 账单周期、自然月统计区间和还款到期区间是三个独立概念，API、界面与字段命名不得混用。

### 8.2 导入批次和原始记录

#### IMP-001 持久化导入批次

每次上传创建独立批次，至少记录：

- 用户、来源类型、关联账户；
- 原文件名、大小和 SHA-256；
- 账期、上传时间、解析器及版本；
- 总行数、有效行数、重复数、待确认数、已入账数和错误数；
- 当前状态和错误摘要。

重复文件需要明确提示，不能仅依赖短期 ClientSessionId。

#### IMP-002 保存原始行

每条有效或无效行都应具备：

- 所属批次和原始行号；
- 来源交易号、订单号、商户单号等可用标识；
- 原始时间、金额、方向、状态、商户、商品说明和支付方式；
- 标准化后的时间、金额、币种、交易方向和账户候选；
- 原始字段快照；
- 解析器版本和标准化规则版本；
- 当前处理状态。

原始行入库后原则上不可覆盖。重新解析应产生新版本或留下变更记录。

#### IMP-003 原文件保存

- 默认在自托管存储中保留原文件，以便审计和重新解析。
- 用户可以删除原文件内容，但需保留文件哈希、批次元数据、原始行和处理结果。
- 文件内容、完整卡号和原始行不得写入普通运行日志。

#### IMP-004 导入历史

用户可以查看、筛选和打开历史批次，看到：

- 文件是否重复；
- 哪些行被跳过或匹配；
- 哪些正式交易由本批次创建；
- 解析错误和人工修改；
- 是否可以安全撤销本批次产生的正式交易。

#### IMP-005 批次级付款账户确认

- 整理任务在入账前汇总付款方式，列出需要新建、已经存在与不要、安全显示名、涉及行数和映射状态。新建必须先允许编辑再点「新建」；已确认映射默认沿用，摘要可见、可改。
- 用户可将整个付款方式组，或组内所选原始行，明确标记为「不要」。不要的行保留原始证据和来源身份，处理状态为已忽略，不得创建正式账户、不得自动或确认入账，也不得计入余额、收支和总览。覆盖仍视为已见到这些证据，不把它们当成缺口。
- 「不要」是通用入账决定，不绑定某个平台、账户名或产品名。支付宝小荷包、别人的卡、代付、不想记的内部划转等，都走同一条路径。
- 整组「不要」必须持久化到该 `uid + source_type + currency + alias_key`，下次同组默认继续不要，允许改回新建或映射到正式账户。只去掉组内部分行时，只影响本任务这些行，不把整组记成永久不要。
- 支付宝/微信存在非空付款方式时，不得用账单平台账号的默认映射覆盖实际付款账户。银行专用月结单解析前不选正式账户，按「银行名 + 卡种 + 末四位」组成付款方式再核对；当前已落地的是光大 PDF，其他银行专用模板按同一通则接入。通用银行 CSV 仍以用户选择的银行/信用卡账户作为默认正式账户。已被「不要」的组除外，它们不需要正式账户。
- 已确认付款方式映射应在重新解析和未来文件中默认复用；旧批次也能按已保存映射获得默认账户。持久「不要」同样默认复用。
- 付款账户处理不改变精确去重身份。账户已明确后，符合 IMP-008 的行可以自动入账，不要求再为账户逐笔确认。已被忽略的行即使账户后来明确，也不得再自动入账，除非用户改回。

#### IMP-006 多账单联合整理

- 用户一次选择的多个账单文件构成一个逻辑整理任务；每个文件、导入批次和原始行仍保持独立、不可变和可追溯，整理任务不得以汇总金额替代原始记录。
- 确认入账前允许增删本轮已解析文件。增删后必须重新汇总付款方式，并作废尚未确认入账的整理预览与本任务待办。确认入账后本轮文件集合不再改。一个批次仍只属于一个任务。
- 联合分析范围同时包含本次全部原始行，以及当前用户已经持久化的来源身份、付款账户映射、正式交易关系、分类规则和贷款/分期合同；任何查询都必须带 `uid`。
- 账户候选按规范别名跨本次批次汇总，再与已有映射和正式账户比较；一次确认应用到全部相关尚未入账行。来源账户身份和正式账本账户仍分别保存。
- 交易先执行同来源身份去重，再与本次其他来源和历史证据生成跨来源事件候选；每条原始行分别裁决，不允许把总金额、时间接近或分类相同作为合并依据。
- 一笔交易入账必须定齐时间、金额与币种、性质、资金账户（转账含对方账户）。账本分类按 TX-001：能映射则带上，不能映射则未分类入账。备注与额外标签可选。分类指餐饮、服饰等账本类别，不是微信「商户消费」这类动作名称。
- 同一经济事件多渠道时，每个字段采用能清晰定义的那一侧：账本分类优先采用支付宝「交易分类」等生活分类；微信「商户消费」「扫二维码付款」不得当作分类。收/支用于辅助判断性质，但充值、还款、红包、不计收支须按转账或退款语义，不得一律记为消费。付款账户取能对应到卡或余额的付款方式。已有人工分类不得被含糊渠道覆盖。
- 无法清晰映射分类时仍入账为未分类，计入余额，进入补分类待办，不得猜测，也不得挡住余额统计。
- 分期按可靠身份跨批次汇总后进入待办，首次只收集是否分期、负债账户、总期数和原消费关系；转账、还款和退款形成关系候选，不能先聚合为单笔净额。
- 界面是一个整理任务页：顶部摘要（新建账户数、沿用账户数、自动入账数、待办数），下方只展开待办。后台顺序为解析留证、账户新建或沿用、同来源去重、跨来源整理、高置信自动入账、分期候选、分类建议、待办汇总。已确认历史事实冲突时失败关闭并展示差异，不静默覆盖。

#### IMP-007 月末暂结与迟到账单回补

- 收入和消费按正式交易的实际发生日期进入自然月；信用卡出账日期不得把原消费整体移动到出账月份。来源只提供入账日期时必须明确日期依据，不得伪装成已知交易日期。
- 月末统计不等待所有信用卡出账。支付宝、微信、信用卡未出账明细等可靠证据已经形成的正式交易正常计入当月；没有证据覆盖的直接刷卡区间只形成覆盖缺口，不生成估算交易。
- 月度状态为 `provisional`（暂结）或 `confirmed`（已确认）。任一纳入范围的账户存在待出账覆盖缺口、待确认记录、解析失败或身份冲突时保持暂结，并返回具体账户、缺口区间和原因；不得只返回一个不可解释的布尔值。
- 后续正式账单导入后，先按来源身份和跨来源关系关联已有正式交易，再补充确实遗漏的交易。账单证据本身不产生第二笔消费；回补应重新计算受影响自然月的覆盖和统计，并保存可追溯的变更原因。
- 默认允许历史月份随迟到账单自动修订，不做阻止回补的硬月结锁。界面应显示最近修订时间和变化来源；未来若增加不可变月结快照，必须作为独立审计能力，不能替代实时权威账本。
- 信用卡展示的已出账应还和已识别未出账金额是当前负债的解释性分解，不能绕过正式交易再次累加到账户余额。资料不足时显示“当前已知”与覆盖缺口，不输出伪精确总额。

#### IMP-008 高置信自动入账与例外待办

- 付款账户已经明确（新建完成或历史映射沿用）、来源身份清楚、TX-001 入账四项都能定齐、核心字段无冲突、且不依赖未决跨来源判断的新行，应自动创建或关联正式交易。分类能映射则带上，不能映射则未分类入账。自动入账必须带规则版本与幂等键，允许事后撤销。
- 下列情况进入待办，不得自动入账：身份冲突、核心金额/币种/方向冲突、与已有手工账关键字段不一致、跨来源关系不唯一或仅凭金额与时间接近、转账/退款/还款关系说不清、分期候选、付款账户未解决。用户已明确「不要」的行不进入待办，也不自动入账。
- 用户第一次导入，或本次新建了账户时，可以先展示入账摘要再点「确认入账」；日常导入默认自动入账并列出待办。
- 同来源精确重复自动跳过并保留证据，不询问。账本分类无法从清晰渠道或已确认规则得到时，仍自动入账为未分类，并进入补分类待办，不阻止余额统计。

### 8.3 去重与对账

#### REC-001 文件级防重

- SHA-256 相同的文件再次上传时明确提示已有批次。
- 用户可以打开原批次、取消上传，或在确有必要时作为新解析版本继续。
- 不因文件名不同而绕过去重。

#### REC-002 同来源精确去重

优先级从高到低：

1. 来源类型 + 来源账户 + 来源交易号；
2. 来源提供的稳定订单号或商户单号组合；
3. 带版本号的强指纹。

强指纹可使用标准化时间、金额、方向、来源账户、对手方和稳定描述，但必须区分正常的同额连续交易。

#### REC-003 跨来源候选匹配

跨来源匹配默认先产生候选。进入对比须金额和币种相同、交易对方/说明相似、付款方式按「银行名 + 卡种 + 末四位」组成后为同一张卡，以及时间对得上。信用卡月结单只有日期时，按账单时区对到同一天即可，不要求时分秒；两边都有时分时仍看时间窗。仅“金额相同且时间接近”不能自动合并。同一整理任务内，上述字段对上且候选唯一，可以自动关联为同一经济事件并只入账一次；否则进入待办。界面所有账单共用表头；每一组是一块，组内两行对照来源、账户、交易对方、商品说明、分类、金额、时间、类型和订单号；信用卡只显示到天，不写 00:00。自动关联必须留痕并可撤销。不得自动删除原始证据。

#### REC-004 关系类型

人工确认时至少支持：

- 同一经济事件：多条原始记录共同证明一笔正式交易；
- 同一内部转账的两侧记录；
- 退款或撤销关系；
- 贷款/分期计划与实际还款关系；
- 相互独立，不匹配；
- 暂不处理。

#### REC-005 合并字段

当多来源记录表示同一经济事件时，用户可选择或自动建议最优字段：

- 账户和金额以真实资金账户流水为优先；
- 商户、商品和订单信息通常以支付平台为优先；
- 分类和标签以用户已有规则及人工选择为优先；
- 所有来源字段仍保留在原始记录中。

#### REC-006 决策持久化

- 用户确认过的匹配或“不匹配”结果必须保存。
- 后续导入重叠账期时不得反复询问相同记录。
- 规则版本变化后可以重新评估，但不能静默覆盖人工决定。

#### REC-007 安全撤销

- 未入账批次可以直接废弃，但不物理删除审计记录。
- 已入账批次只能撤销由该批次自动创建且之后未被人工修改的正式交易。
- 涉及其他批次、贷款计划或人工修改的交易必须先展示影响并要求确认。

### 8.4 贷款和分期

#### DEBT-001 合同类型

第一版支持：

- 信用卡分期；
- 银行贷款；
- 消费金融或网贷；
- 一般借款。

类型主要用于展示和默认值，不参与产品推荐或风险评价。

#### DEBT-002 录入方式

支持两种测算依据：

- 已知合同利率：年利率、月利率、日利率或每期费率；
- 已知实际应还金额：根据还款现金流反算有效年化。

#### DEBT-003 还款方式

沿用 IRR 年化计算器已有能力：

- 等本等息；
- 等额本息；
- 等额本金；
- 先息后本。

#### DEBT-004 合同字段

至少包括：

- 名称、机构或出借方；
- 关联负债账户和默认还款账户；
- 合同本金、实际到账金额、币种；
- 借款日、首次还款日、期数和还款频率；
- 还款方式、利率口径或已知应还额；
- 一次性必付费用和每期必付费用；
- 利息折扣、每期减免或总额减免；
- 备注、状态和计算版本。

MVP 默认人民币、每月一期；模型不得阻止未来扩展其他币种和非月度日期。

#### DEBT-005 计算结果

展示：

- 实际到账、合同本金、总还款、总利息和总费用；
- 有效年化、总成本占本金比例；
- 逐期应还、本金、利息、费用和剩余本金；
- 已还、待还和下一还款日；
- 剩余本金、剩余合同现金流和未来 30 天待还。

月度等间隔场景必须与现有 IRR 计算器测试结果一致。非等间隔现金流将来使用单独命名和说明的 XIRR 口径，不能静默改变已有算法结果。

#### DEBT-006 计划与实际交易关联

- 计划默认只是预期数据，不提前作为实际支出写入账本。
- 一期可以关联一笔或多笔正式交易。
- 一笔综合还款应拆分或分配为本金、利息和费用。
- 支付本金是资产减少和负债减少，不是消费支出。
- 利息与必要费用才进入费用类支出。
- 匹配不足时显示部分已还或待确认，不按日期自动认定已还。

#### DEBT-007 借款到账

借款到账不能记为收入。它应同时表达：

- 银行卡等资产增加；
- 对应贷款负债增加。

实现时优先复用现有账户转账语义，并通过测试验证资产与负债的符号变化。

#### DEBT-008 信用卡分期

- 原消费如果已经入账，转为分期时不得再次记一笔消费。
- 分期本金用于描述信用卡负债的偿还计划。
- 分期手续费或利息按期记入费用。
- 信用卡账单、分期计划和实际还款之间需要可追溯关联。

#### DEBT-009 分期账单识别与首次确认

- 同一分期只建立一份合同和逐期计划；月度账单中的“第 1 期”“第 2 期”等行是对应期次的实际证据，不得逐月新建合同。
- 自动识别结果首先是独立于正式合同的 `pending_installment` 候选。系统应合并同一逻辑整理任务中属于该候选的多期证据，再与当前用户已有合同比较；未经用户确认不得创建合同或推进计划。
- 首次发现尚未管理的分期时，待办默认只问：是否分期、挂哪张负债账户、总期数（若已知）、原消费关系。合同本金、每期应还、利息、手续费、还款方式和首次还款日默认留在待完善，来源没有提供的字段必须保持未知，不得伪造为零。
- 首次确认同时处理原消费关系：`link_existing_purchase` 关联已有正式消费，`create_missing_purchase_candidate` 生成待确认的缺失消费候选，`unresolved` 保持待处理。任何选项都不得静默重复记消费。
- 还款方式候选包括 `equal_payment`（每期总额基本相同/等额本息）、`equal_principal`（每期本金相同、利息逐期减少/等额本金）、`flat`（每期本金和利息都相同/等本等息）、`interest_only`（前期付息、最后还本/先息后本）以及 `statement_or_custom`（按账单记录、自定义或暂不确定）。
- 系统可以依据明确合同字段或多期现金流给出推荐，但单期账单不足以自动裁决还款方式；推荐只能预选，最终由用户确认。
- 用户可以 `link_existing_contract`、补足正式合同所需字段后 `create_contract`，或以 `needs_details` 保存待完善候选。待完善候选可以继续接收后续证据，但不进入贷款总成本、真实年化、剩余本金或完整未来还款统计；未知值与零值必须严格区分。
- 待完善候选及缺失字段在“贷款与分期”的待处理区域展示；候选不阻止当期正式交易按既有账单流程入账，也不能把当期入账误认为完整合同已经确认。

#### DEBT-010 后续账单关联与冲突

- 首次确认后，后续期次优先使用来源分期编号、订单号、原消费关系、账户和已确认别名等稳定材料关联同一合同；金额和日期只能参与候选解释，不能单独形成自动关系。
- 信息一致时自动关联到对应计划期次，不再次询问。总期数、当前期次、金额、币种、负债账户或候选合同不一致时进入 `action_required`，展示冲突字段并保留原始证据。
- 同一期允许关联多条实际交易或证据，但重复文件、重叠账期和多来源证据不得重复推进已还金额。
- 分期原消费只计一次；归还本金减少资产与负债，不进入生活消费；利息和手续费进入借贷成本；银行卡向信用卡还款仍按内部转账处理。
- 合同页应同时展示计划期次、账单期次、实际还款、关联证据、差异和处理状态，用户能够从任一期下钻到正式交易与原始账单。

### 8.5 财务总览

#### DASH-001 财务快照

首屏必须同时给出：

- 净资产（总资产、总负债为次要数字）；
- 本月生活消费，可切换今日/本周/本年；
- 下一笔待还金额与日期（覆盖贷款、分期与信用卡已出账应还，取还款日最近的一笔）；
- 一句可信度（例如月报暂结、未分类笔数、待办笔数、余额未核对），可进入对应待办或覆盖页。

可动用资金、各账户余额、债务剩余本金和 7/30/本月待还汇总放在首屏之下，不得与净资产同等铺开。若存在 `balance_unverified` 账户，净资产必须标明余额尚未核对。未分类交易计入净资产和生活消费总额，不进入餐饮/服饰等分类构成。

#### DASH-002 现金流

按月展示：

- 收入；
- 日常消费；
- 利息与费用；
- 偿还债务本金；
- 内部转账；
- 净现金变化。

日常消费和偿债本金必须分开，避免把还款误认为重复消费。

日常总览默认纳入截至今天的全部正式账户和所示周期内全部正式交易，不要求用户先配置报表起止日期。首屏提供今日、本周、本月和本年四个快捷口径；“本周”遵守用户设置的每周起始日，“本年”为公历年至今。本月与本年必须同时保留收入、日常消费、实际偿债和流动资金净变化，若展示“现金流出”，其口径固定为日常消费、偿债本金、利息和费用之和，排除内部转账。

趋势默认展示最近 12 个自然月，并可在趋势模块内切换 6、12 或 24 个月；收入、消费和实际偿债分别呈现。历史截至日属于高级回看能力，不作为日常总览首屏的必填报表控件。

#### DASH-003 债务概览

展示：

- 每笔债务剩余本金、剩余期数和有效年化；
- 下期日期与金额；
- 未来月份的还款曲线；
- 最近若干月债务现金流占收入的客观比率。

只展示计算事实，不提供借贷产品推荐、还款优先级或个性化金融建议。

#### DASH-004 数据可信度

首屏只用一句结论加可点击数量。覆盖账户数、最近覆盖日期、缺口账户、待确认/解析失败/疑似重复明细放在第二层。

数据不完整时必须显式提示，不能给用户一种“全部消费已经覆盖”的错觉。未核对余额不得呈现为已对账净资产。

### 8.6 界面与设备

#### UX-001 整理任务页

账单整理是单一任务页，不是逐步向导。技术步骤默认折叠。常用文案不得使用“来源账户”等内部词。确认入账前，选账单可勾选或取消已解析文件。

#### UX-002 设备分工

移动端必须能完成总览阅读、手工记一笔、查看下一笔待还。账单整理完整闭环、跨来源复杂决定、新建贷款合同以桌面为主；移动端提供只读摘要和入口即可。

## 9. 关键会计场景

| 原始记录组合 | 正式账本结果 |
| --- | --- |
| 支付宝订单 + 招行信用卡同额扣款 | 一笔从招行信用卡账户发生的消费，两条原始证据 |
| 微信订单 + 银行卡同额扣款 | 一笔从银行卡账户发生的消费，两条原始证据 |
| 银行卡转出 + 信用卡还款入账 | 一笔银行卡到账户转信用卡账户的内部转账 |
| 贷款到账 + 银行入账 | 一笔负债账户到银行卡账户的借款转入，不是收入 |
| 每月贷款扣款含本息 | 本金部分减少贷款负债，利息/费用部分记支出 |
| 原消费转信用卡分期 | 不新增消费；只新增还款计划，后续费用按期记支出 |
| 原交易 + 退款 | 两笔相反方向的正式交易并建立退款关系，不当作重复删除 |
| 两笔同日同额早餐 | 保留为两笔，除非有稳定标识证明重复 |

## 10. 概念数据模型

~~~mermaid

    USER ||--o{ IMPORT_BATCH : uploads
    IMPORT_BATCH ||--o{ RAW_IMPORT_ROW : contains
    RAW_IMPORT_ROW }o--o{ TRANSACTION : evidences
    RAW_IMPORT_ROW }o--o{ RECONCILIATION_CASE : reviewed_in

    LOAN_INSTALLMENT }o--o{ TRANSACTION : settled_by
~~~

建议新增概念实体：

| 实体 | 作用 |
| --- | --- |
| ImportBatch | 文件级来源、哈希、账期、解析版本、状态和统计 |
| RawImportRow | 不可丢失的原始行、标准化字段和处理状态 |
| ReconciliationCase | 候选关系、匹配分数、规则版本和人工决定 |
| RawRowTransactionLink | 多条原始记录与正式交易之间的多对多证据关系 |
| LoanContract | 借款或分期合同及计算参数 |
| LoanInstallment | 每期预期本金、利息、费用和状态 |
| LoanTransactionAllocation | 实际交易分配到某一期的本金、利息或费用 |

早期不要把所有来源字段直接塞进现有 Transaction 表。通过关联表保持现有正式账本模型稳定，也更容易继续合并上游更新。

## 11. 匹配策略

### 11.1 精确层

精确层可自动处理，但结果必须可查看：

- 已存在的文件哈希；
- 同来源稳定交易标识；
- 同一批次内完全相同且来源标识一致的行；
- 已有人工确认关系。

### 11.2 候选层

候选层输出匹配分数和原因，不直接删除：

- 金额、币种；
- 时间差；
- 支付渠道与资金账户；
- 订单号和商户单号；
- 商户、商品、备注相似度；
- 交易状态和方向。

匹配结果必须解释“为什么认为相同”，不能只给一个不可解释的分数。

### 11.3 学习层

第一版不需要机器学习。可以把人工结果沉淀为确定性规则，例如：

- 某支付宝支付方式文字固定映射到某张信用卡；
- 某银行描述固定识别为信用卡还款；
- 某机构扣款按合同映射到本金、利息和费用。

规则需要支持预览、禁用和回溯影响。

## 12. 分阶段交付

### 阶段 0：工程基线

- 确认上游同步方式和开发分支策略；
- 跑通前后端测试及本地开发环境；
- 为新增模块形成技术设计；
- 不修改现有导入语义。

### 阶段 1：持久导入与同来源精确去重

范围：

- 导入批次、文件哈希、原始行和导入历史；
- 支付宝、微信先接入新的来源元数据；
- 同文件、同来源交易号和强指纹去重；
- 显示覆盖账期和未处理数量；
- 保留现有导入接口供兼容。

验收示例：

- 同一个文件再次上传，不新增正式交易；
- 两个重叠月份的支付宝账单只产生一份相同订单；
- 用户能从正式交易追溯到文件和原始行；
- 两笔真实的同日同额消费不会仅凭金额被合并。

### 阶段 2：跨来源人工对账

范围：

- 候选匹配服务和审查页面；
- 同一经济事件、转账两侧、退款和不匹配等决定；
- 多来源证据关联正式交易；
- 决策持久化和安全撤销。

验收示例：

- 支付宝 + 信用卡流水最终只统计一笔消费；
- 银行卡还信用卡最终只统计一笔内部转账；
- 退款不被当作重复消费删除；
- 重叠账期再次导入时不重复询问已确认记录。

### 阶段 3：贷款与分期

范围：

- 合同、四种还款方式、费用、优惠和有效年化；
- 逐期计划与还款进度；
- 实际交易匹配及本金/利息/费用分配；
- 从旧 IRR 项目迁移金标测试数据。

验收示例：

- 四种还款方式在相同输入下与旧计算器结果一致；
- 必付费用会进入总成本和有效年化；
- 还款本金不进入消费统计；
- 信用卡原消费转分期不会新增第二笔消费。
- 同一分期连续出现在多个月账单中，只建立一份合同；首次确认后逐期证据自动关联，冲突才进入人工处理。

### 阶段 4：可信财务总览

范围：

- 资产、负债、净资产和流动资金；
- 消费、债务本金、利息费用和内部转账分开展示；
- 未来待还；
- 账户覆盖率和待确认数据提醒。

验收示例：

- 所有数字都能下钻到正式交易、贷款计划或原始证据；
- 打开总览先看到净资产、本月生活消费、下一笔待还和一句可信度；
- 缺少某个账户账期或余额未核时时，总览有明确警告且不假装已对账；
- 日常总览明确显示“截至今天”，默认周期由系统自动推导；进入历史回看或覆盖明细时，相关截至日期和覆盖区间清晰可见。

## 13. 非功能要求

### 13.1 隐私

- 默认不向外部服务发送账单、商户、卡号、贷款或余额信息。
- 日志必须脱敏，不记录上传文件内容。
- API 返回只允许当前 uid 访问自己的批次、原始行、合同和关联。

### 13.2 可审计和可恢复

- 原始记录、人工决定和正式交易之间可双向追踪。
- 自动动作记录规则和版本。
- 所有批量入账操作具备幂等键。
- 不以物理删除作为去重手段。

### 13.3 金额与计算

- 金额沿用 ezBookkeeping 的最小货币单位整数方案。
- 利率和 IRR 计算避免二进制浮点造成不可解释的金额误差。
- 合同和计划保存 calculationVersion，算法变更不能静默改写历史结果。

### 13.4 兼容性

- 保持 SQLite、MySQL、PostgreSQL 三种数据库可用。
- 新增能力尽量使用独立模型、服务、API 和页面，减少修改上游核心交易模型。
- 保留现有导入功能，在新流程稳定前不做破坏性替换。

### 13.5 测试

- 去重服务使用表驱动测试覆盖相同、相似和不相关场景。
- 每个来源解析器保留脱敏样例文件。
- 贷款算法使用旧 IRR 项目的金标用例。
- 至少覆盖重复上传、并发提交、部分失败、撤销和跨用户隔离。

## 14. 当前非目标

以下内容暂不进入 MVP：

- 银行 OpenAPI 自动拉取；
- 代扣、还款或支付能力；
- 征信查询；
- 借贷产品推荐、评级或还款建议；
- 微信小程序发布；
- 多人家庭共享账本；
- 使用大模型自动处理原始财务数据；
- 仅凭金额与时间接近、且没有付款账户或订单等稳定材料时的跨来源自动合并；
- 一开始支持所有银行的专用解析器。

## 15. 默认假设与待确认项

为避免阻塞第一阶段，先采用以下默认值：

- 默认币种为人民币；
- 贷款默认每月一期；
- 第一批专用来源为支付宝和微信，银行账单先使用通用映射，再按实际样本增加解析器；
- 原文件默认保存在自托管存储，可由用户删除内容；
- 弱跨来源匹配必须进待办；符合 IMP-008 / REC-003 高置信条件的可以自动关联并入账一次；
- 正式交易仍是所有余额和统计的唯一口径。

后续需要用户提供或决定：

- 第一批要导入的具体银行、信用卡和网贷平台；
- 希望把历史收支账单追溯到哪个最早账期；
- 是否长期保留原始文件；
- 不规则还款日和提前还款是否进入首版贷款模块；
- 是否需要把旧 IRR 小程序已有记录迁移进来。

## 16. 完成标准

“全的记账工具”不等于导入文件越多越好。项目达到核心目标的标准是：

1. 每个报表数字都能说明来自哪个账户、正式交易或贷款计划；
2. 每笔正式交易都可以追溯到人工录入或一条以上原始账单证据；
3. 同一经济事件不会因为出现于多个平台而重复计入；
4. 系统能区分消费、内部转账、借款到账、偿还本金、利息和费用；
5. 数据有缺口时主动说明缺口，而不是输出看似完整的结论。
