# 个人财务业务规则与验收

> 状态：已确认产品需求的业务基线；目标设计尚未全部实现
> 产品需求：[个人财务用户需求.md](./个人财务用户需求.md)
> 目标架构：[个人财务架构设计.md](./个人财务架构设计.md)
> 重整前原文：[个人财务业务规则与验收-20260821-重整前.md](./归档/个人财务业务规则与验收-20260821-重整前.md)

本文只规定“什么算对、什么必须阻止、什么可以稍后处理”。当前代码尚未实现的目标会明确标注，不用目标描述冒充现行行为。

## 1. 权威事实与对象边界

### RULE-001 正式账本权威

- 正式 `Transaction`、`Account`、分类和标签是余额、收支与常规报表的唯一权威；
- 原文件、原始行、候选、待办、关系建议和贷款计划不得直接改变余额；
- 不得新增第二套正式账本或用前端汇总替代核心账本。

### RULE-002 证据与交易分离

- 每份文件、批次和原始行独立、不可变、可追溯；
- 一笔正式交易可以关联多条证据；
- 一条证据在同一经济语义下不得重复生成多个正式效果；
- 证据补到既有交易时只新增关系，不重复记账。

### RULE-003 计划与实际分离

- 贷款、分期和信用卡还款计划描述预期；
- 只有实际正式交易能够推进已还进度和改变余额；
- 未发生的计划不得计入现金流、消费或账户余额。

## 2. 正式交易准入

### RULE-010 必需字段

一笔事件进入正式账本前必须明确：

1. 实际发生时间及其依据；
2. 非负最小货币单位金额和币种；
3. 经济性质；
4. 资金账户；
5. 转账、还款、借款等双边事件的对方账户。

生活分类、标签、备注、地点和附件不是入账门槛。

### RULE-011 经济语义分层

必须分别保存或可重建：

- 资金方向：流入、流出；
- 经济性质：收入、消费、内部转账、借款、还款、退款、费用、余额调整、未知；
- 生活分类：餐饮、服饰、交通等，可空；
- 关系：同一事件、退款原交易、转账对端、债务合同和期次；
- 判断状态与依据：自动、人工、待处理、规则版本。

来源“收入/支出/不计收支”不能单独裁决经济性质。来源交易类型、账户性质、对方、状态、关系证据和历史人工规则共同参与判断。

### RULE-012 未知经济性质

- 资金方向已知但经济性质未知时，事件保留在待处理，不计入正式收入、消费、余额和净资产；
- 系统只询问缺失的性质或账户，不重新询问已经确定的金额和方向；
- 其他清晰事件可以先完成；
- 覆盖状态必须说明仍有未入账资金事实。

此规则属于目标行为；当前任务级确认和普通转账默认仍需后续设计改造。

### RULE-013 未分类

- 经济性质、账户等必需字段明确但生活分类未知时，交易可以未分类入账；
- 未分类计入账户余额、净资产和生活消费总额；
- 未分类不进入餐饮、服饰等分类构成；
- 后续补分类不得改变交易身份和金额。

## 3. 文件、解析与来源身份

### RULE-020 文件防重与重解析

- 同一用户相同文件内容使用 SHA-256 防重；
- 普通重传返回已有文件；用户主动上传入口随后自动按当前规则生成新批次，不重复保存原文件；
- 显式重解析产生新版本批次，旧批次和证据保留；
- parser 与 normalization 分别版本化，语义变化不得原地改写历史行。

### RULE-021 解析失败隔离

- 文件级不可读只使该文件失败；
- 行级问题保留原始内容和问题码，其他有效行继续；
- 同一次更新中的其他文件不得被单个失败文件阻止；
- 不支持的来源形成覆盖缺口，不得假装完整。

### RULE-022 来源适配器边界

- 适配器只做探测、解析和统一字段投影；
- 适配器不创建正式账户、不写正式交易、不猜跨来源关系；
- 能可靠 Probe 的自动识别，不能可靠识别的显式选择；
- 通用银行表格只有在工作表、表头、时间、金额与方向结构得到唯一安全结果时才自动解析；单一带正负号金额列的正负语义必须由稳定来源规则或用户明确确认，不得猜测；
- 未经人工复核的 OCR 结果不得自动入账。

### RULE-023 来源记录身份

- 来源身份只使用稳定交易号、完整稳定订单组合，或无稳定标识时的“文件内容 SHA-256 + 规范化物理定位”；
- 同一文件中的不同物理行默认是不同来源记录，内容完全相同也不得自动归为同一身份；
- 同一文件同一物理定位的显式重解析复用来源身份；不同文件中的相同内容在无稳定标识时默认独立；
- 内容指纹、日期、金额、商户、说明和付款方式只能用于候选召回，不得进入来源身份唯一裁决；
- 来源账户身份与正式账户映射分离，修改账户映射不得改写历史来源身份；
- 同一稳定身份金额、币种、方向或经济效果冲突时必须保留证据并转人工处理。

## 4. 账户发现与忽略

### RULE-030 账户发现

- 用户可以先上传账单，再创建或沿用正式账户；
- 支付宝、微信和银行账单中的付款方式按规范名称聚合；
- 银行卡匹配至少使用银行、卡种、币种和脱敏标识，不能只凭末四位；
- 同一任务的同一付款方式只处理一次；
- 唯一可靠的历史映射自动沿用，删除、隐藏、币种冲突或歧义时重新确认。

### RULE-031 忽略与改回

- 整组忽略表示该付款方式不属于当前账本或用户不想管理；
- 忽略只保留证据，不创建账户、不入账、不进总览；
- 开始整理前必须展示本轮完整资金账户清单：已映射账户展示当前正式账户，已忽略账户展示忽略状态，未处理账户要求选择已有账户或创建新账户；已忽略账户不得成为必选项、阻塞整理或生成账户待确认问题，并允许当场恢复；
- 整组决定可记住并在后续默认沿用；
- 单笔不入账不得写成整组永久决定；
- 改回后只恢复尚未入账记录，不静默重写历史正式交易。

### RULE-032 余额可信度

- 账单流水不是期初余额；
- 新建账户未核对余额时总览必须标明；
- 余额调整和真实收入消费分开；
- 账户余额权威仍来自正式账户和交易。

## 5. 去重与跨来源同一事件

### RULE-040 同来源记录再次观察

- 稳定交易号或完整稳定订单组合相同且核心语义一致时，可以确认是同一来源记录的再次观察；
- 无稳定来源标识时，只有同一文件内容与同一物理 locator 才能确认是同一来源记录；
- 不同物理行、不同稳定交易号或不同稳定订单组合必须分别保留；
- 内容相同不进入精确去重。旧强指纹身份只作为历史证据，不能继续决定新事件数量。

### RULE-041 跨来源候选

- 仅金额、日期、时间、商户或说明相同不得自动合并；
- 候选输入必须保留完整来源记录多重集，任何记录不得在跨来源核对前按内容压缩；
- 自动同一事件至少要求金额、币种、账户、方向、候选时间窗和来源语义兼容；
- 信用卡只有日期时可以按账单时区使用自然日；
- 网关词可以从商户比较中去除，但不能因此忽略账户和数量约束；
- 同日同额多笔只有在存在稳定一一解释时自动处理，不能按遍历顺序贪心。

### RULE-042 同一事件结果

- 多渠道同一事件只形成一笔正式交易；
- 字段采用信息更清晰且不冲突的来源；
- 含糊分类不能覆盖人工分类或清晰生活分类；
- 自动决定必须持久、可解释、可撤销。

## 6. 退款、转账与还款

### RULE-050 退款

- 退款与原消费分别保留正式事件；有唯一强证据时建立关系，没有唯一强证据时保留为未关联退款；
- 退款冲回原消费影响，不作为普通收入；
- 明确金额、商户、账户、方向、先后时间且候选唯一时可以自动关联；
- 已关联的部分退款和多次退款累计不得超过原交易可退金额；
- 没有候选或存在多种解释时不得猜测原交易，也不得阻塞整批；未关联退款不继承原消费分类和可退额度，后续可人工补关联。

### RULE-051 内部转账

- 自己账户之间转账不是收入或消费；
- 充值、提现、余额调拨优先解释为账户关系；
- 只有一侧证据且对端未知时保留待处理，不得用资金方向代替经济性质；
- 转账两侧金额或币种不兼容时进入人工处理。

### RULE-052 信用卡还款

- 银行卡向信用卡还款是资产到负债账户的转账；
- 已明确“款项转入”等信用卡还款语义时不再询问是不是还款；
- 还款使用的资金账户未知时只询问资金账户；还款双方都是本人账户时，转出与转入账户必须同时明确且不能相同；
- 信用卡账单还款行不能再次算作收入或消费。
- 支付宝或微信已经投影出完整还款双方时，银行资产侧支出或信用卡侧流入只能作为同一事件的附加证据。自动归并必须同时满足金额、币种、对应正式账户、方向、七十二小时时间窗和明确还款语义，并且每个账户侧候选唯一；多候选不得按顺序或时间最近猜测。

### RULE-053 关闭与失败交易

- 账单明确标记为交易关闭、交易失败、支付失败、收款失败或还款失败时，不得进入正式入账；
- 这类记录保留原始证据和异常原因供用户核对，不得伪装成待补账户或待确认经济性质的问题。

### RULE-054 来源具体动作优先

- 来源适配器先识别商品或动作中的具体语义，再回退到来源交易大类和收支标记；宽泛的“投资理财”不得覆盖“收益发放、买入、卖出”等更具体动作；
- 支付宝“收益发放”是流入所示资金账户的投资收益，不要求虚构基金公司为本人转出账户，也不要求再次确认经济性质；
- 微信的单文件导入与账单整理证据解析必须共用动作和状态分类器；零钱充值、零钱提现、信用卡还款分别保留明确账户关系，退款失败、交易关闭不得生成可入账交易；
- 来源转换器还必须共用同一套双边资金投影：账单归属账户通过来源账户映射解析，付款方式通过当前用户、来源类型、币种和稳定别名映射解析。支付宝和微信的还款目标共用同一解析器，依次查精确付款账户别名、唯一且一致的账户产品族、交易对方中的唯一发卡行信用卡。“花呗”“信用购”“花呗｜信用购”属于同一支付宝消费信贷账户族；该族存在两个不同正式账户映射时不得猜测。两侧均存在、币种一致且账户不同时直接形成可入账关系；任一侧未知、候选不唯一、映射冲突或两侧相同才进入账户待确认。整理器不得再次复制支付宝或微信动作关键词判断；
- 投资买入、卖出、充值、提现、转入、转出和还款仍属于账户关系语义，只有本人账户之间的资金移动才要求两个不同的正式账户；
- 规则语义变化必须提升 normalization 版本，不原地改写历史原始证据行。
- 通用银行 CSV、XLS、XLSX 只在文件容器读取层分流，必须共用同一结构推断、列映射、金额方向与标准化规则；稳定特例只作为声明式表头与方向 profile 注册，不得按银行复制整套解析器。无法唯一可靠识别时由用户显式映射，不得猜测状态、账户和经济语义。支付宝、微信仍使用各自成熟的来源解析与共享动作规则，不能退化为通用银行映射。

## 7. 贷款与分期

### RULE-060 贷款到账与还款

- 贷款到账同时增加资产和负债，不是收入；
- 偿还本金同时减少资产和负债，不是生活消费；
- 利息和手续费是支出；
- 一笔综合扣款需要按本金、利息和费用分配，组件总额必须等于正式交易金额。

### RULE-061 合同与版本

- 合同保存约定，计划保存预期现金流；
- 合同修订追加版本，不覆盖历史；
- 已知利率、已知还款额、费用和优惠使用明确计算版本；
- 未知字段与零值严格区分；
- 算法变化不静默重算历史合同。

### RULE-062 信用卡分期

- 原消费已经入账时，转分期不得新增第二笔消费；
- 分期本金描述负债偿还计划；
- 利息和手续费按实际发生记支出；
- 月度账单期次关联同一合同，不逐月新建合同。

### RULE-063 分期发现

- 自动识别只创建候选，不直接创建合同；
- 稳定身份或既有人工关系唯一命中已关联分期时必须自动复用，不得再次询问“以前是否记过”；无法唯一关联时，核对阶段允许「关联已有分期记录」「新建并关联分期记录」或「这不是分期」。已有记录必须限制为币种和负债账户兼容的活动合同，可按期次等证据推荐并预选，但在没有稳定关系时不得替用户自动提交；列表必须可展开和改选。选择新建必须直接复用现有完整合同表单，表单结果仅作为当前轮次草稿并保存候选引用，不得提前创建正式合同；只有整批原子入账成功后才创建合同与计划。放弃批次、入账失败或从未入账时必须清除草稿，不得留下计划或正式合同；
- 已有稳定来源身份、原消费关系或已确认人工事实且只有一个目标时可自动关联；金额、日期、期次、同一负债账户或文本相似均不能单独裁决；
- 本金无唯一关系时必须进入待确认，且不得投影为普通支出；只有用户明确选择「这不是分期」后才可按普通支出处理。信用卡账单列示的分期本金不是一笔“本次实际转账还款”，不得用还款双方账户问题误导用户；利息和费用仍可按支出就绪；
- 单行同时包含本金、利息或费用但无各组成金额时，必须先拆分，拆分合计必须等于原交易金额；
- 分期本金关系及组成不明会阻止整批入账；合同利率、IRR、费用规则和未来计划不完整不阻塞整批入账；
- 后续期次依靠稳定编号、账户、原消费关系和人工事实关联，不能只凭金额日期；没有稳定原点时，同卡同期的多条记录也必须保持独立。

## 8. 分类和学习

### RULE-070 分类优先级

人工确认事实 > 已确认用户别名 > 清晰来源生活分类 > 保守商户规则 > 未分类。微信“商户消费/扫码付款”和银行“其他”不属于生活分类。

### RULE-071 学习边界

- 用户确认商户分类后可形成同用户规则；
- 规则必须按 uid 隔离；
- 本轮批量补分类只覆盖未入账、未分类、经济性质一致且不可变来源分类、商户或商品线索至少一项相同的交易；来源类型属于匹配键，支付宝与微信不会因同名商户跨来源批量套用；
- 分类弹窗必须复用服务端实际匹配范围展示总影响笔数；总数为一时只允许单笔确认，不显示批量选项；
- 金额和日期不参与批量分类范围判断；批量动作必须原子提交，每笔事件保持独立身份、金额、账户、性质和证据关系；
- 新的模糊来源不得覆盖历史人工规则；
- 分类规则变化只影响尚未确认或用户明确要求重算的范围。

## 9. 任务、待处理与部分完成

### RULE-080 任务容器

一次更新任务保存用户选择的文件和处理进度。确认后文件集合锁定；确认前增删文件会重新计算受影响账户、事件和待处理。

### RULE-081 异常隔离

- 文件失败只影响文件；
- 账户问题只影响使用该账户的事件；
- 关系问题只影响直接成员；
- 分期信息不足只影响债务候选；
- 未分类不阻塞。
- 必须处理问题的展示口径由问题类型、阻塞原因和实际成员数共同决定；单成员问题不得标为“多笔”，非阻塞字段不得冒充待处理原因。

### RULE-082 事件级整理与批次入账

- 已经满足正式准入的事件可以独立完成整理，未解决事件继续待处理，清晰结果不得被反复重算；
- 一次更新任务是唯一核对和入账单位。用户处理或明确跳过全部阻塞事项后，一次确认原子写入本批次全部可入账交易；
- 系统不得在后台静默逐笔入账，也不提供部分入账接口；
- 整批入账必须保持幂等、计数一致、可审计和可撤销，失败不得留下无法解释的半成品。

此规则属于目标行为，当前实现仍主要使用任务级确认；重构直接替换旧工作流，不维护双状态机。

## 10. 核对、纠错与撤销

### RULE-090 核对层级

用户可以从结果逐层查看：最终交易 → 采用字段 → 关联证据 → 自动理由和版本 → 人工决定和修订历史。默认不要求逐笔打开。

### RULE-091 纠错

用户可以拆开错误合并、补合并、修改账户或性质、补分类、恢复不入账和修正关系。纠错只重算受影响对象，不覆盖无关人工事实。

### RULE-092 撤销

撤销前检查正式交易是否被修改、删除、其他批次共享或贷款关系引用。安全时原子撤销自动效果；不安全时展示影响并要求人工处理，不伪装成功。

### RULE-093 计数一致

摘要中的有效证据、附加证据、最终交易、待处理、未分类和已完成数量必须由同一后端计划产生，并与详情列表一一对应。附加证据只表示同一最终事件除主证据外的证据观察，不得解释为重复交易数量。

- `有效证据数 = 最终经济事件数 + 已确认附加证据数`；
- 始终满足：`最终经济事件数 = 已入账 + 待入账 + 待处理 + 明确不入账`；
- 整批入账前“已入账”为零；一次原子入账成功后全部“待入账”事件转为“已入账”；
- 同一批次重复提交入账命令必须幂等返回原结果，不得产生第二次正式写入。

## 11. 覆盖、月末和总览

### RULE-100 覆盖

- 覆盖按账户、来源和日期区间计算；
- 不支持文件、解析失败、尚未出账区间和待处理事件形成明确缺口；
- 部分结果标为暂结，不能冒充完整；
- 迟到账单只补证据和遗漏交易，并修订受影响月份。

### RULE-101 信用卡账期

- 消费按实际交易日期进入自然月；
- 账单日和还款日只用于覆盖、已出账应还和待还提醒；
- 已有可靠未出账证据的消费可以先计入；
- 未被任何来源覆盖的直接刷卡区间保持缺口。

### RULE-102 总览口径

- 净资产来自正式账户余额；
- 生活消费排除内部转账、余额调整、借款到账和偿还本金；
- 未分类计入生活消费总额但不进入分类构成；
- 下一笔待还来自已确认贷款、分期或信用卡信息；
- 每个数字可下钻到正式交易、关系、计划或覆盖依据。
- 总览首屏只展示净资产、本月收入、本月支出、本月结余和下一笔待还；覆盖、解析质量、重复记录和待处理诊断由账单整理工作台负责，不在总览重复实现。

### RULE-103 桌面信息架构

- 总览、交易明细、统计分析、账户和分类管理必须在桌面顶部直接可达；新增区域只保留一个位于业务导航最右侧的加号入口，其菜单同时提供手工记账和账单导入；账单导入入口打开包含上传、核对和记录的完整工作台，页面左侧不重复提供账单整理入口；
- 交易明细必须使用全宽列表，标题旁展示当前范围的收支汇总；交易类型、日期范围和分页必须在内容区控制，交易日历和图片附件不得作为独立交易视图；
- 账户与贷款/分期必须归入同一资产负债导航上下文，进入贷款工作台时顶部账户入口保持激活；账户页侧栏可继续展示资产摘要与账户类别，设置页侧栏只展示当前设置分组；
- 分类管理不得挂载在用户设置布局下，只显示分类类型和一级、二级分类等分类自身上下文；
- 统计上下文只保留标准分析；自定义洞察、交易模板、定时交易、标签管理、交易地点和地图不属于当前产品能力；
- AI 剪贴板文本识别和图片识别保留为显式触发的辅助记账入口，识别结果必须在正式入账前允许用户核对；多用户注册、登录、安全和 `uid` 隔离继续保留，但不增加机构、团队、角色或共享账本；
- 用户资料与应用偏好必须合并为一个设置上下文；移动设备、主题和关于归入头像菜单，汇率管理只在存在非默认币种账户时显示，但直接地址与底层汇率能力不得删除；
- 手机设置页不得重复罗列账单整理、对账、贷款和财务总览等业务模块；首页加号统一提供记一笔和账单整理，贷款入口归入账户上下文，旧重复地址只做兼容跳转；
- 页面级侧栏不得改变交易、账户、统计、账单整理和贷款的业务语义，也不得为了复用布局复制第二套路由或状态；
- 窄屏桌面顶部模块栏允许横向滚动，当前模块、键盘焦点和按钮可访问名称必须保持可识别。

## 12. 多币种

### RULE-110 原币与汇率

- 保留原币金额和币种；
- 不同币种不直接相加；
- 折算记录汇率来源、日期和版本；
- 缺失汇率时展示缺口；
- 购汇、消费、还款和手续费分别表达。

## 13. 隐私、安全与迁移

### RULE-120 隐私

- 所有用户业务查询带 `uid`；
- 原始账单、账户、余额、商户和贷款数据默认不发送外部 AI；
- PF 仓储使用隐私 session，普通日志不记录原始绑定值；
- API 只返回安全名称、脱敏标识和必要业务字段。

### RULE-121 数据和迁移

- PF schema 使用连续、forward-only、可重入显式迁移；
- SQLite、MySQL、PostgreSQL 同时成立；
- 唯一约束和事务是并发最终裁决；
- 公共状态机、表或 API 变化先冻结设计、迁移和回滚方案。

### RULE-122 旧数据

- 正式交易、原始证据、账户映射、来源身份和人工决定必须保留或经过显式迁移；
- 旧 billflow 任务、todo、自动候选和未入账投影不要求兼容，可以在备份后删除并从保留事实重建；
- 新代码不得为旧 API、旧页面或旧状态机保留长期双读、双写和适配分支；
- 新规则不得静默改写历史正式交易；
- 重解析和重算保留版本与原因。

## 14. 最小验收矩阵

| 场景 | 必须结果 |
| --- | --- |
| 重复上传未入账的同一文件 | 复用原文件存储，按当前规则生成新批次；成功后旧工作批次废弃且不再出现在正常列表 |
| 重复上传已入账的同一文件 | 返回已整批入账结果，不重新解析、不创建新批次、不重复正式入账 |
| 同来源稳定身份一致 | 只保留一份经济效果，多次观察证据仍保留 |
| 同一文件不同物理行内容完全相同 | 保留多笔，不标记精确重复 |
| 同一文件同一物理行显式重解析 | 复用来源身份，不新增经济效果 |
| 不同稳定交易号但内容相同 | 保留多笔 |
| 两笔真实同额消费 | 保留两笔 |
| 支付渠道与信用卡同一消费 | 一笔正式消费，多条证据；同日同额多笔按一对一数量匹配 |
| 明确退款 | 原消费和退款两笔事件，建立退款关系 |
| 信用卡还款 | 资产到负债的转账，不算收支 |
| 贷款到账 | 资产与负债同时增加，不算收入 |
| 贷款扣款 | 本金减负债，利息费用算支出 |
| 未分类交易 | 正常入账，进入非阻塞补分类 |
| 一个文件失败 | 其他文件继续完成并显示缺口 |
| 一个事件不确定 | 只阻塞该事件，其他事件先完成整理；整批默认统一确认入账 |
| 点击本轮账单 | 在当前整理工作台展开上传与来源选择，不打开历史账单记录；进入核对后明确显示来源已锁定 |
| 锁定后希望增删来源 | 尚未正式入账时只能放弃本轮并创建新一轮重新选择；原文件、解析行和旧轮审计事实继续保留 |
| 页面数据变化 | 正常操作后自动同步；不得用并列的「重新整理 / 刷新」要求用户理解重算与重载差异 |
| 桌面导航 | 交易明细、账单整理、账户、分类和分析无需展开即可进入；高级与条件能力收纳于「工具」；设备入口和关于信息不占用业务侧栏 |
| 自动结果核对 | 摘要与列表一致，可查看证据和理由 |
| 桌面切换核心模块 | 顶部直接进入总览、交易、统计、账户和分类管理；分类页不出现记账工具、标签或用户设置侧栏；业务导航最右侧只显示一个新增加号，菜单可选择记一笔或进入完整账单整理工作台；统计只提供标准分析 |
| 中文默认与语言范围 | 首次使用默认简体中文、人民币、北京时间、公历和中文日期格式；语言选择只显示简体中文与 English，低频日期、数字和金额格式默认折叠；多币种、汇率、英文账单字段和文件编码继续可用 |
| 设置与条件能力 | 用户资料、偏好、安全、应用锁和数据隐私位于同一设置上下文；设备、主题、关于位于头像菜单；只有非默认币种账户存在时显示汇率管理 |
| 手机入口收敛 | 设置页不出现账单、对账、贷款和重复总览；加号提供记一笔和导入账单，账户页可进入贷款与分期；旧移动页面地址安全跳转到现行入口 |
| 用户纠错 | 只重算受影响范围，人工事实不被覆盖 |
| 跨用户访问 | 不可见且不泄露存在性 |
| 并发重放 | 数据库只保留一个合法结果 |

更细的接口、迁移、算法金标和发布门禁由具体设计任务冻结，不在本文复制。
