> 目标编号：EDITOR-20261009。本文冻结产品逻辑、状态模型、保存契约和实施验收，是本次跨模块重构的唯一详细方案，不是现状说明。基线为远端 main `5d77dee9955e191f4d061f243d31ad96328386cb`，源码树 `c6c3672b78b9c666437ec1e7827361777f71a908`。本次交付中的方案已编写完成；生产编辑器重构是否完成、哪些检查实际运行，只看[实施规划](招财猫记账本实施规划.md)。不能将本文件中的目标表格解释为已实现功能。

现行流程见[主逻辑 §4.6](招财猫记账本入账逻辑说明.md#46-核对与保存决定只改变明确选中的事实)，约束沿用 R01～R19，新增统一编辑目标为[业务规则 R20](招财猫记账本业务规则与验收.md#1-不可破坏的规则)。贷款账务不另起第二套规则，沿用[贷款与分期改造方案](贷款与分期改造方案.md)。

## 1. 本次到底统一什么

**同一性质、同一资金结构、同一业务阶段，应得到相同字段、编辑能力、校验和保存结果；不因自动识别或手动选择、从哪个问题入口进入而改变。**

统一的是交易编辑模型、业务区域、字段权限和保存边界，不是把全部性质做成一张无差别表单，也不是把判重、贷款建档和普通改备注揉成一种操作。

明确采用以下决定：

1. 单笔卡片以 `eventId` 为编辑主体。`issueId` 只表示提示或待处理关系，不能决定表单主体，也不能默认选用问题组第一笔。
2. 待核对编辑、已核对查看、已核对修改使用同一套区域和字段描述。只读/编辑是模式，不再各写一套交易表单。
3. 顶部固定显示性质与金额摘要；基础字段、资金账户、组成和关联、原始账单依次展示。当前问题可以在顶部提示并定位，不改变字段的固定次序。
4. 识别值是可修改的初值，不是锁定依据。只有凭据字段、派生值、生命周期和关系保护可以锁定，并必须说明原因。
5. 普通编辑只改本笔，不隐式修改来源账户长期映射，不把同组成员的金额、备注、性质一起覆盖。
6. 一次保存当前笔的字段及兼容关系决定，在一个请求、一个事务内完成；保存草稿不改正式余额。
7. 判重合并/拆分、历史账目对应和正式贷款创建保留显式专用操作。关系操作影响多笔时，显示完整范围并单独确认。
8. 不增加跨端框架、通用工作流引擎、第二套账本、通用 EAV 字段表或新的长期分支。先收敛现有边界，再删除重复分支。

## 3. 人工核对次序与页面次序

### 3.1 人工核对按依赖，不按固定流水线

后端先做来源语义和基础账户识别。人工待办仅由真实未解决事实产生，默认优先顺序为：状态/来源/身份/核心事实冲突或缺失；判重的必要前提；同笔/历史对应；性质；本人或他人归属；资金账户；金额组成；退款/贷款/分期关联。没有对应问题就跳过。

该顺序是依赖优先级，不是“所有记录必须点八次”。已经可判断同笔的先处理，避免重复填两份；缺少同笔判断必需账户的先补账户。性质和账户可以同屏保存。保存、合并、拆分、改性质后，按新事实重算，已经被解释的事项直接消失。

已知性质仅作上下文。未知性质是一项待办，不能既当置顶标签又重复列一次。未确定性质时只称“资金账户待确认”，不能提前要求“还入账户”。同组其他成员的 reasonCodes 不贴到本笔。

### 3.2 卡片与详情固定结构

卡片左侧：基础核验/同笔提示、性质、适用的剩余事项；沿既有服务端待办顺序排列，不用箭头承诺必经流程。右侧有可处理入口时只显示“处理 ›”；无可处理问题的待核对记录显示“查看详情 ›”，不能伪造一个可保存操作。点击必须继续传入当前 `eventId`。

详情的固定区域顺序为：

- 主标题为“核对交易”或“交易详情”；还款编辑沿用“确认还款”。当前阻断/待办保留提示，不插到原有两张首屏卡片之前。
- 性质、金额和对方/时间摘要卡片；编辑模式允许打开性质选择和金额输入，还款归属保留在同一卡片内。
- 资金账户卡片。两端时复用已认可的纵向样式，付出端在上、收到端在下；缺失端整块强调，已填账户也可打开同一个目录；银行缺尾号的建议入口留在账户卡片中。
- 日期、时间、交易对方、备注与结构切换在“日期、备注与更多设置”展开完整编辑；已有的字段能力和保存规则不因首屏收起而消失。
- 金额组成和业务关联。只展示当前性质适用部分；可选项仍有明确的“选填/稍后补”入口，不能因为没识别就完全消失。
- 原始账单。按来源分别展示原列名、值、文件和行号；与人工修正分开，修改上方字段不改原文。
- 固定底部保存/关闭，长内容独立滚动。按钮状态和错误提示必须来自同一校验结果。

只读模式使用同一字段顺序和值；进入修改时仅切换控件状态，不能再换成另一套账户样式。退款继承分类、组成合计等派生字段始终只读。

## 4. 字段权限与各性质完整规则

### 4.1 共用字段

| 字段 | 编辑规则 | 验证和保存 |
| --- | --- | --- |
| 交易性质 | 未入账普通资金事件可修改，选项按记录角色与实际能力过滤 | unknown 可留草稿，不能作为可入账性质；不把 unknown 自动变成支出 |
| 记账金额 | 允许修正；显示原值和人工值差异 | 整数分、非负、数据库范围；空值不等于零。实际可入账的零值沿现有类型校验，不因 UI 放开而新造零额流水 |
| 交易时间 | 允许修正发生日期和时间，保留秒与原时区 | 严格日期往返校验，拒绝 2 月 30 日等自动滚日；以保存的时区转换，不使用当前设备时区悄悄改义 |
| 交易对方 | 修改记账用名称，不改凭据对方 | 显式空字符串代表清除人工记账名称；不能用 `value || raw` 让已清除的值又出现 |
| 备注 | 修改记账备注，空值可清除 | 不与原始说明混成一个可改字段；长度沿用交易备注上限，超长原文仍在原文区 |
| 币种 | 本期只支持 CNY，显示但不提供伪多币种输入 | 服务端拒绝其他币种；不得只改标签、不换算金额 |
| 资金方向 | 从性质、端点和支付结构派生 | 不再提供可与性质矛盾的第三个独立方向选项 |
| 分类 | 收入/支出/费用可选填或清除 | 同用户、可用、类型匹配；可后补。退款分类随原消费，不单独输入 |
| 原始状态/订单号/来源账户文字 | 只读凭据 | 不可用“改成成功”解除状态冲突 |
| 记账影响/合计/差额 | 派生只读 | 不接受客户端直接指定余额、净资产、ready 状态或已还进度 |

金额、时间的修正也不能凭空解除真实来源身份、状态、同笔、贷款或已有关联冲突；相关决定需重新核实。纯文本修改不自动撤销已经确认的退款或同笔关系。

### 4.2 各性质字段表

所有行都包含上面的基本信息及下方原始账单。表中的“必需”是形成可入账结果的条件，不意味着用户不能保存合法的未完成草稿。

| 性质/角色 | 必需字段 | 选填或条件字段 | 不出现的字段 |
| --- | --- | --- | --- |
| 性质待确认 | 选择性质；已有金额/时间照常可修正 | 已知的账单所属账户、对方、备注 | 不预先展示还入账户、还款本金或强制退款关系 |
| 支出 | 金额、时间、付款账户 | 支出分类；单账户/组合支付；组合支付的账户金额与说明 | 收入分类、借款本金、无关贷款计划 |
| 收入 | 金额、时间、收款账户 | 收入分类、对方、备注 | 付款分配、还款本息费、退款原消费 |
| 内部转账 | 金额、时间、转出与转入账户 | 备注；有关联来源则显示已知关联 | 普通收入/支出分类；不自动创建贷款待办 |
| 借款到账 | 金额、时间、借款负债账户、到账账户 | 已有贷款关联信息；入账后补计划入口 | 还款本息费；未来利息不能混入到账本金 |
| 本人还款 | 金额、时间、付款账户、还入账户、本人归属 | 普通清偿/贷款本息费/多个还入账户；实际适用的计划和费用关联 | 普通收支分类；不能假定总额全是贷款本金 |
| 代他人还款 | 金额、时间、自己的付款账户、他人归属、处理方式 | 无需收回时支出分类；需收回/不确定时保留待核对 | 不创建他人的信用卡为自己的负债；不伪造应收支持 |
| 退款 | 金额、时间、收款账户、关联状态 | 选择原消费，或符合条件时明确暂记待关联；继承分类 | 独立收入分类、自由编辑的继承分类 |
| 利息/手续费 | 金额、时间、付款/承担费用账户 | 费用分类；已识别贷款/分期来源及关联 | 不能把清偿旧费用作为新的费用支出 |
| 分期本金出账（来源角色） | 所属信用卡、本期本金、可用发生时间 | 已知期号/总期数、来源/计划关联状态；来源修正入口 | 实际付款账户、本息费付款分配、自动已还勾选 |
| 分期利息/手续费 | 费用金额、所属账户、费用事实时间 | 费用类别、分类、期次与计划；已有费用认领 | 不重复生成已计费用；没有扣款凭据不填银行卡实付 |
| 余额调整 | 不列为普通导入可选性质 | 历史该类事件只读说明，提供账户维护入口 | 不显示一个后端必然拒绝的“保存为余额调整” |

### 4.3 资金账户类型约束

账户均必须属于当前可信用户，或属于当前批次尚未物化的账户草稿；币种一致、未归档、实际可用。两端必须不同。过滤列表只能改善体验，服务端必须再校验。

- 收入、退款可以增加资产，也可以减少负债，因此收款端不限制为银行卡/钱包。
- 支出、费用可以减少资产或增加负债，因此付款/承担费用端允许资产或负债账户。
- 内部转账允许两个不同、可用的账本账户，包含负债之间的迁移；不因此虚增收支。
- 借款到账为负债端到资产端；本人还款为资产端到负债端（credit 或 other_liability）。用一张负债账户替另一张还债，应显式记为负债间资金转移，不能冒充资产付款。
- 普通信用卡还款允许 credit 还入端；现有贷款本息费模型要求资产端到 other_liability，仍按[repayment-booking](../cloudfunctions/catledger-import/src/repayment-booking.js)校验。不能为了让两个表单看起来相同，把信用卡整单还款硬塞进该贷款模型。
- 分期本金出账所属账户为信用卡类型，不索取实际还款端。

**自动识别与手动改成借/还必须使用同一份上述约束。** 不再依赖是否有 fundsProjection 或 repaymentOwnership 决定是否检查负债类型。

### 4.4 还款归属与本息费

本人为打开表单时的默认模式，不是已保存的事实。已有本人/他人决定、已恢复草稿优先；没有明确来源时允许用户改选，不因名称含银行就断言是本人。

代还无需收回：记账结果为支出，保留“代他人还款”的业务说明与归属决定。代还需收回或不确定：可保存“待核对”的业务决定，但仍阻止整批入账；本期不新增未设计的应收账款系统。界面不能一边显示还款，一边悄悄按普通收入处理。

普通信用卡清偿不强制拆每期本金与费用、不强制关联计划；还款本身不重新产生消费。贷款本息费模式必须明确填写本金、利息、费用，三个分项相加等于付款总额；无费用必须明确为零，未知不能默认零。

利息/费用分别选择“补记本次费用”或“清偿已记费用”。前者需要适用的费用分类与认领保护；后者只清偿原负债，不重复支出。已有收费项、费用清偿、贷款版本和本金时间线继续由现行领域校验。计划关联可以延后，但组成未知不能以“延后关联”掩盖。

### 4.5 组合支付与多账户还款

两者是资金结构，不是经济性质。共用金额行组件，但领域意义分开：组合支付是多个付款端；多账户还款是多个还入端。

组合支付每个账户一行、金额可改，总和必须等于实际付款额；重复账户合并或明确报错，不允许重复算同一份钱。非资金优惠、积分、红包说明不自动当作一个账本账户。保留现行来源组成及必填核对说明保护。支持的性质以现有 payment-resolution 为限（支出、还款），其他性质不能由 UI 自行开启未经定义的组合语义。

多账户还款一付款端、多个可用负债还入端，每行有金额，合计等于总额；不得创建“合并账单”虚拟负债账户。关联原始合并账单只是证据，不是还入账户。

本期不新增“多个付款端 × 多个还入端”的自由配对矩阵。此组合没有明确分配规则时显示结构不支持并保留待核对，不能任选第一账户压扁。已存在的分配不得因切换性质或重新打开而丢失。

### 4.6 退款关系

退款选择原消费的能力由当前草稿性质是 refund 决定，不依赖原来是否生成 refund_relation 问题。候选读取可以检查本笔尚未保存的退款金额/时间，但只读，不提前改事件或创建关系。

候选分为同批事件与正式历史交易；选项必须含类型、稳定 ID 和版本，不能把两种 ID 混用。服务端在用户范围内重验：非自身、原消费/适用费用真实有效、币种一致、时间合理、剩余可退金额足够、未被删改或受贷款/付款组保护。累计校验包含既有有效退款，本次更新不重复累计自身，跨来源同一已记退款不能双算。

只有候选检查已经完成、无仍需裁决的来源冲突或有效候选，才允许沿现有规则“暂记待关联”。加载失败、只加载完第一页、没有拿到详情都不等于“没有候选”。暂记影响账户，但不伪造原消费或继承分类。

修改已有退款的金额、账户或时间，需要同事务重新校验现有关联。修改原消费金额必须检查所有相关退款，不能先改总额后另请求失败。原消费已被退款引用时改为不兼容性质，拒绝并列明处理入口，不能静默删掉他笔关系。

组合支付原消费的退款不能随便挂到一个分项。未具备完整分摊协议时沿用专用保护并显示原因；本次不假定已有多对多退款实现。

### 4.7 分期和贷款资料

记录角色与性质正交：资金事件、分期出账来源分别处理。recordRole 从已有经过验证的来源字段派生，不开放一个“实际付款/来源”任意切换开关，也不迁移历史经济性质枚举来解决界面问题。

本金出账在编辑器内展示所属信用卡、本金、时间、期次、计划状态。人工来源修正保留单独的有效值与来源原值；仍只能修正来源事实，不生成付款。总期数、合同编号等未经证据确认不能自动填入。无计划时显示“入账后关联/新建”，不是必填缺口；识别到期号不代表已还。

已具备来源认领或费用关联时，变更账户、金额或期次先重验原关联；必要时明确解除/重新认领，不能静默转移已被另一计划占用的来源。创建或修改正式贷款计划继续走正式计划命令，不能在读取详情、切换性质或保存普通交易草稿时自动执行。

本息费填写区域可以复用到导入编辑器，但贷款创建、正式付款整组维护、历史已还及余额保全仍按原领域命令执行。统一 UI 不扩大这些操作的授权范围。

## 5. 性质和模式切换的确定规则

### 5.1 统一解释，不改原文

草稿分为基本信息、当前有效性质/模式、资金端点、分配、关联与待恢复输入。当前有效字段构成提交内容；切到其他模式后暂留的旧输入只用于切回恢复，不参与校验、提交或入账。

每次改变性质/模式：按以下表生成新草稿及失效提醒；需要释放已经保存的关系时标出影响并要求显式确认；网络读取只补目录或事实，不能重初始化用户草稿。

| 切换 | 保留 | 本次失效/重验 |
| --- | --- | --- |
| unknown → 已知性质 | 金额、时间、对方、备注；能按原来源方向确定角色的账单账户 | 新性质的账户类型、组成和关联立即计算；没有依据的不猜对端 |
| 支出 ↔ 费用 | 同方向账户和兼容支出分类 | 涉及贷款收费认领时重验；不能把已有清偿又认作新费用 |
| 收入 ↔ 支出/费用 | 基本信息、同一账单账户的身份 | 分类类型切换清空当前有效分类；显示资金影响改变；不继承不兼容分配 |
| 单端 → 转账/借款/还款 | 基本信息；账单账户按原始方向绑定到正确端 | 收支分类退出有效提交；另一端待选，类型约束随性质更新 |
| 转账/借款/本人还款之间 | 当前已明确的实际付出与收到端 | 校验新角色类型；不因 nature 改变再次交换账户；贷款/归属不兼容时清理或要求确认 |
| 双端 → 单端 | 基本信息与该单端性质对应的原账单账户身份 | 对端、还款组成和计划关系退出提交；不可从数组首项猜保留账户 |
| 任意允许性质 → refund | 基本信息；原账单账户 | 按退款规则设置收款端并读取候选；分类变为随原消费；无候选前不得暂记 |
| refund → 非退款 | 基本信息；可复用的账单账户 | 明确解除本笔退款关联/历史原消费引用并同事务保存；受其他业务依赖时拒绝 |
| 本人 ↔ 代他人还款 | 各模式暂存输入 | 代还不提交本人负债端；切回本人重新验证账户可用性；不自动保存 |
| 普通还款 ↔ 本息费 | 基本信息及兼容的真实端点 | 普通模式不提交本息费；切入本息费明确零值、分类和组成；已认领收费项需要受控解除 |
| 单账户 ↔ 组合支付 | 总额、基本信息、可复用账户 | 切入不自动分摊；多行切回不能只保留第一行金额；需明确确认当前有效组成 |
| 任意模式 → 暂不确定 | 基本信息与未提交输入 | 不以未知性质清洗原有硬阻断；已确认关系不能被无提示抹掉；仅保存合法未完成草稿 |

### 5.2 哪些操作需要二次确认

正常选择性质、账户、分类不重复弹确认框。只有会解除**已保存**的退款/贷款/费用/分配关系、改变组操作范围或产生正式计划时，显示具体影响并确认。单纯在未保存草稿的两个选项间往返不弹一串确认框。

触发不支持转换时，保持旧有效草稿并显示原因，不接受“看起来选上了、保存必然报错”的状态。已有原请求结果未知时，禁止切模式或改请求字段，先确认原写入结果。

## 6. 一个草稿与一个编辑会话

### 6.1 草稿模型

使用业务明确的对象，不把输入塞到任意字段字典。以下是目标模型示意，不是当前已经发布的 API：

```js
{
  eventId, eventVersion, updateId, updateVersion, viewVersion,
  recordRole,                         // 服务端派生，只读
  base: { economicNature, amountMinor, occurredLocalAt,
          timezoneOffsetMinutes, currency, counterparty, note },
  funds: { sourceAccountId, destinationAccountId },
  composition: { kind, paymentParts, repaymentParts, evidenceNote },
  repayment: { owner, otherTreatment, mode, components, loanSelection, chargeSelections },
  refund: { mode, originalKind, originalId, originalVersion },
  sourceCorrection: { periodNumber, totalTerms },
  dirtyFields,                        // 精确区分未修改、清除和替换
  dormant                            // 当前会话切回恢复用，永不直接写入服务端
}
```

账户 ID 是草稿值。`pickerIndex` 只从当前目录临时计算，目录搜索、分页、加载顺序不能成为账户身份。无效或不在当前页的已选 ID 显示原选择与不可用原因，不自动回到第一项/新建账户。

`funds.sourceAccountId/destinationAccountId` 表示实际资金端，不等于目前存储字段 ledger/counterparty 的固定位置。唯一适配函数把完整事件转换为实际端点，唯一反向适配函数产生旧存储字段；根据来源方向和现行分配投影完成。页面、账户目录、按钮和提交不得各写一套 reverse 判断。

未知性质阶段保留稳定“原账单账户”锚点；切换到双端后才按已核实的来源方向定位。来源方向尚未完整读取时，不猜、不可提交依赖该方向的双端修改。

### 6.2 只读事实与可编辑草稿分开

服务端快照包括原始/有效事件、适用能力、有效关联、版本和当前待办。原始账单单独分段读取。首次完整读取后初始化草稿一次；晚到的账户名、原文、费用目录只更新事实缓存或标签。

人工草稿优先级高于自动补充。发生外部版本变化时标记 stale、保留输入，要求重新核验；不能悄悄把新版本套在旧字段上自动重发。关闭未保存的普通草稿不写账；保存已发送后关闭页面不代表回滚。

### 6.3 编辑会话状态

| 状态 | 可以做什么 | 禁止什么 |
| --- | --- | --- |
| loading | 立即展示已知摘要与加载反馈、关闭 | 用轻量摘要提交，失败显示成未关联 |
| editing | 修改可编辑字段，按草稿派生区域/待办 | 切换时发送业务写入 |
| saving | 显示提交中；冻结 payload 与 requestId | 再次改字段/重复创建新请求 |
| result_unknown | 恢复原请求、查询原回执 | 换 requestId 重发、整批入账、把超时当失败 |
| saved_refreshing | 显示已保存，刷新摘要与列表 | 因摘要读取失败重写一遍 |
| stale | 保留草稿、重新读取和人工复核 | 自动覆盖草稿或无提示重定位另一交易 |
| readonly/posted | 看同一份字段与原文，走正式账目维护 | 继续调用导入草稿修改绕过正式保护 |

局部候选/目录读取各有 loading/error 状态，不借用全页 busy。所有迟到请求绑定 user/session/update/view/event 及当前选项指纹（例如退款金额/时间/性质），只接受匹配的响应。

## 7. 读取与保存契约

### 7.1 读取：扩展现有详情，不制造第二个权威事件

继续使用 `economicEvents.detail` 与既有原文分段协议，在非原文详情中增加版本化的 editorFacts。它提供记录角色、支持的编辑能力/锁定原因、完整有效字段、关联版本、当前事件待办和必要的原始方向；不是一段可执行的服务端 UI 配置。

客户端持有固定的业务区域定义。性质选择后本地立即计算基础布局；候选、账户可用性、费用/贷款依赖由有界只读查询补充。不能每敲一个数字就调用服务端，也不能把“当前没有加载”当成“该字段不可编辑”。

退款新增独立只读候选查询 `economicEvents.refundCandidates`：输入 eventId、当前版本及本地待验证的 refund 金额/时间/账户、游标/搜索条件；来源可信边界、查询范围和结果预算由服务端重新约束。草稿参数只参与候选筛选，不修改事件性质或落库候选关系。游标绑定完整筛选指纹，旧候选不得对新金额继续使用。

贷款、账户、分类继续使用现有有界目录；必要关联当前项可按 ID 读取。不会为了打开一笔详情，下载整个批次所有事件/原文或完整贷款列表。

### 7.2 写入：扩展 financeUpdates.setReview

保留旧调用的兼容语义，新编辑器明确发送 `editorVersion: 1`。不伪造旧 issueId、不先保存性质再补账户/退款，不从前端串行调用多个写接口冒充原子保存。

目标命令由下列语义组成，具体字段注册必须同步 [shared 契约](../shared/catledger-import.json) 与动作层校验后才能启用：

```js
{
  requestId, updateId, updateVersion, eventId, eventVersion,
  editorVersion: 1,
  fields: { /* 本笔改变的基本信息、合法资金端点和分类 */ },
  composition: { /* 不传=不改；显式替换时传完整分配 */ },
  decisions: { /* 本笔还款归属/本息费/退款关联等明确决定 */ },
  expectedRelations: [ /* 被改变或依赖的关系类型、ID、版本 */ ],
  acknowledgedChanges: [ /* 已确认解除的已保存关系，不能据此跳过重验 */ ]
}
```

字段规则：不传表示保留；nullable 字段传 null 表示明确清除；文本空字符串表示清除记账文本；分配数组显式传入表示完整替换，不与旧数组偷偷合并。拒绝未知键、只读字段、客户端 uid、rawFields、状态/余额/已还进度和超预算数据。

旧服务端没有 editorFacts 版本时，新客户端不能静默退回旧写命令串行保存；显示“需更新导入服务”并允许只读。部署顺序为服务端兼容扩展、验真、新客户端启用；旧客户端仍按旧契约工作。

### 7.3 单事务的固定步骤

1. 沿现有 executeIdempotentMutation 和可信用户锁进入，先处理同 requestId 回执，不自建第二层事务。校验批次仍在 review、event/update 版本正确。
2. 锁定当前事件，读取同一事务下的有效账户投影、源事实及关联。相关账户、原消费、贷款/收费项按现有稳定锁序读取；本批未物化账户只允许引用合法草稿。
3. 对完整候选 next 运行字段白名单、记录角色、转换、账户类型、金额/分配、退款、贷款、收费项保护。客户端 capabilities 和 acknowledgedChanges 都不代替服务端授权。
4. 形成一条可追溯行动，应用本笔字段与被明确允许的关系改变。原始导入行、凭据、稳定身份不改；仅 ordinary 单笔编辑不得写长期账户映射。
5. 重算当前事件的语义有效性和待办。只处理本次确实解释的缺口；状态未知、身份冲突、同笔判断、贷款保护等不得以“保存了性质”为理由删除。
6. 同步受影响关系的版本和相关事件待办；更新当前事件在共享问题中的成员，而不是关闭整组。保留其他成员事实和决定历史。
7. 更新批次版本、汇总及有界命令回执，和业务改变一并提交。任一校验、SQL 或回执写入失败，整个命令回滚。
8. 返回本笔更新版本和仍待核对状态；客户端只刷新必要列表/摘要。若剩余问题仍在，显示“已保存，仍有待核对事项”，不说“核对完成”。

正式余额、收支、贷款付款组和当前净资产只由原 `financeUpdates.post` 整批事务改变。本次保存仅存事件、草稿决定和允许的关联草稿；只读查询不创建问题或计划。

### 7.4 合法未完成草稿与无效数据分开

允许保存字段类型合法、账户引用合法但尚缺必填项的草稿，并保持 needs_action；“保存草稿”不等于“确认可入账”。两端同一账户、越权账户、负数/溢出、失效关联、分项超总额等无效数据不保存。尚未填写的分配需要显式 incomplete 草稿标志，与已确认分配分开，不能传进现有 confirmed paymentResolution 冒充完成。未完成组成保存在版本化的 editorOverrides.incompleteComposition 中，不能写入现有已确认 paymentResolution/repaymentAllocations；postability 必须将它判为待核对。成功确认组成时同事务删除 incompleteComposition 并写入通过原领域校验的正式决定。将一个已确认分配改为未完成状态，也必须显式撤销原有效分配并保持入账阻断，不能让旧分配继续进入 posting。

页面只显示一个主保存按钮：可形成完整结果时“保存核对”，合法未完成时“保存草稿”；提交后由服务端判定余下待办。真实 invalid 错误在字段旁显示，底部不同时出现与按钮相矛盾的泛化提示。旧专用关系按钮仍使用专用验证，不显示普通字段的“请先完成当前确认”。

### 7.5 单笔与关系组的边界

单笔字段命令默认 scope=event，不能因为某字段原来共享问题而覆盖整组。修改同组第二笔的金额/分类/对方必须只有第二笔改变；组数量、待办和 memberVersion 合理更新。

判重、拆分、历史对应涉及多个对象，仍由现有专用命令承担。界面明确“本操作涉及 N 笔/这些来源”。保存普通交易草稿不能顺便合并；改金额可能使已有候选失效，但不能自动决定不同笔并抹去审计。

组字段批量修改保留独立显式入口，只能批量应用用户确认过的兼容字段；金额/时间/备注不默认批量，分类或账户需展示完整应用范围。关系候选不是被编辑成员。

## 8. 持久化、重算与历史兼容

继续使用 EconomicEvent、field_sources_json、manual_field_mask、FinanceAction 和已有关系表。金额/时间/分类复用现行列和字段位，不重编号已持久化位值；币种仍固定 CNY。

交易对方/备注和来源修正的有效值放入 fieldSources 中版本化的 `editorOverrides`，新增明确人工位（追加而非复用旧位）。`editorOverrides` 只接受服务端白名单对象，不是自由业务存储。保留原始行不变，通过单一读取函数按“字段是否存在”选择有效值，避免空字符串回退原文。

这一改动必须同时覆盖：公共事件投影/完整详情、卡片摘要和搜索、正式入账 note 构建、重新整理人工决定保留、重复合并及拆分原始快照、导出恢复。不能只做到页面看见新备注，入账仍使用旧原文。

现有正式交易没有独立的交易对方列，不能只为这个编辑器偷偷增加未迁移列。当前阶段在事件中保存独立的人工对方/备注，正式入账由唯一的 noteForEvent 适配函数组合有效商品说明、有效对方和有效备注；清空对方只移除对方片段，清空备注只移除备注片段，商品原说明不因此消失。原始凭据仍显示完整原值。未来若正式账本引入独立对方字段，必须作为明确的账本数据变更迁移，不能由本次页面字段名推断已支持。

重新整理：保留稳定 event/evidence/source identity，在现有人工覆盖优先规则内重放。合法手动性质、两端、分类、文本和合法关系不能被解析建议覆盖；若新证据使原人工决定失效，保留原决定并给出冲突，不悄悄重置。已入账、已排除和正式计划仍按既有生命周期保护。

合并/拆分：有效人工字段有来源及动作记录；合并冲突必须裁决，不能取第一个覆盖全部。拆分继续使用 mergeOrigins 等既有快照，当前主记录的人工字段保留，其他记录恢复本来的有效字段；新增 overrides 同样纳入快照。既有身份重复禁拆及贷款/退款保护不变。

本期预计不需要新增数据表；实现时确认 fieldSources 与人工位是否足够。若新增正式持久字段或表，必须同步 forward-only 迁移、权限、导出恢复和基线验证，不得运行时自动建表。不能以“不想迁移”为理由丢失人工值。

### 9.1 前端

保留原生小程序和当前 Page 显式绑定，不使用运行时 enhance/方法覆盖链。

| 边界 | 负责 | 不负责 |
| --- | --- | --- |
| 一个 review-editor-model | 从完整快照初始化草稿，模式转换，适用区域、差异、轻量验证、显示值 | 不调用 wx、不取目录、不写服务器，不依赖 issueType 决定普通字段 |
| 一个 review-editor-controller | 当前 eventId 的加载、候选/目录会话、调用模型、保存及恢复 | 不重复定义付款端/负债类型/退款会计规则 |
| 固定业务区域 | basic、funds、composition、refund、loan/source、evidence 的控件和事件 | 不直接发业务写入，不持有第二份交易草稿 |
| review-detail / review-edit 兼容入口 | 在迁移期间传 eventId、mode、focus 到同一 controller | 不保留两套字段白名单/方向/保存实现 |
| group-review 关系操作 | 判重、历史对应、源冲突的完整范围和原命令 | 不决定普通交易表单，不拷贝单笔字段保存 |

区域只有真实重复和独立状态边界时才提成组件；简单字段行用 template 即可。不是“一个字段一个文件”，也不是再写千行万能组件。账户区域只有一份纵向模板，source/destination 为一组有序描述；不复制 destinationFirst 两套 markup。

将现有本息费区域从 repayment-entry 的导入分支提取并复用，正式新增/已入账付款模式保留自己的生命周期和提交适配。通用控件可以共享，不共享互相矛盾的写状态。

### 9.2 后端

优先原位扩展 review/event-review 的单笔边界。从 event-decisions、repayment 提取可在调用者事务内复用的纯决定/关系步骤；这些 helper 接收 connection、uid、current/next/context，不自行开启事务，不调用外层服务或第二个 action/recalculate。

增加一个小型 editor-policy 负责能力、转换和适用字段约束；账户角色验证收敛为一个可复用入口，并被旧普通/新统一/正式入账必要位置共用。财务派生继续来自现有 posting/booking，不在前端重写另一套金额账本。

Issue 生命周期操作集中到 issue-store：明确单笔成员消除/更新和关系组保留。不得在多个新保存分支复制 SQL “把当前 event 所有 issue 都 superseded”。
