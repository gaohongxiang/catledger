## 1. 根本目标

本项目不再以“尽可能维持一个接近官方、可随时丢弃的补丁集”为目标，而采用长期受控 fork：

- `origin/main` 是产品、数据结构和部署的权威主线；
- 官方 ezBookkeeping 的 `upstream/main` 是持续供给源，不是本项目的产品主线；
- 安全修复、基础能力和有价值的上游改进经过评估后吸收；
- 不为追求与上游零差异而牺牲个人财务领域模型的正确性；
- 仍通过清晰的模块边界和少量接入点，把长期同步成本控制在可维护范围内。

## 2. 架构决策摘要

### 2.1 采用模块化单体

继续保持一个 Go 后端、一个 Vue/PWA 前端、一套用户数据库和一个部署单元，不拆分微服务。

理由：

- 确认入账必须让正式交易、账户余额、原始证据关联和批次状态处于同一数据库事务；
- 个人自托管不需要承担分布式事务、服务发现和多套部署的成本；
- 现有认证、权限、配置、数据库兼容和对象存储可以继续复用；
- 模块边界可以在单体内部实现，不需要依靠网络边界。

### 2.2 采用命名隔离的个人财务域

新增能力统一放入 `personalfinance` 代码命名空间、`pf_` 数据表前缀和独立前端 feature，避免与未来上游同名功能碰撞。

### 2.3 核心账本保持权威

现有 `Transaction`、`Account`、分类和标签继续作为实际余额、消费、收入和现金流的唯一口径。

个人财务域负责保存证据、计划和关系，不复制一套正式账本，也不把几十个来源字段塞入 `Transaction`。

### 2.4 依赖方向单向

个人财务域可以通过窄适配器调用现有账本；现有核心账本不得导入或理解个人财务域模型。

### 2.5 数据演进独立版本化

个人财务表从第一版建立迁移版本和校验记录。XORM Sync2 可以辅助全新安装，但不能成为后续重命名、回填和约束变更的唯一机制。

### 2.6 来源账户与账本账户分离

支付宝、微信等“账单属于谁”是来源身份；银行卡、信用卡、余额账户等“钱记到哪里”是账本账户。二者不能混成同一个字段。

阶段 1 即持久化来源账户档案。它为跨文件去重和账期覆盖提供稳定边界；到正式入账时，再通过默认映射和逐行覆盖选择账本账户。修改账本映射不得改变历史来源身份。

### 5.1 关系模型

### 5.2 `pf_import_file`

职责：代表当前用户上传的一份唯一文件内容。

关键字段：

- `file_id`、`uid`；
- 原文件名、文件大小、SHA-256；
- MIME/扩展名和内容存储状态；
- 对象存储中的不透明路径；
- 上传时间、内容删除时间；
- 创建 IP 仅按现有安全规则保留，不记录文件内容。

约束：

- `uid + file_sha256` 唯一；
- 文件名不是身份；
- 删除原文件内容不删除哈希、批次和原始行；
- 对象路径不得包含原始文件名、账号或卡号。

### 5.3 `pf_source_account`

职责：代表当前用户在某一外部来源中的稳定账户档案，是同来源去重和账期覆盖的作用域；它不是正式账本账户。

关键字段：

- `source_account_id`、`uid`、`source_type`；
- 稳定且不含明文敏感信息的 `source_account_key` 及 `source_account_key_version`；
- 用户可识别的脱敏名称；
- 可选默认 `ledger_account_id`；
- 来源标识发现方式、状态、创建和更新时间。

约束：

- `uid + source_type + source_account_key` 唯一；
- 文件提供可靠账户标识时，使用 `source-account-key-v1 + source_type + 规范化标识` 的长度前缀编码后再做 SHA-256；文件不提供时，由用户选择或创建持久档案，不能只凭昵称或尾号静默合并；
- 掩码账号、尾号和微信昵称只能进入脱敏展示候选，公共判别校验器禁止据此计算跨文件 key；
- 修改名称或默认账本映射不改变 `source_account_key`；
- 一个来源账户可以按原始行覆盖默认账本账户；
- 不保存完整卡号、手机号或其他不必要的账户明文。

### 5.4 `pf_import_batch`

职责：代表一次解析运行；同一文件可以显式产生多个解析批次。

关键字段：

- `batch_id`、`uid`、`file_id`、可空 `source_account_id`；
- 来源类型快照和可选账本账户候选；
- parser 名称、parserVersion、normalizationVersion；
- 解析选项摘要和显式重解析原因；
- 账期开始、结束；
- 总行数、有效数、无效数、精确重复数、身份冲突数、待确认数、已入账数；
- 状态、错误码和脱敏错误摘要；
- 创建、开始、完成和更新时间。

同一文件普通重传返回已有文件及最近批次；只有用户显式选择重新解析才新增批次。
当账单只给掩码账号、展示昵称或完全缺少来源账户证据时，批次先进入 `awaiting_source_account`，用户选择持久来源账户后才进行身份计算。

### 5.5 `pf_source_identity`

职责：代表“同一个来源账户中的一个稳定原始交易身份”，是同来源并发去重的数据库锚点。

关键字段：

- `identity_id`、`uid`、`source_account_id`；
- `identity_kind`：来源交易号、订单组合、强指纹或批次局部；
- `source_identity_key`；
- 来源语义不变量的 `source_core_digest`；
- `identity_key_version`、`core_digest_version`、`fingerprint_version`；
- 首次和最近出现时间。

约束：

- `source_identity_key` 始终非空；
- `uid + source_identity_key` 唯一；
- 不依赖可空复合唯一索引；
- 只有身份相同且来源语义不变量兼容才是精确重复；相同身份出现不兼容金额、币种或方向时必须进入冲突态；
- 来源身份不受用户后来修改账本账户映射的影响。

### 5.6 `pf_raw_import_row`

职责：保存每次解析看到的每一条原始证据，包括无效行和精确重复行。

关键字段：

- `row_id`、`uid`、`batch_id`、原始行号；
- 可选 `identity_id`；
- 来源交易号、订单号、商户单号；
- 原始时间、金额、方向、状态、商户、商品、支付方式；
- 标准化 Unix 秒、UTC offset 分钟、非负金额、币种、方向、来源交易类型、经济效果和账户候选；
- 本行观察到的来源 identity key/core digest，身份冲突时也不丢失候选证据；
- 版本化有序原始字段 JSON 与受限问题数组 JSON；
- parser、normalization、identity key、core digest、fingerprint、raw snapshot 六类版本；
- 解析状态、中心语义资格、去重状态、最终处置、入账状态和主问题码；
- 创建时间。

约束：

- `uid + batch_id + row_number` 唯一；
- 原始快照写入后不可覆盖；
- 无效行使用 `identity_state=not_evaluated`，不伪造来源身份；
- 服务层限制单行和整批快照大小；
- 快照和完整标识不得写入普通日志。

### 5.7 `pf_import_posting`

职责：持久化一次确认入账命令、幂等结果和审计信息。

关键字段：

- `posting_id`、`uid`、`batch_id`；
- 客户端幂等键摘要、摘要版本及请求内容摘要/版本；原始幂等键不持久化；
- 状态、选中行数、创建交易数、复用交易数；
- 开始、完成、失败时间和错误码。

约束：

- `uid + idempotency_key_digest` 唯一；
- 同一个键但请求摘要不同必须拒绝；
- `ClientSessionId` 可继续防双击，但不能替代该表。

### 5.8 `pf_raw_row_transaction_link`

职责：建立原始证据与正式交易之间的多对多关系。

关键字段：

- `link_id`、`uid`、`row_id`、`transaction_id`；
- 关系角色和创建方式；
- 创建该关系的 posting、规则版本和时间；
- 创建正式交易时的 `updated_unix_time` 快照，用于安全撤销判断。

约束：

- `uid + row_id + transaction_id + relation_role` 唯一；
- 所有读取和写入同时限定 `uid`；
- 不依赖数据库级跨分片外键，服务层必须验证双方归属。

## 6. ID 策略

现有内部 UUID 类型字段只有 4 bit，类型总数上限为 16。个人财务域不能为每张表长期消耗一个 UUID 类型。

阶段 1 采用一个共享的 `UUID_TYPE_PERSONAL_FINANCE`，所有 PF 实体共用；实体类型由表本身区分。增加新 UUID 类型前必须检查剩余容量。

这比每表占一个类型更适合后续对账、贷款和总览扩展。

## 7. 证据解析器契约

不修改所有旧解析器共同实现的 `TransactionDataImporter` 接口。新增只由首批来源实现的证据解析契约：

```go
type ImportEvidenceParser interface {
    Descriptor() ParserDescriptor
    Probe(ctx context.Context, file EvidenceFile) ProbeResult
    Parse(ctx context.Context, file EvidenceFile, opts ResolvedParseOptions) (*EvidenceDocument, error)
}

type EvidenceDocument struct {
    Metadata DocumentMetadata
    Rows     []EvidenceRow
    Issues   []EvidenceIssue
}

type EvidenceRow struct {
    RowNumber            int64
    Locator              SourceLocator
    RawFields            []RawField // 有序，允许重复列名
    Raw                   CanonicalRawEvidence
    Identifiers          SourceIdentifiers
    Normalized           NormalizedEvidence
    FingerprintMaterials StrongFingerprintMaterials
    ParseStatus          ParseState
    Issues               []EvidenceIssue
}
```

要求：

- 使用标准库 `context.Context`；解析器是纯转换组件，不依赖 User、账本映射、数据库或对象存储；
- 文件服务在字符转码或解包前对原始上传字节计算哈希；解析器接收同一份不可变内容；
- CSV 返回物理行定位，XLSX 返回 sheet 与行定位；返回每一逻辑行而不仅是有效交易；
- `row_number` 是跨 sheet 的全局逻辑序号，CSV/XLSX 物理行号从 1 开始，`sheet_index` 从 0 开始；
- `RawFields` 保留解码后、trim 前的完整有序单元格；`CanonicalRawEvidence` 同时把原始时间、金额、方向、状态、类型、对手方、商品、支付方式和备注投影到固定字段，缺失项用空字符串；
- 语义错误行也返回原始列快照、标识材料和标准化草稿；只有文件级不可读才让整次 Parse 失败；
- `ResolvedParseOptions` 在进入 parser 前已校验：币种是大写 ISO 4217 三字母代码，UTC offset 是 `-720..840` 的分钟数；不存在 nil 默认语义；
- 标准化时间是 Unix 秒，金额始终是非负最小货币单位；退款只由 `economic_effect` 表达，不能复用旧导入器的“负数支出”投影；
- `ParseStatus` 只描述结构、时间、金额等核心字段能否可靠解析；未知方向、来源类型或状态语义仍是 `valid`，由中心规则降为 `review_required`；closed/failed 为 `valid + non_postable`，核心可靠的 refund 可入账；
- parser 不返回 `semantic_eligibility`。中心必须调用 `ValidateEvidenceDocument` 绑定 descriptor、文档来源、来源问题码命名空间和连续逻辑行；该入口再逐行校验定位、快照大小和字段上限，并用 `ResolveSemanticEligibility` 推导资格。最终 `disposition` 和 `processing_state` 再结合去重结果生成；
- 错误使用稳定错误码，原始值不进入日志；公共码由中心维护，来源专属码必须使用 `alipay_` 或 `wechat_` 前缀及小写 ASCII/数字/下划线，两个解析器不得为增加来源码争改公共枚举；
- 上层必须用 descriptor-aware 的 `ProbeResult.Validate` 校验探测结果，并用 `NormalizeEvidenceParseError` 把文件级失败归一为稳定安全码；禁止直接记录 parser 返回的 `err.Error()`，未知错误统一收敛为通用文件格式错误；
- parser 只拥有 parser/normalization 两类版本；中心包唯一拥有 source-account-key、identity-key、core-digest、fingerprint、raw-snapshot 版本，并在批次/账户/原始行中注入相应快照，解析器不得覆盖；
- 解析器只返回稳定编号候选、标准化证据和强指纹材料；身份优先级、`identity_kind`、key/core 编码与 SHA-256 全部由中心 identity 包负责；
- 支付宝、微信旧导入入口与新入口共享底层提取和标准化函数；
- 第一阶段只接支付宝 App/Web CSV、微信 CSV/XLSX；其他来源继续使用旧流程。

来源账户识别也遵守证据强度：稳定标识只接受完整未掩码邮箱，或含可选 `+` 的 8–15 位完整电话；更短/更长数字、尾号、连续 `xx`、星号等证据只能作为掩码展示并要求用户选择档案。稳定标识候选不得携带 parser 自填的展示名，中心必须用 `SafeSourceAccountDisplayName` 生成脱敏显示；掩码展示最多保留末四位，不能因为文本中存在星号或“尾号”就把其余明文原样保存。微信昵称只能作为二次脱敏后的显示候选，不能静默生成跨文件身份。公共 `SourceAccountCandidate.Validate`、`ComputeSourceAccountKey` 与 `SafeSourceAccountDisplayName` 共同强制该判别规则。账单中的支付方式只是账本账户候选，永远不是来源账户身份。

## 8. 同来源精确去重

### 8.1 文件级

上传字节在任何字符转码或解析之前计算 SHA-256：

```text
fileIdentity = SHA256(originalUploadBytes)
```

### 8.2 来源级

`sourceIdentityKey` 使用无歧义的版本化编码后再计算 SHA-256，不使用简单字符串拼接。

`identity-key-v1` 的所有字符串先做 NFKC、去 BOM、trim，并把空值及 `- / n/a / null / none` 哨兵归一为空；编码使用 UTF-8 字节长度前缀。key 的公共前缀固定为 `identityKeyVersion + sourceType + sourceAccountKey + identityKind`，然后按以下优先级追加材料：

1. 非空来源交易号；
2. 同时非空的订单号 + 商户订单号，单独一个不构成订单组合身份；
3. `fingerprint-v1` 强指纹；
4. 信息不足时追加 batch ID + 批次内逻辑 row number，生成批次局部身份，不跨文件自动去重。

`fingerprint-v1` 只有在规范化对手方非空，且商品或支付方式至少一项非空时才成立；摘要材料固定为：

- fingerprintVersion；
- 标准化时间；
- 最小货币单位金额；
- 币种和方向；
- `economic_effect`；
- 规范化对手方、商品、支付方式。

parser 只决定哪些来源字段可以安全放入上述材料，不能修改中心优先级或自行哈希。金额相同、时间接近不能单独形成精确身份。

来源账户档案是上述身份计算的稳定作用域。账本账户映射、显示名称或用户后续分类不参与来源身份计算。

### 8.3 身份一致性

命中相同 `sourceIdentityKey` 后还要比较来源语义不变量。每个解析器只负责把来源字段映射为中心规定的标准化语义，并明确：

- 哪些字段属于不可变核心，例如金额、币种和收支方向；
- 哪些变化是允许的证据演进，例如状态更新或补充商户文本；
- 哪些来源状态和方向映射为 `normal / refund / closed / failed / unknown` 及 `income / expense / neutral / unknown`。

中心 identity 包唯一生成版本化 `sourceCoreDigest`。v001 固定包含：非负最小货币单位金额、币种、来源方向和 `economic_effect`。`economic_effect` 只允许 `normal / refund / closed / failed / unknown`；来源原始状态先由解析器映射为该语义，原始状态文本本身不直接进入 digest。`neutral` 或任何 `unknown` 语义都必须进入人工复核，不能直接入账。标准化来源交易类型仍持久化供审计，但支付宝 App/Web 或不同导出版本可能对同一交易给出不同分类，因此不进入 `core-digest-v1`。

同一 `economic_effect` 内的状态细化、来源分类或商户文字变化允许证据演进；金额、币种、方向或 effect 改变属于核心冲突。身份相同且 core digest 相同才标记 `exact_duplicate`。若核心不兼容，当前行自己的 observed key/core digest 与标准化语义仍然保存，但标记 `identity_conflict`，禁止自动复用正式交易或确认入账，直到用户明确解决。解析器升级导致的不一致也走这一安全路径，不能用新值覆盖旧证据。

### 8.4 并发策略

应用层先计算身份，数据库唯一约束负责最终裁决：

1. 尝试插入 `pf_source_identity`；
2. 唯一冲突时读取同 uid 的既有身份；
3. 比较来源语义不变量，决定精确重复或身份冲突；
4. 当前原始行无论结果如何都写入；
5. 只有精确重复且既有身份已关联正式交易时，才复用这些交易关系；
6. 身份冲突进入人工处理，不删除、不覆盖任何原始行。

## 9. 确认入账与事务边界

### 9.1 数据库内原子操作

一次确认必须在同一个用户数据数据库事务内完成：

1. 按 uid 读取批次、posting 和选中原始行；
2. 通过条件更新认领 posting/batch；
3. 校验账户、分类、标签和交易编辑时间；
4. 对每个来源身份决定创建正式交易或复用既有交易；
5. 调用账本适配器，在当前 XORM session 中创建交易并更新余额；
6. 写入所有证据关系；
7. 更新原始行、posting 和批次统计；
8. 一次提交。

任一步失败必须整体回滚。

### 9.2 不依赖数据库专有锁

批次认领采用条件更新，而不是把正确性完全建立在 `SELECT FOR UPDATE` 上。`partially_posted` 允许同一批次分多轮确认，但同一时刻只允许一个 posting 持有批次：

```sql
UPDATE pf_import_posting
SET status = 'posting'
WHERE uid = ? AND posting_id = ? AND status = 'ready'

UPDATE pf_import_batch
SET status = 'posting'
WHERE uid = ? AND batch_id = ?
  AND status IN ('ready', 'partially_posted')
```

只有更新成功的请求继续执行。唯一索引和最终状态读取共同保证 SQLite、MySQL、PostgreSQL 下的持久幂等。

### 9.3 账本适配器

现有交易创建逻辑需要提供“在调用方已有 session 中写入”的窄入口。适配器负责：

- 生成交易和标签索引 ID；
- 复用现有账户、分类、标签和余额校验；
- 处理转账双侧交易；
- 不提交或回滚调用方事务；
- 不依赖任何 PF 模型。

个人财务服务负责编排；核心交易服务只负责账本不变量。

## 10. 对象存储一致性

对象存储与数据库无法共享事务，采用状态机和补偿，不假装存在跨资源原子提交。

推荐流程：

```text
上传临时对象
  -> 计算并验证哈希
  -> 创建/读取 pf_import_file
  -> 把对象移动或复制到不透明最终路径
  -> 标记 content_state=available
  -> 创建解析批次
```

失败处理：

- 数据库未提交：清理临时对象；
- 数据库已提交但对象落位失败：文件状态标为 missing/failed，可重试修复；
- 原文件被用户删除：标为 deleted，保留哈希、批次、行和关联；
- 周期性检查孤立临时对象和缺失对象，只记录 ID，不记录原文件名或内容。

## 11. 状态机

批次：

~~~mermaid
stateDiagram-v2
    [*] --> receiving
    receiving --> parsing
    receiving --> failed
    parsing --> awaiting_source_account: 缺少稳定来源账户
    awaiting_source_account --> ready: 用户选择来源账户并完成身份计算
    awaiting_source_account --> discarded
    parsing --> ready
    parsing --> failed
    ready --> posting
    ready --> discarded
    posting --> completed: 无待处理有效行
    posting --> partially_posted: 仍有待处理有效行
    posting --> failed
    partially_posted --> posting: 下一轮确认
~~~

posting 完成后仍有待确认行时，批次进入 `partially_posted`；全部有效行已关联或被明确忽略后才进入 `completed`。

原始行采用正交状态，避免一个巨大枚举：

- 解析 `parse_state`：`valid / invalid`；
- 身份 `identity_state`：`not_evaluated / new / exact_duplicate / identity_conflict / batch_local`；
- 中心语义 `semantic_eligibility`：`postable / review_required / non_postable`；
- 最终处置 `disposition`：`postable / review_required / non_postable`；
- 处理 `processing_state`：`pending / linked / ignored / failed`；

固定状态矩阵：无效行是 `invalid + not_evaluated + non_postable + ignored`；来源语义不可入账但 core 完整的有效行仍执行身份计算，最终为 `non_postable + ignored`；身份冲突和 batch-local 有效行一律 `review_required + pending`；已有正式交易关系的精确重复为 `non_postable + linked`，尚无关系的精确重复为 `review_required + pending`。只有仍处于 pending 的有效行会阻止批次进入 completed。

posting：

```text
ready -> posting -> completed
             |
             v
           failed
```

失败状态必须区分可安全重试与需要人工处理。

## 12. 数据库迁移策略

### 12.1 独立迁移账本

新增 `pf_schema_migration`，每个用户数据数据库实例按以下精确 schema 记录；字段均 `NOT NULL`，只有 `applied_unix_time` 可空：

| 字段 | 类型与语义 |
| --- | --- |
| `version` | `BIGINT PK`，严格从 1 连续递增 |
| `name` | `VARCHAR(128)` |
| `checksum` | `CHAR(64)`，冻结 migration 表、业务表和 raw snapshot 规则的 canonical SHA-256 |
| `application_version` / `application_commit` | `VARCHAR(64)`，本次认领者的应用信息 |
| `runner_id` | `CHAR(32)`，一次 Upgrade 调用的随机实例标识 |
| `claim_token` | `CHAR(32)`，每次首次认领或接管都重新生成的随机 fencing token |
| `first_started_unix_time` | `BIGINT`，首次尝试时间，重试不覆盖 |
| `started_unix_time` / `updated_unix_time` / `lease_expires_unix_time` | `BIGINT`，本次认领与租约时间 |
| `applied_unix_time?` | `BIGINT`，成功后写入 |
| `success` | `BOOLEAN` |
| `failure_code` | `VARCHAR(64)`，空字符串表示正在执行，非空表示可重新认领的稳定失败码 |

迁移注册表在运行前校验版本严格从 1 连续递增、无跳号且 checksum 固定。检测到同版本 checksum 改变、数据库版本高于当前二进制或存在不能安全接管的失败迁移时拒绝升级，禁止静默修改已发布迁移。

`pf_schema_migration` 是数据库级结构元数据，不包含用户业务数据，因此不带 uid；这是“所有用户数据模型必须带 uid”的明确且唯一例外。其他所有 `pf_` 业务表必须带 uid。

MySQL 的 DDL 不承诺事务原子性，因此每个迁移必须可重入。runner 使用数据库时间认领 `success=false` 的记录，心跳、失败释放、超时接管和最终成功都必须匹配 `version + checksum + success=false + claim_token + failure_code='' + 有效租约` 并检查 `RowsAffected()==1`；接管还要匹配刚读取的旧租约、更新时间和失败码。迁移主体拆成有名称、可重入且预期短于一个租约周期的步骤；每步前完成 fenced 续租，成功后才能进入步骤，步骤后再次校验。SQLite/PostgreSQL 通过同语句数据库时钟做条件更新；MySQL 的无参 `UNIX_TIMESTAMP()` 固定在语句开始时，因此续租、失败释放和最终成功必须在短事务内先 `SELECT ... FOR UPDATE` 锁定 ledger 行，取得锁后另行读取数据库时间，再校验 token、有效租约、旧租约和更新时间并条件更新。该行锁只保护 migration ledger，不扩散到业务表。旧 runner 丢失 token 或租约后不得进入下一步，也不能再续租、标失败或标成功。heartbeat、DDL、Sync2、schema 元数据和方言目录查询都传播取消信号，heartbeat 停止过程有界且幂等。SQLite、MySQL、PostgreSQL 使用同一状态语义。

bootstrap `CREATE TABLE IF NOT EXISTS` 后先精确验证 migration 表自身。v001 执行前只接受“整张业务表不存在，或已有表列/PK 完整兼容且至多缺少预期索引”；缺列、缺 PK 的半表在 Sync2 修改前直接拒绝。未知 `pf_` 表、未知列/索引和已有字段的不兼容类型、nullable、PK、自增或索引顺序同样拒绝。冻结 bean Sync2 后再精确验证五张业务表，完全匹配才允许 `success=true`。除 XORM 元数据比较外，方言目录还必须拒绝 partial/expression/prefix 索引、无效索引、触发器、外键和生成列，防止同名唯一索引被静默弱化；MySQL 的 migration 表与所有 PF 表必须是 InnoDB。SQLite 按其可表达的类型亲和性归一化，MySQL/PostgreSQL 仍精确比较 `CHAR/VARCHAR` 长度；PostgreSQL 连接与目录校验统一固定到 `public` schema，不能受角色 `search_path` 漂移影响。

### 12.2 与 Sync2 的关系

- 上游核心表继续沿用现有 Sync2，不在本阶段重写其迁移机制；
- 实时 PF 运行模型永远不加入 `cmd/database.go` 的常驻 Sync2 列表；
- `pf_schema_migration` 只通过一段最小、三库通用且可重入的 bootstrap DDL 创建；
- v001 可在迁移包内部使用冻结的 v001 schema beans 对单个 `Database` 执行 Sync2；这些 beans 不能被运行模型替代或随模型演进修改；
- v002 起的加字段、回填、重命名和约束变化全部写成显式迁移；
- 迁移入口遍历 `UserDataStore.Count()/Get()`，每个数据库实例独立读取和推进版本；
- 不使用 JSON 查询、部分索引、数据库专有生成列等三库不一致能力；
- 三种数据库的 DDL 原子性不同，生产迁移默认 forward-only，并要求事前备份。

个人财务 repository 的全部查询和事务使用 privacy session，把 XORM `SessionShowSQLKey` 固定为 false；因此即使管理员打开全局 `log_query`，原始快照、完整标识及其他绑定参数也不会进入 SQL 日志。普通核心查询日志行为保持不变。

为保持上游接触面最小，只修改三个组合点：UUID 类型表新增一个 PF 共享类型；`datastore.Database` 提供单实例 SyncStructs、schema 元数据以及可关闭的独立测试连接；核心 Sync2 全部成功后，`cmd/database.go` 调用一次 PF Upgrade。`cmd/webserver.go` 已复用数据库更新入口，无需再加第二个接触点。

### 12.3 回滚原则

- 第一阶段只新增表和索引，不修改或删除上游核心列；
- 应用版本回滚后，旧版本忽略 PF 表；
- 已写入的正式交易仍属于正式账本，不能靠删 PF 表撤销；
- 数据迁移回滚以恢复备份为主，不承诺所有 DDL 自动逆向；
- 发布说明必须写明最低 schema version 和可回滚边界。

## 14. 安全撤销边界

第一阶段即保存撤销所需审计信息，但撤销实现不得物理删除证据。

正式交易只有同时满足下列条件才可由批次安全撤销：

- 确实由该 posting 自动创建；
- 创建后未被人工修改；
- 没有其他批次、人工录入、贷款计划或对账决定依赖；
- 相关账户仍允许在该时间点修改；
- 整个影响集合能够在一个账本事务中撤销。

否则只展示影响并要求人工处理。

## 15. 上游同步治理

### 15.1 Remote 与分支职责

```text
origin/main                       产品权威、稳定、可部署
upstream/main                     官方只读参考
codex/sync-upstream-YYYYMMDD      每次上游整合
codex/<feature>                   短期功能开发
```

禁止：

- 把 `origin/main` reset 到 `upstream/main`；
- force push 产品主线；
- 让自动依赖更新或上游合并直接触发生产部署；
- 在长期共享分支上通过 rebase 改写已经发布的历史。

### 15.2 更新分级

| 上游变化 | 默认策略 |
| --- | --- |
| 安全、认证、数据损坏、数据库兼容修复 | 优先评估和同步 |
| 普通 Bug、性能和依赖升级 | 按收益和风险同步 |
| UI 大改、导入重构、与 PF 领域冲突的新功能 | 可延后、拆取或拒绝 |
| 与本产品方向相反的语义变化 | 保留自身实现并记录差异 |

### 15.3 每次同步流程

1. 获取 `origin` 和 `upstream` 最新引用；
2. 从最新 `origin/main` 创建同步分支；
3. 记录本次目标 upstream commit；
4. 合并 `upstream/main`，不直接操作产品主线；
5. 重点审查架构接入点和数据库变化；
6. 在数据库备份副本上做迁移和启动演练；
7. 运行后端、前端、三库和 PF 验收测试；
8. 通过 PR 合入 `origin/main`；
9. 创建产品版本标签并记录 upstream 基线；
10. 备份生产数据库与原文件存储后部署。

### 15.4 冲突预算

维护一份“上游接触面”清单。每新增一个对上游核心文件的修改，都必须回答：

- 能否改为新增文件？
- 能否放入适配器或注册函数？
- 是否真的需要核心知道 PF 的存在？
- 能否将通用改进贡献回上游？

若连续多次同步都在同一处产生高成本冲突，应重构边界，而不是长期重复手工解决。

### 阶段 4：可信财务总览

基于正式交易、贷款计划和导入覆盖率展示资产、负债、净资产、现金流、待还和数据缺口。未确认原始行不进入正式统计。

## 17. 持续验收矩阵

### 17.1 后端正确性

- 文件哈希重复；
- 显式重解析；
- 来源交易号重复；
- 来源账户档案选择与映射变更；
- 相同来源身份的核心字段冲突；
- 强指纹重复与不足降级；
- 同额同日独立交易；
- 无效行保存；
- 跨用户隔离；
- 并发上传和并发确认；
- 确认中途失败整体回滚；
- 转账双侧和账户余额一致；
- 原始快照大小限制；
- 日志隐私检查。

### 17.2 数据库兼容

- SQLite 为每次开发的快速验证；
- MySQL 和 PostgreSQL 至少进入 CI/发布门禁；
- 唯一约束、条件更新、事务回滚和迁移均在三库验证；
- 不以某一数据库的 NULL 唯一性、JSON 查询或锁语义作为正确性前提。

### 17.3 前端与接口

- TypeScript 类型检查；
- store 和服务单测；
- 批次状态、重复解释和错误显示；
- 大批次分页和按需原始快照；
- 以 `zh_Hans` 为个人使用的主验收语种，新增 PF 功能仍保留 `en` 国际化骨架；其他既有语言不作为阶段 1 的主动翻译范围，不删减多币种与时区基础能力；
- 构建与桌面关键流程验证。

### 17.4 上游同步门禁

- 当前上游基线记录；
- 上游接触面 diff 审查；
- PF schema 从生产版本副本升级；
- 旧版本回滚可启动；
- 数据库和对象存储备份恢复抽查；
- 正式交易数量、账户余额和证据链接一致性核对。

## 18. 明确不做

- 不拆微服务或独立账本数据库；
- 不重写现有认证、账户和交易系统；
- 不为了跟随上游而放弃 PF 正确的数据模型；
- 不完全停止关注上游安全和基础修复；
- 不修改所有旧导入器的公共接口；
- 不用金额和时间的弱条件自动删除或合并；
- 不物理删除作为去重手段；
- 不在阶段 1 混入跨来源自动合并、贷款或总览实现。
