# 招财猫记账本业务规则与验收

## 1. 正式账本

- `Transaction`、`Account` 和分类共同构成正式账本，只有完成入账的交易进入余额、现金流和统计。
- 支出、收入、转账分开建模；内部转账不计收入或消费。
- 退款关联原消费并冲减消费，不直接当作普通收入。
- 退款作为独立正式交易保存并指向原支出；累计有效退款不得超过原支出金额。原支出存在有效退款时不得改成其他类型、缩减到低于累计退款额或直接删除；退款修改、软删除后余额和统计必须同步重算。
- 借款、还款本金和利息必须分开表达，贷款能力未上线前不得伪装成普通消费。
- 账户余额只能由未删除正式交易按“流入减流出”聚合，不维护客户端余额或可漂移缓存；
- 转账是一条同时关联转出和转入账户的正式交易，任一端失败时整笔回滚；
- 余额起点和余额校正使用 `balance_adjustment`，不进入收入、支出和结余；
- 负债以负的账面余额参与净值，界面通常显示为正的待还金额；溢缴时按资产方向显示；
- 手工交易修改和删除使用版本号防止静默覆盖，删除为软删除；账户只能停用，不物理删除。
- 分类新增、改名、停用、恢复和排序使用服务端用户范围、幂等键与版本号；同一用户同一收支方向的活动分类名称不得重复，停用分类保留历史外键。

## 2. 用户隔离

- 用户身份只能由云函数从微信可信上下文取得，客户端不得指定或替换 `uid`。
- 小程序技术层可天然取得微信可信上下文，但产品层必须等用户主动点击登录后，才调用 `bootstrap` 创建或读取个人账本；未登录浏览不得产生内部用户或默认分类。头像昵称不得阻塞账本登录。
- 微信现行接口不能在登录授权后直接返回真实头像昵称；登录面板可通过 `chooseAvatar` 与 `nickname` 让用户自愿选择，两项都允许留空，首版仅保存在当前设备。服务端身份映射、数据权限和业务唯一约束只使用可信微信上下文。
- 所有用户数据查询、更新、唯一约束、对象存储路径和幂等键均包含用户身份。
- 任一用户不能通过猜测 ID、重放请求或上传相同文件读取、修改另一用户数据。

## 3. 账单与正式交易

- 原文件、原始行、规范化记录、来源身份、经济事件、整理决定和正式交易是独立实体。
- 原始证据不可被规范化结果覆盖；解析规则升级后可重新生成工作结果，但不能静默改写已入账事实。
- 来源账户映射与来源身份分离；调整账户映射不得改变历史记录的身份。
- 经济事件用于归组现实中同一次消费、收入、转账、退款或还款，可以关联一条或多条来源证据，并生成一笔或多笔正式交易；经济事件和证据本身不得改变余额或统计。
- 跨来源关联与同来源去重是两个概念：前者保留多份独立证据并归到同一事件，后者防止同一来源身份被重复处理，二者不得通过删除证据或改写来源身份互相替代。
- 跨来源共享且核验通过的稳定关联号或已冻结的官方强关系可以自动确认；只有金额、时间、对方、摘要或账户尾号等组合线索时只能生成建议，由用户确认。
- 关联完成后按业务语义入账：消费计支出，收入计收入，本人转账不计收支，退款关联并冲减原支出；同一经济事件在多个来源出现不得重复计账。
- 贷款沿用同一经济事件主流程；只有支付平台或银行卡总额时不得猜测本金、利息和费用，有贷款明细后可核验的部分自动整理，无法唯一判定的部分由用户确认。还款各组成项之和必须等于已确认的实际还款金额。

## 4. 去重与幂等

- 同来源稳定身份由 MySQL 唯一约束做最终并发裁决。
- 文件内容相同可识别为重复上传，但只复用安全的原始文件，不因此把不同物理行合并为同一交易。
- 金额相同、日期接近、文本相同都不能单独作为自动合并依据。
- 上传、解析、整理和入账请求都必须可以安全重试；网络重试不得产生重复批次或重复交易。
- 账户和手工交易写动作使用用户范围内的 UUID 幂等键；同键同请求返回首次结果，同键异请求拒绝且不改变数据。

## 5. 批量导入

- 多文件上传逐文件记录状态；单文件格式错误不能让其他文件丢失。
- 同一整理批次默认整批原子入账：全部正式交易和关系同时成功，或全部回滚。
- 核心语义冲突、账户缺失或关系不完整时必须转人工处理，客户端不能强行标记可入账。
- 原始文件保存在临时云存储中；成功入账并超过短期追溯期后删除，数据库只保留必要的摘要、定位和审计事实。

## 6. 隐私与安全

- 日志不得记录原始账单行、完整账户号、完整交易描述、文件正文或 SQL 绑定值。
- AppSecret、数据库凭据和云环境密钥只由平台密钥能力管理，不进入客户端或仓库。
- 数据导出和注销必须由当前用户重新确认；注销清理范围需覆盖数据库记录和对象存储文件。

## 7. 财务状态与情景测算

- 净值只能由正式账户的未删除正式交易聚合；资产为正、负债为负，任何导入草稿、待确认记录或未来付款承诺都不得提前改变净值。
- 可立即使用资金是正式资产余额在用户范围内按流动性规则得到的派生值，不另存一份可漂移的权威余额；账户是否计入必须可解释、可由用户确认，负债额度不得当作可用资金。
- 财务状态必须携带计算时点、账单或账户数据日期、覆盖范围和待确认项；缺失、过期或冲突数据不得按零处理，也不得输出无条件“可负担”结论。
- 未来付款承诺、贷款计划和分期计划是独立实体，不属于已发生交易；实际付款时通过幂等关系生成或关联正式交易，失败不得同时留下部分计划变更和部分正式交易。
- 安全线由用户主动设置，系统不得根据收入、资产或用户画像自行决定；情景测算默认只读，不得创建、修改或删除正式账户、交易和未来付款承诺。
- 大额支出测算至少比较立即付清、分三次支付、推迟 90 天和暂不支付；每种结果使用相同数据快照，按分单位和明确日期确定性计算，并列出来源、假设、缺失资料及未来 30/90 天是否低于安全线。
- AI 如后续接入，只能读取完成用户隔离和必要脱敏的结构化事实、确定性结果与最小证据摘要；默认不得读取原始账单全文，不得改变正式事实、替代人工确认或执行任何真实资金操作。

## 8. 最小验收

- 两个用户使用相同文件名、相同交易文本和相同金额时仍完全隔离；
- 同一账单重复上传与并发入账只产生一组正式交易；
- 两笔同额同日的独立消费不会被自动合并；
- 同一消费、转账、退款或还款出现在多个来源时，各来源证据均被保留，但只按确认后的经济事件语义入账一次；
- 只有金额、时间或文本接近的跨来源记录只产生关联建议，不会自动确认；共享稳定关联号的强关系可自动确认并能下钻到规则版本和证据；
- 贷款还款只有支付平台或银行卡记录时进入待确认；提供贷款明细后，本金、利息和费用正确拆分且合计等于实际还款金额，本金不计支出；
- 多文件中一个失败时，其余文件仍可继续整理，失败文件可独立重试；
- 整批入账任一步失败时数据库不留下部分正式交易；
- 日志、错误响应和客户端缓存中不泄露其他用户身份或原始账单内容。
- 同一用户并发创建同名活动账户时最多成功一个，不同用户允许使用相同名称；
- 支出、收入和转账正确改变账户聚合余额，转账与余额调整不进入月度收支；
- 月份和可选的具体日期筛选都使用交易本地日期；指定日期必须属于请求月份，稳定游标翻页不重复、不遗漏；
- 猜测其他用户的账户、分类或交易 ID 时，服务返回不可用结果且不泄露对象存在性。
- 未登录打开首页、明细、账本或“我的”时不调用个人业务接口；从导入、手动记账、账户、分类或个人数据入口登录后，页面留在触发位置并继续原操作。
- 未登录直接进入受保护子页面时也必须先显示统一登录面板，不得先调用个人业务接口。
- 用户未点击登录时不得完成产品登录；头像昵称选择不得阻塞登录。首页与“我的”只有在已登录且用户主动选择头像后才显示该头像，其余情况统一回退品牌 Logo；已登录但未填写昵称时显示“微信用户”。
- `bootstrap` 成功后才可标记个人账本已连接；后续账户、分类、明细或统计摘要加载失败只能标记对应数据暂未同步，不得回退成身份未连接。仅 `bootstrap` 和只读动作可对明确的网络、超时或云端瞬时错误自动重试一次，写动作不得由通用客户端层自动重放；AppID/项目上下文缺失等配置错误不得无意义重试。
- 退出登录必须清除本机登录许可、头像昵称和临时编辑状态，但不得删除或修改云端账本；退出后访问受保护功能必须重新触发登录。
- 主题选择必须与登录状态和云端账本解耦，只保存在当前设备；切换主题不得改变金额、收支口径、筛选、请求或数据，非法主题值必须回退默认暖橘主题。
- 六套主题必须共享同一语义令牌合同；收入、支出、错误和危险操作不能只靠颜色表达，切换后当前页、后续页面、导航栏和自定义底栏保持一致。
- 财务状态上线时，净值、可立即使用资金和负债必须使用正式账本同一快照计算；待确认或过期资料必须显式展示，不能被显示为零或“数据完整”。
- 未来付款与情景测算上线时，计划不得提前进入月度收支；同一输入重复测算结果必须一致，任何测算都不得产生正式交易或调用真实资金能力。
- AI 解读上线时，相同结构化输入不得改变底层确定性结果；模型失败、超时或输出异常时仍可查看计算表和来源，日志与模型输入不得包含完整账户标识或原始账单全文。
