# 文档维护约定

目标是让新人先读一份逻辑文档就能理解项目，让维护者按问题找到唯一负责该事实的文档，而不是不断增加另一套解释。

## 1. 每类事实只维护一个主位置

| 事实 | 主位置 | 其他文件怎么引用 |
| --- | --- | --- |
| 整个系统怎样运行、每步判断与失败路径 | [项目逻辑说明](招财猫记账本入账逻辑说明.md) | 用稳定章节链接，不再写第二条主流程 |
| 用户目标与范围 | [用户需求](招财猫记账本用户需求.md) | 不粘贴实现/发布流水账 |
| 必须成立的规则与验收条件 | [业务规则与验收](招财猫记账本业务规则与验收.md) | 任务引用规则编号 |
| 模块、数据、调用与依赖入口 | [架构设计](招财猫记账本架构设计.md) | 不复制整套 schema 或动作注册表 |
| 子系统特殊边界 | [专题](现行说明/README.md) | 主文档概括必要部分并链接 |
| 环境、检查和交付操作 | [开发与验证](开发与验证.md) | 其他文件只链接，不维护另一套命令 |
| 任务状态、待验收、最后交付指针 | [实施规划](招财猫记账本实施规划.md) | README 不重复“当前做到第几步” |
| 旧方案、修复过程和固定基线 | [归档](归档/README.md)、[specs](../specs/README.md)、Git 历史 | 标明历史，不作为自动执行指令 |

## 2. 修改时直接更新原章节

业务行为改变时，更新主逻辑受影响步骤；产品范围变化再改需求，规则变化再改验收，入口移动再改架构/专题。不要求每个小修都机械生成 README、requirements、design、tasks、handoff 五份文档。

小 bug 的原因和验证写在提交/既有任务记录。不要在长文顶部追加“最新逻辑覆盖下文”；同一事实的旧口径移入历史，正文只留当前说明。不要保留多段相互矛盾的“当前版本”“下一步”。

任务规格服务于某个明确变更，不是产品手册。复杂迁移或跨模块行为变更才需要完整规格；小范围修复复用现有任务与验收，不能为文档本身再造一套流程。

## 3. 内容与证据

写步骤时检查四件事：输入是什么、按什么条件判断、产生什么结果、失败或重试怎么办。重要分支标注源码/契约/测试入口；金额和关系用合成例子说明，不贴真实账单。

明确区分现有实现、产品目标、保留兼容接口、历史方案和候选方向。不能从接口名推断用户页面，从 CI 推断云端部署，从上传推断手机验收，也不能把整理文档当作修复了原缺陷。

完整参数、版本和容量上限由代码与 shared/迁移维护；说明其含义并链接权威入口，不在多份文档复制数值。历史量化证据必须保留日期、环境与精确提交。

## 4. 不丢信息的归档

本次原文保存在固定提交 `b804bfc405d3cabff5ff277732d657d3020efb47`，其也是审阅分支祖先，用户 `backup-docs` 不改动。原文入口、blob 与迁移对照见归档清单，不依赖会继续变化的 main 链接。

38 个既有 specs 子目录保留原位和原内容，新的规格导航将其视为阶段证据，不批量修改历史完成状态或假装旧方案已实现。需要读当时页内锚点及相对引用时，进入固定提交的完整目录。

保留原文件路径的短指针只用于兼容阅读入口，不重新维护第二份正文。不删除未确认价值的材料，也不把尚未实施的需求从历史记录抹掉。

## 5. 检查和验收

`npm run check:docs` 检查根入口、docs 现行文件及 specs 总导航中的本地链接、文档锚点与源码行引用；`npm run check` 同时执行它。历史 specs 正文保持原状，不按今天的章节结构重写；其旧链接上下文从固定快照阅读。

链接检查不访问外部网络，也不能证明语义正确。内容验收还要人工核对架构、每步逻辑、当前入口、失败恢复、资料保全和真实状态。脚本无新增依赖，不取代原工程检查、单元、数据库或真机验证。
