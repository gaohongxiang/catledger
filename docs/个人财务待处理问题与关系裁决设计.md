# 个人财务待处理问题与关系裁决设计

> 状态：DESIGN-1701 冻结设计；问题投影、关系裁决和统一可入账校验已由 schema v010 落地
> 当前行为：[现行说明/账单整理与入账.md](./现行说明/账单整理与入账.md)
> 基础架构：[个人财务架构设计.md](./个人财务架构设计.md)
> 来源身份：[个人财务来源记录身份与重复语义设计.md](./个人财务来源记录身份与重复语义设计.md)
> 边界：本文保存冻结设计基线；当前运行行为以现行说明和代码为准，报表语义与第一次真实入账仍按实施看板验收

## 1. 背景

当前 `needs_action` 页面以经济事件为列表主体，再由前端按展示字段临时折叠“相似记录”。这能减少部分视觉重复，但不能完整表达用户真正需要回答的问题：

- 多笔独立事件需要同一个答案，例如连续多日同类收益都需要确认经济性质；
- 两条来源记录可能是同一经济事件，也可能是两笔真实独立交易；
- 退款需要选择原消费，候选可能来自当前更新、历史更新或已经存在的正式交易；
- 转账、还款和借款需要确认双方账户；
- 一笔事件可能同时存在账户、性质和关系问题。

“展示相似”不等于“同一交易”。把所有情况都压成事件卡片并逐笔编辑，会产生重复劳动，也可能让尚未解决关系歧义的事件被误标为可入账。

## 2. 设计目标

1. **待处理页展示问题，而不是重复展示流水**：一张卡片对应一个用户决定。
2. **批量回答不等于合并交易**：多笔独立事件可以一次应用同一答案，但仍保留独立身份、日期、金额和证据。
3. **同一事件必须显式裁决**：疑似同一交易提供“同一笔、两笔独立、证据无效、关联已有交易”等动作。
4. **退款必须建立可验证关系**：退款没有原交易关系或明确的外部原交易决定时，不得进入可入账状态。
5. **`ready` 由服务端派生**：客户端提交事实和决定，不能直接把事件状态改成 `ready`。
6. **保持单一正式账本**：正式 `Transaction`、`Account`、分类和标签继续是余额与现金流的唯一权威。
7. **保留审计、幂等和三库一致性**：所有决定都按 `uid` 隔离，带版本、幂等键、请求摘要和事务边界，并兼容 SQLite、MySQL、PostgreSQL。

## 3. 非目标

- 不因为金额相同、日期相近或文案相似就自动合并；
- 不在本阶段引入微服务、消息队列、第二套账本或外部 AI 强依赖；
- 不把分类缺失提升为入账阻塞项；
- 不在设计尚未验收时修改现有正式数据或执行第一次真实入账；
- 不一次解决全部商户学习、订阅识别和债务类型扩展。

## 4. 推荐的完整导入顺序

后台处理顺序调整为：

1. 上传、原文件防重、不可变留证；
2. 来源识别、解析、标准化和失败隔离；
3. 来源账户发现与来源记录身份裁决；无稳定标识时按文件内容与物理定位保留每一行；
4. 正式账户映射：自动沿用、用户选择、建议创建或账户级忽略；
5. 在完整来源记录多重集上执行跨来源一对一证据归并；
6. 经济性质、双方账户和事件关系裁决；
7. 匹配并复用已有正式交易；
8. 生活分类与其他非阻塞增强；
9. 生成分期、贷款、订阅等非阻塞建议；
10. 服务端执行可入账校验、问题生成、守恒和覆盖检查；
11. 用户只处理必要问题；
12. 默认整批原子入账，或由用户显式选择部分入账；
13. 更新总览、覆盖、证据链接、纠错和撤销能力。

用户界面仍只呈现三步：选择本轮账单、处理必要问题、确认可入账交易。解析、去重、候选生成和关系计算不作为并列向导步骤暴露。

## 5. 核心概念

| 概念 | 职责 | 是否影响余额 |
| --- | --- | --- |
| 原始证据 | 文件、批次和原始行，保持不可变 | 否 |
| 经济事件 | 系统当前认为发生的唯一经济事实 | 否 |
| 评审问题 `ReviewIssue` | 当前缺少哪个决定、涉及哪些对象、可选答案是什么 | 否 |
| 问题成员 `ReviewIssueMember` | 精确保存事件、证据、候选交易或候选关系的角色与版本快照 | 否 |
| 财务动作 `FinanceAction` | 命令幂等、执行状态和审计 | 否 |
| 事件关系 | 退款、转账、还款和债务等持久关系 | 否 |
| 正式交易 | 已确认并写入核心账本的余额效果 | 是 |

`ReviewIssue` 是稳定、可分页、可审计的待处理对象，不再由前端临时拼接。问题解决后保留决定和成员快照，供重整、纠错和追溯使用。

## 6. 问题类型

首期至少支持以下业务问题：

| 问题类型 | 典型原因 | 用户动作 |
| --- | --- | --- |
| 账户映射 | 来源付款方式没有唯一正式账户 | 沿用、选择、创建、忽略来源账户 |
| 重复语义判断 | 多笔独立事件缺少相同性质或账户决定 | 对本组全部应用同一答案 |
| 疑似同一事件 | 多来源记录存在一对一或多解候选 | 同一笔、两笔独立、证据无效、关联已有交易 |
| 退款关系 | 退款没有唯一原消费 | 选择原消费、确认部分退款、标记原交易不在账本 |
| 转账与还款 | 双方账户不完整或候选不唯一 | 选择资金转出与转入账户 |
| 来源身份冲突 | 同一稳定身份的核心字段不一致 | 选择有效证据、确认独立事件或保留待处理 |

生活分类缺失默认不进入阻塞问题；可在待入账列表中批量补充，也可以未分类入账。

## 7. 两种“分组”必须严格区分

### 7.1 相同答案的一组独立事件

例如多天发生的同类收益，每天仍是独立经济事件，只是都需要回答“这是什么性质、进入哪个账户”。

服务端使用窄范围决策签名生成问题组，签名可以包含：

- 来源类型和来源账户；
- 规范化商户或对方；
- 稳定的交易说明或业务动作；
- 资金方向、来源交易类型和经济效果；
- 当前缺失字段集合和规则版本。

日期和金额不是必须的分组字段，因为它们可能不影响本次要回答的问题。页面展示日期范围、事件数量、合计金额和抽样明细；用户可展开查看全部成员。

批量动作必须携带精确事件 ID、事件版本和更新版本，在一个事务中全部应用或全部回滚。默认只对本组生效；“以后自动处理”必须作为独立、明确、可预览的窄范围规则操作，不能随普通保存静默创建。

### 7.2 疑似同一经济事件

这类问题不能使用普通批量编辑替代。页面必须并排展示候选来源的时间、金额、币种、账户、商户、订单标识、商品或备注和证据依据，并提供明确动作：

- **确认是同一笔**：受影响的未入账投影在一个事务内重整为一个经济事件、多条证据，只产生一次正式账本效果；旧候选事件不再计入最终事件数，动作审计保存前后映射。
- **确认是两笔独立交易**：保留两个事件，并持久化负面身份决定，后续重整不得再次因相同候选规则把它们合并。
- **一条证据无效**：原始行仍保留，但明确不产生该证据对应的经济效果。
- **关联已有正式交易**：验证用户、账户、金额、币种和版本后只补证据与事件链接，不创建第二笔交易。

“同一笔”不是两个最终事件之间的普通关系；确认后应成为一个最终事件拥有多条证据。

## 8. 退款裁决

### 8.1 候选范围

退款原交易候选按以下范围搜索并排序：

1. 当前更新内尚未入账的消费事件；
2. 历史更新中的经济事件；
3. 已经通过事件链接入账的正式交易；
4. 用户手工创建、尚未关联账单证据的正式交易；
5. 用户明确确认“原交易不在当前账本”的外部历史消费。

稳定退款标识、订单号和来源退款字段优先于商户、金额和时间相似度。金额、日期或文案相似只能用于候选排序，不能单独自动确认。

### 8.2 页面信息

每个候选至少展示：

- 原消费日期、金额、币种、账户；
- 商户和商品或备注；
- 已退款金额和剩余可退金额；
- 证据来源和推荐依据；
- 是否已经入账、是否被其他事实引用。

### 8.3 正确性

- 原消费和退款分别保留为两个经济事件；
- 退款通过确认的 `refund_of` 关系冲减消费影响，不作为普通收入；
- 部分退款和多次退款累计不得超过原消费金额；
- 关系创建、累计金额裁决和事件状态推进必须在同一事务中使用版本或条件更新处理并发；
- 原交易不在账本时必须持久化明确决定，并在报表中排除普通收入；其最终统计口径在实现契约中单独冻结，不能伪造一个不存在的正式原消费。

## 9. 转账、还款和借款

这些是正式会计语义，不是分类后的附加标签：

- 内部转账需要两个不同的正式账户；
- 信用卡还款需要资产账户和信用卡负债账户；
- 借款到账需要债务账户和资产账户；
- 偿还本金需要资产账户和债务账户；
- 利息和费用作为支出单独表达；
- 双方账户、币种或关系仍有歧义时，事件保持待处理。

分期合同或贷款计划发现属于非阻塞建议；它们不得阻止已经具备正式会计语义的普通交易入账，也不得重复创建原消费。

## 10. 服务端派生 `ready`

客户端只提交用户确认的字段和关系决定，不提交最终 `ready` 状态。统一的 `EvaluatePostability` 必须被以下路径共同调用：

- 自动规划；
- 批量问题处理；
- 单事件纠错；
- 关系裁决；
- 正式入账；
- 重建与一致性检查。

最低校验规则：

| 经济性质 | 可入账必要条件 |
| --- | --- |
| 普通收入、消费、费用 | 时间、非负金额、币种、正式账户 |
| 内部转账 | 两个不同账户及兼容币种 |
| 信用卡还款 | 资产账户和信用卡负债账户 |
| 借款到账 | 债务账户和资产账户 |
| 偿还本金 | 资产账户和债务账户 |
| 退款 | 已确认原消费关系或明确外部原交易决定，且累计金额合法 |
| 余额调整 | 账户、调整值和明确的核心账本映射 |

事件只有在语义校验通过且不存在开放的阻塞问题时才能成为 `ready`。关系歧义不能通过普通字段编辑或客户端设置状态绕过。

## 11. 问题依赖和计数

一笔事件可以同时涉及多个原因，但页面不应重复制造多张互相冲突的卡片。服务端按依赖顺序生成可操作问题：

1. 来源账户和证据身份；
2. 是否同一经济事件；
3. 经济性质与退款、转账、还款关系；
4. 非阻塞分类与增强建议。

下游问题可以在上游问题未解决时暂时隐藏或标记等待依赖。摘要同时展示：

- 开放的阻塞问题组数；
- 受影响的独立事件数；
- 可入账事件数；
- 已入账和已排除事件数。

问题组数不参与事件守恒公式；事件守恒仍为：

`有效证据数 = 最终事件数 + 已确认附加证据数`

`最终事件数 = 已入账 + 待入账 + 待处理 + 明确不入账`

## 12. API 与动作边界

仍使用资源化 `updates / events / actions` 体系，但新增明确的领域动作，候选名称如下：

- `resolve_issue_fields`：对问题成员批量应用性质、账户或分类；
- `confirm_same_event`：确认候选属于同一经济事件；
- `confirm_distinct_events`：确认候选是独立事件；
- `discard_evidence`：保留原始证据但不产生经济效果；
- `link_existing_transaction`：关联已有正式交易；
- `link_refund` / `unlink_refund`：建立或解除退款关系；
- `resolve_transfer_accounts`：确认转账、还款或借款双方账户。

所有写请求必须包含：

- `uid` 和目标更新；
- 问题 ID、问题版本；
- 精确成员 ID 及成员版本；
- 预期更新版本；
- 幂等键和请求摘要。

动作在单个用户隐私事务中执行。任何成员变化、版本冲突、候选过期或业务不变量失败都整体回滚，并返回新的问题快照；不得部分成功后让页面自行猜测结果。

## 13. 数据模型

schema v010 已新增两类工作流投影；具体表名、索引和迁移 checksum 以迁移代码与实施规划为准：

### 13.1 `ReviewIssue`

保存：

- `uid`、更新 ID、问题 ID、稳定问题 key 和规则版本；
- 问题类型、状态、版本、阻塞级别和依赖；
- 问题摘要、候选数量和成员数量；
- 已确认动作 ID、创建和更新时间。

状态至少包括 `open / resolved / superseded`。同一稳定问题 key 由数据库唯一约束作并发最终裁决。

### 13.2 `ReviewIssueMember`

保存：

- 问题成员角色；
- 事件、证据、候选关系或正式交易 ID；
- 对应对象版本快照；
- 排序、推荐分数和安全原因码。

成员只保存安全标识和稳定代码，不把原始敏感交易正文复制到问题表。完整内容按需从隐私仓储读取。

`FinanceAction` 继续承担命令生命周期和幂等审计；`EconomicEventRelation` 继续承担已确认的退款、转账、还款和债务关系。是否需要额外持久化可复用用户规则，作为后续独立设计，不与首期问题工作台绑定。

## 14. 正式账本与报表语义

核心 `Transaction` 继续决定余额效果，但财务总览不能只按核心交易类型猜测经济性质。实现阶段应提供只读语义投影，将事件与关系映射为：

- 收入；
- 生活消费；
- 退款冲减；
- 内部转账；
- 借款到账；
- 偿还本金；
- 利息和费用；
- 余额调整。

优先使用已确认的事件、关系和贷款实际分配；没有个人财务链接的历史手工交易才退回核心交易类型。退款不得增加普通收入，借款到账不得增加收入，偿还本金不得增加消费。

## 15. 迁移与重建

- 正式交易、原始文件、原始行、来源身份、账户映射和已经确认的人工事实必须保留；
- 当前未入账事件和临时问题投影可以在一致备份后重建；
- 已经入账或被外部事实引用的事件不得静默重写；
- 新增表、唯一约束、条件更新和事务语义必须通过连续 forward-only 迁移，并在 SQLite、MySQL、PostgreSQL 验证；
- 正式切换前使用生产副本演练问题重建、批量决定、退款关系、原子入账、幂等重放、重启、总览和撤销；
- 当前正式批次尚未执行第一次真实入账，在本设计的阻塞项完成前保持不入账。

## 16. 页面结构

“必须处理”页按问题类型筛选，而不是只按事件状态平铺：

- 全部；
- 账户待确认；
- 性质待确认；
- 疑似同一交易；
- 退款关系；
- 转账与还款；
- 身份或字段冲突。

卡片文案必须明确区分：

- **多笔需要相同判断**：批量应用答案，不合并事件；
- **多笔疑似同一交易**：需要裁决事件身份。

批量卡片显示成员数量、日期范围、合计金额、来源和影响范围；关系卡片采用对比视图和候选选择器。所有动作提交前展示精确影响数量，执行后由后端返回新的事件、问题和守恒摘要。

## 17. 最小验收矩阵

| 场景 | 必须结果 |
| --- | --- |
| 连续多日同类收益 | 多个独立事件、一个问题组，一次决定全部解决 |
| 支付渠道与信用卡证明同一消费 | 一个事件、多条证据、一次账本效果 |
| 同一文件不同物理行内容完全相同 | 默认保留多个来源记录和多个事件 |
| 同日同额真实消费两次 | 保留两个事件 |
| 用户确认两笔独立 | 后续重整不再次自动合并 |
| 用户确认一条证据无效 | 原始证据保留，但不产生重复经济效果 |
| 账单匹配已有手工交易 | 只补证据和链接，不创建第二笔正式交易 |
| 历史月份消费在本月退款 | 可搜索并关联历史原消费 |
| 一笔消费多次部分退款 | 累计不超过原金额，并发只保留一个合法结果 |
| 退款关系未解决 | 事件保持待处理，无法被普通编辑伪装成 `ready` |
| 转账或还款缺对方账户 | 事件保持待处理 |
| 分类未知 | 正常进入待入账，不阻塞 |
| 批量动作重放 | 返回同一结果，不重复应用 |
| 任一成员版本冲突 | 整个批量动作回滚，计数仍守恒 |
| 退款进入总览 | 冲减消费，不增加普通收入 |
| 借款到账和偿还本金 | 不计收入和生活消费 |

## 18. 实施拆分

当前按以下依赖收口：

1. **PFV2-1702：问题投影与统一可入账校验**——新增问题仓储、服务端派生状态和一致性检查；
2. **PFV2-1703：事件身份、已有交易和退款裁决**——实现同一笔/独立/无效证据/已有交易及历史退款候选；
3. **UX-1704：问题工作台与批量决定**——替换前端临时相似分组，增加问题类型筛选、对比和候选选择；
4. **DASH-1705：账本语义投影与报表校准**——确保退款、借款、还款和余额调整口径正确；
5. **PFV2-1706：生产副本集成与第一次真实入账验收**——三库、正式副本、幂等、重启、总览和撤销门禁。

PFV2-1702、PFV2-1703 和 UX-1704 已进入主线并发布，等待正式更新重整后的真实数据验收；DASH-1705 与 PFV2-1706 尚未收口。具体状态以实施规划看板为准。

## 19. 冻结结论

1. 待处理页从事件列表升级为服务端问题列表；
2. 多笔相同答案支持原子批量处理，但不改变事件身份；
3. 疑似同一事件必须提供同一笔、独立、无效证据和已有交易四类显式裁决；
4. 退款搜索跨当前更新、历史事件和正式交易，并要求持久关系或明确外部原交易决定；
5. 客户端不能直接设置 `ready`，由统一服务端校验派生；
6. 第一阶段新增稳定问题投影，表结构由 schema v010 的连续迁移冻结；
7. 来源身份遵循 DESIGN-1802：内容相同不等于同一记录，跨来源匹配保持多重集数量；
8. 第一次真实入账继续暂停，直到来源身份、关系裁决和报表语义通过验收。
