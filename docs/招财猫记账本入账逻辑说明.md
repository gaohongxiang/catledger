<a id="overview"></a>
## 1. 项目全貌：先整理事实，再影响账本

CatLedger 是微信原生小程序。主要用途是把银行、支付宝、微信支付账单整理为可追溯的个人账本，也支持手工记账、账户与分类、统计、贷款与信用卡分期。它记录资金活动，不执行真实付款、转账或借款。

```text
用户：导入账单 / 手工记账 / 管理已有账目
                     ↓
微信小程序：展示、输入、文件选择、分页、请求恢复
         ├─ catledger-api：身份、账户、分类、交易、统计、贷款、导出
         └─ catledger-import：上传意图、解析、整理、核对、整批入账
                     ↓
CloudBase MySQL：正式账本、来源、决定、关系、版本与回执
CloudBase 私有云存储：待解析、短期追溯的文件原件
```

系统没有运行中的 AI 决策主链。当前判断来自确定性代码、来源模板、已经确认的映射以及用户选择。Jev 等模型尚未接入；未来讨论不构成现有功能或本次文档任务的实施范围。

**最重要的分界：上传成功、解析成功、整理完成，都不等于已经记账。只有有效正式交易改变余额和收支。** 贷款计划、分期进度、原始文件和导入候选不是另一份权威余额。

实现入口：[API 动作](../cloudfunctions/catledger-api/src/action-registry.js)、[导入动作](../cloudfunctions/catledger-import/src/action-registry.js)、[客户端路由](../miniprogram/app.json)。

<a id="objects"></a>
## 2. 先区分七种对象

| 对象 | 回答什么问题 | 是否直接影响余额 |
| --- | --- | --- |
| 来源文件与解析批次 | 用户提供了哪份资料，按哪个版本解析 | 否 |
| 原始行与来源身份 | 原文是什么，这条证据是否已经出现 | 否 |
| `FinanceUpdate` 导入批次 | 这次准备把哪些资料一起整理和入账 | 否 |
| `EconomicEvent` 经济事件 | 多份证据可能描述了哪一次资金活动 | 否 |
| `ReviewIssue` 与人工决定 | 哪些事实仍不明确，用户确认了什么 | 否 |
| `Transaction` 正式交易 | 哪个账户在何时发生了多少资金变化 | 是 |
| 贷款资料、期次、来源关联 | 本金依据、计划成本、实际还款和完成进度如何对应 | 不单独计入；实际资金变化仍由交易表达 |

同一经济事件可以有多条证据，也可以生成多笔正式交易。例如一笔明确的还款，可拆成本金转账及尚未计入的利息、费用支出。不能把“行数”“事件数”“正式交易数”当成同一个数量。

### 2.1 金额与账户

金额使用整数分，接口使用十进制字符串；不拿浮点小数反复相加。资产、负债都通过正式交易端点表达流入和流出。余额调整是独立类型，不伪装成收入或支出。

| 资金活动 | 账本含义 | 收支口径 |
| --- | --- | --- |
| 普通消费 | 付款资产减少，或信用账户欠款增加 | 支出 |
| 普通收入 | 收款账户增加 | 收入 |
| 本人账户转账 | 一个账户流出，另一个流入 | 不重复计收支 |
| 已关联退款 | 收款账户增加，关联原支出 | 冲减支出，分类随原支出 |
| 待关联退款 | 先保留实际到账，原消费关系尚待确认 | 关系补齐前不冒充普通收入或已确认的支出冲减 |
| 借款到账 / 归还本金 | 资产与负债之间的资金变化 | 本金不作为普通收入或消费 |
| 利息、手续费 | 按实际经济效果入账；已经计过的不能再记 | 未入账费用计支出 |
| 创建分期或修改完成期数 | 管理资料或进度变化 | 不生成虚构资金流水 |

现金账户受到“不产生或加深负余额”的约束。信用额度是资料，不是资产；贷款本金明细不能再叠加到同一负债账户余额上。

### 2.2 三种容易混淆的“账户”

账单主体回答“文件属于谁”；支付工具引用回答“这一行使用什么工具”；账本账户才回答“余额归谁”。一份支付宝账单可以同时使用余额、银行卡和消费信贷，不能整份绑定一个钱包。字段 `source_account_id` 中的 source 表示转出端，不表示文件来自哪个平台。

实现入口：[正式交易领域](../cloudfunctions/catledger-api/src/transaction-service.js)、[整理模型](../cloudfunctions/catledger-import/src/organizer-model.js)、[资金账户引用](../cloudfunctions/catledger-import/src/payment-account.js)。

<a id="identity"></a>
## 3. 用户入口与身份

当前底部常驻入口是首页、明细、统计、我的；中央记账按钮打开“账单导入 / 记一笔”选择。账户、分类、贷款等使用各自页面。旧文档把“账本”列为底部入口的描述不再作为现行导航。

启动和受保护操作通过既有登录流程识别用户。身份或授权未确认时，不展示其他会话的个人数据；需要登录的动作在用户完成后继续，取消则不执行写入。账号昵称从服务端读取，头像不是身份凭证。

云函数从可信微信上下文解析用户；客户端传来的账户、交易、批次、贷款 ID 都要在该用户范围内查验。跨用户对象不能因为猜中 ID 被读取或操作。本机登录状态只控制页面流程，不能替代服务端授权。

实现入口：[中央记账与导航](../miniprogram/custom-tab-bar/index.js)、[登录保护](../miniprogram/services/login-guard.js)、[API handler](../cloudfunctions/catledger-api/src/handler.js)、[导入 handler](../cloudfunctions/catledger-import/src/handler.js)。

<a id="import"></a>
## 4. 导入全过程

页面分为“选择文件 → 确认账户 → 核对交易 → 确认入账”。后台还包含解析、来源身份判断、关系建立与事务写入；四个页面步骤不等于只有四次判断。

```text
选文件 → 私有上传 → 逐文件解析 → 标准语义与来源身份
                                      ↓
                          创建 / 更新 FinanceUpdate
                                      ↓
                账户归属 → 事件与关系 → 待核对问题
                                      ↓
                     保存用户决定，重算受影响结果
                                      ↓
              核对所选范围 → 锁内复查 → 整批原子入账
                                      ↓
                完成回执 → 独立刷新明细 → 来源追溯
```

<a id="import-files"></a>
### 4.1 选择、上传和单文件失败隔离

**输入：** 用户选中的文件及文件元数据。客户端先检查支持格式、大小、数量和本次重复选择；服务端再验证上传意图与所属用户。限制以现有契约为准，不能只依赖页面检查。

`imports.prepareMany` 为文件准备服务端认可的上传信息；原件进入用户隔离的私有对象路径，再由 `imports.parseFile` 触发解析。文件路径和名称本身不是授权凭证。

同路径、同内容或已有解析结果需要按现有摘要与解析版本判断是否复用。复用的是证据，不是无条件复用上一次正式入账结果。规则版本变化可以追加解析批次，不能覆盖原始证据。

**结果：** 每份文件有自己的进度、解析结果或错误。单份失败不清空其他成功文件；重试该文件，不从头重复上传所有文件。放弃某文件与放弃整个导入批次是不同操作。

实现入口：[upload-flow](../miniprogram/pages/import-workbench/upload-flow.js)、[导入服务](../cloudfunctions/catledger-import/src/import-service.js)；保护测试：[上传行为](../test/import-upload-flow.test.js)。

<a id="import-parse"></a>
### 4.2 解析与列映射：先知道字段是什么

**输入：** 原始字节、文件格式、来源模板，以及需要时由用户确认的银行列映射。

解析器识别容器、工作表、表头与数据行。支付宝、微信和银行分别适用经过测试的模板；同时命中多个完整模板或多个账单工作表时不能随意选一个。通用银行表格在含义不明确时先要求确认列，不能靠金额外观猜借贷方向。

日期、金额、方向、状态、交易类型、对方、商品、支付方式、交易号等投影为统一字段，同时保留原始列名、位置和内容。空值、零、缺列、`/`、重复列、额外列不能被混成一种“没有信息”。文本含“合计”不代表整行应删除，结构判断优先。

银行金额可能是“带符号单列”“金额加方向”“收入/支出分列”。符号含义不明、两列冲突、无效日期或不支持币种必须留下诊断。不能丢掉异常行来凑出漂亮的成功率。

**结果：** 规范化行、原文定位、字段观测、文件控制结果以及解析/语义版本。文件总笔数、收支控制项与行级解释分别保留。

实现入口：[解析器目录](../cloudfunctions/catledger-import/src/parsers)、[来源 profiles](../cloudfunctions/catledger-import/src/profiles)；详细边界见[语义与验证](现行说明/账单语义与工程验证.md)。

<a id="import-semantics"></a>
### 4.3 语义解释：这条记录究竟产生什么经济效果

**输入：** 规范化行、来源 profile 和原始语义证据。Row Semantic Resolver 先解释动作、状态、资金效果、账户引用及冲突；后面的通用事件层消费标准结果，不再次遍历平台文字猜含义。

| 条件 | 处理原则 |
| --- | --- |
| 动作、状态和方向相互支持 | 产生相应资金语义，再检查账户与关系 |
| 明确失败、关闭或非资金授权等 | 保留来源证据，不伪造成功扣款 |
| 退款到账 | 进入退款关系判断，不简单记成收入 |
| 本人转账、借款、还款 | 分清两端及本金/费用，不按页面上的“收入/支出”字样直接记消费 |
| 未知动作、矛盾状态或多账户缺少金额组成 | 保留未知/冲突并生成需要处理的问题 |
| 用户明确排除本次记录 | 从本次入账范围排除，但不提高来源识别率 |

**不能跳过的限制：** 填上一个账户或分类，不足以解除“资金性质未知”“多账户缺少分项”等语义阻断。系统没掌握的信息需要用户明确处理，不能通过默认值变成事实。

普通分类规则、历史分类别名可以给出分类；分类与经济性质不同。分类可以稍后补充，不意味着未知的交易性质也可以直接入账。

实现入口：[row-semantic-resolver](../cloudfunctions/catledger-import/src/row-semantic-resolver.js)、[rule-evaluator](../cloudfunctions/catledger-import/src/rule-evaluator.js)、[economic-event-builder](../cloudfunctions/catledger-import/src/economic-event-builder.js)、[category-mapping](../cloudfunctions/catledger-import/src/category-mapping.js)。

<a id="import-match"></a>
### 4.4 来源去重与交易关系：相似不等于同一笔

**输入：** 已解释的行、稳定来源身份、已有证据与正式历史交易。

同来源身份由用户范围的唯一约束兜底；相同稳定 ID 仍要核验核心字段，冲突不能静默覆盖。不同来源中，只有已核验的稳定关联证据或明确规则才能自动确认关系；同额、同日、同商户只是候选线索。银行流水号也要放在正确账户范围内，不能与平台订单号碰巧相同就合并。

| 关系 | 系统可以确定什么 | 需要用户确认什么 |
| --- | --- | --- |
| 同一笔的多份来源 | 强证据支持时保留多来源、避免重复记账 | 弱匹配时确认同笔或不同笔；同额独立交易应保留 |
| 本批退款与原消费 | 强且唯一的订单/退款证据支持原消费 | 弱候选必须人工核对；不能列任意近期消费让用户猜 |
| 与已入账历史可能重复 | 生成有证据的历史候选，并显示原记录 | 明确是同笔、不同笔，或暂不处理 |
| 没有可确认原消费的退款 | 可以保留待关联关系及真实到账 | 以后从明细补原消费，不能先伪造冲减分类 |

“同笔”不删除另一份原文；“不同笔”不应再次被同一弱匹配自动吞并。已经被贷款实际付款等关系占用的交易，不能绕过整组维护挂接某个成员。

实现入口：[evidence-matching](../cloudfunctions/catledger-import/src/evidence-matching.js)、[relation-resolver](../cloudfunctions/catledger-import/src/relation-resolver.js)、[historical-duplicates](../cloudfunctions/catledger-import/src/historical-duplicates.js)、[refund-relation-policy](../cloudfunctions/catledger-import/src/refund-relation-policy.js)。

<a id="import-accounts"></a>
### 4.5 确认账户：先归属，再分配金额

**输入：** 支付工具引用、当前有效账户、历史映射、本批和事件级决定。

账户映射优先级由统一规则确定，从低到高为：**精确推断 → 历史别名 → 历史明确映射 → 本批决定 → 事件级决定**。同级最高候选冲突时需要明确处理，不能以数组最后一项为准。历史账户类型不兼容时不能继续沿用；保存时还要验证真实账户是否可用。

| 场景 | 页面与保存结果 |
| --- | --- |
| 已有可靠归属 | 复用，允许在现行流程中修订 |
| 稳定现实账户在多个来源出现 | 合组确认，但仍保存各自来源引用，不能丢来源身份 |
| 账户信息不足 | 保持待选择，不默认新建，不因同名未知项而自动合并 |
| 用户选择新账户 | 先形成账户草稿；只有最终被有效入账事件引用的草稿才物化 |
| 用户明确不计入某稳定支付工具 | 保存对应决定；本批排除与持久规则的作用范围必须区分 |
| 多付款或多收款端 | 先确认各账户，再确认受支持的逐项金额；总额必须守恒 |

合并还款名称不是一个真实账户，不能创建虚构的“花呗和信用购合并账户”掩盖分项。账户选择也不能任意改写来源金额。复杂多对多关系只按现有明确支持的模型处理，不在文档中宣称已经通用支持。

批量确认在原事务内完成，复用映射索引并统一收尾，不等于逐笔网络提交。`refreshAccountGroups` 会展开旧账户引用、处理问题与成员；无候选时不为了“刷新”制造新业务行动。

实现入口：[account-mapping-policy](../cloudfunctions/catledger-import/src/account-mapping-policy.js)、[review/account-mapping](../cloudfunctions/catledger-import/src/review/account-mapping.js)、[account-draft](../cloudfunctions/catledger-import/src/account-draft.js)、[funds-allocation](../cloudfunctions/catledger-import/src/funds-allocation.js)。

<a id="import-review"></a>
### 4.6 核对与保存决定：改变的是明确选中的事实

**输入：** 当前问题、相关事件/关系、用户选择和它们的版本。页面先保证必填选择完整，再交给服务端检查决定是否适用于该问题。

核对内容包括账户、本人或他人还款性质、资金分配、同笔/不同笔、退款关系、排除及分类。可共享决定的记录可以合组，但共享依据和成员范围必须明确；不能因同一问题标题就替整批作决定。

服务端在原幂等事务内取得锁、检查版本、应用允许的字段，并同步事件、问题成员、关系、投影、历史核对、草稿可达性和批次计数。单笔事件保存与批量保存有各自的引用校验与批量路径，不能理解成不带业务规则的普通 UPDATE。

**结果：** 保存决定、更新受影响版本、返回操作回执，随后读取新摘要。不是每次选择都重新解析原文件。旧语义计划升级保留人工字段、排除与关系决定，不把系统重算伪装成人工确认。

**失败：** 版本过期则重新读取并核对；结果丢失则用原请求号核实。客户端先持久化待发决定和幂等键，不能把网络超时解释成“肯定没保存”。

实现入口：[review-issue-service](../cloudfunctions/catledger-import/src/review-issue-service.js)、[review/policy](../cloudfunctions/catledger-import/src/review/policy.js)、[review/reconciliation](../cloudfunctions/catledger-import/src/review/reconciliation.js)、[semantic-plan-upgrade](../cloudfunctions/catledger-import/src/semantic-plan-upgrade.js)、[import-draft-session](../miniprogram/services/import-draft-session.js)。

<a id="import-ready"></a>
### 4.7 确认入账：分别看完整识别与所选范围可入账

以下两个状态回答不同问题，不能合成一个“全部成功”：

| 指标 | 含义 | 不能据此推断 |
| --- | --- | --- |
| `statementFullyRecognized` | 当前文件观测、字段和受支持控制项是否支持完整识别 | 不能仅凭行数相等就认为完整；旧文件缺当前观测不能补写为通过 |
| `selectedEventsReadyToPost` | 用户本次选择的事件是否满足入账条件 | 不代表文件每一行都被完整解释；分类待补也不等于所有问题均阻塞 |

每条来源行都应有可解释归宿：资金、非资金、重复、待确认、明确排除、无效或未分配。排除不会把未知行变成已识别行；缺证据和语义阻断不会因为页面按钮亮了而消失。

点击入账前，页面 flush 现有草稿、取得权威结果，再判断条件。正常摘要更新不取消本次合法提交；如果刷新后出现新的阻塞项，提示继续核对，不发送尚未满足条件的入账请求。

实现入口：[coverage-report](../cloudfunctions/catledger-import/src/coverage-report.js)、[organizer-model](../cloudfunctions/catledger-import/src/organizer-model.js)、[posting-flow](../miniprogram/pages/import-workbench/posting-flow.js)。

<a id="import-post"></a>
### 4.8 正式入账：一个事务决定成功或失败

**输入：** 用户、导入批次及版本、原 `requestId`，以及已持久化的事件和决定。客户端不能直接上传一份自算交易列表绕过整理结果。

下面是业务检查顺序的说明，不是允许重排 SQL 的新设计；实际锁序由现有实现维护。

1. 进入用户范围的幂等写事务，核对批次状态、规则/计划版本和请求重放。
2. 锁定并读取持久化事件及来源，检查逐行归宿、证据完整性、未决阻塞和可入账状态。
3. 在锁内复查历史重复、关系与目标交易有效性；核对期间新增的历史变化仍可能要求回到人工核对。
4. 只物化可达账户草稿，检查账户、分类、现金余额、金额分配、退款累计和贷款/分期关系。
5. 按明确经济性质生成或复用正式交易，保存事件—交易、来源、映射等关系及必要的副作用记录。
6. 保存批次结果、版本、数据修订与首次回执，一起提交；任何失败整组回滚。

消费通常一笔支出；本人转账一行连接两账户；明确还款可以多项入账。信用卡分期本金明细只作为管理来源，已确认的利息/费用按防重复规则写支出。复用历史交易与本批新建交易必须区分，供后续维护使用。

**结果：** 首次小回执先确认“已经入账”，明细和摘要另行读取。读取失败显示“已入账，明细待刷新”，不能把成功写入改显示为未提交。重复请求返回原结果，不新增第二笔。

实现入口：[finance-update-posting](../cloudfunctions/catledger-import/src/finance-update-posting.js)、[import-transaction](../cloudfunctions/catledger-import/src/import-transaction.js)、[command-result](../cloudfunctions/catledger-import/src/command-result.js)。

## 5. 手工账本、账户、分类与统计

### 5.1 账户和分类

账户保存名称、类型、币种、版本及停用状态。新增时的余额/欠款起点用独立调整表达；资产账户可按现行入口校正余额，负债不提供日常校正入口。账单日、还款日、信用额度允许未填，未填不显示假零。

分类最多两级，一级和二级都能直接记账。支持同级排序、停用、恢复；父级创建后固定。停用不删除历史账目；收入、支出分类类型必须与交易匹配。退款沿用原消费分类，不自行再分一套。

### 5.2 新建、编辑和删除手工交易

先读当前账户/分类目录，填写资金类型、金额、时间与必要端点，服务端验证用户、账户状态、分类、退款和现金约束。成功事务保存交易、版本、修订和回执；失败保留输入。修改与删除还要检查当前版本及贷款等关联限制。

新增支出、收入和本人转账不需要模型决定；规则能够确定的检查直接由代码执行。停用账户不得用于新增或编辑，但符合原删除约束的历史记录仍可删除，账户不会因此恢复。

### 5.3 查询和统计

明细按发生地本地日期支持月份/日期、账户、分类、来源、备注搜索和导入批次范围；未分类是明确筛选条件，不等于包含退款与转账的任意空分类记录。游标绑定查询及版本，改变条件后不能接着使用旧游标。

有效正式交易产生余额、收入、净支出和净值。退款按关联口径冲减支出；本人转账、本金和余额调整不重复算收支；软删除记录退出当前聚合。计划总成本属于预计值，不与已发生费用再次相加。

实现入口：[账户服务](../cloudfunctions/catledger-api/src/account-service.js)、[分类服务](../cloudfunctions/catledger-api/src/category-service.js)、[交易服务组装](../cloudfunctions/catledger-api/src/transaction-service.js)、[API 契约](../shared/catledger-api.json)。

## 6. 贷款与信用卡分期：资料、实际流水、计划分开

### 6.1 三本不同的明细

贷款资料回答基准本金和借款条件；实际借还关联真实交易及本息费；期次计划回答预计何时应还多少。已有负债账户余额是正式账本结果，不把资料本金重复叠加。

登记明确的实际还款前，必须知道总额、资产账户、贷款及本金/利息/费用构成。分项总额必须相等；已经计入负债的费用随转账清偿，未记过的费用才产生新支出。信息不足就待确认，不从总额猜本息。

关联已有账目只建立合法关系，不再付款；构成不一致需要整组更正而不是硬挂接。撤销、更正受全组版本、外部引用、退款与现金/本金约束保护，不能只删组内一笔留下半份还款。

### 6.2 当前分期使用“一笔记录、一张逐期表”

创建时保存完整方案、原本金、总期数、首期日期、还款方式、明确的利息/费用依据和可选历史进度。已有信用卡消费形成欠款时，创建管理记录不再借入一次本金。

| 后续动作 | 发生什么 | 不发生什么 |
| --- | --- | --- |
| 信用卡分期本金明细入账 | 保存分项来源，供归期和进度使用 | 不重复消费，不伪造资产账户扣款 |
| 明确利息/手续费入账 | 校验身份、期次和已有费用后写入或复用 | 不因为后来关联而再记一份费用 |
| 明确编号已有唯一绑定 | 同用户、同账户下归入对应分期 | 不跨账户、跨用户按编号裸匹配 |
| 暂无唯一归属 | 保留待建立来源，稍后新建/关联 | 不从一条账单猜完整原本金和首期日期 |
| 手动确认完成至第 N 期 | 改连续进度 | 不补造 N 笔历史付款，不自动补记利息 |
| 明确补记某期缺失费用 | 只补当前缺少且合法的费用 | 不再写本金或重复费用 |

只有已确认信用卡账单、真实信用账户及明确期号/分项才启用信用卡特例。普通银行贷款不能套用“本金消费已经记过”的假设。

### 6.3 完成进度与逾期判断

连续进度综合手动确认、有效已关联来源和既有结清记录，限制在总期数内。明确取消、未还或部分未还异常优先保留，不被后面一期的来源覆盖。

第 12 期已到、只确认至第 10 期，第 11 期没有凭据时显示“缺少账单，待补充”；只有明确未还且过了应还日才能称逾期。前面期次按连续进度变灰，不等于系统补出了原始付款凭证。预览、打开详情和时间经过本身不推进进度。

详情首次展示一批期次，使用“显示更多”向下追加。读取失败保留已有内容和重试，不把未知金额或状态当零/完成。普通旧贷款仍保留相应借还与计划维护能力，不能因分期期次读取失败误切旧界面。

### 6.4 删除分期不删除账目

删除分期是归档管理记录，并在同一事务解除来源及编号绑定。有效来源回到待建立，可重新关联；原消费、费用、还款与来源身份保留。重复执行旧删除请求不能拆掉后来新建的关系。费用来源失效时重新计算有效进度，独立手动确认和明确异常仍保留。

详见[贷款管理专题](现行说明/贷款管理.md)。实现入口：[loan-service](../cloudfunctions/catledger-api/src/loan-service.js)、[installment-service](../cloudfunctions/catledger-api/src/installment-service.js)、[installment-link](../cloudfunctions/catledger-api/src/installment-link.js)、[installment-view](../cloudfunctions/catledger-api/src/installment-view.js)。

## 7. 已入账之后：当前界面与保留的后台能力分开

### 7.1 当前用户入口

在明细中点哪笔就编辑哪笔。手工交易按现有规则编辑；导入交易的普通编辑入口主要修改分类，不在普通表单任意改来源金额/账户。支出分类修改会同步相关退款分类；不改原始账单或偷偷学习成持久映射。

手工和导入账目可以混选删除。全选覆盖当前筛选范围，而不是只选当前页；分页没读完不能谎称全部选中。删除冻结 ID、版本和请求号，服务端可分块处理，但只提交一个事务；后块冲突或关联约束失败就整组回滚，不静默跳过。

删除正式账目保留账户、来源、映射和导入历史。重复导入仍受有效来源防重约束，不能把“删了一笔账”理解成所有来源身份已被清空。待关联退款从明细补原消费时仍验证用户、方向、时间和累计金额。

### 7.2 后台更正/整批撤销不是现行页面的主入口

服务端仍保留 `economicEvents.correctionImpact/correct`、`financeUpdates.undoImpact/undo` 等能力。当前路由不注册旧 `import-maintenance` 页面，不能从接口存在推断用户现在能打开旧更正/撤销界面。

这些保留能力要求先预览影响，再在锁内重算版本和 `previewToken`。只撤销本批 created 的有效交易，不能删除 reused 的历史交易；外部退款、贷款关联、现金约束或无法证明归属的旧副作用可能阻断。预览不是授权凭证，也不是免复查通行证。

详见[维护专题](现行说明/已入账账单维护.md)；实现入口：[finance-update-maintenance](../cloudfunctions/catledger-import/src/finance-update-maintenance.js)、[客户端实际路由](../miniprogram/app.json)。

## 8. 读取、缓存与失败恢复

### 8.1 谁负责哪份状态

| 状态 | 唯一主要负责人 |
| --- | --- |
| 正式业务事实、用户隔离、对象版本 | 服务端 MySQL 与命令事务 |
| 普通查询内存缓存、请求去重、失效与写入屏障 | `read-cache` 等读取服务 |
| 最近完整展示的有限持久快照 | `read-snapshot-store`，不是离线权威账本 |
| 导入摘要版本、游标和页缓存 | `import-view-session` |
| 导入待发决定、在途请求、原 requestId、postFlight | `import-draft-session` |
| 页面是否活动、局部读取令牌、弹层、显示状态 | 显式装配的页面 runtime 与各操作流程 |

读取先尽量复用有效结果，必要时再校验版本或联网；写入使用屏障和修订使旧结果失效。内存命中不代表每次展示都没有派生与 setData 开销。不能仅因页面慢就再增加一层缓存。

导入使用摘要加分页，不把整批原始数据放在 Page.data。详情只读取当前必要证据；大原文按现有接口分段，失败可单项重试。缓存容量、响应和 SQL 分块预算分别受现有实现与测试约束。

### 8.2 读结果可以过期，已发命令不能被当作没发生

| 场景 | 正确处理 |
| --- | --- |
| 切批次、翻页、关弹层后旧读取返回 | 拒绝回填新页面 |
| 输入过程中后台摘要更新 | 延后应用，不能覆盖用户未完成输入 |
| 页面隐藏/卸载，写请求尚未发出 | 不因旧异步续体继续发起不再有效的提交 |
| 写请求已发送，随后离开 | 保留原持久请求；旧回执不回填，但可按原协议确认事实 |
| 写成功，摘要失败 | 保留成功事实，仅提示明细待刷新 |
| 请求超时、结果未知 | 核实或原键重试，不生成新 requestId 当另一笔写入 |
| 明确放弃/重新开始旧导入 | 终止首次恢复意图；不能顺手删除未确认写请求 |
| 普通隐藏后返回 | 允许正常恢复；不同于用户明确放弃 |

页面活动 `_viewEpoch` 与列表读取 `_pageEpoch` 已分离。正常摘要换版不使合法入账失效；刷新使用自己的操作令牌，旧 finally 不能清掉新操作加载态。第四步没有列表也要结束刷新状态。

实现入口：[runtime](../miniprogram/pages/import-workbench/runtime.js)、[posting-flow](../miniprogram/pages/import-workbench/posting-flow.js)、[read-cache](../miniprogram/services/read-cache.js)、[view-session](../miniprogram/services/import-view-session.js)、[draft-session](../miniprogram/services/import-draft-session.js)。回归：[异步审核](../test/import-async-review.test.js)、[首次恢复](../test/import-initial-recovery.test.js)。

## 9. 数据生命周期与规则升级

原件在私有云存储按既有保留/清理流程处理；结构化来源、来源身份、正式账目与审计关系分别保存。清理原文件不等于清理来源身份；软删除交易也不等于删除全部证据。

个人导出通过 start → page → finish 形成一致版本的 JSONL 或交易 CSV。导出期间账本改变，旧任务必须作废重做，不能交付混合快照；失败的半文件不叫完整导出。用户主动选择后才分享文件，已分享副本由用户管理。JSONL 的隔离库恢复验证不是产品已提供生产恢复按钮。

规则升级按解析器、profile、语义和计划的各自版本进行。旧未入账计划可以在保护人工决定的前提下升级；已经正式入账的事实不因换规则被偷偷改写。显式 MySQL 迁移必须可重入、向前推进，不能为回退代码删掉账本或审计列。

详见[数据生命周期](现行说明/数据生命周期.md)、[开发与验证](开发与验证.md)。版本入口：[domain-versions](../cloudfunctions/catledger-import/src/domain-versions.js)、[迁移目录](../migrations)、[导出清单](../cloudfunctions/catledger-api/src/export-manifest.json)。

## 10. 用四个例子串起来

**同一笔 100 元消费同时出现在支付宝和银行账单。** 两行先各自保留身份与原文。强关联成立或用户确认同笔后，构成一个经济事件并只产生应有的一次消费；若只是同额同日，不能直接合并。入账前还要检查是否已在历史账本出现。

**收到 30 元退款，但没有能确认的原消费。** 先识别退款而非收入；有冻结候选则供核对，没有候选可走待关联退款。真实到账与支出冲减是两个层次，不能凭空找一笔 30 元消费关联。

**信用卡分期本期本金 500 元、利息 20 元。** 在信用卡分期条件确实满足时，本金来源用于管理，不再重复记录原消费；明确的 20 元利息按防重复规则入账。后来建立分期只是关联来源，不再新增 520 元欠款；实际整单还卡仍是另一条有凭据的还款资金活动。

**确认入账时网络断开。** 客户端保留原 postFlight/requestId。下一次核实若已经成功，就展示已入账；若需重试仍用原请求。不得因为页面上没收到明细就新建第二个入账命令。

以上金额仅用于说明分支，不是任何用户真实账目。

## 11. 遇到问题先查哪一层

| 现象 | 先检查 |
| --- | --- |
| 文件不能识别 / 银行列不对 | 模板命中、列映射、格式、原始观测和单文件错误 |
| 金额有了却不能入账 | 资金性质/状态冲突、账户端点、组成金额、证据归宿与阻塞项 |
| 分类补完仍被阻塞 | 分类不是语义、关系和账户阻断的替代品 |
| 同笔重复 / 同额记录消失 | 来源身份、强弱证据、人工同笔/不同笔、历史链接与版本 |
| 导入后没出现在贷款列表 | 分期是否满足特例条件，来源是否正式入账及唯一关联；查待建立来源 |
| 显示缺账单或逾期 | 连续进度、有效来源、明确未还异常与应还日期分别检查 |
| 保存成功但列表没更新 | 先查原回执，再查摘要、缓存修订、会话与读取令牌 |
| 旧功能文档与页面不一致 | 先查 app.json/实际页面，再查现行专题；历史规格不是当前入口清单 |

需要判定正确与否，查[业务规则与验收](招财猫记账本业务规则与验收.md)；需要知道是否已发布，查[实施规划](招财猫记账本实施规划.md)。未来的复式分录、影子双写、财务预测、决策模型等保留为讨论/候选，不混进上述现有流程。
