<a id="overview"></a>
## 1. 项目全貌：先整理事实，再影响账本

CatLedger 是微信原生小程序。主要用途是把银行、支付宝、微信支付账单整理为可追溯的个人账本，也支持手工记账、账户与分类、统计、贷款与信用卡分期。它记录资金活动，不执行真实付款、转账或借款。

```text
用户：导入账单 / 手工记账 / 管理已有账目
                     ↓
微信小程序：展示、输入、文件选择、分页、请求恢复
         ├─ catledger-api：身份、账户、分类、交易、统计、贷款、导出
         └─ catledger-import：上传意图、解析、整理、核对、整批入账
                     ↓
CloudBase MySQL：正式账本、来源、决定、关系、版本与回执
CloudBase 私有云存储：待解析、短期追溯的文件原件
```

系统没有运行中的 AI 决策主链。当前判断来自确定性代码、来源模板、已经确认的映射以及用户选择。Jev 等模型尚未接入，不属于本次贷款改造范围。

**上传成功、解析成功、整理完成，都不等于已经记账。只有有效正式交易改变记账余额和收支。** 贷款计划、分期进度、原始文件和导入候选不是另一份权威余额。方案记费也必须先经过用户授权和正式写入，并保留其尚未与银行核对的依据。

实现入口：[API 动作](../cloudfunctions/catledger-api/src/action-registry.js)、[导入动作](../cloudfunctions/catledger-import/src/action-registry.js)、[客户端路由](../miniprogram/app.json)。

<a id="objects"></a>
## 2. 先区分七种对象

| 对象 | 回答什么问题 | 是否直接影响余额 |
| --- | --- | --- |
| 来源文件与解析批次 | 用户提供了哪份资料，按哪个版本解析 | 否 |
| 原始行与来源身份 | 原文是什么，这条证据是否已经出现 | 否 |
| FinanceUpdate 导入批次 | 这次准备把哪些资料一起整理和入账 | 否 |
| EconomicEvent 经济事件 | 多份证据可能描述了哪一次资金活动 | 否 |
| ReviewIssue 与人工决定 | 哪些事实仍不明确，用户确认了什么 | 否 |
| Transaction 正式交易 | 哪个账户在何时记了多少资金变化，依据是什么 | 是 |
| 贷款资料、期次、来源关联 | 本金依据、计划成本、实际还款和进度如何对应 | 不单独计入，仍通过正式交易表达账务 |

同一经济事件可以有多条证据，也可以生成多笔正式交易。例如一笔明确还款，可拆成本金转账及尚未计入的利息、费用支出。“行数”“事件数”“正式交易数”不是同一个数量。

### 2.1 金额与账户

金额使用整数分，接口使用十进制字符串；不拿浮点小数反复相加。资产、负债通过正式交易端点表达流入和流出。余额调整是独立类型，不伪装成收入或支出。

| 资金活动 | 账本含义 | 收支口径 |
| --- | --- | --- |
| 普通消费 | 付款资产减少，或信用账户欠款增加 | 支出 |
| 普通收入 | 收款账户增加 | 收入 |
| 本人账户转账 | 一个账户流出，另一个流入 | 不重复计收支 |
| 已关联退款 | 收款账户增加，关联原支出 | 冲减支出，分类随原支出 |
| 待关联退款 | 保留真实到账，原消费关系待确认 | 补关系前不冒充普通收入或已确认支出冲减 |
| 借款到账 / 归还本金 | 资产与负债之间的资金变化 | 本金不作为普通收入或消费 |
| 利息、手续费 | 明确实费或授权后到期方案费，见第6节 | 同一费用只计一次，计费用与付款分开 |
| 创建分期或确认管理进度 | 资料或进度变化 | 不据此生成虚构资金流水 |

现金账户受“不产生或加深负余额”约束。信用额度是资料，不是资产；贷款本金明细不能再叠加到同一负债账户余额。

### 2.2 三种容易混淆的“账户”

账单主体回答“文件属于谁”；支付工具引用回答“这一行使用什么工具”；账本账户回答“余额归谁”。一份支付宝账单可以同时使用余额、银行卡和消费信贷，不能整份绑定一个钱包。字段 source_account_id 中的 source 表示转出端，不表示文件来源平台。

实现入口：[正式交易领域](../cloudfunctions/catledger-api/src/transaction-service.js)、[整理模型](../cloudfunctions/catledger-import/src/organizer-model.js)、[资金账户引用](../cloudfunctions/catledger-import/src/payment-account.js)。

## 3. 用户入口与身份

当前底部常驻入口是首页、明细、统计、我的；中央记账按钮打开“账单导入 / 记一笔”选择。账户、分类、贷款等使用各自页面。旧文档把“账本”列为底部入口的描述不再作为现行导航。

启动和受保护操作通过既有登录流程识别用户。身份或授权未确认时，不展示其他会话的个人数据；需要登录的动作在用户完成后继续，取消则不执行写入。账号昵称从服务端读取，头像不是身份凭证。

应用启动后即发起身份确认，与首屏绘制并行；登录入口承接同会话、未过期的启动请求，不因界面挂载再发一次。正常过程只显示简洁加载，成功即自动进入，不展示连接或休眠说明，不要求用户额外选择是否进入。失败后才显示重试和返回。身份确认的云调用与自动重试共用固定等待上限；超时请求从在途读取中释放，重试不会继续挂在旧请求上，迟到结果不能写入缓存或打开账本。关闭、组件卸载和换会话同样阻止旧入口继续操作，首次资料草稿及普通业务写入不受启动等待上限影响。提前发起减少界面与请求之间的串行等待，不保证消除数据库休眠唤醒时间。实现入口：[应用启动](../miniprogram/app.js)、[登录组件](../miniprogram/components/login-sheet/index.js)、[身份请求](../miniprogram/services/catledger-api.js)、[云调用等待控制](../miniprogram/services/cloud-function-client.js)。

每次启动仍由微信可信上下文确认身份和用户有效状态。已完成默认数据初始化的用户，在同一只读快照内读取身份、分类与修订，不再维护分类或取得用户写锁；不会因为打开账本递增数据修订。新用户和初始化标记落后的用户才进入原有锁内初始化事务，补齐缺失默认项并设置标记；已归档分类、自定义同名分类不被恢复或覆盖。分类仍完整返回，不用空列表冒充完成。

身份确认后，首页先交付同环境、同用户的已有快照并标注更新中；没有快照则显示骨架。随后必要费用检查／补记完成，再读取最新首页。费用失败、部分完成或检查后又出现外部修订时，旧余额保留待核实状态，不能成为最新确认依据。检查成功的结果仅在服务端业务日和截止有效期、相关缓存令牌与会话都匹配时短暂复用；贷款及会影响费用核对的导入写入、前台校验发现跨设备变化、跨日、失败都会要求重查。新首页返回另一修订时最多再核对一次，连续变化提示待核实，不循环等待。

云函数从可信微信上下文解析用户；客户端传来的账户、交易、批次、贷款 ID 都要在该用户范围查验。跨用户对象不能因猜中 ID 被读取或操作。本机登录状态只控制页面流程，不能替代服务端授权。

实现入口：[中央记账与导航](../miniprogram/custom-tab-bar/index.js)、[登录保护](../miniprogram/services/login-guard.js)、[API handler](../cloudfunctions/catledger-api/src/handler.js)、[导入 handler](../cloudfunctions/catledger-import/src/handler.js)。

<a id="import"></a>
## 4. 导入全过程

页面分为“选择文件 → 确认账户 → 核对交易 → 确认入账”。后台还包含解析、来源身份判断、关系建立与事务写入；四个页面步骤不等于只有四次判断。

```text
选文件 → 私有上传 → 逐文件解析 → 标准语义与来源身份
                                      ↓
                          创建 / 更新 FinanceUpdate
                                      ↓
                账户归属 → 事件与关系 → 待核对问题
                                      ↓
                     保存用户决定，重算受影响结果
                                      ↓
              核对所选范围 → 锁内复查 → 整批原子入账
                                      ↓
                完成回执 → 独立刷新明细 → 来源追溯
```

<a id="import-files"></a>
### 4.1 选择、上传和单文件失败隔离

**输入：** 用户选中的文件及元数据。客户端先检查格式、大小、数量和本次重复选择；服务端再验证上传意图与所属用户。限制以现有契约为准，不能只依赖页面检查。

imports.prepareMany 准备上传信息；原件进入用户隔离的私有对象路径，再由 imports.parseFile 触发解析。路径和名称本身不是授权凭证。

同路径、同内容或已有解析结果按摘要与解析版本判断是否复用。复用的是证据，不是无条件复用上次正式入账结果。规则版本变化可以追加解析批次，不能覆盖原始证据。

**结果：** 每份文件有自己的进度、解析结果或错误。单份失败不清空其他成功文件；重试该文件，不从头重复上传全部。放弃某文件与放弃整个导入批次是不同操作。

首次点击整理前，客户端用现有 pending-ledger-write 按环境和已确认用户保存原 requestId 与 batchIds；本机保存失败则不发送。prepare 响应丢失时查询或重放同一请求，取得原 updateId 后接续，不解除文件占用或另建整理批次。成功后读取失败显示“整理已完成，结果待刷新”；隐藏、退出和换用户阻止旧响应回填及跨用户重试。恢复依据先交给当前用户的最近批次指针，再清理原在途请求。验证：[首次整理恢复](../test/import-prepare-recovery-db.test.js)。

实现入口：[upload-flow](../miniprogram/pages/import-workbench/upload-flow.js)、[导入服务](../cloudfunctions/catledger-import/src/import-service.js)；测试：[上传行为](../test/import-upload-flow.test.js)。

<a id="import-parse"></a>
### 4.2 解析与列映射：先知道字段是什么

**输入：** 原始字节、文件格式、来源模板，以及需要时由用户确认的银行列映射。

解析器识别容器、工作表、表头与数据行。支付宝、微信和银行分别适用经过测试的模板；同时命中多个完整模板或多个账单工作表时不能随意选一个。通用银行表格含义不明时先确认列，不靠金额外观猜借贷方向。

银行确认页修改表头行号后自动重新识别列，连续输入合并处理，完成输入或离开输入框立即识别。已有信用卡类型和资金方向选择保留；新表头未识别成功前不按旧表头提交，失败保留输入供重试。预览样例与正式解析共用行类型判断，中英文重复表头、空行及控制说明不冒充交易样例；异常交易仍展示并保留诊断。关闭页面或会话改变后，旧预览不得回填。

日期、金额、方向、状态、交易类型、对方、商品、支付方式、交易号等投影为统一字段，同时保留原始列名、位置和内容。空值、零、缺列、斜线占位、重复列、额外列不能混成一种“没有信息”。文本含“合计”不代表整行应删除，结构判断优先。

银行金额可能是“带符号单列”“金额加方向”“收入/支出分列”。符号含义不明、两列冲突、无效日期或不支持币种必须留下诊断。不能丢异常行来凑成功率。

**结果：** 规范化行、原文定位、字段观测、文件控制结果及解析/语义版本。文件总笔数、收支控制项与行级解释分别保留。

实现入口：[解析器目录](../cloudfunctions/catledger-import/src/parsers)、[来源 profiles](../cloudfunctions/catledger-import/src/profiles)；详见[语义与验证](现行说明/账单语义与工程验证.md)。

<a id="import-semantics"></a>
### 4.3 语义解释：这条记录产生什么经济效果

**输入：** 规范化行、来源 profile 和原始语义证据。Row Semantic Resolver 先解释动作、状态、资金效果、账户引用及冲突；通用事件层消费标准结果，不再次遍历平台文字猜含义。

| 条件 | 处理原则 |
| --- | --- |
| 动作、状态和方向相互支持 | 产生相应资金语义，再检查账户与关系 |
| 明确失败、关闭或非资金授权 | 保留证据，不伪造成功扣款 |
| 退款到账 | 进入退款关系判断，不简单记成收入 |
| 本人转账、借款、还款 | 分清端点及本金/费用，不按“收入/支出”字样直接记消费 |
| 未知动作、矛盾状态、多账户缺少金额组成 | 保留未知/冲突并产生核对问题 |
| 用户明确排除本次记录 | 排除本次入账，不提高来源识别率 |

**不能跳过：** 填账户或分类不足以解除资金性质未知、多账户缺分项等阻断。未知状态目前可查看原文或排除本次记录，尚无用户确认其资金效果并继续入账的完整入口；提示“待核对”不代表已支持人工解决。普通分类规则和历史分类别名可以给分类；分类可稍后补，交易性质未知不能因此直接入账。

自动分类只作用于已确认的收入、支出和费用，且目标必须是同用户可用、收支类型相符的分类。先复用同来源“商户＋商品”的具体记忆，再按商品用途词、商户用途词细分；没有明确规则时，才依次参考旧商品记忆、商户记忆和支付宝原分类。旧的宽泛交易类型记忆不再参与匹配。美食、饮品、水果零食、交通、医疗、生活缴费等细类有明确用途词才落到二级；同一记录命中同大类的多个子类时保留大类，跨大类冲突则待分类，平台名称本身不证明用途。子类已停用可回到可用父类，不恢复停用项。

整批入账成功或明确补分类后，新记忆只记录商户与商品组合；商品没有有效信息时才记录商户，不学习宽泛平台或交易类型。同批同一具体证据出现不同分类时停用其旧记忆；记忆与账务在同一事务中提交或回滚。旧草稿按当前规则重新整理时只更新未人工决定的自动分类，保留人工分类、账户、金额、时间及排除决定；已入账记录不自动重分类，读取不产生这些写入。

贷款规则区分计划、已出账、计费和实际付款证据，不能单靠期号推导已还，具体见第 6 节；未知银行模板仍保留待核对，不宣称全部模板均已适配。

实现入口：[row-semantic-resolver](../cloudfunctions/catledger-import/src/row-semantic-resolver.js)、[rule-evaluator](../cloudfunctions/catledger-import/src/rule-evaluator.js)、[economic-event-builder](../cloudfunctions/catledger-import/src/economic-event-builder.js)、[category-mapping](../cloudfunctions/catledger-import/src/category-mapping.js)。

<a id="import-match"></a>
### 4.4 来源去重与交易关系：相似不等于同一笔

**输入：** 已解释的行、稳定来源身份、已有证据与正式历史交易。

同来源身份由用户范围唯一约束兜底；相同稳定 ID 仍核验核心字段，冲突不能静默覆盖。跨来源只有已核验的稳定证据或明确规则才能自动确认；同额、同日、同商户只是候选。银行流水号在正确账户范围内使用，不能与平台订单号碰巧相同就合并。

| 关系 | 系统可以确定什么 | 需要用户确认什么 |
| --- | --- | --- |
| 同一笔的多份来源 | 强证据下保留多来源、避免重复记账 | 弱匹配确认同笔/不同笔，同额独立保留 |
| 本批退款与原消费 | 强且唯一的订单/退款证据支持原消费 | 弱候选人工核对，不列任意近期消费让用户猜 |
| 与历史可能重复 | 生成有证据候选，显示原记录 | 同笔、不同笔或暂不处理 |
| 无可确认原消费的退款 | 保留待关联及真实到账 | 以后补原消费，不伪造冲减分类 |

同笔不删除另一份原文；不同笔不再被同一弱匹配吞并。已被贷款付款关系占用的交易，不绕过整组维护挂接单个成员。

银行与支付平台缺少共同订单号时，在双方已确认同一账本账户、金额/币种/方向一致、原始时间明确到分钟且落在同一分钟，并且银行摘要明确标出对应支付渠道的条件下，生成同笔候选。支持财付通、财付通快捷、微信支付、支付宝及支付宝快捷的明确前缀；商户文字中偶然出现平台名不算渠道。Excel 小数日期保留其时间信息，只有日期或整数日期不能按补出的零点匹配。银行卡尾号不能代替账户确认，银行记录也不能绕过这些条件改走宽松文本匹配。

候选不会自动减少交易数。账户确认后统一补齐候选；旧草稿原位升级，保留账户、分类、排除及此前“不同笔”决定；尚未确认的旧银行/平台候选按新条件重验，失效后回到相应核对，旧标签也不能绕过提交时验证。

服务端在完整有效候选图上检查双方都只有一个候选、账户仍有效且没有历史交易占用，才列为“建议配对”；一页只有一条不代表唯一。核对交易页可集中预览全部建议范围，取消本页或跨页例外后，一次点击“确认所选配对”。总组数、来源数、消费／退款性质来自服务端完整范围；100组普通消费分别形成100笔待入账事件，不是把200条合成一笔。

建议入口与下方逐笔卡片等宽，标明“判断是否同一笔”、完整建议组数和“批量核对”。这些建议也属于下方待核对列表，任一入口确认后同步更新，无须重复判断。组数随整理摘要的 `workbench.pairingSuggestedCount` 返回；服务端复用摘要已读取的事件、问题成员和证据，与配对分页共用完整图判定，不额外扫描整批候选。客户端每次应用摘要都更新组数，包括同一视图版本的新摘要，不以旧入口缓存覆盖它；仅旧服务端缺少该字段时，才回退到与弹层首页共用的有界读取。点击后仍按原方式读取弹层分页，保存后随新摘要刷新；读取失败或组数不合法保留重新核验入口，不显示为零。卡片状态随每次视图应用和弹层关闭按当前步骤与页签资格对账，资格恢复即重建，不依赖下一次整页重读。无唯一建议时，下方多候选仍可逐笔核对。核对与分类卡片日期按“月-日”单行显示。配对内联原文和完整原文的日期列统一显示可读时间，包括 Excel 日期序号；原始字段、金额、编号及匹配使用的时间精度保持不变。

逐笔候选从待核对项进入“判断是否同一笔”，每次展示具体一对，两边原文自动展开；异步补齐原文时保留商户、金额、时间及当前配对。底部左右按钮“不是同一笔／是同一笔”点击即保存当前这一对，无须先选再确认，不夹带以前跨页未提交的选择。“不是同一笔”只拒绝这一条候选关系，剩余有效候选继续核对。关闭不作决定，也不排除记录。确认同笔沿用平台主记录和完整平台语义，保留全部有效原文、来源账户决定与退款关系。仅允许解释银行缺少交易类型这一缺口，未知状态、组合支付、贷款分期及核心冲突不借同笔确认解除；退款与原消费仍单独核对。

具体同笔／不同笔决定按可靠来源身份和必要事实摘要持久保存。刷新、重新整理及重导相同可靠来源时，重新核验账户、事实、规则和占用后复用；不依赖临时事件ID，也不推广成商户或金额规则。身份不可靠、来源实质变化或账户事实改变时重新核对。重复数量同时计入同来源重复和已经确认同笔的辅助来源；尚未确认的候选归入待核对。

实现入口：[evidence-matching](../cloudfunctions/catledger-import/src/evidence-matching.js)、[bank-channel-matching](../cloudfunctions/catledger-import/src/bank-channel-matching.js)、[候选与人工决定](../cloudfunctions/catledger-import/src/review/bank-channel-candidates.js)、[relation-resolver](../cloudfunctions/catledger-import/src/relation-resolver.js)、[historical-duplicates](../cloudfunctions/catledger-import/src/historical-duplicates.js)、[refund-relation-policy](../cloudfunctions/catledger-import/src/refund-relation-policy.js)。

支付宝关闭原单与退款存在可靠同源编号矛盾时，保留整组核对原因，不能用普通“待关联退款”绕过。未支付关闭仍不记消费；有可信已入账原支出则复用，实际退款保持真实日期与到账账户。只有同平台可靠来源身份才能在退款账户不同的情况下证明原单；同额同日不够。个人导出状态扩展仍需真实模板证据，见[语义专题](现行说明/账单语义与工程验证.md)。

### 4.5 确认账户：先归属，再分配金额

**输入：** 支付工具引用、当前有效账户、历史映射、本批和事件级决定。

账户映射优先级从低到高为：**精确推断 → 历史别名 → 历史明确映射 → 本批决定 → 事件级决定**。最高同级候选冲突时明确处理，不以数组最后一项为准。历史类型不兼容不能沿用；保存时还要验证真实账户可用。

| 场景 | 页面与保存结果 |
| --- | --- |
| 已有可靠归属 | 复用，允许按现行流程修订 |
| 稳定现实账户在多个来源出现 | 合组确认，仍保留各自来源引用 |
| 信息不足 | 待选择，不默认新建，不按同名未知项合并 |
| 选择新账户 | 先建草稿，最终有效入账事件可达才物化 |
| 明确不计入稳定工具 | 本批排除与持久规则作用范围分开 |
| 多付款/收款端 | 先确认账户，再确认受支持金额分配，总额守恒 |

合并还款名称不是一个真实账户，不创建虚构的合并账户掩盖分项。账户选择不能改写来源金额；复杂多对多只按现有明确支持的模型处理。

解析完成后还需整理账户分组，再读取账户列表；整理期间留在原位置显示“正在准备账户”，不是额外确认步骤。每项账户只要有记录，笔数都可点开查看分页原文，不依赖首条预览是否齐全。点开立即显示弹层；会话过期时保留输入、只读刷新摘要后继续，失败留在弹层重试。关闭、隐藏、换用户后不回填旧结果；查看期间背景更新会提示重新读取，不覆盖正在看的记录。验证：[账户原文交互](../test/import-inline-evidence.test.js)。

批量确认使用原事务、复用映射索引并统一收尾，不是逐笔网络提交。refreshAccountGroups 展开旧引用、处理问题与成员；无候选时不为了刷新制造新业务行动。

连续确认时，前一项保存可能先于新摘要返回；若下一项目录因此判定旧视图过期，客户端先保留当前选择、等待同一个保存请求和权威摘要，再核验原账户问题版本、决定内容及所选账户可用性后接续确认。不会重复提交前一项，也不替换已变化的问题版本自动保存。摘要或目录失败、问题实质变化、批次结束时停止确认并保留可恢复信息；隐藏、退出和换用户后不回填或提交旧选择。放弃后重新开始会清除旧批次的延迟摘要与输入计时器。验证：[账户会话衔接](../test/import-account-session.test.js)。

实现入口：[account-mapping-policy](../cloudfunctions/catledger-import/src/account-mapping-policy.js)、[review/account-mapping](../cloudfunctions/catledger-import/src/review/account-mapping.js)、[account-draft](../cloudfunctions/catledger-import/src/account-draft.js)、[funds-allocation](../cloudfunctions/catledger-import/src/funds-allocation.js)。

### 4.6 核对与保存决定：只改变明确选中的事实

**输入：** 当前问题、事件/关系、用户选择和版本。页面先检查必填，服务端再校验决定是否适用。

核对包括账户、本人/他人还款性质、资金分配、同笔/不同笔、退款、排除及分类。可共享决定的记录合组必须有明确依据及成员范围，不能同标题就替整批决定。

整理账目的各页签按交易本地时间从早到晚展示，同一时间以稳定ID排序，未知日期放最后；服务端按同一规则分页，不在取页后按类型或商户重排。待核对与待分类也逐笔展示，每页50笔、末页显示余数；分页总数与页签交易笔数使用同一口径，不按问题组数量分页。服务端短响应由客户端沿同版本游标补齐，全部补齐才推进页码，失败保留原页；加载或失败时不显示已完成、没有记录。每笔附当前未决问题入口，共享决定仍在原问题中核对完整成员范围；同一交易有多个问题时依次处理，未关联问题的待核对交易也展示并可查看来源。标题下显示“有效交易＝全部－已排除－重复”的整批数量；核对与分类关系合成一行“有效交易＝待核对＋已核对＝待分类＋已分类＋无需分类”，各项数量仍在对应页签展示。已分类直接显示具体分类，二级显示“父类 / 子类”，由同一用户范围的分类表读取，不依赖前一页是否打开分类目录。 每笔“修改分类”打开当前选择，可从同一收支类型的完整分类目录搜索、翻页选择一级或二级并保存；只修改当前笔，记为人工分类，后续重新整理不能自动覆盖。同商户其他记录、原文、金额、资金账户和未决核对保持。保存前校验批次与事件版本、分类归属和可用状态；结果未知保留原请求，先确认该修改再整批入账。成功但摘要读取失败保留“已保存”，刷新只读列表。关闭未保存选择不写入，背景更新保留选择并要求重新核对，迟到响应不得回填。

交易核对和分类各自保留搜索词，在当前页签的整个批次内搜索商户/交易对方、商品描述、一级或二级分类路径及交易本地日期；输入年月日、年月、月日或年份可筛选日期，兼容横杠、斜杠和中文日期。日期匹配事件的交易日期，未知日期不伪装为匹配；列表只显示匹配的真实交易，搜索可以找到同组非首笔成员；打开共享问题后仍核对完整成员，候选不作为命中依据，搜索不缩小决定范围。搜索文字同步保留，异步读取只更新结果，不能替换输入框内容；账户与分类目录弹层遵循相同约束。搜索从第一页开始，清空恢复列表，整批计数和入账门禁不随搜索改变；无结果显示没有匹配，迟到请求不能覆盖当前搜索。

正式入账前，重复记录可“修改判断”：已人工合并的来源可以恢复为多笔；来源原文和身份不复制、不丢失，保留主记录当前人工字段，其他来源恢复合并前字段，旧版无快照时按原文及当前有效映射重建。拆开后交易类型、归属、退款等未决事项继续待核对，不因修改判断解除入账门禁。之前确认不同笔的记录在待核对或已核对项中也可重新打开指定来源对，核验双方版本和当前事实后改为同一笔。误选“关联已有账目”可撤回本次关联并返回历史核对，原正式交易与余额保持。同一可靠来源身份的重复账单不可拆成多笔再次入账，已正式入账记录仍走原账目维护。修改同步更新具体来源对记忆，重新整理或重导不得恢复已被纠正的旧判断。

核对与分类列表统一每页50项，只有最后一页可以不足50项；服务端因响应大小提前截断时，客户端沿同一版本的游标补齐当前页，不读取整批全集。全部片段成功后才显示和推进页码；补读失败保留原页，离开页面、切换筛选或版本变化后不接收旧片段。核对页签依次为“待核对、已核对、重复交易、已排除”。已核对与重复交易卡片统一显示“查看”；详情自动展开各份来源的原始列和值，无须逐份翻页。普通已核对交易从详情“修改核对结果”调整交易类型和资金账户，转账选择不同的转出、转入账户；只保存当前笔的人工决定，原文、金额、时间与其他记录不变。类型变化后重新判断分类、退款关联和入账条件；仍缺信息的记录返回待核对，不能绕过入账门禁。多账户分配和贷款付款继续由专用核对流程维护，通用修改不覆盖其组成。已有同笔事实仍可在详情修改同笔判断。取消修改保留原文且不写入；保存校验用户归属、批次/事件双版本，结果未知保留原请求，确认成功后只读刷新并返回列表。来源读取失败在本卡重试，超长原文保留完整查看入口。分类与已排除沿用直接原文入口。已排除在服务端按整批记录的实际排除依据归组：存在本次整账户排除决定或已保存的账户排除规则时，按具体来源账户汇总成一张卡片，无法确定账户名时归入“账户已排除”；其余记录按非资金记录、交易关闭、交易失败等原因归组，单笔手动排除归入“手动排除”，未知原因保留在“其他排除”。自动关闭或失败即使带具体支付账户，也归入对应原因卡片；同一账户的整账户排除和自动排除记录不能混为一组，同一自动原因可跨账户合组。先整批归组再分页，不受交易分页或时间穿插影响。账户卡片用账户名称，自动排除卡片用原因作标题；展开后每笔明确显示实际排除原因和原账单状态，区分交易关闭或失败等自动排除、已保存的账户规则和本次手动选择，原因缺失则显示待核对。卡片显示整批该组总笔数，按全组最早一笔排序；展开后才读取该组交易，在卡片内每50笔按时间翻页。一次展开一个组，收起或换组释放当前明细，刷新保留正在查看的组；搜索时组笔数和明细对应同一关键词的匹配范围。分组读取失败可原位重试，组内翻页失败保留原页。关闭、页面隐藏、会话或批次版本变化后，旧原文响应不得回填；旧顺序或旧分类版本的游标不能继续混页。

点击列表项立即打开对应弹窗或骨架，先展示已有摘要；详情首段成员直接复用，目录按决定需要读取，原文自动有界补齐。详情、必需目录或历史候选未核实前禁用对应确认，摘要与预选不能替代。非必需目录不挡首次内容，目录／原文局部失败在原处重试；输入、跨页配对选择与例外由原草稿会话保留，迟到读取不得覆盖。切A再切B、关闭、隐藏或换用户都使旧读取失效。输入或弹层期间挂起的新版本延迟到打开弹层时应用，仍保持用户当前步骤，不按最新工作流把用户降级到较早步骤。

原幂等事务内取锁、检查版本、应用允许字段，并同步事件、成员、关系、投影、历史核对、草稿可达性和计数。单笔与批量保存各有引用校验和路径，不是无业务规则的 UPDATE。

**结果：** 保存决定、更新版本、返回回执后读摘要；不是每次选择都重解析。旧计划升级保留人工字段、排除和关系决定，不伪装人工确认。

**失败：** 过期版本需刷新；结果丢失用原键核实。客户端先持久化待发决定和 requestId，不把超时理解为肯定没保存。

配对预览范围绑定可信用户、批次、视图和完整候选摘要；翻页游标绑定候选事实而非目录视图或数据修订，无关账本写入不影响继续翻页，提交范围令牌与续批令牌仍校验数据修订。跨页全选提交原范围及例外；服务端重新还原并校验，不能临时扩大。每次最多100对在同一个用户锁事务内全部保存或回滚，局部合并后统一更新关系成员、后续问题和计数。更大范围由一次授权接续有界批次，回执累计已保存／剩余数量和签名续批依据；自身版本推进只在剩余事实完全相同时延续，外部变化须重新核验。失败准确保留前序已保存进度和原请求，最终摘要只刷新一次；摘要失败显示选择已保存、结果待刷新。仍沿用 import-draft-session，不另建任务队列。

“这两条是同一笔，只记一次”只合并本批待入账事件，确认时不改变正式账务。“这笔已经记过，关联已有账目”从历史重复候选选择指定有效正式交易，复用原交易而不删除、合并或转移历史账目；两者不能混用。最终仍须通过整批入账门禁，取消配对不等于排除本次，排除本次也不承诺以后补记。

### 4.7 确认入账：完整识别与所选范围可入账分开

| 指标 | 含义 | 不能推断 |
| --- | --- | --- |
| statementFullyRecognized | 当前文件观测、字段和受支持控制项支持完整识别 | 行数相等不代表完整；缺当前观测不能补写通过 |
| selectedEventsReadyToPost | 本次所选事件满足入账条件 | 不代表文件每行都已解释；分类待补不等于所有问题都阻塞 |

每条来源应有资金、非资金、重复、待确认、明确排除、无效或未分配等归宿。排除不把未知变已识别；按钮可点不消除缺证据或语义阻断。

提交前 flush 草稿、取得权威结果再判断。正常摘要换版不取消合法提交；新增阻塞则提示继续核对，不发送未满足条件的请求。

### 4.8 正式入账：一个事务决定成功或失败

**输入：** 可信用户、批次及版本、原 requestId，以及持久化事件和决定；不能由客户端直接上传自算交易列表绕过整理。

以下说明业务检查，不授权重排原 SQL 锁序：

1. 进入用户范围幂等事务，核对状态、规则/计划版本及重放。
2. 锁定持久化事件与来源，检查归宿、证据、未决阻塞及可入账性。
3. 锁内复查历史重复、关系和目标有效性，历史变化可能要求重新核对。
4. 只物化可达草稿，检查账户、分类、现金、分配、退款累计和贷款关系。
5. 按经济性质新建或复用交易，保存来源/事件/交易/映射关系和副作用依据。
6. 结果、版本、修订和首次回执共同提交，失败整组回滚。

当前消费通常一笔支出、本人转账连接两账户、明确还款可以多项入账。信用卡分期应还本金行不重复写本金，真实现金到账和还款行不套用该特例；明确费用先查合同/期次覆盖，复用方案费或保持期初覆盖，差异与独立收费先确认。created 与 reused 分开，供维护使用。

信用卡账单固定摘要“电销现分按月收N期第M期共N期”“电销总账分月N期第M期共N期”按本期本金出账识别，连写的分期利息同样提取期号及总期数；须为信用卡账单、方向为支出且期号一致，缺失或矛盾不猜。正负号继续遵守用户确认的原账单规则，不能把本金出账反转为实际还款。列表和详情展示分期项目及期次；本金只保存来源，费用记一次支出，整批入账后从“补充分期记录”关联或新建计划。没有明确合同编号时，各来源独立保留，不因同账户、同额或同期而自动关联。旧未入账草稿重新打开时原位补识别，保留事件、证据与人工账户；已有人工转账决定冲突时需明确确认为“分期本金出账”，已入账和已排除记录不重写。

**结果：** 小回执先确认成功，明细另读。读取失败显示“已入账，明细待刷新”；重复请求返回原结果，不再记一笔。

实现入口：[finance-update-posting](../cloudfunctions/catledger-import/src/finance-update-posting.js)、[import-transaction](../cloudfunctions/catledger-import/src/import-transaction.js)、[command-result](../cloudfunctions/catledger-import/src/command-result.js)。

## 5. 手工账本、账户、分类与统计

### 5.1 账户和分类

账户保存名称、类型、币种、版本及停用状态。创建时余额/欠款起点用独立调整；资产账户可校正余额，负债没有日常校正入口。账单日、还款日、额度可未填，不显示假零。

账户停用前说明有余额及未结清贷款的维护限制，不要求虚假清零。“停用账户 → 账户详情 → 恢复使用”调用 accounts.restore，沿用原 accountId、用户锁、版本和回执，只解除停用并失效缓存；不改余额、本金或自动记费授权。活动账户重名时提示先修改该活动账户名称，不覆盖另一账户。验证：[账户恢复DB](../test/account-restore-db.test.js)、[真实Page](../test/account-restore-ui.test.js)。

分类最多两级，一级/二级均可记账；同级排序、停用恢复、父级固定。餐饮的子类为美食、饮品、水果零食；原预设“吃饭”通过显式迁移改名为“美食”，保持分类ID及旧账关联，用户改名、归档或同级已有“美食”时保留现状。停用不删历史，收支分类类型匹配；退款沿用原支出分类。

默认支出按生活用途组织：服饰鞋包、日用家居、数码电器、美容美发、运动健身、宠物、旅行直接作为大类；饰品属于服饰鞋包，快递邮寄与家政服务属于生活服务。购物保留给未细分的购买；餐饮、交通等可继续选子类。收入保留工资、奖金、兼职、理财收益、礼金、其他收入，中奖收入属于其他收入。转账、还款、退款仍是资金动作，不混作普通支出分类。分类图标按稳定系统键匹配具体用途，改名不会丢失图标；“其他”和未知自定义分类保留通用图标。明细中的转账、退款、余额校正按交易类型显示专用图标，退款文字仍沿用原支出分类；未分类账目及统计使用标签图标，分类筛选的“全部分类”使用网格图标。动作图标不靠分类名称判断，不改变账务或统计口径。

默认目录在首次登录初始化时创建；后续登录仍只补缺失项，不自动改名或调整归属。实现见[预设目录](../cloudfunctions/catledger-api/src/default-categories.js)。

### 5.2 手工交易

先读账户/分类，填写类型、金额、时间及端点，服务端验证用户、账户、分类、退款与现金。写入、版本、修订和回执同事务，失败保留输入。修改/删除检查版本和贷款关联等保护。

新增不需要模型决定。停用账户不能新增或编辑普通交易，但符合约束的历史交易仍可删除，账户不因此恢复。

### 5.3 查询与统计

明细按本地发生日期支持月份/日期、账户、分类、来源、备注与导入批次筛选。未分类不等于所有空分类的转账或退款；游标绑定查询和版本。

退款新增和待关联退款共用原消费查找：每页20条，可按消费月份、原付款账户和备注/分类/账户关键词查询，并继续翻页；也可从原消费详情点“为这笔消费记退款”。只列出有效、尚可退款且不晚于本次退款的普通消费，贷款费用及整组付款成员需从专用费用详情退费。切换筛选取消旧选项，迟到响应不覆盖新列表；游标绑定查询和账本版本，变化后重新查询。保存提交原消费版本，在用户锁内再次核对状态、日期和累计退款上限；失败保留金额草稿，结果未知仍恢复原请求。

正式有效交易产生余额与收支，已关联退款冲减支出，本人转账、本金和余额调整不重复算收支。用户永久删除的普通交易不再存在于正式交易表；系统内部软删除历史仍退出聚合。全期计划不与已记费用再相加。贷款详情显示费用净额及其中方案未核对金额，与真实付款现金流分开。

首页大卡片不带月份，固定展示当前净资产和全账本累计收入、累计支出，不再并列显示累计结余。首页请求 `dashboard.get` 时明确使用 `summaryScope: all`，月份只决定下方近半年趋势的终点。服务端在可信用户的一致性只读快照内聚合全部有效正式交易；当前净资产另取全部账户账面余额。无收支时累计为零，期初余额仍可使净资产非零；因此收支差不代表当前净资产。导入中的草稿、已删除交易和其他用户账目不参与累计。

首页沿用同身份快照和费用检查顺序，但旧的本月结果不能当作累计结果展示或缓存。服务端未确认累计范围时本次读取失败；已有累计结果保留并提示更新未成功，没有累计结果则显示未读取状态，重试重新取得累计。统计页仍按用户选择月份汇总。验证：[首页Page与缓存](../test/home-overview.test.js)、[累计口径DB](../cloudfunctions/catledger-api/test/integration.test.js)。

首页的加载、费用检查异常和读取失败集中显示在大卡片下方，重试重新读取整页数据；账户标题不放全页加载或重试按钮，账户区读取失败仅显示尚未读取，不能误示为没有账户。更新失败仍保留已显示的账本结果。

实现入口：[账户服务](../cloudfunctions/catledger-api/src/account-service.js)、[分类服务](../cloudfunctions/catledger-api/src/category-service.js)、[交易服务](../cloudfunctions/catledger-api/src/transaction-service.js)、[API 契约](../shared/catledger-api.json)。

## 6. 贷款与分期：在逐期表中一次处理

本节描述 main 代码，迁移、部署和真机状态分别见[实施规划](招财猫记账本实施规划.md)。当前普通流程为勾选已还后保存，同时补齐该期利息与手续费；无需独立历史授权或自动记费设置。旧接口和费用保护仍兼容。

### 6.1 创建与已有账单

从第6期账单创建时，账户与来源期次取已确认账单；原本金、首期日期和还款依据仍由用户补全。在原预览表第1～6期对应行选择已还，默认勾选，可逐期改；不再显示第二份期次列表，预览覆盖全部可选择的历史期次。保存创建就是提交，无二次弹窗。按勾选的本金计算接入基准，并在一个事务内生成计划、关联第6期及已有同编号来源、补记缺失息费、保存已还选择和回执。建资料不重复原消费、不虚构放款。

### 6.2 补记历史

缺失费用按确认方案/已保存期次记录到各自原月，费用账户是导入选定的信用卡/贷款账户。已有稳定费用身份或已核验来源的同费用先复用；独立手工费用须由用户在原逐期预览中点“选已记”明确选择原账目。同账户、同月、同额仅推荐候选，可查所有日期及翻页定位跨月记录；没有候选不弹确认，仍一次保存。提交重查用户、交易版本、金额、退款、来源和付款占用；原金额、账户、日期、创建归属保持。明确一次实收覆盖多期沿用父项覆盖，不逐期重复认领。新增历史费用同时建立同额同账户的余额保全记录，当前银行卡、负债与净资产不变。两笔记录由收费关系绑定，不能单独编辑或删除。历史费用按支出统计；历史清偿金额独立保存，不能用余额保全记录代替。已有费用只增加清偿依据，不补余额调整。真实退款从净费用中扣一次，父费用及逐期覆盖不重复计算可清偿额。

旧已还进度不在升级或读取时自动补息。详情返回全部待选择历史期次（最长600期），在原逐期表的“还款”列勾选。详情使用带版本的紧凑完整快照，一次读取期次、来源核对结果与原计划成本，不再连续分页重算全集。完整行数、期号或版本核对失败时禁止保存；旧服务分页响应仍须加载到最后一个待选择期次。重试与版本刷新保留尚未保存的选择；未展示的选择不能提交。实际已付、部分实付和明确未还的选择保留；确认历史不制造银行卡扣款。

### 6.3 后来导入与漏月

已有第6期，后来第8期：同一分期来源放入第8期，详情询问尚未选择的第7、8期是否已还，默认勾选，保存才生效。第3期曾选未还的，不因第8期到来重置。后到同一费用同额仅补来源；差额按原影响预览和确认净调，不另新增一次总费用。身份冲突、独立收费、已抑制收费仍阻断错误合并。

### 6.4 不再导入时

第9期以后没文件，直接点对应行“记本期还款”。该入口直接新增本期还款，不再询问“这笔钱记过了吗”；已导入账目的关联或更正从原账目入口处理。带入未付本息费，选择实际付款账户和日期，保存一次完成缺失费用入账、银行卡总额扣款、本金冲减及期次关联。费用属于贷款账户，实际钱从所选资产账户转出；沿用上次该笔贷款的有效付款账户，没有时请用户选择。先记过费用的只清偿，未记过的在同一事务记一次。金额明细可展开修改，不能超额分配或篡改原账单。

已经有信用卡还款转账时，从账目详情点“分配到分期”，选择该信用账户下的分期，输入期号并“使用该期金额”，核对实际本息费及未分配额后保存；可添加其他分期。各贷款分配与未分配余额之和必须等于原总额。原账户、金额、时间和交易保持不变，已导入同一期利息可在保存时认领，不能重记；已有付款组进入“还款详情”，需要更正或撤销时展开“更多操作”。关联方式记入的还款，更正关联保留原转账，撤销只解除关联；其他记入方式继续按原整组语义处理。一期实际付款只改变该期，不推导前面各期全还。明确关联到已有历史确认的期次时，记录被真实凭证替换的本金/费用覆盖，剩余本金与费用不再扣第二次；撤销关联保留历史确认，改回未还遇真实付款依赖时先维护原付款组。

### 6.5 页面与兼容

已关联借还的账目显示只读详情，保留一个“还款详情”或“放款详情”入口，不显示无法保存的普通编辑表单与删除按钮。借还详情默认显示实际金额、日期、本息费和对应账目；费用为零、整单没有未分配金额时省略相应行。贷款名称可进入贷款详情，修改、调整对应期次、核对重复导入及撤销集中在“更多操作”，仍受原会话、版本、待确认请求与整组保护约束。调整本次期次时不展示整笔贷款的总览，每期先显示金额与选择入口，编辑、付款历史及计划修订按需展开；缺少期次仍可明确新增。展开和返回不写账，修改取消回到原记录，写入未知结果仍核实原请求。

一张逐期表，每期只出现一行：待选择历史已还的直接在该行“还款”列勾选，点击勾选不打开详情；其余未还行有“记本期还款”，已还行显示“已还”。实际记录从对应期次查看，不另设页签或重复的勾选列表。费用摘要显示已记净额，编辑与删除直接放在逐期列表底部，不另设管理入口。旧自动设置仍生效时保留停止入口；用户保存新的已还选择时停止旧设置，未来费用由后续还款或导入处理。

有非零一次性手续费时，详情始终显示“一次性费用”。未确认发生只保留计划；点“处理已发生的一次性手续费”，填写实际金额、收费日期和账户/分类，或按月份认领已有支出。记在贷款账户表示已计负债，记在银行等资产账户表示实际已付；关联已有支出保持原账户、日期和金额，不新增交易。无需先选择首期历史已还。可明确覆盖连续期次手续费，合计必须守恒，只记一次实收；资产账户已付的覆盖费用退出逐期待付款；后到逐期银行费用沿用同用户的父项实收，只补有效来源，不新增支出。新操作复用收费身份、保护关系、原请求回执和原子事务，不开启自动记费。

旧授权接口继续按原日期、范围、覆盖和幂等条件工作；普通读取/导出没有隐式写账。利率变化、提前结清、一次性费用、退费与冲突仍保留既有维护能力：已付/已退款/来源绑定的费用不能直接删除，归档和取消未来项不伪造退款。普通页面不再让用户先理解收费身份、授权或人工与实际进度的技术区别，后台保护仍生效。

| 旧费用配置预览 `chargePlan(configuration)`；保存期次分项优先于计划推算 | 只读分页展示起算、已覆盖、未来与本次缺项金额；一次性费用需独立确认计费日。已有实际交易/来源、期初覆盖先于待记方案 | 游标绑定用户、贷款、修订与同一配置；输入变更重预览，预览不替代执行校验 |
| `configureCharges`：版本、固定/日期/覆盖确认、起源、范围和 auto/once | 用户锁内建立稳定合同/收费身份；认领精确交易和一次实收覆盖，保存审计，不生成支出或本金。无明确复用依据建立独立合同；只有明确选择原合同或经过核验的来源身份才认领旧合同，输入编号冲突要求核对 | 冲突整批回滚；未知结果查原回执，不能换请求号重建身份 |
| 既有自动授权：进入或刷新相关页面 | 协调器先 `dueCharges`，再 `syncCharges`，每批最多40项，每次前台最多3批。服务端上海业务日、授权范围和收费状态共同裁定，只记负债端费用 | 原请求先持久化，已完成批次不重做；换用户、隐藏、后台停止后续批次，未确认写仍可恢复；写成功而摘要失败单独提示 |
| 明确账户、编号、期次/分项的后到实单 | 同费同额仅补来源；期初已含不新建交易；20遇18先 `chargeImpact` 再确认净调-2；独立追加项需明确确认 | 导入原事务内重查，差异/停止标记/冲突阻断该批；撤销补证来源保留原方案费并恢复未核对依据 |
| 真实付款：实际总额与版本、明确费用分配 | 已记费须引用未清偿收费或有效实费；未记费首次登记；信用卡整单各贷款分配加未分配额等于总额 | 本金、现金、费用容量及完整组一起校验，失败全回滚。费用不由 accrued 标签单独证明 |
| 普通本期还款 `loans.record(simplePeriod=true)`，单一期次版本与本息费 | 服务端在同一事务记缺失费用于贷款账户，自动绑定该期费用，再执行原付款、容量与期次校验；不接受跨期/更正冒用简单模式 | 任何金额、版本、依赖失败整体回滚；原请求回执防止重扣 |
| 创建 `repayments` 或 `confirmInstallments`：具体期次 paid 选择 | 只记所选已还缺失费用；历史费用和余额保全记录成对提交；按已还选择修正本金基准（不改变账户余额）；保存当时实际确认的本金及期次版本，撤回使用原确认金额；计划修订不改历史事实。叠加有效实际借还校验完整本金时间线；已有交易/覆盖优先；保存后停用旧自动模式 | 可信 uid、贷款版本与唯一收费键兜底；失败全回滚，未保存复选框无账务效果；旧确认缺少可证明金额时保留原状态并提示待核对，不按现计划回填 |
| 旧进度接口、调费、删除或终止 | 旧单期/批量进度仅对尚未接入新流程的贷款兼容；已接入者拒绝绕过本金与费用事实，普通界面使用合并保存。调费/抑制/恢复先签名预览；实退独立退款，终止仅暂停/取消未来计划 | 版本及付款/退款/来源/覆盖依赖在执行时复查；抑制费不会被同步复活，旧请求只返旧回执 |

写事务复用现有可信用户锁，费用、正式交易、分配、审计、贷款版本、数据修订和成功回执共同提交。费用身份 `(uid, contract_id, charge_key)` 不随请求号、金额、方案版本或管理 loanId 改变；数据库唯一键承担并发兜底。原始来源与费用身份保持独立。

### 6.7 删除整笔贷款／分期与重新建立

详情底部“删除”针对整笔管理记录。先读取实际影响，只有一次确认：显示将撤销的放款、还款和费用数量，以及已有账目、已核实来源保留。未保存的已还选择不随删除提交。共享付款、外部退款或旧归属待核对时展示原因与原付款／账目入口，不自动拆分、不部分删除。

判断依据是原始创建归属和当前有效使用。计划独占新增、未被有效银行账单认领的放款、还款、利息和手续费撤销有效账务影响；费用和配套余额保全一起撤销，一次性覆盖多期只撤销父项一次。先独立存在、后来关联的手工／导入账目保留。计划新增账后来获有效银行来源认领时保留同一交易及必要余额保全；已有账经贷款流程更正过本息费时保留当前正确分项，不恢复更正前原账。原消费、账户、分类、文件及其他计划不动。无法安全分离的共享付款或独立退款阻止整次操作；无法证明旧创建归属提示待核对。

新命令 `loans.deleteImpact/delete` 在原用户锁、版本和幂等事务内统一复核并执行，保存必要审计与删除快照，解除有效付款、期次、来源和编号占用，停止旧自动记费；任一步失败全部回滚。保留费用只沿用仍有效的人工历史确认、完整保留付款及原资产实付依据；已撤销付款不转成历史已还，部分付款、覆盖父子项和退款分别核算。被撤销交易保留系统历史，退出余额与统计。已删除计划不能普通写入或恢复，原成功请求只返回原结果。旧客户端 `archiveInstallment` 仍只归档和解除管理关联，不撤销账务；普通永久删账规则保持原行为。

旧归档不会因升级自动变成整组撤销。维护时，用户可逐笔明确确认旧逐期费用由该计划新增，预览和删除携带相同的 `reviewedCreations` 与交易版本；普通页面不自动提交此确认。仅接受创建归属为NULL、有原逐期收费审计且没有独立创建、银行来源、付款交易或合同改绑证据的费用；已知归属不能覆盖。预览仍只读，确认记录及审计与整组撤销同一事务提交或回滚，共享、退款、来源及版本保护照常生效。

重建必须使用新 loanId。只有经过核验的稳定来源身份或用户明确选择原费用合同才复用关系；无依据的新分期建立独立合同，同账户旧合同不阻止确认历史或还款，金额／日期相似不构成身份。`plan_removed_at` 只标记随整组删除撤销的费用，明确重建可再次记入；用户单独抑制／取消的项不会复活。保留账目可查看和维护；原费用从账目详情进入“维护费用／实际退费”，也可明确关联到新计划。贷款列表仅在有保留费用时显示入口，继续使用原费用详情和重建页面。原完整付款通过已有账目入口复用，按原交易ID、版本及删除快照核验；普通负债还款沿用原明确本息费，任意转账不猜作还款。目标计划已有历史本金时须选择对应期次，只替换历史覆盖，不重复冲减。删除阻断中的 transactionId 直达会按当前用户读取指定账目，失效记录显示错误，受保护账目保持只读，不依赖全局旧对象。删除成功而列表刷新失败显示“已删除，列表待刷新”，重试只读列表；结果未知先核实原请求。

实现：[完整范围](../cloudfunctions/catledger-api/src/loan-deletion-scope.js)、[原子执行](../cloudfunctions/catledger-api/src/loan-deletion-service.js)、[创建归属](../cloudfunctions/catledger-api/src/transaction-provenance.js)、[原付款复用](../cloudfunctions/catledger-api/src/loan-payment-reuse.js)。验证：[真实接口与隔离MySQL](../test/loan-deletion-db.test.js)、[真实Page与恢复](../test/loan-deletion-ui-db.test.js)。

## 7. 已入账之后：当前界面与后台能力分开

### 7.1 当前用户入口

明细点哪笔就编辑哪笔。手工交易按现有规则编辑，导入交易普通编辑主要改分类，不任意改来源金额/账户。支出改分类同步关联退款；不重写原文或偷偷学成持久映射。

普通手工与导入账目支持单笔或混选永久删除。只确认一次：“永久删除所选账目，不可恢复。余额和统计将更新。”全选覆盖筛选全部而非当前页，分页未完成不标全选。冻结 ID、版本及请求号，在可信用户锁内检查完整退款组、贷款/费用历史引用和整组现金变化。同一来源的组合付款/多目标还款分配共用来源身份，须在明细显式选中全部当前有效分配后删除；不完整选择整组拒绝，不能留下会拦截重导的半组。可分块但只提交一个事务，冲突或任一步异常全部回滚，不跳过或扩大选择。

通过校验后，解除被删交易的专属事件链接与核对候选；普通旧软删除退款仅解除对原消费的引用，保留其历史行；先删所选退款再物理删除其余正式交易。账户、分类、共享来源、文件、映射及“当时导入成功”的事实保留。旧事件只记集合变化原因，防止更正/撤销误用残余集合；不保存用于恢复的账目副本。数据修订和最小请求回执共同提交；响应丢失核实原回执，后来重新添加的账目不会被旧请求再删。成功后读取失败显示“已删除，列表待刷新”。

没有回收站、恢复或永久忽略名单；误删可重新添加或主动重导。同文件可复用解析证据，但仍须走整理、账户确认、核对和入账校验；其他有效交易继续防重。旧草稿曾复用的交易已删除时，先要求重新核对，不静默恢复或永久排除。待关联退款补原消费仍检查身份、方向、时间与累计金额。贷款付款、费用和可恢复历史受保护，继续从贷款/分期详情处理，不能只删付款却保留本金冲减。实现：[普通永久删除](../cloudfunctions/catledger-api/src/transaction-permanent-delete.js)。

### 7.2 后台更正/撤销不是现行主入口

服务端保留 economicEvents.correctionImpact/correct、financeUpdates.undoImpact/undo 等；当前路由没有旧 import-maintenance 页面。

先预览，再锁内重算版本与 previewToken。系统更正、替换和整组撤销保持原有软删除及历史语义，保留 deleted_at 与查询过滤。只撤销本批 created，不能删 reused 历史交易；外部退款、贷款关系、现金、已被用户删除的原集合或无法证明的旧副作用可阻断。预览不是授权凭证。

详见[维护专题](现行说明/已入账账单维护.md)；入口：[finance-update-maintenance](../cloudfunctions/catledger-import/src/finance-update-maintenance.js)、[实际路由](../miniprogram/app.json)。

## 8. 读取、缓存与失败恢复

### 8.1 状态所有权

| 状态 | 主要负责人 |
| --- | --- |
| 正式业务事实、身份、版本 | MySQL 与服务端命令事务 |
| 普通内存读取、去重、失效和写屏障 | read-cache 等服务 |
| 最近完整展示的有限快照 | read-snapshot-store，不是离线权威账本 |
| 导入摘要版本、游标、页缓存 | import-view-session |
| 首次整理 prepare 原请求与尚未确认写入 | pending-ledger-write，按环境和用户隔离 |
| 已有批次核对队列、配对范围/例外与续批进度、requestId、postFlight、最近批次指针 | import-draft-session |
| 页面活动、局部令牌、弹层和显示 | 显式 runtime 与操作流程 |

读取复用有效结果，必要时校验或联网；写屏障和修订使旧结果失效。内存命中不等于无派生/setData，不能看到慢就加缓存。导入摘要加分页，原始全集不放 Page.data；原文有界分段，失败单项重试。

### 8.2 读可失效，写不能被当作没发生

| 场景 | 正确处理 |
| --- | --- |
| 切批次/翻页/关弹层后旧读返回 | 拒绝回填 |
| 编辑中后台更新 | 延后，不覆盖输入 |
| 隐藏/卸载，写未发 | 不继续旧提交 |
| 写已发后离开 | 保留原请求核实，旧回执不回填 |
| 写成功摘要失败 | 保留成功，只提示明细待刷新 |
| 超时结果未知 | 原键核实/重试，不换键记第二次 |
| 首次整理响应丢失 | 原 prepare 查询/重放取回 updateId，不新建批次；成功后只读刷新 |
| 明确放弃/重新开始 | 终止首次恢复意图，不删除未确认写请求 |
| 普通隐藏返回 | 可正常恢复，不当明确放弃 |

页面活动 _viewEpoch 与列表 _pageEpoch 已分离；正常换版不取消合法提交，旧 finally 不解锁新操作，第四步无列表也结束刷新。费用同步复用这些原则，缓存校验或旧回调不会重复写费。

入口：[runtime](../miniprogram/pages/import-workbench/runtime.js)、[posting-flow](../miniprogram/pages/import-workbench/posting-flow.js)、[read-cache](../miniprogram/services/read-cache.js)、[view-session](../miniprogram/services/import-view-session.js)、[draft-session](../miniprogram/services/import-draft-session.js)。回归：[异步审核](../test/import-async-review.test.js)、[首次恢复](../test/import-initial-recovery.test.js)。

## 9. 数据生命周期与规则升级

原件按私有存储保留/清理规则处理；结构化来源、身份、正式账目和审计分别保存。普通用户永久删账只物理删除所选正式交易及专属关系，不删除共享证据、整份文件或整批历史。系统内部软删除历史、既有软删除数据、审计与数据库备份不在本次清理范围；不新增定时清理、归档搬迁或 OPTIMIZE TABLE，空间复用交给 MySQL，不承诺磁盘或费用立即下降。

个人导出 start → page → finish 形成一致版本 JSONL 或交易CSV。期间写入改变账本则旧任务失效重做；半文件不叫完整导出。用户主动分享，副本由用户管理；隔离库恢复验证不等于产品已有生产恢复按钮。

规则按解析器、profile、语义与计划各自版本升级。旧未入账计划保护人工决定；已入账事实不因换规则被偷偷改写。MySQL 显式迁移向前且可重入，不能为回退删账本/审计。贷款历史补记要有授权，0026、0027 不在旧数据迁移中生成费用或默认授权。

详见[数据生命周期](现行说明/数据生命周期.md)、[开发与验证](开发与验证.md)。版本入口：[domain-versions](../cloudfunctions/catledger-import/src/domain-versions.js)、[迁移](../migrations)、[导出清单](../cloudfunctions/catledger-api/src/export-manifest.json)。

## 10. 用四个例子串起来

**同一笔100元消费同时出现在支付宝和银行账单。** 各保留原文与身份；强关联或人工确认后只记应有消费，同额同日不能直接合并，入账前再查历史。

**30元退款没有明确原消费。** 识别为退款而非收入；有候选就核对，无候选可待关联。真实到账与支出冲减分开，不凭空找一笔同额消费。

**贷款示例：首次导入第6期，后来才导入第8期。** 创建时将账单放在第6期，前面期次默认勾选已还，保存时补齐所选期次利息、保留当前余额。第8期到来时询问尚未选择的第7、8期，已明确未还的不覆盖；第9期以后没文件，就点该行记还款。后传同费只核对，不重复支出。

**入账时断网。** 保留原 postFlight/requestId，核实已成功则展示成功，需重试仍用原键，不因没有明细再新建入账命令。

以上金额为合成示例，不是用户真实账目。

## 11. 问题先查哪一层

| 现象 | 先检查 |
| --- | --- |
| 文件/列不能识别 | 模板、映射、格式、原始观测与单文件错误 |
| 有金额仍不能入账 | 语义、端点、分项、归宿与阻塞 |
| 补分类仍阻塞 | 分类不是其他阻断的替代品 |
| 重复或同额记录消失 | 身份、强弱证据、人工决定、历史版本 |
| 导入后没有贷款 | 当前特例、正式来源与唯一归属，查待建立来源 |
| 账单期号变已还 | 核对运行版本、schema2旧进度待确认记录与人工/实际付款依据；docs已移除来源最大期号推进已还，云端仍待发布 |
| 无文件如何记费 | 逐期保存、历史余额保全、同费复用与部署状态 |
