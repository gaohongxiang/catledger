# 招财猫记账本入账逻辑说明

> 用途：帮助理解招财猫记账本从账单文件到正式账本、再到统计与资金决策的完整逻辑。
>
> 性质：通俗理解稿，不替代[用户需求](./招财猫记账本用户需求.md)、[业务规则与验收](./招财猫记账本业务规则与验收.md)、[架构设计](./招财猫记账本架构设计.md)和[实施规划](./招财猫记账本实施规划.md)；发生冲突时，以这些正式文档以及代码、迁移和自动测试为准。
>
> 当前状态（2026-09-06）：账单导入云函数已部署本轮信用免押语义分层和旧批次保留升级，小程序开发版已上传 0.4.28，组合分项 v2 的全部金额、差额联动与零金额记录已部署；当前计划版本 `organizer-plan-v27`、支付宝策略 `alipay-semantic-policy-v4`。保存状态、组合支付资金卡和分类可跳过规则已完成本地与原生验证。迁移 0009/0010 已在开发云应用，分项退款、完整真机验收和主线集成仍未完成。上传不等于正式审核发布；部署与测试证据以[实施规划第 22 章](./招财猫记账本实施规划.md)为准。

## 0. 当前账单导入权威执行口径

本节是当前支付宝、微信账单导入的首要验收口径。当前本地代码规则版本为 `source-action-v3`、`organizer-plan-v27`、`alipay-semantic-policy-v4`、`source-funds-v8`、`review-issue-v11`、`category-alias-v1`、`repayment-allocation-v2`、`refund-relation-state-v1`、`refund-link-v1`。后文负责解释原因和数据模型；若旧状态文字或示例与本节冲突，以本节、当前代码和自动测试共同验证的结果为准，当前部署状态以文首及实施规划为准，第 11 节的带日期记录为历史快照。无尾号银行建议、同层证据和展示转换的逐条审核规则见第 6.4.1～6.4.7 节。

### 0.1 用户看到的四步和系统实际动作

| 页面步骤 | 系统实际动作 | 会不会写正式账本 | 用户可以做什么 |
| --- | --- | --- | --- |
| 1. 解析 | 选择 1～5 份文件；五份可同时执行各自的上传→解析流水线；形成不可变原始行和解析批次 | 不会 | 追加、删除、逐份重试；成功文件不因其他文件失败而丢失 |
| 2. 账户 | 将支付方式候选对应到已有账户、本批新账户草稿，或选择不计入 | 不会 | 随时回看和修改；这里只保存 FinanceUpdate 内草稿 |
| 3. 整理 | 服务端先自动处理明确记录，只展示仍需用户决定的 ReviewIssue | 不会 | 处理待整理项，查看原始记录；返回账户步骤修改后由服务端重算 |
| 4. 入账 | 重新校验全部事件，在一个数据库事务中创建账户、提升映射、写交易和证据链接 | 会 | 明确点击“确认整批入账”；成功前可放弃整批 |

“解析完成”表示文件已经读懂，不表示所有经济关系都能自动确定；“整理”不是再解析一遍，而是处理退款对应、重复候选、未知资金端等必须由人裁决的业务事实。普通且确定的记录不出现在整理页。

### 0.2 文件、失败、重试和重新解析

1. 单份文件不超过 5 MiB、规范化记录不超过 5000 条；当前支持支付宝和微信导出的 CSV、XLSX，来源由服务端读取正文和表头判定，不相信文件名。
2. 每份文件有自己的 `准备中 → 上传中 → 解析中 → 解析完成/解析失败/已入账` 状态。文件区域尺寸保持稳定，只更新行内状态、进度和错误，不通过跳页或整体替换制造页面跳动。
3. “开始解析”点击后原位变为“解析中”并显示旋转状态；按钮在任务结束前不可重复点击。当前最多五份文件并发执行各自的“上传→解析”流水线，不要求所有上传完成后再串行解析。
4. 每份上传任务独立收口。明确的瞬时网络错误或超时最多尝试三次，退避间隔逐次增加；Android 微信若只触发上传 `complete` 回调，也必须按 `fileID` 成功收口。没有任何回调时，每次尝试到期都会中止该 UploadTask，最终落为该文件失败，不能让整页永久停在“解析中”。
5. 一份失败不阻塞其他成功文件。失败行显示可读错误和“重试/删除”；重试只处理该文件，不重传、重算其他成功文件。至少一份成功即可继续，全部失败才禁用下一步。
6. 同一内容从未正式入账时，明确重新上传代表“重新开始”，不是“恢复进度”：服务端直接放弃占用该来源的旧未入账 FinanceUpdate，复用原不可变解析批次，并在用户继续后建立新的 FinanceUpdate 和整理计划。旧更新只改为 `abandoned`；它的资金方向、账户草稿和待整理决定不得继承到新更新，也不得改变正式账户、交易、余额或统计。
7. 只有来源已经随正式交易成功提交，才显示“已经入账，不会再次创建交易”。数据库里出现过文件摘要不等于已经入账。
8. 用户只是返回页面或重新打开同一个工作台、且客户端仍持有原 `updateId` 时，才调用 `financeUpdates.get` 恢复该 FinanceUpdate；若它的 `planVersion` 落后于当前规则版本，则通过服务端组织入口升级；当前 v26 → v27 原位刷新系统语义，保留已确认决定，不删除事件重建。这个“继续处理”路径和第 6 条“明确重新上传”路径不得混用。
9. 上传和正文解析当前确实会执行；持久化前发现内容摘要相同时，才裁决是否复用规范来源。`reused_unposted / replaced_unposted_update` 是服务端内部裁决，不要求用户理解；只要未正式入账，文件行仍以普通“解析完成”收口，系统必须在后台保证新整理不继承旧资金方向、账户草稿和待整理决定。

#### 0.2.1 三个主要按钮的精确执行过程

| 用户动作 | 客户端请求 | 服务端事务和计算 | 返回与恢复 | 明确不做的事 |
| --- | --- | --- | --- | --- |
| 点击“开始解析” | 先用一个 `imports.prepareMany` 为本次尚未准备的 1～5 份文件取得私有随机路径；随后最多 5 条“上传→`imports.parseFile`”流水线并行运行 | `prepareMany` 在一个幂等事务中一次建立全部待上传文件记录；文件正文经私有存储上传后，每个 `parseFile` 独立下载、探测格式、解析，并在自己的幂等事务中写摘要、批次和不可变原始行 | 每份文件独立成功、失败和重试；`prepareMany`、`parseFile` 遇明确瞬时故障时沿用原 `requestId` 恢复一次，上传通道最多尝试三次 | 不创建 FinanceUpdate；不生成账户草稿；不写正式账户、映射或交易；一份失败不回滚其他文件 |
| 点击“下一步：确认账户” | 若当前页面已有 `updateId`，只调用 `financeUpdates.get` 恢复；首次进入时只调用一次 `financeUpdates.prepare` | `financeUpdates.prepare` 在同一个幂等 MySQL 事务中锁定成功批次、建立一个 FinanceUpdate、冻结来源、生成 Event / Evidence / Relation / ReviewIssue 和完整初始视图；不再由客户端先 `create` 再 `organize` | 首次请求成功但响应丢失时，相同 `requestId` 返回已提交结果；已有旧规则计划时，恢复路径才调用一次 `financeUpdates.organize`；v26 → v27 原位升级，保留事件与人工决定 | 不把“返回页面”误当成新批次；不产生 create 成功、organize 响应丢失的半流程；不写正式账本 |
| 点击“确认此账户” | 客户端先校验名称和选择，只把当前 open 或确实改动过的目标账户组放进一个 `reviewIssues.resolveAccountMappings` | 服务端在一个幂等 MySQL 事务中锁定 Update 一次、按稳定顺序锁定 Issue、建立一条批次 FinanceAction、应用全部账户/忽略草稿和事件版本；批内共用并即时更新一份支付映射索引。全部决定完成后，只重算直接受影响或引用同一支付工具键的资金投影，再统一计数并生成一次完整视图 | 任一项冲突或 SQL 失败，整个账户批次回滚；响应丢失时相同 `requestId` 返回同一结果。错误恢复只额外读取服务端当前视图，不重复提交另一套决定 | 同组成员不逐笔开启事务；不为同组每条记录全量重算、全量计数或返回完整视图；不提前创建正式账户；不影响最终整批 posting 的事务边界 |

因此三个按钮没有重复执行同一业务阶段：解析只建立来源事实；下一步只建立一次未入账整理工作区；账户确认只修改该工作区内的草稿和事件。唯一允许的重复是带同一幂等键的故障恢复，它返回首次已提交结果，不会再次产生文件、FinanceUpdate、动作、账户草稿或交易。

入口请求与领域动作使用两层幂等范围：`catledger_mutation_receipts` 以“用户 + 客户端 requestId”保证同一次接口请求可以安全重放；`FinanceAction` 以“用户 + FinanceUpdate + 动作类型 + 动作请求”保证同一个更新内不会重复执行领域动作。`FinanceAction` 的唯一键必须包含 `updateId`，不能只按用户和批次内容去重。用户明确重新上传同一内容、旧 FinanceUpdate 被放弃后，新 FinanceUpdate 可以复用不可变 ImportBatch，但必须建立自己的 Event、Issue 和 Action；旧更新的动作审计不得与新更新撞键，也不得被新更新复用。

### 0.3 原始记录永远保留在哪里

一条外部账单行依次形成以下对象，职责不能混用：

```text
ImportFile（来源文件和内容摘要）
  → ImportBatch（某版解析结果）
    → ImportRow.raw_fields_json（不可变原始字段）
      → Evidence（该原始行在经济事件中的证据角色）
        → EconomicEvent（系统整理出的经济事实）
          → Transaction（最终正式账本交易）
```

- 原始字段、文件名、原始行号、来源定位符、解析器版本和快照版本保存在原始证据层，不因账户修改、退款关联、排除或重复合并而改写。
- 整理列表只显示轻量摘要；打开待整理详情即在同一滚动区显示交易与原始证据，不再要求二次点击。账户步骤通过“查看 N 笔”打开同层记录面板。客户端调用只读 `economicEvents.evidence(eventId)`；服务端先校验可信身份与事件归属，再从事件证据、原始行及批次来源读取全部证据。分页、候选隔离、错误恢复及字段转换见第 6.4.5～6.4.6 节。
- 合并重复只改变 Evidence 角色，不删除原始行；本次不计入也保留证据；普通列表和日志不展示完整原文，避免把敏感账单内容扩散到错误响应或日志。

### 0.4 支付工具怎样变成账户候选

1. 原文先完整保留，再对候选副本执行全角转半角、NFKC、空白收敛和控制字符清理。实现不得依赖部分安卓 WebView 不支持的 Unicode 属性正则；中文、英文字母、数字及原文中合理的日文、韩文字符都可作为账户名文本保留，平台规则不因微信运行于 Android 或 iOS 而分叉。
2. 原文含 `&` 时按金融成分和已认证优惠成分拆分；只有唯一金融成分才形成单一资金账户，多个金融成分分别确认账户及金额，不默认取第一段。例如 `光大银行信用卡(2690)&两轮充电券` 的账户候选是 `光大银行信用卡(2690)`。
3. 连续长数字在普通界面只保留尾四位；完整原文只存在受保护证据中。
4. 账户候选必须先明确归属方。支付宝自有工具统一使用 `支付宝账户余额`、`支付宝余额宝`、`支付宝花呗`、`支付宝借呗`、`支付宝信用购`、`支付宝小荷包…`；微信自有工具统一使用 `微信零钱`、`微信零钱通`、`微信亲属卡…`。原文已经包含归属前缀时不重复添加。
5. 银行或机构名称已经明确时保留机构全名，例如 `光大银行信用卡(2690)`；不得再加成 `支付宝光大银行…` 或 `微信光大银行…`。只有来源自己的通用账户名才补来源前缀。
6. `余额`、`账户余额` 在支付宝来源下使用同一个稳定键并显示为 `支付宝账户余额`；`余额宝` 使用独立稳定键，显示为 `支付宝余额宝`，二者不得合并。微信的 `零钱` 和 `零钱通` 也使用不同稳定键，二者不得合并。
7. `银行卡`、`信用卡`、`其他`、空值等泛称没有足够身份信息，不生成可复用映射键；系统不得只凭账户类型猜具体账户。
8. 历史账户映射只是一条可修改的账户建议，不是不可推翻的事实。只有映射指向当前用户仍存在的账户，且支付工具可确定的强类型与账户类型兼容时才允许沿用；例如平台余额只能映射到平台钱包，不能静默映射到现金账户。强类型冲突时必须忽略该历史映射并重新要求确认。旧键版本的规则保留原键，同时从稳定提示派生低优先级当前键别名；新版精确键、本批选择和事件手工选择均可覆盖该兼容候选，别名冲突时不得猜测。
9. 没有可用映射时，服务端先用带归属前缀的规范全名与当前用户的 CNY 活动账户做唯一精确匹配。唯一完全同名时可以建议沿用；零命中或多命中时不得猜测。银行主体与尾号、去平台前缀等近似匹配只可在界面给推荐，仍需用户确认；不同银行同尾号、币种不符或最高分并列时不得推荐。
10. 账户步骤必须展示本批出现的每一个稳定账户候选，包括唯一同名命中、有效历史映射和本批账户草稿；已匹配项可以预选，但用户仍可修改。不得把被自动匹配的账户从列表隐藏，否则用户无法发现和纠正旧映射。界面显示数量必须与候选项实际数量一致。
11. 当前 FinanceUpdate 内刚确认的账户草稿立即参与同批后续重算，因此先确认 `光大银行信用卡(2690)` 后，本批其他相同稳定键必须沿用，不得再次显示“创建新账户”。

### 0.5 支付宝、微信资金动作逐项规则

`row-semantic-resolver` 是统一入口：Source Profile 解释字段角色、候选动作和生命周期，再输出 `sourceAction / moneyEffect / settlement / fromAccountRef / toAccountRef / ruleIds / issues`。解析、事件整理、账户分组、覆盖检查和入账校验共用这个结果；前端只读服务端经济性质和资金引用，不再扫描商品或商户猜还款。

判定分为以下层次，同层强证据冲突时阻断，不能取先匹配的一条：

1. 先识别字段角色：支付宝 App 的 `交易分类` 是 `category`；支付宝 Web 的 `类型` 和微信交易类型是 `action`。分类背景不能直接等同于借款、还款等动作。
2. 收集严格来源规则给出的手续费、退款、收益、理财流转、充值、提现、借款、还款及转账动作；同值合并依据，异值保留 `row_semantic_conflict`。普通商品中出现动作词不能覆盖服务用途。
3. 没有强动作时，App 的非空普通分类依据明确 `income / expense` 得到收入／支出，不依赖逐项扩充消费分类白名单。`账户存取 / 不计收支 / 理财 / 投资理财 / transfer` 等金融专用域仍需明确动作；Web 和微信动作字段继续按已登记协议解释。小荷包中性方向消费仍须严格满足已认证分类、账户、成功状态和正金额组合。
4. 独立判断生命周期和到账状态：零元、中性方向、`信用借还` 且精确 `芝麻免押下单成功 / 解冻成功` 属于非资金记录；失败和关闭不入账。还款成功、退款成功、提现到账等专属状态必须与动作兼容，未知状态和不明零元记录保留阻断。
5. 仅对实际资金效果解析账户端点，再由同一结构化动作决定经济性质。明确转账才询问双端账户；多金融付款成分没有分项金额时继续阻断，不能因性质已知而略过确认。

信用免押租借的服务使用费（如充电宝、雨伞或设备租赁）在明确支出且成功扣收时记为支出，不把信用分免押当作借款；零元免押授权和解冻按上述生命周期处理。`信用借还` 下明确还款／借入文字仍按债务动作；已识别消费信贷账户的账单付款同样为还款，目标引用由服务端产生。该规则不依赖特定商户、金额或商品名单。


普通收入或支出只有一个属于用户的账本账户；商户、朋友、平台商家等外部交易对方只保留为交易对方证据，不进入账户选择器。只有证据明确证明资金在用户自己的两个账户之间移动时，才建立内部转账并显示“转出账户 / 转入账户”。页面不得使用含义不清的“账本账户 / 对方账户”代替资金方向。

| 场景 | 经济性质 | 转出端 | 转入端 | 自动与人工边界 |
| --- | --- | --- | --- | --- |
| 支付宝余额宝转出 | 本人转账 | `支付宝余额宝` | 行内明确到账方式；缺省为 `支付宝账户余额` | 两端均有唯一映射则自动；只缺哪端就只问哪端 |
| 支付宝余额宝转入 | 本人转账 | 行内明确付款方式；缺省为 `支付宝账户余额` | `支付宝余额宝` | 同上 |
| 支付宝提现 | 本人转账 | 原始支付方式明确为余额时是 `支付宝账户余额`，明确为余额宝时是 `支付宝余额宝`；只有严格官方提现且来源字段缺失时，才按该账单模板兜底为账户余额 | 行内明确银行卡或其他到账工具 | 不是把所有提现写死成余额；已有明确来源证据时不再询问转出端，银行卡无法唯一映射时只问转入账户 |
| 支付宝账户余额充值 | 本人转账 | 行内明确银行卡或其他付款工具 | 原始字段明确为余额，或严格官方账户存取动作的余额目标 | 只问无法唯一确定的一端 |
| 支付宝明确还款 | 还款 | 行内付款方式 | 明确的信用卡或消费信贷目标 | 目标只是泛称时人工确认；两端明确且唯一时自动 |
| 支付宝普通消费/收款/向他人转账 | 普通支出或收入 | 按收支方向使用该行支付账户 | 不制造第二个自有账户 | 不显示双账户确认；只有业务性质本身冲突才进整理 |
| 微信零钱充值 | 本人转账 | 行内付款方式 | `微信零钱` | 两端唯一则自动，否则只问缺失端 |
| 微信零钱提现 | 本人转账 | `微信零钱` | 行内到账方式 | 同上 |
| 微信信用卡还款 | 还款 | 行内付款方式；`零钱`即确定为`微信零钱` | 只在银行主体和卡尾号等稳定身份同时存在时确定信用卡目标 | 没有卡尾号时只问转入信用卡，不能反过来询问已明确的微信零钱 |
| 微信普通转账、红包、群收款 | 普通支出或收入 | 按账单方向归属支付账户 | 不因“转账”二字制造第二个自有账户 | 方向明确时按普通收支；证据冲突才进整理 |

必须通过的两个典型例子：

- `余额宝转出到余额`：`支付宝余额宝 → 支付宝账户余额`。两个账户已映射时自动整理，不出现手工确认。
- `07-06 支付宝账户余额提现到浙江农商联合银行`：原始记录同时给出“账户存取 / 提现-实时提现 / 支付方式=余额”，因此转出端由证据确定为支付宝账户余额。若银行记录没有尾号且不能唯一命中已有账户，只生成“转入账户待确认”；不得再次让用户选择已有明确证据的转出端。
- 支付宝提现行若“支付方式”列仍写 `余额`，而 `浙江农商联合银行` 出现在“交易对方”列，整理器必须从交易对方读取到账银行；不得把支付方式再次当成转入端，形成 `余额 → 余额` 或退化成双端未知。

### 0.6 双端账户解析和修改后的重算

| 当前解析结果 | 页面行为 | 用户提交内容 |
| --- | --- | --- |
| 转出、转入都已知且不是同一账户 | 不生成账户问题，继续检查其他业务条件 | 无 |
| 只缺转出端 | 标题“转出账户待确认”，转入端只读 | 只提交转出账户或账户草稿 |
| 只缺转入端 | 标题“转入账户待确认”，转出端只读 | 只提交转入账户或账户草稿 |
| 两端都缺 | 才显示两个账户选择器 | 分别提交两端；两端不得相同 |

资金端没有可靠默认值时，选择器初始必须显示“请选择”，不得默认取账户列表第一项，更不得把同一个现金账户同时填入转出和转入。转入/转出选择只列用户自己的正式账户和本批账户草稿，不列外部交易对方。

- 账户归属在正式入账前始终可修改。修改只写 FinanceUpdate 内草稿，不提前创建或修改正式账户。
- 来源账户未识别且尚无人工决定时，账户归属项默认显示“请选择账户归属”，保持未完成；不能默认新建账户。已有选择失效时也回到待选择，明确选择新建后才展开名称和类型输入。
- 待选择项在标题后使用橙色“待确认”文字标记，编辑行白底。选择器上方直接展示代表交易，完整原始记录独立可读；多笔组显示示例并可打开全部成员，按时间排序、每次显示 20 笔，核对后回到该组账户选择。查看证据不保存账户决定。
- 每次确认或修改映射后，服务端重新解析受影响的未入账事件；已不适用的 open Issue 变为 `superseded`，仍存在的问题按新事件版本重建。客户端不得仅隐藏卡片来假装已经解决。
- 用户手工确认过的一端有 manual field mask，自动重算不得覆盖。修改账户若会抹掉已完成的退款或关系裁决，服务端必须先报状态冲突并要求用户基于新版本处理。
- 转出、转入相同，币种不同，账户停用，账户不属于当前用户，或任一端仍未知时，事件不可入账。

#### 0.6.1 双端资金引用与账户映射的唯一口径

内部转账不能再把“一条事件”当成“一个待映射账户”。一条事件至少包含以下三类信息，职责必须分开：

| 信息 | 示例 | 用途 | 禁止用途 |
| --- | --- | --- | --- |
| 原始支付方式 | 微信提现行中的 `浙江农商联合银行储蓄卡(5564)` | 原始证据、来源动作判定的一个输入 | 不能直接假定它就是账本转出账户 |
| 资金投影 `from` | `微信零钱` | 表示这笔内部转账的转出资金工具 | 不能被 `to` 端选择覆盖 |
| 资金投影 `to` | `浙江农商联合银行储蓄卡(5564)` | 表示这笔内部转账的转入资金工具 | 不能被 `from` 端选择覆盖 |

每个来源中的精确账户引用使用 `sourceType + paymentMethodKey` 作为可追溯映射键；现实账户身份另由 `AccountIdentity` 负责跨引用归组，二者不能混为一个键。当前问题再携带 `fundsSide(from/to)`，明确该映射要写回事件哪一端。`account_mapping` 的成员角色使用 `mapping_from` 或 `mapping_to`；普通收入、支出的单账户事件才继续使用 `subject`。因此：

1. 同一事件两端都未归属时生成两个独立账户归属项；只缺一端时只生成该端的一项。
2. 页面标题、候选账户、默认建议和提交值都来自该成员自己的资金引用，不再从原始支付方式列反推方向。
3. 用户选择后，服务端先把账户写入该引用的 FinanceUpdate 映射草稿，再只写回对应的 `ledgerAccountId(from)` 或 `counterpartyLedgerAccountId(to)`；禁止把同一个选择复制到两端。
4. 批内后续事件通过完全相同的稳定引用复用本批映射；不同引用即使来自同一原始行也互不覆盖。
5. 全部账户决定完成后，服务端用最新映射索引定向重算受影响投影。两端均已知、币种一致且账户不同的内部转账直接 `ready`；不得再额外生成“资金流转待确认”。只剩一端未知时，整理页只显示那个未知端。
6. 投影重算可以替换过期的资金流转问题，但不得把尚未处理的另一个账户归属项误标为 `superseded`。
7. 仓储层必须返回历史和本批的全部候选事实，不负责选择赢家；否则被提前覆盖的候选无法参加类型校验或冲突检测。首次规划、账户确认后的增量重算、返回修改和最终入账只能调用同一裁决策略。

映射取值优先级固定为：`唯一规范全名推断 < 旧键兼容别名 < 当前键历史映射 < 当前 FinanceUpdate 的本批选择 < 本事件手工选择`。同一级存在两个不同结果时不能取“最后一条”，必须把整个现实账户身份退回一个待确认问题。

- 唯一规范全名推断只在当前账本中唯一、同币种、完全同名时生效，是最低级提示；它不能覆盖用户留下的任何有效决定。
- 历史映射用于减少重复选择，但必须通过账户存在、币种和强类型兼容校验；错误的“支付宝余额 → 现金账户”等历史记录不能覆盖本批事实。
- 本批选择是当前未入账工作区内的账户归属决定，相同稳定引用立即复用，并覆盖历史建议。
- 本事件手工选择只用于用户在整理阶段明确改动某个事件端点；它带 manual field mask，后续自动重算不得覆盖。

`organizer-plan-v23 / review-issue-v11` 在双端资金引用之上进一步建立三层唯一模型：`AccountIdentity` 表达现实账户，`PaymentReference` 表达某来源账单中的精确引用，`AccountDecisionGroup` 表达用户只需回答一次的账户问题。带银行主体和稳定尾号的同一银行卡可跨支付宝、微信等来源合为一个决策；平台余额、余额宝、花呗、微信零钱等必须按平台来源隔离；无尾号的银行卡泛称证据不足，也不得跨来源合并。`PaymentReference` 还明确区分可映射到现实账户的 `atomic` 与只代表来源合并口径的 `aggregate`，后者永远不生成账户身份或历史映射。`RefundRelationPolicy` 负责退款候选共同资格、证据分层、排序和自动确认条件，planner、详情、客户端、保存和 posting 共享同一冻结边界。零候选退款另由版本化的 `refund-relation-state-v1` 表达“用户确认暂记待关联”，不得靠空字段或提示文案猜状态。旧版未入账计划在恢复时由服务端声明需要升级，客户端不再复制规则版本；当前 v26 → v27 保留事件与人工决定原位更新系统语义；明确重新上传则放弃旧 FinanceUpdate，新计划不得继承旧事件字段或账户草稿。

### 0.7 什么自动整理，什么必须进入“待整理”

整理器先自动生成事件、关系和可入账状态。第三步“整理账单”分为 `交易核对 / 分类` 两个主 Tab。交易核对内部固定为 `待核对 / 已排除 / 重复记录`；退款、资金流转等按服务端安全分组显示问题卡。`category_assignment` 单独进入分类，其他问题仍在交易核对；核对中的必需问题阻塞入账，分类是可跳过的建议，未选分类保留 NULL。`已排除` 是按需下钻的审计视图，不平铺全部交易：先按明确领域原因显示“某账户已排除 / 交易已关闭 / 交易失败 / 已经入账 / 手动排除 / 其他排除”，每组默认收起，只有用户展开时才列出该组交易。账户归属步骤产生的排除必须写入 `account_mapping_excluded`，不能让客户端根据标题或文案猜原因。

| ReviewIssue | 什么时候出现 | 用户真正决定什么 | 能否批量共用决定 |
| --- | --- | --- | --- |
| `account_mapping` | 具体支付工具尚未归属 | 已有账户、新账户草稿、本次不计入或以后不计入 | 同一稳定支付工具可以 |
| `category_assignment` | 收入、支出或费用没有可靠分类 | 为冻结的同类事件选择一个同性质分类 | 仅同来源分类证据和同收支性质可以 |
| `shared_fields` | 一组安全同类事件共同缺少性质、分类等字段 | 补全缺失字段 | 仅同账户上下文、方向、性质和来源特征均一致时可以 |
| `same_event` | 不同来源疑似描述同一经济事件，但证据不足以自动合并 | 是同一笔或多笔独立记录 | 只限服务端给出的精确候选组 |
| `refund_relation` | 退款没有唯一可靠原消费、候选多于一个或累计退款超额 | 为这一笔退款选择原消费；零候选时可明确暂记待关联 | 不可以；每笔在列表中独立打开，保存后回列表 |
| `transfer_accounts` | 本人转账、还款等缺一端或两端账户 | 只补未知资金端 | 仅服务端判断为同一安全上下文时可以 |
| `identity_conflict` | 稳定来源编号相同但核心内容冲突 | 核对是否为独立记录 | 不按页面相似度批量 |
| `field_conflict` | 多份证据对同一事件的金额、方向、性质等描述冲突 | 裁决正式采用的字段 | 不按页面相似度批量 |
| `installment_origin` | 分期本金来源或组成缺少可靠证据 | 确认本金来源/组成 | 不可以 |

普通确定记录不要求逐笔点击“确认”。一张卡只要求一个真实决定，最多预览 3 笔；更多记录进入详情继续处理。每张卡都应展示轻量标题、原因、记录数、日期/来源/金额摘要，避免用大字号和多层重底色把文字堆到用户面前。

#### 0.7.1 分类可以跳过，选定后必须合法

1. `expense / fee` 必须使用支出分类，`income` 必须使用收入分类；本人转账、还款、借款、余额校正和退款自身不要求另选分类。退款通过原消费关系继承统计分类，不复制一份容易失真的退款分类。
2. 分类来源按固定顺序裁决：来源解析器的确定性分类规则 → 当前用户已经正式入账形成的来源分类映射 → 当前 FinanceUpdate 内用户选择 → 本事件手工选择。后一级覆盖前一级；同一级对同一来源别名出现冲突时不得取最后一条，必须退回人工确认。
3. 自动规则只处理已经验证的精确来源语义；宽泛的“消费”“付款”“其他”等文本不自动猜分类。未得到分类时保留 `category_required` 和非阻塞 `category_assignment`；其他必需条件齐全时为 `ready`，允许未分类入账。
4. `category_assignment` 只按“收支性质 + 来源类型 + 规范分类证据”安全分组。页面必须先显示“请选择分类”，不得把分类列表第一项当成用户决定；用户选定后，一次应用到服务端冻结的成员集合。
5. 分类选择只修改 FinanceUpdate 事件草稿并记录手工字段来源，不改写原始交易。最终 posting 重新校验分类存在、属于当前用户、未停用且性质匹配；任一成员不合法，整批回滚。
6. 只有整批入账成功，系统才在同一个 posting 事务中把本批无冲突的 `sourceType + categoryAliasKey` 提升为正式分类映射。放弃或入账失败不学习；同一别名在本批被选成多个分类时不提升，避免污染以后导入。
7. 正式账本中历史遗留的未分类收入/支出不要求重新上传文件。统计页按“收支性质 + 来源 + 分类证据”聚合待分类交易，用户选择分类后，`categories.assignTransactions` 用可信用户身份、交易版本和分类性质一次锁定并原子更新；同时只学习这组可追溯来源别名。
8. 已经归类的交易不会出现在待分类列表。补分类只改 `category_id` 和版本，不改金额、时间、账户、原交易关系或原始证据，因此余额不变化，分类统计立即重算。

整理弹层遵循主题色层级：证据摘要使用当前主题的弱强调色；“稍后处理”和“不计入本次账本”并排作为次要动作；“保存选择/确认”独占下一行、与上行左右边界一致并保持主题主色，不得缩成脱离操作区的居中窄按钮。原始交易详情不在标题旁放返回文字，内容列表下方使用一个全宽“返回处理”按钮。不得混入其他主题的灰绿底色。

### 0.8 重复记录的判断

1. 同一稳定来源身份（例如平台交易号在同一用户和来源命名空间内一致）可以自动归到同一经济事件。
2. 跨文件或跨来源只有在稳定编号、核心金额/币种/方向和业务关系兼容时，才能自动成为同一事件的多份 Evidence。
3. 只有同额、近时、相似商户或相似文案时，只能生成 `same_event` 候选，不能自动合并。
4. 用户确认是同一笔后，选择一份 primary，其余保留为 supporting/duplicate；原始记录仍可查看，不删除。
5. 用户确认是多笔独立记录后，各自保留为独立事件；后续同一旧版本提交必须因版本冲突被拒绝，防止重复裁决覆盖新状态。

### 0.9 退款关系的判断

1. 原消费行状态写“已退款/退款成功”时，该行仍是原支出证据，不能把原消费本身改成退款收入。
2. 真正资金回流的退款入账行才分类为 `refund`，并通过 `refund_of` 关联原消费。
3. 支付宝退款行即使原始“收/支”为“不计收支”，只要交易类型/状态明确表达真实退款到账，也投影为 `refund + inflow`；原始字段仍原样保存为 Evidence，不被改写。
4. `RefundRelationPolicy` 先执行共同资格：原消费必须是未排除的支出或手续费，币种一致，发生在退款之前且相隔不超过 180 天，原金额足以覆盖本次退款，并且账户或来源分组上下文兼容。
5. 通过共同资格后按强度分四层：同来源命名空间内共享稳定交易标识；原消费明确写出本次退款金额且同来源、同商户、相隔不超过 72 小时；同来源、同账户、同币种、同金额、72 小时内且规范化商品标题一致；同来源且同商户。商品标题规范化使用 Unicode NFKC、统一大小写和空白，并去除“退款”“全款交易”等来源业务前缀，但不做模糊语义猜测。只保留最高的非空层，低层候选不得混入高层结果。
6. 只有前两层的唯一候选可以自动确认；“商品标题”与“同商户”即使唯一也只能进入人工核对。多个候选、关系失效或累计退款超额时进入 `refund_relation`。账户还未归属时先处理 `account_mapping`，因为退款共同资格依赖资金账户；账户确定后由同一 planner 定向重算关系，不允许客户端自己补候选。
7. planner 生成的 proposed `refund_of` 关系及其 ReviewIssue candidate 成员，是详情展示、客户端选择和服务端保存的唯一候选权威。详情不得追加近期消费，客户端不得合并额外选项，保存必须拒绝集合外事件。
8. 不得用“最近几笔金额足够大的消费”冒充候选；候选始终允许查看两边不可变的原始证据。
9. 零候选时不要求用户猜原消费。用户可明确选择“暂记待关联退款”，系统在 FinanceUpdate 内保存带版本、状态和确认来源的结构化领域状态；未经这一步的空关系退款仍然不能入账。
10. 待关联退款正式入账后只增加到账账户余额，不计普通收入，也不冲减未知原支出的月支出、分类、每日或趋势统计；交易列表明确返回 `refundLinkStatus=pending`。手工创建退款仍必须立即关联原支出，不共享这个导入出口。
11. 用户以后从交易明细关联原消费时，`transactions.linkRefund` 在一个幂等事务内锁定退款和原消费，验证当前用户、版本、退款仍未关联、原交易仍是有效支出、发生顺序、金额与累计退款上限；成功后补 `original_transaction_id`、继承原分类并写 `refund_original` 审计链接。该动作不再调整余额，因为退款到账在首次入账时已经记过；统计从此按已关联退款冲减原支出。
12. 整理页中的每笔退款是独立列表项，直接显示摘要、日期、来源、金额和候选状态；点击只处理这一笔，保存后回到列表，不自动打开下一笔。

### 0.10 “本次不计入”和“以后不计入”

| 选项 | 当前批次 | 下次识别到同一支付工具 | 何时形成正式规则 |
| --- | --- | --- | --- |
| 仅本次不计入 | 排除本 FinanceUpdate 的相关事件，保留证据 | 无影响 | 不形成正式规则 |
| 以后不计入 | 本次同样排除，并保存一份待提升的忽略草稿 | 自动排除匹配事件，并显示一条已按历史规则处理、无需再次确认但仍可修改的账户项 | 只有整批入账成功时与交易同事务生效 |

泛称或空值没有稳定键，只能“仅本次不计入”。历史忽略会自动排除匹配事件，但不是不可见过滤器，也不是锁定：账户步骤保留一条非阻塞、已确认且可修改的记录；若用户改选具体账户并成功入账，新账户映射覆盖旧忽略偏好。放弃或整批失败时，本次产生的忽略草稿不得留在正式规则中。

### 0.11 正式入账的硬门槛

同时满足以下条件，事件才可能进入最终事务：

- 金额为正整数分，时间、币种和经济性质合法；收入/支出有一个有效资金账户，本人转账/还款有两个不同且同币种的有效账户；
- 所有阻塞 ReviewIssue 已关闭，事件不是 `needs_action`，退款、重复、转账和还款关系有效；
- 账户、账户草稿、分类和关系全部属于当前用户，账户未停用；
- 同一来源身份没有已经生成另一笔正式交易；
- 整批写入后，原本非负的现金账户不得变负，历史遗留负数不得进一步降低。

用户点击“确认整批入账”后，正式账户物化、账户映射提升、交易写入、Event/Evidence/Relation 链接、状态和计数更新必须在一个 MySQL 事务中全部成功。任一项失败则全部回滚，不能出现“账户建了但交易没入”“交易成功但原始记录丢了”或“忽略规则生效但批次失败”。

### 0.12 明确禁止的错误实现

- 不得把“解析完成”理解为已经写入正式账本，也不得从账户步骤进入整理时再次解析文件。
- 不得把支付宝余额宝与支付宝账户余额合并；只能合并支付宝来源中的“余额”和“账户余额”。
- 不得在余额宝转出到余额、零钱充值/提现等两端明确且已有映射时继续要求人工确认。
- 不得在支付宝余额提现场景重新询问已知的支付宝转出端；银行卡不明确时只问转入端。
- 不得把普通微信转账一律当作本人账户互转。
- 不得让用户对已经命中“以后不计入”的稳定支付工具重复确认；也不得把自动排除结果完全隐藏或禁止改选账户。
- 不得在账户步骤提前创建正式账户，也不得因返回修改账户归属而抹掉已经完成的业务裁决。
- 不得只保留合并后的结果而丢弃原始行、重复证据或被排除证据。
- 不得依据文件摘要存在、页面隐藏或客户端传入的 `ready` 判断已经入账；正式交易和服务端 postability 才是权威事实。

## 1. 一句话原则

原文件不是账，解析结果也不是账。只有经过规则校验和用户确认、生成正式交易以后，才真正入账。

```text
账单文件
  ↓
保留原始证据
  ↓
解析成统一记录
  ↓
识别账户、重复和业务关系
  ↓
不确定项由用户确认
  ↓
整批原子生成正式交易
  ↓
正式交易计算余额、收支和净值
  ↓
未来计划、情景测算和 AI 只读解释
```

## 2. 完整逻辑分为六层

| 层级 | 通俗理解 | 是否改变余额 | 当前状态 |
| --- | --- | --- | --- |
| 1. 原始证据层 | 保存用户上传了什么、文件里原来写了什么 | 否 | 开发候选已实现，待真机闭环验收 |
| 2. 解析整理层 | 把支付宝、微信的不同格式翻译成统一记录 | 否 | 支付宝/微信开发候选已实现，银行模板待扩展 |
| 3. 身份与关系层 | 判断来自哪个账户、是否重复、是否为转账/还款/退款 | 否 | 当前规则版本已实现，复杂贷款关系待扩展 |
| 4. 待确认层 | 系统整理明确项目，用户只处理真正有歧义的项目 | 否 | ReviewIssue 开发候选已实现，待真机闭环验收 |
| 5. 正式入账层 | 用户确认后生成正式交易 | 是 | 手工入账已实现；导入原子入账开发候选已实现 |
| 6. 计算展示层 | 用正式交易计算余额、收支、净值和后续资金测算 | 只读 | 基础统计已实现；决策能力待实现 |

## 3. 第一层：原始证据层

这一层保存“系统到底读到了什么”，确保后续判断可以追溯。

### 原文件

用户上传的支付宝、微信账单，例如 CSV、Excel 或压缩包。

### 原始行

文件里未经业务改写的一条记录。原始行和系统整理出来的结果必须分开保存，解析规则升级也不能静默覆盖原始证据。

### 文件摘要

根据文件内容计算出的指纹，用来识别重复上传。文件相同可以复用安全的原始证据，但不能因此把文件中的不同物理行合并成一笔交易。

### 数据日期与证据定位

需要记录账单覆盖的日期范围，并让后续正式交易能够追溯到来源文件和原始行。

原始文件只在云存储保留上传、解析、重试和短期追溯所需的时间；超过保留期后删除文件正文，数据库保留必要的摘要、定位和审计关系。

## 4. 第二层：解析整理层

这一层把不同平台、不同格式的记录翻译成账本的统一表达。

解析不是“看到一列就直接写入正式交易”，而是分成三级：

```text
平台原字段
  ↓ 字段识别、保留原文
统一候选字段
  ↓ 金额、日期、方向、状态标准化
整理决定
  ↓ 账户映射、去重、关系判断、用户确认
正式交易字段
```

### 4.1 文件级字段

一份账单文件先产生文件级信息：

| 统一概念 | 通俗解释 | 用途 |
| --- | --- | --- |
| `sourceType` | 支付宝、微信支付或银行 | 选择对应解析器和身份命名空间 |
| `format` | CSV、XLS、XLSX 等具体格式 | 选择文件读取方式 |
| `statementStart` / `statementEnd` | 账单覆盖的起止时间 | 判断账期和数据是否过期 |
| 账单主体候选 | 谁导出了这份账单，例如某个支付宝或银行账户 | 建立来源档案，不直接决定资金从哪个账本账户流出 |
| `parserVersion` | 使用了哪一版文件解析规则 | 复现当时如何读文件 |
| `normalizationVersion` | 使用了哪一版标准化规则 | 复现当时如何解释字段 |

### 4.2 每一行的统一候选字段

无论来源平台是什么，每一行都先投影成同一组候选字段：

| 统一候选字段 | 通俗解释 | 是否直接成为正式交易字段 |
| --- | --- | --- |
| `transactionTimeRaw` | 来源文件中的交易时间原文 | 否；先转换成带时区的本地时间和 UTC 时间 |
| `amountRaw` | 来源文件中的金额原文 | 否；先转换成正的分单位金额 |
| `directionRaw` | 来源写的收入、支出或其他方向 | 否；只形成收入/支出/未知候选 |
| `statusRaw` | 成功、关闭、退款等来源状态 | 否；先判断是否产生真实经济影响 |
| `transactionTypeRaw` | 消费、转账、红包等来源业务类型 | 否；只作为关系判断线索 |
| `counterpartyRaw` | 交易对方 | 否；用于展示、分类和关系判断 |
| `itemRaw` | 商品或交易说明 | 否；用于展示、分类和关系判断 |
| `paymentMethodRaw` | 零钱、余额、银行卡、花呗等支付工具线索 | 否；先映射到账本账户 |
| `noteRaw` | 来源备注 | 否；保留证据后再生成展示备注 |
| `transactionIdRaw` | 平台交易号候选 | 否；用于来源身份和精确去重 |
| `orderIdRaw` | 平台订单号候选 | 否；用于来源身份和辅助核验 |
| `merchantOrderIdRaw` | 商户订单号候选 | 否；用于来源身份和辅助核验 |
| `sourceLocator` | CSV 行号或 Excel 工作表及行号 | 否；用于证据下钻 |

标准化后形成中性草稿：

```text
发生时间 + 时区
非负分单位金额 + 币种
收入 / 支出 / 未知方向
来源交易类型
正常 / 退款 / 无效 / 未知经济效果
规范化后的对方、商品、支付方式和备注
来源交易号、订单号和商户订单号候选
问题码和证据位置
```

“规范化记录”只是系统对原始行的结构化理解，不是正式交易，不能进入余额和统计。

金额统一按分保存为整数或十进制字符串，不能用 JavaScript 浮点数心算；日期需要保留交易本地日期、时间和时区信息。

下面的平台表头别名来自仓库归档 Web 版中已有解析器，并已在 MINI-1905 中以 Node.js 事件云函数重建。平台仍可能改变导出字段；当模板变化时，必须新增解析或标准化版本并用合成模板重新验收，不能静默改变旧批次的解释方式。

### 4.3 微信支付字段对应关系

微信 CSV/XLSX 不同版本可能使用不同表头，因此解析器按别名识别：

| 微信原字段或别名 | 统一候选字段 |
| --- | --- |
| `交易时间`、`交易日期` | `transactionTimeRaw` |
| `交易类型`、`业务类型` | `transactionTypeRaw` |
| `交易对方`、`交易对象`、`对方` | `counterpartyRaw` |
| `商品`、`商品说明`、`商品名称` | `itemRaw` |
| `收/支`、`收支`、`收支类型` | `directionRaw` |
| `金额(元)`、`交易金额(元)`、`金额` | `amountRaw` |
| `支付方式`、`付款方式` | `paymentMethodRaw` |
| `当前状态`、`交易状态`、`状态` | `statusRaw` |
| `交易单号`、`微信交易单号` | `transactionIdRaw` |
| `订单号` | `orderIdRaw` |
| `商户单号`、`商家单号` | `merchantOrderIdRaw` |
| `备注`、`交易备注` | `noteRaw` |

微信账单前言中的昵称最多只能作为账单主体的展示线索，不能当作稳定账户身份，也不能直接决定正式账本账户。

### 4.4 支付宝字段对应关系

支付宝 App 与网页导出字段不完全相同，需要分别识别后再投影到相同候选字段：

| 支付宝 App 常见字段 | 支付宝网页常见字段 | 统一候选字段 |
| --- | --- | --- |
| `交易时间` | `交易创建时间` | `transactionTimeRaw` |
| `交易分类`、`交易类型` | `类型`、`交易类型`（如存在） | `transactionTypeRaw` |
| `交易对方` | `交易对方` | `counterpartyRaw` |
| `商品说明` | `商品名称` | `itemRaw` |
| `金额` | `金额（元）` | `amountRaw` |
| `收/支` | `收/支` | `directionRaw` |
| `收/付款方式`、`付款方式`、`资金渠道` | 对应列如存在 | `paymentMethodRaw` |
| `交易状态` | `交易状态` | `statusRaw` |
| `备注` | `备注` | `noteRaw` |
| `交易订单号`、`支付宝交易号`、`交易号` | `交易号`、`支付宝交易号`、`交易订单号` | `transactionIdRaw` |
| `订单号` | `订单号` | `orderIdRaw` |
| `商家订单号`、`商户订单号` | `商户订单号`、`商家订单号` | `merchantOrderIdRaw` |

支付宝文件里的账号或掩码可以用于建立账单主体候选，但一行的实际资金账户仍要看 `paymentMethodRaw`。例如同一支付宝账单可以同时出现余额、银行卡和消费信贷，不能把整份支付宝账单机械映射成一个资金流出账户。

### 4.5 付款账户如何从原始文本变成候选

这一步必须同时满足两个目标：一是减少用户重复整理，二是绝不把系统候选冒充为用户决定。

付款账户有三个并行表达：

| 表达 | 内容 | 用途 |
| --- | --- | --- |
| 原始支付方式 | 账单中的完整原文 | 审计、下钻和规则回放，不被标准化覆盖 |
| 规范账户候选 | 页面用于分组和建议的安全显示名 | 让用户识别“这些钱经过哪个账户” |
| 版本化映射键 | 用来复用用户历史确认的不可逆摘要 | 后续相同支付工具可建议同一正式账户 |

规范化按以下顺序执行：

1. 保留 `paymentMethodRaw` 完整原文，不先删文字。
2. 对候选副本做 Unicode NFKC，收敛首尾空白和连续空白，把全角形态收敛到稳定形式。
3. 若原文含 `&`，按语义拆为金融／已认证优惠／未知成分。一个金融成分加优惠只使用唯一资金账户；多个金融成分分别建立账户引用、明确各自金额，不能取第一段代替整笔；未知成分保留阻断。
4. 安全显示时，连续长数字只保留尾四位，前面以 `****` 表示；控制字符不进入界面。原始证据仍按受保护字段保留，不进入普通日志。
5. 归一“末四位/后四位/尾号/卡号/主卡”等格式词和平台前缀，使同一工具的表达可稳定比较。
6. 先给平台自有工具补归属方，再统一账户身份：支付宝使用“支付宝账户余额 / 支付宝余额宝 / 支付宝花呗 / 支付宝借呗 / 支付宝信用购 / 支付宝小荷包…”；微信使用“微信零钱 / 微信零钱通 / 微信亲属卡…”。支付宝账单中的“余额”和“账户余额”归并为同一个账户候选“支付宝账户余额”并生成同一个版本化映射键；“余额宝”使用独立候选和独立键，不得与账户余额合并。银行主体已经出现在名称中时保留原机构全名，例如“光大银行信用卡(2690)”，不叠加支付宝或微信前缀。
7. 空值标记为“支付宝支付方式未标明”或“微信支付方式未标明”；“银行卡、信用卡、储蓄卡、未知、其他”等只说类别、没有具体身份的泛称显式标为“未识别具体账户”。这些项不生成可复用映射键。
8. 解析器本身不创建账户、不写正式交易。整理器可在当前用户活动账户中按“规范全名 + CNY”做唯一精确匹配；唯一完全同名时安全沿用该账户，并在账户步骤显示为“已确认、可修改”，不能因为它不再阻塞入账就从列表消失。没有完全同名、同名不唯一、币种不同或只有银行/尾号近似线索时，必须由用户选择已有账户或确认创建新账户。
9. 能生成稳定映射键的具体支付工具在账户步骤同时显示“仅本次不计入”和“以后不计入”。前者只排除当前 FinanceUpdate 中的相关事件，不形成复用规则；后者排除本次事件，并在最终整批入账成功时保存为历史忽略偏好。后续识别到同一支付工具时自动排除匹配事件，账户步骤显示非阻塞、已确认的“以后不计入”项，不要求重复保存；用户仍可选择已有账户或创建新账户覆盖它。忽略偏好与账户映射共用一条用户范围规则；空值和泛称没有稳定键，因此只显示“仅本次不计入”，不得显示后续选项。

例子：

| 原始支付方式 | 系统候选 | 是否可生成复用键 | 用户仍要做什么 |
| --- | --- | --- | --- |
| `光大银行信用卡(2690)&两轮充电券` | `光大银行信用卡(2690)` | 是 | 已有唯一同名账户则自动沿用；否则选已有卡账户、创建负债账户或忽略 |
| `余额` 或 `账户余额` 出现在支付宝账单 | 同一个候选 `支付宝账户余额` | 是，二者使用同一个映射键 | 已有唯一同名账户则自动沿用；否则只处理一次；不与余额宝合并 |
| `余额宝` 出现在支付宝账单 | `支付宝余额宝` | 是，使用独立映射键 | 单独选择或创建余额宝账户 |
| `零钱` 出现在微信账单 | `微信零钱` | 是 | 选已有平台钱包或确认创建 |
| `银行卡` | `支付宝 · 银行卡（未识别具体账户）` | 否 | 手工选已有账户、填名或忽略 |
| 空值 | `支付宝支付方式未标明` | 否 | 手工处理，系统不猜 |

金融成分决定资金账户，顺序不代表整笔主账户。组合支付使用版本化人工分项决定，改变来源解释时须升级策略并保留旧批次人工选择。

### 4.6 支付平台资金动作如何确定转出和转入账户

支付工具映射和资金动作投影是两层逻辑。`row-semantic-resolver` 先按来源字段角色、明确动作与生命周期生成结构化语义；`paymentMethodRaw` 给出该行明确出现的支付工具，是资金端判断的第一账户证据；`source-funds-v8` 消费统一账户引用，再结合交易对方，把结构化动作投影为转出、转入端。只有严格识别到官方账户存取动作而该端字段缺失时，来源专用模板才可兜底；微信外部转账收入在支付方式为空或 `/`、且原始状态明确“已存入零钱”时，可把微信零钱派生为单端账本账户。解析器、整理器和页面都不能再次用其他文案猜动作或方向。

每个结构化资金端包含：来源类型、版本化支付工具键、安全显示名和角色。事件只保存这组结构化引用及规则版本；原始全文仍在 `catledger_import_rows.raw_fields_json`，不会复制进事件或日志。账户引用优先级固定为“当前用户 CNY 活动账户的规范全名唯一精确命中 < 已发布历史映射 < 本批映射草稿 < 本事件用户手工端点”；右侧优先级更高。本批选择必须覆盖旧映射，事件上已经手工确认的端点又必须覆盖自动重算；旧映射绝不能把用户刚选的“支付宝账户余额”改回其他账户。零命中、多命中或仅近似命中时不产生 `account_id`。

这里没有“看见支付宝提现就把转出账户写死为支付宝账户余额”的通用代码。具体规则是：先读该行明确支付方式；`余额/账户余额` 得到支付宝账户余额，`余额宝` 得到支付宝余额宝，具体银行卡得到该银行卡。仅当动作被严格识别为支付宝官方提现、但来源端字段确实没有提供平台账户时，才根据该账单模板兜底到账户余额。其他交易仍按各自结构化动作处理，互不套用这个兜底。

#### 4.6.1 支付宝

| 来源证据 | 资金转出端 | 资金转入端 | 自动处理条件 | 缺失时询问 |
| --- | --- | --- | --- | --- |
| `余额宝-转出…`、明确“余额宝转出” | `支付宝余额宝` | 该行付款/到账方式；缺省时为 `支付宝账户余额` | 两端都已有映射且不是同一账户 | 只问缺失的一端 |
| `余额宝-转入…`、明确“转入余额宝” | 该行付款方式；缺省时为 `支付宝账户余额` | `支付宝余额宝` | 同上 | 只问缺失的一端 |
| 原始交易类型以`提现`开头，或`账户存取`且商品说明以`提现`开头 | 原始支付方式为余额/余额宝时使用该明确账户；严格官方动作缺少来源字段时才兜底为`支付宝账户余额` | 支付方式或交易对方中的明确到账工具 | 两端都能唯一映射 | 只问缺失的一端；没有卡尾号时绝不猜银行卡 |
| 原始交易类型以`充值`开头，或`账户存取`且商品说明以`充值`开头 | 支付方式或交易对方中的明确付款工具 | 原始字段明确的平台账户；严格官方动作缺少目标字段时才兜底为`支付宝账户余额` | 两端都能唯一映射 | 只问缺失的一端 |
| 明确还款 | 付款方式 | 账单明确给出的信用卡/消费信贷目标 | 目标可形成具体账户键且两端唯一 | 只问无法确定的一端；目标只是泛称时保留人工确认 |
| 普通消费、收款或转账给他人 | 按收支方向归属该行支付账户 | 不投影第二个自有账户 | 按普通收入/支出规则处理 | 不出现“确认两个资金账户” |

支付宝账户身份固定为：

- `余额` 与 `账户余额` 是同一账户键，展示名统一为 `支付宝账户余额`；
- `余额宝` 是另一账户键，展示名为 `支付宝余额宝`，永远不与账户余额合并；
- “余额宝转出到账户余额”因此是 `支付宝余额宝 → 支付宝账户余额`，两端已有映射时直接成为可入账事件，不再人工确认；
- “账户存取 / 提现-实时提现 / 支付方式=余额 / 交易对方=浙江农商联合银行”由支付方式证据把支付宝账户余额放在转出端。若银行名称没有足以唯一定位的尾号或既有映射，事件只生成“转入账户待确认”，不得把已有明确证据的支付宝端再次交给用户选择。
- 支付方式明确为`余额宝`的提现必须从`支付宝余额宝`转出，绝不能被通用提现规则改成账户余额；普通消费说明里的“商家提现优惠券”“话费充值活动”等文本仍按普通收支处理。

支付宝消费和还款还要区分“真实账户”和“合并账单名称”：

1. 普通付款记录明确写`花呗`时，产生原子引用和真实账户候选`支付宝花呗`；明确写`江苏银行信用购`等机构信用购时，产生另一原子引用并保留机构名称。两者可以分别记消费、分别形成余额，不因同属支付宝而合并。
2. 还款记录写`花呗｜信用购`、`花呗|信用购`等平台合并名称时，只生成 `aggregate / alipay_huabei_credit` 引用。它表达“这次还的是花呗与信用购合并账单”，不代表现实中存在第三个负债账户，因此不进入账户归属页、不创建账户草稿、不生成 `paymentMethodKey`，也不读写历史账户映射。
3. 该还款的转出端仍严格来自行内付款方式，例如`浙江农商联合银行储蓄卡(5564)`；合并名称只影响转入负债端，不能覆盖付款资产账户。
4. planner 从当前 FinanceUpdate 的原子账户引用中收集同渠道、同聚合族候选；`支付宝花呗｜信用购`只能得到本事件投影明确列出的`支付宝花呗`和各具体机构`信用购`。其他信用卡、其他平台消费信贷以及本批未参与该聚合族的负债账户都不属于候选，客户端不得自行追加。
5. 若本笔合并还款总额实际上全属于一个账户，用户在该账户填写全额即可；若同时归还多个账户，分别填写金额。界面只展示必要的负债账户和金额输入，不要求用户理解 AccountIdentity、aggregate 或交易投影。
6. 客户端先用十进制字符串把元转换成整数分并检查合计，不能使用浮点数；服务端重新验证 1～20 个分配项、UUID、正整数分、账户不重复、账户活动、币种为人民币、类型为`credit / other_liability`、不得等于转出账户、分配合计严格等于事件总额。v2 人工选择不要求属于本批候选；候选只供推荐，补选账户由可信目录校验资格，不自动推断产品成员关系或提升长期映射。旧 v1 已保存决定保留原候选限制，重新确认后写 v2；详见 ALLOC 规则。
7. 新确认的合法分配以 `repayment-allocation-v2` 写入事件的版本化 `field_sources_json`，同时留下手工字段位和 FinanceAction 审计；普通的单账户还款继续使用单一转入账户，不进入分配模式。
8. posting 对合并还款生成一笔或多笔正式内部转账：每笔都从同一付款资产账户转到一个真实负债账户，金额取对应分配项，并以 `repayment_allocation` 角色链接同一个 EconomicEvent。所有分配交易、账户草稿物化、映射提升、余额校验和事件状态仍在同一个 MySQL 事务内，任一失败全部回滚。
9. 重复导入判断把所有 `repayment_allocation` 链接视为同一事件已入账；整批撤销会覆盖该事件创建的全部分配交易。当前合并还款更正使用完整交易集合预览和原子替换，不能只改其中一笔；组合付款的分项单笔更正仍不支持，按维护页规则提示整批撤销。
10. 页面每次输入都用同一个金额草稿模型计算已分配、剩余或超出金额；分配合计少于或大于原始还款金额时，“保存选择”必须禁用，只有精确相等且至少存在一笔正数分配时才可提交。服务端仍调用同一领域规则复核正数、账户唯一、候选边界与金额守恒，不能把前端禁用当成安全边界。

#### 4.6.2 微信

| 来源证据 | 资金转出端 | 资金转入端 | 处理 |
| --- | --- | --- | --- |
| `零钱充值` 或明确余额充值 | 该行付款方式 | `微信零钱` | 两端唯一则自动整理，否则只问缺失端 |
| `零钱提现` 或明确余额提现 | `微信零钱` | 该行到账方式 | 同上 |
| `信用卡还款` | 该行付款方式；付款方式为`零钱`时固定投影为`微信零钱` | 交易对方中的信用卡目标 | 银行主体和卡尾号等稳定身份都存在且两端唯一时才自动整理；只有“兴业银行信用卡还款”而没有卡尾号时，保留“兴业银行信用卡”提示但不生成账户键，只询问转入端 |
| 普通微信转账、红包、群收款 | 不自动假设是本人账户互转 | 不凭文本制造第二个账户 | 按方向和普通收支证据处理；需要业务裁决时保留 ReviewIssue |

`微信零钱` 与 `微信零钱通` 是不同账户，不能因为都属于微信而合并。只有明确的零钱充值/提现等官方资金动作才使用双端投影；“转账”两个字本身不足以证明对方也是用户自己的账户。

#### 4.6.3 双端解析、单侧确认和重算

整理器按以下固定顺序处理：

1. `source-action-v2` 读取冻结的来源、原始交易类型、商品说明和收支方向，生成唯一结构化动作；解析、旧批次重建和整理不得各自维护另一套关键词。
2. `source-funds-v7` 读取该动作、支付方式和交易对方，产生 `from`、`to`；明确支付方式优先于动作兜底，没有严格动作就不产生双端投影。微信外部转账收入只有在支付方式为空或 `/` 且状态明确“已存入零钱”时，才派生单端微信零钱引用；其他斜杠记录保持未知。银行卡或信用卡只有机构泛称而没有尾号等稳定定位信息时，可以保留安全显示名和“身份不足”原因，但 `paymentMethodKey` 必须为空，不能伪装成已确定账户。合并还款目标可以产生 `aggregate` 引用和原子候选，但本身不产生账户键。
3. 映射优先级固定为：唯一规范全名建议 < 旧键兼容别名 < 类型兼容的当前键正式历史映射 < 当前 FinanceUpdate 的本批选择 < 当前整理项的手工选择。历史映射用于减少重复选择，但必须通过账户存在性和强类型兼容检查；`支付宝账户余额 → 现金账户` 这类冲突映射直接失效。所有实际采用的账户归属或历史忽略仍在账户步骤可见、可修改。草稿只在本批有效，最终入账成功前不写正式映射。
4. 两端都解析成功且账户不同：事件直接进入服务端 postability；其他字段和关系也完整时为 `ready`。
5. 只缺 `from`：生成“转出账户待确认”，界面显示已知转入端，只提交 `ledgerAccountId` 或对应账户草稿。
6. 只缺 `to`：生成“转入账户待确认”，界面显示已知转出端，只提交 `counterpartyLedgerAccountId` 或对应账户草稿。
7. 两端都缺失：才显示两个账户选择器；两端必须是不同、同币种、属于当前用户的活动账户或本批账户草稿。
8. 用户在账户步骤新增或修改映射后，服务端汇总本批直接变更的事件 ID 和支付工具引用，只重新计算直接受影响或引用同一支付工具键的未入账资金投影，不扫描并保存无关事件；受影响的旧 open Issue 变为 `superseded`，按新事件版本生成真正仍需处理的问题。客户端不得靠隐藏卡片假装问题已解决。
9. 用户手工选择的某一端用 manual field mask 保护，后续自动重算不得覆盖；返回修改账户归属时仍执行双版本 CAS，避免抹掉已完成的退款或关系决定。
10. 账户页点击确认时，客户端把当前点击的账户组决定提交给 `reviewIssues.resolveAccountMappings`，不再逐项携带一组会在处理中失效的 `updateVersion / issueVersion` 连续请求。服务端只在批次开始锁定 FinanceUpdate 一次，并按 `issueId` 稳定排序锁定全部目标 Issue，避免并发锁顺序不一致。
11. 批量账户确认本身就是一个幂等事务：只建立一条 `resolve_account_mappings` FinanceAction，在同一事务内完成全部 resolve / revise、账户草稿、映射草稿、事件版本和后续 Issue；任一项失败全部回滚。批内支付映射索引只读取一次，前一项刚写入的本批选择立即更新这份索引，后一项直接使用，不重复查询或套用旧历史映射。全部决定完成后只执行一次受影响投影重算、一次 Update 计数和一次完整视图读取。网络结果不确定时以同一请求号重放事务回执，不存在“前几项成功、后几项待继续”的部分状态。
12. 解析页已经持有 `updateId` 时，“下一步：确认账户”只能读取并恢复该 FinanceUpdate；不得再次创建更新。分离的 `financeUpdates.create` 已退出公共动作，首次创建和组织只能通过一个原子 `financeUpdates.prepare`。这样不会把一次返回页面或重复点击误判为新的整理批次，也不会再出现旧批次已存在导致的创建冲突。

任何转账、还款或充值/提现若最终两端相同、币种不一致、目标账户停用、证据规则冲突或仍有阻塞 Issue，都不能进入正式入账。

### 4.7 银行账单字段对应关系

银行之间没有统一表头，不能维护一张“所有银行通吃”的固定映射。首轮银行模板扩展应采用专用模板；通用 CSV/XLS/XLSX 只能在安全推断成功或用户明确确认列映射后解析。

通用银行映射至少需要确认：

| 银行列配置 | 统一候选字段或规则 |
| --- | --- |
| 交易日期/时间列及其格式 | `transactionTimeRaw` → 标准时间 |
| 单个带正负号金额列 | 正负号结合用户确认的“正数代表收入还是支出”得到金额和方向 |
| 金额列 + 收支方向列 | 金额进入 `amountRaw`，方向值字典进入 `directionRaw` |
| 分开的收入金额列和支出金额列 | 哪一列非空决定方向，两列同时有值则转待确认 |
| 币种列 | 必须与当前人民币账本一致，否则拒绝或待确认 |
| 交易流水号/订单号 | 对应三个来源编号候选 |
| 对方、摘要、用途、附言 | 分别映射到对方、商品/说明和备注候选 |
| 本方账号或卡号线索 | 只用于建立账单主体和账户映射；必须脱敏，不能进入普通日志 |

银行卡账单通常可以把文件级账单主体映射到一个账本银行卡账户，但仍需用户确认；信用卡账单映射到负债账户，不能因为存在信用额度就把额度当作可用资金。

### 4.8 从候选字段到正式交易不是一对一复制

最容易混淆的对应关系如下：

| 候选字段 | 真正作用 | 不能直接做什么 |
| --- | --- | --- |
| `directionRaw` | 形成收入/支出方向候选 | 不能单独决定最终交易类型 |
| `paymentMethodRaw` | 提供资金账户线索 | 不能未经用户映射直接写账户 ID |
| `statusRaw` | 判断正常、退款、无效或未知经济效果 | 不能把“退款成功”当普通收入 |
| `transactionTypeRaw` | 判断消费、转账、还款等业务语义 | 不能直接当账本分类 |
| 三类来源编号 | 构造稳定来源身份、精确去重 | 不能作为账户 ID |
| 对方、商品、备注 | 分类和关系判断线索 | 不能仅凭文本自动合并交易 |

最终正式字段由“规范化候选 + 账本账户映射 + 业务关系 + 用户确认”共同决定：

```text
正式交易类型：expense / income / transfer / refund
资金流出账户：source_account_id
资金流入账户：destination_account_id
分类：category_id
退款原交易：original_transaction_id
金额与时间：标准化金额和明确本地时间
```

这里 `source_account_id` 的英文 `source` 表示资金流出的方向角色，不表示账单来源平台或账单主体。

## 5. 第三层：身份与关系层

这一层回答“它到底是哪一笔钱、属于哪个账户、与其他记录有什么关系”。

### 5.1 来源身份

来源身份用于回答：

> 这是不是之前已经处理过的同一笔来源交易？

优先使用平台提供的稳定交易号；没有稳定交易号时，只能使用经过冻结和验证的来源身份规则。最终并发去重必须由数据库唯一约束裁决。

金额相同、日期接近或文本相同，都不能单独证明是重复交易。两笔同日、同额、同商户的真实消费必须允许同时存在。

### 5.2 三种不能混用的账户概念

一份支付宝或微信账单中可能同时出现余额、银行卡和消费信贷，所以要区分三种概念：

| 概念 | 回答的问题 | 示例 |
| --- | --- | --- |
| 账单主体 | 这份文件属于哪个外部账户或资料主体 | 某个支付宝账号、微信资料或银行卡账单 |
| 支付工具线索 | 这一行通过什么工具收付 | 零钱、余额、某银行卡、消费信贷 |
| 账本账户 | 最终影响哪个正式账户余额 | 招财猫记账本中的“微信零钱”“工资卡”“信用账户” |

账户映射用于回答：

> 账单中的微信零钱、银行卡或信用卡，对应账本里的哪个账户？

来源身份与账户映射必须分开：

- 来源身份决定“是不是同一笔来源记录”；
- 账户映射决定“这笔钱影响账本中的哪个资金流出或资金流入账户”；
- 用户以后调整账户映射，不能改变历史来源身份。

### 5.3 业务关系

系统需要区分：

- 普通支出；
- 普通收入；
- 本人账户之间的转账；
- 信用卡还款；
- 退款与原消费；
- 借款本金、利息和还款。

无法确认的账户、用途、重复身份或关系必须进入待确认，不能猜测。

### 5.4 跨来源关联是所有交易的通用逻辑

不只是贷款，同一次现实资金活动都可能在多个系统留下记录：

- 微信或支付宝消费，同时在绑定银行卡产生扣款；
- 本人转账，同时出现在付款账户和收款账户；
- 原消费、平台退款和银行卡退款到账分别留下记录；
- 工资单和银行卡工资入账描述同一次收入；
- 还款支付、银行卡扣款和贷款明细描述同一次贷款还款。

这些记录不是需要重复入账的多笔钱，而是同一个经济事件的多份证据。每份来源记录都要独立保留来源身份，关联后也不能互相覆盖或当作重复行删除。

系统的组织方式应是：

```text
多条独立来源记录
  ↓ 保留各自来源身份和原始证据
同一个经济事件候选
  ↓ 自动确认强关系；其余关系交给用户
一组正式交易
```

“经济事件”是对现实中同一次消费、收入、转账、退款或还款的归组。它不是余额本身，也不能替代正式交易。当前实现已由 FinanceUpdate 统一读取多份支付平台账单，生成 `catledger_economic_events`、Evidence、Relation 和 ReviewIssue；只有共享且核验通过的稳定标识可自动归组，银行通用模板和完整贷款/分期资料仍属于后续能力。

一个经济事件可以关联一条或多条来源证据，也可以生成一笔或多笔正式交易：

| 经济事件 | 可能关联的来源证据 | 通常生成的正式交易 |
| --- | --- | --- |
| 普通消费 | 支付平台记录、银行卡扣款 | 一笔支出 |
| 本人转账 | 转出账户记录、转入账户记录 | 一笔同时影响两个账户的转账 |
| 退款 | 原消费、平台退款、银行卡入账 | 一笔关联原支出的退款 |
| 工资收入 | 工资单、银行卡入账 | 一笔收入 |
| 贷款还款 | 支付平台记录、银行卡扣款、贷款明细 | 一笔本金转账，加若干利息或费用支出 |

跨来源关系分三级处理：

| 级别 | 判定依据 | 系统动作 |
| --- | --- | --- |
| 可确定 | 两个来源共享并核验通过的稳定关联号，或存在已冻结、已测试的官方强关联规则 | 自动关联，同时保存规则版本和证据 |
| 高可能 | 只有金额、时间、对方、银行卡尾号或支付工具等组合线索 | 给出关联建议，由用户确认 |
| 不确定或冲突 | 存在多个候选、金额不守恒、期次冲突或账户无法确定 | 不自动关联，交给用户决定 |

金额相同、时间接近或文本相似只能用于生成候选，不能单独触发自动合并。这里做的是“多份证据关联到同一个经济事件”，不是把来源身份不同的记录去重成一行。

关联完成后仍要按业务语义入账：消费计支出，工资计收入，本人转账不计收支，退款冲减原支出。不能因为银行和支付平台都出现了一条记录，就把同一笔钱计算两次。

### 5.5 贷款是跨来源关联的复杂特例

贷款遵循同一套“来源证据 → 经济事件 → 正式交易”逻辑，只是还要额外回答贷款账户、期次、本金、利息、费用和剩余本金等问题。

不同资料能证明的内容不同：

| 资料来源 | 通常能证明什么 | 通常不能单独证明什么 |
| --- | --- | --- |
| 支付宝或微信账单 | 用户发起了多少金额的支付、支付时间、交易对方、平台交易号和支付工具线索 | 贷款本金、利息和费用的准确拆分；支付工具线索未完成账户映射时，也不能证明最终账本账户 |
| 银行卡流水 | 哪张银行卡实际扣款、扣款金额、银行流水号和摘要 | 扣款内部有多少本金、利息或手续费 |
| 贷款或分期对账单 | 贷款账户、期次、本金、利息、费用、应还日和剩余本金等明细 | 如果缺少可核验关系，也不能单凭同额就断定对应某一条支付宝、微信或银行卡流水 |

贷款信息按资料完整度处理：

- 只有支付宝或微信记录时，系统最多确认发生了总额支付，并标记为“疑似贷款/分期还款”；贷款账户、本金、利息、费用和期次均不得猜测，需用户补充或确认。
- 有银行卡流水但没有贷款明细时，可以补强实际扣款账户和总额，仍不能自动拆分本金、利息和费用。
- 有贷款或分期对账单时，优先用稳定关系关联；可核验的部分自动整理，无法唯一对应的部分让用户选择。
- 本金、利息和费用拆分之和必须等于实际还款总额；不相等时不得正式入账，除非差额已被解释为另一个明确组成项。

## 6. 第四层：待确认层

系统先自动整理明确项目，只把真正有歧义的项目交给用户。

常见待确认原因包括：

- 不知道对应哪个账本账户；
- 不知道是消费还是本人转账；
- 找到疑似重复，但缺少稳定来源身份；
- 退款找不到原消费；
- 信用卡还款找不到对应的付款账户或信用账户；
- 疑似贷款还款缺少贷款账户、期次或本金/利息/费用拆分；
- 支付宝、微信、银行卡和贷款明细之间只有弱匹配，或存在多个同额候选；
- 金额、状态、币种或关系互相冲突。

用户确认的是“整理决定”，例如选择账户、分类、交易类型和关联关系，而不是修改原始证据。

待确认记录、被排除记录和解析草稿都不能影响正式余额、收支和统计。

### 6.1 小程序多账单导入的完整时序

页面顶部固定为“解析 → 账户 → 整理 → 入账”。单文件和多文件共用这套用户流程，差别只在内部来源数量和跨来源整理，不另做一套难以理解的界面。

```text
一次选择 1～5 份账单
  ↓ 每份独立上传、解析、失败和重试
成功批次冻结成一个 FinanceUpdate
  ↓ 跨来源生成 EconomicEvent / Evidence / Relation
确认账户（已有账户或本批新账户草稿）
  ↓ 只处理真正打开的 ReviewIssue
全部阻塞问题清零
  ↓ 用户单独点击“确认整批入账”
同一事务创建新账户、提升映射、写交易和链接
```

已开放步骤可以返回；任何决定变化都由服务端重算 postability。客户端不能自行把事件改成 `ready`。从 FinanceUpdate 建立到正式入账前，页面常驻“放弃本批账单”：确认后关闭本更新、释放来源并回到空白文件选择页。

### 6.2 第一步：选择、上传与解析

1. “添加账单”按钮常驻，一次最多累计 5 份，每份不超过 5 MiB；达到 5 份后按钮禁用。账单列表位于操作按钮上方，每份只有一个删除入口。
2. “开始解析”在没有文件时禁用；文件选择只是追加，相同内容只保留一份。
3. `imports.prepareMany` 为每份文件签发独立、随机、用户隔离的私有路径，小程序分别直传；`imports.parseFile` 再校验可信身份和精确对象路径。
4. 最多五份同时执行上传→解析。每份文件有自己的 UploadTask、超时、三次瞬时错误尝试、进度和最终状态；任一任务失败或回调异常不得取消、覆盖或悬挂其他任务。
5. 每份文件独立保存摘要、来源、原始行、解析批次和版本。一份失败只改变自身，可重试或移除；其他成功来源不回滚。解析结束后仍可追加新账单，系统只准备和解析新加入的文件，不会重复处理已经成功或失败的来源。
6. 文件名和扩展名不能声明真实来源；服务端按正文、表头和容器结构探测支付宝、微信 CSV/XLSX，且保留编码、行列和压缩结构上限。
7. 只要至少一份文件成功，用户就可以继续；全部失败时只禁用“下一步”，重试、删除和追加账单仍然可用。用户选择继续后，客户端只调用一次 `financeUpdates.prepare`，服务端在一个幂等事务中把全部成功批次按稳定顺序冻结到同一个 FinanceUpdate 并完成首次整理；失败文件不混入，但仍保留自己的失败事实。

#### 6.2.1 文件内容重复不等于已经入账

必须把下面三件事分开判断：

1. **本次选择内重复**：用户在当前文件列表中再次选择了同名、同大小且内容相同的文件。客户端只保留当前列表中的一份，提示“同一账单只保留一份”；原来那一行不能被删除。
2. **历史上传重复**：服务端文件摘要命中以前上传或解析过的文件，但对应来源没有随正式交易成功入账。这不是入账重复，不得拦截。
3. **正式入账重复**：既有来源已经处于 `committed`，并已随 posted FinanceUpdate 或兼容旧链路形成正式交易。只有这种情况才提示“这份账单已经正式入账，不会再次创建交易”。

服务端按以下状态处理历史同内容文件：

| 既有来源状态 | 活动 FinanceUpdate | 服务端决定 | 客户端行为 |
| --- | --- | --- | --- |
| `review_ready` 或曾被 `discarded`，解析批次仍可用 | 无，或只属于 `abandoned / undone` 更新 | 返回原 `importId` 和不可变 `batchId`，标记 `reused_unposted` | 普通显示“解析完成”，可与其他成功文件一起继续 |
| `review_ready` | 存在 `draft / failed / review` 未入账更新 | 在同一事务写放弃审计并关闭旧更新，返回原 `importId` 和不可变 `batchId`，标记 `replaced_unposted_update` | 普通显示“解析完成”，不询问、不显示“继续”；新整理不得继承旧判断 |
| `committed` | 已正式入账 | 返回 `already_posted` | 保留文件行，明确显示“已经入账”，不进入本次 FinanceUpdate；用户可主动删除该行 |

新上传的冗余云存储对象可以在摘要核验完成后清理，但原文件行、解析证据、历史 FinanceUpdate 和行动审计不能因此被覆盖或删除。被替换的旧更新只改为 `abandoned`，正式账户、映射、交易、余额和统计保持不变。客户端收到任一种重复裁决后都不得把唯一文件行移除并退回空白页。

`catledger_import_files` 通过 `(uid, content_sha256)` 唯一约束，为同一用户的同一文件内容只保留一个持有摘要的规范来源；后续冗余上传行只记录重复裁决，不再次占用该摘要。即使用户先重复上传并复用过一次，之后又在未入账 FinanceUpdate 期间再次上传，服务端仍必须定位到规范来源，自动放弃旧更新并把原批次交给本次流程。

这一规则的核心判断是“是否存在正式入账事实”，不是“数据库里是否见过这个文件摘要”。文件摘要用于复用解析和防止并发重复，不能替代账本状态。

复用范围必须严格分层：`ImportFile / ImportBatch / ImportRow / Evidence` 是来源证据，可以复用；旧 FinanceUpdate 内生成的 `EconomicEvent` 资金方向、账户草稿、映射草稿、ReviewIssue 和用户处理决定属于一次整理过程，明确重新上传时全部随旧更新作废。已经通过正式入账事务提升的用户范围账户映射属于正式规则，可在新整理中作为历史建议参与匹配，但优先级低于本批选择和本事件手工选择，且不得把泛称或无法唯一识别的账户自动套到具体账户。

### 6.3 第二步：账户归属

- 多文件仅扩大本次 FinanceUpdate 的来源集合，不改变已经确认过的单文件账户交互。页面继续按支付工具分组：名称与影响记录数在上方，处理方式、新账户名称、账户类型在同一行，每项下方独立“确认此账户”；转账/还款明确选择转出与转入两端。不得再把每个账户问题渲染成重复的大按钮卡片。
- 已有账户只能从当前用户的活动账户中选择；服务端校验归属、币种和状态。
- 账户决策优先级为“唯一规范全名推断 < 已存在正式支付工具映射 < 本批账户映射草稿 < 本事件手工端点”。本批草稿必须覆盖 planning row 携带的旧正式映射；本事件手工端点只保护用户真正手工确认过的那一端。整理详情读取时按此优先级生成有效视图，用户保存缺失端前再按同一规则重算一次，不能把事件中缓存的旧账户快照带进最终决定。例如旧历史映射把支付宝余额指向“开发验收现金”，而本批已选择“支付宝账户余额”时，弹层展示和保存都必须使用本批选择。唯一完全同名自动沿用后仍生成一条非阻塞的已确认账户项，用户可以返回修改；零命中或多命中保持待处理。客户端只对银行主体与尾号、去平台前缀等非精确线索推荐唯一账户并提示“推荐已有账户，请核对”；不同银行仅尾号相同、币种不同或最高分并列时保持人工选择。
- 每个可识别账户候选提供“创建新账户、选择已有账户、仅本次不计入、以后不计入”四类处理方式；两种不计入操作固定放在同一分组，不混入可能很长的账户列表。没有稳定映射键的空值或泛称只提供前三类，不得接受后续忽略偏好请求。
- 已保存“以后不计入”的支付工具在后续导入中自动排除匹配事件，同时生成一条非阻塞、已解决且可编辑的账户归属项，默认显示“以后不计入”，不要求用户再次确认。它不能被完全隐藏或锁定；用户可重新选择已有账户或创建新账户，本次改选账户并成功入账后，新的精确账户映射覆盖原忽略偏好。
- 账户归属在整批正式入账前始终可回看和修改。已经确认的项目仍显示原选择；用户改选后只更新 FinanceUpdate 内的账户映射草稿，重新计算受影响事件的 `ready / needs_action / excluded` 和尚未处理的后续问题，不提前创建、修改或停用正式账户。若同一事件的后续业务决定已经完成，必须先阻止覆盖并提示状态变化，不能静默抹掉退款、重复或关系决定。
- 资金流转详情在“转出 → 转入”路径卡上选择缺失端，已确定端只读；符合条件时显示同银行候选建议，仍需用户点击及保存。交易摘要与原始字段位于同一详情滚动区，不再二次下钻，详见第 6.4.1～6.4.6 节。
- “新建账户”要求 1～32 字符名称和明确类型。此时只生成 `catledger_finance_update_account_drafts` 草稿和未来账户 UUID，`catledger_accounts` 中不创建任何行，现有账户也不修改。
- 用户确认支付工具归属或永久忽略时，只写 `catledger_finance_update_account_mapping_drafts`：`mapping_action = account` 必须指向账户或本批账户草稿，`mapping_action = ignore` 必须保持 `account_id = NULL`。正式 `catledger_import_account_mappings` 在最终入账前保持不变。
- 新账户草稿初始余额为零；只有最终事务中的正式交易影响余额，不能把账单金额再当初始余额。
- 本次排除、永久忽略、账户映射等决定都属于 FinanceUpdate 范围。只有最终整批入账成功，允许持久规则与交易一起生效；放弃或失败不会留下规则。
- 旧单文件路径中“先调用 `accounts.createBatch`，再进入整理”的做法已废止。导入主链路不得在账户步骤提前创建正式账户。
- 点击“确认此账户”只发送包含该账户组的一个请求。服务端锁定 Update 一次、锁定目标 Issue 一次、写一条批次 Action，并在同一事务内完成所有账户决定；最后只对受影响资金投影重算一次、计数一次、返回一次完整视图。任何一项失败时整批账户草稿回滚，每次确认的目标组整体成功或回滚；其他账户组保持原状态，用户可逐项推进。

### 6.4 第三步：只处理 ReviewIssue

普通且可确定的事件不逐行请求批准。页面只展示服务端投影的打开问题，包括账户归属、交易分类、共享字段、同一笔候选、退款关系、转账/还款账户、身份冲突、字段冲突和分期本金来源。

一张卡片只要求一个真实决定。用户选择后，服务端在同一事务中更新事件草稿、Evidence 角色、Relation、ReviewIssue、FinanceAction 和守恒计数，再统一重算 `ready / needs_action / excluded`。同额、近时或文本相似只能生成候选；只有强稳定关系能自动归组。

可共享的决定沿用原 organizer 的安全分组边界：`account_mapping` 按同一具体支付工具分组；`transfer_accounts` 和 `shared_fields` 只有在经济性质、资金方向、阻塞原因族、来源/支付账户上下文、交易类型、经济效果、币种以及规范化的交易类型、对方、商品和支付方式都相同时，才进入同一 ReviewIssue。`same_event` 只按服务端生成的精确候选组聚合；`refund_relation`、`identity_conflict`、`field_conflict`、`installment_origin` 不因界面相似而批量套用决定。不同支付账户、不同原因族或不同证据上下文必须拆开。

`category_assignment` 与账户问题职责严格分离：账户回答“钱从哪里来、到哪里去”，分类回答“这笔收支用来做什么”。分类问题不显示账户选择器，账户问题不隐式改分类。分类下拉框首项固定为“请选择分类”，未选择时“保存选择”禁用；保存后 planner 只重算被冻结成员的 postability，同组收入不得套支出分类，同组支出不得套收入分类。

退款关系由 `RefundRelationPolicy` 一次性完成共同资格和证据分层。共同资格约束原消费性质、排除状态、币种、发生顺序、180 天窗口、金额以及账户/来源分组兼容；证据按“同来源稳定标识 → 明确退款金额凭据 → 规范化商品标题 → 同来源同商户”分层，只保留最高非空层。标题层还要求同来源、同账户、同币种、同金额且 72 小时内；它能覆盖“1688 平台商家消费、实际商家退款”这类商户名变化，但只生成待核对候选。只有前两层唯一候选才自动确认，标题和同商户候选始终人工核对。支付平台在原消费行写“已退款/退款成功”时，该行仍按支出处理；真实退款到账行才按 `refund + inflow` 处理。不得把近期金额足够的任意支出加入候选。

整理页按问题类型分组，列表直接显示主体交易的标题、日期、来源、金额和需要决定的原因。所有问题复用同一套“轻量分组标题 + 完整交易摘要 + 操作入口”卡片骨架；退款不再维护一套更拥挤的特殊列表样式。退款详情只显示 planner 已冻结为当前问题 candidate 成员的原消费，并用“订单匹配 / 退款凭据 / 商品匹配待核对 / 同商户待核对”说明证据层级；没有候选时提供“暂记待关联退款”，也保留稍后处理和本次不计入，不允许从详情或客户端扩大到其他消费。界面不展示裸分金额、关系状态码或“涉及 N 个关联对象”作为主要信息。

`已排除` 页只负责解释“为什么不会入账”。服务端事件保存结构化 `reasonCodes`，客户端只做确定性投影：账户归属排除按具体 `PaymentReference` 的安全展示名分组，关闭、失败和已经入账按状态原因分组，人工单笔排除单独归组；原因优先级和稳定分组键由版本控制的 view-model 固定。新决定使用 `account_mapping_excluded`，已有未入账批次若带旧的明确账户忽略码 `source_account_ignored_default`，也兼容投影到同一账户组，不要求用户重新上传。每个原因组本身是一整行展开入口，默认收起；不得在整行内部再放一个窄的原生按钮而产生左右白边。展开后仅显示交易摘要，不重复为每条记录铺一行相同的“不计入”说明；原始 Evidence 仍通过原始记录入口独立下钻，不因排除而删除或改写。

移动端对可共享决定仍按安全分组显示一张批量卡，最多预览 3 笔并明确批量范围；退款关系不能共享原消费决定，因此不做汇总入口，而是在“退款关系”分组内把每笔退款直接列出。每行独立打开和保存，完成后只刷新列表，不自动跳到下一笔。

原始证据必须可查。账户记录面板与待整理详情直接同层显示原文，并保留分页和失败重试；同笔主记录选择使用独立控件。原始字段不因账户选择、退款关联或排除而修改，普通列表及日志不铺原文。具体展示字段、加载和异常规则见第 6.4.5～6.4.6 节。

资金流转问题还要遵守“只问未知事实”：已知转出端时标题为“转入账户待确认”，已知转入端时标题为“转出账户待确认”；详情先展示一条轻量的 `转出 → 转入` 路径，已知端只读，未知端才出现账户选择器。只有两端都无法解析时才允许同时选择两个账户。用户提交后，服务端保存缺失端对应的映射草稿并重新运行 postability，不要求客户端把已知端原样回传。

#### 6.4.1 无尾号银行推荐：适用范围与输入

以下规则对应开发版 0.4.9，编号供逐条审核。它是第三步 `transfer_accounts` 的人工候选展示，不替换第二步的稳定支付账户映射，也不重新解析原始账单。

| 规则 | 当前执行条件 | 不满足时 |
| --- | --- | --- |
| BANK-01 | 问题详情包含至少一个事件，且事件带 `fundsProjection` | 不显示此类银行建议，沿用原确认流程 |
| BANK-02 | 转出账户已有 ID、转入账户无 ID，推荐 `to`；反之推荐 `from` | 两端都缺或都已有时不进入本功能 |
| BANK-03 | 缺失端的资金引用存在，且不是 `aggregate` | 合并还款继续使用金额分配流程，不能推荐一张卡替代分配 |
| BANK-04 | 输入取缺失端引用的 `value`，没有则取 `label` | 不从金额、时间、商户相似度推断账户；此处不另读原始字段重新提取银行 |
| BANK-05 | 输入不含半角/全角数字及 `& / ＆ / + / ＋` | 有任何这些字符都不走“无尾号”降级建议；不丢弃已有尾号，也不替组合资金选一张卡 |
| BANK-06 | 能按下述银行和账户类型规则得到非空结果 | 类型或银行不明确时保持人工选择 |
| BANK-07 | 同一问题的全部事件都满足以上条件，而且银行、类型、缺失端三者一致 | 不给该问题整体套用银行候选 |

银行名处理的实际边界：先删除空白、`·`、`•` 和半角连字符，再从文本开头提取以“银行”结尾的中文银行名称（正则前缀为 2～20 个中文字符）。不做任意子串、拼音、缩写或编辑距离模糊匹配；例如自定义账户名以其他昵称开头，可能不会进入候选。

目前仅有以下显式别名归一；其他名称精确比较，不自动扩充：

| 原名称 | 统一名称 |
| --- | --- |
| 中国工商银行 | 工商银行 |
| 中国农业银行 | 农业银行 |
| 中国建设银行 | 建设银行 |
| 中国邮政储蓄银行 | 邮政储蓄银行 |
| 上海浦东发展银行 | 浦发银行 |
| 中国光大银行 | 光大银行 |
| 中国民生银行 | 民生银行 |

类型判定按以下顺序执行：

1. 同时包含“信用卡/贷记卡”和“储蓄卡/借记卡”，视为冲突，不推荐。
2. 明确包含“储蓄卡/借记卡”，要求候选账户 `type=bank`。
3. 明确包含“信用卡/贷记卡”，要求 `type=credit`。
4. 未明确卡类型，但事件 `economicNature=repayment` 且缺失端为转入端，按信用卡类型筛选。
5. 其余没有明确类型的情况不推荐。不能把任意“银行”转账都视为信用卡还款。

#### 6.4.2 候选账户筛选与排序

BANK-08：从详情返回的正式账户及本批账户草稿中筛选；本批草稿以“（本批新建）”标明。账户必须有 ID，`type` 与推导类型相同，账户名称按上节规则提取的银行必须相同；排除 `archived=true` 或 `status=archived` 的账户，并排除本问题任一事件已经确定的另一端账户，避免推荐自己转自己。

BANK-09：保留接口返回顺序，不按金额、日期、使用次数或尾号大小排序；没有“第一张最可信”的规则。相同银行和类型不证明属于某张具体卡，候选数量也不是置信度。

| 候选数量 | 界面初始状态 | 用户确认方式 |
| --- | --- | --- |
| 0 | 显示识别依据和“暂无同银行同类型账户”，未知端仍待选择 | 使用原账户选择器选择其他账户或新建 |
| 1 | 候选显示“建议 · 待确认”，未知端不自动预选 | 点击候选填入本地选择，再点保存 |
| 多个 | 全部显示为同银行候选，不预选第一张 | 用户点选具体账户，再点保存 |

BANK-10：推荐依据显示“账单显示××银行信用卡/储蓄卡，未提供尾号，请核对。”候选使用待确认底色。点击候选仅更新本地 `issueDraft.accountIndex`，候选文字变成“已选 · 待保存”；问题仍 `open`，不调用保存接口，不改变正式余额。

BANK-11：推荐不是强制白名单。普通单项保存仍允许用户通过原账户选择器选择其他账户；这条人工覆盖路径不等于系统认定它符合推荐规则。新建仍需账户名称和类型，只提交本批账户草稿，不提前创建正式账户。

#### 6.4.3 可选批量的范围、证据与勾选粒度

BANK-12：批量入口只在当前问题有银行候选，且列表摘要中存在其他同键开放问题时显示。键为“银行 + 账户类型 + 缺失端”；初筛只取当前列表中 `status=open` 的其他 `transfer_accounts`，排除当前项，优先检查其 `subjects`，没有则检查 `subject`。不跨批次、不批量处理退款关系或分类问题，不重新改变服务端已有的问题分组。

BANK-13：点击展开后，逐问题读取最新详情，重新检查问题类型、开放状态、同一 `updateId` 和全部事件的推荐键。已完成、不同批次或不兼容的问题跳过；界面入口的初筛数量可能大于最终可显示数量。全部被跳过时显示没有仍需确认的同类记录。

BANK-14：每个额外问题的全部事件及其全部原始证据同层展示。问题依次读取，每个问题的证据最多 4 笔并发；此批量区域当前没有“每 20 笔”分页。只有该问题有事件、全部事件证据请求完成、没有错误且每个事件至少返回一条证据，才允许勾选。证据是否有有效内容仅按上述响应条件判断，不等于系统确认业务事实正确。

BANK-15：**勾选单位是一个 ReviewIssue，不一定是一笔交易。** 每个选项标明笔数；一项有多笔时，一次勾选覆盖该项全部事件，取消也是取消整个问题。当前不能从同一问题内剔除某一事件而把剩余事件单独应用。当前打开的问题始终包含在保存范围内；额外问题默认全部不选。

BANK-16：勾选前必须已选择一个有 ID 的账户，且该账户必须在该额外问题最新读取的候选 ID 中。未选择账户则提示先选择；新建入口不能直接作为批量账户使用。选择了非推荐账户时，可走单项人工保存，但不允许把它批量套给不包含该候选的问题。

BANK-17：允许逐选项勾选和取消。换账户（包括重选同一个账户）或收起批量区域，清空额外勾选；重新展开会重新读取。加载或保存中禁止勾选，批量加载中禁止保存。关闭详情使请求令牌失效，晚到响应不能改写下次打开的详情；卸载同样使令牌失效。

BANK-18：某条证据失败保留对应摘要并禁止勾选该问题；批量详情读取失败显示错误。批量区域当前通过收起再展开重新读取，不提供独立逐条重试按钮。普通详情中的原始证据则有逐条重试入口。

#### 6.4.4 单项与批量保存的精确执行过程

| 路径 | 请求与字段 | 事务边界 |
| --- | --- | --- |
| 未勾选其他问题 | `reviewIssues.resolve`，`decision=apply_fields`，携带当前批次版本、问题版本、请求 ID | 一个问题一个服务端幂等事务 |
| 勾选了其他问题 | 先按下述规则预检，再对当前问题及所选其他问题依次调用同一接口 | 多个独立事务；不承诺整个批量原子回滚 |
| 第二步“确认账户归属” | 原有 `reviewIssues.resolveAccountMappings` | 所有账户项在一个事务内完成；与本节不是同一批量路径 |
| 最终“确认整批入账” | 原有 posting | 正式账户、映射与交易整批原子提交；本次没有改变 |

BANK-19：保存缺失转入端只写 `counterpartyLedgerAccountId`；保存缺失转出端只写 `ledgerAccountId`。不把另一已知端从客户端复制回去。单项新建对应使用 `counterpartyLedgerAccountDraft` 或 `ledgerAccountDraft`。占位选择、无名称/类型的新账户等按既有表单校验阻止提交。

BANK-20：批量开始时冻结当前选择的账户 ID、目标问题 ID、各问题版本；顺序为当前问题在前，再按展示顺序处理已勾选的问题。预检逐一重新读取所有目标，检查：

1. 仍属于相同批次，批次状态仍 `review`。
2. 问题仍 `open`，类型仍为 `transfer_accounts`，版本等于用户查看时版本。
3. 全部事件仍符合相同银行/类型/缺失端键。
4. 已选账户仍在各问题最新候选中，包括重新检查归档状态和已知另一端。

任一预检失败，本次不发出任何保存请求，刷新状态后提示。预检是客户端读取，不加数据库锁；并发变化仍由保存接口的服务端版本检查最终裁决。

BANK-21：预检通过后，第一项带打开详情时的批次版本保存，后续项使用前一项成功响应返回的 `update.version`；各项带自己的问题版本和独立请求 ID。每项仅提交缺失端字段。不会把未勾选项、原消费候选、分类或金额混入提交。

BANK-22：服务端仍按可信用户身份、批次/问题归属、review/open 状态及版本检查并锁定；从服务端重算有效资金端，验证账户及事件条件，写整理行为审计、事件决定，解决该问题并生成必要后续问题、刷新资金投影和计数。可能仍有别的阻塞问题；保存账户不等于事件已可入账。

BANK-23：前项成功、后项失败时停止剩余请求，不撤回前项；刷新工作台并报告本次收到成功响应的项数。网络错误可能发生在服务端已提交之后，因此这个数字不是所有最终成功项的证明；剩余结果以刷新后的服务端状态为准，不盲目继续或宣称整批失败。若刷新也失败，页面保留错误，需要再次读取当前状态。

BANK-24：此批量在页面层没有额外的后台续传队列，不持久化批量进度，也没有跨问题回滚动作。接口仍沿用原幂等机制；前端不会把“用户重新点保存”假称为恢复同一个完整批量事务。

BANK-25：这些动作只保存未入账整理结果，不写正式 Transaction，不改变正式余额。无尾号引用没有稳定 `paymentMethodKey`，服务端不会凭本次银行建议创建“同银行以后都归这张卡”的规则。其他已有稳定资金引用仍沿用服务端原本的映射草稿逻辑，不能把“无新增银行宽泛规则”误解为完全禁止已有精确映射。

#### 6.4.5 原始证据同层展示与分页

EVIDENCE-01：账户步骤默认不铺开交易正文，标题右侧“查看 N 笔”打开记录面板。单笔、多笔都直接显示摘要和原始字段，无需再点一层。普通待整理详情先显示账户/分类等决策表单，下方同一滚动区展示交易和原文，主保存操作固定在滚动区外；查看证据不提交决定。

EVIDENCE-02：账户记录面板与普通待整理详情首屏加载 20 笔，每次“再显示 20 笔”继续加载。完整的账户记录/裁决事件集合不会被可见分页截断。共享加载器每组最多 4 笔并发，只回写仍有效的页面令牌；关闭后停止后续组，已发出的请求即使返回也不重新打开面板。

EVIDENCE-03：每笔展示来源文件、原始行号和原始键值字段。当前模板不把来源定位符、解析器版本、快照版本全部铺在界面上；它们在证据层保存，不能把“保存了”写成“页面已显示”。失败保留摘要并允许重试，空证据有明确空态。

EVIDENCE-04：退款详情将冻结候选原消费也放进证据展示集合，按事件 ID 去重，标明“待处理记录/候选原消费”；候选不加入当前 `issueEvents` 裁决主体集合。展示全部候选不等于自动选择关联；退款选择仍使用原独立关系控件。判断同一笔时，“选为主记录”保留独立按钮，不能通过点原文暗中改变主记录。

EVIDENCE-05：批量区域的加载/勾选规则见 BANK-14～18，与普通详情每 20 笔分页不同。被排除事件、已入账维护等其他现有独立原始记录入口继续保留，本次没有把所有入口都改成同一弹层。

#### 6.4.6 摘要与原始字段的展示转换

DISPLAY-01：摘要标题依次尝试商品、交易对方，跳过空值、纯空白/斜杠/全角斜杠/长横线/连字符以及完全等于“不详”“未知”的值。仍没有标题时，按经济性质回退为“信用卡还款、账户转账、退款、支出、收入”，没有对应中文标签则显示“待确认事件”。这是显示层回退，不修改原始商品；原文中的 `/` 继续可见。

DISPLAY-02：字段名必须以“日期”或“时间”结尾，字段值转为字符串后必须是 5 位整数（可带小数），数值在 20000～80000（含端点），才尝试 Excel 日期序号转换。其他日期文本原样保留；金额、交易单号、商户单号即使是相同数字也不转换。

DISPLAY-03：转换按 Excel 1900 日期体系，以 1899-12-30 为基点，序号乘 86400 四舍五入到秒，以 UTC 算术生成 `YYYY-MM-DD HH:mm:ss`。UTC 只用于避免设备时区改变钟面时间，不把账单本地时间解释成 UTC 交易时刻。当前没有根据工作簿元信息识别 1904 日期体系；不能把该展示补丁称为任意 Excel 日期体系支持。

DISPLAY-04：转换仅影响返回给模板的字符串，不更新 `raw_fields_json`、规范化 `localAt`、排序、身份或账务计算。字段对象和 `{name,value}` 数组形式都走相同转换。原值空/null/undefined 显示占位“—”；其他数字、布尔值按字符串显示，数组以中文分号连接，对象按“键：值”展开。金额摘要继续走原有整数分转元字符串格式，不因本次日期处理引入浮点金额计算。

### 6.5 第四步：最终确认与整批放弃

最终页先展示用户能核对的业务结果：本批支出、收入、退款金额，分类完成度，内部资金流转笔数，新建账户数、受影响账户数，以及准备入账/排除数量；重复来源证据只作为次级审计信息。只有阻塞问题为零且所有收入、支出、费用分类完整时，“确认整批入账”可用。确认后，正式账户、账户映射、分类映射、交易、事件链接和状态必须在一个 MySQL 事务中同时成功或同时回滚。成功页直接提供“查看明细、补全历史分类、校正余额、查看统计、继续导入”，不要求用户理解内部状态码。

在点击最终确认前，用户可从任何已开放步骤选择“放弃本批账单”。放弃只把 FinanceUpdate 标为 `abandoned`、释放来源并清空当前工作台；原始证据和行动审计保留，正式账户、映射、分类、交易、余额和统计与开始导入前逐项一致。

## 7. 第五层：正式入账层

用户确认后，系统才把整理结果转换成正式 `Transaction`。

### 7.1 支出

```text
资金流出账户减少
月度支出增加
```

例如银行卡消费 100 元：

```text
银行卡 -100 元
本月支出 +100 元
```

### 7.2 收入

```text
资金流入账户增加
月度收入增加
```

例如工资到账 10000 元：

```text
银行卡 +10000 元
本月收入 +10000 元
```

### 7.3 本人转账

```text
资金流出账户减少
资金流入账户增加
收入和支出不变
净值不变
```

例如银行卡转入微信零钱 500 元：

```text
银行卡 -500 元
微信零钱 +500 元
```

### 7.4 信用卡消费和还款

信用卡消费会增加信用卡负债，并计入支出。

信用卡还款本质是本人账户转账：银行卡余额减少，同时信用卡负债减少；因为刷卡时已经记录过消费，还款不能再算一次支出。

支付宝`花呗｜信用购`属于合并还款口径，不是账户名。花呗和具体银行信用购仍各自保留负债；一笔合并还款由用户确认各账户金额后，可由同一个经济事件生成多笔内部转账。各笔金额之和必须等于原始还款总额，因此既不会重复算支出，也不会把两个负债余额混在一个虚构账户里。

### 7.5 余额起点与余额校正

创建账户时填写当前余额，或者以后修正余额，系统使用独立的 `balance_adjustment` 调整交易：

```text
账户余额改变
收入和支出不变
```

这样不会把“账户原本有一万元”误算成本月收入，也不会把余额修正误算成消费。

### 7.6 退款

退款关联同一用户的一笔原支出，资金进入用户选择的退款到账账户，并冲减原消费，不作为普通收入。系统限制累计退款不能超过原支出剩余可退金额；这一手工退款闭环当前已经实现，账单导入阶段仍需补齐自动识别和关联规则。

### 7.7 贷款还款

贷款到账和贷款还款都不能按普通收入或普通消费直接处理：

- 贷款到账：贷款负债增加，同时银行卡等资产增加，不计收入；
- 偿还本金：银行卡等资产减少，同时贷款负债减少，不计支出；
- 利息和手续费：银行卡等资产减少，并计入真实支出。

例如三份资料最终确认描述同一次还款：

```text
支付宝记录：支付 5200 元
银行卡流水：扣款 5200 元
贷款明细：本金 5000 元 + 利息 180 元 + 手续费 20 元
```

这些不是需要重复入账的三笔钱，而是同一个经济事件的三份证据。正式入账应拆成：

```text
本金：银行卡 → 贷款负债账户 5000 元（转账，不计支出）
利息：银行卡 → 利息分类 180 元（支出）
手续费：银行卡 → 手续费分类 20 元（支出）
```

三笔正式交易共享同一个经济事件关系，组成金额合计必须等于实际扣款 5200 元。支付宝行、银行卡行和贷款明细行仍分别保留来源身份，并共同关联到该事件，不能只保留其中一行。

如果只有支付宝的 5200 元记录，系统不能自行假定“本金 5000、利息 180、手续费 20”。它只能形成总额支付和疑似贷款还款候选；用户需要确认贷款账户和拆分金额，或者暂缓入账。用户明确作出的简化选择也要保存为用户决定，不能伪装成系统从账单中解析出的事实。

在贷款能力上线前，当前手工账本可以用“一笔本金转账 + 若干利息/费用支出”表达用户已经知道的拆分结果，但不会自动把这些交易归成一次还款，也不会替用户核验贷款明细。

## 8. 什么叫整批原子入账

用户确认一个整理批次后：

```text
全部正式交易和关系同时成功
或者
全部回滚，一笔正式交易都不留下
```

例如一个批次包含 100 笔，第 99 笔写入失败，前 98 笔也必须回滚，不能留下半本账。

但文件解析采用失败隔离：

- A 文件解析成功，可以继续整理；
- B 文件格式错误，不会让 A 文件结果丢失；
- B 文件可以单独修复和重试。

因此：

> 文件失败隔离发生在解析和整理阶段；整批原子发生在正式入账阶段。

### 8.1 提交前必须重新验证

客户端的页面门禁只负责及时提醒，服务端不能相信客户端已经检查过。`financeUpdates.post` 进入事务后必须再次完成：

1. 用微信可信身份锁定当前 FinanceUpdate，核对状态、版本、来源快照和守恒计数。
2. 要求所有阻塞 ReviewIssue 已关闭，不存在 `needs_action` 事件；客户端不能提交或伪造 `ready`。
3. 对每个待入账事件重新执行 postability，验证金额、时间、经济性质、退款/转账/还款关系和已有交易链接。
4. 按稳定顺序锁定来源身份；同一来源身份已经关联正式交易时复用原交易，不重复创建。
5. 校验账户草稿、现有账户和分类均属于当前用户、币种兼容且未停用；新账户名称冲突必须让整批失败。
6. 检查账户映射草稿不存在同一支付工具指向多个账户的冲突。
7. 对 `cash` 账户记录入账前账面余额；整批正式交易写入后再核对最终余额。原本非负不得变负，历史遗留的负数不得进一步降低；触发时返回 `INSUFFICIENT_CASH_BALANCE`。

任意一项失败都在正式写账之前中止，页面重新读取批次状态，不允许绕过账户或整理步骤。

### 8.2 一个数据库事务中写什么

通过验证后，同一 MySQL 事务按以下顺序写入：

1. 新建 FinanceUpdate posting 和 FinanceAction，保存请求摘要、版本与选中事件数。
2. 把本更新的账户草稿物化为零余额正式账户；这一步仍在未提交事务内。
3. 为 ready 事件创建或复用正式 `catledger_transactions`；收入、支出、退款、转账和还款按各自语义写入，金额始终使用整数分。
4. 建立 EconomicEvent、Evidence 与正式交易的稳定链接。
5. 把本更新明确确认的账户映射草稿提升为正式可复用映射；未入账、已排除或冲突草稿不提升。
6. 在未提交事务中核对全部受影响的现金账户；任一账户新增或加深负余额时中止。
7. 逐事件更新为 `posted`，同步来源批次、文件、Update 计数和 Action 状态。

任何 SQL 失败都会回滚以上全部写入，包括刚物化的新账户和刚提升的映射。客户端看见的成功结果只可能来自已提交事务，不能出现“账户建了但交易没入”“映射生效但整批失败”或“交易成功但证据链接失败”的半状态。

### 8.3 重试、并发和文件清理

- 最终提交使用用户范围幂等键和请求摘要：同键同请求返回首次结果，同键不同请求拒绝。
- 账户归属批量确认使用一个客户端批请求、一个请求幂等键、一个数据库事务和一条批次 Action；目标 Issue 按稳定顺序一次锁定，批内决定共享当前映射索引，最后只执行一次受影响投影重算、一次计数和一次视图读取。它只修改 FinanceUpdate 草稿，不提前创建正式账户，也不改变最终整批原子入账边界。
- 客户端只对只读动作，以及契约声明为幂等且携带有效 `requestId` 的写动作，在明确瞬时错误时有限恢复；文件上传是独立通道，每份最多三次并按 0.6 秒、1.2 秒退避。云函数对连接断开、连接超时、死锁和锁等待使用新连接有限重试。提交结果不确定时依靠数据库幂等回执重放首次结果，不能仅凭客户端超时判断失败。
- 文件版本号负责乐观并发；两个页面基于同一旧版本同时提交时，只有先完成的事务可以改变状态。
- 来源身份唯一约束和事务锁负责最后裁决；即使客户端或函数重复执行，同一来源身份也不能生成两笔正式交易。
- 文件状态依次为 `awaiting_upload`、`review_ready`、`committed`；主动放弃进入 `discarded`，可重试解析失败保持 `failed`。行和事件分别保存自己的处理状态，不能只看文件状态猜逐笔结果。
- 成功入账、重复内容裁决或主动放弃后，函数在数据库事务之外尽力删除云存储原文件。删除失败只返回 `cleanup_pending`，不能把已经成功的账本事务伪装成失败；后续清理可重试。
- 小程序只在本机保存 24 小时内恢复解析所需的导入 ID、云文件引用、幂等请求和基本文件信息，不缓存原始账单正文；成功、放弃或过期后立即清除。
- 旧单文件 `imports.get/commit` 与逐行 `post/skip` 已退出公共动作；原始记录读取走事件证据接口，正式交易只允许由 FinanceUpdate 整批 posting 生成。

## 9. 第六层：计算展示层

账户余额不保存为一份可以随意修改的权威数字，而是由所有未删除正式交易聚合：

```text
账户账面余额 = 正式流入合计 - 正式流出合计
```

展示不能只看余额正负号猜账户性质：

- 资产账户始终按真实账面值展示；余额为负时必须保留负号，例如现金账户显示“余额 -¥47.80”，不能取绝对值并改称“待还”。
- 负号展示是对历史异常的如实呈现，不代表允许现金透支。新的手工写账和整批导入由服务端锁定账户后拦截；既有负数不可被新支出加深。若能定位到一笔本不应存在的错误交易，必须通过正式交易删除动作软删除该笔并保留审计；只有交易事实都正确但账面起点或实际余额有差异时，才使用显式余额校正。禁止通过取绝对值、截为零或直接改聚合结果掩盖异常。
- 负债账户账面值为负时，以正数“待还金额”展示，但计算净值时仍使用负账面值。
- 负债账户出现正账面值表示溢缴或余额资产化，应按“余额”方向展示正数。
- 停用账户不出现在首页活动账户列表中，但历史余额仍参与净值；首页净值与活动账户摘要不能因此被理解成同一组可见行的简单相加。

账户管理页的展示口径固定如下：

- `净资产 = 所有未停用账户账面余额之和`，负债在账面中本来就是负数，不再重复相减；
- `资产合计` 汇总当前所有正向账面余额，包括负债账户溢缴后形成的正余额；资产账户的异常负数不伪装成资产，而是在账户行标记“待校正”；
- `负债合计` 只汇总负债账户的负向账面余额并转成正数待还金额；
- 页面首屏使用“账户总览—大号左对齐净资产—资产合计/待还负债”的单一阅读层级；“新建”是标题右侧轻量动作，净资产使用无外框、无页签式装饰线的平面报表区，资产与负债分别成组，账户数量放入组标题；
- 页面只常驻账户名称、类型、余额和必要状态。资产负数显示红色“待校正”，负债负数转换为红色“待还”，负债正数显示绿色“溢缴余额”；颜色之外必须同时保留文字状态；
- 详情页余额标题按财务语义显示为“当前余额”“当前待还”或“溢缴余额”。校正、改名、停用收进点击整行后的账户详情，并按财务操作、普通设置、危险操作纵向排列；弹层内容过高时在安全区内滚动，不允许底部操作被系统手势区遮挡；
- 已停用账户作为一组默认收起，展开后只用于查看历史，不参与新交易选择；
- 余额校正仍通过一笔 `balance_adjustment` 差额交易实现，不直接覆盖聚合余额，也不进入收入或支出统计。

分类管理页与账户管理页使用同一交互边界：

- 分类页页头只保留标题；“新建分类”下沉到列表工具栏，不与页面标题竞争；
- 列表承担浏览、进入详情和直接拖拽排序，不在每行同时堆放改名、上移、下移和停用；右侧把手是唯一排序入口，触摸过程中只计算目标位置，松手后一次提交完整顺序；保存失败必须恢复服务端原顺序并提示，不得保留假成功状态；
- 支出/收入使用平面标签切换，当前分类数量随标签展示；整行显示稳定顺序、名称和性质；
- 点开分类后只处理改名、停用或恢复，不再提供另一套上移/下移排序入口；
- 已停用分类默认收起，展开后仍可进入详情并恢复；停用不修改历史交易分类事实。

在正式账本之上派生：

- 账户余额；
- 本月收入和支出；
- 净值；
- 分类统计；
- 收支趋势；
- 后续的可立即使用资金；
- 后续的未来 30/90 天确定支出；
- 后续的大额支出情景测算。

这些结果只能读取正式事实，不能反向静默修改正式交易。

月度统计使用一次只读一致性快照返回全部视图，页面不得为每张图分别请求并拼出口径不同的数据：

1. 顶部显示当月收入、净支出和结余；已关联退款从支出中冲减，待关联退款既不算收入也不冲减支出。
2. 质量指标显示正式交易笔数、发生交易的本地日期数、按活跃天数计算的日均支出和最大单笔支出。
3. “近六个月”以同一最大值为比例基准显示收入、净支出双序列；月份补零，不能因某月无交易缩短序列。
4. “每日收支”补齐当月每个本地日期，收入与净支出共用比例基准并排展示；不是只画支出。
5. 分类排行按当月净额计算。已关联退款使用 `original_transaction_id` 读取原消费当前分类并做负向冲减，因此以后修改原消费分类时，退款会自动移动到同一分类；退款自身不创建第二份分类事实。
6. 若正式账本仍有历史未分类收入/支出，统计页显示“待分类”数量和金额入口；补齐成功后重新读取整个只读快照，收入、支出、余额均不变化，只更新分类结构和完整度。

## 10. 未来计划、情景测算和 AI 为什么不算入账

未来付款计划只是“以后可能或确定要付的钱”，不是已经发生的交易：

```text
未来付款承诺 ≠ 正式交易
```

计划只有在实际付款发生并经过确认后，才能幂等地关联或生成正式交易。

情景测算只是比较不同选择的结果：

```text
情景测算 ≠ 实际付款
```

立即付清、分三次、推迟 90 天和暂不支付四种方案必须使用同一数据快照和确定性程序计算，不能产生业务写入。

AI 只允许解释已经计算好的结构化结果：

```text
AI 解释 ≠ 正式交易
AI 建议 ≠ 用户决定
```

AI 不能计算权威金额、修改正式账本、读取不必要的原始账单全文，也不能拥有付款、转账、投资或借款能力。

## 11. 当前已经实现的路径

当前已经实现手工记账闭环：

```text
用户填写
  ↓
服务端校验身份、账户、分类、金额和时间
  ↓
幂等写入正式交易
  ↓
正式交易自动改变余额和统计
```

当前支持：

- 支出；
- 收入；
- 本人转账；
- 关联原支出并限制金额的退款；
- 余额起点和余额校正；
- 手工交易修改；
- 手工交易软删除；
- 分类新增、改名、停用和恢复；
- 账户余额、净值、月度收支和统计查询。

MINI-1905/1906 已形成支付宝/微信多账单统一导入的本地开发候选：

```text

  ↓ 每份使用用户私有随机路径并独立解析
成功批次冻结为一个 FinanceUpdate
  ↓ 跨来源生成 Event / Evidence / Relation / ReviewIssue
用户确认账户草稿和真正有歧义的问题
  ↓ 用户明确确认整批入账
单个 MySQL 事务物化账户、提升映射、写交易和链接
  ↓ 尽力删除临时原文件
```

- 支付宝 App/Web CSV、微信支付 CSV/XLSX；单文件不超过 5 MiB，规范化记录不超过 5000 条；
- UTF-8、UTF-8 BOM、GB18030/GBK 兼容 CSV，以及受限 OOXML XLSX；
- 基于内容而不是文件名的来源和格式探测；
- 用户隔离的来源文件、解析批次、原始行、来源主体、稳定来源身份、FinanceUpdate、经济事件、Evidence、Relation、ReviewIssue、FinanceAction 和正式交易关系；

## 13. 贯穿所有层的四道护栏

### 可信身份

用户身份只由云函数从微信可信上下文取得，客户端不能指定 `uid` 或 OpenID。

### 用户隔离

所有业务表、查询、唯一约束、对象路径和幂等键都必须包含用户身份；两个用户上传相同文件也必须完全隔离。

### 幂等与并发

相同请求可以安全重试，同一来源交易并发入账只能成功一次；同一个幂等键对应不同请求时必须拒绝。

### 隐私与最小权限

普通日志不记录原始账单行、完整账户号、完整交易描述或数据库绑定值；原文件只短期保存；AI 和客户端都不拥有数据库凭据或真实资金操作能力。

云函数使用受限 MySQL 账号。多账单持久化和整批入账会通过 `SELECT ... FOR UPDATE` 锁定来源归属与既有交易链接，因此 `catledger_finance_update_sources`、`catledger_import_transaction_links` 即使在业务上只追加，也必须授予 `SELECT, INSERT, UPDATE`；这里的 `UPDATE` 仅满足 MySQL 锁定读取权限检查，应用不得改写既有证据链。缺少该权限属于服务部署错误，不得被解释为账单格式不支持，也不得把尚未入账的已解析文件判为“已入账重复”。

账户归属批处理每保存一个受影响事件，都要把仍关联该事件的 ReviewIssueMember `object_version` 同步到事件新版本，保证同一事务后的继续整理和返回修改仍使用正确的乐观并发基线。因此 `catledger_review_issue_members` 在 `SELECT, INSERT, DELETE` 外必须具备 `UPDATE(object_version)` 列级权限，不需要整表 UPDATE。缺少该权限时，账户批次会按原子边界整体回滚并产生 `ER_COLUMNACCESS_DENIED_ERROR`；这属于运行权限部署错误，不得解释为账单格式、账户选择或导入服务不可用。发布门禁除函数状态、VPC 和环境变量外，必须运行版本化的数据库权限契约检查。

### 人工组合支付决定（2026-09-05，当前实现）

#### COMBO-01 适用范围与不变事实

多个资金账户、来源未提供逐项金额时仍不自动记账。用户明确核对支付详情后，可以手工确认分项和性质。原始行、来源语义错误及付款总额保持不变；人工决定单独存入事件 field_sources_json.paymentResolution，FinanceAction 保留请求决定及审计。不存在按比例估算、默认第一个账户承担全部金额或用优惠补足差额。

本版仅支持原始 normalized_direction=expense 的出款；金融成分 2～20 个，其余成分只能是已认证优惠。未知成分、入款、退款及需要多个还款目标的情形不走此入口。需要原事件有 payment_components_ambiguous 语义阻断；不能给任意普通事件注入分项。多条来源构成一个事件时，所有有效证据的付款成分及原始方向必须一致，否则不提供可确认的分项。

#### COMBO-02 来源成分、兼容读取与界面

新规划在 field_sources_json 保存 paymentComponents（种类、展示名、来源分项金额）与 paymentSourceDirection；当前解析器尚不提取任意模板里的分项金额，金额仍由用户核对填写。旧 v26 事件缺这两个字段时，服务端详情/保存读取按可信 uid、updateId、eventId 查询未丢弃 Evidence 对应的不可变 ImportRow.semantic_json，使用同一成分投影函数补齐内存视图。只读详情不写事件、不增加批次版本；用户保存时才随决定一起持久化。不升级 organizer-plan-v26、不重建用户正在整理的批次，不清除已确认的卡、分类或其他决定。

账户步骤统一按来源账户归组，组合交易的每个付款账户均并入对应普通账户组，明确的还款目标也进入独立账户组；不再展示“组合支付待核对”账户组或专用多账户弹层。同一事件可在多个账户组的“查看 N 笔”中出现，但事件及正式交易不因此复制。已有账户、新建草稿和修改继续走普通账户选择器。分项金额、性质及尚未解决的交易问题仅在整理出现，细则见 COMBO-09。交易性质优先采用事件已明确的 repayment/expense；性质未知时保留未选；页面只消费服务端统一语义，不再单独匹配原始摘要关键词。各支付成分复用 suggestExistingAccount：同币种，名称规范化精确匹配优先，其次银行名称与相同尾号，再次同平台余额别名；唯一最高分才预选，最高分并列、无匹配或多个成分命中同一账户均留空。账户来自已有账户/已有本批账户草稿，性质和账户均可修改；预填不保存决定、不增加批次版本、不解除后台阻断。各成分金额仍为空，不推测比例。分项在同一行展示：左侧可修改的账户选择器，右侧人民币金额输入；不重复展示账户标题或单列金额标签。未匹配时左侧保留来源成分名并提示选择，长账户名称允许换行；仅布局改变，金额校验与保存条件不变。还款目标只展示信用类或其他负债账户。当前该分项表单不提供内嵌新建账户，缺少账户时需先准备可选账户。

#### COMBO-03 用户输入与前后端校验

| 输入 | 规则 |
| --- | --- |
| version | 新决定固定 payment-resolution-v2；已有 v1 仍按正金额原规则验证 |
| nature | 必须明确选 expense（本次支出）或 repayment（偿还既有欠款） |
| allocations | 每个资金成分恰好一项；componentIndex 对应原始成分位置，不得缺漏、重复或额外添加 |
| accountId | 有效 UUID；每个成分使用不同账户，不得与还款目标相同 |
| amountMinor | v2 接受规范的非负整数字符串，最多 19 位；零必须显式填写，空白不是零，不接受负数、浮点或前导零。前端元输入最多两位小数，以十进制字符串转分；事件总额仍须为正数 |
| 总额 | 服务端 BigInt 求和必须严格等于事件原始 amountMinor；不允许在同一请求中改总额 |
| targetAccountId | 支出必须为空；还款必须为一个有效负债账户 ID |

前端缺账户、缺性质、缺说明、金额有误、账户重复或目标与来源相同均禁止保存；显示剩余/超额。后端重新校验全部约束，并在可信 uid 内验证正式账户或本批账户草稿、归档状态、币种及负债目标类型，不能信任前端下拉过滤。仅 paymentResolution 字段可出现在该次 apply_fields.fields，拒绝与金额/性质/其他字段混写绕过。

#### COMBO-04 解除阻断的范围与状态

有效决定只允许在 postability 计算时解除 payment_components_ambiguous 与 row_transaction_type_unknown。原始 semanticBlockers 仍保存，未知状态、来源 profile、语义冲突、身份冲突及其他门禁继续生效；不能把填金额当作修复未知到账状态。

事件性质改为用户确认的性质，支出方向为 outflow，还款为 neutral；还款清空消费分类，支出若没有分类则生成后续分类待确认项。ledgerAccountId 保存按 componentIndex 排序后首个正金额分项账户作为现有事件结构的索引字段，不代表全部金额从该账户支出；正式金额影响必须读取完整分项。还款目标保存在 counterpartyLedgerAccountId。以后若总额、性质、方向或索引端点与保存的决定不一致，原决定失效并继续阻断；不能复用过期分项。

保存仍是单 ReviewIssue 的幂等事务，校验批次和问题版本，写 FinanceAction、事件及问题状态、后续问题和计数。保存人工分项并不保证马上 ready，所有分类/关系/其他硬阻断仍须解决。不建立“这个组合文本以后永远按本次比例分摊”的历史规则。

#### COMBO-05 正式入账、预览及重复来源

支出：每个正金额分项产生一条 expense，来源账户及金额使用该分项，共用事件分类和发生时间。还款：每个正金额分项产生一条 transfer，从该资金账户转到同一个负债目标，共用发生时间，不产生消费支出。每条交易通过 payment_allocation 角色关联同一事件，统一原始证据及审计。全部分项总和等于事件总额；零分项仅保留核对证据，不生成正式交易或余额变化，最终摘要按事件总额计一次。账户归属与草稿引用仍保留全部已确认账户，不因单笔零支付移除。

posting 重新验证人工决定、锁定全部分项及目标账户、检查币种/归档与负债类型，现金余额保护覆盖所有分项。新建账户草稿可达性包括全部分项，不能因为不是第一成分就误判为未使用。一个最终 FinanceUpdate 仍是单数据库事务，任一分项 SQL 失败全部回滚；相同请求重试不重复写入。

来源身份保护继续有效：多分项事件不能把一条已存在交易当作整笔复用；检测到已有身份交易时拒绝冲突，不复制第二套分项。普通重复来源仍沿用原去重/排除规则。

#### COMBO-06 退款、更正、撤销及明确限制

拆分原消费没有唯一一条可直接绑定的原交易。当前退款候选策略排除已人工拆分的原消费；对已冻结候选再次尝试关联时，服务端明确拒绝并提示核对退款分项，可先暂记待关联退款。不得选择第一分项冒充原消费总额。完整“退款分别退到哪些分项”的自动/人工分配尚未实现。

维护页不允许对含 paymentResolution 的事件做普通单笔更正（包括 v2 仅一个正数项的情况），返回“需要整批撤销后重新整理”。整批撤销则覆盖所有由本批创建且未被独立修改的分项；既有退款依赖、版本变化、现金余额等约束继续执行。撤销处理账户草稿时，其他未入账批次对任意分项账户的引用都会阻止误回收，不只检查事件第一账户。

#### COMBO-08 账户确认与交易整理分步（0.4.13 历史兼容命令）

本节记录旧版 paymentAccounts 整组提交命令，保留用于兼容及审计。当前账户页使用 COMBO-09 的按账户分组与普通选择器，不再提供此专用入口；旧命令校验仍保留。

账户阶段以 account_mapping + payment_components_ambiguous 识别组合支付，前端 paymentAccountsOnly 控制专用表单；已有唯一匹配预填仍可修改。只要求 2～20 个金融成分各选一个不同账户，无金额、性质、目标或核对说明要求。保存 apply_fields.fields.paymentAccounts[{componentIndex,accountId}]，不同时提交其他字段。服务端按不可变来源成分验证完整索引、无重复、UUID、字段白名单及原语义阻断；已存在完整 paymentResolution 时拒绝再以账户阶段命令覆盖。引用统一校验可信 uid、同批草稿/正式账户存在性、未归档及同币种。

决定保存在 field_sources_json.paymentAccounts，manualFieldMask 的第 10 位标记账户决定；使用现有 FinanceAction、批次/问题版本与事务保存及幂等重试，不修改原始证据，不把首个账户写成整笔 ledgerAccountId，不改变金额或经济性质。跨用户/过期版本等失败不部分写入。合法账户决定使组合支付剩余问题归入 shared_fields（整理），但 payment_components_ambiguous 等入账阻断保留，仍不能正式入账；身份冲突、账户映射冲突和核心字段冲突优先级不被此分流覆盖。

整理初始化优先按 componentIndex 恢复已保存 paymentAccounts，失效账户留空而不换成另一推荐；未保存成分才使用来源匹配。在整理中可改账户，完整 paymentResolution 是最终分项入账依据，先前 paymentAccounts 保留为早期决定。账户草稿可达性和跨批次撤销时的账户使用检查均包含 paymentAccounts，避免清理仍被引用的账户。不新增数据库列，不重建旧批次；未确认旧组合项仍走账户确认，已完成 paymentResolution 的旧项保持原状。

代码：payment-resolution.inspectPaymentAccounts、review-issue-service.applyFields/validateEventReferences、organizer-model.classifyReviewIssue、account-draft.reachableAccountIds、maintenance-side-effects，以及前端 paymentResolutionDefaults/refreshPaymentDraft/resolveWithFields。测试：payment-resolution.test.js 验证阶段流转且不可入账；import-account-choice.test.js 验证无金额可保存和已确认账户恢复；integration.test.js 覆盖真实 MySQL 保存、跨用户拒绝、幂等、整理详情恢复及之后整批入账/回滚/撤销。

#### COMBO-09 按来源账户归组、1688 目标及旧草稿升级（当前实现）

**AGROUP-01 账户组和交易的关系。** 第二步的单位是来源账户引用，而非组合支付这一交易类型。对于多个金融付款成分，每个引用保存 sourceType、paymentMethodKey、accountIdentityKey、label、componentIndex 和 memberRole=payment_component_N；明确先采后付还款目标使用 payment_target。引用存在 field_sources_json.paymentAccountReferences，升级标记为 payment-account-groups-v1。每个账户问题通过 ReviewIssueMember 引用原 EconomicEvent：同一事件可属于多个账户问题，事件、原始行和证据不复制。组内 memberCount 是本组关联记录数；不同组的笔数不能相加当作总交易笔数，也不在账户阶段把原始总额视为该账户实际分项金额。

**AGROUP-02 来源输入与一致性。** 显式 refreshAccountGroups 查询当前可信 uid/updateId 中 ready/needs_action、没有完整 paymentResolution、尚无升级标记的事件；关联所有非 discarded 的原始证据，读取付款方式、原交易类型、交易对方、商品和来源平台。按原有 paymentComponents 规则拆 &/＆，已认证优惠不生成账户组，金融成分使用原串索引（优惠插入不改变对应关系）。多证据的全部账户引用必须完全相同，否则不升级，保留原问题等待人工核对。未知/没有稳定尾号的引用不可与其他记录默认合并，也不写长期映射。

**AGROUP-03 分组键及重用。** 稳定引用使用 accountIdentityKeyForReference，缺少时使用 paymentReferenceKey，并附加币种；银行卡尾号及规范化名称按既有 portable 规则允许跨平台同卡归组，平台余额保留平台身份。不稳定引用使用 eventId + memberRole + currency，只影响该事件。先查本批 open/resolved 的已识别账户组，相同键增加成员和笔数；无对应组才创建账户问题。组合付款旧 subject 账户问题被 superseded，其原历史不删除；单一付款账户的原分组保留。这样同一张卡原有 4 笔、新增组合付款 1 笔后是该卡 5 笔，而非再增加一个组合支付账户组。

**AGROUP-04 已确认结果。** 原事件 paymentAccounts 已保存的账户优先；没有时沿用同组已 resolved 的账户。沿用只复用之前确认结果，不按字符串顺序选第一账户。新增成员与组内既有确认冲突时组重新打开，不覆盖原记录中的选择；新建组全部成员已有一致确认时保持 resolved，否则等待统一选择。历史排除组无可沿用账户时重新打开，避免把组合交易静默丢弃。已存在完整 paymentResolution 的事件不在此次升级中改写。旧草稿不重解析、不重建 EconomicEvent、不清除分类/退款决定。

**AGROUP-05 1688 先采后付。** 仅当来源为 alipay、原交易分类严格为“信用借还”、交易对方包含“1688…先采后付”、商品包含“先采后付…账单付款”同时成立时，生成名为“1688先采后付”的 repayment_target 引用；普通 1688 购物、其他商家或仅商品模糊提及不命中。单账户付款及组合付款均适用。引用通过原有 accountReference/buildPaymentMethodKey/accountGroupingKey 生成稳定键，expectedAccountType 和前端新建默认类型均为 credit。目标选择服务端只接受 credit/other_liability，不能选资产账户。没有已有账户时可在正常账户页新建本批草稿，正式账户仍等最终入账才创建。这里只明确账户角色，原始行、总额和解析历史均不改写；没有将“先采后付”虚构成某张银行信用卡。

**AGROUP-06 账户保存。** 仍使用 reviewIssues.resolveAccountMappings 普通已有账户/新建草稿流程。付款成分按其 memberRole 写入 paymentAccounts 的对应 componentIndex，允许逐个账户组确认，不要求其他成分同时完成；验证所给索引属于来源金融成分、无重复账户，以及可信 uid、正式账户或同批草稿、同币种、未归档。单一普通交易仍保存 ledgerAccountId；组合付款不把整笔 ledgerAccountId 设成第一个成分。payment_target 保存 counterpartyLedgerAccountId 并保留手工位，整理表单据此预选被还款账户。稳定引用沿用已有映射草稿机制；不稳定引用仅保存在本事件。更新事件后同步其他账户问题及仍开放的整理问题的成员版本（已解决的非账户历史快照不改），同笔多组按批次事务连续处理，不因上一组确认制造虚假版本冲突。

**AGROUP-07 修改和排除。** 按账户修改通过现有 revise 命令作用于该组关联事件，组合事件只改变对应付款成分/目标，不替换其他账户分项。若该事件后续已有已确认的非账户整理决定，现有冲突门禁仍禁止回改。当前“本次不计入”仍是排除该组所关联的整笔事件，不能仅丢弃组合交易的一部分；跨组出现的是同一事件，排除不会生成半笔交易。永久忽略仅用于有稳定引用的账户，不稳定引用不建立长期规则。最终入账的 paymentResolution 必须完整校验金额守恒、目标、性质等，账户分组本身不解除语义阻断。

**AGROUP-08 命令、事务和重试。** reviewIssues.refreshAccountGroups 是显式、幂等、批次版本受控的写命令，参数 requestId/updateId/version。小程序 prepare 后及加载 review 草稿时调用；financeUpdates.get 和 reviewIssues.get 自身保持只读。服务端锁批次并要求 review 与版本匹配；所有引用、问题/成员、事件版本、映射草稿、计数及 FinanceAction 在同一事务里提交。actionType=refresh_account_groups，expected/applied 版本和规则版本可审计；成功升级批次版本加一，无候选时不改变批次版本。重复 requestId 返回原结果；新请求在已升级草稿上不重复加成员。身份不符、过期、引用或账户校验失败整体回滚；前端失败显示错误，可重新加载重试，不能强行使用过时版本。没有新数据库列、运行时 DDL、正式 Transaction 写入或自动入账。

**AGROUP-09 展示与阶段流转。** grouped accountContext.fundsSide 为 payment_component_N/payment_target 时，issueView 不使用组合支付标题/专用弹层；普通账户名称、账户选择及查看交易入口保持一致。确认所有关联账户问题后，仍有金额/性质等阻断的事件进入整理；整理恢复已保存付款账户及 counterpartyLedgerAccountId，可按原门禁修改。来源不足或无稳定身份仍需人工账户选择，不能因为界面分组就猜分项金额。完整 paymentResolution 是最终正式分项依据，不把账户问题数量当作正式交易数量。

### 6.3.1 导入草稿与即时确认（MINI-1906UI-DRAFT）

- 输入：服务端已鉴权的 FinanceUpdate 完整视图、账户本地编辑及用户明确确认的核对／分类决定。按云环境和 updateId 隔离本地存储，恢复前必须成功 get/prepare 同一批次；只存决定、选项和必要关联 ID，不保存原始账单或完整交易。重新进入导入页自动恢复最后一个已验证批次及原选择，但未完成批次停在第一步；来源文件、账户和整理结果继续保留。
- 账户确认先将草稿及队列原子落入微信本机存储，再收起并刷新计数。方式、名称、类型变化撤销 localConfirmed 并递增 revision，同时撤回尚未发送的旧决定；已经发送的单项不能改写，其他项目仍可处理。未完成的账户表单也在变更时保存本机。
- 核对／分类确认经既有前端校验后，将 decision、issueId/issueVersion、相关事件 ID 和选择表单保存到同一队列，立即关闭当前弹层并投影已核对／所选分类。多个阻塞未全部确认时仍计入待核对；不在客户端推断新的财务关系、变更金额或修改正式就绪状态。后台响应保留另一张正在编辑的弹层，不覆盖未提交输入。
- 后台合并 700ms 内的决定：账户最多 50 项一请求，其他核对先于分类、按队列串行调用既有 resolve；每笔继续保留服务端版本、事务和幂等裁决，不引入跨请求事务。成功使用响应版本供下一项提交，队列排空后仅重读一次完整视图，不再每次确认都锁页面和完整重读。依赖变化导致的冲突交给服务端拒绝，不自动升级 issueVersion。
- 发送前持久化完整请求（包含版本和 requestId）；超时、响应丢失、进程恢复后原样重试。网络错误按 2／5／15 秒有限退避，随后保留手动重试。业务错误保留选择并恢复待核对展示；“重新核对”移出被拒绝命令，仍保留其选择供原项目重新打开时恢复，用户再次确认才生成新请求。存储失败时不发送新决定、不虚报保存成功。
- 下一步作为同步屏障：等待在途及排队决定完成后读取服务端视图，出现新阻塞问题则停在对应步骤。分类仍可跳过。最终 post 再执行同步屏障，只按权威 coverage/版本提交；完整 post 请求在本机持久化，响应不明时重用原请求。正式账户、映射、余额与交易仍由既有整批原子事务写入，前面的草稿同步不提前入账。
- 离页取消页面订阅但保留进行中的会话；重入同一批次复用，进程退出后从本机请求恢复。放弃先暂停队列并等待已发送请求结束，再取最新版本调用既有 abandon，成功才清理本机草稿；失败恢复同步。已入账／已放弃视图不自动发送旧决定。
- 第二至第四步上一步只切换页面，不重复解析。账户按钮保留“还需确认 N 项”，整理按钮保留“还需核对 N 笔”；本地计数用于提示，最终入账资格只由服务端决定。
- 代码：`miniprogram/services/import-draft-session.js`、`pages/import-workbench/index.js` 和 `model.js`；验证：`test/import-draft-session.test.js`、`test/import-account-choice.test.js`、`test/import-workbench-model.test.js`。无新增 schema 或后端接口；回滚前端不会撤回已经保存到导入域的决定，也不会改变正式账目。

## 银行还款目标归属不确定时的处理（MINI-1906OWN）

### 触发与证据边界

当前仅解析支付宝 App/Web CSV、微信 CSV/XLSX，不含直接银行卡账单解析。平台行必须先被既有整行语义规则识别为还款，且资金投影为 `kind=repayment`、目标为单一银行／信用卡引用；普通商户文本提及还款、普通转账、聚合负债分配与组合付款不复用本入口。对尚未映射的目标账户，银行名称、信用卡字样和卡尾号都不是账户属于本人的证明。服务端公开事件及问题 subject 的 `repaymentOwnershipRequired` 决定是否展示归属确认，不由客户端自行声称已取得银行卡账单证明。已明确选择的账户沿用原决定，不清空或追问历史正式账目。

### 输入、优先级与分支

核对弹层首先选择「自己的账户／替他人还款」，首次不预选。本人分支才展示账户候选和新建字段，只接受当前用户本人可用的信用卡或其他负债账户，不能与转出账户相同；新建名称、类型沿用原校验。保存时发送 `{ repaymentOwnership: { owner: "self" }, counterpartyLedgerAccountId }`，新建先用原有 `counterpartyLedgerAccountDraft` 在事务中转为草稿 ID。服务端记录用户确认来源，按 `repayment/neutral` 处理，等待最终整批入账时更新本人负债。

他人分支隐藏目标信用卡选择和新建，必须再选处理方式：

- 「无需收回，记为支出」发送 `{ repaymentOwnership: { owner: "other", treatment: "expense" } }`，保留转出账户和金额，清空目标账户、旧分类，设为 `expense/outflow`；进入已有待分类流程，分类仍沿用现有可跳过口径。
- 「需要收回或暂不确定，保留待核对」发送同结构但 treatment 为 `pending`，只保存已确认的他人归属，设为 `unknown/outflow`，保持 `repayment_other_treatment_required` 阻塞并生成后续核对项。此动作不是确认交易已整理完成，不能因此减少本地待核对数量或开放整批入账。本轮没有新增应收款资产／借出回收模型，不能把代垫强制记成支出。
- 未选择归属、未选择他人处理方式、本人未补齐有效账户均不能保存；「稍后处理」沿用不提交当前未确认表单的行为。

决定只覆盖当前明确展示的核对对象；新的归属问题按事件分开，不按同银行合组。归属弹层不提供同银行其他问题的批量套用。既有已人工确定的事件账户优先于系统推断；原始银行引用始终保留作证据，不因他人决定被改写。

### 写入、事务与最终入账

复用 `reviewIssues.resolve(decision=apply_fields)`，新增可选 `fields.repaymentOwnership`，只允许 `{owner:self}` 或 `{owner:other,treatment:expense|pending}`，拒绝额外证明字段和非法组合。服务端验证本事件适用条件；他人决定不得同时传账户绑定／新建／金额等字段。新建草稿若随后校验失败，随整个原事务回滚。决定以 `repayment-ownership-v1`、`confirmedBy=user` 存入当前事件 `field_sources_json.repaymentOwnership`，并通过 manual field mask 保留账户目标、性质、方向和分类的人工优先级；无 schema 变化，不写真实账目或永久银行归属规则。

账户查询仍由服务端 uid 限定，本人目标仅限同币种、未归档的信用卡／其他负债，跨用户 ID 拒绝。保存、动作审计、问题关闭／后续问题创建及批次计数沿用同一个幂等 MySQL 事务。正式余额、账户与交易仍只由原 `financeUpdates.post` 原子事务物化；pending 分支不能越过该屏障。

后续 `reconcileProjectedAccounts` 遇到已确认他人还款时保留原银行证据和已选转出账户，持续保持目标账户为空；同银行的新映射或本批其他账户确认不能再把它写成本人的信用卡。v26／v27 review 批次通过保留事件的升级入口进入 `organizer-plan-v28`，保留人工字段和归属标记；未确认银行目标即使来源语义没有变化，也补充归属原因并重建受影响开放核对项，旧共享项的其他成员保留，不重建已入账事件。

### 失败、刷新和重试

本地已确认选择复用导入草稿队列保存，后台同步及下一步等待屏障不变；网络失败沿用相同请求和幂等键重试。归属为 other/pending 的乐观投影保持该问题开放，不伪装成已核对；服务端返回后显示新的待核对项。冲突或非法账户会保留草稿并要求重新核对，不自动换账户或把他人款项转为支出。关闭后再次读取／进程恢复从服务端决定或原草稿恢复归属选项。

### MINI-1906UI-RESUME 自动恢复到第一步

### MINI-1906UI-COVERAGE 组合付款核对后的入账门禁修复

当组合付款已有有效人工分项、事件为 ready/posted 时，覆盖报告使用与事件可入账判断相同的 `effectiveSemanticReasons`，仅解除该决定允许解除的组合歧义和交易类型未知标记。原始 `reasonCodes`、`semanticBlockers` 仍保留；金额、账户端点或性质变化使决定失效时继续阻断，其他语义硬阻断、开放必核对问题和来源行守恒校验仍生效。待分类的非阻断建议不影响入账。

### 客户端读取复用与写入失效（MINI-1906UI-REQUESTS）

页面调用 catledger-api 时，登录门禁先于缓存；白名单查询以动作和完整排序参数为键。优先等待同领域在途写入，再用有效缓存，最后合并或发起同键云调用；force跳过缓存值但仍合并同代次请求。白名单查询在连续前台使用期间保留，App从后台恢复时统一失效。缓存最多48条，仅内存，向调用者返回副本；首页完整账户集合按源有效期供accounts.list复用。

read-policy声明每个正式写入影响的accounts/transactions/categories领域，发送前及结束后失效；失败也失效以处理提交结果未知，不因此重复写入。旧读取返回时检查领域代次，若已失效则等待相关写入并重读；退出更新会话代次并清空缓存，包括未缓存动作在内的旧响应不能交付。page-read-session清除跨会话页面数据与旧句柄，旧回调不能结束新请求或恢复连接状态。正式余额、事务和原有带幂等键重试规则不变。

普通切页命中新鲜结果不显示加载，已有内容在重读期间保留；手动刷新force读取服务端。明细筛选项和交易并行读取，按ID保持选择，新鲜回访保留分页；加载下一页期间首屏失效时重读首屏，禁止新旧拼接。普通记账不提前加载退款候选，进入退款才读取；失败显示重试，候选未就绪禁止保存退款。导入的草稿队列、核对证据和维护预览继续走原有读取与版本机制；仅post/undo/correct失效普通账本查询。其他设备修改在从后台恢复后按需重读或手动刷新时发现，不提供推送即时同步。

## 用户ID展示与复制（MINI-1904E / MINI-1904F）

触发条件：用户主动确认登录，或已有产品登录许可后进入“我的”。`catledger-api` 从可信微信上下文计算身份摘要，repository 在既有 bootstrap 事务中锁定身份并读取其 uid；新用户生成首位非0的10位数字字符串UID，再创建身份映射和默认分类，提交成功后返回该uid。重复/并发初始化继续由原身份唯一索引与有限重试裁决，返回已提交用户主键；旧UUID通过0011显式迁移，所有正式归属仍只用一个uid，不新增业务表或永久别名。handler 只增加 uid 响应字段，不接受客户端 uid 或 OpenID，不改变任何账本查询的服务端身份条件。

客户端成功登录将 uid 留在 app 内存，资料存储仍只保存头像昵称。“我的”读取 bootstrap 结果，把原 uid 保存于会话并将相同完整值放入displayUid用于展示，刚登录已确认身份时复用本次返回值，避免追加请求。uid 受现有读取会话检查保护；退出清除 app 和页面值，重启等待重新读取，旧请求不能回填。现有后端缺少 uid 时显示“ID 暂未获取”并提供强制刷新重试，不在客户端随机生成，也不从头像昵称缓存推断。账户摘要失败不撤销已确认的 ID；bootstrap 失败沿用原连接提示与重试规则。

点击 ID 时只在当前已登录读取会话调用 `wx.setClipboardData`，复制同一完整10位uid，不在客户端另行编号。成功提示“ID 已复制”，失败提示“复制失败，请重试”，不写云端。用户可在反馈时主动提供 ID，现有反馈入口的缺失不在本轮扩展。ID 不是登录凭证，OpenID、身份摘要与普通日志隐私约束不变。

代码入口：`cloudfunctions/catledger-api/src/user-repository.js`、`handler.js`、`shared/catledger-api.json`、`miniprogram/app.js`、`components/login-sheet/`、`pages/profile/`。验证入口：API `handler.test.js`（返回原 uid、伪造输入拒绝及日志不含身份）、`user-repository.test.js`（冲突重试采用获胜 uid）、`integration.test.js`（原主键一致、重复/并发稳定、身份隔离、事务回滚），以及 `test/login-default-profile.test.js` 和 `test/cached-page-requests.test.js`（会话清除、复制、缺字段提示与强制刷新重试）。原uid响应已于2026-09-10更新开发云，并通过当前真实微信会话读取验证；小程序界面尚未重新上传，真机仍待验收。


MINI-1904E 界面收口：昵称下只保留ID；移除常驻成功连接文案和三列摘要卡片，账户/分类计数仍由原请求更新并在管理入口展示。未取得ID且正在读取时显示“ID 读取中…”，读取结束仍缺少时显示“ID 暂未获取”；点击该处重试或错误提示时以force重新读取bootstrap与账户数据，避开旧响应缓存。内部connected仍区分身份和局部摘要结果，失败不伪造零值，也不清除同会话已知ID。首页三个分区标题改为28rpx、页头头像56rpx/16rpx圆角；金额、图表高度与比例、请求和数据流均沿用原逻辑。验证入口为既有page-refresh、cached-page-requests、ui-all-pages、ui-system及微信开发者工具；不为尺寸另写测试。

## 10位用户UID生成与历史归属迁移（MINI-1904F）

触发与优先级：已存微信身份优先读取其uid，重复登录不重新编号；新用户使用`crypto.randomInt(1000000000, 10000000000)`生成数字字符串。用户表主键裁决碰撞；ER_DUP_ENTRY回滚用户、身份、默认分类整体事务，再取新值，最多5次。并发同微信身份仍读取获胜身份的同一uid；上限或其他错误按现有失败信封返回，无默认占位ID。客户端只接收自己的uid，仍不接受以uid指定调用身份。

SQL整事务实现（未用于最终开发云切换，实际维护模式见下文）：`0011_short_user_ids.sql`先核对0010的29张uid业务表均为InnoDB/CHAR(36)、不存在未审查触发器，并取得迁移连接锁；同一事务先锁身份、再锁用户行。旧UUID使用数据库安全随机字节、拒绝采样和临时唯一索引分配10位ID，原短ID直接保留；分配连续碰撞32次则失败。临时映射仅存在当前连接中，不成为产品身份表。

写入边界：在同一事务中更新所有业务uid列，显式保持ON UPDATE时间列，按表核对受影响行数与未映射归属，并逐一反查全部外键，检查通过后提交。仅迁移连接暂时关闭即时外键检查；不能用“重新开启检查”替代逐行关联验证。旧账本实体ID、金额、内容、分类、幂等摘要/结果、版本和时间戳均保持。任何步骤失败整体回滚，恢复连接设置并销毁临时映射；提交后尚未登记checksum而中断时可直接重跑，已经缩短的UID不会再变。

导入与并发：已有storage_object_key、cloud_file_id及返回过的cloudPath不改动，继续通过当前身份对应的导入记录进行精确对象校验；新文件路径使用新UID。已完成解析、来源身份去重、单文件入账与FinanceUpdate整批入账全部沿用既有规则。迁移先等待已有写事务，切换前读出旧uid但尚未取得写锁的请求可能失败并回滚；刷新后用原requestId重试，不允许把失败当作成功或产生新归属。迁移期间不新增常驻服务、运行时建表或数据重建逻辑。

限制与入口：该迁移用于0010基线，未审查的新表/触发器应停止并单独更新方案；云函数代码回退仍可使用10位字符串UID，数据不反向迁移旧UUID。代码入口为`src/user-id.js`、`src/user-repository.js`、`migrations/0011_short_user_ids.sql`及`migrations/runner.js`；数据库验证由API `test/helpers/short-user-id-migration.js`注册到现有integration测试，覆盖29表非空合成数据逐项一致、重跑稳定、存储路径与幂等重放、跨用户隔离、故障回滚、碰撞与并发。前端入口与会话保护沿用上一节。


MINI-1904F 原生连接适配：`migrations/short-user-id-native.js`在同一连接内执行与0011相同的用户锁定、临时唯一映射、29表UID更新及时间戳保持、72外键校验，失败回滚；不创建永久第二ID。设置`CATLEDGER_TEST_NATIVE_UID_MIGRATION=1`运行API integration中的0011及短UID测试可覆盖此路径。早期大事务模式在开发云触发断连；最终使用下述维护窗口分段模式完成，SQL大事务模式不得用于该小规格实例直接重试。
