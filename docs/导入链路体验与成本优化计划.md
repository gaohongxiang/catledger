# 导入链路体验与成本优化计划

> 状态：进行中（P1 已实现，待真机/弱网与基准验收）。目标编号：`IMPORT-OPT-20261019`。
> 本文是本次改造的实施方案，不改变现行 [R21](招财猫记账本业务规则与验收.md#21-完整草稿与本地核对r21)，也不构成迁移、部署或发布授权。任务状态只维护在[实施规划](招财猫记账本实施规划.md)。

## 1. 目标与边界

### 1.1 目标

1. **降低首次可用时间**：从选完文件到能开始核对的总等待更短，弱网下可恢复，不再一次失败就从头下载。
2. **降低腾讯云成本**：优先减少云函数分块调用、临时快照和数据库压力，而不是只砍最便宜的对象存储。
3. **明确原件保留策略**：原件按状态分级、限期保留；该留的留，该删的删，不做永久堆积。
4. **不牺牲正确性**：完整快照、版本校验、不打开半份结果、单事务入账和用户隔离保持。

### 1.2 非目标

- 不把解析搬到客户端作为主方案；服务端仍是原文校验、来源身份、历史去重和审计的权威。
- 不取消“完整快照后才开放交易核对”；如要调整，必须先改 R21 和产品口径。
- 不改正式账务、退款、贷款和余额语义。
- 不把原始文件二进制或 Base64 写入数据库。
- 不自动执行迁移、部署、上传或发布。

### 1.3 约束

- 请求 64KiB、响应 256KiB、快照 256MB/16384 块的现行协议预算不放宽。
- 原始账单、完整账户和交易信息不进入普通日志、提交或聊天。
- 云端用户隔离、最小权限、幂等回执和原请求恢复继续成立。
- 优先复用现有 `content_deleted_at`、`idx_catledger_import_files_cleanup` 和本地草稿协议，避免为优化再造一套状态。

## 2. 现状与基线

### 2.1 现行链路

```text
选文件
→ imports.prepareMany        建批次、分配私有云存储路径
→ 客户端直传云存储
→ imports.parseFile          云函数下载原件、解析、落库
→ financeUpdates.prepare     跨文件整理事件、关系、问题
→ prepareSnapshot            编码不可变快照、分块写 MySQL
→ snapshotManifest
→ N × snapshotChunk          客户端逐块串行下载、校验、落盘
→ 本地核对                    0 网络
→ N × stageDecisions
→ sealDecisions
→ financeUpdates.post        单事务复核入账
```

### 2.2 已知基线

以下来自[实施规划](招财猫记账本实施规划.md)的本机隔离容量测试，**不是手机或云网络时延**：

| 样本 | 快照 | 分块 | 本机下载 |
| --- | --- | --- | --- |
| 3,000 行 | 5,013,315 字节 | 38 块 | 未单独记录 |
| 24,990 行 | 43,136,336 字节 | 320 块 | 4.5～4.9 秒 |

补充事实：

- 客户端目前逐块串行 `await`，见 [import-local-files.js](../miniprogram/packages/finance/services/import-local-files.js)。
- 每次 `snapshotChunk`、`stageDecisions` 都是一次云函数调用；3,000 行约 38 个快照块 + 17 个决定块，24,990 行约 320 + 138 块。
- 原件在私有云存储；入账、放弃、丢弃、重复复用时清理；未入账且无后续动作时会一直保留，当前没有定时清扫。
- 数据库保存 `raw_fields_json` 等原文，删原件不等于删证据，见[数据生命周期](现行说明/数据生命周期.md)。
- 完整快照的门禁见 [R21](招财猫记账本业务规则与验收.md#21-完整草稿与本地核对r21) 与[草稿本地化方案](导入草稿本地化与保温方案.md)。

### 2.3 2026-10-19 云端初步观测

通过 CloudBase CLI 读取环境、套餐、存储和数据库聚合数据；金额账单因当前登录身份缺少财务只读权限，尚未取得。

| 项目 | 现状 |
| --- | --- |
| 环境套餐 | 个人版 `baas_personal`，ap-shanghai，状态 Normal；公开资料为 19.9 元/月、40,000 资源点，但当前环境 CLI 报“非资源点计费模式”，实际配额以套餐页为准 |
| 续费 | 预付费、自动续费开启，到期 2027-01-19；`EnableOverrun=false`，未开启超限按量 |
| 云存储原件 | 15 个对象，合计约 0.41MiB；其中 8 个超过 30 天 |
| MySQL | 48 张表，data+index 约 61.78MB；Serverless CynosDB，0.25～0.5 CCU，实例处于可暂停状态 |
| 当前快照 | 1 个 sealed snapshot，8 块，约 0.96MB；仅 1 个 `local_v3` review 批次 |
| 10 月 1～19 日云函数调用 | import 4,943 次，API 1,618 次；错误 1、2 次 |
| 待清理原件 | 10 个 `failed` 对象；另有 12 个 `awaiting_upload` 记录，未见实际对象 |

初步判断：**当前规模下，原件存储和数据库都不是成本主因**。0.41MiB 原件即使全部删除，节省也几乎不可见；真正需要先确认的是云函数调用/时长、CDN/外网流量和 MySQL 计费方式。若按资源点口径，4,943 + 1,618 次调用约消耗 8.5 点，远低于 40,000 点；但这个换算不含数据库调用、函数资源用量和可能的最低消费，且当前环境并非资源点模式，不能替代真实账单。

因此，**P2 的原件清理在当前规模下主要是隐私和卫生收益，不是降本主力**；如果目标是降本，应先看 P3 快速入账、P5 快照传输和云函数调用结构，而不是删这 0.41MiB。

### 2.4 上线前的解释边界

以上是**上线前自测数据**，只能证明测试环境没有异常消耗，不能当作生产账单基线，也不能用来判断“用户多了以后贵不贵”。上线后的成本主要由四个变量决定：

- 每月导入批次数 `I`；
- 每批文件数和行数（决定快照、决定块和 SQL 数）；
- 单批云函数调用数、SQL 数和快照字节数（单位成本）；
- 原件和临时对象的保留天数 `D`。

所以现在要测的不是“账户里还剩多少钱”，而是**单次导入的单位成本**；用户量上来后，用 `I × 单位成本` 外推。

### 2.5 生产单位成本模型（待真实数据校准）

单批导入的近似结构：

```text
Calls ≈ 每文件 parse + prepare + prepareSnapshot + manifest 页数
        + snapshotChunks + decisionChunks + seal + post
Bytes ≈ snapshot 字节数
SQL   ≈ 解析写入 + 整理写入 + 核对读取 + 入账事务
Storage-days ≈ 未入账原件数 × 文件大小 × 保留天数
```

按当前容量样本：

| 档位 | 单批快照 | 单批云函数调用量级 | 单批入账 SQL | 说明 |
| --- | --- | --- | --- | --- |
| 3,000 行 | 约 5.0MB / 38 块 | 约 60～100 次 | 入账事务约 527 次，另加解析/整理/读取 | 普通个人账单上限附近 |
| 24,990 行 | 约 43.1MB / 320 块 | 约 450～550 次 | 入账事务约 3,386 次，另加解析/整理/读取 | 5 文件压力上限，不等于手机目标 |

上线后按三个节点校准：

1. **前 100 批**：确认单位成本是否与合成测试同量级；若单批调用/字节明显偏高，先修协议或客户端，不急着改业务。
2. **前 1,000 批**：用真实账单核对 `I × 单位成本`，判断是否接近套餐点数或超限；再决定是否做 P3/P5。
3. **前 10,000 批**：检查留存原件、快照临时对象、日志和数据库增长；此时再定 TTL 和归档策略。

**当前不建议做的事**：为了 0.41MiB 原件做架构改造；在没有真实用户数据时升级套餐；按测试数据预测生产账单。**当前建议做的事**：把单位成本指标埋好，保留 P1 的体验优化，等真实导入量上来再按数据决策。

### 2.6 需要补的观测

当前缺少按阶段、按账单规模的稳定指标，先补观测，避免“凭感觉优化”：

| 指标 | 用途 |
| --- | --- |
| 上传、解析、整理、快照生成、manifest、下载、解码各阶段耗时 | 找到真实首屏瓶颈 |
| 快照/决定块数、字节数、重试次数、续传命中 | 量化传输成本 |
| 每批云函数调用次数与时长 | 对齐腾讯云账单 |
| 原件按状态/年龄的字节数 | 决定 TTL 和清理频率 |
| 手机内存峰值、OOM/崩溃 | 判断大账单上限 |
| 用户从选文件到开始核对、到入账的完成率 | 判断等待是否导致放弃 |

## 3. 方案总览

| 阶段 | 内容 | 预期收益 | 风险 | 粗估 |
| --- | --- | --- | --- | --- |
| P0 | 观测与基线 | 知道钱和时间花在哪 | 低 | 1～2 人日 |
| P1 | 并行下载、断点续传、单块内联、进度文案 | 弱网等待和重试成本明显下降 | 低 | 4～6 人日 |
| P2 | 原件分级保留与 TTL 清理 | 降低存储/隐私面，行为不变 | 中 | 3～5 人日 |
| P3 | 干净批次快速入账 | 省掉整份快照和分块调用 | 中高，需产品拍板 | 5～10 人日 |
| P4 | 账户预确认/两段式快照 | 首屏更早可用 | 高，需改 R21 口径 | 5～15 人日 |
| P5 | 快照传输与大账单内存 | 降调用/DB 压力，覆盖大账单 | 中高，按实测决定 | 5～15 人日 |

执行顺序建议：**P0 → P1 → P2 → 决策门 → P3/P4/P5**。P1 是纯收益，先做；P3 省得最多但改产品口径；P4 体验最好但架构复杂；P5 必须有账单和真机数据再动。

## 4. P0：观测与基线

### 4.1 任务

- **OPT-01 客户端阶段计时**：在上传、解析回执、整理、快照生成、manifest、逐块下载、解码、首屏可核对分别打点；只记录阶段、耗时、块数、字节数、结果码，不记录原文、账户或交易字段。
- **OPT-02 服务端调用计量**：按 `imports.parseFile`、`prepareSnapshot`、`snapshotManifest`、`snapshotChunk`、`stageDecisions`、`sealDecisions`、`post` 统计调用次数、时长和错误码；沿用现有 performance observer，不新增敏感日志。
- **OPT-03 成本盘点**：从腾讯云账单分别拉 COS、云函数、MySQL 的用量；至少区分存储、请求、流量、函数调用/GB·秒。没有账单就先用调用次数和字节数做代理指标。
- **OPT-04 真机基线**：iPhone/Android 各一台，Wi-Fi 与 4G/弱网，至少覆盖 100、3,000、10,000 行；记录首屏时间、下载 P50/P95、内存峰值、失败和放弃率。

### 4.2 产出

- 一份基线报告：按阶段、按规模、按网络类型的时间与调用表。
- 一张成本拆分表：原件、快照、决定、云函数、MySQL 各占多少。
- 一个明确的决策门：如果下载占首屏等待不到 20%，优先做 P4；如果超过 40%，优先做 P1/P5；如果原件成本占比很低，P2 只做隐私和卫生，不投入过度。

### 4.3 验收

- 同一批合成数据重复测量，阶段耗时之和与端到端时间误差可解释。
- 不出现原始字段、完整账号或数据库绑定值。
- 基线报告能回答“3,000 行和 25,000 行分别慢在哪、贵在哪”。

## 5. P1：低风险体验优化

### 5.1 OPT-05 分块下载并行化

- 将顺序 `for` 改为有界并发，默认 4 路，可配置降到 2；每块仍独立校验 `objectId`、`baseVersion`、`index`、字节数和 SHA-256。
- 落盘仍按 `part-<index>.json` 写不同文件；进度按“已完成块数”统计，不要求按序完成。
- 只有全部块校验通过、整体清单验证通过后，才写 `complete-*` 标记；任何一块失败都不能开放编辑。
- 对 429/超时做退避；并发过高触发限流时自动降级，不把限流错误当成草稿损坏。
- 兼容旧服务端：功能开关关闭或 manifest 不支持时退回串行。

### 5.2 OPT-06 断点续传

- 同一 `objectId` 下，重试前检查已有 `part-*.json`：重新计算摘要并与 manifest 描述符比对，匹配则跳过下载，不匹配则重下该块。
- 只允许跨同一 `objectId`、同一 `baseVersion`、同一根摘要复用；版本或对象变化时清理/忽略旧块，不能混代次。
- 失败后保留已校验块和完整旧代次；用户重试只补缺块。
- 记录续传命中块数/字节数，作为成本指标。

### 5.3 OPT-07 单块小快照内联

- `prepareSnapshot` 在快照只有 1 块且响应预算允许时，直接返回内容；客户端按同一摘要规则校验。
- 超过 256KiB 响应预算、块数大于 1 或旧客户端时，仍走 manifest + chunk。
- 内联失败必须可回退到分块，不能出现“服务端说内联、客户端无法验证”的半状态。

### 5.4 OPT-08 进度与文案

- 首次等待显示阶段（上传/解析/整理/准备核对资料/下载核对资料），不只显示“3 / 38”。
- 每份文件解析完成即显示行数、模板、日期范围和账户提示；整理完成后显示“已识别 N 条、M 个待核对问题”。
- 进度更新必须单调；迟到响应、切页、换用户后不回填。
- 不展示技术块号、SQL、文件路径或原始字段。

### 5.5 代码入口

- 客户端：[import-local-files.js](../miniprogram/packages/finance/services/import-local-files.js)、[import-local-manager.js](../miniprogram/packages/finance/services/import-local-manager.js)、[runtime.js](../miniprogram/packages/finance/pages/import-workbench/runtime.js)。
- 服务端：[local-review-objects.js](../cloudfunctions/catledger-import/src/local-review-objects.js)、[local-review-protocol.js](../cloudfunctions/catledger-import/src/local-review-protocol.js)。
- 测试：[import-local-files.test.js](../test/import-local-files.test.js)、[import-local-page.test.js](../test/import-local-page.test.js)、[benchmark-local-review.js](../scripts/benchmark-local-review.js)。

### 5.6 验收

- 缺块、乱序、重复、混版本、摘要错误、单块中断仍不开放半份草稿。
- 并发下载与串行下载得到完全相同的 facts、块数、根摘要和本地文件。
- 续传只复用同代次块；换对象/换版本必须重下。
- 3,000/25,000 行弱网下载 P95 相对基线下降至少 50%（目标值在 P0 后校准）。
- 重试场景重复下载字节下降至少 90%。
- 现有完整下载、恢复、换号、清理测试不回归。

## 6. P2：原件分级保留与清理

### 6.1 保留策略

| 状态 | 保留 | 理由 |
| --- | --- | --- |
| `awaiting_upload` | 短期保留（建议 24 小时） | 上传中断可重试 |
| `failed` / `BANK_MAPPING_REQUIRED` | 保留（建议 30 天） | 需要重新解析/列映射 |
| `review_ready` 未入账 | 解析成功后短期保留（建议 7 天） | 支持排查、重解析；核对本身不依赖原件 |
| `committed` / `duplicate` / `discarded` / `abandoned` | 立即删除，失败重试 | 已不需要原件 |

保留期做成配置，不写死在页面；默认值经评审后定。

### 6.2 OPT-09 清理任务

- 新增有界清理入口：按 `content_deleted_at IS NULL`、状态、`updated_at` 年龄筛选当前用户或全局批次，单次最多 50 个对象。
- 先 `storage.remove` 成功，再写 `content_deleted_at`；删除失败不标记为已删除，保留重试。
- 清理必须幂等、用户隔离、可观测（只记录数量/结果码，不记录文件名或路径）。
- 实现方式二选一：
  - **优先**：新增受授权的定时清理函数/触发器，按批处理，最可靠；
  - **备选**：在准备/进入导入时有界清扫当前用户，避免新增触发器，但会增加请求延迟，必须严格限流。
- 不做破坏性回溯：不批量删数据库原文、审计、回执或正式账目。

### 6.3 本机是否保存原件

- **默认不做**。本机已保存完整快照，原件只增加敏感数据和清理负担；对象存储本身不是主要成本。
- 如隐私或合规要求“服务端不留原件”，可选：解析成功后删服务端对象，本机在 `USER_DATA_PATH` 留一份短期副本，用于失败重传/重解析；成功、放弃、注销时删除，失败可补清。
- 该选项单独评审，不能默认开启；它不解决跨设备恢复，也会增加本机空间和泄露面。

### 6.4 验收

- 超过保留期的 `review_ready`、`failed`、`awaiting_upload` 文件按策略删除；未到期、待映射、当前正在使用的文件不删。
- 删除失败不写 `content_deleted_at`，下次可重试。
- 入账、放弃、丢弃、重复复用路径的清理行为不回归。
- 清理不跨用户，不删除原始行、事件、回执或正式账目。
- 上线后按周统计：超期原件数量为 0，清理失败可告警。

## 7. P3：干净批次快速入账（需产品拍板）

### 7.1 适用条件

同时满足才允许：

- 所选事件全部 `ready`，没有 open issue、冲突、待配对、待退款、待分期归属。
- 账户已确认或有可靠历史映射，不需要新建账户。
- 用户没有修改金额、时间、性质、账户、分类或关系。
- 没有历史重复待办、贷款费用保护、现金约束风险。

### 7.2 流程

```text
服务端摘要确认“无阻断”
→ 展示交易笔数、金额汇总、账户、来源、问题数 0
→ 用户明确确认
→ 直接 financeUpdates.post（空决定/默认决定）
→ 服务端按当前账本复核
→ 成功入账；冲突则退回完整核对
```

### 7.3 收益与代价

- 收益：省掉整份快照生成、manifest、N 个下载块和 N 个决定块；对简单账单是最大的一笔云函数/传输节省。
- 代价：放松“逐笔核对”的产品口径；如果产品要求每笔都看，不能做。
- 必须保留：服务端复核、幂等、冲突回退、用户明确确认；不能变成“上传即入账”。

### 7.4 验收

- 只在 0 问题时出现快速入口；任何阻断都退回完整核对。
- 冲突/版本变化不产生半批入账。
- 快速路径与完整路径最终账务结果一致；重复提交只入账一次。
- 需要产品/规则文档同步更新，不能只改页面。

## 8. P4：账户预确认与两段式快照（需改契约）

### 8.1 目标

把“账户确认”从“交易核对”里拆出来，让用户在整理/下载进行时先处理账户和计入范围；**交易核对仍然等完整快照**。

### 8.2 可选实现

- **轻量版**：`prepare` 后先返回紧凑的账户/来源/计入范围摘要，页面打开账户步骤；完整快照下载完成后绑定本地决定，再开放交易核对。
- **完整版（两段式快照）**：base facts 快照 + relation delta 快照，两者绑定同一 `baseVersion`；账户步骤可先基于 base facts，交易核对必须等 delta 完整并校验。
- 无论哪种，都不能让用户在关系未完整时做“同笔/退款/还款/分期归属”决定。

### 8.3 风险

- 账户决定可能与后续整理结果冲突，需要重绑/重核。
- 两个版本的绑定、清理和恢复比单快照复杂。
- R21 的“完整快照后才开放核对”需要明确改写为“交易核对前完整；账户预确认可提前”，否则测试和口径会打架。

### 8.4 验收

- 完整快照未完成时，交易编辑、配对、退款、还款、分期归属入口不可用。
- 账户决定在快照到达后正确绑定；版本冲突保留决定并提示重核。
- 迟到下载、换用户、放弃、后台切换不把预确认数据带入其他会话。
- 原有 12 项 R21 反例继续通过。

## 9. P5：快照传输与大账单内存（按实测决定）

### 9.1 快照传输

- 评估把快照作为私有对象存储的短期对象，客户端一次性下载/断点续传，减少 N 次云函数调用和 MySQL 分块读取。
- 必须满足：短期生命周期、用户隔离、签名 URL 短有效期、摘要校验、成功/放弃清理；这与现行“云存储只放原始文件”的规则冲突，需先改规则。
- 备选：服务端流式返回、压缩、减少块数；不要在没有账单数据时先做。

### 9.2 大账单内存

- 真机验证 3,000/10,000/25,000 行的峰值内存；25,000 行本机客户端 RSS 已到数百 MB，不能假设手机可承受。
- 可选：分页/懒解码原文、只保留当前页对象、降低 `sourceRows` 上限、按文件分批核对；任何方案都不能破坏整批单事务入账。
- 如果真机 OOM，优先给出明确上限和拆分提示，而不是静默崩溃。

## 10. 成本模型与决策门

### 10.1 每次导入的主要成本

```text
COS：原件存储 + 上传/下载请求 + 流量
云函数：每份 parse + prepare + prepareSnapshot + manifest + N×chunk + N×stage + seal + post
MySQL：原文行 + 快照对象/分块 + 暂存决定 + 查询/写入
客户端：下载流量 + 本地文件 + 内存
```

### 10.2 决策门

- **G1（P0 后）**：下载是否占首屏等待 >40%？是 → P1/P5 优先；否 → P4 优先。
- **G2（P2 后）**：原件存储在总成本中占比是否 >10%？否 → 不再为省原件做架构改动，只保留卫生清理。
- **G3（P3 前）**：产品是否接受“0 问题批次汇总确认后入账”？不接受 → 取消 P3。
- **G4（P4 前）**：是否接受账户预确认早于完整快照？不接受 → 只做 P1。
- **G5（P5 前）**：是否有真实手机 OOM 或云账单证明分块调用是主要成本？没有 → 暂缓。

## 11. 验证与交付

### 11.1 验证层次

- 单元/Page：并行、续传、内联、进度、失败恢复、换号隔离。
- 隔离 MySQL：清理状态、用户隔离、删除失败重试、入账/放弃路径不回归。
- 容量：用[基准脚本](../scripts/benchmark-local-review.js)复测 3,000/24,990 行，记录调用数、字节、耗时、RSS。
- 真机：iPhone/Android、Wi-Fi/4G/弱网，分别报告，不用模拟器代替。
- 云端：先用合成数据观察调用和账单，再决定是否放量；不自动部署。

### 11.2 文档

- P1 不改变业务语义，更新架构/开发说明中的传输细节即可。
- P2 改变原件生命周期，更新[数据生命周期](现行说明/数据生命周期.md)、主逻辑导入章节和架构。
- P3/P4 改变产品口径，先更新[用户需求](招财猫记账本用户需求.md)、[业务规则](招财猫记账本业务规则与验收.md)，再改代码。
- 任务状态、分支、部署和验收只在[实施规划](招财猫记账本实施规划.md)维护。

### 11.3 交付门

- P1：功能开关可关；旧客户端可回退；无迁移。
- P2：清理默认 dry-run/关闭，评审后开启；删除失败可重试；需要运维授权。

- P5：对象存储/定时触发器需单独授权；不做静默策略变更。

## 12. 风险与回滚

| 风险 | 缓解 | 回滚 |
| --- | --- | --- |
| 并发下载触发云函数限流 | 4 路起步、退避、自动降级 | 关闭并发开关回串行 |
| 续传混入旧代次 | 绑定 objectId/baseVersion/根摘要，逐块校验 | 清空当前对象块，重新下载 |
| 内联超响应预算 | 先算 wire bytes，超限回退分块 | 关闭内联开关 |
| TTL 误删待用原件 | 状态白名单、宽限期、dry-run、删除前复查 | 停止清理任务；从数据库原文恢复核对，不伪造原件 |
| 快速入账绕过核对 | 仅 0 问题 + 明确确认 + 服务端复核 | 关闭入口，回完整核对 |
| 账户预确认产生半份状态 | 交易核对仍等完整快照；版本冲突重核 | 关闭预确认，回原流程 |
| 快照对象存储扩大泄露面 | 私有桶、短签名 URL、用户范围、摘要校验 | 回 MySQL 分块传输 |
| 大账单拆分破坏原子入账 | 只拆本地核对/传输，不拆最终 post 事务 | 回单批完整快照 |
