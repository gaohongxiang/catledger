# 个人财务来源记录身份与重复语义设计

> 关联：[个人财务业务规则与验收.md](./个人财务业务规则与验收.md)、[个人财务架构设计.md](./个人财务架构设计.md)、[个人财务待处理问题与关系裁决设计.md](./个人财务待处理问题与关系裁决设计.md)
> 安全边界：不修改正式交易，不执行真实入账；现有原文件和原始行作为重建事实保留

## 1. 问题与结论

光大信用卡月结单没有稳定交易流水号。旧规则在交易号和订单号缺失时，使用日期、金额、币种、方向、经济效果、交易说明、商品和付款方式生成强内容指纹，并把相同指纹当作同一来源身份。因此，同一文件中内容完全相同但位于不同物理行的真实消费会被标记为“精确重复”，并在经济事件生成前提前折叠。

已确认的回归场景是：同一银行账单中，2026/07/01 的两条 ¥43.50 记录以及 2026/07/06 的两条 ¥43.50 记录分别位于不同物理行。四行代表四笔真实消费，不是两笔重复。

冻结结论：

1. **内容是属性，不是身份。** 日期、金额、商户、说明、付款账户和时间完全相同，也不能证明是同一笔交易。
2. **证据集合是多重集。** 内容相同的多个物理行必须分别保留出现次数。
3. **不同物理行默认是不同来源记录。** 只有稳定来源标识或同一文件的同一物理定位能够证明来源记录身份相同。
4. **来源记录身份与经济事件身份分开。** 银行记录和支付宝记录可以共同证明一个经济事件，但任何来源记录都不能在跨来源核对前被内容指纹吞掉。
5. **不确定时保留多笔。** 系统承担暂时多保留的核对成本，不承担静默丢失真实消费的风险。

## 2. 严格分层

| 层级 | 含义 | 身份依据 | 是否可以减少经济事件数量 |
| --- | --- | --- | --- |
| 原文件 `ImportFile` | 用户上传的一份不可变内容 | `uid + 文件 SHA-256` | 否 |
| 解析批次 `ImportBatch` | 某解析器、版本和参数的一次运行 | 批次 ID、文件、规则版本 | 否 |
| 原始证据行 `RawImportRow` | 文件中的一个物理记录观察 | 文件内容身份 + 物理定位 | 否 |
| 来源记录身份 `SourceIdentity` | 来源系统中的同一条记录 | 稳定来源标识，或文件内容 + 物理定位 | 只折叠同一来源记录的再次观察 |
| 经济事件 `EconomicEvent` | 现实中发生的一次消费、退款、转账等 | 已确认的证据归属与关系 | 是，一个事件可有多条证据 |
| 正式交易 `Transaction` | 权威账本效果 | 事件与入账幂等关系 | 一个事件只入账一次 |

候选、相似度和内容签名不属于身份层。它们只能帮助召回可能相关的来源记录。

## 3. 来源记录身份规则

### 3.1 稳定来源标识

来源明确提供并由适配器验证可用时，按以下优先级确定来源记录身份：

1. 同一来源账户下的稳定交易流水号；
2. 同一来源账户下同时存在的稳定订单号与商户订单号组合。

脱敏编号、单独一个订单号、占位符和过短或明显掩码的字符串不属于稳定标识。

相同稳定身份再次出现：

- 核心语义一致：属于同一来源记录的再次观察；
- 金额、币种、方向或经济效果冲突：形成来源身份冲突，保留全部证据并阻塞相关事件；
- 不得用后来记录覆盖第一次观察的核心摘要。

不同稳定交易号或不同稳定订单组合明确代表不同来源记录，即使其余内容完全相同。

### 3.2 无稳定来源标识

没有可靠交易号或订单组合时，来源记录身份必须使用：

`文件内容 SHA-256 + 规范化物理定位`

物理定位按载体保存：

- CSV：原始记录起止行；
- XLSX：工作表与原始行号；
- PDF：页码与页内物理行号；
- 后续格式：必须提供可重复定位到原内容的稳定 locator。

因此：

- 同一文件的同一物理行重解析，仍是同一来源记录；即使解析器升级后新提取出稳定交易号，也不得把同一物理记录拆成两个事件；
- 同一文件的不同物理行，无论内容是否相同，都是不同来源记录；
- 不同文件中的相同内容在没有稳定标识时默认是不同来源记录，只能进入重叠候选；
- 批次 ID 和解析后顺序不得作为跨重解析身份，因为它们会随解析运行变化。

### 3.3 内容签名

日期、金额、币种、方向、商户、商品、说明和支付方式可以继续形成内容签名，但其权限被限定为：

- 搜索和相似候选召回；
- 跨来源一对一匹配评分；
- 退款、转账和历史交易候选排序；
- 核对页面的相似记录展示。

内容签名不得用于数据库唯一约束、来源身份键、自动删除、同来源物理行折叠或直接减少经济事件数量。“强指纹”作为来源身份的旧行为停止用于新解析。

## 4. 重复概念拆分

| 场景 | 领域名称 | 正确处理 |
| --- | --- | --- |
| 相同文件内容再次上传 | 重复文件 | 返回已有文件；不创建第二份原始内容 |
| 同一文件显式重解析 | 解析重放 | 新批次、旧批次保留；同一 locator 复用来源记录身份 |
| 同一稳定流水号再次出现 | 同一来源记录再次观察 | 保留证据，复用来源身份；核心冲突转人工 |
| 不同文件疑似覆盖同一银行记录 | 来源重叠候选 | 一对一候选；无确定依据时不自动折叠 |
| 银行与支付平台记录同一次消费 | 跨来源同一经济事件 | 两条来源记录归入一个事件，不删除任一证据 |
| 同日同额同商户发生多次 | 多次相同消费 | 保留多条来源记录和多个事件 |
| 同一事件再次写正式账本 | 重复入账 | 由事件交易链接和幂等约束阻止 |

产品文案不得用一个“重复”数字同时表示上述不同事实。

## 5. 跨来源匹配与基数守恒

跨来源核对的输入必须是完整来源记录多重集。处理顺序固定为：

`完整物理证据 → 来源记录身份 → 保留所有独立记录 → 跨来源候选 → 一对一或组级数量匹配 → 经济事件`

### 5.1 自动确认条件

自动归入同一经济事件至少要求：

- 来源账户、金额、币种、方向和经济语义兼容；
- 来源类型不同；
- 有共享稳定业务引用，或存在唯一、完整的一对一解释；
- 日期级银行记录与高精度支付记录匹配时，使用自然日和数量约束；
- 同一候选组中每条来源记录最多使用一次。

普通金额、日期和文本相似只能产生候选。

### 5.2 多重集规则

假设银行有两条内容相同记录，支付宝有两个不同交易号：

- 必须保留两条银行来源记录和两条支付宝来源记录；
- 完整一对一匹配后形成两个经济事件、四条证据；
- 不能先把银行两条压成一条；
- 具体逐条对应无法证明时，可以保存组级数量解释或转人工，但事件数量仍保持为两笔。

`N ↔ M` 候选不能简单取最小值合并。未匹配记录继续独立存在，匹配不唯一时不得按遍历顺序贪心裁决。

## 6. 时间精度

来源时间必须按证据精度解释：秒、分钟、日期或未知。银行月结单只给交易日时，午夜 Unix 值只是该自然日的规范化表示，不等于来源证明交易发生在零点，也不证明同日多条记录时间相同。

日期级时间可以参与自然日匹配，但不能用于同来源去重。后续需要新增字段时，通过连续迁移显式保存精度；本次先以来源格式和解析器语义作为匹配约束，不伪造精确时间。

## 7. 计数与文案

用户可见统计必须区分：

- 有效物理证据数；
- 最终经济事件数；
- 已确认归入既有事件的附加证据数；
- 来源身份冲突数；
- 开放的同一事件候选数；
- 文件重传和解析历史。

事件守恒表述为：

`有效证据数 = 最终事件数 + 已确认附加证据数`

`最终事件数 = 已入账 + 待入账 + 待处理 + 明确不入账`

内部历史字段 `duplicateEvidenceCount` 在未迁移 schema 前只作为“每个最终事件除主证据外的附加证据数”解释；界面和文档不得把它描述为“系统证明了这么多重复交易”。文件重复和解析运行不进入该事件守恒式。

“精确重复”只适用于稳定来源身份或同一文件同一 locator 的再次观察。内容相同但身份不同的记录不得显示为精确重复。

## 8. 旧数据兼容与修复

现有原文件、批次和原始行均保留，因此错误事件投影可以重建。迁移策略：

1. 新解析使用来源身份策略 v2；稳定交易号和稳定订单组合保持与 v1 的兼容身份；无稳定标识改用文件内容与 locator。
2. 旧 v1 行若没有稳定交易号或完整订单组合，整理器不得再信任由强内容指纹产生的共享身份；每个物理行先作为独立来源记录。
3. 旧 v1 稳定交易号和完整订单组合继续按来源身份归组。
4. 旧 v1、v2 或解析器升级后的记录，只要属于同一用户、来源类型、来源账户、文件和 locator，就必须先复用同一物理观察；新提取出的稳定交易号只升级身份解释，不增加事件数量。
5. 未入账更新通过 UX-1801 放弃旧轮并选择显式重解析后的批次创建新轮；新轮按修正规则重建事件和问题。
6. 已入账正式交易不自动重写。若以后发现历史缺失事件，只生成可审计的补充候选并等待用户授权。
7. 不删除旧 `SourceIdentity`、原始行或动作历史；旧强指纹身份作为历史事实保留但不再决定新事件数量。

本次不需要改变表结构；规则版本、兼容判断和工作投影重建足以修复当前未入账场景。若后续拆分附加证据统计字段，再使用新的 forward-only schema 迁移。

## 9. 最小验收矩阵

| 场景 | 必须结果 |
| --- | --- |
| 同一文件中两行内容完全相同且无流水号 | 两个来源身份、两个事件、零条来源内精确重复 |
| 同一文件中四行分为两组相同内容 | 四个来源身份、四个事件 |
| 同一文件同一 locator 显式重解析 | 一个事件、多条观察证据，不因批次或行 ID 变化新增事件 |
| 旧 identity-v1 同一 locator 重解析 | 仍复用同一物理观察，不因旧行 ID 不同新增事件 |
| 同一 locator 重解析后新增稳定交易号 | 只升级身份解释，仍保持一个事件 |
| 不同稳定交易号但内容完全相同 | 明确保留多笔 |
| 相同稳定交易号且核心语义一致 | 同一来源记录、多条观察证据 |
| 相同稳定交易号但金额不同 | 身份冲突，不能入账 |
| 银行两条相同行、支付宝两个不同交易号 | 两个事件、四条跨来源证据 |
| 银行两条、支付宝一条 | 至少两个事件，一条银行记录保持未匹配 |
| 不同文件相同行且无稳定标识 | 默认独立，只生成候选 |
| 用户确认多笔独立 | 后续重建不得再次自动合并 |
| 文件重传 | 返回已有文件，不新增解析和事件 |
| 并发持久化同一稳定身份 | 数据库只保留一个来源身份结果 |
| 光大目标回归样例 | 第17、19、38、40物理行均保留；来源内重复为零 |

## 11. 冻结结论

1. 无稳定来源标识时，以文件内容和物理 locator 确定来源记录身份；
2. 不同物理行默认不同来源记录，内容完全相同也不例外；
3. 内容指纹只用于候选，不再用于来源身份或自动同来源去重；
4. 跨来源匹配在完整多重集上执行并保持一对一数量约束；
5. 旧 v1 无稳定标识行在新事件规划中按物理行拆开；
6. 用户可见统计使用“附加证据”，不把跨来源证据、解析重放和多次相同消费混称为重复；
7. 当前正式更新和所有正式交易保持不动，第一次真实入账继续暂停。
