## 请评审的核心问题

我们正在开发一款面向中国个人用户的记账小程序。用户定期上传支付宝、微信支付以及未来的银行账单，系统将原始记录整理成经济事件，经用户确认后原子写入正式账本。

真实账单验收暴露出一个根本问题：账单格式和业务语义无法靠开发者手中的少量样本穷举。即使已有大量自动测试，也只能证明已知样本和已知规则没有退化，不能证明下一份真实账单不会出现新的列名、枚举、账户表达、状态组合、导出渠道差异或产品语义。

支付宝和微信已经出现这种情况；后续接入不同银行的 CSV、XLSX、PDF、信用卡、贷款和分期账单后，组合数量和风险会急剧增加。如果继续采用“真实账单发现一个特例—增加一条规则—补一个回归测试”的方式，系统可能长期陷入特例堆积，却仍然无法回答何时可以安全发布。

请基于下面的现状和约束，给出一个能够公开发布、持续演进并守住账务正确性的最优架构。不要只回答“增加测试样本”“做插件化”“引入 AI”或“灰度发布”，而要给出各层职责、数据模型、置信与降级机制、测试方法、发布门禁和实施顺序。

## 一、当前系统已经具备什么

当前主链路是：

```text
原始账单文件
  → 来源解析与规范化记录
  → EconomicEvent（现实中发生了什么）
  → FinanceUpdate（待确认、未入账批次）
  → ReviewIssue（只询问真正不确定的问题）
  → Transaction（确认后的正式账本交易）
  → Account（承载余额的正式账户）
```

当前重要边界：

1. 原始 Evidence 保留来源事实，解析和推导不能悄悄改写原文。
2. `PaymentReference` 只是账单里的账户引用，不等于正式 `Account`。
3. `AccountIdentity` 用于判断不同来源引用是否指向同一个现实账户。
4. 新账户草稿、账户映射和整理决定在正式入账前不污染 `Account` 与 `Transaction`。
5. `Transaction` 是当前余额和统计的唯一权威，本阶段不新增 `JournalEntry / Posting`。
6. 多条来源证据可以组成一个经济事件，一个事件也可以生成多笔正式交易。
7. 整批入账使用单事务：账户、映射、交易、关系、余额和统计要么全部成功，要么全部回滚。
8. 已入账后的修改、撤销、退款关系和统计读取走正式交易体系，不继续修改导入记录。
9. 不确定时原则上进入 ReviewIssue，不允许为了提高自动化率而静默猜测。
10. 当前主要支持人民币；真实文件、完整账户标识、微信身份和凭据不得进入仓库或普通日志。

这套领域分层已经不是“解析一行直接写一条交易”，但来源理解仍以确定性解析器和持续补充的业务规则为主。

## 二、真实账单刚刚暴露了什么

本轮仅使用支付宝、微信真实账单，就发现了以下已知测试没有暴露的问题：

1. 用户以前对支付宝小荷包选择了“以后不入账”，但旧版账户引用键和新版规范键不同，历史规则没有命中新账单，系统再次要求用户选择账户。
2. 微信收入转账的“支付方式”列是 `/`，但交易状态明确写着“已存入零钱”。系统只看支付方式，未利用状态字段推导到账账户，因此显示“未识别具体账户”。
3. 支付宝的零金额免押下单和解冻成功记录属于非资金生命周期，却被当作待入账记录并触发账户问题。
4. 来源中的“交易类型”“收支类型”“交易状态”“支付方式”不是统一枚举。字段必须组合解释，同一个 `/` 在不同交易类型和状态下可能有不同含义。

这些缺陷已形成一个本地修复候选，并通过根目录 93/93、API 71/71、导入服务 143/143 和 MySQL 8.4 集成测试。但这只证明本轮已知问题得到修复，不能证明导入能力已经覆盖支付宝、微信的全部语义，更不能推导出银行账单可以安全接入。

## 三、真正难点不是“格式多”，而是以下矛盾

### 1. 解析成功不等于财务语义正确

文件能打开、列能映射、金额能读取，只能说明语法解析成功。账户端、资金方向、退款关系、还款拆分、是否属于资金事件仍可能判断错误。当前缺少清晰分离的“格式识别可信度、字段解析可信度、业务语义可信度、账本可入账性”。

### 2. 静默错账比明确失败危险得多

不支持某份账单并提示用户，体验不好但账本仍然安全；把一条退款记成收入、把本人转账记成支出、把还款记成消费、把未知账户猜成已有账户，则会悄悄污染余额和统计。系统应优化的第一指标可能不是自动识别率，而是静默财务错误率。

### 3. “让用户确认”也不能无限兜底

如果每个未知枚举、账户文字和边缘状态都逐行询问，用户需要重新理解整份账单，批量导入失去价值。人工确认必须按稳定问题簇、账户身份或规则影响批量处理，而不能把解析器的不确定性原样倾倒给用户。

### 4. 规则会演进，但历史决定不能失联

规范化、括号、全半角、银行别名、尾号和产品名称都会变化。新规则既要命中旧历史偏好，又不能覆盖用户后来做出的更精确决定；旧 FinanceUpdate 重建还必须可复现，不能因为当前规则变化而得到无法解释的新结果。

### 5. 不同来源既不能完全统一，也不能无限分叉

支付宝、微信、银行储蓄卡、信用卡、贷款账单都有自己的字段和产品语义。如果把所有特例塞进统一核心，核心会成为条件分支集合；如果每个机构建立一套完整流程，去重、退款、转账、原子入账和审计又会重复实现并逐渐不一致。

### 6. 隐私限制了“收集所有失败样本”

真实账单是高度敏感数据。不能默认上传到公共样本库，也不能把原文打进日志。因此系统需要在不收集原始隐私内容的情况下，知道线上出现了哪些未知格式、规则命中分布和高风险降级；若用户明确同意提供样本，也必须有最小化、脱敏、期限和删除机制。

### 7. 样本永远有限，发布门禁不能等于样本数量

没有任何现实可行的测试集能证明“所有账单都支持”。我们需要定义的是：什么范围被明确支持、遇到范围外输入怎样安全失败、哪些结果可以自动整理、哪些只能人工确认、哪些必须阻止整批入账，以及如何用可量化指标决定发布或回滚。

## 四、希望你重点比较的候选方向

请至少比较下列四类架构，不要默认其中任何一个必然正确：

1. **继续扩展确定性规则解析器**：每个来源维护代码适配器和金标测试集。
2. **声明式账单画像/规则包**：将格式探测、列映射、枚举、组合规则、账户引用和非资金记录定义为带版本的配置或 DSL，核心只执行受限规则。
3. **概率模型或 LLM 辅助抽取**：模型理解未知列和文本，再由确定性约束验证金额、方向、账户和关系；模型结果是否只能生成候选，永远不能直接形成正式交易？
4. **编译器式混合管线**：原始语法层、来源观测层、业务语义层、账本影响层严格分开，每层输出类型化未知、置信证据和诊断；确定性规则优先，模型/用户只补候选，最终由不变量验证器决定能否入账。

请说明你推荐哪一种或怎样组合，并明确：

- 哪些能力必须写代码，哪些适合规则包，哪些可以由模型辅助；
- 是否应该允许远程下发规则包，怎样签名、版本锁定、灰度、回滚并避免规则供应链风险；
- 新增一家银行时，理想情况下需要修改哪些模块，哪些核心模块绝对不应修改；
- 如何防止“配置化”只是把难以维护的 `if/else` 搬进 JSON；
- 如何保证同一规则版本和同一 Evidence 可以重放出同一工作结果；
- 当前架构中哪些部分应该保留、拆分、替换或删除。

## 五、请回答的具体问题

### A. 支持范围与能力协商

1. “支持一份账单”应如何定义？是能读取文件、能识别 95% 行、能完成余额核对，还是所有可入账行都通过财务门禁？
2. 是否应建立来源、导出渠道、模板指纹、模板版本、账户产品类型和能力项组成的 `CapabilityProfile`？
3. 当模板未知、部分字段未知或语义规则缺失时，系统应整份拒绝、部分隔离，还是进入受限人工模式？边界如何决定？
4. 用户在上传前后怎样知道“完整支持、有限支持、实验支持、无法安全导入”，而不被技术术语淹没？

### B. 类型化未知与置信门禁

1. 是否应该把 `unknown` 从空字符串或 `/` 提升为一等领域状态，并区分“来源明确为空”“解析失败”“规则未覆盖”“证据冲突”“需要用户提供”？
2. 是否应该为每个关键结论保存 `value + provenance + ruleVersion + confidenceClass + alternatives`，而不是只保存最终值？
3. 哪些字段缺失必须阻止事件入账：金额、币种、方向、账户端、事件性质、时间、稳定身份、分类、关系？不同交易类型是否需要不同最小完备集？
4. 如何定义“可以自动整理但不能自动入账”“必须人工确认”“完全不能入账”三类门禁？
5. 是否应彻底禁止基于无法校验的概率分数自动写正式账本，只允许通过有限枚举和不变量验证后的结构化候选？

### C. 财务不变量与对账

1. 除逐行规则外，能否利用账单期初/期末余额、账单总收入/总支出、信用卡应还额、退款总额、贷款本金/利息/费用合计等控制总数做整批校验？
2. 当来源没有余额或总计时，如何区分“无法核对”和“核对通过”，避免把缺少证据当成成功？
3. 本人转账、退款、还款和跨来源重复怎样用守恒关系和双端证据降低规则依赖？
4. 应建立哪些硬不变量，任何解析器、规则包、模型或用户操作都不能绕过？
5. 一份账单部分行无法解释时，是否允许已解释部分入账？如果允许，怎样避免未来补录时重复或破坏期间统计？

### D. 规则版本、历史决定与用户纠错

1. 来源规范化键怎样演进，才能同时支持旧偏好、新精确规则、冲突检测和可重放？
2. 用户纠错应该保存为“这一次事件决定”“这个来源引用决定”“这个现实账户身份决定”还是“全局解析规则反馈”？作用域怎样避免误扩散？
3. 什么纠错可以仅对当前用户生效，什么可以经过审核提升为全局规则？
4. 规则升级后，未入账批次、已入账交易、历史审计和用户映射分别应怎样处理？
5. 是否需要规则影响预览：升级前先计算会改变多少事件、账户和排除结果，超过阈值则阻止发布？

### E. 测试方法：没有全量真实账单时怎样建立可信度

请设计不依赖穷举真实文件的测试体系，至少讨论：

- 金标脱敏夹具与每个模板版本的契约测试；
- 语法变异测试：列顺序、缺列、增列、编码、BOM、空行、合并单元格、数字格式、时区和本地化；
- 语义组合测试：交易类型 × 收支方向 × 状态 × 支付方式 × 金额正负/零值；
- 属性测试和模糊测试：金额精度、稳定身份、去重、顺序无关性、重放确定性；
- 变形测试：只改变无关文案不得改变账务结论，改变关键状态必须触发预期差异；
- 差分测试：新旧规则、不同解析器或模型与确定性实现之间比较；
- 影子运行和规则影响分析：只生成候选和差异，不触碰正式账本；
- 合成账单生成器：怎样保证它不是重复实现同一套错误逻辑；
- 用户授权的隐私样本如何脱敏、保存、删除并转化为最小复现。

请给出测试金字塔、最低覆盖维度和发布必须为零的错误类型。不要把“代码覆盖率高”当作财务正确性的替代品。

1. 对 CSV/XLSX/PDF、储蓄卡/信用卡/贷款，是否应拆成“文件容器解析器 + 机构模板画像 + 产品语义适配器”，而不是一家银行一个巨型解析器？

4. 银行模板无公开稳定协议时，怎样建立版本探测和失效机制？
5. 是否值得提供一个安全的“通用表格导入向导”，由用户映射日期、金额、方向和账户；它怎样避免把业务语义识别责任全部转嫁给用户？

### I. AI 的合理边界

4. 在真实账单隐私、成本、离线可用性和中国境内合规约束下，引入模型是否真的优于规则包与人工映射向导？
5. 请明确列出“不应使用 AI”的环节。

## 六、不可妥协的结果

无论选择什么架构，最终方案至少要满足：

1. 未知和不支持是正常状态，不得伪装成已识别。
2. 无足够证据时不得静默改变正式余额、收支、分类或账户关系。
3. 原始证据不可变；所有推导、规则、模型和人工决定均可追踪。
4. 同一 Evidence、同一规则版本和同一用户决定可以确定性重放。
5. 规则升级可预览影响、可灰度、可停止、可回滚；已经入账的事实不能被后台规则静默重写。
6. 人工确认按问题簇和可复用身份处理，不把整份账单逐行扔回用户。
7. 新来源的适配不得绕过正式账本写屏障、幂等、用户隔离和整批原子入账。
8. 测试全绿只能证明已定义行为成立；发布安全必须同时依赖能力声明、安全降级、财务不变量、线上观测和快速止损。
9. 产品可以明确只支持有限来源和模板，但不能声称“万能导入”。
10. 微信账单文件导入与微信支付接口是两个问题。本项目当前处理用户导出的账单文件，不调用 `wx.requestPayment`，也不以支付回调作为账单真相来源；不要用微信支付集成方案替代导入架构。
