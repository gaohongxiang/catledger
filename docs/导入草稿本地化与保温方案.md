# 完整草稿与本地核对实施方案

本文承接完整草稿下发、本地核对和服务端整批入账的工程契约。进度、分支与验收证据只在[实施规划](招财猫记账本实施规划.md)维护；业务流程见[主逻辑第3节](招财猫记账本入账逻辑说明.md#import)，参数与容量以[共享契约](../shared/catledger-import.json)为准。文件名保留以兼容既有链接；定时保温、修订拆分和冷启动瘦身不属于本次改造，也未配置触发器。

## 1. 流程与权威边界

服务端上传、解析和初步整理 → 完整快照下载及校验 → 原工作台本地核对 → 冻结全部最终决定 → 分块暂存并封存 → `financeUpdates.post` 单事务复核入账。

- 正式交易、账户和分类仍以 MySQL 为权威。本地只有只读基础事实和待提交决定，不维护第二份余额或完整离线账本。
- 核对阶段所有账户、编辑、分类、配对、拆分、排除、原文、退款、还款和分期目录均从已准备资料读取；不后台保存、补读摘要或目录。
- 准备允许分块传输；结果未知允许原请求查询或重放；明确冲突允许下载补充事实、修改后重新提交。这些不拆分正式账务事务。
- 原始凭据只读；普通编辑绑定当前 `eventId`，多笔操作必须给出明确范围。未选择不是接受建议，本次排除不是永久忽略。

## 2. 完整快照与历史边界

`prepareSnapshot` 在一致读取中捕获事件、来源身份、全部原始列和值、证据成员、关系、问题、既有决定、本批账户草稿、账户/分类/贷款/费用目录及必要历史引用。编码与分块在写锁外完成；进入原用户事务后复查批次版本，保存不可变对象并把模式切为 `local_v3`。

`local-review-snapshot` 使用无损表结构和共享字段字典；`snapshotManifest` 返回身份、版本、记录数量、分块清单与摘要，`snapshotChunk` 返回受用户范围约束的块。客户端逐块核验字节数、顺序、SHA-256、对象及基础版本，并验证整体计数和引用后写完整标记。缺块、乱序、重复、混版本、损坏或中断均不能开放编辑，旧完整代次保留。

历史只下载相关引用，不为任意未来编辑下载全账本。快照声明原金额、时间、账户及退款候选覆盖；修改超出覆盖时本地标为待服务端复核，不能推断不存在重复、原消费或额度占用。最终复核按修改后字段重查当前历史，发现新候选或冲突则整批退回，返回稳定事件ID及必要补充事实，其他决定保留。

## 3. 最终决定与纯规则

完整决定集合分为 `accounts/events/pairings/reviews/duplicates`。每项有稳定键和准确的原始 `sourceIds`；事件编辑仍以 `eventId` 为主体，不绑定位置、排序或临时展示组。只保存最后的明确状态，不重放点击日志，也不接收客户端自算正式交易。

统一编辑器、账户映射、金额组成、退款、还款、分期归属和配对规则从既有实现提取。服务端保留SQL、可信身份与写入；小程序财务分包使用必要纯函数的逐字节镜像，工程检查验证依赖闭包和镜像一致。主包路由只注册会话，不反向引用分包。

本地模型按事件、来源、关系和候选索引更新受影响对象；统计做增量更新，基础文件不因单笔编辑重写。合并保留原成员身份与字段，拆分恢复各自稳定身份和仍有效决定。换账户、金额/时间、性质或组成会重验相关配对和退款；不兼容关联失效并要求重核，同一来源不能被多个配对占用。列表保留本地分页，Page.data 只包含当前显示范围。

## 4. 本地持久化与恢复

`import-local-files` 在 `wx.env.USER_DATA_PATH` 下按环境、可信用户摘要和草稿分目录：不可变基础块、完整代次标记、独立决定增量和修订提交标记。写临时文件、回读校验、重命名后才确认保存；顺序修订和摘要链阻止半写、旧代次或旧保存覆盖新决定。损坏明确提示，不把未完整提交内容说成已保存。

`import-local-session` 接续原草稿接口；`import-local-manager` 负责模式迁移、文件恢复、登录边界和补清；`import-local-router` 接管已准备批次的核对读写。隐藏、卸载和关闭应用保留已保存决定，同一用户冷启动恢复；已准备的核对页前后台切换保持零网络，普通账本缓存只标失效，在离开核对页后刷新。登录入口仍可能联网核验身份。注销或换号清理原用户文件、内存及指针，失败登记补清，完成前不恢复其他用户草稿。会话代次守卫阻止迟到下载、上传、查询或回执重新生成已清理数据。

成功回执先写本地，随后删除快照、原文及决定；清理失败仍显示入账成功并在下次补清。未发出入账请求可明确放弃；离线时仅本地清理并登记原废弃请求，在下次准备时重试，不能声称服务端已取消。未知入账结果不能直接放弃。

## 5. 最终提交与唯一事务

1. 先持久化冻结请求ID、快照/基础/规则版本及确定的最终状态。
2. `stageDecisions` 以不可替换分块暂存，原块可重放，不同内容拒绝；`sealDecisions` 检查完整载荷并封存。
3. `local-review-submit` 在写锁外读取校验载荷、用户范围、结构、摘要及来源归属。
4. 进入原用户锁和幂等事务，用同一连接调用账户、拆分、配对、统一编辑与关系内核，集中收尾，不循环调用另开事务的公开接口，也不逐项全批重算。
5. 按修改后字段复核当前账户、分类、来源占用、历史重复、退款额度、贷款费用、现金及其他依赖，再调用唯一 `postInTransaction`。
6. 正式账户、交易、来源/贷款关系、映射记忆、批次状态、全部服务端临时对象清理和成功回执共同提交。按可信用户和批次删除所有代次的快照、决定、补充及未使用上传对象，分块随外键级联删除；清理或回执写入故障均整批回滚。

已知业务冲突回滚所有本次草稿和正式写入，再保存 `outcome=recheck` 的确定失败回执和不可变补充对象。客户端保留决定，标记受影响项重新核验；修改后才生成新的 `requestId` 和不可变上传引用，冷恢复也遵循这一边界。网络错误或超时保留冻结内容，重启后查询 `imports.commandResult` 或原样重放；不同内容使用同一ID被拒绝。回执查询先于对象读取，成功清理临时对象后仍可重放原成功或确定失败回执。

所有成功的新服务端变更继续递增全局 `data_revision`，包括快照、决定暂存和确定失败回执，因为完整私有导出包含这些对象；幂等重放不重复递增。它们不提前改变正式账户、交易、余额、贷款或映射记忆。

## 6. 兼容、容量与发布依赖

旧草稿先暂停原队列，用原ID核实在途编辑和入账请求，再整理并生成一致快照。迁移失败保留旧内容，已入账/放弃批次不开编辑。新模式在服务端拒绝旧核对写入与旧 `post`；旧回执仍可查询，兼容接口仅服务旧模式及在途请求。

容量限制由 `local-review-protocol.LIMITS` 与共享契约共同检查，保留原请求/响应预算和现有业务规模。快照与决定分别有限额，候选及块数受限；超出明确拒绝，不截断原文、不缩小输入范围、不拆分入账。实测方法、运行环境和内存结果见[开发与验证](开发与验证.md)，实际结果见实施规划。

`0034_local_import_review.sql` 显式增加模式列和用户范围的对象/分块表；数据库不存文件二进制或Base64。导出清单、导出版本和运行权限同步覆盖新增数据。服务端快照/决定/补充对象是临时传输副本，成功入账时在同一事务删除，废弃时沿原派生回收删除；未入账批次保留恢复所需对象。原来源证据、人工决定关系、行动和回执沿既有生命周期保留，不新增定时回收。

上线需要先迁移并同步最小权限，再发布两个函数及对应小程序。源码实施不自动授权迁移、部署、上传、提审或发布。
