# 导入草稿本地化与服务保温实施方案

> **状态：未开始（目标已确定，代码未实现）。** 本文是唯一实施方案；进度、分支、部署与验收证据只在[实施规划](招财猫记账本实施规划.md)登记。实施前先读 [AGENTS.md](../AGENTS.md)、[项目逻辑说明](招财猫记账本入账逻辑说明.md)第4节与[开发与验证](开发与验证.md)。本文不授权云数据库迁移、云函数部署、触发器配置、小程序上传或发布。

## 0. 目标与不变量

**目标：** 导入的“确认账户 → 核对交易 → 分类 → 确认入账”阶段，用户每次点击都在本地瞬时生效；整个核对阶段的网络交互收敛为“下发草稿 + 一次提交”。日常请求去掉数据库唤醒与云函数冷启动造成的秒级等待。

**不变量（不得因本方案改变）：**

- MySQL 中的 Transaction、Account、分类仍是余额与收支唯一权威；本地草稿只是待提交的意图，不是账本。
- 整批原子入账、`requestId` 幂等、可信服务端身份、用户范围唯一约束、锁内复查历史重复与现金约束全部保留，服务端在提交事务内**全量复核**，不信任客户端算出的结果。
- 上传、解析、银行列映射仍在线完成；解析器、profile、来源身份与去重规则不搬到客户端。
- 原始账单字段与编码语义不变；原文、交易信息、`requestId` 绑定值不进普通日志。
- 已入账事实不因本方案重写；旧草稿与旧接口在过渡期继续可用。

## 1. 现状问题（实施依据）

| 问题 | 证据 |
| --- | --- |
| 核对阶段每个决定都是一次写事务：取用户行锁、写回执、递增 `data_revision` | [import-transaction.js#L80-L109](../cloudfunctions/catledger-import/src/import-transaction.js) |
| 任何导入写（含改分类、重命名、无变化的 organize）都递增全局 `data_revision`，使首页/明细缓存全部标脏、导出失效、费用核对判定外部修订 | 同上 L102；[read-cache.js](../miniprogram/services/read-cache.js) L51-L55 |
| 首次整理串行三次调用：prepare（写）→ summary → refreshAccountGroups（写）；重开草稿：summary → organize（写）→ refreshAccountGroups（写） | [runtime.js](../miniprogram/packages/finance/pages/import-workbench/runtime.js) `organizeFiles`、`loadUpdate` |
| 请求 64KB、回执 32KB、摘要 64KB 上限，迫使大量分页与多轮调用 | [performance-contract.js](../cloudfunctions/catledger-import/src/performance-contract.js) |
| CloudBase MySQL 连续 10 分钟无访问自动暂停，唤醒数秒；云函数 512MB、依赖 43MB/53MB 冷启动 | [cloudbaserc.json](../cloudbaserc.json) |

## 2. 分阶段计划

| 阶段 | 内容 | 依赖 | 可独立交付 |
| --- | --- | --- | --- |
| P0 | 耗时计量 | 无 | 是 |
| P1 | 定时保温 + 冷启动瘦身 | P0 | 是 |
| P2 | 导入写路径减负（修订拆分、合并调用） | P0 | 是 |
| P3 | 草稿快照下发（只读） | P2 | 是（先不切 UI） |
| P4 | 本地草稿存储与本地核对 UI | P3 | 否（与 P5 同时上线） |
| P5 | 决定暂存 + 一次提交入账 | P3 | 否 |
| P6 | 下线逐条写接口的客户端调用、文档收敛 | P4/P5 验收 | 是 |

建议分支：`codex/<task-id>-import-local-draft`；P1/P2 可单独分支先合入。

### P0 耗时计量

- 两个云函数 handler 记录：是否冷启动（模块级标记）、取连接耗时、事务/SQL 总耗时、总耗时、action 名、结果码。**只记数字与 action 名**，不记 uid 明文、参数、绑定值或原文。
- 客户端 `cloud-function-client` 记录调用往返耗时（开发版/体验版开启，正式版关闭或采样）。
- 交付：一份典型导入（单份微信账单、单份支付宝账单、银行+平台组合）与首页启动的分段耗时表，写入实施规划证据。

### P1 定时保温与冷启动瘦身

**保温（低成本方案，不需要升级套餐）：**

- 给 `catledger-api` 增加定时触发器，常用时段每 5 分钟一次，例如 CloudBase 7 段 cron `0 */5 8-23 * * * *`（以控制台实际语法为准）。
- handler 最前面识别定时触发事件（以 CloudBase 实际事件字段为准，如 `Type === 'Timer'`），只执行 `SELECT 1` 后返回；**不解析用户、不进业务路由、不写库**。普通客户端调用不能伪造该分支获得任何数据（该分支无数据返回即可）。
- 触发器写进 `cloudbaserc.json` 还是控制台配置，由负责人决定；配置与部署须用户单独授权。
- 若之后升级标准版并关闭 MySQL 自动暂停，可删除数据库部分保温，仅保留函数保温或改用预置并发。

**冷启动瘦身：**

- `catledger-import` 中 `xlsx`、`yauzl`、`saxes`、`csv-parse`、`iconv-lite` 改为解析函数内首次使用时 `require`，核对/读取类 action 不加载。
- 核对 `catledger-api` 是否引入不需要的重依赖；`wx-server-sdk` 仅在需要的路径加载（若可行）。
- 验收：P0 计时对比冷启动耗时下降；全部现有测试通过。

### P2 导入写路径减负

1. **拆分修订号。** `executeIdempotentMutation` 增加按 action 判定：只有改变正式账务的动作（`financeUpdates.post`、`financeUpdates.undo`、`economicEvents.correct`，以及入账时会物化账户/映射的动作）递增 `catledger_users.data_revision`；草稿动作只推进 `catledger_finance_updates.version`。
   - 先全量梳理 `data_revision` 的读方：[data-export-service.js](../cloudfunctions/catledger-api/src/data-export-service.js)、[ledger-read.js](../cloudfunctions/catledger-api/src/ledger-read.js)、[user-repository.js](../cloudfunctions/catledger-api/src/user-repository.js)、[bank-channel-pairings.js](../cloudfunctions/catledger-import/src/review/bank-channel-pairings.js)。配对范围令牌改为绑定批次 `version` + 候选摘要；导出一致性只需账务修订。
   - 若某草稿动作会改变导出内容（导出是否含草稿需核实），则该动作继续递增或导出改为绑定两个修订。
2. **无变化的 organize 走只读。** `loadUpdate` 先读 summary，服务端返回 `requiresReorganization`/`requiresAccountGroupRefresh` 均为 false 时不发写请求；服务端 `organizeUpdate` 在计划版本当前且无修复时不建动作、不写回执（客户端仍可安全重放旧请求）。
3. **合并调用。** `financeUpdates.prepare` 与 `organize` 在同一事务内完成账户分组展开（现 `refreshAccountGroups` 逻辑），回执直接附带首屏摘要（受 64KB 摘要上限约束，超出则只返回 updateId+version）。客户端首次整理变为“一次写 + 至多一次读”。
4. **整理计算移出锁。** `buildOrganizePlan` 的纯计算移到取用户锁之前（读取用一致快照），事务内只做版本校验与批量写；版本不符时重试一次再报冲突。
5. 入账时映射升级（[finance-update-posting.js](../cloudfunctions/catledger-import/src/finance-update-posting.js) `promoteAccountMappings`/`promoteCategoryMappings`）由逐行“读-写-读”改为批量读、批量写、批量读审计。

验收：数据层测试覆盖修订拆分后首页缓存不因草稿动作失效、导出仍在账务变化时失效、配对令牌仍拒绝候选变化；首次整理调用次数用测试断言。

### P3 草稿快照下发（新只读接口）

新增 `financeUpdates.snapshot`（只读，`executeUserRead` + 一致快照）：

- **输入：** `updateId`、可选 `cursor`、`pageSize`。
- **输出（分页，每页 ≤ 摘要预算）：** `snapshotId`（= updateId + version + planVersion 的摘要）、`version`、`planVersion`、`page`、`totalPages`、`counts`，以及按段返回：
  - `events`：精简字段（eventKey、eventCoreDigest、类型、方向、经济性质、金额分、币种、本地日期时间、账户/对端、分类、状态、阻塞原因码、manualFieldMask、已有人工决定）。
  - `evidence`：事件到来源行的映射与**界面展示所需**原文列（原文可单独段落分页，按需拉取亦可）。
  - `relations`、`candidates`（同笔/退款/历史重复候选，含历史交易的展示摘要）、`issues` + `members`。
  - `accountGroups`、`catalog`（同用户可用账户、分类两级目录）、`categorySuggestions`。
- 游标绑定用户、updateId、version；版本变化返回 `CONFLICT`，客户端重新从第一页拉取。
- 每页带段内摘要，末页带整体摘要，客户端校验完整性后才可进入本地核对。
- 契约写入 [shared/catledger-import.json](../shared/catledger-import.json)。

**仍需在线的读取（不阻塞本地核对）：** 退款原消费的开放式搜索（`economicEvents.refundCandidates`）、新建分类。它们只读或走 catledger-api 既有命令，结果合并进本地草稿。

### P4 本地草稿存储与本地核对

**存储：**

- 使用 `wx.getFileSystemManager()` 写 `wx.env.USER_DATA_PATH/import-drafts/<envId>/<uidDigest>/<updateId>/`，不用 `wx.setStorage`（10MB 总量、单键 1MB）。
- 文件：`snapshot.json`（下发内容）、`decisions.json`（决定集合，见下）、`meta.json`（snapshotId、更新时间、本地版本）。写入采用“写临时文件 → rename”避免半文件。
- 换用户、退出登录、入账成功、放弃批次时立即删除对应目录；App 启动时清理非当前用户目录与超过 30 天的草稿。
- 本地原文只用于本机展示，不上传日志，不进入分享/导出。

**决定模型（关键）：** 决定以**稳定键**而不是临时 ID 标识，以便服务端重新整理后仍能对上：

```json
{
  "decisionId": "本地 uuid",
  "kind": "account | category | pairing | refund | duplicate | exclude | repayment | allocation",
  "target": { "eventKey": "...", "eventCoreDigest": "...", "issueKey": "...", "relationKey": "..." },
  "value": { "...": "按 kind 定义，复用现有 resolve/setCategory 等接口的入参结构" },
  "basis": { "snapshotId": "...", "issueVersion": 3 },
  "updatedAt": "ISO"
}
```

- 同一 target 同一 kind 只保留最后一次决定；“恢复默认”删除决定。
- 新建账户沿用现有“账户草稿”语义：本地生成临时 key，提交时由服务端物化。

**本地校验（只为即时提示，最终以服务端为准）：**

- 把决定适用性、阻塞判定、计数、排序、搜索中的**纯函数**抽到 `shared/`（或现有可被两端引用的位置），云函数与小程序共用同一份代码，避免双份规则漂移。不能共用的规则只在服务端执行，客户端显示“提交时核验”。
- 页面：账户、核对、分类、配对、排除的列表与弹层全部从本地草稿读取；分页改为本地切片，`setData` 只传当前页。
- 移除这些页面中的迟到响应/版本守卫逻辑（因为不再有网络往返），保留会话/用户切换守卫。

### P5 决定暂存与一次提交

请求上限 64KB，决定可能超出，因此分两步：

1. **`financeUpdates.stageDecisions`（幂等写，不递增 data_revision，不改草稿）：** 输入 `updateId`、`snapshotId`、`stageId`、`chunkIndex`、`chunkCount`、`decisions[]`。写入新表 `catledger_import_decision_stage`（uid、update_id、stage_id、chunk_index、payload_json、digest、created_at，唯一键 `(uid, update_id, stage_id, chunk_index)`）。同 chunk 重放返回原结果；内容不同则冲突。
2. **`financeUpdates.post` 扩展（或新增 `financeUpdates.commit`）：** 输入原有字段 + `stageId` + `stageDigest`。在**同一个**用户锁幂等事务内：
   1. 核对批次状态、`snapshotId` 对应版本、暂存完整性与摘要。
   2. 按稳定键把决定映射到当前事件/问题；复用现有服务端决定应用逻辑（`review/*` 中 resolve、setCategory、resolvePairings 等的事务内实现），批量应用并重算关系、问题、计数。
   3. 走现有入账全部检查与写入（[finance-update-posting.js](../cloudfunctions/catledger-import/src/finance-update-posting.js)），成功则整体提交并清理暂存。
   4. 任一决定不适用或出现新阻塞：**整体回滚**，回执返回 `rejections: [{ decisionId, target, code }]` 与 `requiresSnapshot`（版本/历史变化时为 true）。
- 客户端收到拒绝：本地标出对应条目，用户修改后以**新 requestId、新 stageId**重新提交；若 `requiresSnapshot`，拉新快照并按稳定键迁移本地决定，失配的决定标“需重新确认”。
- 结果未知：沿用 pending-ledger-write，用原 requestId 查询 `imports.commandResult`，不换键重发。
- 多设备：服务端版本已被其他设备推进时返回冲突并提示“草稿已在其他设备修改”，按 `requiresSnapshot` 处理。
- 暂存表需要显式 forward-only 迁移（下一个编号），并约定过期清理方式（随批次 posted/abandoned 删除；不新增定时任务时，在 post/abandon 事务中清理）。

### P6 收敛

- 客户端不再调用逐条写接口（`reviewIssues.resolve*`、`financeUpdates.setCategory/setRepayment/setReview`、`economicEvents.duplicateReview`、`financeUpdates.reviseDuplicate`、`reviewIssues.refreshAccountGroups` 等）；服务端接口保留到旧草稿与旧客户端退场后再评估删除。
- 旧草稿（服务端已存逐条决定）：快照把已存决定作为基线下发，本地决定叠加其上。
- 原位更新[项目逻辑说明](招财猫记账本入账逻辑说明.md) 4.5～4.8 与 8 节、[架构设计](招财猫记账本架构设计.md)、[界面视觉与导入状态](现行说明/界面视觉与导入状态.md)；删除不再适用的迟到响应描述；本文状态改为已完成或归档。

## 3. 验收用例（明确反例）

| 场景 | 预期 |
| --- | --- |
| 核对阶段连续改 50 条分类/账户/排除 | 0 次网络调用，界面即时更新；杀进程重进决定仍在 |
| 提交时某决定引用的候选已被历史交易占用 | 整体回滚，返回该决定的拒绝码，未写任何交易；修改后重提成功 |
| 提交响应丢失 | 原 requestId 查回执，不重复入账 |
| 同 requestId 不同决定内容 | 拒绝（摘要不符），不覆盖原结果 |
| 暂存缺块或摘要不符 | 拒绝提交，无写入 |
| 两台设备同一草稿，A 先提交 | B 提交得到冲突，拉新快照后决定按稳定键迁移 |
| 服务端规则升级导致重新整理 | 稳定键匹配的决定保留，失配的标“需重新确认” |
| 换用户/退出登录 | 旧用户本地草稿目录被删除，新用户看不到 |
| 入账成功/放弃 | 本地草稿与暂存表数据清除 |
| 草稿动作后打开首页 | 首页缓存不因草稿动作失效（P2） |
| 定时触发事件 | 只执行 `SELECT 1`，不触达业务路由、不写库、无数据返回 |
| 单文件解析失败 | 不影响其他文件与本地草稿（原规则保持） |
| 3000 行银行+平台组合 | 快照分页完整校验通过；提交在函数超时内完成（以 P0 计量设定上限） |

数据层另需覆盖：迁移可重入、用户隔离、并发提交（同用户两请求只有一个成功）、事务回滚无残留。页面需覆盖真实 Page、会话切换、写入恢复；原生编译、合成交互、真机走查分别报告。

## 4. 风险与待核实

- CloudBase 定时触发事件的实际字段、cron 语法、callFunction 实际负载上限，以官方文档/控制台为准。
- 共享纯函数抽取可能牵动较多 `review/*` 模块；若抽取成本过高，P4 可先只做“必填/阻塞原因码展示”，其余全部依赖提交时服务端核验。
- 本地草稿体积：按 3000 行估算并实测 `snapshot.json` 大小与解析耗时，必要时原文段按需拉取不入本地。
- 套餐：个人版不能关闭 MySQL 自动暂停，定时保温在保温时段内仍按数据库算力计费；是否升级标准版由用户决定。
