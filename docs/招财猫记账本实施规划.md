## 4. MINI-1903 冻结契约

1. `bootstrap` 是用户主动确认微信登录后的首个业务动作。未登录浏览不调用个人业务接口；客户端只发送动作名，云函数必须从 `cloud.getWXContext().OPENID` 取得身份，请求中出现 `uid`、`openid` 或同义身份字段时直接拒绝。
2. 数据库不保存明文 OpenID。服务端将 `wechat-mini:<OPENID>` 计算为 SHA-256 身份摘要，通过 `catledger_user_identities(provider, subject_hash)` 唯一约束映射到内部 UUID；响应、日志和客户端缓存均不返回内部 `uid` 或身份摘要。
3. 首版迁移只建立 `catledger_schema_migrations`、`catledger_users`、`catledger_user_identities` 和 `catledger_categories`。除迁移表外，每张业务表均带 `uid`；表、索引和环境变量全部使用 `catledger_` / `CATLEDGER_` 命名空间。
4. 初始化在单个 MySQL 事务中创建用户、身份映射和默认分类；重复、并发请求只能产生一个用户和一套默认分类，任一步失败必须整体回滚。迁移编号连续、forward-only、可重入并校验 SHA-256 checksum。
5. 默认分类只覆盖支出和收入；转账由交易类型表达，不伪装成分类。系统键稳定，中文名称可在后续版本中由用户调整；退款不作为普通收入默认分类。
6. 数据库使用官方推荐的 `mysql2` 连接池，通过云函数私有环境变量和 VPC 内网连接。仓库不保存数据库地址、账号、密码或密钥；允许像 AppID 一样保存非敏感的开发环境 ID，个人或生产环境配置不得提交。
7. 当前 AppID 下的旧宠物业务函数与 NoSQL 集合已按用户授权清理；云环境、AppID 绑定、认证配置和平台静态文件继续保留。本任务只新增 `catledger-api` 和 `catledger_*` 表；用户确认部署后，函数开发版已绑定 VPC 和受限 MySQL 应用账号，函数权限默认拒绝并只允许非匿名登录身份调用。

候选验证：`catledger-api` 的身份、隐私、请求契约和事务重试单元测试及 MySQL 集成测试通过；覆盖迁移重跑与 checksum、重复初始化、并发唯一裁决、死锁与锁等待有限重试、双用户隔离、明文 OpenID 不落库和失败整体回滚。函数开发版已绑定 VPC、私有数据库变量和最小权限 MySQL 账号，真实微信身份连续初始化验证通过。当前保留正式版 `wx-server-sdk`，通过受控兼容覆盖消除其传递依赖告警，两支函数生产依赖审计均为 0。

## 5. MINI-1905～MINI-1910 方向契约

1. MINI-1905/1906 先把账单转化为可追溯的正式事实：来源文件、数据日期、原始行、规范化记录、来源身份、经济事件、账户映射、整理决定和正式交易保持独立并可关联；不为后续“智能分析”牺牲证据、幂等或人工确认边界。
2. 所有导入业务统一采用“来源证据 → 经济事件候选 → 整理决定 → 正式交易”主流程。一个经济事件允许多份来源证据和多笔正式交易；贷款只是需要本金、利息和费用拆分的复杂类型，不另建一套导入主链路。
3. 跨来源关联与同来源去重分开处理：共享并核验通过的稳定关联号或已冻结官方强关系可以自动确认，仅金额、时间、文本、对方或账户尾号接近只能生成建议。无法确认的账户、用途、身份或关系进入待确认。
4. 消费、收入、本人转账、信用卡还款、退款和借款还款必须使用各自业务语义；同一事件的多来源证据不得重复入账。贷款缺少明细时不得猜测本金、利息和费用，有明细时组成项必须与实际还款总额守恒。
5. 统一导入候选先由 MINI-1906V 在真实微信身份、私有云存储和开发 MySQL 的完整链路上验收。该阶段只验证既有候选，不以“顺手优化”为由引入 schema、公共 API 或业务规则变化；发现缺陷时先记录可复现证据，再另行授权修复。
6. MINI-1906V2 把来源识别拆成三个能力通道：认证整账 adapter、用户声明式映射和维护者开发 adapter。三者共享 FieldObservation、SemanticClaim、RowDisposition、CoverageReport、EconomicEvent 和 posting 门禁；只有认证通道可宣称整账覆盖完整，辅助通道只承诺用户确认的选中交易。
7. MINI-1906V2 以全字段观测、分阶段联合判断和覆盖证明为主干，吸收 ezBookkeeping 的来源 adapter、统一中间表、日期/金额格式建议、映射 JSON 复用、按原始引用批量修正和导入预览；不得吸收静默跳行、账户显示名即身份、负数支出模拟退款、请求级防重替代来源身份或运行时执行用户脚本。
8. MINI-1906A1 只收口现有 Transaction 账本的完整性：最终可达账户草稿才可物化，修正与首次入账使用同一现金安全语义，撤销处理账户/映射/分类别名副作用，多交易事件按完整集合维护。完成前 Transaction 仍是余额和统计唯一权威。
9. MINI-1906Q 在更高风险的账本迁移前建立持续门禁：根目录契约、两支函数测试、生产依赖审计、迁移连续性与 checksum、MySQL 8 集成、主线保护和分支清理必须可重复执行。
10. MINI-1907-0 先补齐用户需求已列为首发必须的数据导出、账户注销、数据生命周期和隐私说明，再开展受控封闭测试；不得让底层分录迁移无限推迟产品反馈。
11. MINI-1906A2/A3 采用“用户可理解的 Transaction + 内部不可变 JournalEntry / Posting”双层模型。先新增 schema、统一正式写入适配器和影子双写，再做历史回填、全量与增量零差异比对；未达到零差异不得切换读取，切换后保留回退开关且不得删除已生成审计分录。
12. MINI-1907-1 的财务状态以正式账本同一数据快照为基础，分别表达净值、可立即使用资金和负债。账户流动性必须可解释并由用户确认；数据日期、覆盖范围、过期账户和待确认项属于结果的一部分，未知不得按零处理。
13. MINI-1908 的未来付款承诺、贷款和分期计划独立于已发生交易；计划不得提前进入余额或月度收支，实际付款必须通过用户范围内的幂等关系与经济事件、正式交易关联。最低保留资金由用户设置，系统不得根据画像自动决定。
14. MINI-1909 的情景测算是只读确定性能力：金额使用分单位，日期使用明确本地日期，四种方案使用同一数据快照、规则版本和用户输入。测算必须列出付款后可用资金、未来 30/90 天安全线、受影响支出、来源、假设和缺失资料，且不得创建或修改正式业务数据。
15. MINI-1910 的 AI 只解释已经计算完成的结构化结果，不负责解析权威事实或计算金额。模型默认不接收原始账单全文，不拥有数据库写权或付款能力；模型失败时用户仍能查看完整计算表和来源。
16. 首轮仍只支持人民币，不承诺证券实时价格、房产估值、万能银行 PDF、多币种换算或投资建议；这些能力如需进入产品，必须另行冻结数据来源、估值日期、汇率和风险口径。
