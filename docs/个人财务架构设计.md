# 个人财务目标架构设计

> 状态：DESIGN-1501 设计已冻结，等待用户验收
> 约束：不建立第二套正式账本；账单工作流允许破坏性重构，不兼容旧 billflow API、状态机和页面；继续兼容 SQLite、MySQL、PostgreSQL

## 1. 设计目标

系统需要同时满足两件看似冲突的事：

- 普通用户默认只看结果并处理少量问题；
- 当自动处理可能出错时，用户能够核对证据、理解依据、纠错和撤销。

因此采用“后台分层、前台渐进披露、异常按事件隔离”的架构，而不是删除专业能力或把专业能力全部放在主流程。

## 2. 架构总览

~~~mermaid
flowchart LR
    A[来源适配器] --> B[不可变证据]
    B --> C[标准化资金事实]
    C --> D[经济语义解释]
    D --> E[正式 Transaction]
    D --> F[事件与交易关系]
    G[贷款与分期计划] --> F
    E --> H[总览与报表]
    B --> I[覆盖与可信度]
    F --> H
    I --> H
~~~

依赖方向固定为：来源适配器 → `personalfinance` 证据与解释 → 既有核心账本。核心 `Transaction`、`Account`、分类和标签不得反向依赖 `personalfinance`。

## 3. 领域边界

### 3.1 正式账本

现有 `Transaction` 和 `Account` 是余额、现金流和报表的唯一权威。目标架构不创建平行账本，也不让贷款计划或原始账单直接参与余额计算。

### 3.2 证据

证据包含原文件、解析批次、原始行、来源身份和物理定位。证据不可变、可版本化、可追溯，但不直接产生余额。

### 3.3 经济语义解释

每个待入账事件分别表达：

| 维度 | 取值示例 |
| --- | --- |
| 资金方向 | 流入、流出 |
| 经济性质 | 收入、消费、内部转账、借款、还款、退款、费用、余额调整、未知 |
| 生活分类 | 餐饮、服饰、交通，可空 |
| 判断状态 | 自动建议、用户确认、待处理 |
| 可信依据 | 来源字段、历史规则、关系决定、规则版本 |

来源中的“收入/支出/不计收支”只是解释材料，不直接等于最终经济性质。

### 3.4 关系

关系类型至少包括：

- 多条证据证明同一经济事件；
- 原消费与退款；
- 内部转账两侧；
- 付款账户与信用卡还款；
- 贷款到账、偿还本金、利息和费用；
- 正式交易与贷款/分期期次。

关系必须持久、版本化、可解释，人工决定优先于后续自动规则。

### 3.5 计划与覆盖

贷款合同、分期计划和信用卡账期描述预期与覆盖，不直接改变账本。实际交易发生并关联后才推进已还进度。覆盖状态独立说明账户和日期区间是否完整。

### 3.6 新工作流实体

新代码使用 `personalfinance/organizer`，不继续扩展旧 `billflow` 与 `reconciliation` 状态机：

| 实体 | 职责 | 是否影响余额 |
| --- | --- | --- |
| `FinanceUpdate` | 用户一次多文件更新、计数、状态和版本 | 否 |
| `FinanceUpdateSource` | 更新包含的文件与解析批次快照 | 否 |
| `EconomicEvent` | 唯一经济事件及待入账语义 | 否 |
| `EconomicEventEvidence` | 原始行属于哪个事件、承担什么证据角色 | 否 |
| `EconomicEventRelation` | 退款、还款、转账和债务等事件关系 | 否 |
| `EconomicEventTransaction` | 事件与正式 `Transaction` 的稳定链接 | 间接链接 |
| `FinanceAction` | 幂等命令、人工决定、纠错和撤销审计 | 否 |

这些表只是可重建的解释与工作投影，不是第二账本；只有核心 `Transaction` 参与余额、现金流和报表。

## 4. 目标状态机

### 4.1 文件和证据

文件上传后独立经历上传、解析成功、部分成功、失败、删除原文件等状态。单个文件失败只影响该文件，不能阻止同一更新中的其他文件。

### 4.2 经济事件

~~~mermaid
stateDiagram-v2
    [*] --> ready: 必需语义明确
    [*] --> needs_action: 账户/性质/关系缺失
    [*] --> excluded: 明确不入账
    ready --> posted: 整批确认或显式部分入账
    needs_action --> ready: 用户确认
    needs_action --> excluded: 用户跳过
    posted --> corrected: 用户纠错
    corrected --> posted: 重算受影响范围
~~~

分类未知不进入 `needs_action`；它可以随正式交易以未分类状态存在。

### 4.3 财务更新

~~~mermaid
stateDiagram-v2
    [*] --> draft
    draft --> organizing: 锁定文件
    organizing --> review: 生成事件计划
    review --> posting: 整批确认或显式先入账
    posting --> posted: 全部可入账事件完成
    posting --> partially_posted: 仍有待处理事件
    partially_posted --> posting: 后续再次明确确认
    organizing --> failed: 整理失败
    posting --> review: 写入整体回滚
    posted --> undone: 安全撤销
~~~

`review` 表示计划已稳定但尚未写账；`partially_posted` 只能由用户明确选择产生，后台处理不得自动进入该状态。

### 4.4 异常隔离

阻塞范围必须精确到最小对象：

| 异常 | 影响范围 |
| --- | --- |
| 文件不可读 | 该文件 |
| 账户未知 | 使用该账户的事件 |
| 来源身份冲突 | 该身份及证据 |
| 退款或转账不唯一 | 直接关系成员 |
| 分期信息不足 | 债务候选，不阻塞普通交易 |
| 未分类 | 不阻塞 |

整理任务是用户一次更新的核对、计数和默认入账单位，但不是所有事件必须一起完成整理的全局闸门。异常只阻塞直接事件；清晰事件保持 `ready`，等待批次确认。

## 5. 输入与解析架构

### 5.1 适配器接口

每个来源适配器只负责 `Descriptor / Probe / Parse` 和标准字段投影，不访问数据库、账户映射或正式账本。解析规则与标准化规则分别版本化。

### 5.2 覆盖顺序

1. 支付宝、微信等高频结构化账单自动识别；
2. 银行 CSV/XLSX/OFX/QIF/MT940 等结构化格式优先；
3. 可靠文本型 PDF 使用银行和模板版本专用适配器；
4. 通用映射保存字段规则，不保存用户交易内容；
5. OCR 只产生待核对草稿，不静默入账。

不设计“中国银行 PDF 万能解析器”。未知银行文件形成覆盖缺口，不影响其他来源。

## 6. 整理与入账架构

### 6.1 处理顺序

后台顺序保留为：解析留证 → 账户解释 → 同来源身份裁决 → 跨来源同一事件 → 经济性质和关系 → 分类 → 可入账事件 → 待处理。

用户界面不逐层暴露这些算法，只展示结果和缺失决定。

### 6.2 整理完成与正式入账

目标行为是：清晰事件独立完成整理并进入 `ready`，不确定事件继续留在同一批次的待处理区。默认只有在用户处理或明确跳过阻塞事项并确认整批后，才在一个数据库事务中写入或复用本批次全部可入账的正式交易；任何失败都回滚本次写入。

系统不得后台静默逐笔入账。用户可以主动选择“先入账已确认项”，此时批次进入 `partially_posted`，必须持续保存批次成员快照、已入账集合、剩余事件、执行记录和守恒计数。后续只补入尚未入账事件，不重复写入已经完成的交易。

实施时必须保留批次和事件幂等键、数据库唯一裁决、事务失败回滚及正式交易链接；不得用前端列表状态冒充正式完成。

### 6.3 核对和纠错

每笔最终交易提供四层信息：

1. 最终金额、账户、性质和分类；
2. 使用了几条来源证据；
3. 每个字段取自哪条证据以及自动判断原因；
4. 规则版本、人工决定、后续修订和撤销影响。

纠错只重算受影响的事件、关系、覆盖和报表，不重跑无关批次。

### 6.4 持久表契约

目标 schema v009 新建七张表：

- `pf_finance_update`：`uid + update_id` 主键范围，保存状态、版本、计划版本和六类守恒计数；
- `pf_finance_update_source`：唯一约束 `uid + update_id + batch_id`，锁定本次更新的来源集合；
- `pf_economic_event`：唯一约束 `uid + update_id + event_key`，保存状态、经济性质、账户、金额、币种、分类、人工字段掩码和规则版本；
- `pf_economic_event_evidence`：唯一约束 `uid + update_id + row_id`，一条原始行在一次更新中只归属一个最终事件；
- `pf_economic_event_relation`：唯一约束 `uid + relation_key`，保存关系类型、两端事件、金额、状态和版本；
- `pf_economic_event_transaction`：唯一约束 `uid + event_id + transaction_id + role`，保存正式交易链接与交易版本快照；
- `pf_finance_action`：唯一约束 `uid + idempotency_key_digest`，保存请求摘要、预期更新版本、应用版本、动作类型、状态和审计时间。

所有查询和唯一约束都包含 `uid`。金额使用整数最小币种单位，ID、时间和币种沿用现有安全表示；JSON 只保存原因码或字段来源，不承担唯一性和并发正确性。

### 6.5 守恒计数

后端在同一计划事务中写事件和更新摘要，前端不得分别拼接计数：

`有效证据数 - 被折叠的重复证据数 = 最终事件数`

`最终事件数 = 已入账 + 待入账 + 待处理 + 明确不入账`

整理完成时 `已入账=0`；显式部分入账会把当时全部 `ready` 事件转为 `posted`，不会留下用户无法解释的任意选择子集。

### 6.6 批次原子入账

`organizer` 在授权预检后，按批次 ID 排序取得进程内锁，并在同一个用户隐私数据库事务中完成：

1. 以更新版本和事件版本做条件校验；
2. 为所有选定事件创建或复用正式交易；
3. 写证据链接、事件交易链接和关系账本效果；
4. 推进事件、动作和更新状态并重算守恒计数。

任一步失败都回滚整个确认动作。动作键与请求摘要保证重放返回同一结果；同键不同请求、旧版本确认和并发确认全部冲突退出。旧 `PostImportBatch` 可保留为底层历史证据能力，但新工作流只调用同事务的会话级账本写入器，不再按来源批次逐个提交。

### 6.7 关系与退款裁决

- 多渠道同一笔交易表现为一个事件拥有多条证据，不再创建“合并关系”待办；
- 退款是独立事件，通过 `refund_of` 指向原消费；明确退款文本、稳定订单身份和金额约束优先于时间猜测；
- 同一原消费的有效退款累计额不得超过原消费金额，关系版本和数据库条件更新负责并发裁决；超额或多解只阻塞相关退款事件；
- 内部转账、信用卡还款和贷款本金还款是一个双账户事件，不计收入和消费；只有关系不唯一时进入 `needs_action`；
- 未分类不阻塞，经济性质未知必须阻塞。

### 6.8 人工事实、纠错和撤销

人工修改按字段保存锁定位：合并、账户、经济性质、关系、分类和不入账互不连带。后续自动整理只能重算未锁定字段。

未入账事件使用事件版本 CAS 原地修订；已入账事件先检查正式交易版本、共享证据和债务引用。安全时在一个事务中撤销原效果并重建，存在外部修改或共享引用时转人工影响确认，不静默覆盖。

### 6.9 API 边界

新端点围绕资源而不是旧页面步骤设计：

- `updates`：创建、锁定来源、整理、读取摘要；
- `events`：分页查看、筛选、读取证据、纠错或排除；
- `actions/post-all-ready`：默认整批确认；存在待处理时拒绝；
- `actions/post-ready`：用户显式部分入账；
- `actions/undo`：先返回影响，再执行安全撤销。

所有写请求携带 `expectedUpdateVersion` 和 `idempotencyKey`。旧 billflow 路由、五步页面和状态枚举直接删除，不提供兼容字段。

## 7. 债务架构

债务模块由合同、版本、计划期次、实际交易分配和证据关系组成。

- 贷款到账映射为负债账户到资产账户的转账；
- 偿还本金映射为资产账户到负债账户的转账；
- 利息和费用映射为支出；
- 信用卡分期保留原消费，只新增计划；
- 自动发现只创建非阻塞候选；
- 没有债务数据的用户不看到合同工作台主入口。

现有贷款计算和合同能力继续保留，但界面降为按需出现的高级能力。

## 8. 信息架构

### 8.1 页面数量

日常只保留四类页面：

1. **财务总览**：结果、可信度和“更新账单”入口；
2. **更新账单**：选择文件、处理必要问题、查看更新结果；
3. **待处理与核对**：异常、最终交易、证据解释和纠错；
4. **债务与待还**：只有存在债务或主动启用时突出显示。

账户、分类、导入历史和全局对账继续存在，但属于二级管理或高级入口。

### 8.2 视觉设计规格

- **目的**：让财务结论一眼可读，同时保留严谨的审计下钻；
- **美学方向**：Brutally minimal，延续当前温暖纸张与深墨色品牌语言；
- **色板**：墨绿 `#173A34`、暖纸 `#F7F2EA`、琥珀 `#C97C42`、薄荷 `#DCEFE4`、错误红 `#B34D45`；
- **字体目标**：中文正文使用 Source Han Sans SC，金额和证据标识使用 IBM Plex Mono；实现前核对字体打包和现有主题兼容；
- **布局**：桌面采用结果主栏加窄可信度侧栏，核对详情按层展开；手机采用单列结果流，待处理数量固定在可触达位置；
- **图标**：沿用项目现有专业图标体系，不使用 emoji；
- **品牌约束**：现有主题令牌和可访问性优先于通用设计建议，实施阶段不得为换字体或色板扩大依赖面。

## 9. 接口与数据边界

- 账单整理 API 和页面直接切换到新契约，不维护旧 billflow 双路由或兼容字段；
- ID、金额、日期和币种继续使用现有安全表示；
- 所有 PF 查询带 `uid`，响应只返回安全投影；
- 状态机和关系若需新字段，先冻结显式 forward-only 迁移；
- SQLite、MySQL、PostgreSQL 同时成立，不依赖单库特性；
- 正式交易、原始证据、账户映射、来源身份和人工决定必须保留；旧任务、todo、自动候选和未入账投影可以删除重建。

## 10. 隐私与安全

- 原始账单、商户、余额、账户和贷款信息默认不发送外部 AI；
- 证据仓储、关系和业务表通过隐私 session 访问；
- 普通日志不记录原始字段绑定值；
- 自动决定和人工纠错均保留安全审计；
- 文件、数据库和对象存储备份必须视为同一敏感快照。

## 11. 迁移策略

实施按“备份事实、替换工作流、重建投影”推进：

1. 备份数据库和原文件，核对正式交易、原始证据、账户映射、来源身份和人工决定数量；
2. 通过连续显式迁移建立新事件与批次结构，删除或停止读取旧 billflow 工作表；
3. 从保留事实重建未入账事件，不迁移旧任务状态、todo 和自动候选；
4. API 与页面一次切换到新状态机，不保留适配层；
5. 在真实副本验证计数、余额、关系和覆盖后切换正式站，失败时整库回滚到切换前备份。

任何需要核心 `Transaction` 新类型或第二账本的方案，以及超出本次 billflow 范围的其他破坏性接口变更，都必须单独决策，不能作为实现细节顺带落地。

## 12. 已冻结决策与剩余范围

债务主导航、银行模板覆盖和最终页面视觉细节分别属于 DEBT-1504、INGEST-1503 和 UX-1502，不阻塞账单核心重构。
