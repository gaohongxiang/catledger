# 猫账小程序架构设计

## 1. 总体结构

```text
微信原生小程序
  ├─ catledger-api 云函数：登录、账户、分类、交易、统计、贷款
  ├─ catledger-import 云函数：文件读取、解析、去重、整理、入账
  ├─ CloudBase MySQL：正式账本、来源身份、整理事实和审计关系
  └─ CloudBase 云存储：待解析和短期追溯的原始账单
```

不使用云托管和常驻服务器。只有当真实账单解析的执行时间、内存或依赖经测量超过云函数边界时，才单独评估迁移导入函数；不能为假设负载提前增加服务。

## 2. 客户端

- 使用 WXML、WXSS 和 JavaScript，优先微信原生组件和能力；
- 客户端只负责展示、输入、文件选择、上传进度和调用云函数；
- 不在客户端保存数据库凭据、AppSecret 或权威用户 ID；
- 首发只维护简体中文，不引入跨端框架和国际化运行时。

## 3. 云函数边界

### `catledger-api`

负责低延迟、结构化业务：用户初始化、账户、分类、手动交易、交易查询、首页统计，以及后续贷款/分期。每个入口都从可信微信上下文取得用户身份。

### `catledger-import`

负责资源消耗和失败边界不同的任务：读取临时对象、识别文件类型、解析、规范化、来源身份去重、整理和整批入账。多文件由独立任务驱动，单文件失败可重试。

首发阶段不拆更多云函数，避免部署、权限、冷启动和费用复杂度。

## 4. 数据与存储

- MySQL 是唯一正式数据库，使用显式迁移、事务、外键/唯一约束和索引；
- 每张用户业务表都含 `uid`，复合唯一键把 `uid` 放入身份边界；
- 原始文件对象键由服务端生成并包含用户隔离前缀，不使用原始文件名作为权限边界；
- 文件上传成功但业务失败时保留短期重试窗口；成功入账后按策略异步删除原文件；
- 云函数本地目录仅作一次调用内的临时空间，不承担持久化。

## 5. 版本与迁移

- 数据迁移放在 `migrations/`，编号连续、forward-only、可重入；
- 公共请求与响应契约放在 `shared/`，服务端先校验再执行业务；
- 解析规则有显式版本，已入账事实不随解析器升级自动变化；
- `main` 只维护小程序，旧 Web 版固定在 `catledger-web` 和 `web-v2-final`。
