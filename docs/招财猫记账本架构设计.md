# 架构与代码导航

> 这是一份现有实现的定位图，不是待实施的大架构。完整业务顺序见[项目逻辑说明](招财猫记账本入账逻辑说明.md)，当前任务状态见[实施规划](招财猫记账本实施规划.md)。整理基线：`b804bfc4`。历史设计见[归档](归档/README.md)。

## 1. 部署边界

```text
miniprogram（微信原生 UI 与客户端服务）
    ├── catledger-api（普通账本、贷款、统计、导出）
    └── catledger-import（账单解析、整理、核对、入账）
                     ↓
                CloudBase MySQL
原始文件另外使用私有云存储；它不是权威余额来源。
```

两个函数分别打包、部署，不跨函数目录 require。不使用常驻应用服务、云托管或新增数据库；是否改变部署形态须另有实测与授权。未来资金预测、决策模型、复式分录和影子双写不是这张现状图中的运行组件。

小程序主包保留首页、明细、统计、账户、记账与设置；导入工作台、导入历史及贷款相关页面位于 `packages/finance` 分包，导航使用完整分包路径。主包与分包共享的贷款展示模型放在 [loan-present](../miniprogram/services/loan-present.js) 和 [loan-link-view](../miniprogram/services/loan-link-view.js)，主包不得反向引用分包私有模块。页面注册以 [app.json](../miniprogram/app.json) 为准；检查脚本与真实 Page 测试同时覆盖主包和分包。

<a id="theme-lifecycle"></a>
### 主题、实例与原生窗口

主题是一份应用级运行态；`globalData.themeId` 仅作兼容镜像，本机存储负责持久化。业务 data、草稿恢复和读会话快照不拥有主题，业务重置不能恢复旧配色。

主导航由注册在 `app.json` 首位的 [shell/index](../miniprogram/shell/index.js) 常驻原生 Page 承载首页、明细、统计、我的四个独立原生组件，不再配置原生 `tabBar`。四个主入口的切换只改变活动面板，不依赖新 Page 窗口创建后再补主题。主壳负责原生窗口、主导航和面板活动调度；业务组件保留自己的数据、事件和读取生命周期；独立账户、贷款、交易编辑等页面继续走原生路由。原四个页面路径通过 [router](../miniprogram/shell/router.js) 兼容进入对应面板；接入及验收状态统一见[当前任务](招财猫记账本实施规划.md#theme-20261028)。

| 模块 | 职责与边界 |
| --- | --- |
| [registry](../miniprogram/theme/registry.js) | 校验三套主题标识，异常值回退；缓存冻结的有效 tokens 统一派生 CSS、SVG、预览和原生颜色，原始配置保留基础规范 |
| [store](../miniprogram/theme/store.js) | 唯一主题运行态；首次同步读取已保存偏好，选择先保存、成功后发布，失败保留原状态 |
| [service](../miniprogram/theme/service.js) | 组织存储、实例同步和原生配色；维护已挂载实例，包括主壳中隐藏的业务组件；派生图表通过主题变化回调更新 |
| [lifecycle](../miniprogram/theme/lifecycle.js) | Page/Component 显式适配：定义时提供主题默认值，`onLoad`/`attached` 校准并登记，隐藏时保留订阅，`onUnload`/`detached` 释放；保留业务生命周期的参数、返回值和 `this` |
| [native-chrome](../miniprogram/theme/native-chrome.js) | 仅活动 Page 拥有原生窗口配色；加载、显示时在业务回调前调用原生颜色接口；失败留待后续显示重试，旧请求失败不使新主题失效 |
| [主壳](../miniprogram/shell/host.js)与 [panel 适配](../miniprogram/shell/panel.js) | 一个主 Page 拥有主窗口；适配器把活动状态转为业务显示/隐藏生命周期，转发宿主能力并分别管理面板滚动与恢复；组件就绪前不展示业务内容；每次激活先提交当前会话的同步清屏，再以渲染回执开放，迟到回执不能重开隐藏组件；组件不争用原生外壳 |
| 业务定义工厂 | [首页](../miniprogram/pages/index/page.js)、[明细](../miniprogram/pages/transactions/page.js)、[统计](../miniprogram/pages/statistics/page.js)、[我的](../miniprogram/pages/profile/page.js)返回纯业务定义；显式注入 `app/api/themeService/wx`，不自行注册 Page 或包装主题；实例数据独立，财务调用与会话规则沿用原逻辑 |
| 四个原生业务组件 | [首页](../miniprogram/pages/index/panel.js)、[明细](../miniprogram/pages/transactions/panel.js)、[统计](../miniprogram/pages/statistics/panel.js)、[我的](../miniprogram/pages/profile/panel.js)通过 `panel(tabId, definition)` 接入；共享各自 `content.wxml` 与原样式，组件不复制一套业务 UI |

主 Page 和独立页面的 `<page-meta>` 负责根节点及声明式外壳，使用与原生接口同源的字面颜色；四个业务组件只渲染内容并消费 CSS 变量，不包含 `<page-meta>`。常驻壳针对四主入口之间首次切换时新建窗口的触发条件；冷启动、独立页面进入和返回仍须单独检查。模块注册初值、实例挂载和原生窗口首帧不能视为同一时刻；入口与验收范围见[界面专题](现行说明/界面视觉与导入状态.md#theme-acceptance)。

## 3. 普通账本与贷款

`catledger-api` 保持模块化单体。账户、分类、资料、导出各有服务；交易薄门面连接命令、查询和统计；贷款资料、实际借还、期次计划、分期来源、费用身份/授权和明确还款进度分别建模。读模型不按来源期号推定付款，自动记费只由独立授权命令写入。

| 要修改的职责 | 从哪里进入 |
| --- | --- |
| 账户、期初、停用/恢复与账单设置 | [account-service](../cloudfunctions/catledger-api/src/account-service.js)、[account-billing](../cloudfunctions/catledger-api/src/account-billing.js) |
| 两级分类、分配、停用和恢复 | [category-service](../cloudfunctions/catledger-api/src/category-service.js) |
| 交易命令、明细与统计 | [transaction-service](../cloudfunctions/catledger-api/src/transaction-service.js)及其直接依赖 |
| 首页全账本总览、构成与趋势 | [reporting-service](../cloudfunctions/catledger-api/src/reporting-service.js)在同一只读快照内返回账户、累计收支、当前净资产与月度趋势；[首页业务定义](../miniprogram/pages/index/page.js)固定请求累计范围，[构成派生](../miniprogram/pages/index/net-worth-composition.js)是纯函数，只从账户的 `nature` 与账面余额算两条构成，不参与余额计算，[客户端调用层](../miniprogram/services/catledger-api.js)按完整参数缓存并拒绝未确认范围的旧响应 |

## 4. 导入服务的真实分层

```text
解析器 + profiles → 标准行语义 → 证据与关系 → organizer-planner
                                              ↓
                            FinanceUpdate / Event / ReviewIssue
                                              ↓
        review-issue-service（命令事务入口）→ review 场景模块
                                              ↓
            policy / event-store / issue-store / reconciliation
                                              ↓
                       finance-update-posting（正式入账）
```

已分类修改和统一编辑仍使用原 `category-edit`、`review-edit` 与编辑器模型。已完整准备的 `local_v3` 会话由[本地路由](../miniprogram/services/import-local-router.js)接管 `setCategory/setReview/resolve*` 等旧形状调用，保存为最终决定，不发网络。服务端对应公开接口保留旧模式兼容，新模式逐条写入被拒绝；最终批量提交复用原连接内核。

本机[提交协议](../miniprogram/packages/finance/services/import-local-posting.js)集中管理暂存、正式发送前的持久屏障、原回执核实和成功清理；[会话](../miniprogram/packages/finance/services/import-local-session.js)保存业务决定，[恢复管理器](../miniprogram/packages/finance/services/import-local-manager.js)负责入口和生命周期，页面不自行解释或清除请求。完整快照和迁移后的决定由[文件存储](../miniprogram/packages/finance/services/import-local-files.js)一起发布；损坏日志不能被旧快照回退或 TTL 清理掩盖。版本升级按服务端[账户问题对应关系](../cloudfunctions/catledger-import/src/account-plan-upgrade.js)及[绑定升级](../cloudfunctions/catledger-import/src/account-binding-upgrade.js)承接原成员、原来源范围的已存选择；冲突或覆盖不全重新确认，不把旧组决定广播到新成员，来源身份不随账户族变化。

待核对按当前 eventId 进入 [review-edit](../miniprogram/packages/finance/pages/import-workbench/review-edit.js)，已核对与重复项由 review-detail 展示后进入同一编辑模型。本地 `import-local-model/read/summary` 负责受影响对象派生、目录/原文/关系读取和增量计数；完整事实在文件及逻辑层，显示仍有界分页。共享 `editor-policy`、组成、映射、配对、退款和还款纯规则镜像由 [import-local-rules](../scripts/import-local-rules.js)验证逐字节一致，不包含数据库或服务端运行依赖。

同笔修改沿用[duplicate-edit](../miniprogram/packages/finance/pages/import-workbench/duplicate-edit.js)的明确范围。本地决定保存稳定事件与原始来源ID，合并前字段和身份保存在 `fieldSources.mergeOrigins`；拆分恢复原身份及仍有效人工字段，旧无身份快照使用确定来源派生ID。服务端[duplicate-revision](../cloudfunctions/catledger-import/src/review/duplicate-revision.js)在最终事务应用同一语义，历史撤回只移除本次引用，正式账务不提前变化。

`saveEvent/saveEvents` 负责引用校验、可入账重算、原因、版本与操作来源；旧升级的引用保护与 semantic 来源是契约的一部分。自动分类升级只允许在semantic来源、未人工指定分类时替换分类，并重新校验同用户可用分类；其他引用仍保持。`recalculateUpdateCounts` 还涉及历史核对、草稿可达性和批次版本，不是无副作用统计函数。需要改这些函数时先读完整调用链和测试。

新模式列表在 `import-local-read` 按本地时间、稳定ID和筛选分页，当前修订绑定游标；问题范围与真实事件笔数分开，保留50笔显示页、分段原文及整批排除分组。`import-view-session` 继续协调显示页和迟到读取；隐藏或切换不会把部分数据混入页面。旧模式的 `finance-update-read/repository` 服务端分页保留兼容。两条路径复用相同展示与规则，不维护第二套编辑器。

普通还款沿统一编辑器确认实际两端，`account-ownership`保留原业务性质并派生有效记账性质，账户 ID 仍保存在事件端点列，确认依据存于 `fieldSources.accountOwnership`。`finance-update-posting.transactionDrafts` 对本人资产→本人负债生成全额转账；他人→本人负债生成记在该负债账户上的收入，本人资产→他人债务生成支出；两端外部须明确无账本影响才零交易，未知端继续阻断。组合决定逐项保存明确的外部类型及金额，不保存外部账户ID；付款分配与还入分配分别验证总额，仅本人影响生成正式交易。普通还款不调用贷款本息拆分或计划分配；复杂组成与渠道仍走原业务内核。`review/repayment`保留旧拆分决定的清除兼容，旧代还决定兼容读取，旧待定或不适用的未入账决定重核后才替换；未知原请求及已入账交易保持。正式贷款付款仍由 API 的 `repayment-booking` 承接，现金分期借款与登记继续沿分期计划命令。

还款来源合并与还款信息确认分开保存于既有 `repaymentChannelResolution`。`repayment-channel` 的 `relationValid/evidenceValid` 保护同笔关系，待确认也能重新整理及修改普通字段；`valid/postingEvidenceValid` 只允许已明确确认的信息参与费用汇总和入账。唯一还款候选复用完整候选图与批量同笔范围；`repayment-channel-merge.confirmDetails` 由 `setReview` 的原事务调用，重验来源后完成平台目标映射和费用分类。待确认沿用普通核对问题及统一编辑器，不新增表、独立写入协议或入账旁路。

## 5. 数据分层与事务

正式账本为账户、分类、交易。导入保存文件/批次、原始行、来源身份、事件证据、事件关系、问题与成员、用户行动、事件—交易关系及副作用。贷款保存资料、付款与分配、计划与修订、分期编号绑定和分项来源；0026增加稳定费用合同/授权、收费项及覆盖/抑制、来源、清偿分配和只追加审计；0027把历史新费用与同额余额保全交易成对关联。0029保存交易原创建归属、计划删除快照及随计划撤销费用标记；重绑不覆盖原创建，审计保留，旧归档接口不改语义。表与列的完整事实在迁移和导出清单中，不在文档再复制一份易漂移的 schema。

0030初始化默认目录，0031保存可靠来源对，0033保存文件别名。0034增加 `finance_updates.review_mode` 和 `catledger_import_review_objects/chunks`：对象、分块、复合外键与幂等均按可信用户隔离。快照、暂存和补充对象不产生正式账务，成功入账时在同一事务删除该用户该批次全部临时对象并级联清除分块；废弃沿原派生回收。原来源、决定关系和审计回执保持。完整私有导出清单及导出版本同步覆盖新表；API仅需新增读取权限，import按运行契约读写及清理。所有服务端新变更保留 `data_revision` 递增，使跨页完整导出正确失效。

[0038](../migrations/0038_scoped_account_bindings.sql)在正式账户映射和本批映射草稿中追加可空 `binding_json`，并允许无账本账户 ID 的 `external` 动作。原用户范围唯一约束与外键保留；新绑定键写在映射表，原始行的付款键不变。旧数据不回填确认依据；旧历史仅供建议，本批明确决定按原成员恢复。两处 JSON 纳入完整[导出清单](../cloudfunctions/catledger-api/src/export-manifest.json)，API 读取及 import 映射读写复用既有表级最小权限。依赖新列的函数须在迁移核验后部署，客户端再接入；旧回执、旧草稿和归属兼容由新代码处理，不能回退到忽略外部端点或确认依据的写入代码。部署与中断恢复契约见[迁移说明](../migrations/README.md#0038-账户绑定依据与外部端点)，本轮未执行线上迁移或部署。

用户业务查询、复合外键、唯一键及幂等回执都有用户边界。客户端 uid 不能成为授权依据；原文和 SQL 绑定值不进入普通日志。

写操作在既有用户锁与事务内执行，业务变化和回执共同提交。金额、版本、约束、锁序及读取隔离级别以对应事务入口为准：不要把一致只读快照与持锁后的当前账本检查混为一谈。批量 SQL 分块不等于分批提交。

只读汇总需要同一快照内的内部一致性；导出还将多页绑定到同一数据修订。余额守恒和退款/贷款依赖在写入时再次确认，不信任之前页面或预览中的数值。

## 6. 前端职责

贷款相关账目在 [transaction-editor/loan-context](../miniprogram/pages/transaction-editor/loan-context.js) 读取保护关系并展示只读详情，统一进入 [loan-payment](../miniprogram/packages/finance/pages/loan-payment/index.js) 查看一次借还。该页默认展示结果，展开维护操作后才进入修改、核对或 [loan-plan](../miniprogram/packages/finance/pages/loan-plan/index.js) 的期次调整；贷款名称进入贷款详情。transactionId 直达由编辑页按当前用户读取，加载期间及费用/付款保护下保持只读。贷款列表通过 loans.retainedCharges 分页读取保留费用并进入既有详情；历史已记支出候选复用 transactions.refundable 的有界金额/月查询，选择交给 installment-coverage/adoptTransaction 事务校验。显示与展开状态不承担账务变更，沿用原 API 和 pending-ledger-write 恢复路径。

### 6.1 统一交易编辑边界

[review-editor-model](../miniprogram/packages/finance/pages/import-workbench/review-editor-model.js) 负责草稿、模式转换、适用字段和轻量校验；[review-edit](../miniprogram/packages/finance/pages/import-workbench/review-edit.js) 管理唯一 eventId 会话、目录、退款/费用候选、原请求恢复和一次保存；review-detail 复用同一字段模板的只读模式。transaction-review 根据当前卡片的 pendingIssue 将同笔事项直接交给原有问题入口，银行渠道候选进入 pairing-review 的逐对判断；其他待办及关系页内的单笔修改进入 review-edit。transaction-review/detail-form 保留同笔、历史、证据和明确的批量账户/分类入口。Page 显式绑定，不增加方法覆盖链或通用工作流引擎。

普通资金端点的账户选择同时确定归属，前端不另存独立本人／他人模式。`detail-fields`和共享资金方向规则把付款／收款标签映到固定事件字段，来源流入不能导致保存时再次交换 ID；本机与服务端应用同一归属规则。普通收入／支出的交易对方按业务语义保留，只有会改变本账本结果的端点需要明确选择，复杂业务仍使用专有表单。

后端 editor-policy、editor-composition、editor-refund 与 repayment 步骤接受现有连接和可信身份；最终提交集中更新成员、关系和问题，保留未解释阻断。editor-fields 统一有效文本和资金角色，`fieldSources.editorOverrides` 保存清空、来源修正及未完成草稿。旧 setReview 回执和 editorVersion=1 兼容保留；新模式调用由本地会话处理，服务端只在最终协议重新应用。详细字段边界见[统一编辑方案](导入交易统一编辑方案.md)。
