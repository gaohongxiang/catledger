# 架构与代码导航

> 这是一份现有实现的定位图，不是待实施的大架构。完整业务顺序见[项目逻辑说明](招财猫记账本入账逻辑说明.md)，当前任务状态见[实施规划](招财猫记账本实施规划.md)。整理基线：`b804bfc4`。历史设计见[归档](归档/README.md)。

## 1. 部署边界

```text
miniprogram（微信原生 UI 与客户端服务）
    ├── catledger-api（普通账本、贷款、统计、导出）
    └── catledger-import（账单解析、整理、核对、入账）
                     ↓
                CloudBase MySQL
原始文件另外使用私有云存储；它不是权威余额来源。
```

两个函数分别打包、部署，不跨函数目录 require。不使用常驻应用服务、云托管或新增数据库；是否改变部署形态须另有实测与授权。未来资金预测、决策模型、复式分录和影子双写不是这张现状图中的运行组件。

已核对与重复交易共用[review-detail](../miniprogram/pages/import-workbench/review-detail.js)展示各份原文；复用既有只读接口自动接续来源读取、两路补齐字段，并隔离关闭、会话和版本变化后的响应。列表只负责查看。普通已核对单笔修改由[review-edit](../miniprogram/pages/import-workbench/review-edit.js)与[review/event-review](../cloudfunctions/catledger-import/src/review/event-review.js)承接：`financeUpdates.setReview`只接受类型与资金账户的变化，复用用户锁、双版本、幂等回执和现有引用/入账校验；按新类型处理分类与退款关系，生成必要后续问题，不改原始来源或正式余额。多账户分配与贷款付款不走通用字段覆盖；已有同笔事实继续使用独立纠错流程。

同笔判断修改由[duplicate-edit](../miniprogram/pages/import-workbench/duplicate-edit.js)与[duplicate-revision](../cloudfunctions/catledger-import/src/review/duplicate-revision.js)承接。`economicEvents.duplicateReview`只读重验来源和可修改范围；`financeUpdates.reviseDuplicate`复用用户锁、批次/事件版本和幂等回执，拆分搬移原证据、重建未决成员及关系，反向合并复用原配对事务，历史关联只撤回本次引用。合并前人工字段留在服务端`fieldSources.mergeOrigins`，不向列表或日志返回；旧版没有快照时由来源重建。无需新表或运行权限，正式入账仍由整批事务负责。

`saveEvent/saveEvents` 负责引用校验、可入账重算、原因、版本与操作来源；旧升级的引用保护与 semantic 来源是契约的一部分。自动分类升级只允许在semantic来源、未人工指定分类时替换分类，并重新校验同用户可用分类；其他引用仍保持。`recalculateUpdateCounts` 还涉及历史核对、草稿可达性和批次版本，不是无副作用统计函数。需要改这些函数时先读完整调用链和测试。

整理列表在 `finance-update-read` 按本地时间和稳定ID做服务端游标分页，未知日期置后；问题组取非候选成员的最早时间，事件成员页采用相同顺序。游标绑定顺序、筛选、用户与视图版本。`finance-update-repository` 在同用户范围联查分类及父类，直接提供名称；前端不依赖目录预加载，待核对及分类不按类型或商户重排页内记录。`import-view-session` 为核对与分类主列表沿原有游标补齐50笔，传输片段保持原服务端预算；全部补齐才提交显示页与导航位置，失败、关闭、取消及版本变化不混入部分数据，原文与成员分页保持各自边界。待核对与待分类直接使用 `economicEvents.list` 的交易视图，事件附当前页批量查询所得的紧凑 `pendingIssue`；总数、游标和显示条目均按交易，问题成员和决定范围不变，无入口的交易也保留展示。`presentation` 只向列表传有界摘要，完整字段保留给详情。`economicEvents.list` 的 `excluded_groups` 视图在服务端以精简字段汇总整批排除组，仅账户排除决定按来源账户归组，其余按自动或单笔排除原因归组；分组规则版本参与视图及游标，规则改变后旧缓存不能混用，返回稳定组标识及总笔数；`excludedGroupId` 只读取该组当前50笔成员，沿用同一用户、批次、关键词和版本游标。前端 `excluded-review` 保持整张排除组卡片，展开明细独立分页，不下载整批交易详情；一次只持有一个展开组，收起、换组和隐藏取消迟到读取。

## 5. 数据分层与事务

正式账本为账户、分类、交易。导入保存文件/批次、原始行、来源身份、事件证据、事件关系、问题与成员、用户行动、事件—交易关系及副作用。贷款保存资料、付款与分配、计划与修订、分期编号绑定和分项来源；0026增加稳定费用合同/授权、收费项及覆盖/抑制、来源、清偿分配和只追加审计；0027把历史新费用与同额余额保全交易成对关联。0029保存交易原创建归属、计划删除快照及随计划撤销费用标记；重绑不覆盖原创建，审计保留，旧归档接口不改语义。表与列的完整事实在迁移和导出清单中，不在文档再复制一份易漂移的 schema。

0030为用户增加默认初始化版本，0031保存用户范围内可靠银行/平台来源对、必要事实摘要与原决定行动。迁移不产生交易、不回填猜测关系；运行时权限和导出清单同步覆盖新增表。老用户首次安全维护后走只读 bootstrap。配对复用原 FinanceAction、幂等回执与用户锁；大范围每100对原子保存，最终入账仍是原整批事务。

用户业务查询、复合外键、唯一键及幂等回执都有用户边界。客户端 uid 不能成为授权依据；原文和 SQL 绑定值不进入普通日志。

写操作在既有用户锁与事务内执行，业务变化和回执共同提交。金额、版本、约束、锁序及读取隔离级别以对应事务入口为准：不要把一致只读快照与持锁后的当前账本检查混为一谈。批量 SQL 分块不等于分批提交。

只读汇总需要同一快照内的内部一致性；导出还将多页绑定到同一数据修订。余额守恒和退款/贷款依赖在写入时再次确认，不信任之前页面或预览中的数值。

## 6. 前端职责

贷款相关账目在 [transaction-editor/loan-context](../miniprogram/pages/transaction-editor/loan-context.js) 读取保护关系并展示只读详情，统一进入 [loan-payment](../miniprogram/pages/loan-payment/index.js) 查看一次借还。该页默认展示结果，展开维护操作后才进入修改、核对或 [loan-plan](../miniprogram/pages/loan-plan/index.js) 的期次调整；贷款名称进入贷款详情。transactionId 直达由编辑页按当前用户读取，加载期间及费用/付款保护下保持只读。贷款列表通过 loans.retainedCharges 分页读取保留费用并进入既有详情；历史已记支出候选复用 transactions.refundable 的有界金额/月查询，选择交给 installment-coverage/adoptTransaction 事务校验。显示与展开状态不承担账务变更，沿用原 API 和 pending-ledger-write 恢复路径。

| 层 | 负责的状态与流程 |
| --- | --- |
| 工作台 index | 初始数据、生命周期和 WXML 处理者逐项绑定；没有 enhance 覆盖链 |
| runtime | 页面活动、首次恢复、摘要/主分页协调、共享状态和资源释放 |
| upload/account-review/transaction-review/pairing-review/posting-flow | 各自操作流程，复用既有服务，不维护第二份持久命令 |
| model/presentation | 展示转换，不充当业务账本 |
| import-view-session | 读视图版本、分页和缓存 |
| import-draft-session | 已有批次草稿队列、原请求、幂等键、postFlight 与按环境/用户隔离的最近批次指针 |
| pending-ledger-write | 首次整理prepare及账务命令的原请求持久化、查询回执与重放；不另建恢复队列 |
| read-cache / read-policy / read-snapshot-store | 普通查询去重、屏障、失效、有限展示快照 |

页面/登录/批次有效性与列表读取令牌分开。旧读结果可以废弃，已发送的写入仍要按原请求确认；不得用清空缓存或页面卸载当成服务端回滚。

## 7. 版本、预算与验证边界

工程检查验证依赖图、部署边界、平台语义层和页面显式装配；行为测试验证账务与恢复。当前代码是否部署、真机是否通过，均不由本架构图推断。运行方法只维护在[开发与验证](开发与验证.md)。
