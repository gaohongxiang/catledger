# 招财猫记账本架构设计

## 1. 总体结构

```text
微信原生小程序
  ├─ catledger-api 云函数：登录、账户、分类、交易、统计、未来计划和情景测算
  ├─ catledger-import 云函数：文件读取、解析、去重、整理、入账
  ├─ CloudBase MySQL：正式账本、来源身份、整理事实和审计关系
  └─ CloudBase 云存储：待解析和短期追溯的原始账单
```

不使用云托管和常驻服务器。只有当真实账单解析的执行时间、内存或依赖经测量超过云函数边界时，才单独评估迁移导入函数；不能为假设负载提前增加服务。

## 2. 客户端

- 使用 WXML、WXSS 和 JavaScript，优先微信原生组件和能力；
- 客户端只负责展示、输入、文件选择、上传进度和调用云函数；
- 不在客户端保存数据库凭据、AppSecret 或权威用户 ID；
- 首发只维护简体中文，不引入跨端框架和国际化运行时。

## 3. 云函数边界

### `catledger-api`

负责低延迟、结构化业务：用户初始化、账户、分类、手动交易、交易查询、首页统计，以及后续贷款/分期、未来付款承诺、安全线和只读情景测算。每个入口都从可信微信上下文取得用户身份。

函数内部保持模块化单体：`handler` 独占可信身份和公开错误边界，`action-registry` 保存公开动作映射，账户与分类各有独立服务；交易由薄门面组合领域校验、正式交易命令、明细查询和报表统计。写动作统一进入用户范围的幂等事务，明细摘要、首页和完整统计分别在同一 `REPEATABLE READ` 只读快照内生成，避免同一响应混用不同连接时点的数据。

财务状态和情景测算必须由结构化数据与确定性程序完成，不调用模型计算金额。后续如加入 AI 解读，仍由 `catledger-api` 在服务端提供最小化、脱敏后的结构化结果；模型不可直接写数据库，也不新增支付或交易权限。

### `catledger-import`

负责资源消耗和失败边界不同的任务：读取临时对象、识别文件类型、解析、规范化、来源身份去重、整理和整批入账。多文件由独立任务驱动，单文件失败可重试。

首发阶段不拆更多云函数，避免部署、权限、冷启动和费用复杂度。

## 4. 数据与存储

- MySQL 是唯一正式数据库，使用显式迁移、事务、外键/唯一约束和索引；
- 每张用户业务表都含 `uid`，复合唯一键把 `uid` 放入身份边界；
- 原始文件对象键由服务端生成并包含用户隔离前缀，不使用原始文件名作为权限边界；
- 文件上传成功但业务失败时保留短期重试窗口；成功入账后按策略异步删除原文件；
- 云函数本地目录仅作一次调用内的临时空间，不承担持久化。

### 4.1 正式账本首版模型

- `catledger_accounts` 保存账户类型、资产/负债方向、币种、活动名称唯一键、版本和停用时间；
- `catledger_transactions` 用可空转出/转入账户表达支出、收入、转账和余额调整，金额统一为分单位正整数；
- 账户余额由交易流入减流出聚合，转账只占一行，软删除交易统一从余额和统计排除；
- `catledger_mutation_receipts` 在业务事务内保存用户范围的幂等摘要和首次公开结果；
- 账户、交易、分类外键和索引均带 `uid`，跨用户对象与不存在对象使用相同公开错误；
- 发生时间同时保存本地日期时间、UTC 时间和当时时区偏移，自然月查询以本地日期为准。

### 4.2 `catledger-api` 当前动作

`bootstrap` 保持兼容；结构化业务使用 `dashboard.get`、`statistics.get`、`accounts.list/create/update/archive/correctBalance`、`categories.list/create/update/archive/restore/reorder` 和 `transactions.list/refundable/create/update/delete`。所有写动作可重试，修改/删除再使用版本号做乐观并发控制。金额在请求和响应中使用十进制字符串，不经过 JavaScript 浮点数。

退款在 `catledger_transactions.original_transaction_id` 内关联同用户原支出，并作为目标账户流入；收支汇总以 `expense - refund` 计算支出，分类沿用原支出分类。原支出行承担并发锁，数据库自关联外键和服务端累计金额校验共同防止孤立或超额退款。

### 4.3 导入证据与经济事件模型

- 导入链路统一采用“来源证据 → 经济事件候选 → 整理决定 → 正式交易”，消费、收入、转账、退款和还款不得各建一套互不兼容的主流程；
- 来源文件、原始行、规范化记录和来源身份各自保留；同来源身份由用户范围内的数据库唯一约束裁决，跨来源关联不得改写或删除任一来源身份；
- 经济事件表示现实中的一次资金活动，可以关联一条或多条来源证据，也可以关联一笔或多笔正式交易；只有正式 `Transaction` 影响余额、现金流和统计；
- 通用关联器只负责产生带证据和规则版本的关系候选：共享并核验通过的稳定关联号或已冻结官方规则才可自动确认，仅金额、时间、文本、对方或账户尾号接近时必须转用户确认；
- 业务语义规则在通用关联结果之上生成正式交易：普通消费或收入通常一笔，本人转账一笔关联两个账户，退款关联原支出，贷款还款可拆为本金转账和若干利息/费用支出；
- 贷款模型是经济事件的扩展，额外保存贷款账户、期次、本金、利息、费用、应还日和剩余本金等结构化事实。缺少贷款明细时不得猜测拆分，拆分组成项必须与已确认还款总额守恒；
- 具体表名、关系唯一性、状态机、冲突码和版本字段由 MINI-1905/1906 在迁移前冻结，贷款扩展字段由 MINI-1908 冻结。

### 4.4 解析器统一投影契约

平台字段不能直接写入 `catledger_transactions`。每个解析器先保留来源原文，再投影到统一候选字段：

```text
平台原字段 → 统一候选字段 → 规范化记录
          → 经济事件候选 → 整理决定 → 正式交易
```

文件级至少记录来源类型、文件格式、账单起止日期、账单主体候选、解析器版本和标准化版本。每一行统一投影为：

| 候选字段 | 用途 | 进入正式交易前必须完成 |
| --- | --- | --- |
| `transactionTimeRaw` | 来源交易时间原文 | 生成明确时区的本地时间和 UTC 时间 |
| `amountRaw` | 来源金额原文 | 转换为非负分单位金额，不经过 JavaScript 浮点数 |
| `directionRaw` | 收入、支出或其他方向原文 | 形成方向候选，不能单独决定交易类型 |
| `statusRaw` | 成功、关闭、退款等状态原文 | 判断正常、退款、无效或未知经济效果 |
| `transactionTypeRaw` | 消费、转账、红包、还款等来源类型 | 只作业务关系线索，不直接作为账本分类 |
| `counterpartyRaw` / `itemRaw` | 对方、商品或交易说明 | 用于展示、分类和关系候选，不能单凭文本合并 |
| `paymentMethodRaw` | 余额、零钱、银行卡、消费信贷等工具线索 | 经用户范围内账户映射后才能形成正式账户 ID |
| `noteRaw` | 来源备注 | 保留原始证据后生成必要的展示备注 |
| `transactionIdRaw` | 平台交易号候选 | 构造来源身份和精确去重 |
| `orderIdRaw` / `merchantOrderIdRaw` | 平台订单号和商户订单号候选 | 来源身份辅助核验 |
| `sourceLocator` | CSV 行号或工作表及行号 | 证据下钻 |

支付宝、微信和银行模板都映射到同一组候选字段，但解析规则分别版本化：

- 微信和支付宝解析器维护经过脱敏或合成样本验证的表头别名，不假定平台格式永久不变；
- 银行之间没有统一表头，优先采用经过测试的专用模板；通用表格只有在列含义可安全确定或用户明确确认后继续；
- 带符号金额、金额加方向、收入/支出分列是三种不同输入方式，正负语义不明或收支列同时有值时转待确认；
- 币种与人民币首版冲突、状态缺失、账户无法映射或标识互相冲突时，不生成确定事实；
- 具体平台别名和示例见通俗说明，MINI-1905 实现后以解析代码、测试夹具和现行说明为准。

账单主体、支付工具线索和账本账户必须分开：账单主体回答“这份资料属于谁”，支付工具回答“这一行可能通过什么工具收付”，账本账户才是正式余额归属。同一支付宝或微信账单可以同时出现余额、银行卡和消费信贷，不能把整份文件机械映射为一个账户。`source_account_id` 的 `source` 始终表示资金流出角色，不表示账单来源平台。

### 4.5 后续财务状态与决策模型

- 账户后续增加可解释、可由用户确认的流动性语义；可立即使用资金由正式账户余额派生，不维护第二份权威余额；
- 导入批次、来源账户和正式账本保留数据日期与覆盖事实，用于判断财务状态是否完整和新鲜；
- 未来付款承诺、贷款/分期计划及其实际付款关系独立建模，不提前写入 `catledger_transactions`；
- 用户安全线属于用户范围内的明确设置；情景请求默认只读并使用同一数据快照计算四种方案，不因重复请求产生业务写入；
- 情景结果必须包含计算时点、正式账本版本或等价快照标识、来源覆盖、显式假设和待确认项，以便复算和审计；
- AI 解读属于可选展示层，晚于确定性测算上线；默认只接收必要的结构化聚合和脱敏证据摘要，模型不可成为余额、现金流、未来支出或安全线判断的权威来源。

## 5. 版本与迁移

- 数据迁移放在 `migrations/`，编号连续、forward-only、可重入；
- 公共请求与响应契约放在 `shared/`，服务端先校验再执行业务；
- 解析规则有显式版本，已入账事实不随解析器升级自动变化；
- 财务状态和情景计算规则同样使用显式版本；历史报告如需复现，必须能确认其数据快照、规则版本和用户输入；
- `main` 只维护小程序，旧 Web 版固定在 `catledger-web` 和 `web-v2-final`。
- 迁移运行器使用数据库命名锁防止并发 DDL；既有表索引变更先检查 `information_schema`，保证迁移半完成后可安全重跑。

### MINI-1908A2a 实际放款、还款与整组撤销

独立贷款详情新增“登记实际借还”和按需读取的实际记录；仍不修改记一笔、导入或底栏入口。loans.record 的 new 模式要求明确资产账户、发生时间、总额及最多 20 笔贷款各自的当前版本、本金/利息/费用和费用入账情况。未知构成不提交，明确零可以提交，各分项的整数分总和严格等于实际总额。

0014 新增实际批次、逐贷款分配和正式交易关系；用户范围的生成列唯一约束禁止一笔活动正式交易属于两个贷款批次。写入、各贷款版本、正式账目、现金检查及幂等回执共用同一用户锁和事务。loans.reverse 校验整批/全部贷款/全部交易版本；外部复用或退款依赖时阻止，成功后整组软删除新增账目、停用关联、恢复本金并保留撤销历史。活动借还存在时资料接口拒绝直接改基准、日期、类型和账户。普通交易编辑/删除/分类/退款、导入更正/撤销/退款/已有单笔关联均检查活动贷款关系并提示前往贷款管理；两支函数独立打包相同的最小分块保护查询，未跨部署目录 require。
