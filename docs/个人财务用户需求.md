# 我的个人财务记账需求

> 状态：用户需求主文件，可随时补充和调整

> 当前产品形态：自托管 ezBookkeeping Web/PWA

这份文件是我的个人财务产品总规划，只记录“我要解决什么问题、产品应该怎样使用、页面需要展示什么、什么最重要”。细化后的会计语义与验收规则维护在 [个人财务业务规则与验收.md](./个人财务业务规则与验收.md)，技术架构和工程任务维护在 [个人财务实施规划.md](./个人财务实施规划.md)。

以后需求有变化时，直接修改或补充这份文件，并把已确认的变化同步到业务规则与实施规划。

## 1. 一句话目标

我要的是一个真正好用的个人记账工具：把支付宝、微信、银行卡、信用卡、贷款和分期等所有真实账目放进同一本账，尽量少手工录入、不重复计算，并且随时能看清资产、负债、收支和还款情况。

它不应该要求我先学会一套复杂的财务系统，才能完成最基本的记账。

## 2. 我的账户和账单来源

需要覆盖：

- 支付宝；
- 微信支付；
- 银行卡和银行账户；
- 信用卡；
- 银行贷款、消费金融、网贷和一般借款；
- 各类分期；
- 现金，以及没有电子账单的少量手工账目。

系统必须分清“钱实际存放在哪个账户”和“通过什么渠道支付”。例如，用支付宝调用信用卡付款，本质上是一笔信用卡支出，同时可能在支付宝账单和信用卡账单中各有一份证据，不能算成两笔消费。

账户既可以由我手工建立，也可以由账单中的“付款方式/支付方式”发现。导入支付宝或微信账单后，系统应先汇总本批次出现的实际付款账户，例如“兴业银行信用卡（6106）”“江苏银行信用购”“微信零钱”，再进行下面的处理：

- 忽略空格、全角/半角括号、“尾号”等不影响身份的格式差异，优先推荐已有的同一账户；
- 只有唯一且足够可信时才预选已有账户，不能仅凭“银行卡”这类泛称乱匹配；
- 没有对应账户时，给出建议名称和账户类型，展示给我确认；只有我点击同意后才能创建正式账户；
- 我也可以改选其他已有账户，或修改建议名称和账户类型后再创建；
- 同一批次中相同的付款方式只确认一次，确认后所有对应订单共同使用该账户，不再逐笔询问；
- 已确认的付款方式映射需要持久保存，后续账单遇到同一付款方式时自动复用；账户被删除、币种冲突或匹配存在歧义时重新让我确认。

“账单属于哪个支付宝/微信用户”是账单来源身份，“这笔钱实际从哪张银行卡、信用卡或余额账户支付”是正式账本账户，两者必须始终分开。

## 3. 我希望怎样记账

### 3.1 主要方式：批量导入账单

- 支付宝、微信、银行卡、信用卡等有电子账单的交易，不要求平时再逐笔手工录入。
- 每周或月末批量导入账单，由系统完成解析、账户映射、精确去重和跨来源整理。
- 系统应尽量自动处理明确的记录，只把无法确定、互相冲突或确实需要判断的少量项目交给我。

### 3.2 辅助方式：手工“记一笔”

以下情况才需要手工记录：

- 现金消费；
- 没有电子凭证的收支；
- 我希望当下立即看到、暂时还没有账单的交易。

如果之后导入的账单对应到已经手工记录的交易，系统应把账单作为这笔交易的新证据关联上去，不能再新增一笔支出。金额、币种、方向或账户等关键信息不一致时，应让我确认，不能静默覆盖。

### 3.3 最终统计口径

- 只有已确认进入正式账本的交易，才能影响余额、收支和统计。
- 原始账单行是证据，不等于正式交易。
- 待确认、冲突或仅处于整理区的数据，不得提前进入总览。
- 同一经济事件可以有多份来源证据，但正式账本中只能计算一次。

## 4. 必须正确的记账规则

- 自己账户之间转账，不是收入也不是支出。
- 银行卡偿还信用卡，是账户间资金转移，不是再次消费。
- 贷款到账会同时增加资产和负债，不是收入。
- 偿还贷款本金会减少资产和负债，不是生活消费；利息和手续费才是借贷成本。
- 退款、撤销应冲回原交易的影响，不应作为普通收入重复统计。
- 调整账户余额与真实消费必须区分开。
- 金额相同或时间接近，不能作为自动合并两笔交易的唯一依据。
- 同一来源有稳定且相同的记录身份时可以精确去重；身份相同但核心内容冲突时必须保留证据并交给我处理。
- 不同币种不能直接混成一个没有解释的总数；缺少汇率时要明确提示。

## 5. 总览需要展示什么

### 5.1 当前完整财务状况

资产、负债和净资产默认统计全部正式账户截至今天的完整状态，不需要我先选择“报表起始日”和“截至日期”。总览中出现日期时，主要用于解释数据截至何时或某个流量指标覆盖哪个时期，不是让我先定义“统计全不全”。

总览至少要让我快速看到：

- 总资产、总负债、净资产；
- 可随时使用的资金；
- 各类债务的剩余本金；
- 未来 7 天、30 天和本月待还金额；
- 各账户余额及其更新时间。

### 5.2 收支、现金流与趋势

总览需要展示：

- 今天、本周、本月和今年的真实收入与生活消费；
- 本月收入、生活消费、偿债本金、借贷利息与费用、流动资金净变化；
- 最近 6、12 或 24 个月的收入、生活消费和实际偿债趋势；
- 当前月份和趋势中的数字都能下钻到对应正式交易；
- 金额一键隐藏或显示，隐藏时卡片、图表和明细摘要都不能泄露金额。

### 5.3 还款安排与数据可信度

总览还需要展示：

- 未来 7 天、30 天和本月的应还金额及涉及的贷款或分期；
- 每笔债务的下一还款日、下一期金额和完成进度；
- 各账单来源的最近覆盖日期和明显缺口；
- 待确认、解析失败、身份冲突和疑似重复的数量；
- 哪些数据已经进入正式统计、哪些仍未计入，以及当前结论是否可信。

### 5.4 信用卡未出账与月末统计

每张信用卡的账单日和还款日可以不同，但月度收支仍按自然月和实际交易日期统计，不能把消费统一归到信用卡出账月份。信用卡账单周期只用于判断账单覆盖范围、已出账应还和还款日期。

我在月末查看当月统计时，不需要等待所有信用卡出账：

- 已经从支付宝、微信、信用卡未出账明细或其他可靠来源确认的消费，按实际交易日期计入当月；
- 尚未出账且没有其他证据覆盖的信用卡日期区间，明确标记为覆盖缺口，不能假装当月已经完整；
- 月报在覆盖尚未完整时显示“暂结”，同时列出哪些信用卡待出账、各自覆盖到哪一天；
- 后续正式账单导入时，与已有交易关联并补齐遗漏，不重复记账；对应历史月份自动修订并保留变更说明；
- 相关账单覆盖完整、冲突处理完毕后，月报显示“已确认”。

每张信用卡应展示常规账单日、实际账单周期、还款日、已出账应还、已识别未出账消费、当前已知负债和未覆盖区间。常规账单日只是提醒依据，每份账单提供的实际起止日期才是覆盖判断依据；账单日调整时不能改写历史周期。

## 6. 账单导入与整理体验

- 账单整理应在一个连续流程中完成上传、账户确认、去重、跨来源整理和入账，不要让我在不相关的页面之间来回寻找下一步。
- 一次可以同时上传支付宝、微信、银行卡、信用卡等多份账单，组成同一次“账单整理任务”。系统应联合分析这些账单以及已经保存的账户、证据、正式交易、分类规则和分期合同，但每个文件、每条原始记录仍分别保存，不能先合并成一个总额而丢失来源。
- 第一次使用时，流程应当是：建立账户 → 导入账单 → 只处理异常项 → 查看总览。
- 日常使用时，流程应当是：上传本期账单 → 检查系统整理结果 → 处理少量待确认项 → 完成。
- 系统应明确告诉我哪些记录已导入、哪些重复、哪些冲突、哪些尚未进入正式账本，以及原因是什么。
- 证据预览必须直接展示账单已经提供的付款方式，不能让我到原始 Excel 中自行寻找。
- 每次账单整理任务在逐笔确认交易前，先跨本次全部文件展示“检测到的付款账户”：哪些已匹配已有账户、哪些建议新建、各影响多少笔交易；同一账户只确认一次，再应用到全部相关批次。
- 同一份文件重复上传、重叠账期重复导入或多来源出现同一笔交易，都不能造成重复统计。
- 高级映射、证据详情和技术信息可以保留，但默认折叠；常用路径应使用普通人能理解的说法。

多账单联合整理按不同信息采用不同粒度：

- 账户：先汇总所有新账单中的付款方式和账户别名，再与已有账户及映射统一比较；同一账户只让我确认一次，并应用到全部相关记录；
- 交易：每条原始记录分别按稳定身份与历史证据、本次其他账单和正式交易核对；属于同一经济事件的多条记录只关联同一笔正式交易，但原始证据全部保留；
- 分类：在交易去重和跨来源整理完成后，对最终正式交易推荐分类；相同且可信的商户规则可以批量确认，但每笔交易仍保留自己的分类；
- 分期：把多份账单中属于同一分期的期次信息汇总成一个候选，再与已有分期合同比较；
- 转账、还款和退款：把相关记录组成可解释的关系候选，不把多笔金额简单相加后入账。

整理顺序应是：解析全部账单 → 汇总确认账户 → 同来源精确去重 → 跨来源事件整理 → 分期候选整理 → 正式交易分类 → 展示少量待确认项。已经确认的历史信息不得被新账单静默覆盖，发现冲突时应展示新旧依据并让我决定。

## 7. 贷款与分期

需要管理：信用卡分期、银行贷款、消费金融或网贷、一般借款等。

每笔贷款或分期需要能够记录并计算：

- 合同本金和实际到账；
- 期数、起止日期和还款方式；
- 利率、每期还款额、一次性费用、每期费用、优惠和减免；
- 总成本、真实年化、逐期本金/利息/费用；
- 已还进度、剩余本金、下一还款日和未来还款计划。

贷款的“计划还款”与账本中的“实际还款”必须分开。计划不能直接代替真实账目；只有实际发生并关联到正式交易后，才能计入已还。

一笔分期只建立一次完整合同和还款计划，不能因为每个月账单里出现“第 1 期”“第 2 期”就重复创建分期。每月账单中的分期行是该计划对应期次的实际证据，应关联到同一份分期合同。

自动识别只能先生成“待确认分期”，不能直接生成正式合同。首次在账单中识别到一组尚未管理的分期，或现有信息不足以可靠关联时，系统应先汇总同一次整理任务中的全部相关期次，并让我一次确认：

- 关联的信用卡、贷款或平台负债账户；
- 分期名称或原始消费、总期数和当前期数；
- 合同本金、每期应还、本金、利息和手续费；账单没有提供的字段允许暂时未知；
- 首次还款日、还款频率和还款方式；
- 原消费是否已经存在于正式账本，以及应该关联哪一笔交易。

确认时我可以选择：关联已有分期合同、补充信息后创建正式合同，或保存为“待完善分期”等待以后账单继续补充。待完善分期应显示在“贷款与分期”的待处理区域，但不能用未知字段计算真实年化、总成本或完整未来还款计划；未知必须明确显示为未知，不能当作零。对应的当期真实交易仍可按账单正常整理和入账。

还款方式使用容易理解的选项，并在旁边标注专业名称：

- 每期总额基本相同（等额本息）；
- 每期本金相同、利息逐期减少（等额本金）；
- 每期本金和利息都相同（等本等息）；
- 前期付息、最后归还本金（先息后本）；
- 按账单记录、自定义或暂不确定。

系统可以根据合同或多期账单给出建议，但不能只凭一期金额擅自认定还款方式。确认后，后续账单应按稳定的分期编号、订单号、原消费关系或其他可靠身份自动关联；只有总期数、期次、金额、账户或候选合同冲突时才再次让我处理，不能仅凭金额相同或日期接近关联。

分期的会计口径必须保持一致：原消费只计算一次；每期归还本金不是新的消费；利息和手续费才计入借贷成本；银行卡向信用卡还款仍是账户间转账。如果首次发现分期时还不能确认原消费是否已入账，系统应让我选择“关联已有消费”“补建缺失消费候选”或“暂不确定”，不能静默新增消费。

界面默认先展示剩余本金、下一期应还、总成本和进度等常用信息；专业计算明细可以展开查看，不要一上来就要求填写或理解所有术语。

已有 loan-cost-calculator 项目只作为算法和交互参考，不作为本项目的运行依赖。

我已有一份完整的历史贷款、借贷和分期 JSON 备份。未来需要提供一次性迁移能力，把其中有效记录融合进本系统；这项目前暂缓，不影响先把现有网站和正常记账流程做好。

## 8. 易用性和信息架构

日常最重要的入口应尽量控制为：

1. 总览；
2. 记账与明细；
3. 账单整理；
4. 贷款与分期。

账户、分类、标签、模板、统计分析等能力可以保留，但不应阻挡新用户完成第一次记账。高级功能放在次级导航或“更多”中，按需要再展开。

页面和操作应遵循：

- 先给结论，再给解释；
- 先显示常用操作，再显示高级配置；
- 使用生活化文案，必要的专业术语附带解释；
- 空页面要告诉我下一步做什么；
- 错误和冲突要告诉我原因以及如何处理；
- 如果打开网站后仍然不知道“第一步该做什么”，就不能算易用性验收通过。

## 9. 隐私、部署和架构边界

- 保持一个轻量、自托管的应用和一套正式账本，不为了功能堆叠引入微服务或第二套账本。
- 账单和财务数据默认只进入我自己的服务，不上传到外部 AI 或第三方分析平台。
- 原始账单内容、完整账户标识和真实交易详情不得进入普通日志、公开仓库或测试夹具。
- 即使目前主要是我自己使用，也必须保留用户数据隔离。
- 产品架构以我的实际需求、正确性、易用性和长期可维护性为优先，并持续维护必要的安全修复和基础能力。

## 10. 当前优先级

### 10.1 当前必须做好

- 先优化现有网站的使用流程和信息架构；
- 建立准确的统一账本口径；
- 做好批量导入、去重、跨来源整理和人工确认；
- 做好清晰、完整、可解释的财务总览；
- 做好贷款与分期的记录、成本和还款管理；
- 保证数据隐私、可恢复和统计可解释。

### 10.2 当前暂缓

- 历史贷款 JSON 的一次性迁移；
- 微信小程序；
- 微信登录、云开发、上架和商业化；
- 依赖外部 AI 的全自动分类；
- 与核心记账无关的复杂外部基础设施。

“暂缓”表示以后可以继续讨论，并不等于永久取消。

## 11. 最小可用验收场景

产品至少应通过这些真实场景：

1. 同一笔信用卡消费同时出现在支付宝和信用卡账单中，最终只统计一次。
2. 我先手工记了一笔，后来导入对应账单，最终仍只统计一次，并保留账单证据。
3. 银行卡偿还信用卡，不被算作新的消费。
4. 贷款到账不被算作收入；还本金不被算作消费；利息和费用被正确计入借贷成本。
5. 重复上传同一账单或导入重叠账期，不改变已经正确的统计。
6. 未确认或冲突的记录不会悄悄进入总览。
7. 打开网站后能直接看懂当前财务状况、近期收支、待还款和下一步要做什么。
8. 新用户无需先配置分类、标签或模板，也能完成账户建立、账单导入和查看结果。
9. 支付宝或微信账单中的“兴业银行信用卡(6106)”能推荐已有的“兴业银行信用卡（6106）”；没有账户时只需按付款方式确认一次创建，同批次其他相同付款方式交易不再询问账户。
10. 同一笔分期连续出现在多个月账单中，只形成一份分期合同和逐期证据，不重复增加合同、消费或本金。
11. 首次识别分期时可以一次确认账户、期次、还款方式和原消费关系；后续信息一致时自动关联，冲突时明确说明原因并等待处理。
12. 同时上传支付宝、微信和信用卡账单时，账户与分期只需按组确认，交易仍逐条留证并在去重后只统计一次，分类只作用于最终正式交易。
13. 月末有信用卡尚未出账时，已确认消费仍按交易日期进入当月，月报明确显示暂结和覆盖缺口；以后导入账单只补证据和遗漏，不重复消费，并自动修订对应月份。
