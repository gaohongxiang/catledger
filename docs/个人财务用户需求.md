## 1. 产品宪法

### 1.1 一句话定位

这是一个**不用每天手工记账、每月更新一次数据，就能看清真实消费、资产、负债和待还事项的个人财务助手**。

它不是要求用户培养“每天记一笔”习惯的流水账工具，也不以覆盖所有银行、所有金融产品和所有文件格式作为开始使用的前提。

### 1.2 用户价值

用户更新账单后，应快速得到这些答案：

- 本月实际花了多少，主要花在哪里；
- 当前资产、负债和净资产大致是多少，数据是否可信；
- 最近要还什么、何时还、还多少；
- 是否存在重复扣款、退款、遗漏、异常或覆盖缺口；
- 哪几项确实需要本人判断。

记账、解析、去重和对账本身不是最终价值，它们只是生成这些答案的后台能力。

### 1.3 长期原则

1. **结果优先但不做黑箱**：默认先展示财务结论，用户可随时核对最终交易、处理过程和原始证据。
2. **自动整理**：清晰事项自动处理，确认是例外，不是每次导入的固定劳动。
3. **异常隔离**：一条不确定记录只影响自己及直接关系，不得迫使整批清晰交易重新整理；正式入账默认仍以本次更新为单位统一确认。
4. **账本正确**：不为减少点击而把借款、还款、退款或内部转账误算成收入和消费。
5. **覆盖诚实**：数据不完整时显示缺口和可信度，不用伪精确数字冒充完整财务状况。
6. **渐进披露**：账户身份、证据、候选、解析器和合同计算默认藏在后台或高级详情。
7. **可追溯可撤销**：自动结论必须能说明依据，用户确认的事实不得被新规则静默覆盖。

## 2. 目标用户与非目标

### 2.1 优先服务的用户

- 日常使用支付宝、微信，并可能使用多张银行卡或信用卡；
- 不愿每天手工记账，但愿意每周或每月花几分钟更新财务数据；
- 关心消费、净资产、信用卡待还和债务，而不只是保存流水；
- 接受首次使用时核对少量账户，之后希望系统自动沿用；
- 重视隐私、数据所有权和结论可解释性。

### 2.2 当前不作为目标

- 企业会计、税务申报、经营核算和多人审批；
- 证券、基金和加密资产的完整投资组合系统；
- 覆盖所有银行实时同步或所有银行 PDF；
- 完全依赖外部大模型读取原始财务数据；
- 以复杂贷款计算器、IRR 或合同管理作为首次使用入口；
- 通过每日打卡和提醒强迫用户维持手工记账习惯。

## 3. 核心使用闭环

~~~mermaid
flowchart LR
    A[更新账单] --> B[系统自动整理]
    B --> C[只处理少量必要问题]
    C --> D[查看消费、资产、负债和待还]
    D --> E[下次按周或按月继续更新]
~~~

### 3.1 第一次使用

1. 用户直接上传支付宝、微信或已支持的银行账单，不必先建立账户、分类和模板；
2. 系统从付款方式发现账户，自动分成“可沿用、需要确认、已忽略”；
3. 用户只处理无法可靠确定的账户和经济关系；
4. 系统完成所有可以确定的交易，不让少量异常卡住整批整理；
5. 用户核对本批次的证据、合并、最终交易和待处理数量，处理或明确跳过异常后统一确认入账；
6. 用户立即看到第一份财务结果和数据覆盖情况。

### 3.2 后续使用

1. 系统默认沿用已确认的账户、商户分类和关系事实；
2. 用户上传本期新增或重叠账单；
3. 重复证据自动折叠，清晰交易自动完成整理；
4. 只出现真正新增、冲突或无法确定的事项；
5. 用户确认本批次后统一入账，财务总览随之更新并说明本期是否完整。

### 3.3 手工记一笔

手工记账只作为补充：

- 现金消费；
- 没有电子凭证的收支；
- 用户希望立即记录、尚未取得账单的事项；
- 对自动结果进行修正或补充。

后续账单若与手工交易可靠对应，只补充证据，不再创建第二笔交易。

## 4. 产品概念边界

| 概念 | 用户含义 | 产品约束 |
| --- | --- | --- |
| 账户 | 钱或债务实际在哪里 | 支付渠道不等于资金账户 |
| 原始证据 | 支付宝、微信、银行、手工记录提供的材料 | 证据不直接影响余额和报表 |
| 正式交易 | 已经能够进入权威账本的经济事件 | 同一经济事件只统计一次 |
| 关系 | 同一事件、退款、转账、还款、分期等关联 | 关系不能靠金额接近单独确定 |
| 债务计划 | 贷款或分期未来预计发生的事项 | 计划不等于实际交易，不直接改变余额 |
| 覆盖与可信度 | 当前数据覆盖了哪些账户和时间 | 缺口必须明确展示 |

现有 `Account`、`Transaction`、分类和标签继续作为正式账本的唯一权威，不建立第二套正式账本。个人财务扩展负责证据、解释、关系、计划和覆盖，不反向替代核心账本。

## 5. 一笔钱必须分开的五个维度

| 维度 | 示例 | 是否必需 |
| --- | --- | --- |
| 资金方向 | 流入、流出 | 进入正式账本前必须明确 |
| 经济性质 | 收入、消费、内部转账、借款、还款、退款、费用、余额调整 | 进入正式账本前必须明确 |
| 生活分类 | 餐饮、服饰、交通、住房 | 可空，不阻止入账 |
| 关系 | 退的是哪笔、还的是哪个账户、转到哪个账户 | 该性质需要对方时必须明确 |
| 判断状态 | 自动确定、用户确认、待处理 | 必须可追溯 |

来源中的“收入、支出、不计收支”主要描述资金方向或来源动作，不必然等于最终会计性质。例如“收入”可能是工资、借款到账、别人还钱或自己账户转入。

当资金方向清楚但经济性质仍不明确时，系统应只询问缺失的经济性质，并允许其他清晰交易先完成；该事项在确认前不进入正式收入、消费、余额和净资产统计，覆盖状态应说明仍有待处理资金事实。

## 6. 数据来源与覆盖策略

### 6.1 第一核心入口

- 支付宝 App/Web CSV：自动识别；
- 微信支付 CSV/XLSX：自动识别；
- 手工记一笔：现金和补充；
- 已支持的银行结构化文件或专用模板：作为可选覆盖增强。

支付宝和微信覆盖大量日常交易，因此用户不上传全部银行账单也能先获得部分结果。

### 6.2 银行账单

产品不承诺覆盖所有银行 PDF。优先级为：

1. 银行提供的 CSV、XLSX、OFX、QIF、MT940 等结构化格式；
2. 已内置并可可靠识别的银行 PDF 模板；
3. 用户首次映射后可复用的通用结构化模板；
4. 扫描 PDF 或 OCR 仅作为未来辅助能力，结果必须人工复核。

某个银行文件不支持或解析失败时，不得阻止同一次任务中的支付宝、微信和其他文件继续完成。系统应将该文件标为覆盖缺口，并告诉用户可能遗漏直接刷卡、手续费、还款或利息。

### 6.3 数据覆盖

系统应按账户和时间说明：

- 已覆盖到哪一天；
- 来自哪些渠道；
- 哪些区间只有部分渠道证据；
- 哪些文件解析失败或尚未支持；
- 哪些待处理事项尚未进入正式统计。

“暂结”表示已有结果可用但仍有缺口，“已确认”表示所需覆盖和阻塞事项已经完成。

## 7. 账户体验

- 第一次可从账单发现账户，不要求预先建立；
- 账户按“银行/平台 + 卡种/余额 + 脱敏标识”匹配，不能只凭末四位；
- 同一次任务的同一付款方式只处理一次；
- 已确认映射后续自动沿用，用户可以改回；
- 不属于自己的钱可整组忽略，只保留证据；
- 只排除个别记录时使用单笔不入账，不污染整组映射；
- 账单流水不能冒充真实期初余额，未核对时总览必须标明。

## 8. 账单更新体验

### 8.1 用户只看到三步

~~~mermaid
flowchart LR
    A[选择账单] --> B[处理必要问题] --> C[查看更新结果]
~~~

解析、身份、同来源去重、跨来源合并、退款关系和分类建议属于后台阶段，不应作为并列主任务暴露给普通用户。

### 8.2 结果摘要

默认摘要优先展示：

- 本次识别的最终交易数量；
- 已经自动完成的数量；
- 当前必须处理的数量；
- 可稍后补分类的数量；
- 本次数据覆盖了哪些账户和日期；
- 完成本次更新后财务结果发生了什么变化。

摘要计数必须同时满足：`有效证据数 - 被合并的重复证据数 = 最终经济事件数`，以及 `最终经济事件数 = 已入账 + 待入账 + 待处理 + 明确不入账`。尚未入账时“已入账”为零；用户主动选择部分入账后必须继续显示全部四种状态，并将批次标为“部分入账”。

摘要必须提供明确的“核对结果”入口。有效证据数、重复证据数、候选组、来源指纹和解析版本放入“为什么这样整理”高级详情，而不是删除或只允许运维人员查看。

### 8.3 异常隔离

- 文件不可读只影响该文件；
- 账户未确认只影响使用该账户的记录；
- 退款、转账或还款不明确只影响直接关系成员；
- 身份冲突只影响对应身份；
- 分期合同不完整只影响债务计划；
- 未分类不阻止任何已经具备正式会计性质的交易。

清晰交易可以独立完成整理，未解决事项继续保存在同一批次的待处理区。默认情况下，用户处理或明确跳过阻塞事项后统一确认整批入账；系统不得在后台静默地逐笔写入正式账本。只有用户主动选择“先入账已确认项”时才允许部分入账，且剩余事项、计数和后续补入仍归属于原批次。

### 8.4 核对、纠错与撤销

用户不必逐笔确认，但必须能够按需核对：

- 查看本次全部最终交易，并按自动完成、人工确认、待处理、未分类和不入账筛选；
- 查看一笔最终交易来自几条证据、采用了哪一侧的时间、账户、对方、性质和分类；
- 查看重复证据如何折叠、退款如何关联、转账和还款如何组成；
- 将错误合并拆开、将漏合并的证据重新关联、修改账户或经济性质、恢复误设的不入账；
- 查看自动规则版本、用户决定和后续改动记录；
- 在影响范围可控时撤销自动处理，涉及已修改交易、其他批次或债务关系时先展示影响。

所有汇总计数必须能够互相解释，列表内容必须与摘要一致。系统不能用“系统已自动处理”代替可核对的具体结果。

## 9. 交易、分类与关系规则

### 9.1 去重与同一经济事件

- 相同文件、同来源稳定身份、重叠账期和多渠道同一事件不得重复统计；
- 同额同日不能单独证明重复；
- 多条证据共同证明同一事件时只创建一笔正式交易；
- 自动合并必须有版本、依据和撤销能力。

### 9.2 分类

- 支付宝等明确生活分类可以优先采用；
- 微信“商户消费”“扫码付款”和银行“其他”不是生活分类；
- 分类未知仍可入账为未分类，并计入生活消费总额；
- 未分类不进入餐饮、服饰等分类构成，用户可稍后批量补充；
- 人工确认过的分类不得被模糊来源覆盖。

### 9.3 退款

- 明确退款应关联原交易并冲回其消费影响，不作为普通收入；
- 原消费和退款是两笔经济事件，不能净额删除证据；
- 部分退款和多次退款的总额不得超过原消费可退金额；
- 无法唯一对应时只把相关事项放入待处理。

### 9.4 内部转账与还款

- 自己账户之间转账不算收入或消费；
- 银行卡偿还信用卡是资产账户到信用卡负债账户的转账；
- 已识别还款只询问付款账户，不再询问是不是还款；
- 充值、提现和余额调拨应形成账户关系或保持待处理，不得直接算收入和消费。

### 9.5 多币种

- 正式交易必须保留原始币种和金额，不同币种不能直接相加；
- 汇总到默认币种时必须记录汇率来源和日期；
- 汇率缺失时应展示缺口，不输出无法解释的折算总额；
- 外币消费、购汇、还款和手续费应分别表达，不得把全部差额塞进消费金额。

## 10. 贷款、信用卡分期与待还

### 10.1 产品位置

债务能力有价值，但不进入普通账单主流程。没有债务的用户不应被要求理解合同、年化、期数和结算分配；存在债务时，总览只优先展示下一笔待还和总负债，完整合同放在独立高级页面。

### 10.2 会计原则

- 贷款到账同时增加资产和负债，不是收入；
- 偿还本金同时减少资产和负债，不是生活消费；
- 利息和手续费才是借贷成本；
- 原消费转为信用卡分期时不得重复记消费；
- 贷款或分期计划描述预期，只有实际交易才能改变账本。

### 10.3 自动发现

账单中发现疑似分期时，只创建非阻塞建议：

- 关联已有合同；
- 创建待完善债务候选；
- 明确不是分期；
- 稍后处理。

候选不得阻止当期清晰交易完成。合同信息不足时保持未知，不能用零值伪造本金、利率、费用、年化或完整计划。

### 10.4 信用卡账期

- 消费按实际交易日期进入自然月，不能统一移动到信用卡出账月份；
- 账单日、到期还款日和实际账期用于判断覆盖、已出账应还和下一笔待还；
- 月末尚未出账但已有其他可靠证据的消费可以先计入，未被任何来源覆盖的区间标为缺口；
- 迟到的信用卡账单只补证据和确实遗漏的交易，不得重复创建消费；
- 历史月份允许因迟到账单修订，并保留变更原因。

## 11. 财务总览

### 11.1 首屏回答四件事

- 净资产，并附总资产、总负债；
- 本月真实生活消费，可切换今日、本周、本月、本年；
- 下一笔待还的日期和金额；
- 一句可信度说明，例如余额未核对、账单暂结、存在覆盖缺口或待处理。

### 11.2 第二层信息

- 可动用资金和账户余额；
- 收入、生活消费、偿债本金、利息费用和资金净变化；
- 6、12、24 个月趋势；
- 债务剩余本金和未来 7/30 天待还；
- 未分类、待处理和覆盖缺口的下钻入口。

所有金额可一键隐藏；所有汇总数字应能下钻到正式交易、关系、计划或原始证据。

## 12. 桌面、手机与未来客户端

- 当前以自托管 Web/PWA 为权威实现；
- 桌面负责文件导入、高级核对和债务编辑；
- 手机必须方便查看总览、下一笔待还、待处理摘要和手工补一笔；
- 完整手机账单整理只有在 Web 核心闭环经真实用户验证后再启动；
- 微信小程序、云端部署和商业化属于独立未来阶段，不改变当前账本与产品语义。

## 13. 隐私、信任与安全

- 原始账单、账户、商户、余额和贷款信息默认不发送给外部 AI 或第三方；
- 所有用户业务数据按 `uid` 隔离；
- 原始证据不可被自动结论覆盖或删除；
- 自动规则必须版本化，历史人工决定优先；
- 正式入账、关系决定和债务结算必须幂等、可审计、可安全撤销；
- 用户可以清理自己的数据，但高风险操作必须明确确认并提供备份建议。

## 14. 用户故事与验收标准

### US-001 不预设配置开始使用

作为第一次使用的用户，我希望直接上传账单并尽快看到结果，而不是先学习和配置账户、分类与模板。

- 当用户首次上传支持的账单时，系统应自动解析并提出账户建议，不要求预先创建正式账户。
- 当已有账户能够唯一匹配时，系统应自动沿用并允许用户改回。

### US-002 自动整理并避免重复

作为不愿逐笔记账的用户，我希望系统自动把多渠道记录整理成唯一交易。

- 当多条证据可靠证明同一经济事件时，系统应只创建一笔正式交易并保留全部证据。
- 当记录只有金额相同或时间接近时，系统不得据此自动合并。

### US-003 少量问题不阻塞整批

作为按月更新财务数据的用户，我希望清晰事项先完成，只处理真正不确定的少量记录。

- 当某笔记录存在账户、性质或关系问题时，系统应只阻塞该记录及直接关系成员。
- 当其他记录的入账必需字段已经明确时，系统应允许它们先完成整理并保留稳定结果，不因异常记录而重新计算。
- 当用户解决或明确跳过本批次的阻塞事项时，系统应在一次明确确认后原子写入本批次全部可入账交易。
- 当用户主动选择先入账已确认项时，系统才可以部分入账，并应持续展示原批次的已入账、待处理和不入账数量。
- 当部分入账后的待处理事项完成时，系统应只补入尚未入账的对应交易并更新覆盖和受影响统计。

### US-004 不支持的银行不影响已有结果

作为使用未知银行的用户，我希望即使某个文件暂不支持，也能继续使用支付宝、微信和其他已支持数据。

- 当某个文件无法识别或解析失败时，系统应继续处理同一次任务中的其他文件。
- 当存在未覆盖银行或日期区间时，系统应展示覆盖缺口，不得把部分结果标为完整。

### US-005 会计性质正确

作为关心真实收支和净资产的用户，我希望转账、借款、还款和退款不会污染收入和消费。

- 当来源只说明资金方向而经济性质不明确时，系统应询问缺失性质，不得直接把流入当正式收入。
- 当信用卡还款已经识别但付款账户未知时，系统应只要求选择付款账户。
- 当贷款到账或偿还本金时，系统应按资产与负债变化处理，不计入收入或生活消费。

### US-006 分类可以稍后补

作为只想先把余额和消费记准的用户，我希望生活分类不清楚时仍能完成更新。

- 当交易性质和账户明确但生活分类未知时，系统应以未分类状态入账。
- 当用户以后确认分类时，系统应更新分类和报表构成，不改变原交易身份。

### US-007 更新后立即获得价值

作为不愿为记账本身花时间的用户，我希望每次更新后立即看到有用的财务结论。

- 当本次可完成事项处理结束时，系统应展示消费、资产负债、下一笔待还和覆盖可信度变化。
- 当用户查看任一汇总数字时，系统应提供对应正式交易或计划的下钻路径。

### US-008 债务功能按需出现

作为没有贷款或不需要高级计算的用户，我不希望债务合同干扰普通记账。

- 当用户没有债务数据且未主动启用时，系统不应在主流程要求填写贷款或分期字段。
- 当发现分期候选时，系统应把它放入非阻塞债务待处理区，不影响普通交易完成。

### US-009 核对自动处理结果

作为重视账本正确性的用户，我希望默认直接看结果，但在怀疑系统处理错误时能够查看依据并纠正。

- 当系统自动完成本次更新时，应提供最终交易列表和“为什么这样整理”入口，不要求用户先理解技术过程。
- 当用户打开某笔最终交易时，系统应展示采用字段的来源、全部关联证据和自动判断理由。
- 当用户认为自动合并、账户、性质、分类或关系错误时，系统应提供对应纠错入口，并只重算受影响范围。
- 当用户已经确认某项决定时，后续规则刷新不得静默覆盖该决定。
- 当摘要显示证据数、重复数、最终交易数或待处理数时，各详情列表应与摘要保持一致并可相互核算。

## 15. 当前范围与延期事项

### 当前产品核心

- 支付宝、微信账单自动解析；
- 账户发现、沿用、忽略和余额可信度；
- 原始证据、精确去重、跨渠道唯一交易；
- 最终交易核对、证据解释、纠错和安全撤销；
- 分类建议、明确退款、信用卡还款和异常隔离；
- 正式入账、证据下钻和安全撤销；
- 财务总览、覆盖状态和下一笔待还；
- 已有债务能力保留，但退出普通账单主流程。

### 暂缓

- 全银行 PDF 覆盖和扫描件 OCR；
- 银行实时同步；
- 历史贷款 JSON 迁移；
- 复杂投资组合；
- 微信小程序完整迁移；
- 依赖外部 AI 的自动财务判断；
- 在核心闭环验证前继续增加新的复杂渠道和合同类型。

### 后续实现阶段必须落实

1. 交易级异常隔离和批次原子入账的新状态机；
2. 资金方向已知、经济性质未知时的持久状态和报表排除方式；
3. 多次部分退款、混合退款和费用差额的关系模型；
4. 银行模板注册、结构化文件映射和覆盖度计算；
5. 债务功能从主导航退出后的入口；
6. 正式账本与证据保留、工作数据重建、回滚和三库迁移方案。

本产品尚未对外发布，账单整理重构不要求兼容旧 billflow API、旧页面、旧任务状态和未入账工作数据。正式账本、原始证据、账户映射、来源身份和人工确认事实属于用户资产，必须保留；其余工作投影可以在备份后按新规则重建。
