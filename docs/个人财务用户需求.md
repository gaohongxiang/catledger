## 1. 一句话目标

我要的是一个真正好用的个人记账工具：把支付宝、微信、银行卡、信用卡、贷款和分期等所有真实账目放进同一本账，尽量少手工录入、不重复计算，并且随时能看清资产、负债、收支和还款情况。

它不应该要求我先学会一套复杂的财务系统，才能完成最基本的记账。

体验原则是：**第一次慢而清楚，第二次快而可改。** 第一次要把账户建对、看懂摘要；之后默认沿用已确认的判断，只把新的、冲突的、说不清的交给我。确认是例外，不是每周例行。

### 用户体验流程

打开网站（电脑）：总览 → 想记账去「记账与明细」或「账单整理」→ 贷款在「贷款与分期」。高级功能在「更多」。

打开网站（手机）：总览、记一笔、下一笔待还。账单整理、复杂对账、新建贷款用电脑。

#### 手记一笔

现金、没凭证、或想马上看见时，在「记账」里记一笔，直接进正式账本。以后账单对上了，只给这笔补证据，不再新增一笔支出；对不上就进待办问我。

#### 待办里通常有什么

| 类型 | 我要做什么 | 不进待办的 |
| --- | --- | --- |
| 新账户 | 改名称/类型后点新建 | 上次已确认的付款方式 |
| 未分类 | 选餐饮/服饰等，或等支付宝账单补上 | 支付宝已经能映射的分类 |
| 冲突 | 看两边依据，选留哪边 | 身份相同且内容一致的重复 |
| 转账/退款说不清 | 确认是转账、退款还是消费 | 还信用卡、充零钱等已能判断的 |
| 分期 | 是否分期、挂哪张卡、几期、原消费记过没有 | 已有合同且信息一致的后续期次 |

## 2. 我的账户和账单来源

需要覆盖：

- 支付宝；
- 微信支付；
- 银行卡和银行账户；
- 信用卡；
- 银行贷款、消费金融、网贷和一般借款；
- 各类分期；
- 现金，以及没有电子账单的少量手工账目。

系统必须分清“钱实际存放在哪个账户”和“通过什么渠道支付”。例如，用支付宝调用信用卡付款，本质上是一笔信用卡支出，同时可能在支付宝账单和信用卡账单中各有一份证据，不能算成两笔消费。

账户既可以由我手工建立，也可以由账单发现后再确认创建。第一次使用不必先去账户页建账户，可以直接导入账单。

无论首次还是平时，解析后都先给出本次发现的付款账户列表，例如“兴业银行信用卡（6106）”“江苏银行信用购”“微信零钱”，分成三类：

- 需要新建：给出可编辑的建议名称和账户类型，我改到满意后再点「新建」；未点新建不得创建正式账户。需要新建时也可以改选已有账户，改选后按「已经存在」处理。
- 已经存在：展示匹配到的正式账户和影响笔数。若上次已经确认过同一付款方式，默认沿用，不必再逐项点「确认使用」；页面用一句话说明「本次沿用 N 个已确认账户」，我可以改，但不改就继续。没有历史映射、账户已删除、币种冲突或匹配有歧义时，必须由我选择或新建。
- 忽略账户：这些账目不是我自己的钱，或我不想记进这本账。整组忽略在「核对账户」点「忽略账户」（例如某本小荷包、别人的卡）。只去掉其中几笔，在「整理交易」每笔上勾选不入账。点过后只保留账单证据，不创建正式账户，不进入正式账本和总览。整组忽略过的付款方式，下次默认继续忽略，我可以改回来改成新建或沿用。
- 银行/信用卡账单已经能看出是哪家银行时，付款方式应写成「光大银行信用卡(2690)」这种「银行名 + 卡种 + 末四位」，再去对账本里已有的卡。不能只显示末四位，也不能拿别的银行同尾号的卡去对。支付宝、微信账单里本来就有完整付款方式名称的，继续用账单原文。
- 忽略空格、全角/半角括号、“尾号”等不影响身份的格式差异；只有唯一且足够可信才算已经存在，不能仅凭“银行卡”这类泛称乱匹配。
- 同一整理任务中相同的付款方式只处理一次。支付宝、微信和银行账单里同一张卡只出现一块，笔数加总；来自哪份账单在明细里看，不在核对账户里摆多块同名。确认、沿用或整组忽略后，对应订单共同使用该决定；若只去掉其中几笔，其余仍按该组账户处理。
- 列表应提供「全部沿用已确认账户」；只对需要新建、忽略账户、和有问题的项逐项操作。

账本里必须分清“钱从哪张卡或哪个余额出去”和“这份账单来自支付宝还是微信”。常用界面只说「付款账户」「支付宝账单」「微信账单」「信用卡账单」，不要使用“来源账户”这类内部词。文件已经能唯一看出是哪一份支付宝/微信账单时，不要再问“这是哪个账号”；只有多账号或看不出来时才问。

第一次从账单新建账户之后，系统应可选地问一句「这些账户现在大概多少钱」，问在核对账户的已沿用卡片上，不必另开一页。账单是流水，不是期初余额；跳过也可以，但总览要标明「余额尚未核对」，不能把从零累加的数字假装成真实净资产。

## 3. 我希望怎样记账

### 3.1 主要方式：批量导入账单

- 支付宝、微信、银行卡、信用卡等有电子账单的交易，不要求平时再逐笔手工录入。
- 每周或月末批量导入账单，由系统完成解析、账户映射、精确去重和跨来源整理。
- 系统应尽量自动处理明确的记录，只把无法确定、互相冲突或确实需要判断的少量项目交给我。

### 3.2 辅助方式：手工“记一笔”

以下情况才需要手工记录：

- 现金消费；
- 没有电子凭证的收支；
- 我希望当下立即看到、暂时还没有账单的交易。

如果之后导入的账单对应到已经手工记录的交易，系统应把账单作为这笔交易的新证据关联上去，不能再新增一笔支出。金额、币种、方向或账户等关键信息不一致时，应让我确认，不能静默覆盖。

### 3.3 最终统计口径

- 只有进入正式账本的交易，才能影响余额、收支和统计。
- 原始账单行是证据，不等于正式交易。
- 待确认、冲突或仅处于整理区的数据，不得提前进入总览。
- 同一经济事件可以有多份来源证据，但正式账本中只能计算一次。
- “进入正式账本”不等于每一笔都要我点一次。时间、金额、性质、账户都能从清晰渠道或已确认规则定下来、又没有冲突的，应自动入账；冲突、对不上的转账/退款、分期、账户说不清、以及和已有手工账对不齐的，才挡住入账。分类说不清不挡住入账，见 3.4 节。
- 第一次导入（或刚新建了一批账户）可以先看摘要再点「确认入账」；之后默认自动入账，并允许事后撤销或改正。

### 3.4 一笔正式交易要定什么

入账、余额、净资产只要求下面四项。缺任何一项，这笔记不能进正式账本，也不能进总览里的钱。

| 入账必须定齐 | 是什么 | 多渠道时用哪边 |
| --- | --- | --- |
| 1. 时间 | 这笔钱实际发生的时间 | 有明确交易时间的账单；只有入账日时要标明依据 |
| 2. 金额和币种 | 多少钱、什么币 | 真实扣款那一侧；两边不一致则进待办 |
| 3. 性质 | 收入、支出，或转账 | 参考收/支；充值、还款、红包、「不计收支」按转账或退款，不能都当消费 |
| 4. 账户 | 钱从哪张卡或哪个余额走；转账还要有对方账户 | 付款方式能对应到卡或余额的那一侧 |

第五项是分类（餐饮、服饰、日用）。它决定「这个月钱花在哪」，**不决定「我现在有多少钱」**：

- 能从清晰渠道映射时，入账就带上分类。用支付宝「交易分类」（餐饮美食、服饰装扮）；**不用**微信「交易类型」（商户消费、扫二维码付款）。微信那列只说明付过钱，不能当分类。
- 说不清时（例如只有微信「商户消费」，又没有我以前确认过的商户规则）：仍然入账，标成未分类，余额、净资产和本月生活消费总额照常计入；总览写「有 N 笔未分类」；只有餐饮/服饰等分类构成不含未分类。未分类进待办让我补，不要猜。
- 同一笔出现在支付宝和微信里，只形成**一笔**正式交易，各字段用更清楚的那份账单。我已经手工定过的分类，不能被后来含糊的账单改掉。确认过的商户或支付宝分类映射，下次默认沿用。

可选、入账不必填：额外标签（如出差）、备注、地点、图片。

## 4. 必须正确的记账规则

- 自己账户之间转账，不是收入也不是支出。
- 银行卡偿还信用卡，是账户间资金转移，不是再次消费。
- 贷款到账会同时增加资产和负债，不是收入。
- 偿还贷款本金会减少资产和负债，不是生活消费；利息和手续费才是借贷成本。
- 退款、撤销应冲回原交易的影响，不应作为普通收入重复统计。
- 调整账户余额与真实消费必须区分开。
- 金额相同或时间接近，不能作为自动合并两笔交易的唯一依据。
- 同一来源有稳定且相同的记录身份时可以精确去重；身份相同但核心内容冲突时必须保留证据并交给我处理。
- 不同币种不能直接混成一个没有解释的总数；缺少汇率时要明确提示。

## 5. 总览需要展示什么

资产、负债和净资产默认统计全部正式账户截至今天的完整状态，不需要我先选择“报表起始日”和“截至日期”。总览中出现日期时，主要用于解释数据截至何时或某个流量指标覆盖哪个时期，不是让我先定义“统计全不全”。金额一键隐藏或显示，隐藏时卡片、图表和明细摘要都不能泄露金额。

### 5.1 打开先看这四件事

首屏只要快速回答：

- 净资产（以及总资产、总负债可作次要数字）；
- 这个月的真实生活消费（可切换今天/本周/本年）；
- 下一笔要还多少、什么时候还（在贷款、分期和已出账信用卡里，取还款日最近的一笔）；
- 一句可信度，例如「本月暂结，招行还没出账」「有 6 笔未分类」或「有 6 笔待处理」，并可以点进去处理。不要把缺口清单和净资产摆成同样大的一块。

若账户余额尚未核对，净资产旁必须标明，不能假装已经对账。

### 5.2 往下再看明细

第一屏之下再展示：

- 可随时使用的资金、各账户余额和更新时间；
- 本月收入、生活消费、偿债本金、借贷利息与费用、流动资金净变化；
- 最近 6、12 或 24 个月的收入、生活消费和实际偿债趋势；
- 各类债务剩余本金、下一还款日、下一期金额和进度；
- 当前月份和趋势中的数字都能下钻到对应正式交易。

### 5.3 覆盖情况和待办

覆盖缺口、待确认、解析失败、身份冲突和疑似重复，作为第二层信息：用一句结论加可点击数量，不要在首屏铺开全部账户覆盖表。点进去再看各账单盖到哪一天、哪些还没进正式统计。

### 5.4 信用卡未出账与月末统计

每张信用卡的账单日和还款日可以不同，但月度收支仍按自然月和实际交易日期统计，不能把消费统一归到信用卡出账月份。信用卡账单周期只用于判断账单覆盖范围、已出账应还和还款日期。

我在月末查看当月统计时，不需要等待所有信用卡出账：

- 已经从支付宝、微信、信用卡未出账明细或其他可靠来源确认的消费，按实际交易日期计入当月；
- 尚未出账且没有其他证据覆盖的信用卡日期区间，明确标记为覆盖缺口，不能假装当月已经完整；
- 月报在覆盖尚未完整时显示“暂结”，同时列出哪些信用卡待出账、各自覆盖到哪一天；
- 后续正式账单导入时，与已有交易关联并补齐遗漏，不重复记账；对应历史月份自动修订并保留变更说明；
- 相关账单覆盖完整、冲突处理完毕后，月报显示“已确认”。

每张信用卡的账单日、实际周期、已出账应还、已识别未出账和未覆盖区间，放在账户或覆盖下钻里看，不挤进总览首屏。常规账单日只是提醒依据，每份账单提供的实际起止日期才是覆盖判断依据；账单日调整时不能改写历史周期。

## 6. 账单导入与整理体验

账单整理是一个任务页，按步骤推进：选账单 → 核对账户（含现在多少钱，可跳过；第三桶是忽略账户）→ 整理交易（多渠道证据先自动合成唯一交易，再对唯一交易确定分类；每笔可勾不入账）→ 其他事项 → 确认入账。上传后，摘要直接说明有效证据数、合并重复数、最终交易数和需要我看的数量；摘要卡片同时是导航：点重复证据看审计对照，点待确认关系进入其他事项，点待补分类看分类列表，不再另放重复的 Tab。原始账单对照按需展开，去重、跨来源、解析版本等技术步骤在后台完成。

- 一次可以同时上传支付宝、微信、银行卡、信用卡等多份账单，组成同一次“账单整理任务”。每个文件、每条原始记录仍分别保存，不能先合并成一个总额而丢失来源。
- 确认入账前，这一次的账单可以随时勾选或拿掉，后解析的文件也加进这一次，不必另开一轮。点确认入账之后，这一次的文件不再改。
- 第一次和平时的具体步骤见第 1 章「用户体验流程」；不必先手工建账户，也不必先配置分类、标签、模板。
- 系统应明确告诉我哪些已自动入账、哪些重复已跳过、哪些冲突、哪些还在待办，以及原因是什么。
- 证据预览必须直接展示账单里的付款方式，不能让我到原始 Excel 里找。
- 各来源对同一件事叫法不同（银行叫「交易说明」，支付宝、微信叫「交易对方」），系统必须把它们统一成一套我的字段：时间、金额、方向、交易对方、商品说明、支付方式、单号、状态、备注。界面上只出现这套统一说法，同时保留各来源原文；来源改版只更新对照规则并重新解析，历史数据不动。
- 同一份文件重复上传、重叠账期重复导入或多来源出现同一笔交易，都不能造成重复统计。
- 高级映射、证据详情和技术信息可以保留，但默认折叠；常用路径使用普通人能懂的说法。

多账单联合整理按不同信息采用不同粒度：

- 账户：先汇总付款方式，新的要我新建，已确认的默认沿用；同一账户只处理一次。
- 交易：每条原始记录按稳定身份核对；同一经济事件只形成一笔正式交易，原始证据全部保留。3.4 节入账四项都定齐且无冲突的自动入账；分类说不清也入账并标未分类。
- 一笔交易要定什么、多渠道用哪边、分类用哪个渠道，以 3.4 节为准。
- 分期：同一分期的多期汇总成一个候选，放进待办，不在账户确认里夹杂一长串合同字段。
- 转账、还款和退款：组成可解释的关系候选；说得清的可以自动处理，说不清的进待办。不能把多笔金额加总后再入账。不能只凭金额相同或时间接近自动合并。
- 跨来源同一笔：银行月结单的交易说明不会正好等于支付宝、微信的交易对方。说明里的「支付宝」「微信」「财付通」表示支付网关，后面可能是商户，也可能只是持卡人或通用说明。已经沿用到同一张卡、金额币种与方向一致时，银行只有日期而渠道有准确时间，可以按同一自然日核对；同日同额出现多笔且两边数量相等时，应收成相同数量的唯一交易，不能因为银行商户含糊就全部漏掉，也不能把多笔压成一笔。数量不等或仍有银行独立交易的可能时才交给我。退款可在同日匹配后允许 48 小时内唯一对照。打开页面只查看已有结果，点「重新分析」才按当前规则重算。最终交易是主列表，原账单对照只作为可展开证据；相互独立、转账、退款或暂缓必须分别显示。

后台处理顺序可以是：解析留证 → 账户（新建或沿用）→ 同来源去重 → 跨来源整理 → 高置信自动入账 → 分期候选 → 分类建议 → 待办。已经确认的历史信息不得被新账单静默覆盖；冲突要展示新旧依据并让我决定。

## 7. 贷款与分期

需要管理：信用卡分期、银行贷款、消费金融或网贷、一般借款等。

每笔贷款或分期需要能够记录并计算：

- 合同本金和实际到账；
- 期数、起止日期和还款方式；
- 利率、每期还款额、一次性费用、每期费用、优惠和减免；
- 总成本、真实年化、逐期本金/利息/费用；
- 已还进度、剩余本金、下一还款日和未来还款计划。

贷款的“计划还款”与账本中的“实际还款”必须分开。计划不能直接代替真实账目；只有实际发生并关联到正式交易后，才能计入已还。

一笔分期只建立一次完整合同和还款计划，不能因为每个月账单里出现“第 1 期”“第 2 期”就重复创建分期。每月账单中的分期行是该计划对应期次的实际证据，应关联到同一份分期合同。

自动识别只能先生成“待确认分期”，不能直接生成正式合同。首次发现尚未管理的分期时，先汇总同一次整理任务中的相关期次，待办里只问这几件事：

- 这是不是分期；
- 挂哪张信用卡、贷款或平台账户；
- 总共几期（知道的话）；
- 原消费记过没有：关联已有消费、补建缺失消费，或暂不确定。

合同本金、每期应还、利息、手续费、还款方式和首次还款日可以留在「待完善」，账单没给的必须保持未知，不能当 0。我可以选择：关联已有合同、补这几项后创建正式合同，或保存为待完善。待完善显示在“贷款与分期”待处理区，不能用未知字段计算真实年化、总成本或完整未来计划。当期真实交易仍可按账单正常入账。

还款方式使用容易理解的选项，并在旁边标注专业名称：

- 每期总额基本相同（等额本息）；
- 每期本金相同、利息逐期减少（等额本金）；
- 每期本金和利息都相同（等本等息）；
- 前期付息、最后归还本金（先息后本）；
- 按账单记录、自定义或暂不确定。

系统可以根据合同或多期账单给出建议，但不能只凭一期金额擅自认定还款方式。确认后，后续账单应按稳定的分期编号、订单号、原消费关系或其他可靠身份自动关联；只有总期数、期次、金额、账户或候选合同冲突时才再次让我处理，不能仅凭金额相同或日期接近关联。

分期的会计口径必须保持一致：原消费只计算一次；每期归还本金不是新的消费；利息和手续费才计入借贷成本；银行卡向信用卡还款仍是账户间转账。如果首次发现分期时还不能确认原消费是否已入账，系统应让我选择“关联已有消费”“补建缺失消费候选”或“暂不确定”，不能静默新增消费。

界面默认先展示剩余本金、下一期应还、总成本和进度等常用信息；专业计算明细可以展开查看，不要一上来就要求填写或理解所有术语。

已有 loan-cost-calculator 项目只作为算法和交互参考，不作为本项目的运行依赖。

我已有一份完整的历史贷款、借贷和分期 JSON 备份。未来需要提供一次性迁移能力，把其中有效记录融合进本系统；这项目前暂缓，不影响先把现有网站和正常记账流程做好。

## 8. 易用性和信息架构

日常最重要的入口应尽量控制为：

1. 总览；
2. 记账与明细；
3. 账单整理；
4. 贷款与分期。

账户、分类、标签、模板、统计分析等能力可以保留，但不应阻挡第一次记账：直接导入账单，从账单发现账户后再新建或沿用。高级功能放在次级导航或“更多”中。

手机（PWA）现在必须能：看总览、记一笔、看下一笔待还。账单整理、复杂对账、新建贷款合同当前以桌面为主，手机给摘要和入口即可。

长期目标：随着自动入账和待办收敛，日常全部流程（包括账单整理的待办处理，本质是几道选择题）都能在手机上完成。Web 是流程打磨期的主力客户端；等新整理流程用真实账单验证稳定后，再评估全功能小程序、Web 是否退役以及部署路线（见第 12 章）。

页面和操作应遵循：

- 第一次慢而清楚，第二次快而可改；
- 先给结论，再给解释；
- 先显示常用操作，再显示高级配置；
- 使用生活化文案，必要的专业术语附带解释；不要在常用界面出现“来源账户”等内部词；
- 空页面要告诉我下一步做什么；
- 错误和冲突要告诉我原因以及如何处理；
- 如果打开网站后仍然不知道“第一步该做什么”，就不能算易用性验收通过。

## 9. 隐私、部署和架构边界

- 保持一个轻量、自托管的应用和一套正式账本，不为了功能堆叠引入微服务或第二套账本。
- 账单和财务数据默认只进入我自己的服务，不上传到外部 AI 或第三方分析平台。
- 原始账单内容、完整账户标识和真实交易详情不得进入普通日志、公开仓库或测试夹具。
- 即使目前主要是我自己使用，也必须保留用户数据隔离。
- 产品架构以我的实际需求、正确性、易用性和长期可维护性为优先，并持续维护必要的安全修复和基础能力。

## 10. 当前优先级

### 10.1 当前必须做好

- 先优化现有网站的使用流程和信息架构；
- 建立准确的统一账本口径；
- 做好批量导入、去重、跨来源整理和人工确认；入账定齐时间、金额、性质、账户；分类说不清可先入账再补；
- 做好清晰、完整、可解释的财务总览；
- 做好贷款与分期的记录、成本和还款管理；
- 保证数据隐私、入账可撤销、数据可备份导出、统计可解释。

### 10.2 当前暂缓

- 历史贷款 JSON 的一次性迁移；
- 微信小程序：有明确前置条件的规划项，独立计划见第 12 章；启动条件满足前暂缓；
- 微信登录、上架和商业化；用云开发（serverless）重写后端明确不做（见 12.5 节）；
- 依赖外部 AI 的全自动分类；
- 与核心记账无关的复杂外部基础设施。

“暂缓”表示以后可以继续讨论，并不等于永久取消。

## 11. 最小可用验收场景

产品至少应通过这些真实场景：

1. 同一笔信用卡消费同时出现在支付宝和信用卡账单中，最终只统计一次。
2. 我先手工记了一笔，后来导入对应账单，最终仍只统计一次，并保留账单证据。
3. 银行卡偿还信用卡，不被算作新的消费。
4. 贷款到账不被算作收入；还本金不被算作消费；利息和费用被正确计入借贷成本。
5. 重复上传同一账单或导入重叠账期，不改变已经正确的统计。
6. 未确认或冲突的记录不会悄悄进入总览。
7. 打开网站先看到净资产、本月生活消费、下一笔待还和一句可信度；余额未核对或月报暂结时必须写明。
8. 新用户无需先手工建账户，也无需先配置分类、标签或模板；直接导入账单，新建本次新账户后即可看到整理摘要。
9. 支付宝或微信账单中的“兴业银行信用卡(6106)”若上次已确认对应“兴业银行信用卡（6106）”，本次默认沿用，只在摘要里说明；没有账户时出现在“需要新建”，我可先改名称和类型再点「新建」。同批次相同付款方式不再询问。若某组账目不是我自己的钱，我在核对账户点「忽略账户」后只留证据、不进账本；整组忽略下次默认沿用，仍可改回。只去掉其中几笔，在整理交易每笔上勾选不入账。
10. 同一笔分期连续出现在多个月账单中，只形成一份分期合同和逐期证据，不重复增加合同、消费或本金。
11. 首次识别分期时，待办只问是否分期、挂哪张卡、总共几期、原消费记过没有；本金利率等可待完善。后续信息一致时自动关联，冲突时说明原因并等待处理。
12. 同时上传支付宝、微信和信用卡账单时，新账户按组新建、已确认账户沿用；清楚的交易自动入账且只统计一次；分类用支付宝等能说清「餐饮/服饰」的渠道，不用微信「商户消费」；哪个渠道都说不清的仍入账为未分类并计入余额和当月消费总额，总览提示未分类笔数，餐饮等分类构成不含这些笔。
13. 月末有信用卡尚未出账时，已入账消费仍按交易日期进入当月，月报明确显示暂结和覆盖缺口；以后导入账单只补证据和遗漏，不重复消费，并自动修订对应月份。
14. 第一次从账单新建账户后，可以跳过「现在多少钱」；跳过后总览标明余额尚未核对，补填对账余额前不把净资产当成已对账结论。
15. 手机能看总览、记一笔和下一笔待还；不必在手机上完成全部账单整理。
16. 一笔消费发生退款或撤销后，冲回原消费的影响，不算新收入，当月消费统计相应减少。
17. 一键隐藏金额后，总览的卡片、图表和明细摘要都看不到金额。

## 12. 微信小程序计划（未来形态）

小程序不是 Web 的补充，而是未来的主客户端：**长期目标是手机完成全部日常流程**。Web 是打磨期的主力客户端，小程序稳定接管后可以退役。

### 12.1 为什么可行

- 体验原则决定了日常交互会收敛成「上传账单 → 三行摘要 → 几道选择题」，选择题天然适合手机；
- 账单文件本来就在手机侧产生（支付宝、微信、手机银行导出到邮箱或聊天），小程序可以直接从微信聊天记录选文件上传；
- 后端已经前后端分离，小程序只是又一个客户端，后端几乎不用改。

### 12.2 启动条件（未满足前不开工）

1. 账单整理新流程已完成，并用真实账单实际使用数月；
2. 日常待办确实收敛为少量选择题，不再依赖大屏对比；
3. 我确认需要微信入口。

### 12.3 方案要点

- 全功能：总览、记一笔、账单整理、待办处理、贷款与分期都能在小程序完成；备份恢复等低频管理操作可保留简易入口或运维方式；
- 技术：Taro 或 uni-app（Vue 3 + TypeScript），复用现有 API 客户端逻辑和类型定义；
- 后端不动：继续用现有 REST API 和同一本账；**不用云开发**（用云函数重写后端这条路排除）。

### 12.4 部署二选一（启动时再决定）

| 路线 | 好处 | 代价 |
| --- | --- | --- |
| A. 备案域名 + 自己的服务器 | 数据完全自己拿着 | 需要备案域名和国内可访问的服务器 |
| B. 微信云托管 + 云 MySQL | 小程序调用免域名免备案，最快能用 | 财务数据托管到腾讯云；SQLite 迁到 MySQL；按量付费 |

只用小程序、Web 退役之后，路线 B 完全不需要备案。数据主权和省事只能选一个，到时候再拍板。

### 12.5 边界

- 云开发（serverless 重写后端）明确排除；
- 上架和商业化不在本计划内，个人使用优先；
- 小程序稳定接管之前，Web 端的所有验收标准照常有效。
