# MINI-1906A 实施计划

> 状态：未开始。必须先完成 MINI-1905/1906 真实微信身份验收，再按顺序执行；未经确认不提前实现贷款、多币种或 AI。

- [ ] 0. 冻结基线与失败证据
  - 记录主线提交、开发云迁移版本、函数版本和体验版版本
  - 为孤儿账户草稿、修正现金负数、撤销残余副作用和聚合多交易局部修正建立失败测试
  - 核对所有现有 Transaction 写入口和余额/统计读取入口
  - _Requirement: R1, R2, R3, R4, R8_

- [ ] 1. 收口账户草稿物化
  - 从服务端冻结事件端点、映射草稿和聚合分配计算可达草稿集合
  - posting 只物化可达草稿，修改决定和放弃批次时 supersede 不可达草稿
  - 覆盖同请求重放、并发入账和既有历史草稿兼容
  - _Requirement: R2, R8_

- [ ] 2. 收口事件修正、整批撤销和聚合维护
  - `economicEvents.correct` 复用现金余额安全门禁和完整事件锁定
  - 实现撤销后的账户停用、映射与分类别名撤回策略
  - 聚合还款按完整交易集合原子重建；未支持的多交易事件只允许整批撤销
  - 统一 impact 与执行的规则版本、摘要、CAS 和幂等回执
  - _Requirement: R3, R4, R8_

- [ ] 3. 建立不可变分录 schema 与领域投影
  - 新增 LedgerAccount、JournalEntry、Posting 和迁移进度表
  - 冻结内部资产、负债、权益、收入、支出和清算科目规则
  - 实现每种现有 Transaction 的确定性借贷投影及守恒测试
  - 保证 uid 外键、唯一约束、正金额、状态转换和 posted 不可变
  - _Requirement: R1, R5, R6, R8_

- [ ] 4. 接入统一正式写入适配器
  - 手工收入、支出、转账、退款、余额校正和 FinanceUpdate posting 共用分录写入边界
  - Transaction、Entry、Posting、事件关系、映射提升和动作回执在同一事务完成
  - 增加旁路门禁测试，任何未生成守恒分录的正式交易不得提交
  - _Requirement: R5, R6, R8_

- [ ] 5. 实现历史回填与断点恢复
  - 按用户分页回填既有有效 Transaction，使用稳定幂等键和规则版本
  - 把无法确定投影的旧数据隔离为只读异常，不猜测账户、分类或币种
  - 覆盖中断重跑、并发回填、旧软删除交易和跨用户隔离
  - _Requirement: R6, R7, R8_

- [ ] 6. 建立影子比对和读取切换门禁
  - 对账户余额、月度收支、每日统计和分类排行运行旧新双口径比对
  - 只记录脱敏差异摘要，并提供按用户范围重算与阻断切换能力
  - 全量和增量零差异后通过服务端版本开关切到 Posting 读取
  - 保留一个稳定发布周期的旧读取回退开关，再关闭旧权威路径
  - _Requirement: R6, R7, R8_

- [ ] 7. 接入小程序修正与撤销闭环
  - 为符合条件的导入交易提供影响预览、确认、冲突和完成态
  - 多交易事件隐藏单笔编辑，提供聚合重建或整批撤销路径
  - 完成后统一刷新账户、明细、统计和导入记录
  - 补齐模型、公共契约、云调用策略和页面回归测试
  - _Requirement: R1, R3, R4, R9_

- [ ] 8. 完成全量验收与发布准备
  - 运行根目录、两支云函数单元测试和 MySQL 8 全量集成测试
  - 覆盖迁移重跑、事务回滚、并发、幂等、跨用户隔离和日志隐私
  - 使用脱敏多账单和真实微信身份走通导入、修正、撤销及统计刷新
  - 执行生产依赖审计、`git diff --check` 和 CloudBase 代码审查
  - 同步架构设计、业务规则、入账逻辑、现行说明和实施规划
  - 取得单独授权后再更新开发云、上传体验版、合入并推送主线
  - _Requirement: R1-R9_

## 执行门禁

1. 用户确认 requirements 后才冻结 design；确认 design 后才开始任务 0。
2. 任务 0～2 全部通过后才能新增分录 schema。
3. 任务 3～5 期间用户读取仍以 Transaction 为权威。
4. 未达到全量与增量零差异不得执行任务 6 的读取切换。
5. 新读取稳定前不删除兼容代码、不开始贷款、多币种和期间结账。
6. 数据模型、迁移、公共 API、幂等和冲销规则由单一主负责人串行冻结。
