# MINI-1906A 账本完整性与可逆入账内核需求

> 状态：未开始
>
> 依赖：MINI-1905/1906 完成真实微信身份验收并形成可回归基线
>
> 目标：在不增加普通用户理解成本的前提下，消除当前导入后维护缺口，并把余额权威升级为可审计、可逆、可迁移的分录内核。

## 1. 问题与目标

当前系统已经形成 `ImportFile / ImportBatch → FinanceUpdate → EconomicEvent → Transaction → Account` 的统一主链路，正式交易是余额和统计的唯一权威。下一阶段需要解决两类问题：

1. 收口当前写屏障、修正、撤销和聚合还款的边界，保证任何操作都不会留下孤儿账户、残余映射或不可解释余额；
2. 在 `Transaction` 下增加用户不可见的不可变分录内核，使贷款拆分、对账、多币种和期间审计不再依赖继续扩张交易类型与条件分支。

用户继续使用“收入、支出、转账、退款、余额校正”等语言。借方、贷方、内部科目和冲销分录只属于内部实现与审计，不进入首发主界面。

## 2. 用户故事

1. 作为记账用户，我希望导入后创建的账户都确实被正式交易使用，不出现空账户或重复账户。
2. 作为记账用户，我希望修正或撤销一笔已入账记录后，账户余额、收支统计和原始证据仍然一致且可解释。
3. 作为记账用户，我希望一笔聚合还款即使拆成多笔正式资金流，也能整体撤销和重新整理，不产生部分成功。
4. 作为维护者，我希望每一笔正式业务交易都能追溯到一组守恒分录，并可从原始证据追到最终余额影响。
5. 作为维护者，我希望历史数据能在可验证、可回退的阶段中迁移，切换前后余额和统计为零差异。

## 3. 功能需求与验收标准

### R1. 保持现有产品语义

- 当用户查看、创建或导入交易时，系统应继续使用收入、支出、转账、退款和余额校正等现有业务语义。
- 当内部启用分录内核时，小程序应保持现有 `Transaction` 标识、来源追溯和主要交互，不要求普通用户理解会计借贷。
- 当新内核未完成切换时，系统不得用未验证的分录结果替换正式余额或统计。

### R2. 账户草稿可达性与物化

- 当 FinanceUpdate 入账时，系统只能物化仍被服务端冻结事件端点或有效映射草稿引用的账户草稿。
- 当用户把新账户决定改为既有账户、忽略引用或放弃批次时，系统应使不再可达的草稿失效，且不得创建孤儿正式账户。
- 当同一请求重试或发生并发提交时，数据库唯一约束和幂等动作应保证同一草稿最多物化为一个正式账户。

### R3. 已入账修正与撤销

- 当用户修正已入账事件时，系统应先计算影响并再次执行账户余额安全检查，再以冲销旧分录和创建新分录的方式完成修正。
- 当用户撤销 FinanceUpdate 时，系统应原子撤销该批次创建的全部余额影响，并按冻结策略处理账户、账户映射和分类别名副作用。
- 当正式交易已被批次外操作修改、撤销或引用时，系统应拒绝静默覆盖并返回可理解的冲突结果。
- 当同一修正或撤销请求重放时，系统应返回首次结果，不得重复冲销。

### R4. 聚合事件原子维护

- 当一个 EconomicEvent 对应多笔正式交易时，修正、撤销和重建应覆盖完整关联集合，禁止只修改其中一笔。
- 当聚合还款重新分配时，各分配金额之和应等于来源付款金额，且所有分录在同一事务中成功或回滚。
- 当系统无法安全重建聚合事件时，应要求整批撤销后重新整理，不得提供伪装成功的局部编辑。

### R5. 不可变复式分录

- 当系统确认一笔正式 Transaction 时，应在同一数据库事务内创建一个或多个 JournalEntry 及其 Posting。
- 当 JournalEntry 进入 posted 状态时，同一币种的借方合计应严格等于贷方合计，且金额全部使用整数最小货币单位。
- 当已 posted 的业务需要改变时，系统应创建反向分录和替代分录，不得原地修改已生效 Posting。
- 当任何正式写入口没有生成有效分录时，系统应拒绝提交；导入、手工记账、退款、余额校正均不得绕过该门禁。

### R6. 余额、统计与追溯权威

- 当分录读取切换完成后，Account 余额、收支、净值和分类统计应只从 posted Posting 派生。
- 当用户查看一笔导入交易时，系统应能沿 `ImportRow / Evidence → EconomicEvent → Transaction → JournalEntry → Posting` 追溯到每个账户影响。
- 当一条业务交易包含多个经济组成项时，系统应保留 Transaction 的整体业务语义，并允许分录按本金、利息、费用或内部清算项拆分。

### R7. 历史迁移与兼容切换

- 当执行历史回填时，系统应按用户范围和稳定幂等键为每笔有效 Transaction 生成确定性分录，重复执行不得重复创建。
- 当处于影子比对阶段时，系统应同时计算旧交易口径和新分录口径，并记录脱敏差异摘要，不改变用户读取结果。
- 当任一用户、账户、月份或分类存在非零差异时，系统不得切换该范围的读取权威。
- 当全量门禁通过后，系统应先切换读取、再关闭旧直写入口；回退只允许切回旧读取，不删除已生成的审计分录。

### R8. 安全、隔离、幂等与可观测性

- 当读写任何新增表时，查询、外键、唯一约束和幂等键都应包含可信服务端 `uid`。
- 当任一步骤失败时，业务交易、分录、余额影响、映射提升和动作回执应全部回滚。
- 当记录迁移或差异日志时，系统不得输出原始账单字段、完整账户标识、数据库凭据或用户交易明细。
- 当云函数处理超时或响应不确定时，客户端应使用同一幂等键安全恢复，不自动生成新的业务请求。

### R9. 用户侧维护闭环

- 当导入批次已入账且满足维护条件时，小程序应提供影响预览、确认和结果页面，而不是要求直接操作导入原始行。
- 当事件包含多笔交易或存在外部修改冲突时，小程序应展示为什么不能直接编辑，并提供整批撤销或返回账本的安全路径。
- 当操作完成时，账户、明细、统计和导入记录应在同一刷新周期内展示一致结果。

## 4. 非目标

本阶段不实现：

- 面向用户的会计科目表、借贷录入界面或企业财务报表；
- 多币种换算、汇兑损益和证券/房产估值；
- 银行自动联网同步、开放银行接口或支付执行；
- 完整贷款产品、未来付款计划和情景测算；
- AccountIdentity 主数据合并、换卡有效期和对账差异工作台。

上述能力在本阶段只保留明确扩展接口，分别进入后续独立规格。

## 5. 完成门禁

只有同时满足以下条件，MINI-1906A 才能标记完成：

1. 已知账户草稿、修正、撤销和聚合事件缺口均有失败测试及修复证据；
2. 所有正式写入口均生成守恒分录，无法绕过；
3. 历史全量回填可重入，旧口径与新口径余额、收支和分类统计零差异；
4. MySQL 事务回滚、并发、跨用户隔离、幂等和冲销关系测试通过；
5. 真实微信身份完成导入、修正、撤销及统计刷新走查；
6. 现行说明、架构设计、实施规划和迁移清单同步；
7. CloudBase 代码审查、生产依赖审计与发布前检查无未解释高风险项。
