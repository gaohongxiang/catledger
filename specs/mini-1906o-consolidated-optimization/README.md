## 1. 优化目标与约束

优先级依次为：账务正确性与用户隔离、失败可恢复、用户可操作时间、维护复杂度与运行成本。这里的“最优”指在现有产品范围和可验证负载下作出有证据的取舍，不指无条件采用最多的基础设施。

继续使用微信原生小程序、catledger-api/catledger-import 两支事件云函数与 MySQL。暂不引入微服务、常驻服务器、第二套正式账本、通用事件溯源框架或客户端权威余额。服务端身份、整数分金额、事务、幂等、版本冲突和账本快照不能为了速度削弱。

目标结构：

```text
小程序页面
  ├─ 本地编辑草稿：金额、日期、备注先可填写
  ├─ 轻量目录：账户/分类元数据，不含余额，短期会话缓存
  ├─ 财务读模型：余额、明细、统计，独立失效与快照
  └─ 显式提交：服务端校验、事务、幂等、版本检查

导入来源证据 → 身份与关系判断 → 待核对问题 → 用户确认
                                          ↓
                               整批原子写入正式账本
```

## 2. 现有评审的事实边界

基线的历史 GitHub CI 记录为 585 项通过；这不是本候选的测试结果，更不代表真实账单准确率或真机端到端验收。本轮环境没有微信开发者工具、真机和生产 MySQL；不能报告真实首帧耗时、云函数冷启动占比、查询扫描量或生产权限已验证。

已读代码能确认：记账表单等待账户和分类后才显示；accounts.list 会汇总交易计算余额；bootstrap 会执行初始化事务；前台切换会失效旧的三类缓存；个人页存在串行初始化/账户读取；历史月份统计可能额外读取首页；导入恢复存在分组刷新和全量派生视图计算。实际耗时占比必须由埋点或性能面板证明。

跨来源桥接合并在此前分组函数隔离检查中有反例；原支出后移日期缺少反向退款时间校验属于代码路径发现。两项均需完整数据库链路回归，不能据此宣称用户真实账本已出现损失。

## 4. O1 设计与反例集

### 4.1 跨来源桥接合并

反例：同来源两笔不同交易身份 A/B，与另一来源 C 共享商户订单号、金额和时间窗口，不能因为 A-C、B-C 分别匹配就默认三者是一笔。

设计要求：先确定来源身份，再校验整个候选分组，而非依赖两两连接或输入顺序；商户订单号的命名空间及一对多付款关系不能默认全球唯一。出现多个不同稳定身份时保留独立记录和全部证据，转为一次有解释的人工核对；只拒绝合并不应导致证据丢失。已有待确认计划需版本升级与显式复核，不能仅修新解析路径，也不能静默丢掉旧人工选择。

回归必须覆盖：A/B 独立；加入 C 不少记；合法多来源同笔仍只计一次；同订单多次付款/退款；来源身份冲突；不同输入顺序结果一致；重复上传及重叠账单；已提交身份并发裁决；人工选择和服务端最终 posting 不能绕过约束。

### 4.2 退款关系双向不变量

新增或修改退款、修改原支出、导入更正和后补退款关联，都必须保持：原消费有效且属于当前用户；退款时间不早于消费；累计退款不超过可退金额；分类和统计口径一致；不会二次增加到账余额。

“9月1日消费、9月3日退款、再把消费改成9月5日”必须被拒绝或通过明确的成组修正流程处理。使用同一事务和统一锁顺序，覆盖并发新增退款与原消费修改。不同部署函数不能通过跨目录 require 破坏独立部署，应先冻结共同规则，再在统一写入适配器演进中收敛执行路径。

## 5. O2 已实现的增量契约

### 5.1 服务端目录

新增 `catalog.get`，输入 `{}`，经现有可信微信身份解析，返回：

- `uid`：用于显示的当前用户 ID，不作为客户端写入身份；
- `accounts`：accountId/type/nature/name/currency/version/archived；不含余额；
- `categories`：当前活动分类的 id/kind/systemKey/name/sortOrder/version。

目录在一个只读一致性事务中查询账户与分类，不读取交易表、不计算余额、不创建默认分类。无需 schema 迁移。所有正式写入继续使用现有服务端校验；目录新鲜不代表账户仍必然可用。

### 5.2 缓存

复用现有 read-cache 的单飞、写屏障、版本失效和会话隔离。目录使用 accountDirectory/categoryDirectory 标签和五分钟上限；不写持久化本地账务缓存。五分钟是可调整的工程默认值，不是实测最优参数。

普通交易写入只失效财务缓存，不使目录失效；账户创建/更名/停用及分类生命周期使目录失效。导入提交、撤销及更正可能改变账户结构，保守失效目录。失败写入同样触发所需失效。peek 不得在关联写入进行中返回旧目录。回前台仍刷新原财务缓存，目录在有效期内可以复用；退出会话清空全部缓存。

### 5.3 页面

记一笔在目录返回前显示可填写金额、日期和备注的草稿；选择器与正式提交在依赖未满足时禁用。目录返回不能覆盖已输入内容或把收支类型改回默认值。目录重排按 ID 保留选择；原账户/分类消失时保持待选择，不自动换成其他项。无账户时显式进入创建页并保留当前草稿。

中央记账菜单只在已有登录许可时预取目录，预取失败不阻止导航。交易详情先显示已取得的交易，分类编辑权限后开放；目录刷新不覆盖未保存分类选择。

明细并行读取目录与交易，目录失败不阻止成功的列表展示；个人和账本结构摘要不再为数量计算余额。普通新增不预取退款候选，切到退款才读取。

保存/删除等待服务端成功后立即返回，不再额外延迟350ms。当前页面内未变更请求的失败重试沿用幂等键；旧会话或已卸载页面的晚到响应不能回填状态或触发导航。此处不承诺跨进程手动记账恢复；响应不确定后修改表单、进程退出和离开页面的统一恢复协议仍须在后续独立收口。

## 6. 逐页后续优化与性能证据

| 页面 | 本候选 | 后续检查 |
| --- | --- | --- |
| 首页 | 保留现有聚合查询和财务快照 | 分段 SQL、冷热函数耗时、首屏数据量；必要时可重建汇总读模型 |
| 明细 | 用目录替代初始化/余额读取 | 快速重复搜索最后意图不丢；分页增量下发；旧条件结果不冒充新条件 |
| 记一笔/编辑/详情 | 即时草稿、目录复用、按需退款、即时成功返回 | 真机键盘、焦点、页面返回与目录失效；手动写入跨进程恢复 |
| 我的/账本 | 轻量目录一次读取并共享 | 身份失败与局部同步失败文案；确认账本结构页的保留范围 |
| 账户/分类 | 沿用当前实现 | 服务端返回实体后局部更新；目录版本共享；拖拽帧率与回滚 |
| 统计 | 沿用当前实现 | 冻结 trendEndMonth 或独立趋势契约；不为历史月份再读完整首页 |
| 主题 | 无业务云请求，不盲目增加缓存 | 真机主题应用、主包/分包成本 |
| 导入 | 本候选不改业务整理和 posting | 见 O4；按行数、文件数、问题数测量 |

埋点只记录页面/动作名、耗时、缓存命中、请求次数、返回字节数、视图版本及非敏感错误码；不得记录金额、交易原文、完整账户、OpenID、请求正文或数据库参数。分别量化点击反馈、可输入时间、关键数据可见时间和同步完成时间。

真实设备验收建议首轮目标：已登录打开记一笔可输入 P95≤300ms；目录有效时无必要前置网络请求；普通连续记账不重新计算账户目录。该目标尚未实测，不得写成已经达标。大批次需覆盖普通规模、数千行及接近允许上限，记录事务持锁、SQL次数、内存峰值、重试最终结果和 setData 大小。

## 7. 发布、测试与回滚

本地候选使用 Node22 的定向隔离测试；测试包含真实页面方法、缓存/请求模块及 SQL 形状检查，传输、微信渲染及数据库部分用桩替代。它不是完整 MySQL/真机测试。完整仓库必须继续执行 `npm run check`、`npm run test:db` 和生产依赖审计，并检查新动作的最小权限运行。

发布顺序：先部署兼容旧客户端的 API（新增 catalog.get），验证旧/新客户端接口，再上传小程序。新客户端依赖该动作，不能先上传客户端。无需迁移、无需改变 import 函数或已有账务数据。回滚先回退客户端，待新客户端不再依赖后再考虑移除 API；新增只读动作可保留，不需要删除数据。

真机最少覆盖：新用户首次登录、已有用户冷启动、首页进入记账、直接进入、连续记账、短暂后台、目录过期、其他页面修改目录、慢网、目录失败、零账户、退款、导入详情、保存响应丢失、退出换身份、页面卸载、保存成功返回。绝不能通过减少验证范围把待验收标成已完成。
