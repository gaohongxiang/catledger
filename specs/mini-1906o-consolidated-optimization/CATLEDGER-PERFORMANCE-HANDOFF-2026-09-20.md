## 2. 目标、事实与禁止扩张的范围

目标是减少用户等待：已经访问过的页面可快速恢复；后台返回但账本未变化时不执行重查询；写后不清空整个页面；翻页不重复计算汇总。最优方案必须由当前版本的测量证明，不能把静态审查写成压测结论。

以下为本次读取审查基线确认的行为；不是旧导入计划尚未实施的清单：[E7]

| 代码入口 | 当前行为 | 本轮方向 |
| --- | --- | --- |
| `miniprogram/services/read-cache.js` | 会话内 Map，默认 48 项；失效删除；有请求合并、会话保护及写屏障 | 保留保护，分离快照可读与数据新鲜度 |

## 4. 阶段 R0：测量与契约冻结

### 实施内容

客户端在请求与页面加载入口记录：页面、动作、缓存来源（内存／持久化／网络）、缓存命中、请求尝试次数、端到端请求时间、响应字节数及 setData 回调时间。setData 回调是数据更新代理指标，不冒充屏幕真正绘制完成；可见帧与交互等待用开发者工具／真机记录补足。

服务端拆分连接获取、身份查询、业务 SQL、映射与响应序列化成本；用 SQL 指纹和调用次数定位热点。现有 handler 总耗时不能独自衡量传输或函数模块初始化。任何日志不得记录原始账单、SQL 参数、金额、真实账号和完整响应。

优先复用仓库现有 `scripts/performance-observer.js`、`scripts/benchmark-import.js`、`scripts/benchmark-performance-matrix.js`、`scripts/benchmark-complex-import.js` 和隔离数据库／权限工具；读取页缺少的指标才补充，不重新实现既有压测框架。在隔离数据库生成固定种子的合成数据：建议 0、1,000、10,000、50,000 笔，包含多账户、退款、转账、已删除交易、贷款与导入关联。按冷启动、同会话切页、短暂后台返回、写后返回、第二页以后、弱网失败分别测量。记录设备、网络、冷热状态和样本量；不足以支撑 p95 的小样本不宣称稳定分位数。

## 5. 阶段 R1：先实现同会话快照与新鲜度分离

### 设计

保留现有请求合并、会话世代、写屏障和迟到响应保护。把内部逻辑分成“可展示快照”和“已确认新鲜数据”；失效只标脏，不把现有画面一律清空。身份退出和用户主动清缓存属于清除，不是普通标脏；本版不为缓存优化新建账号注销业务。

不直接改变现有 `peek()`／`isFresh()` 的语义而不检查消费者。可以新增只供展示的快照读取入口，正式网络 read 仍遵守写屏障。旧值必须标注更新中、更新时间或刷新失败；编辑选择、余额校验和正式入账不能依赖陈旧快照裁决。

普通 onShow 不应无条件 force 请求。贷款页等已有 force 路径只能在相关写失效和跨前台校验覆盖后逐个替换，不能全局删 force。

### 测试

同参数并发只发一次请求；写读交错不回填旧值；失败不清空已有视图；退出或换会话后的迟到响应不能更新页面；筛选条件变化不复用其他查询画面；普通快照读取不绕过现有幂等与会话门禁。

## 6. 阶段 R2：版本校验与受控持久化

### 6.1 版本覆盖审计是启用门槛

已有 `data_revision` 不等于所有路径都已具备正确同步语义。先列出 API 和 import 两支函数的相关写入口，包括创建／修改／删除、分类、退款关联、余额校正、导入入账／撤销／更正、贷款与还款计划、资料变更、初始化和维护修复。

逐项确认：影响缓存的成功变更与版本递增同事务提交；回滚不递增；幂等重放不把原请求当新变更。版本按十进制字符串传输，不转成可能失真的 JavaScript Number。无法覆盖的写路径先保持保守刷新。

请求可附带 `knownRevision`，但不能接受客户端 uid 作为身份。服务端从可信身份解析用户，并在同一个只读一致性快照中读取版本和页面数据。版本未变可返回显式 `unchanged`；消费者必须同时持有匹配环境、用户、查询参数、结构版本的完整快照，否则重新读取。版本标记不能贴到另一份快照的数据上。

前台恢复合并一次校验，不给每个页面额外串联“查版本→再查数据”。可以将版本检查复用到已有身份／业务响应；无变化不做昂贵聚合，有变化先刷新可见页面，其他页面标脏后按需读。当前协议不匹配时明确报错／保持只读历史视图，不能把未知响应误认为未变化，也不能偷偷请求旧接口；任何禁用缓存后的网络读取仍使用同一当前协议。

全局版本只回答“是否变化”，不是变更日志；本轮不假装实现逐笔增量同步。第一版允许全局版本引起保守重取，再用测量判断是否值得拆域。

### 6.2 持久化快照

先保存首页、账户／分类目录、最近访问的统计结果及有界流水页，不保存全量历史或导入原始证据。键至少包括环境、已确认用户、结构版本、动作和规范化查询条件。

建议快照信封：

```js
{
  schemaVersion: 1,
  revision: '123',
  fetchedAt: 0,
  data: {}
}
```

这只是字段示意，不是可直接接线的最终协议。不要原样 JSON 序列化 Infinity、内存 Map、在途 Promise 或会话 token。恢复到新会话后重新分配本地 token，并标记需要校验；本地 token 不代表服务端分页版本。

异步合并写入；设置条目数及总字节上限，超限淘汰可再生快照。存储失败、损坏、旧 schema、空间不足均退回网络，不影响正式记账。异步磁盘写入也需检查会话和写入世代，防止旧响应覆盖新快照。

冷启动确认当前身份前不展示缓存财务数据，也不凭本机旧 UID 自动登录。确认同一身份后可先展示历史快照再校验，但必须区分历史与当前已确认值。退出和用户主动缓存清理按明确的数据生命周期清除财务快照；在途原请求另按现有恢复协议隔离处理，不被普通缓存淘汰误删。

### 6.3 分页一致性

分页缓存绑定完整查询条件和服务端版本；基页过期、版本变化或筛选变化后不追加旧游标的结果。检查本地恢复与现有 `_listCacheToken`／baseToken 的关系。允许重新读取首屏，但不得跨快照静默拼接导致缺条、重条。

### 测试

覆盖两个用户同设备、两个云环境、重启、退出／主动清缓存、损坏／超额缓存、版本前进、协议不匹配、缓存关闭后的同协议读取、写入中读、旧异步落盘、跨设备变化、跨月及换筛选条件、旧游标、旧 schema。磁盘快照无论是否持有 UID，都不能参与服务器鉴权。

## 7. 阶段 R3：低风险减少重复工作

### 翻页汇总

在当前单一流水协议中明确定义 summary 的请求／返回规则，并同步服务端、共享契约、客户端和测试：首屏需要 summary，后续翻页可省略；客户端处理字段缺席，保留属于当前查询／版本的汇总，版本变更时重取首屏。不要为此维护新旧两个实现；具体字段由 R0 冻结。保留既有汇总口径，不暗中把按月汇总改为按搜索结果汇总。

### 列表渲染

使用小程序支持的数组路径 setData 追加新增项，不每次传完整 concat 数组；同时检查选择态、批量删除、排序、返回页面和滚动位置。长列表是否需要窗口化，由真机数据再决定，不先引入新列表框架。

### 写后更新

只使用服务端确认成功的结果更新当前匹配查询的实体。金额汇总、贷款状态或跨多个实体关系不能由客户端猜算；结果不足时标脏并后台重读。跨版本局部更新不强行复用，必要时整页重取。提交成功后刷新失败显示“已保存，页面待更新”，不得重新生成 requestId 再提交。

### 验收

从第二页起不再调用月度汇总 SQL；每次翻页的数据桥接量以新增页为主。写成功后已有页面内容不消失；超时核实／重放不重复记账。

## 8. 阶段 R4：只处理被证据确认的服务端热点

已有数据可安全复用时，评估精简老用户 bootstrap 路径；但身份有效性、状态检查及必要初始化修复不能省略，不能无条件改成免事务查询。

统计可考虑合并重复聚合或复用同一快照的趋势。不要把同一连接上的一致性读取简单换成多个连接 Promise.all，造成一屏数据来自不同提交状态。索引必须以实际已部署结构、执行计划和合成／授权只读负载证明，不盲加。

余额汇总确实占主要成本后，才另立小设计引入可重建投影。所有增删改、转账、退款、导入与撤销、贷款相关写入必须同事务维护派生余额；提供回填／重建、对账、灰度读取与回退原查询。未覆盖写入口或对账不一致时不切换权威读取。新增表和迁移单独审查；本轮计划不授权执行真实云数据库迁移。

SQLite 不进入本轮依赖。只有在另行明确“大规模离线查询和本地复杂检索”需求后，才评估小程序宿主适配、同步协议、存储治理和真实性能，不用引擎替换掩盖请求／计算／渲染问题。
