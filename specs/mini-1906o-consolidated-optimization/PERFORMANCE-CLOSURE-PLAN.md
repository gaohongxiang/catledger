## 3. 架构边界

保持原生小程序、catledger-api/catledger-import 两支事件函数、MySQL正式账本，不为性能收口新增微服务或重写不可变分录底座。

目标数据流：

```text
页面本地输入/待同步决定
    ↓ 有界命令（requestId + 预期版本 + 显式选择）
服务端版本和账务校验 → 整批原子写入 + 同事务紧凑回执 → commit
    ↓ 回执仅说明该次操作结果，不组装整个页面
摘要/游标分页/单条证据读取 → 有限客户端实体缓存 → 当前步骤/当前页展示
```

不可退让：服务端可信用户隔离、整数分金额、整批原子入账、幂等、并发版本与唯一约束、退款/组合付款/现金保护、证据守恒及旧计划升级。缓存和分页不是新账本。不同云函数不得跨部署目录 require。

可预先完成的是确定性计算，不是把最终校验移出事务：提交时必须重新检查批次、规则、身份、账户、分类、退款和余额等相关版本与当前状态。不得以取消锁、跳过校验、INSERT IGNORE、禁用外键、截断证据或多次提交正式账本换速度。

## 5. PERF-0 / PERF-1：契约、小回执、摘要与服务端分页

### 5.1 先冻结契约，再修改消费者

在共享契约与实施规划冻结具体字段/版本。建议新增 `financeUpdates.summary`、`economicEvents.list`，并为现有 `reviewIssues.list`、`economicEvents.evidence` 增加版本化游标能力；已有同义能力则扩展而非重复造接口。写动作采用明确的 `resultMode: 'receipt'` 或等价协议版本，不能悄悄改变旧返回结构。

冻结后记录：请求字段、响应字段、错误码、版本来源、游标作用域、最大条数/字节、幂等重放语义、旧/新客户端组合、部署和回滚顺序。不要让每个页面自定义一套协议。

### 5.2 命令只返回该次操作的事实

覆盖 prepare/organize、账户归属、核对、post、undo、correction 及幂等重放中所有仍返回完整视图的入口。回执包含操作/回执标识、updateId、应用版本、操作结果状态、必要计数和失效范围；可附有界的变化ID或变化实体，超过预算改为分页失效标记，不夹带整个batch。

回执必须与正式写入在同一事务中保存；同一请求重放应返回同一操作结果，不能因之后又改了账本而把重放伪装成另一次操作。现有精简回执/引用化机制优先演进，先检查 import-transaction 的持久化及重放分支，不能只改 post 的正常返回。

提交成功后读取明细失败，页面应显示“已入账，明细待刷新”；不能称入账失败或自动生成新requestId再入一遍。命令响应丢失时先按原幂等请求/回执确认结果。

### 5.3 摘要与分页必须在服务端完成

摘要只返回批次状态、权威数量/金额摘要、就绪/阻塞情况、来源概要、协议和视图版本。coverage保留服务端完整校验，但公开读取只暴露所需汇总，逐行归宿另分页查询。不能为得到一页或一个计数再构造完整getUpdateView。

事件页、问题页、问题成员页、证据页分别有界；事件嵌套的全部成员、完整证据、支付分配等也不能绕过上限。单项原文过大应独立分段/授权读取，完整证据留存且可达，不静默截掉业务内容。

游标复用既有可信作用域设计：绑定服务端用户、updateId、视图/计划版本、规范化筛选条件、稳定排序及末项键，并防篡改。优先键集分页，不使用大offset。批次或筛选版本改变时拒绝旧游标并重读，不拼接不同快照；每页返回版本，跨用户/批次/筛选的游标不可用。

“全选某个问题组”必须指向服务端冻结的成员集合与版本，不是当前可见40条，也不要把几万ID塞进一个请求。选择全部、部分选择、排除项及成员变化的语义必须明确且有界；未解决的隐藏页成员仍参与入账门禁。

### 5.4 不用兼容性重新引入超大响应

新版客户端使用新版读取能力；旧协议如仍返回全集，只在已验证的小规模内兼容，对超预算返回明确需升级/使用分页的错误，不截断结果。大数据不经Base64压缩塞回同一个响应，也不先下载全部分页再显示首屏。旧目录接口降级只用于读取兼容，不允许绕过账务规则。

主要入口：`finance-update-repository.js` 的 getUpdateView/selectEvents/selectIssues/listOptions；`finance-update-core.js`、`review-issue-service.js`、`finance-update-posting.js`、`finance-update-maintenance.js`、`import-transaction.js`；`shared/catledger-import.json`；小程序导入服务和草稿会话。

## 6. PERF-2：集合化、批量SQL与计算热点

按动作/SQL指纹记录执行次数、耗时、返回行数和阶段，使用隔离库 EXPLAIN ANALYZE/执行计划确认扫描来源。参数、金额、原始账单和完整账户标识不得进日志。

优先处理已测热点：分类问题重复存在性检查/生成/收口、每事件 eventContext、transactionLinks、历史复用检查、成员查询，以及大JSON字段参与GROUP BY的完整视图查询。

- 同一批次需要的关系、链接、已存在分类问题、有效目录与身份，批量读取到有界Map/集合；重复判定和退款关系仍按完整领域语义处理。
- evidence先按事件预聚合数量再连接必要字段，问题成员分页或批量读；不对完整JSON/原文字段做无必要分组。
- 合成交易、关系链接、问题及成员采用参数化多行INSERT/INSERT SELECT或有界批量UPDATE；按外键依赖顺序执行。先生成稳定关联ID，匹配全部预期版本并核对受影响数量，任一冲突整批回滚。
- 批量受占位符数量、max_allowed_packet、字节和内存预算共同约束，不能生成无限IN子句；批内多条SQL仍属于同一个事务，不是分批提交正式账本。
- 金额/退款按原消费分组累计，锁定最终对象后校验总额。多来源复用、组合支付、聚合还款不能退化成普通单笔快路径。
- 不在单连接上用无界Promise.all制造伪并行；不为提速放大连接池到压垮数据库。

prepareUpdate另行测CPU、堆内存、GC、序列化和各纯函数调用次数。通过预建索引、时间窗口和增量失效减少重复全表filter/find、候选两两比较和深拷贝；若算法必须输出大量真实歧义，应显式建模并分页，不能截断候选或跳过来源冲突以取得漂亮性能。

索引只在执行计划证实需要后新增；使用下一编号、forward-only、可重入迁移，不改历史迁移checksum。核对读收益与写放大，禁止默认给每个字段加索引。

## 7. PERF-3：缩短关键事务，不削弱原子性

当前用户锁范围先保留。优先消除锁内全量展示读取、每事件重复查询及不必要计算，不直接通过删除用户锁改变并发语义。

事务前：可在明确版本快照上构建确定性计划和有界写入集；若计划变更则重算，不以客户端ready作为依据。

事务内：按既有统一顺序锁用户/批次及相关账户、分类、身份、原消费；采用适当当前读重新检查批次版本、规则版本、覆盖守恒、退款累计/时间、账户状态、资金分配和现金余额；执行有界批量写入、审计、副作用及回执，随后commit。

事务后：仅返回已保存的小回执，按需启动独立只读摘要/分页。不得因为commit后的非关键展示失败而回报“账务失败”。数据库连接释放、提交结果不确定、重试和迟到响应要覆盖。

原子边界仍包括正式交易、草稿账户物化、映射提升、事件状态、审计及幂等回执。预计算依据过期必须拒绝/重算，不接受先验结果绕过最终锁内校验。

如果前述优化后上限仍无法稳定落在真实云调用预算内，才提出持久化任务方案：明确任务ID、租约/检查点、重试去重、进度和原子发布方式。先提交ADR及测量证据；不能把983秒长事务原封不动搬到后台，也不能偷偷把云函数改成常驻服务或扩大云资源费用。

## 8. PERF-4：客户端与逐页收口

导入工作台不再要求下载完整批次后才能操作。权威摘要控制计数与门禁，当前页按对象ID/版本缓存，有限LRU或页数上限控制内存；记录选择通过显式状态管理，不依赖一直保留所有页面对象。

仅同步状态变化更新同步字段；业务变化按服务端版本/有界deltas失效相关页与摘要。完整聚合不在每次输入或同步回调里重做。关闭弹层/卸载/退出后旧响应不可回填；在途命令及草稿持久化保障不减。

| 页面/场景 | 保留成果 | 剩余验收 |
| --- | --- | --- |
| 记一笔/交易详情 | 先输入、按ID选择、按需退款、成功即返回 | 真机输入/光标、失败不丢草稿、过期目录/会话；不得恢复整页依赖门禁 |
| 首页/账户 | 正式余额及快照口径 | 真实耗时分段、已有数据刷新提示；目录缓存不冒充最新余额 |
| 明细 | 最后意图和分页写屏障 | 游标版本、分页增量、目录失败仍显示主体 |
| 统计 | 独立trendEndMonth | 新旧服务需验证返回终点；旧服务忽略新增参数时不能静默显示错误月份 |
| 我的/账本 | 目录数量摘要、导入入口 | 缓存命中、局部失败不显示伪零、身份隔离 |
| 分类/账户管理 | 服务端实体局部更新 | 结构变更目录失效、冲突回读和原输入保留 |
| 导入 | 活动步骤/40项显示、单条证据 | 改为真正服务端分页；末页、组选择、恢复和金额/数量守恒 |
| 主题/启动 | 本地主题、原生框架 | 有启动测量证据再拆包，不把分包当数据库问题的解决方案 |

旧目录fallback目前每次目录失效都可能先探测UNSUPPORTED_ACTION再组合旧读取。需要时按环境、会话及服务协议版本缓存短期能力结果；显式刷新/版本变化能重新探测，不能永久粘在旧路径。权限错误与瞬时失败不降级。记录“新接口/旧兼容”的非敏感路径标签，使验收可识别真实运行版本。

前后台策略区分目录新鲜度与财务新鲜度，保留内容时明确刷新状态；不全量清屏，也不把旧财务值无提示永久当最新。旧bootstrap/categories缓存和新catalog尽量复用经过验证的目录版本，不能据目录缓存伪造已认证身份。

## 9. PERF-5：验收预算与回归矩阵

### 9.1 冻结工程预算（不是当前测量成绩）

以下作为首轮门禁；需更改时在PERF-0记录证据、原因和产品影响，不能测不达标后悄悄放宽。

- 回执及轻摘要：完整UTF-8 JSON分别不超过32KiB/64KiB。
- 普通分页响应不超过256KiB；页大小默认40、服务端最多100，同时按字节裁剪页边界并返回游标。单项过大走明示详情读取，不丢内容。
- 普通命令请求不超过64KiB；选择集合以服务端版本化组引用或受限分批草稿命令表达，最终正式入账仍整批原子。
- 每次setData不超过64KiB，导入活动page.data目标不超过256KiB；大字段详情单独验收，不把数据偷偷移到其他常驻全集对象以伪装通过。
- 1000/5000/24990条普通合成交易，核心SQL次数应呈“固定开销 + 有界批次次数 + 必要业务异常数量”，而不是每事件重复扫描完整问题集合。PERF-0按实际实现冻结可计算的Q(n)上限并加入测试，保留语句次数和调用次数两个口径。
- 本机固定合成基准的首轮预算：24990条prepareUpdate、resolveAccounts、post各不超过20秒，post用户锁持有不超过10秒；这是改造目标，不是云端SLO或完成承诺。旧基线同数据同环境比较，至少3次报告分布与最大值。
- 真实云端支持的最大规模：每个同步动作P95须留在有效超时预算一半以内，最大值不触及链路限制；有效预算取客户端、调用链和函数配置中的最小值。若无法满足，执行第7节架构决策，不只调长timeout或静默减少上传范围。
