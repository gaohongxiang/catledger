# MINI-1906V2 账单语义识别规则需求

> 状态：精简需求候选，等待用户确认；尚未进入设计或实现。
>
> 基线：MINI-1906V1 本地修复候选 `3e83a9e2f872efdc5c7b1199f35314a60f69c430`

## 1. 要解决的问题

当前代码可以识别已经写过特例的支付宝、微信记录，但不能证明一份新账单是否被完整理解：

- `parsers/platform.js` 保留了 `rawFields`，却只把已知列投影给后续逻辑，未知列没有进入语义覆盖判断；
- `parsers/normalize.js` 用“包含成功、完成、到账”等宽泛文本提前判断状态和资金效果；
- `source-action.js`、`source-funds.js` 与 `organizer-planner.js` 分别读取不同字段并重复推断语义；
- 同一个 `/`、同一个“收入”或同一个“转账”，在不同动作和状态下可能表示不同含义；
- 测试只能证明已有样本通过，不能发现新列、新枚举和新字段组合没有规则。

本阶段只解决一件事：

> 对账单每行的全部来源字段进行一次完整观测，再由来源 profile 下的组合规则确定资金效果、来源动作、账户端点、经济性质和关系；任何无法唯一确定的记录都明确进入待确认或未知，不得静默入账或消失。

## 2. 目标架构

```text
账单文件
  → Source Adapter
  → Row Semantic Resolver
  → Relation Resolver
  → EconomicEvent Builder
  → 现有 FinanceUpdate → Transaction
```

### 2.1 Source Adapter

每个真实导出模板维护一个版本化 profile：

```text
wechat_csv
wechat_xlsx
alipay_app_csv
alipay_web_csv
未来的 bank_xxx_csv
```

每个 profile 首期只是一个受测试的 JavaScript 配置及配套解析函数，负责：

- 识别模板、表头和数据区；
- 声明必需列、可选列、列别名和允许扩展列；
- 把来源列映射为标准字段，同时保留全部原始字段及位置；
- 解析日期、金额、币种和来源方向；
- 区分 `/`、空单元格、缺少列、解析失败和未知枚举；
- 登记该模板实际允许的交易类型、状态、方向等有限 token。

Source Adapter 不判断最终收入、退款、账户归属或正式交易，也不创建 Account、Category、EconomicEvent 或 Transaction。

用户手动选择“微信”或“支付宝”只能缩小候选，不能绕过缺列、重复列或模板冲突。

### 2.2 RawBillRow

Source Adapter 输出统一 `RawBillRow`：

```text
时间、金额、币种
原始交易类型、方向、状态、支付方式
交易对方、商品、备注
交易号、订单号、商户订单号
全部额外字段及来源位置
```

`RawBillRow` 只统一字段形状，不提前决定最终账务语义。原始值继续保存在现有 Evidence/raw snapshot 中，不额外复制一套敏感数据。

### 2.3 Row Semantic Resolver

每个 profile 拥有一套完整行决策规则。输入是完整 `RawBillRow`，输出简单的 `RowSemantic`：

```js
{
  disposition,
  sourceAction,
  settlement,
  amountMinor,
  currency,
  fromAccountRef,
  toAccountRef,
  relationRefs,
  ruleIds,
  issues
}
```

Resolver 按以下顺序处理：

1. 判断资金效果：资金变化、非资金、失败、关闭、处理中或未知；
2. 判断来源动作：消费、收入、退款、转账、充值、提现、还款、借款、收益、费用或未知；
3. 根据动作解释账户端点；
4. 检查单行关键事实是否完整。

首期不建设通用规则 DSL。规则使用 profile 内的小型决策表或纯函数表达，并至少记录 `ruleId`、读取字段、条件、输出和版本。

同一结论可以获得多条证据；无规则命中产生 `unknown`，多个不同结果同时命中产生 `conflict`。不得依赖代码顺序或最后写入覆盖冲突。这个合并逻辑只是共享纯函数，不是新的数据库领域对象。

### 2.4 Relation Resolver

Relation Resolver 处理不能由单行确定的关系：

- 退款与原消费；
- 微信、支付宝与银行卡中的同一笔转账；
- 信用卡还款和聚合还款；
- 多来源重复证据；
- 同订单部分退款。

它只读取 `RowSemantic`、稳定来源标识和现有账本候选，不再读取微信、支付宝原始字符串。

来源交易号、订单号等已认证强标识可以自动关联；仅金额、日期、商户或备注相近只能生成 ReviewIssue 候选，不能自动合并。

### 2.5 EconomicEvent Builder

Builder 不知道支付宝、微信或具体银行，只处理标准动作：

```text
purchase
income
transfer
refund
repayment
borrow
withdrawal
top_up
fee
non_financial
unknown
```

它把已经解析的动作、账户端点和关系转换为现有 EconomicEvent。失败、关闭和非资金记录只保留 Evidence 与归宿，不生成正式资金事件。

posting 继续消费已经保存的 EconomicEvent，不在正式提交时重新解析账单。预览和提交至少使用相同的 profile/rule policy 版本与分析摘要，版本或事件集合变化时要求重新整理。

### 2.6 覆盖报告

覆盖报告只保留三个真正需要的判断：

1. 所有行都有归宿：资金事件、非资金、重复证据、需要确认、用户排除或无效来源行；
2. 所有准备入账的事件都具备金额、日期、币种、正确经济性质、必要账户端点和必要关系；
3. 认证 profile 的当前文件没有未知交易类型、未知状态、规则冲突或待确认关键行。

字段清单、枚举清单和实际组合命中情况作为同一份轻量诊断信息输出，不建立独立业务模型。

用户排除一条已经识别的记录不降低语义识别率；用户排除一条未知记录不能把它伪装成“整份账单已完整识别”。

## 3. 验收需求

### R1. 模板和字段完整读取

- 当系统读取一个候选账单时，应保留全部表头、全部数据字段和来源位置，不得只保存当前认识的列；
- 当出现未知列、缺少必需列、重复冲突列、错误工作表或关键公式字段时，应明确报告；
- 当结构与唯一 profile 不匹配时，不得仅凭最高相似分继续按认证模板处理。

### R2. 原始枚举完整盘点

- 当有限枚举字段出现新 token 时，应标记 `unknown_token`，不得归入宽泛“其他”；
- `/`、空值、缺列和解析失败不得归为同一种状态；
- 当状态包含“成功”或“完成”但不在该 profile 的已知组合中时，不得自动视为已结算。

### R3. 完整行组合判断

- 当系统判断资金效果和来源动作时，应联合读取 profile、交易类型、方向、状态和金额类别；
- 当支付宝记录严格匹配零金额免押、冻结或解冻生命周期组合时，应归为非资金记录且不再询问账户；任一必要条件变化都不得继续命中；
- 原消费行的退款状态与独立退款到账行必须分开表达，不能生成重复退款；
- 前一阶段已经确定失败、关闭或非资金的记录，不得继续进入账户选择。

### R4. 账户端点

- 当微信转账收入的支付方式为 `/` 或空、状态精确为“已存入零钱”且金额为正时，应把微信零钱作为流入端；`/` 本身不得直接推出账户未知或微信零钱；
- 当记录属于提现、充值、余额宝转入转出或信用卡还款时，应按动作决定支付方式代表流出端还是流入端；
- 当账户引用只有“银行卡”“信用卡”等泛称时，不得自动绑定现实账户；
- 历史账户或忽略决定应绑定稳定来源引用键，并支持已知旧键 alias；规范字符串变化不得让相同来源引用重新询问，概念确实拆分或发生冲突时不得自动继承。

### R5. 经济性质与关系

- 当来源写“收入”“支出”或“转账”时，系统应结合动作、账户端点和关系确定最终 EconomicNature，不得直接照抄来源方向；
- 只有稳定官方标识或经过认证的强关系可以自动合并事件；金额、日期、商户和备注相近只能形成 ReviewIssue 候选；
- 退款、本人转账、还款和借款不得降级成普通收入或支出以绕过缺失关系或账户端点。

### R6. 入账门禁

- 普通支出必须有金额、币种、日期和流出账户；普通收入必须有金额、币种、日期和流入账户；
- 内部转账必须有两个不同账户；信用还款必须有付款资产账户和目标负债账户；退款必须有到账账户以及原支出或明确待关联状态；
- 任何关键字段为 `unknown` 或 `conflict` 时，不得生成 ready 事件；
- 分类完整度可以单独提示，但不得改变 Account / Transaction 的既有权威边界。

### R7. 行守恒和诚实提示

- 输入数据记录数应严格等于各最终记录归宿数量之和，不得静默跳行或重复计数；
- 覆盖报告应分别显示已识别、待确认、未知、冲突、用户排除和无效数量；
- 只有全部疑似资金记录均已识别、关键未知和冲突为零、可入账事件事实完整且来源提供的控制项通过时，才可显示“整份账单已完整识别”；
- 只导入用户选中的部分记录时，应显示“已确认选中交易”，不得冒充整账完整。

### R8. 测试与切换

- 每条关键规则必须有一个正例和逐个破坏必要条件的 near-miss 反例；
- 微信 CSV/XLSX、支付宝 App/Web 应分别维护脱敏金标夹具和实际 token 清单；
- 新逻辑应按稳定 Evidence/来源身份比较事件性质、金额、账户端点、关系和可入账性，不比较随机 ID 或展示顺序；
- 新逻辑在四个 profile 的金标、未知检测、冲突检测和真实账单回归通过前，只能影子运行；
- profile 切换后才按该 profile 删除旧字符串判断，不一次性删除全部旧逻辑。

### R9. 兼容现有正式账本

- 本阶段继续使用现有 Evidence、EconomicEvent、ReviewIssue、FinanceUpdate、Transaction 和 Account；
- 不新增 JournalEntry / Posting，不建设第二套正式账本；
- 规则层只生成语义结果和候选事件，无权直接创建正式 Account、Category 或 Transaction；
- 规则版本应记录在现有分析/计划版本中；同一批预览与提交必须使用同一版本，版本变化时要求重新整理；
- 所有读取、映射和报告继续使用服务端认证上下文的 uid 隔离，不接受客户端自报 uid。

## 4. 首轮范围

首轮只迁移四个现有 profile：

- 微信支付 CSV；
- 微信支付 XLSX；
- 支付宝 App CSV；
- 支付宝 Web CSV。

新增银行时，通过增加 profile 和配套完整行规则接入，不修改通用 Relation Resolver、EconomicEvent Builder 或 FinanceUpdate 主链路。

用户自定义列映射、JSON 映射配置、银行通用导入、PDF、OCR、AI、远程规则包、动态脚本和通用账户概念图谱均不属于本期。

## 5. 完成定义

本阶段只有同时满足以下条件才算完成：

1. 四个 profile 都能完整保留字段并报告未知列和 token；
2. 微信、支付宝来源字符串判断从 normalize、source-action、source-funds 和 planner 收口到 profile + Row Semantic Resolver；
3. Relation Resolver 与 EconomicEvent Builder 不读取来源专属原始字符串；
4. 用户真实问题中的微信零钱、小荷包历史忽略、支付宝零金额非资金记录全部通过；
5. 关键规则正例和 near-miss、行数守恒、未知/冲突阻断和新旧结果差分全部通过；
6. 真实微信身份下完成单文件、混合文件、重复上传、返回恢复、账户确认和整批入账验收；
7. 未部署、未迁移开发云、未上传体验版，除非另行获得明确授权。
