# MINI-1906V1 真实账单语义修复需求

> 状态：本地候选通过，等待真实身份回归
>
> 来源：MINI-1906V 于 2026-09-04 使用真实微信、支付宝账单发现的阻断缺陷
>
> 目标：只修复账户忽略规则、微信入账账户推导和支付宝非资金记录，不扩展正式账本模型。

## 1. 问题与范围

真实账单验收确认了三类错误：同名支付宝小荷包的旧版长期忽略规则无法命中新版账户键；微信收入转账虽然状态明确为“已存入零钱”，仍被当作 `/` 未知账户；支付宝零金额免押下单和自动解冻被当作待入账事件并要求创建账户。

本任务修改来源语义、账户映射兼容、FinanceUpdate 规划和对应小程序展示。保留原始 Evidence，不修改 `Transaction` / `Account` 权威边界，不新增表，不部署或迁移开发云。

## 2. 用户故事

1. 作为用户，我希望“以后不计入”在后续账单中真正自动生效，不再重复要求我创建或选择账户，同时仍能在入账前看见并修改结果。
2. 作为用户，我希望微信明确写着“已存入零钱”的收入自动归到微信零钱，而不是把 `/` 当成一个账户。
3. 作为用户，我希望零金额免押授权和解冻只保留为来源证据，不生成账户、正式交易或待整理问题。
4. 作为维护者，我希望账户键演进兼容旧规则，并让新版精确规则稳定覆盖兼容候选，不通过名称和时间猜测正式事实。

## 3. 验收需求

### R1. 旧账户键兼容

- 当启用中的历史账户规则具有可识别的来源类型和支付工具提示时，系统应派生当前规范键作为低优先级兼容候选，并保留原键供旧批次重建；
- 当同一规范键同时存在新版精确规则与旧版兼容候选时，系统应以新版精确规则为准；同级兼容候选相互冲突时不得猜测；
- 空值、`/` 和泛称不得通过兼容逻辑变成稳定账户；不得修改或删除原历史规则。

### R2. 长期忽略真正自动生效

- 当历史 `ignore` 规则命中稳定支付工具时，planner 应把相关未入账事件自动标记为 `excluded`，写入结构化历史规则原因，不生成阻塞账户问题、账户草稿或正式交易；
- 小程序应把该账户项显示为已按历史规则不计入，不要求用户再次选择；用户在整批入账前仍可将它改为已有账户或新账户草稿；
- 用户改选账户并最终入账后，新版精确账户规则应优先于旧兼容忽略候选；整批失败时不得改变历史规则。

### R3. 微信“已存入零钱”资金端

- 当微信原始记录是收入方向、外部转账、支付方式为空或 `/`，且状态明确包含“已存入零钱”时，系统应派生一个带规则来源的微信零钱账本端；
- 派生只影响工作结果，原始支付方式和状态必须原样保留在 Evidence；
- 其他 `/`、其他状态、支出或中性记录不得套用该规则。

### R4. 支付宝零金额非资金生命周期

- 当支付宝记录同时满足零金额、中性方向、`信用借还` 和明确的免押下单/解冻成功状态时，系统应将其识别为非资金生命周期证据并自动排除；
- 该记录不得生成账户问题、账户草稿、正式交易、余额或统计影响；
- 非零金额、收入/支出方向或仅商品文案碰巧包含“免押/解冻”的记录不得被自动排除。

### R5. 重建、兼容与隐私

- 规则版本升级后，已有未入账 FinanceUpdate 应由服务端声明需要重建，并基于不可变原始字段得到新结果；
- 公共动作名称和响应结构保持向后兼容；日志、测试和文档不得包含真实账单、完整账户标识、用户身份或凭据；
- 修复必须以失败回归测试起步，并通过根目录、导入函数非数据库及 MySQL 8 测试、语法、依赖审计与差异检查。

## 4. 非目标

- 不新增 `JournalEntry` / `Posting`；
- 不实施 MINI-1906A1 的账户草稿可达性、修正、撤销或多交易事件维护；
- 不修改已入账正式交易；
- 不新增银行账单格式，不部署云函数，不执行云迁移，不上传体验版。
