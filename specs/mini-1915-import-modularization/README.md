当前主流程已经分层，常规账本 API 也有实际模块边界。优先整理两个集中点：**导入核对服务**和**导入工作台页面**。现有解析器、来源规则、正式入账事务和读取缓存继续使用，避免一次重写整条资金链路。

## 请 6 sol 重点评审

1. 拆分是否解决了真实依赖问题，是否存在过多小文件、换名字却不分职责的情况？
2. P1 的依赖方向能否消除旧计划升级、读取服务对 `review-issue-service` 的依赖，而不产生新的循环？
3. P2 能否保留同一连接、同一事务、原锁顺序、版本、幂等回执和失败回滚？历史核对与分期费用复用是否都被覆盖？
4. P3/P4 的生命周期所有权是否足以替代 `paged.enhance` 的方法覆盖？是否遗漏草稿恢复、切后台、切问题、分页和迟到响应？
5. 哪些已有回归已经足够，哪些只有静态字符串断言、需要换成实际行为验证？是否有不必要的重测或新框架？
6. 银行身份冲突分支和两处资金方向推导能否原样抽取？若不能，是否应明确留在后续业务变更任务？

建议评审结果给出：结论（可执行 / 修改后执行 / 暂不执行）、按风险排序的问题、建议修订的文件边界和阶段，以及最小首个实施提交。评审不自动触发实施。
