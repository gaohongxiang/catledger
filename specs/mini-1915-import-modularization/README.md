## 结论与范围

采用局部、行为等价的模块化：先解除导入核对公共能力对总服务的依赖，再拆事务内场景，最后明确导入工作台生命周期和操作流程。不是重写整条导入链路，也不是一次性能优化承诺。

保留常规账本 API、现有解析器与静态 profile、正式入账事务、共享规则、读取缓存和草稿恢复。不接入其他决策模型、AI 框架、运行时插件、微服务、云托管或新数据库；不改变页面布局、导航、账务规则或公开协议。

### 已核对的集中点

行数只用于定位，不作为验收指标：初稿基线的 `review-issue-service.js` 为 1696 行，工作台 `index.js` / `model.js` / `paged.js` 为 1788 / 1032 / 623 行。core、read、maintenance、旧语义升级实际依赖核对总服务；页面实际由 `paged.enhance` 覆盖部分方法和生命周期。普通 API 已有交易、贷款、分期等模块边界，不整体重拆。

进一步核对 `action-registry.js` 与 `import-service.js`：核对工厂返回五个方法，但其中 `reviseAccountMapping` 仅由内部 service 暴露，没有注册同名公开 action。P0 必须查明其实际调用方；本轮不得为了“补齐五个接口”而增加网络入口。
