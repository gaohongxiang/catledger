# MINI-1915 验收要求

实施状态：未开始。以下是重构约束，不是新增产品需求。基线与范围见 [计划入口](README.md)。

## R1. 业务行为等价

- 当相同来源、账户目录、已入账记录和人工决定交给拆分前后实现时，应产生相同的有效事件、核对问题、来源关系、分类、金额和入账结果。
- 当存在同来源重复、来源身份冲突、同额独立交易、历史疑似重复或人工确认时，应保持现行分支和优先级；不能靠金额、时间或文本相近自动合并。
- 当导入银行分期本金、利息和费用时，应保持本金不重复记消费、费用防重、来源晚关联和分期进度的现行行为。
- 当来源明确值、持久映射、本批决定和人工覆盖发生交互时，应保持当前已实现的优先级；发现规则歧义先写出差异，不能顺手统一口径。

## R2. 金融事务与身份边界

- 当执行整理、核对或入账命令时，应由既有服务端可信身份确定用户范围，使用原事务入口及原连接；子模块不得独立提交、开启嵌套事务或把写入移出事务。
- 当请求重放、并发提交、版本过期、历史记录变化、数据库中途失败或成功响应丢失时，应保持原拒绝条件、完整回滚、幂等回执及原请求恢复语义。
- 当正式入账发生时，应保留整批原子写入、来源唯一约束、锁内历史复查和分期费用校验；本计划不重排正式入账 SQL。

## R3. 契约与旧数据兼容

- 当重构版本读取已有草稿、旧语义计划、已入账批次或本机持久请求时，应能沿原流程继续或恢复，不能要求用户清库、重新导入或删除草稿。
- 当只移动内部代码时，接口 action、请求/响应、错误码、schema、身份键、摘要、游标、规则/计划版本及回执内容应保持兼容；不得为消除旧数据问题随意递增版本。
- 如果证明必须改变业务输出、持久字段或公开契约，应停止把这部分当作等价重构，列为独立变更并说明迁移和验收。其余可独立验证的拆分继续推进。

## R4. 页面与恢复

- 当用户切步骤、翻页、切核对项、关弹层、切后台、退出登录或页面卸载时，只应接收仍属于当前用户、页面、批次和版本的响应。
- 当用户正在编辑、后台刷新返回、写入成功但明细读取失败时，应保留输入或已确认操作事实；不能闪现错误、覆盖新值或再发一笔入账命令。
- 当展示原始记录时，应继续直接展示当前页原始列和值，保留空值、零、重复列、原始编码含义、失败重试和超长原文入口。
- 当拆分页面模型时，应继续使用现有 `import-draft-session`、`import-view-session`、`read-cache`、`view-patch`，不引入另一套草稿、缓存或全局状态管理。

## R5. 可理解的模块边界

- 当新增或修改一个核对场景时，应能从明确的入口定位到处理模块、共享规则和存取模块；不需要在页面覆盖链或核对大函数中搜寻实际执行者。
- 当纯规则模块被加载时，不应依赖数据库、微信页面、存储或服务工厂；读取与升级模块不应反向依赖人工核对入口。
- 当页面注册生命周期和 WXML 处理函数时，应只有一份明确的所有权清单；冲突应在开发检查中报错，不能由对象合并顺序静默决定。
- 当未来扩展银行模板时，应沿现有 `profiles` 和解析器契约扩展；本轮不为尚不存在的插件或模型增加占位接口。

## R6. 资源预算、证据与交付

- 当大批次分页、账户批量映射、历史比对或正式入账运行时，应继续满足现有响应、`setData`、缓存和 SQL 预算，不新增逐事件查询或整批前端常驻数据。
- 当一个阶段完成时，应提交对应调用关系、受影响行为验证、实际通过/失败/跳过结果和可回退提交；行数下降或文件增多不单独构成验收。
- 当代码入口改变时，应同步入账逻辑说明、架构与相关现行说明的入口和边界；用户行为若意外改变，必须先归为独立业务变更并更新需求/业务规则。
- 当报告完成时，应区分源码、自动检查、原生开发者工具、云函数、体验版和真机验收的状态。未执行的发布与验证不计作完成。
