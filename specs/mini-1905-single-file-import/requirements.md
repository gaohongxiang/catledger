# MINI-1905/1906 多账单统一导入需求

## 1. 目标与基线

MINI-1905 与 MINI-1906 合并为一个连续交付：用户一次选择多份支付宝或微信账单，系统逐文件上传和解析，再把所有成功来源冻结为一个 `FinanceUpdate`，跨来源整理为 `EconomicEvent`，只把真正需要用户决定的问题投影为 `ReviewIssue`，最后整批原子入账。

`origin/catledger-web` 的 `importing`、`organizer`、`ReviewIssue`、`postability` 与 `posting` 是业务迁移基线。Node.js、CloudBase MySQL 与原生小程序只改变运行时和交互载体，不得把原模型缩减为逐行 `post/skip/linked`。本规格明确覆盖并替代原“单文件可信导入”的最终产品边界；现有单文件代码只作为可复用基础和迁移兼容层。

## 2. 用户故事

1. 作为用户，我可以一次选择多份账单，并分别看到每份文件的上传、解析、失败与重试状态。
2. 作为用户，我希望同一次现实资金活动在不同账单中的证据被保留并整理为一个经济事件，而不是重复入账。
3. 作为用户，我只处理账户归属、同一事件、退款关系、转账/还款账户、身份冲突等真正有歧义的问题，不逐行批准系统已经能确定的普通记录。
4. 作为用户，我可以下钻查看问题关联的文件、原始行定位、事件、关系和已有正式交易，但普通列表不暴露不必要的原始敏感正文。
5. 作为用户，我只在所有阻塞问题解决后确认一次，系统要么把整批正式交易和关系全部写入，要么全部回滚。
6. 作为用户，我可以在正式入账前随时放弃整批并重新选择；即使已经填写“新建账户”或账户映射，也不能提前改变现有账户、余额、交易、规则或统计。

## 3. 需求与验收标准

### R1. 多文件生命周期与失败隔离

- 当用户一次选择 1～5 份文件时，系统应为每份文件签发独立的用户隔离对象路径和幂等上传身份，并保留选择顺序；客户端选择器和服务端批量校验必须使用同一上限。
- 当任一文件上传或解析失败时，系统应只标记该文件失败，并允许其独立重试或从本次更新中移除；其他成功文件和解析证据不得回滚、覆盖或丢失。
- 解析结束后文件选择入口应继续可用；用户可以保留成功来源、追加其他账单并只解析新加入的文件。只要至少一份文件成功即可进入账户步骤，全部失败时仍可重试、删除或追加文件，不得把用户困在失败摘要页。
- 当用户确认使用全部成功解析的来源时，系统应按固定顺序把各来源的不可变解析批次冻结到一个 `FinanceUpdate`；同一解析批次不得被两个活动更新重复占用。
- 当文件内容、解析器或规范化规则相同时，重试应复用安全结果；当规则版本或解析选项改变时，系统应建立新的不可变解析批次而不是静默改写旧批次。
- 文件摘要相同只证明内容相同，不证明已经入账。既有文件尚未 `committed` 且未形成正式交易时，再次选择应直接放弃占用它的旧 FinanceUpdate、保留审计并复用其不可变解析批次进入本次流程，不询问用户是否继续旧进度。只有来源已经正式入账时才作为“已经入账”阻止重复交易。任何一种结果都不得让客户端静默删除唯一文件并退回空白页。
- 每份文件应保留文件摘要、来源类型、格式、账期、账单主体候选、行数、错误码、解析器版本、规范化版本、身份规则版本与原始行定位。

### R2. 证据、来源身份与重复裁决

- 当一条来源记录被解析时，系统应分别保存原始行、规范化字段、来源身份候选、问题码和规则版本；规范化结果不得覆盖原始证据。
- 当同一用户同一来源的稳定身份首次出现时，系统应依靠 MySQL 用户范围唯一约束裁决身份；并发重试只能留下一个身份事实。
- 当稳定身份相同且核心摘要一致时，系统应识别为同来源重复证据；当稳定身份相同但核心摘要冲突时，系统应生成 `identity_conflict` ReviewIssue，不得覆盖旧证据或自动入账。
- 当两条记录只有金额、时间、文本、对方或账户尾号相近时，系统只能生成候选关系；不得自动删除证据、合并事件或复用正式交易。
- 当两条物理记录同额同日但稳定来源身份不同，或仅有文件内物理定位身份时，系统应保留为独立证据，除非用户通过 `same_event` 问题明确确认合并。

### R3. FinanceUpdate 与跨来源整理

- 当 `FinanceUpdate` 进入整理时，服务端应统一读取所有冻结来源，以原规划器的领域规则生成 `EconomicEvent`、`Evidence`、`Relation` 和守恒计数。
- 每个 `EconomicEvent` 应使用 `ready / needs_action / excluded / posted / corrected` 之一，并保存版本、经济性质、资金方向、账户、对方账户、时间、金额、币种、分类、字段来源和原因码。
- 经济性质应至少覆盖 `income / expense / internal_transfer / borrow / repayment / refund / fee / balance_adjustment / unknown`；退款、本人转账、信用卡还款和借款还款不得被简化为“跳过”。
- 当多个来源共享并核验通过的稳定关联号，或命中已冻结并有规则版本的官方强关系时，服务端可以自动归组；其他跨来源线索只能形成候选 ReviewIssue。
- 当来源证据证明本人转账或还款的两端时，系统应形成一项中性经济事件并保留两端账户；当缺少任一端或候选不唯一时，系统应生成 `transfer_accounts` 问题。
- 支付平台在原消费行上标记“已退款/退款成功”时，该行仍是原支出；只有退款入账方向的记录才建立退款事件，不得把一买一退识别成两笔退款。
- 退款候选必须先满足账户身份、币种、先后时间和金额守恒，再由明确退款状态、共享稳定标识或相同商户证据证明关联；不得仅按“最近几笔金额足够大的支出”生成可靠候选。当退款可唯一、合法地指向原支出且累计退款不超额时，系统应自动确认 `refund_of` 关系；无法唯一确认、金额超限或目标无效时，系统应生成 `refund_relation` 问题。
- 客户端不得提交或覆盖 `ready`；每次事实修改、关系决定和最终入账前，服务端都应通过统一 `EvaluatePostability` 等价规则重新裁决状态。

### R4. ReviewIssue 投影与决定

- 当事件处于 `needs_action` 时，系统应保证每个事件恰好由一个当前打开的阻塞 ReviewIssue 覆盖；一张卡片只询问一个可执行决定。
- ReviewIssue 类型应等价迁移为：`account_mapping`、`shared_fields`、`same_event`、`refund_relation`、`transfer_accounts`、`identity_conflict`、`field_conflict`、`installment_origin`。
- ReviewIssue 决定应等价迁移为：`apply_fields`、`confirm_distinct`、`confirm_same`、`exclude_events`、`confirm_installment_principal`、`discard_evidence`、`link_refund`、`link_existing_transaction`。
- 当用户解决问题时，服务端应校验更新版本、问题版本、成员版本、决定与问题类型的适用性，并在一个事务中更新事件、证据角色、关系、问题、行动审计和守恒计数。
- 当一个决定解决当前问题但仍留下另一类阻塞原因时，系统应关闭原问题并生成一个新的后续 ReviewIssue，不得在同一张已解决卡片中静默改变问题含义。
- 可共享决定只能按原 organizer 的稳定签名安全分组：账户归属按具体支付工具；资金流转和共同字段还必须保持经济性质、方向、原因族、来源/支付账户上下文、交易类型、经济效果、币种及规范化证据文本一致。退款、身份冲突、字段冲突和分期来源不得仅因界面文案相同而批量套用决定。
- 已关闭问题应保留 `resolved / superseded` 审计状态和对应 `FinanceAction`，重复提交同一幂等请求应返回首次结果。
- 账户步骤中的“新建账户”、支付工具映射和永久忽略都只应保存为当前 `FinanceUpdate` 的草稿决定；不得调用正式账户创建接口或提前更新可复用规则。
- “仅本次不计入”和“以后不计入”应固定放在同一个不计入分组，不得混入已有账户滚动列表；两者在没有用户决定时均不应默认选中。已有后续忽略偏好命中时，账户归属项仍应展示并提示上次选择，但任何处理方式仍不默认选中；用户必须重新明确选择，选择账户可覆盖该偏好。
- 整批正式入账前，用户返回账户步骤时应看到已确认选择并可修改；修改只更新本 FinanceUpdate 草稿和受影响的未完成问题，不得提前改动正式账户、正式映射或账本。已完成的后续关系决定不得被静默覆盖。
- 账户步骤应优先沿用已经生效的支付工具映射；没有映射时，可按规范化账户名称、银行主体、尾号和币种推荐唯一匹配的活动账户并默认选中，同时明确提示用户核对。不同银行仅尾号相同、币种不同或最高分并列时不得自动选择；用户手动修改后的选择不得被推荐逻辑覆盖。
- 支付宝余额宝转出/转入、账户余额充值/提现和微信明确零钱充值/提现应由版本化来源资金投影器产生 `from / to` 引用；支付宝“余额/账户余额”共用一个账户键，余额宝独立。两端映射完整时不得生成账户问题，只缺一端时 ReviewIssue 和客户端都只能询问缺失端。
- 每个 EconomicEvent 应能通过用户隔离的只读动作下钻全部原始 Evidence，包括文件、原始行号、来源定位符、角色、解析/快照版本和不可变原始字段；普通问题列表和日志仍只返回安全摘要。
- 当微信、支付宝或银行账单引用同一张具有银行主体与稳定尾号的银行卡时，系统应只展示一个账户归属决定；该决定应覆盖本批中这一物理账户的全部来源支付键。平台余额、余额宝、零钱、零钱通等平台自有账户必须继续按来源隔离，不得跨平台合并。
- 当同一物理账户的最高优先级明确映射一致时，系统应在本次规划中统一沿用该账户；当同一优先级出现多个不同账户时，系统应撤销自动确认并生成一个可修改的账户归属问题，不得拆成多个“已确认”项或静默任选其一。
- 账户映射优先级固定为“规范全名唯一推断 < 类型兼容的正式历史映射 < 本 FinanceUpdate 明确选择 < 本事件手工端点”；低优先级结果不得覆盖高优先级结果。历史忽略只作为上次选择提示，不属于默认账户，也不得跨来源传播。
- 支付宝付款记录中的`花呗`与具体银行`信用购`应保留为两个真实负债账户；还款记录中的`花呗｜信用购`只表示合并账单引用，不得创建第三个账户、支付映射或账户归属项。系统应优先列出本批已识别的真实负债账户，让用户把还款总额全部归入一个账户或按金额拆分；分配账户必须唯一、有效、与转出账户不同，且正整数分之和必须严格等于还款总额。

### R5. 已有交易、服务端可入账裁决与整批入账

- 当来源身份已经链接正式交易时，系统应复用或展示该链接，不得再创建一笔正式交易。
- 当用户选择 `link_existing_transaction` 时，系统应校验该交易属于当前用户、尚未被不兼容事件占用，并与事件金额、账户和业务方向相容。
- 当任一打开的阻塞问题、`needs_action` 事件或守恒计数不一致存在时，系统应拒绝整批入账。
- 当用户确认整批入账时，服务端应在同一 MySQL 事务中锁定更新、行动、全部待入账事件、关系、正式账户、分类和必要的已有交易链接，重新计算每个事件的可入账性，再创建正式交易和不可变链接。
- 正式账户新建、正式账户映射/永久忽略规则、正式交易、余额派生依据和统计依据只能在上述整批 posting 事务中生效；posting 之前以及 posting 回滚后，这些正式数据必须与导入开始前逐项一致。
- 当任一正式交易、退款关系、转账双端、链接或状态更新失败时，系统应回滚本次更新的全部正式账本写入；不得留下部分交易或部分关系。
- `cash` 账户不得被新的手工交易或整批导入从非负变为负数，历史负数也不得被进一步降低；校验必须在账户锁和同一 MySQL 事务内执行。导入触发时整个 FinanceUpdate 回滚，公开错误码为 `INSUFFICIENT_CASH_BALANCE`。
- 重复、并发或提交结果不确定后的同幂等键重放应返回首次结果；同键异请求应拒绝。
- 当已入账事件需要纠错时，系统应先检查全部关联正式交易的版本和整批影响，再在一个事务中重建受影响交易与链接并把事件标记为 `corrected`；外部已修改、缺失或被其他事件共享的交易应阻止静默重建。
- 当用户请求撤销一次已入账更新时，系统应先返回影响预览；只有全部交易仍可安全撤销时才整批执行，任一冲突不得留下部分撤销。
- 当用户在 `draft / failed / review` 状态放弃更新时，系统应以幂等 `financeUpdates.abandon` 把更新标记为 `abandoned`、释放来源供新更新使用，并保留证据与决定审计；不得创建、修改或删除任何正式账户、映射、分类、交易、余额或统计事实。

### R6. 用户隔离、迁移与隐私

- 所有新表、外键、查询、唯一约束、对象路径、游标和幂等键都应包含服务端取得的 `uid`；客户端身份形状字段应继续被拒绝。
- 数据库应通过连续的 `0006` 及后续 forward-only、可重入迁移扩展；已经应用的 `0004`、`0005` 文件不得修改。
- 迁移应保留既有文件、批次、原始行、来源身份、已提交交易和链接；现有未提交单文件投影应能安全重建为新整理计划，不得重复入账。
- 普通日志、错误响应、ReviewIssue 列表和客户端恢复状态不得包含文件正文、完整账号、完整交易描述、OpenID、内部 `uid`、SQL 或绑定值。
- 成功入账后的原文件清理由事务外生命周期任务处理；清理失败不得把已经提交的账本伪装成失败，也不得阻塞幂等重放。

### R7. 小程序交互

- 小程序应沿用用户熟悉的四步视觉结构，把内部能力升级为“多文件摘要 → 账户归属 → ReviewIssue → 整批入账”，不能因单/多文件差异另造一套页面。
- 文件区应逐项显示状态和摘要；问题区只渲染打开的 ReviewIssue，不再显示逐行“将入账 / 不新建”作为最终整理模型。
- 当 ReviewIssue 为 `same_event` 时，界面应明确提供“同一笔 / 多笔独立”；其他问题应按类型只展示合法决定，并允许下钻证据。
- 整理页应按问题类型分组；每个问题在列表中直接显示主体交易的标题、日期、来源和金额。退款问题还应显示可靠候选数，详情按可靠候选优先列出原消费的商户、日期和金额；没有可靠候选时可从本批满足账户、币种、时间和金额约束的原消费中手动选择，不得只展示内部成员数或状态码。
- 移动端应以处理批次压缩主页面：安全分组后的单个 ReviewIssue 显示一张批量卡并最多预览 3 笔；多笔退款只显示一个汇总入口，进入后仍逐笔决定且确认后自动进入下一笔，不得把同一个原消费批量套给多笔退款。
- 当所有阻塞问题解决后，界面应展示 ready、excluded、已关联既有交易和将创建正式交易的汇总，再提供唯一的整批确认入口。
- 在服务端返回新状态前，客户端不得乐观地把事件标记为 `ready`、`posted` 或 `corrected`。
- 解析后至最终确认前应常驻“放弃本批账单”入口；二次确认必须说明账户选择和整理结果会被放弃、正式账本不会改变，成功后回到空白文件选择状态。

## 4. 业务守恒

- `validEvidenceCount - duplicateEvidenceCount = finalEventCount`；经人工确认同一事件后，事件数减少、重复证据数等量增加。
- `finalEventCount = readyEventCount + needsActionEventCount + excludedEventCount + postedEventCount`，`corrected` 计入已入账事件。
- 一个有效证据行在同一 `FinanceUpdate` 中只能归属一个最终事件；丢弃证据仍保留审计行和 `discarded` 角色。
- 一个经济事件可关联多份证据和一笔或多笔正式交易；正式余额与统计仍只由 `catledger_transactions`、账户和分类决定。
- 还款、转账和退款的组成金额必须守恒；缺少贷款明细时不得猜测本金、利息和费用。
- 一条合并还款 EconomicEvent 可按用户确认的守恒分配投影为多笔正式内部转账；每笔交易分别减少付款资产、减少对应负债，并通过 `repayment_allocation` 角色回链同一事件。

## 5. 非目标

- 本阶段不扩展通用银行 PDF、证券、多币种、贷款合同与分期计划的完整产品能力；`installment_origin` 只保留原整理兼容门禁，完整贷款模型属于 MINI-1908。
- 本阶段不实现 MINI-1907 的导出、注销、全局生命周期任务和正式发布。
- 本阶段不部署云函数、不执行开发云迁移、不提交、合并或推送；这些动作需在实现和本地验收后另行授权。
- 设计冻结前不继续打磨当前逐行“将入账 / 不新建”页面。
