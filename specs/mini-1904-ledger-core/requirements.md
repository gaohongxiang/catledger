# MINI-1904 需求：账户、手动记账与交易列表

> 状态：已确认，进入技术与界面设计。

## 1. 问题与目标

MINI-1903 已建立可信微信身份、内部用户和默认分类，但用户还没有可用的正式账本。MINI-1904 要建立后续账单导入依赖的唯一账户与交易底座，让用户能够创建自己的资金账户，手动记录支出、收入和内部转账，并按自然月查看交易与基础统计。

本阶段必须保证：正式余额只由账户与已入账交易推导；内部转账不重复计入收支；客户端不能指定用户身份；所有写操作可以安全重试。

## 2. 用户故事

1. 作为首次使用者，我希望创建现金、银行卡、平台钱包或负债账户，并填写当前余额，以便账本从真实起点开始。
2. 作为记账用户，我希望快速记录支出、收入或自己账户之间的转账，以便账户余额和月度统计立即更新。
3. 作为记账用户，我希望修改或删除误记的手工交易，以便账本可以纠错且不会留下余额偏差。
4. 作为记账用户，我希望按月份浏览和搜索交易，并看到当月收入、支出和结余，以便快速了解资金变化。
5. 作为多账户用户，我希望看到每个账户的当前余额和总净值，并能停用不再使用的账户，同时保留历史记录。
6. 作为长期使用者，我希望按心情选择一套舒适的账本视觉主题，同时保证金额、收支含义和数据完全不变。

## 3. 功能范围

### 3.1 账户

- 用户手动创建账户，不根据微信身份或历史宠物数据自动生成账户。
- 首版提供六类账户：`cash`（现金）、`bank`（银行卡）、`wallet`（微信/支付宝等平台余额）、`credit`（信用卡/消费信贷）、`other_asset`（其他资产）、`other_liability`（其他负债）。
- 首版界面只允许人民币 `CNY`；schema 保留显式币种字段，不在本阶段实现汇率和跨币种统计。
- 账户名称在同一用户的活动账户中唯一；名称长度为 1～32 个可见字符，不要求填写完整卡号或账户号。
- 创建账户时可以填写“截至某日的余额”。资产账户输入持有金额，负债账户输入待还金额；服务端把它记录为独立的余额调整交易，不计入收入或支出。
- 用户可以在账户详情中发起“校正余额”；服务端根据当前聚合余额计算差额并新增一笔余额调整，不直接改写历史交易或伪造收入支出。
- 用户可以修改账户名称；有历史交易的账户不能物理删除，只能停用。停用账户仍出现在历史交易中，但不能用于新交易。
- 当前余额由未删除的正式交易聚合，不由客户端提交，也不依赖单独的可漂移余额缓存。
- 资产余额按账面正负值展示；负债通常以“待还金额”的正数展示，但净值计算按负数处理。信用卡溢缴款可以显示为资产方向余额。

### 3.2 手动交易

- 用户可创建 `expense`、`income`、`transfer` 三种可见交易；`balance_adjustment` 仅由账户余额初始化或后续余额校正流程创建。
- 金额以人民币分为最小单位持久化，接口不接受二进制浮点金额；用户输入必须大于等于 0.01 元并在 `BIGINT` 安全范围内。
- 支出必须选择付款账户和支出分类；收入必须选择收款账户和收入分类；转账必须选择两个不同的活动账户且不选择分类。
- 支出使付款账户账面余额减少，收入使收款账户账面余额增加，转账在同一数据库事务中令转出账户减少、转入账户增加；转账不计入收入或支出。
- 每笔交易保存用户本地发生日期、发生时间和时区偏移；自然月筛选使用发生地的本地日期，不使用服务器时区猜测。
- 备注可选，最长 200 个字符；日志和错误响应不得输出备注正文或 SQL 绑定值。
- 手工交易支持修改和软删除。修改或删除使用版本号做乐观并发检查，冲突时返回稳定错误，不静默覆盖较新的结果。
- 创建、修改和删除请求都携带客户端生成的 UUID 幂等键；同一用户、同一键、同一请求重放返回已有结果，同键不同请求必须拒绝。

### 3.3 列表、搜索与统计

- 交易页默认展示当前自然月，可切换前后月份；点击中间月份可使用原生日期选择器选择具体日期，选中后列表和收支摘要只统计当天，并可恢复整月视图。
- 列表按本地发生时间倒序排列，同一时间用交易 ID 稳定排序，并使用游标分页；单页默认 50 条。
- 每项展示交易类型、金额、分类、账户方向、时间和可选备注摘要；转账明确展示“转出账户 → 转入账户”。
- 用户可按账户、分类或备注关键词搜索当前月份；搜索不跨用户，不返回已删除交易。
- 月度摘要返回收入、支出和“收入－支出”；转账与余额调整不进入三项收支统计。
- 首页展示人民币账户净值、本月收入、本月支出、最近交易和快捷入口。没有账户时，首要动作是创建账户。
- 底部导航使用“首页 / 明细 / 中央记账 / 账本 / 我的”。中央记账不是页面入口；账户和分类放在“账本”，可信微信身份状态、隐私与应用信息放在“我的”。
- 未登录可以浏览公开页面结构，但不读取或伪造个人账本；导入、记一笔、账户管理、分类管理和个人数据入口按需发起登录。
- 登录只要求用户主动点击确认，头像昵称可按微信现行能力选择也可留空，完成后留在当前页面并继续触发操作；未选择时“我的”使用中性头像和“微信用户”，不以品牌 Logo 替代。
- “我的”允许用户退出登录；退出只清除本机登录许可、展示资料和临时编辑状态，不删除云端账本，后续受保护操作重新触发登录。
- 账本页以两个同规格可点击行分别进入“账户管理”和“分类管理”；分类不在账本页直接铺开。
- 首页已承担基础财务总览，不设独立统计底栏；首页的“统计分析”展示截至当月的近半年收入/支出趋势，点击“全部”进入二级页查看月度收支、每日支出趋势和收支分类排行。
- 所有统计只读取正式、未删除交易；客户端不得自行拼接另一套权威统计。

### 3.4 安全与隔离

- 所有动作从 `cloud.getWXContext().OPENID` 映射内部 `uid`，客户端传入 `uid`、OpenID 或同义身份字段时拒绝请求。
- 账户、交易、分类查询和写入都同时限定服务端 `uid`；仅凭账户 ID、交易 ID 或分类 ID 不得读写数据。
- 所有业务表、索引、外键、幂等唯一键和查询路径包含用户边界；数据库约束负责并发最终裁决。
- 云函数响应不返回内部 `uid`、身份摘要、数据库绑定值或运行时上下文。

### 3.5 视觉主题

- “我的”提供“主题”入口，未登录也可以进入；主题选择保存在当前设备，不上传、不绑定微信身份，也不改变任何云端账本数据。
- 首批提供“暖橘手账、青绿清单、红印编辑、石墨秩序、墨绿留白、票据凭证”六套原创视觉方案，默认使用暖橘手账。
- 六套主题共享相同的信息架构、组件语义与交互位置，只调整画布、表面、文字、强调色、留白、圆角和阴影等视觉令牌。
- 收入、支出、危险操作、错误和禁用状态必须继续同时依赖文字或图形表达；主题不得仅靠互换颜色改变财务语义。
- 主题切换应立即作用于当前页面、微信导航栏和自定义底栏；再次打开小程序时恢复上次有效选择，无效或过期主题 ID 回退到默认主题。
- 视觉方案只提炼公开参考项目的高层设计原则，不复制其 AGPL 代码、HTML、CSS、组件或页面结构。

## 4. EARS 验收标准

### R1 账户创建与余额

- 当已登录用户提交合法账户时，系统应创建仅属于该用户的活动账户并返回公开账户字段。
- 当未登录用户浏览公开页面时，系统不应调用 `bootstrap` 或创建个人数据；当用户从受保护动作确认登录时，应先建立可信身份账本，再继续原动作且不强制跳到“我的”。
- 当账户带有非零初始余额时，系统应在同一事务中创建账户与余额调整交易；任一步失败时两者都不保留。
- 当两个并发请求使用同一用户和同一幂等键时，系统应只创建一个账户和一笔余额调整。
- 当两个用户创建同名账户时，系统应允许各自在自己的账本中创建，且互相不可见。
- 当用户停用账户时，系统应保留其历史交易并拒绝用该账户创建新交易。
- 当用户校正账户余额时，系统应以校正时点新增且只新增一笔余额调整，使校正后的聚合余额等于用户确认值，月度收支保持不变。

### R2 支出、收入与转账

- 当用户创建合法支出时，系统应原子写入交易，并使付款账户聚合余额减少相同金额。
- 当用户创建合法收入时，系统应原子写入交易，并使收款账户聚合余额增加相同金额。
- 当用户创建合法转账时，系统应在一笔正式交易中保存两端账户，使转出与转入余额分别减少和增加相同金额，且月度收支不变化。
- 当转账两端账户相同、任一账户停用、账户币种不同或账户不属于当前用户时，系统应拒绝整笔请求且不留下部分数据。
- 当支出/收入分类类型不匹配、分类已停用或分类不属于当前用户时，系统应拒绝请求。

### R3 纠错与幂等

- 当用户重放相同幂等键和相同请求时，系统应返回第一次成功结果且不重复改变余额。
- 当用户重放相同幂等键但请求内容不同，系统应返回幂等冲突且不改变数据。
- 当用户使用当前版本修改自己的手工交易时，系统应更新交易并让账户余额、列表和统计反映新值。
- 当用户使用过期版本修改或删除交易时，系统应返回并发冲突且不覆盖现有数据。
- 当用户软删除自己的手工交易时，系统应从余额、列表和统计中排除该交易，同时保留必要审计事实。

### R4 月份、搜索与统计

- 当用户打开交易页时，系统应按客户端当前自然月返回第一页交易和月度摘要。
- 当用户切换月份时，系统应按交易本地日期筛选，不受云函数服务器时区影响。
- 当用户选择具体日期时，系统应只返回该本地日期的交易和收支摘要；日期与月份不一致时应拒绝请求。
- 当用户继续翻页时，系统应使用稳定游标返回不重复、不遗漏的后续交易。
- 当用户按账户、分类或关键词搜索时，系统应只在当前用户、当前月份和未删除交易中匹配。
- 当月份中包含支出、收入、转账和余额调整时，系统应只用支出和收入计算月度收支。

### R5 隔离与失败关闭

- 当客户端提交用户身份字段时，系统应在访问数据库前拒绝请求。
- 当用户猜测另一用户的账户、交易或分类 ID 时，系统应返回不可用结果且不泄露对象是否存在。
- 当数据库事务任一步失败时，系统应回滚本次账户或交易变更。
- 当服务端记录错误时，日志应只包含动作、公开错误码和必要数据库错误码，不包含账户名称、备注、金额或绑定值。

### R6 主题一致性

- 当用户选择任一主题时，当前页、后续打开页面和自定义底栏应使用同一组语义令牌，账目值、筛选条件和业务请求不得变化。
- 当用户重启小程序时，应从本机恢复最后一次有效主题；当存储值不存在或非法时，应安全回退到“暖橘手账”。
- 当用户未登录、登录、退出登录或切换账本页面时，主题选择应保持不变。
- 当主题使用不同强调色时，收入、支出、危险操作和错误状态仍应可由文案、符号或位置辨认，不只依赖颜色。

## 5. 非目标

- 本阶段不实现账单文件上传、解析、自动去重或来源账户映射；这些属于 MINI-1905/1906。
- 本阶段不实现退款关系、贷款/分期、预算、标签、地图、票据图片、汇率或跨币种转账。
- 本阶段不实现数据导出、账户注销、年度报告或正式发布；这些属于后续任务。
- 本阶段不复制旧 Web 版的数据表或页面，只参考已验证的会计语义并按小程序重新设计。

## 6. 待确认的推荐口径

1. 首版只开放人民币，避免在没有汇率权威的情况下错误合并多币种净值。
2. 初始余额和余额校正记录为独立 `balance_adjustment`，不伪装成收入或支出。
3. MINI-1904 同时包含手工交易修改/软删除和账户停用，形成可纠错的完整闭环。
4. 首版使用六类账户；不要求用户填写完整卡号，只保存自定义名称。
