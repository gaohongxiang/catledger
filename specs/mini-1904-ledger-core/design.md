# MINI-1904 设计：账户、手动记账与交易列表

> 状态：已确认，进入任务拆分与实现。

## 1. 设计目标与约束

本设计把 MINI-1904 的已确认需求落成一套可实现、可验证的账户与正式交易底座。它必须同时满足以下约束：

- 客户端为微信原生小程序，通过 `wx.cloud.callFunction` 调用现有 `catledger-api` 事件云函数。
- 服务端只信任 `cloud.getWXContext().OPENID`，映射为内部 `uid` 后再访问数据。
- 正式业务数据继续使用现有 CloudBase MySQL，不增加云托管、常驻服务或新的业务云函数。
- 金额以人民币分为单位，跨进程和接口边界一律使用十进制字符串，不经过 JavaScript 浮点数。
- 账户余额、净值和月度统计都从未删除的正式交易推导，不增加可漂移的余额缓存。
- 所有迁移 forward-only、可重入并受校验和保护；所有写操作可安全重试。
- 本阶段不部署数据库或云函数；实现和本地验证通过后，另行经过部署门禁确认。

## 2. 总体架构

```text
微信原生小程序
  ├─ 首页 / 明细 / 中央记账 / 账本 / 我的
  └─ wx.cloud.callFunction({ name: "catledger-api" })
                 │
                 ▼
catledger-api 事件云函数
  ├─ handler：动作路由、身份字段拒绝、公开错误封装
  ├─ identity：OPENID 摘要 → 内部 uid
  ├─ ledger-service：校验、权限、幂等、事务与并发规则
  ├─ repositories：账户、交易、分类、统计 SQL
  └─ utilities：金额、时间、游标、规范化与请求摘要
                 │
                 ▼
CloudBase MySQL
  ├─ 既有：users / identities / categories / schema_migrations
  └─ 新增：accounts / transactions / mutation_receipts
```

现有 `bootstrap` 动作保持兼容。其他动作先从可信微信身份解析既有内部用户；未完成初始化时返回稳定的初始化错误，不在普通业务动作中隐式创建另一套用户数据。

## 3. 数据模型

### 3.1 迁移策略

新增 `migrations/0002_accounts_and_transactions.sql`，不修改已经应用的 `0001`。迁移包含三张新表，并为既有分类表补充 `(uid, category_id)` 唯一键，使交易到分类的外键也包含用户边界。

MySQL DDL 不能依赖事务整体回滚，因此设计采用以下办法保证可重入：

1. 新表使用 `CREATE TABLE IF NOT EXISTS`。
2. 既有表新增索引前查询 `information_schema.statistics`，通过同一连接上的预备语句只补缺失索引。
3. 迁移运行器取得数据库级命名锁，避免两个发布进程同时执行 DDL。
4. 全部语句成功后才写入迁移版本与校验和；重复执行已完成迁移只校验内容，不重复变更结构。
5. 集成测试同时覆盖 MySQL 5.7 兼容目标与当前云端 MySQL 8 行为，重点验证生成列索引和预备语句。

### 3.2 `catledger_accounts`

| 字段 | 类型/规则 | 用途 |
| --- | --- | --- |
| `uid` | `CHAR(36)` | 服务端用户边界 |
| `account_id` | `CHAR(36)` | 公开账户标识 |
| `type` | ASCII 枚举字符串 | 六类账户之一 |
| `nature` | `asset` / `liability` | 默认展示方向，由账户类型确定 |
| `name` | `VARCHAR(32)` | 规范化后的展示名称 |
| `normalized_name` | `VARCHAR(64)` | NFKC、去首尾空白、合并连续空白并统一大小写后的唯一性键 |
| `active_name_key` | 生成列 | 活动时等于 `normalized_name`，停用后为 `NULL` |
| `currency` | `CHAR(3)` | 本阶段固定 `CNY` |
| `version` | 无符号 `BIGINT` | 乐观并发版本，从 1 开始 |
| `archived_at` | 可空时间 | 停用标记 |
| `created_at` / `updated_at` | 毫秒时间 | 审计时间 |

主键为 `(uid, account_id)`；活动名称唯一键为 `(uid, active_name_key)`。这样停用旧账户后可以重新使用同名账户，同时并发创建同名活动账户仍由数据库唯一约束最终裁决。账户只软停用，不物理删除。

`nature` 由服务端根据 `type` 写入，客户端不能自行指定。`cash`、`bank`、`wallet`、`other_asset` 为资产；`credit`、`other_liability` 为负债。

### 3.3 `catledger_transactions`

| 字段 | 类型/规则 | 用途 |
| --- | --- | --- |
| `uid` | `CHAR(36)` | 服务端用户边界 |
| `transaction_id` | `CHAR(36)` | 公开交易标识 |
| `type` | `expense` / `income` / `transfer` / `balance_adjustment` | 正式交易类型 |
| `source_account_id` | 可空 `CHAR(36)` | 余额减少的一端 |
| `destination_account_id` | 可空 `CHAR(36)` | 余额增加的一端 |
| `category_id` | 可空 `CHAR(36)` | 支出或收入分类 |
| `amount_minor` | 无符号 `BIGINT` | 正数金额，单位为分 |
| `occurred_local_date` | `DATE` | 自然月筛选键 |
| `occurred_local_at` | `DATETIME(3)` | 用户当地发生时间 |
| `timezone_offset_minutes` | `SMALLINT` | 当时的 UTC 偏移，范围 -840～840 |
| `occurred_at_utc` | `DATETIME(3)` | 统一排序和审计时间 |
| `note` | 可空 `VARCHAR(200)` | 手工备注 |
| `origin` | `manual` / `system` / `import` | 来源；本阶段只生成前两类 |
| `version` | 无符号 `BIGINT` | 乐观并发版本 |
| `deleted_at` | 可空时间 | 手工交易软删除标记 |
| `created_at` / `updated_at` | 毫秒时间 | 审计时间 |

主键为 `(uid, transaction_id)`。账户和分类外键都采用包含 `uid` 的组合外键，删除策略为 `RESTRICT`。所有月份、账户、分类和游标索引都以 `uid` 开头。

交易形态固定如下：

| 类型 | 转出账户 | 转入账户 | 分类 | 收支统计 |
| --- | --- | --- | --- | --- |
| `expense` | 必填 | 空 | 支出分类必填 | 计入支出 |
| `income` | 空 | 必填 | 收入分类必填 | 计入收入 |
| `transfer` | 必填 | 必填且不同 | 空 | 不计入 |
| `balance_adjustment` | 二选一 | 二选一 | 空 | 不计入 |

账户的账面余额统一按“流入减流出”聚合：

```text
bookBalance = Σ(destination amount) - Σ(source amount)
```

因此一条转账天然同时影响两端而不会形成半笔交易。资产初始余额写成流入；负债的初始待还金额写成流出，故其账面余额为负数并直接参与净值。界面显示负债时把负数翻译为正的“待还金额”；信用卡溢缴导致账面余额为正时，界面显示为资产方向余额。

`balance_adjustment` 永远由账户创建或余额校正服务生成，不能从普通交易创建、编辑或删除接口操作。校正余额时，服务端锁定账户、聚合当时余额并只插入一笔差额调整。

### 3.4 `catledger_mutation_receipts`

| 字段 | 类型/规则 | 用途 |
| --- | --- | --- |
| `uid` | `CHAR(36)` | 幂等用户边界 |
| `idempotency_key_digest` | `CHAR(64)` | 客户端 UUID 的 SHA-256 摘要 |
| `action` | ASCII 字符串 | 写动作名称 |
| `request_digest` | `CHAR(64)` | 规范化请求的 SHA-256 摘要 |
| `result_json` | `JSON` | 首次成功的公开响应数据 |
| `created_at` | 毫秒时间 | 首次执行时间 |

主键为 `(uid, idempotency_key_digest)`。原始幂等键和请求正文不写日志。写操作先在事务内预占幂等键，再执行业务变更并写入公开结果；任一步失败，收据和业务数据一并回滚。

并发重复请求会在唯一键处等待首次事务结束：同请求摘要返回首次结果，不同摘要返回 `IDEMPOTENCY_CONFLICT`。若首次事务回滚，后续请求可重新预占并正常执行。

## 4. 业务与并发规则

### 4.1 金额与时间

- 接口金额字段使用只含数字的十进制字符串，如 `"12345"` 表示 123.45 元。
- 服务端解析为 `BigInt` 并做范围检查；数据库读取也保留字符串，响应前不转成 `Number`。
- 手工金额必须大于 0；余额目标可以为 0。负债界面的“待还金额”由账户类型转换为负的账面目标。
- 客户端提交 `occurredLocalAt`（无时区本地时间）和 `timezoneOffsetMinutes`；服务端校验日期存在性，并推导 UTC 时间与本地日期。
- 月份请求使用 `YYYY-MM`，可选具体日期使用 `YYYY-MM-DD` 且必须属于请求月份；SQL 统一采用本地日期的左闭右开区间，不依赖云函数服务器时区。

### 4.2 事务加锁顺序

所有改变账户余额语义的操作遵循同一顺序：

1. 开始事务并预占幂等键。
2. 修改或删除时先按 `(uid, transaction_id)` 锁定原交易。
3. 收集旧交易和新请求涉及的全部账户 ID，排序后按固定顺序 `FOR UPDATE`。
4. 在同一 `uid` 下校验账户状态、币种和分类类型。
5. 插入或更新一条正式交易；版本条件不匹配则返回 `CONFLICT`。
6. 生成公开结果并完成幂等收据，然后提交。

账户创建依靠活动名称唯一键裁决并发；余额校正因为锁住账户，且其他交易写入也必须先锁相关账户，所以“读取当前余额—计算差额—插入调整”之间不会被另一笔写入穿插。死锁和锁等待超时只做有上限、带抖动的整事务重试。

### 4.3 修改、停用与删除

- 账户改名、停用均要求当前 `version`，成功后版本加一。
- 停用账户不能参与新交易、交易改动或余额校正，但仍可查询并参与历史余额和净值。
- 仅 `origin = manual` 且类型为支出、收入或转账的交易可由用户修改或软删除。
- 修改交易可以更换类型、账户、分类、金额、时间和备注；服务端同时校验旧、新账户集合并一次提交。
- 删除仅写 `deleted_at` 并增加版本；余额、列表和统计查询统一排除软删除交易。
- 跨用户对象与不存在对象统一返回 `NOT_FOUND`，不泄露对象是否真实存在。

## 5. 云函数接口契约

调用结构保持 `{ action, data }`，成功响应为 `{ ok: true, data }`，失败响应为 `{ ok: false, error: { code, message } }`。服务端在任何数据库访问前递归拒绝 `uid`、`openid`、`openId`、`OPENID` 等客户端身份键。

### 5.1 动作列表

| 动作 | 作用 | 是否幂等写 |
| --- | --- | --- |
| `bootstrap` | 初始化内部用户与默认分类 | 既有幂等逻辑 |
| `dashboard.get` | 净值、本月收支、近半年收支趋势、账户摘要、最近交易 | 否 |
| `accounts.list` | 活动/停用账户及聚合余额 | 否 |
| `accounts.create` | 创建账户和可选初始余额调整 | 是 |
| `accounts.update` | 改名 | 是 |
| `accounts.archive` | 停用账户 | 是 |
| `accounts.correctBalance` | 插入一笔余额调整达到目标余额 | 是 |
| `transactions.list` | 月份、可选具体日期、账户/分类/搜索筛选、摘要和游标分页 | 否 |
| `statistics.get` | 月度收支、每日支出趋势与收支分类排行 | 否 |
| `transactions.create` | 创建支出、收入或转账 | 是 |
| `transactions.update` | 按版本修改手工交易 | 是 |
| `transactions.delete` | 按版本软删除手工交易 | 是 |

所有“是”的动作都要求 `requestId` UUID。账户修改/停用和交易修改/删除还要求 `version`。客户端不得直接调用 `balance_adjustment` 类型。

### 5.2 公开字段约定

- 标识字段使用 `accountId`、`transactionId`、`categoryId`，不返回内部 `uid`。
- 金额响应使用 `bookBalanceMinor`、`displayBalanceMinor`、`amountMinor` 等十进制字符串。
- 账户响应同时返回 `balanceDirection: asset | liability`，避免客户端自行猜测负债溢缴状态。
- 交易列表游标为服务端生成的不透明字符串，包含筛选摘要、排序时间和交易 ID；客户端不得构造或修改。
- `transactions.list` 默认 50 条，最大 100 条；游标必须与当前月份、可选日期和其他筛选条件匹配。
- 搜索词先去首尾空白，最长 40 个字符，只在当前月份的备注中做字面匹配；不把搜索词写日志。
- `dashboard.get` 和 `transactions.list` 的汇总均由服务端 SQL 计算，转账和余额调整显式排除。

稳定公开错误码包括：

- `AUTH_REQUIRED`
- `INITIALIZATION_REQUIRED`
- `INVALID_REQUEST`
- `VALIDATION_ERROR`
- `NOT_FOUND`
- `CONFLICT`
- `IDEMPOTENCY_CONFLICT`
- `ACCOUNT_INACTIVE`
- `UNSUPPORTED_CURRENCY`
- `INTERNAL_ERROR`

日志只保留动作、公开错误码、请求追踪 ID 和必要的数据库错误码；不得输出账户名称、备注、金额、SQL、绑定值、事件或运行时上下文。

## 6. 小程序信息架构与界面设计

### 6.1 体验目的

用户打开猫账后，应在几秒内回答三个问题：现在净值是多少、本月收支怎样、最近记了什么；完成一笔日常记账不超过“选类型—填金额—补账户/分类—保存”的短路径。空账本首要动作是创建账户，而不是展示无意义统计。

### 6.2 视觉方向

采用温暖、现代、轻巧的生活账本风格，关键词为“干净留白、灵活紧凑、适度圆角、编辑式层次、克制的猫咪陪伴”。卡片、按钮、底栏和标题避免过高、过粗或过度圆润造成笨重感。默认仍使用 Logo 同源暖橘；用户可在“我的 → 主题”选择青绿、红印、石墨、墨绿或票据方向。参考项目只用于提炼配色约束、留白、细线和纸张隐喻，不复制其 AGPL 代码、组件、素材或页面结构。

颜色冻结如下：

| 角色 | 色值 | 用途 |
| --- | --- | --- |
| 暖米白 | `#F8F3EA` | 页面底色 |
| Logo 暖橘黄 | `#ECA33D` → `#DF7F35` | 首页主卡、金额面板 |
| 猫咪橘 | `#CF7439` | 重点数字、细线和局部强调 |
| 墨棕 | `#29231E` | 主标题和正文 |
| 鼠尾草绿 | `#64705D` | 次级状态、收入与平衡提示 |
| 柔和灰褐 | `#746A60` | 说明文字 |

主视觉使用接近 Logo 的暖橘渐变，不使用亮柠檬黄。支出不使用刺眼纯红，而以墨棕配猫咪橘区分；收入使用克制的鼠尾草绿。页面使用干净的暖米白渐变底，不使用横线、格纸、噪点或做旧纸张纹理。

六套主题共用一套语义令牌合同：`page/canvas/surface/ink/text/accent/secondary/line/border/hero/income/expense/danger/shadow/radius/navigation`。页面只消费令牌，不读取主题 ID；主题注册表负责名称、说明、预览和令牌完整性，运行时服务负责本机存储、导航栏同步和页面绑定。默认暖橘以外的方案如下：

| 主题 | 视觉重点 | 主色锚点 |
| --- | --- | --- |
| 青绿清单 | 清醒、高频、列表感 | 青绿与麦黄 |
| 红印编辑 | 纸白、批注、克制强调 | 砖红与暖灰 |
| 石墨秩序 | 数字优先、细线、低阴影 | 石墨灰与少量暖橘 |
| 墨绿留白 | 舒展、安静、低饱和 | 墨绿与米白 |
| 票据凭证 | 凭证编号、纸张、硬朗边界 | 凭证绿与票据黄 |

主题只改变视觉令牌，绝不改变财务计算、接口、筛选、文本含义或身份。收入和支出分别消费稳定的 `income`、`expense` 语义色，并继续由箭头、标题和金额符号共同表达。

### 6.3 字体与数字

- 品牌标题和正文统一使用现代无衬线中文字体栈，以 `PingFang SC` / `Source Han Sans SC` 为主；标题靠字号、字重和留白建立层级，不使用复古宋体感。
- 金额与月份方向：`IBM Plex Sans Condensed SemiBold`，使用等宽数字特性。
- 实现前验证字体许可证、小程序包体与目标基础库加载能力；未验证前以平台安全字体栈和 Logo 图形承载品牌识别，不把未加载字体写成已生效能力。
- 金额为首要信息，层级明显高于单位；长金额允许缩小一级，不截断、不横向滚动。

### 6.4 页面与布局

首版使用四个一级页面、一个中央动作和三个任务页面：

1. **首页 `pages/index`**：只承担财务展示。顶部为暖橘渐变净值主卡，本月收入/支出摘要轻微压住卡片下沿；有账户时最多显示 3 个活动账户的类型图标、名称和余额紧凑行，已停用账户不进入首页，底部显示最近交易。导入、手记和创建账户不在首页重复设置操作卡；无账户时隐藏账户摘要，无交易时仅显示轻量文字说明。首次加载失败时仍保留概览结构，用“—”表示未知而不是伪造零值，同步状态压缩为一行，不向用户暴露平台原始错误。
2. **明细 `pages/transactions`**：删除重复大标题和顶部“记一笔”，月份切换置顶，点击中间日期打开原生日期选择器；选中具体日期后由服务端按本地日期返回当天明细和摘要。收入/支出/结余压缩为横向三项，账户、分类和按需展开的备注搜索收在同一紧凑工具条；交易每行首行展示分类与金额，次行合并时间、类型和账户方向。
3. **账本 `pages/ledger`**：展示账户与分类数量摘要，以两个同规格可点击行分别进入“账户管理”和“分类管理”。账户和分类都是账本结构，不放进个人设置，也不各自占用一级导航。
4. **我的 `pages/profile`**：承载当前微信身份连接状态、用户在登录面板中自愿选择的头像昵称、账本概况、数据隐私和应用信息；不展示 OpenID、内部 uid。未登录时可在本页打开统一登录面板，登录后仍停留本页；资料未选择时使用中性头像和“微信用户”。
5. **记一笔 `pages/transaction-editor`**：顶部用文本分段切换支出、收入、转账；金额输入占据视觉中心；账户、分类、时间和备注按使用频率排列。创建与编辑共用页面，保存按钮固定在安全区上方。手动记账是账单导入的补充方式，不占据全局主入口。
6. **账户 `pages/accounts`**：由“账本”进入，按资产、负债分组展示名称和余额；创建、改名、停用、校正余额使用原生页面内抽屉/弹层，不再新增页面。
7. **分类 `pages/categories`**：由“账本”进入，在独立页面按支出和收入切换展示当前可用分类；MINI-1904 只读取现有分类，不伪造尚未实现的增删改操作。
8. **主题 `pages/theme`**：由“我的”进入，不要求登录。使用六张原创微型账本预览展示每套方案的画布、主色、次色、数字和图表气质；点击后立即写入本机存储并同步当前页面、导航栏和自定义底栏。

底部使用自定义图标 `tabBar`：`首页 / 明细 / 中央记账 / 账本 / 我的` 五个位置围绕中央中轴排列；暖橘色大号加号向上悬浮且下方不显示文字。点击后打开记账方式面板，主位是“导入账单”，次位是“手动记一笔”。导航使用随包保存并保留许可证的 Lucide 线性图标和小号中文标签，不使用 emoji；“账本”和“我的”都必须承载真实信息与操作，不为视觉对称增加空页面。

未登录页面保留原有页面结构但不请求个人账本数据。导入、手动记账、账户管理、分类管理与个人数据入口通过自定义 tabBar 复用同一暖色底部登录面板；面板使用微信现行 `chooseAvatar` 与 `nickname` 能力提供可选资料，两项留空也能登录。用户点击登录后调用 `bootstrap`，由触发入口持有的回调继续原动作，不做全局跳转；头像昵称只作当前设备展示，服务端身份只信任 `cloud.getWXContext().OPENID`。

首页已是净值、收入、支出、结余与最近账目的轻量总览，首发不增加独立“统计”底栏。年度、趋势和分类深度分析在口径成熟后作为首页二级页面扩展。

首页在月度摘要下方以轻量双柱图展示近半年收入/支出趋势，恢复迁移前产品的核心趋势语义，点击“全部”进入 `pages/statistics`。该页只读服务端汇总的正式交易，显示月度收入/支出/结余、每日支出柱形趋势、支出分类与收入分类排行；不从客户端分页结果拼接统计，不伪造零数据。

布局和交互约束：

- 使用 8rpx 基线网格；页面横向安全边距 32rpx，卡片内边距 28～36rpx。
- 主要触控目标不小于 88rpx；不能只用颜色表达收入、支出、停用或错误状态。
- 空状态分别覆盖“未创建账户”“本月无交易”“筛选无结果”，每个状态只给一个主动作。
- 加载期间保留骨架结构；保存按钮防重复点击，但最终正确性依赖服务端幂等。
- 稳定错误使用就近说明；并发冲突提示重新载入最新数据，不静默覆盖。
- 删除和停用为二次确认操作；文案明确说明历史记录仍保留。

## 9. 部署、风险与回滚

### 9.1 部署顺序

1. 本地单元与 MySQL 兼容测试通过。
2. 只读确认目标云环境、MySQL 状态、函数配置和当前迁移版本。
3. 经用户确认部署门禁后，先应用 forward-only 迁移并验证表、索引和权限。
4. 更新 `catledger-api` 代码，保留现有环境变量和 VPC 配置，验证函数详情与最小调用。
5. 微信开发者工具编译、开发版预览和真机走查。

### 9.2 主要风险与控制

- **金额精度**：全链路字符串 + `BigInt`，禁止浮点运算。
- **迁移半完成**：可重入 DDL、迁移命名锁、校验和与半完成恢复测试。
- **余额并发**：统一账户行锁顺序、单条转账、无余额缓存。
- **重复写入**：事务内幂等收据和数据库唯一键。
- **跨用户访问**：可信身份映射、组合键/外键、所有 SQL 首条件为 `uid`。
- **VPC 配置丢失**：部署更新时合并而非覆盖函数现有环境变量和 VPC；部署后只读复核。
- **样式在设备上不一致**：字体能力先验证，品牌识别优先依赖现有 Logo、颜色和排版结构。

### 9.3 回滚边界

数据库迁移不做向后删除。若新函数代码出现问题，回退到上一版函数代码；新增表保留但旧代码不会使用。若仅小程序页面出现问题，回退小程序代码即可。任何已写入的正式交易不通过 `DROP` 或批量删除回滚，而通过受控修复迁移或业务纠错流程处理。

## 10. 设计决策摘要

1. 沿用一个 `catledger-api` 事件云函数，账户、记账和统计集中在同一可信事务边界。
2. 转账存为一条双端交易；余额按流入减流出聚合，不维护余额缓存。
3. 负债在内部以负账面余额参与净值，界面显示为正的待还金额。
4. 所有写动作使用用户边界内的幂等收据；修改/删除再叠加版本号并发控制。
5. 自然月由本地日期字段确定，金额由分单位十进制字符串确定。
6. 界面采用干净暖米白、Logo 同源暖橘渐变和现代无衬线层级，不使用格纸、横线、做旧纹理或用户否定的黄色主卡，也不复制第三方素材。
