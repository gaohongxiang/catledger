# MINI-1906A1 现有账本完整性收口需求

> 状态：未开始
>
> 依赖：MINI-1906V 与 MINI-1905/1906 完成并形成可回归基线
>
> 目标：在继续以 `Transaction` 作为余额和统计唯一权威的前提下，修复当前导入后维护的四类完整性缺口，为后续不可变分录迁移建立稳定基线。

## 1. 问题范围

当前已确认的风险边界是：

1. posting 会物化 FinanceUpdate 下全部未物化账户草稿，旧决定留下的不可达草稿可能成为孤儿正式账户；
2. `economicEvents.correct` 可以原地更新导入交易，但没有执行与首次 posting 等价的现金负余额保护；
3. `financeUpdates.undo` 主要软删除本批创建交易，没有完整处理本批创建账户、提升映射和分类别名等副作用；
4. 修正逻辑只允许恰好一笔本批创建交易，多交易 EconomicEvent 缺少完整集合级维护规则。

本阶段只修复这些现有边界，不引入 JournalEntry / Posting。

## 2. 用户故事

1. 作为用户，我希望把“新建账户”改成已有账户或不计入后，不会在最终提交时出现空账户。
2. 作为用户，我希望修正已入账记录时仍遵守现金不可透支规则，并在执行前看到准确影响。
3. 作为用户，我希望撤销一次导入后，金额、账户、映射、分类规则和原始证据仍保持一致且可解释。
4. 作为用户，我希望聚合还款等多交易事件只能整体维护，不会出现只修改其中一笔的部分成功。
5. 作为维护者，我希望上述操作在重试、并发和超时后仍可通过同一幂等键得到唯一结果。

## 3. 功能需求与验收标准

### A1-R1. 保持现有权威与产品语义

- 用户仍只看到收入、支出、转账、退款、余额校正和整批导入；
- `Transaction`、`Account` 和分类继续构成正式账本；
- 本阶段不得新增或切换到 JournalEntry / Posting；
- 既有交易 ID、来源追溯和主要公共动作保持兼容，必要的响应扩展必须向后兼容并同步 `shared/`。

### A1-R2. 账户草稿可达性

- posting 只能物化仍被最终服务端事件端点、有效账户映射草稿或有效聚合分配引用的账户草稿；
- 用户修改账户决定、排除事件或放弃批次后，不再可达的草稿必须进入明确的 `superseded` 等价状态；
- 不依赖客户端清理来判断可达性；
- 同请求重放和并发 posting 时，同一可达草稿最多物化一个正式账户；
- 不可达草稿永久保留必要审计，但不得进入 `catledger_accounts`。

### A1-R3. 修正影响与现金安全

- `economicEvents.correctionImpact` 必须返回旧影响、新影响、按账户汇总的差额、完整关联交易集合、冲突原因和规则版本；
- `economicEvents.correct` 必须重新锁定 Update、事件、完整交易集合、受影响账户、退款依赖和幂等动作；
- 修正前后差额必须执行与手工交易和首次 posting 相同的现金规则：不得把非负现金变负，也不得加深历史负数；
- 影响预览与最终执行使用同一规范化规则、摘要和版本；预览后发生变化必须返回冲突；
- 同一请求重放不得重复修改。

### A1-R4. 撤销副作用

- 撤销必须原子撤回本批创建交易的余额影响；
- 本批新建且从未被其他正式交易、活动映射或后续批次使用的账户应停用，不物理删除；
- 已被其他正式事实使用的账户保留启用；
- 本批提升的来源账户映射和分类别名，只有在没有独立使用证据时才标记为由该批次撤回；不得覆盖后续用户决定；
- 原始文件元数据、原始行、Evidence、EconomicEvent、FinanceAction 和关系保留审计状态；
- 已被批次外交易修改、删除、退款引用或重新映射时，撤销必须拒绝静默覆盖并返回可理解冲突；
- 相同撤销请求重放返回首次结果。

### A1-R5. 多交易事件整体维护

- 维护单位是 EconomicEvent 的完整有效 EventTransaction 集合；
- 聚合还款重新分配时，全部交易在同一事务内重建，分配账户唯一、金额为正、与付款账户不同且合计严格守恒；
- 其他未冻结重建规则的多交易事件不提供单笔修正，只允许整批撤销后重新整理；
- 客户端不得显示会造成局部维护的入口；
- 完整集合、事件版本或任一交易版本变化都必须返回冲突。

### A1-R6. 隔离、幂等和审计

- 所有新增字段、查询、唯一约束和动作摘要包含可信 `uid`；
- 锁顺序稳定，事务失败时交易、账户状态、映射状态、别名状态、事件关系和回执整体回滚；
- 相同幂等键同请求返回首次结果，相同键不同摘要拒绝；
- 日志只记录动作、规则版本、对象摘要、计数、差额和冲突类型，不记录原始账单或完整标识。

### A1-R7. 用户侧闭环

- 已入账记录提供影响预览、确认、冲突和完成态；
- 多交易事件明确说明为何不能单笔编辑，并提供聚合重建或整批撤销路径；
- 完成后账户、明细、统计和导入记录在同一刷新周期内一致；
- 暂不支持的冲突不得伪装成功。

## 4. 非目标

本阶段不实现：

- JournalEntry、Posting、复式分录或读取切换；
- 历史全量分录回填和新旧统计比对；
- 多币种、贷款产品、未来计划、对账或期间结账；
- 数据导出、账户注销和审核发布；
- 对所有多交易事件设计通用可编辑 DSL。

## 5. 完成门禁

只有同时满足以下条件，MINI-1906A1 才能标记完成：

1. 四个已知缺口都有先失败后通过的回归测试；
2. 不可达草稿不会物化，历史草稿兼容规则已验证；
3. 修正造成或加深现金负数时整体回滚；
4. 撤销后的账户、映射、分类别名、关系和交易状态符合冻结策略；
5. 聚合还款完整集合重建通过，其他多交易事件无法局部修改；
6. MySQL 事务回滚、并发、幂等、跨用户隔离和日志隐私测试通过；
7. 真实微信身份完成修正、撤销和统计刷新回归；
8. 公共契约、业务规则、架构、现行说明和实施规划同步；
9. 未新增 JournalEntry / Posting，Transaction 口径回归零变化。
