# MINI-1906V 统一导入真实身份验收设计

> 本设计只定义验收方法，不改变当前产品、数据库或公共接口。

## 1. 验收对象

```text
真实微信身份
  → imports.prepareMany
  → 私有云存储直传
  → imports.parseFile
  → financeUpdates.prepare
  → ReviewIssue 处理
  → financeUpdates.post
  → Account / Transaction
  → 首页、明细与统计刷新
```

验收对象同时包含失败、重试、放弃、重复文件和返回工作台恢复路径。

## 2. 基线记录

验收开始时建立一份不含敏感值的基线表：

| 项目 | 记录内容 |
| --- | --- |
| 仓库 | 完整 commit SHA |
| 数据库 | `catledger_schema_migrations` 中最新编号和 checksum 状态 |
| 云函数 | 函数名、代码版本、Node.js 运行时、状态、内存、超时 |
| 网络 | VPC 是否绑定、导入函数是否具备读取私有对象所需出站能力 |
| 配置 | 只记录环境变量键是否存在，不记录值 |
| 触发器 | 事件函数且无 HTTP 入口 |
| 小程序 | AppID、体验版版本和编译时间 |
| 测试数据 | 来源类型、文件数量、脱敏编号和预期语义，不记录正文 |

任何一项无法核对或与实施规划不一致，都先停止验收并记录漂移。

## 3. 测试数据组合

至少准备以下脱敏数据集：

1. 支付宝 App CSV；
2. 支付宝 Web CSV；
3. 微信支付 CSV；
4. 微信支付 XLSX；
5. 支付宝与微信描述同一现实事件的强关系样本；
6. 同额、同日、同文本但确为两笔独立交易的样本；
7. 普通退款、弱候选退款和零候选退款；
8. 本人转账双端样本；
9. 花呗与具体信用购消费及聚合还款样本；
10. 至少一个无效文件、一个瞬时失败和一个最终 posting 冲突样本。

真实文件只在用户主动选择后用于运行，不复制进仓库。需要长期回归的场景转写为合成夹具。

## 4. 执行顺序

### 阶段 A：身份与文件

- 退出状态进入导入，确认按需登录；
- 登录后连续调用 `bootstrap`，确认幂等；
- 单文件上传、解析和原始证据下钻；
- 不同身份尝试访问同一 ID，确认公开结果不泄露对象存在性。

### 阶段 B：多文件与恢复

- 同时选择混合来源；
- 制造一个文件失败，确认其他文件保留；
- 制造上传中断和返回工作台，确认路径与 `updateId` 恢复；
- 明确重新上传同一未入账文件，确认复用安全解析结果但进入新的动作域；
- 重新上传已入账来源，确认不创建重复交易。

### 阶段 C：ReviewIssue

按账户归属、转账端点、退款、聚合还款、分类和排除原因逐类完成。每次保存后重新读取服务端完整视图，客户端不得自行扩大候选或推断 ready。

### 阶段 D：posting

- 先执行完整成功路径；
- 记录入账前后账户、交易和统计的脱敏计数与金额摘要；
- 再分别制造版本冲突、现金负数、重复身份或数据库事务失败；
- 核对失败前后的正式账户、映射、交易和报表摘要完全一致。

### 阶段 E：补分类与最终一致性

- 从统计页进入未分类记录；
- 按服务端冻结分组补分类；
- 核对退款继续冲减原分类且不重复改变余额；
- 核对首页、明细、账户和完整统计使用相同正式数据。

## 5. 证据格式

每个场景只记录：

- 场景编号；
- 基线 commit、迁移头、函数版本和体验版；
- 输入来源类型与脱敏样本编号；
- 预期结果；
- 实际公开结果、对象计数与金额摘要；
- 通过、失败或阻塞；
- 平台 trace ID 或内部脱敏动作摘要；
- 缺陷任务链接。

禁止记录原文件内容、完整交易号、完整卡号、OpenID、内部 uid、凭据和 SQL 参数。

## 6. 缺陷路由

- 纯环境漂移：先恢复或重新登记基线；
- 明确代码缺陷：建立边界单一的修复任务和失败测试；
- 业务规则歧义：先更新用户需求或业务规则，再冻结实现；
- 数据污染：停止当前批次，保留审计，不直接改数据库聚合结果；
- 平台不可用：标记阻塞，记录平台状态和未验证风险。

验收会话不顺手修改代码，也不把未运行项目写成通过。

## 7. 结束状态

通过后：

1. MINI-1905/1906 与 MINI-1906V 同时标记已完成；
2. 记录新的仓库、迁移、函数和体验版回归基线；
3. 清理临时测试对象和本机敏感文件；
4. 下一任务切换到 MINI-1906A1；
5. 不自动提交审核或正式发布。
