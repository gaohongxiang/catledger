# MINI-1906V 统一导入真实身份验收需求

> 状态：未开始
>
> 依赖：MINI-1905/1906 候选已经合入 `main`，开发云已应用 `0001`～`0008`
>
> 目标：在不新增业务能力的前提下，用真实微信身份和脱敏账单验证多账单统一导入的完整开发链路，并形成可重复、可追溯的验收基线。

## 1. 范围与原则

MINI-1906V 是验收阶段，不是实现阶段。验收对象是当前已经合入的上传、解析、FinanceUpdate、EconomicEvent、ReviewIssue、账户草稿、退款/转账/聚合还款、分类补全和整批原子入账能力。

- 不修改业务代码、数据库 schema、公共 API 或规则版本；
- 不把真实账单、完整账户标识、OpenID、数据库凭据或云密钥写入仓库、普通日志或验收文档；
- 只使用用户主动选择的真实文件或脱敏/合成夹具；
- 不提交微信审核，不正式发布；
- 发现缺陷时先形成脱敏可复现证据，再由主负责人另行拆分修复任务。

## 2. 用户故事

1. 作为用户，我希望在真实微信身份下选择一份或多份账单，单个文件失败不会让其他文件丢失。
2. 作为用户，我希望系统只询问真正不确定的账户、退款、还款或分类问题，并且我的选择能在最终入账前安全修改。
3. 作为用户，我希望同一现实交易的多份证据不会重复计账，而两笔内容相同的真实交易不会被错误合并。
4. 作为用户，我希望最终确认要么整批成功，要么完全不改变账户、映射、余额和统计。
5. 作为维护者，我希望能够从脱敏验收记录确认代码、迁移、函数、体验版和测试数据范围，后续可以复现同一闭环。

## 3. 验收需求

### V1. 基线冻结

- 记录仓库提交、数据库迁移头、两支云函数实际版本与状态、运行时、VPC、环境变量键、触发器和体验版版本；
- 验收开始前发现任一环境漂移时停止并记录，不在未知版本上继续；
- 当前预期基线为主线集成 `52147e19`、迁移 `0001`～`0008`、体验版 `0.19.30`，实际平台结果优先。

### V2. 身份与隔离

- 所有个人业务必须在用户主动点击登录后，以云函数可信微信上下文取得身份；
- 请求中的 `uid`、`openid` 或同义身份字段必须被拒绝；
- 另一个微信身份不得读取、恢复、修改或提交当前用户的导入文件、FinanceUpdate、账户或交易；
- 原始对象路径必须由服务端签发并按用户隔离，解析只能接受已登记的精确对象。

### V3. 文件与恢复

- 支付宝 App/Web CSV、微信支付 CSV/XLSX 分别至少完成一次解析；
- 一次混合选择多份文件时，每个文件独立上传、解析、失败、重试或移除；
- 网络中断、上传超时、解析瞬时错误和返回工作台必须沿用原路径或原 `updateId` 安全恢复，不生成重复业务请求；
- 同一未入账文件重新开始时可以复用不可变解析结果并保留审计；已入账来源不得再次创建正式交易。

### V4. 整理语义

至少验证以下业务：

- 选择已有账户；
- 明确创建新账户；
- 仅本次不计入；
- 对稳定支付工具选择以后默认不计入，并在下一次导入时仍显示可编辑提示；
- 一条本人转账分别确认 `from` 与 `to`，不得把一个选择写到两端；
- 自动关联退款、人工候选退款和零候选待关联退款；
- 花呗与具体信用购保持独立账户，聚合还款只能向冻结候选分配且金额严格守恒；
- 收入、支出和费用在入账前具备有效分类；入账后的未分类补全按同性质安全分组；
- 关闭、失败、已入账、账户排除和手工排除使用结构化原因，不由客户端文案猜测。

### V5. 去重与关联

- 同来源稳定身份重复上传或并发提交时最多形成一份正式事实；
- 同一现实事件在多个来源出现时保留全部证据，只生成正确数量的正式交易；
- 金额、日期、文本和账户线索相同但没有稳定身份或强关系的两笔真实交易必须保持独立或进入人工确认；
- 退款、转账和还款不得降级为普通收入或支出以绕过关系问题。

### V6. 原子入账与一致性

- 所有阻塞 ReviewIssue 清零后才能执行 `financeUpdates.post`；
- posting 在一个事务中物化账户、提升映射、创建或复用交易、写关系和更新状态；
- 人为制造账户冲突、现金负数、版本冲突或数据库失败时，账户、映射、交易、余额、统计和动作状态必须整体回滚；
- 成功后账户余额、明细、月度收支、近半年趋势、每日统计、分类排行和导入记录在同一刷新周期内一致；
- 重放相同幂等请求返回首次结果，相同键不同请求返回冲突且不改变数据。

### V7. 隐私与清理

- 普通日志只记录 action、平台追踪 ID、稳定错误类别、阶段和耗时；
- 日志、截图和验收记录不出现原始账单字段、完整账户标识、OpenID、内部 uid、SQL 绑定值或凭据；
- 成功、放弃或重复内容裁决后的原始对象按现行策略清理；清理失败只进入可重试状态，不伪造账本失败；
- 仓库只保存合成或充分脱敏的测试夹具。

## 4. 非目标

本阶段不实现：

- 新账单格式或银行 PDF；
- 不可变 JournalEntry / Posting；
- 新的修正、撤销或聚合维护规则；
- 数据导出、账户注销、贷款、分期、情景测算或 AI；
- 微信审核或正式发布。

## 5. 完成门禁

只有同时满足以下条件，MINI-1906V 才能标记完成：

1. 基线信息完整且平台无未解释漂移；
2. 单文件、混合多文件、重复、恢复和失败隔离全部通过；
3. 账户、转账、退款、聚合还款、分类和排除语义全部通过；
4. 整批成功与故障回滚后，正式账本和统计结果一致；
5. 多用户隔离、幂等和日志隐私通过；
6. 原始对象生命周期得到核对；
7. 验收记录仅含脱敏摘要，发现的问题均已关闭、拆成后续任务或明确标记阻塞；
8. 实施规划、现行说明和版本基线同步。

MINI-1906V 完成时，MINI-1905/1906 才能一起从“待验收”改为“已完成”。
